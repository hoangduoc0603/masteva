### Các tầng truy cập database trong Java

```text
 OrderQueryService, ReportController                     code của bạn
        |                                    |
 OrderRepository (Spring Data JPA)           |            interface, Spring sinh phần cài đặt
        |                                    |
 EntityManager (JPA) <- Hibernate            JdbcClient    Hibernate sinh SQL từ entity;
   persistence context, dirty checking       (Spring JDBC) JdbcClient chạy SQL bạn viết
        |                                    |
        +--------------- JDBC ---------------+            java.sql: Connection, PreparedStatement, ResultSet
                          |
                 HikariCP (DataSource)                    pool giữ sẵn kết nối
                          |
                 pgJDBC driver --- TCP ---> PostgreSQL :20120 / shopapp
```

Mọi tầng phía trên cuối cùng đều gọi **JDBC** (Java Database Connectivity), API chuẩn trong gói `java.sql`. Bài J8.3 đã dùng JDBC trực tiếp qua `DriverManager`. Ở đây bạn chọn tầng phù hợp với từng việc:

| Cách | Bạn viết | Hợp với | Cái giá |
|---|---|---|---|
| JDBC thuần | SQL, map `ResultSet` bằng tay, đóng tài nguyên | Thư viện, công cụ nhỏ | Nhiều code lặp, dễ quên đóng kết nối |
| `JdbcClient` (Spring) | SQL; Spring map sang record và đóng tài nguyên | Báo cáo, truy vấn phức tạp, cập nhật hàng loạt | Tự viết mọi câu SQL |
| JPA + Spring Data | Entity và interface repository | Nghiệp vụ CRUD trên đồ thị đối tượng | Phải hiểu SQL nào được sinh ra |

### JDBC và transaction thủ công

Mặc định một `Connection` JDBC ở chế độ **auto-commit**: mỗi câu lệnh tự commit. Muốn hai câu lệnh cùng thành công hoặc cùng huỷ, bạn tắt auto-commit và tự commit hay rollback:

```java
try (Connection c = dataSource.getConnection()) {
    c.setAutoCommit(false);
    try (PreparedStatement take = c.prepareStatement(
                 "UPDATE products SET stock = stock - ? WHERE id = ? AND stock >= ?");
         PreparedStatement line = c.prepareStatement(
                 "INSERT INTO order_items (order_id, product_id, quantity, unit_price) "
                         + "SELECT ?, id, ?, price FROM products WHERE id = ?")) {
        take.setInt(1, quantity);
        take.setLong(2, productId);
        take.setInt(3, quantity);
        if (take.executeUpdate() == 0) {
            throw new IllegalStateException("not enough stock");
        }
        line.setLong(1, orderId);
        line.setInt(2, quantity);
        line.setLong(3, productId);
        line.executeUpdate();
        c.commit();
    } catch (SQLException | RuntimeException e) {
        c.rollback();
        throw e;
    }
}
```

- Dấu `?` của `PreparedStatement` gửi giá trị tách khỏi câu SQL, nên chuỗi `'; DROP TABLE orders; --` chỉ là một giá trị, không thành lệnh: đây là cách chặn **SQL injection**. Không bao giờ ghép giá trị người dùng vào chuỗi SQL.
- `try (...)` đóng `PreparedStatement` rồi `Connection`. Với pool, `close()` không cắt kết nối mà **trả nó về pool**; quên đóng là pool cạn dần.
- `@Transactional` của Spring làm đúng những việc trên cho bạn: lấy kết nối, tắt auto-commit, commit khi method kết thúc bình thường, rollback khi có `RuntimeException`.

### Connection pool

Mở một kết nối PostgreSQL gồm bắt tay TCP, xác thực, và PostgreSQL tạo hẳn một tiến trình mới cho kết nối đó: tốn vài mili giây tới hàng chục mili giây, lâu hơn nhiều so với một truy vấn đơn giản. **Connection pool** mở sẵn một số kết nối và cho mượn. Spring Boot dùng **HikariCP** mặc định, với `maximumPoolSize = 10` và `minimumIdle` bằng chính số đó, nên ứng dụng giữ 10 kết nối ngay khi khởi động. Bài SB3.3 chỉnh kích thước và timeout của pool.

### JPA, Hibernate và persistence context

**Jakarta Persistence (JPA)** là đặc tả ánh xạ class Java sang bảng; **Hibernate** là bản cài đặt Spring Boot dùng. Một **entity** là class có `@Entity` và `@Id`. Spring Boot cấu hình Hibernate đổi tên kiểu camelCase sang snake_case, nên field `fullName` khớp cột `full_name` mà không cần `@Column`.

Mỗi transaction có một **persistence context**: một bản đồ "id → đối tượng entity" mà Hibernate quản lý. Entity đi qua các trạng thái:

```text
 new Product()  --persist()-->  MANAGED  --hết transaction-->  DETACHED
  (transient)                   |  findById() trả về đối tượng managed
                                |  đổi field -> lúc commit, Hibernate so với
                                |  ảnh chụp ban đầu và tự sinh UPDATE (dirty checking)
                                |  đọc cùng id hai lần -> cùng một đối tượng, một câu SQL
```

- **Dirty checking:** bạn không gọi `save()` để cập nhật. Đổi field của entity managed, Hibernate tự sinh `UPDATE` khi flush trước commit. Bài SB3.3 dựa vào điều này.
- **Detached:** sau khi transaction đóng, entity vẫn còn trong bộ nhớ nhưng Hibernate không quản lý nữa. Đổi field không ghi xuống database; truy cập quan hệ chưa tải thì lỗi.

### Lazy loading và N+1

Quan hệ có hai cách tải (fetch): **EAGER** tải ngay cùng entity, **LAZY** chỉ tải khi code chạm tới. Với quan hệ lazy, Hibernate đặt vào field một **proxy** hoặc một collection rỗng chưa khởi tạo; lần đầu bạn gọi `getEmail()` hay duyệt `getItems()`, nó chạy một câu `SELECT`.

| Annotation | Mặc định của JPA | Nên đặt |
|---|---|---|
| `@ManyToOne`, `@OneToOne` | EAGER | `fetch = FetchType.LAZY`, rồi tải có chủ đích khi cần |
| `@OneToMany`, `@ManyToMany` | LAZY | Giữ LAZY |

Lazy có hai cái bẫy:

- **`LazyInitializationException`:** chạm vào quan hệ lazy khi persistence context đã đóng. Spring Boot mặc định bật **open-in-view**, giữ persistence context mở tới hết request HTTP để che lỗi này, đổi lại kết nối database bị giữ trong lúc render JSON và truy vấn lazy chạy rải rác ngoài tầng service. Bài này tắt nó bằng `spring.jpa.open-in-view=false`, nên mọi việc đọc dữ liệu phải nằm trong một method `@Transactional`.
- **N+1:** một câu lấy N đơn hàng, rồi mỗi đơn thêm một câu lấy khách, một câu lấy dòng hàng. Code Java trông vô hại; log SQL thì không.

| Cách sửa | Viết thế nào | Ghi chú |
|---|---|---|
| `join fetch` trong JPQL | `@Query("select o from PurchaseOrder o join fetch o.customer ...")` | `join fetch` là inner join: đơn không có dòng hàng sẽ biến mất |
| `@EntityGraph` | `@EntityGraph(attributePaths = {"customer", "items", "items.product"})` | Dùng left join; giữ được derived query |
| Batch fetching | `spring.jpa.properties.hibernate.default_batch_fetch_size=50` | Gom N câu thành vài câu `where id in (...)`; sửa toàn cục |
| DTO projection | `select new ...View(o.id, c.email) from ...` | Chỉ lấy cột cần; không có entity để sửa |

Hibernate gộp các dòng trùng của đơn hàng do join với collection, nên không cần `distinct`. Đừng fetch hai collection kiểu `List` trong cùng một truy vấn: Hibernate báo `MultipleBagFetchException`, vì tích Descartes của hai collection làm số dòng nhân lên.

### Spring Data JPA

Bạn khai báo interface, Spring sinh phần cài đặt lúc khởi động:

| Cách | Ví dụ | Dùng khi |
|---|---|---|
| Derived query | `findByStatusOrderByCreatedAtDesc(String status)` | Điều kiện đơn giản; tên method chính là truy vấn |
| `@Query` | JPQL hoặc `nativeQuery = true` | Join, điều kiện phức tạp, `join fetch` |
| `Pageable` | `Page<PurchaseOrder> findByStatus(String s, Pageable p)` | Phân trang; Spring chạy thêm một câu `count(*)` |
| Projection | `List<OrderSummary> findByStatus(...)` với `OrderSummary` là interface hoặc record | Chỉ cần vài cột |

Phần giữa `find` và `By` là tự do, nên `findWithDetailsByStatus...` vẫn là derived query theo `status`; "WithDetails" chỉ để bạn phân biệt nó với method không có entity graph.

### Migration với Flyway

Schema là code: nó phải có version, được review, và chạy giống nhau trên máy dev, CI và production. Lab chọn **Flyway**, ghi migration bằng SQL thuần:

- File `src/main/resources/db/migration/V<số>__<mô tả>.sql`, ví dụ `V1__schema.sql`. Hai dấu gạch dưới tách số version và mô tả.
- Khi ứng dụng khởi động, Flyway đọc bảng `flyway_schema_history`, chạy theo thứ tự các migration chưa chạy, và ghi lại version, thời gian, **checksum** của từng file.
- Migration đã chạy là **bất biến**. Sửa nó, checksum lệch và Flyway từ chối khởi động. Muốn đổi gì, viết migration mới.
- `spring.jpa.hibernate.ddl-auto=validate`: Hibernate chỉ kiểm tra entity khớp schema, không tự tạo hay sửa bảng. Flyway là nguồn sự thật của schema.

| | Flyway | Liquibase |
|---|---|---|
| Viết migration bằng | SQL (có thể Java) | Changelog XML, YAML, JSON hoặc SQL |
| Rollback | Viết migration mới để đảo ngược | Changeset có thể khai báo rollback |
| Hợp với | Team đọc SQL thoải mái, một loại database | Nhiều loại database, cần rollback có cấu trúc |

<Callout kind="production">

Một lập trình viên phát hiện giá trong `V2__seed.sql` sai, sửa thẳng file đó và merge. CI xanh vì database của CI tạo mới mỗi lần. Lúc deploy, mọi instance production chết ngay khi khởi động với `Migration checksum mismatch for migration version 2`, vì production đã chạy bản V2 cũ từ tháng trước. Bạn sẽ gặp đúng lỗi này ở bước 8; cách sửa đúng là trả file về như cũ và viết `V3`.

</Callout>

package vn.masteva.shop;

import jakarta.persistence.Entity;
import jakarta.persistence.FetchType;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import jakarta.persistence.ManyToOne;
import jakarta.persistence.OneToMany;
import jakarta.persistence.OrderBy;
import jakarta.persistence.Table;
import java.time.Instant;
import java.util.ArrayList;
import java.util.List;

@Entity
@Table(name = "orders")
public class PurchaseOrder {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    private Customer customer;

    private String status;
    private Instant createdAt;

    @OneToMany(mappedBy = "order")
    @OrderBy("id")
    private List<OrderItem> items = new ArrayList<>();

    protected PurchaseOrder() {
    }

    public Long getId() { return id; }
    public Customer getCustomer() { return customer; }
    public String getStatus() { return status; }
    public List<OrderItem> getItems() { return items; }

### Khi gặp lỗi

- `Connection to localhost:20120 refused`: container chưa chạy. `docker start masteva-j12-pg` rồi chạy lại.

- `grep -c` in `0`: bạn đã xoá log sau khi gọi API, hoặc ứng dụng thiếu `logging.file.name`. Thứ tự đúng là xoá log, gọi API, rồi đếm.

<DeepDive>

<Reveal title="Vì sao Spring Boot bật open-in-view mặc định, và vì sao nên tắt?">

Open-in-view (OSIV) giữ persistence context mở suốt request HTTP, nên code ở controller và lúc Jackson ghi JSON vẫn tải được quan hệ lazy. Nó giúp người mới không gặp `LazyInitializationException`, vì vậy Spring Boot bật nó và in cảnh báo `spring.jpa.open-in-view is enabled by default` lúc khởi động. Cái giá: kết nối database bị giữ suốt request kể cả lúc gọi dịch vụ khác, và truy vấn lazy chạy rải rác ở tầng web nên N+1 khó thấy. Tắt nó buộc tầng service quyết định rõ cần tải những gì.

</Reveal>

<Reveal title="Phân trang (Pageable) cùng với fetch một collection thì sao?">

`LIMIT 20` trên câu SQL join với `order_items` sẽ cắt theo **dòng** của kết quả join, không theo đơn hàng, nên đơn cuối có thể chỉ còn một nửa số dòng hàng. Hibernate 6 xử lý bằng cách tải hết rồi cắt trong bộ nhớ, kèm cảnh báo `HHH90003004`, rất tệ với bảng lớn. Hibernate 7.4 trong lab này đẩy `offset ... fetch first ... rows only` vào một subquery trên `orders` rồi mới join dòng hàng. Dù phiên bản nào, cách an toàn là hai bước: lấy một trang id đơn hàng, rồi tải chi tiết bằng `where o.id in (...)` với entity graph.

</Reveal>

<Reveal title="Khi nào chọn JdbcClient hoặc jOOQ thay vì JPA?">

JPA mạnh khi bạn tải một đồ thị đối tượng, sửa nó, và để dirty checking ghi lại. Báo cáo, cập nhật hàng loạt (`UPDATE ... WHERE`), window function, `ON CONFLICT`: viết SQL trực tiếp rõ ràng và nhanh hơn. `JdbcClient` đủ cho vài truy vấn như vậy. **jOOQ** (chủ đề tuỳ chọn của chặng) sinh code Java từ schema và cho viết SQL bằng DSL được kiểm tra lúc biên dịch: đổi tên cột là code không biên dịch được, thay vì lỗi lúc chạy. Một service có thể dùng cả JPA lẫn `JdbcClient` trên cùng `DataSource` và cùng transaction.

</Reveal>

<Reveal title="Đọc log SQL bằng mắt không ổn trên CI. Làm sao chặn N+1 tự động?">

Đếm số câu SQL trong integration test. Hibernate có `Statistics` (bật bằng `hibernate.generate_statistics=true`), cho số câu đã chạy qua `getPrepareStatementCount()`; một test gọi endpoint rồi assert số câu không vượt ngưỡng sẽ đỏ ngay khi ai đó thêm một quan hệ lazy vào DTO. Kết hợp với Testcontainers (bài J8.3) để chạy trên PostgreSQL thật. Trên production, theo dõi số truy vấn mỗi request qua tracing (SB8) thay vì bật log SQL ở mức debug.

</Reveal>

Nhờ AI viết entity và repository từ một schema có sẵn, hoặc chuyển một truy vấn SQL sang JPQL. AI hay để `@ManyToOne` ở EAGER mặc định, hay dùng `javax.persistence` thay vì `jakarta.persistence`, hay bật `ddl-auto=update` "cho tiện", và hay "sửa" `LazyInitializationException` bằng cách bật open-in-view hoặc đổi sang EAGER, hai cách làm N+1 nặng hơn. Kiểm tra bằng log SQL: đếm số câu trước và sau thay đổi, như bước 7 và 8.

</Callout>
