<Goal>

Thay chuỗi lệnh `javac`, `java -cp` thủ công bằng Maven: tạo project theo cấu trúc chuẩn, chạy test, đóng gói file `.jar` chạy được, và hiểu mỗi lệnh `mvn` kích hoạt những plugin nào. Học xong bài này, bạn giải thích được:

- Vì sao `mvn package` chạy cả test dù bạn chỉ muốn đóng gói.
- Vì sao `mvn surefire:test` báo `BUILD SUCCESS` mà không chạy test nào.
- Vì sao Maven báo `release version 25 not supported` trong khi `java -version` đang là 25.

</Goal>

<Knowledge>

### Build tool giải quyết việc gì

Ở J1 bạn tự gõ `javac -d out src/*.java` rồi `java -cp out Main`. Cách đó hết dùng được khi project có thư viện bên ngoài, có test, cần đóng gói và cần mọi người trong nhóm build giống nhau. **Build tool** (công cụ build) gom những việc đó vào một file mô tả project:

| Việc | Làm tay | Build tool |
|---|---|---|
| Lấy thư viện | Tải file `.jar`, tự ghép `-cp` | Khai báo toạ độ, tự tải từ Maven Central |
| Biên dịch | `javac` với đúng classpath | Một phase hoặc task |
| Chạy test | Tự gọi JUnit | Chạy tự động trước khi đóng gói |
| Đóng gói | `jar cfe ...` | Sinh `.jar` có manifest |

Hai build tool phổ biến của Java là **Maven** và **Gradle**. Các bài J7 dùng Maven: file cấu hình là XML khai báo, ít cách viết khác nhau, nên dễ đọc khi bạn mới vào một project lạ. Cuối phần này có bảng đối chiếu sang Gradle.

### POM và cấu trúc thư mục chuẩn

Maven theo nguyên tắc **convention over configuration** (quy ước thay cho cấu hình): đặt file đúng chỗ thì không phải khai báo gì thêm.

| Đường dẫn | Chứa |
|---|---|
| `pom.xml` | Mô tả project: toạ độ, dependency, plugin |
| `src/main/java` | Mã nguồn chính |
| `src/main/resources` | File cấu hình, template đi kèm ứng dụng |
| `src/test/java` | Test, không đóng vào `.jar` |
| `target/` | Mọi thứ Maven sinh ra; xoá đi lúc nào cũng được |

**POM (Project Object Model)** là file `pom.xml`. Mỗi project có **toạ độ** gồm `groupId` (thường là tên miền đảo ngược, ví dụ `vn.masteva`), `artifactId` (tên module) và `version`. Version kết thúc bằng `-SNAPSHOT` nghĩa là bản đang phát triển, có thể thay đổi; bỏ `-SNAPSHOT` khi phát hành. Thuộc tính `maven.compiler.release` truyền `--release` cho `javac`, đúng tuỳ chọn bạn gặp ở J1.

### Lifecycle, phase và goal

Maven chia build thành các **lifecycle** (vòng đời). Ba lifecycle có sẵn: `clean` xoá `target/`, `default` build project, `site` sinh trang tài liệu. Mỗi lifecycle là một chuỗi **phase** (giai đoạn) theo thứ tự cố định. Phase tự nó không làm gì; việc thật do **goal** của **plugin** làm, và mỗi goal được **gắn** (bind) vào một phase. Với project `jar`, Maven gắn sẵn như sau:

```text
mvn package
   |
   v
phase (theo thứ tự)          goal gắn sẵn
validate                     (chưa có)
process-resources       ->   resources:resources
compile                 ->   compiler:compile
process-test-resources  ->   resources:testResources
test-compile            ->   compiler:testCompile
test                    ->   surefire:test
package                 ->   jar:jar            <- dừng ở đây
verify, install, deploy      không chạy
```

Sơ đồ lược bớt các phase chưa có goal nào, như `initialize` hay `generate-sources`.

Hai quy tắc quan trọng nhất:

- Gọi một **phase** thì Maven chạy mọi phase đứng trước nó trong cùng lifecycle. `mvn package` luôn chạy `compile` và `test` trước.
- Gọi một **goal** trực tiếp theo dạng `plugin:goal` thì chỉ goal đó chạy, không kéo theo phase nào.

| Lệnh | Kết quả | Dùng khi |
|---|---|---|
| `mvn compile` | `target/classes` | Kiểm tra code biên dịch được |
| `mvn test` | Biên dịch và chạy unit test | Vòng lặp hằng ngày |
| `mvn package` | Thêm file `.jar` trong `target/` | Cần artifact để chạy |
| `mvn verify` | Thêm các kiểm tra sau đóng gói (integration test) | Lệnh chuẩn cho CI |
| `mvn install` | Chép artifact vào `~/.m2/repository` | Project khác trên máy cần dùng nó |
| `mvn clean package` | Xoá `target/` rồi build lại từ đầu | Nghi ngờ kết quả cũ còn sót |

<Check id="j7.1.lifecycle-phases">Kể được thứ tự các phase chính của lifecycle `default` và goal nào gắn vào `compile`, `test`, `package`.</Check>

### Plugin và cấu hình plugin

Mọi việc trong Maven đều do plugin làm, kể cả biên dịch. Plugin có toạ độ và version như thư viện. Log của Maven ghi rõ từng bước theo dạng `--- plugin:version:goal (execution id) @ module ---`, ví dụ `--- compiler:3.13.0:compile (default-compile) @ invoice ---`.

Bạn cấu hình plugin trong `<build><plugins>`. Ví dụ bảo `maven-jar-plugin` ghi class chứa `main` vào manifest, để chạy được bằng `java -jar`:

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-jar-plugin</artifactId>
  <version>3.5.0</version>
  <configuration>
    <archive>
      <manifest>
        <mainClass>vn.masteva.invoice.Main</mainClass>
      </manifest>
    </archive>
  </configuration>
</plugin>
```

- `<configuration>` đặt tham số cho goal của plugin. Tên tham số tra ở trang tài liệu của plugin đó.
- `<executions>` gắn thêm một goal vào một phase, ví dụ chép thư viện vào `target/lib` ở phase `package`. Bài J7.2 dùng cách này.
- Plugin gắn sẵn vào lifecycle mà không ghi version thì Maven lấy version mặc định của **chính bản Maven đang chạy**. Plugin không nằm trong bảng gắn sẵn mà thiếu version thì Maven lấy bản mới nhất trên kho, nên có thể đổi theo ngày build. Bài J7.3 cho thấy vì sao cả hai điều này làm hai máy build khác nhau.

<Callout kind="production">

Một nhóm thêm `-DskipTests` vào lệnh build trên CI cho nhanh, định "tạm thời". Vài tháng sau, một thay đổi làm sai công thức tính thuế vẫn được đóng gói và triển khai, dù test bắt được lỗi đó đã có sẵn trong repo. Phase `test` đứng trước `package` là có chủ đích: artifact chỉ nên tồn tại khi test đã qua. Nếu test chậm, tách test chậm sang phase `verify` (J8) thay vì bỏ qua tất cả.

</Callout>

### Gradle làm cùng việc thế nào

Gradle mô tả build bằng code Kotlin (`build.gradle.kts`) thay vì XML, và tổ chức build thành một **đồ thị task** thay vì chuỗi phase cố định. Project dưới đây tương đương project Maven của bài; nó đã được build thử bằng Gradle 9.8.0. Bạn không cần cài Gradle để học tiếp.

```kotlin
plugins {
    application
}

group = "vn.masteva"
version = "1.0.0-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:6.1.3")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

application {
    mainClass = "vn.masteva.invoice.Main"
}

tasks.test {
    useJUnitPlatform()
}
```

Lệnh `gradle build` trên project này chạy lần lượt các task `compileJava`, `processResources`, `classes`, `jar`, ..., `compileTestJava`, `test`, `check`, `build`. Lần chạy thứ hai, task nào có đầu vào không đổi được đánh dấu `UP-TO-DATE` và bỏ qua.

| Maven | Gradle |
|---|---|
| `pom.xml` | `build.gradle.kts` và `settings.gradle.kts` |
| Phase (`compile`, `test`, `package`) | Task (`compileJava`, `test`, `jar`, `build`) |
| `mvn package` | `gradle build` (có chạy test) hoặc `gradle assemble` (không chạy test) |
| `<scope>test</scope>` | `testImplementation(...)` |
| `maven.compiler.release` | toolchain (chọn JDK, `java { toolchain { ... } }`) hoặc `options.release` |
| `~/.m2/repository` | `~/.gradle/caches` |
| `mvnw` | `gradlew` |

<Check id="j7.1.gradle-map">Đọc được file `build.gradle.kts` ở trên và chỉ ra phần tương ứng trong `pom.xml` của bài.</Check>

### 2. Tạo project

Project là hoá đơn quen thuộc từ J1, giờ đặt trong package `vn.masteva.invoice` và có một unit test. Thư mục `~/masteva-j7` dùng cho cả ba bài của chặng J7.

```bash

cat > src/main/java/vn/masteva/invoice/Invoice.java <<'EOF'
package vn.masteva.invoice;

import java.util.ArrayList;
import java.util.List;

public class Invoice {
    private final List<Long> prices = new ArrayList<>();

    public void add(long price) {
        prices.add(price);
    }

    public long subtotal() {
        return prices.stream().mapToLong(Long::longValue).sum();
    }

    public long vat() {
        return subtotal() * 10 / 100;
    }

    public long total() {
        return subtotal() + vat();
    }
}
EOF
cat > src/main/java/vn/masteva/invoice/Main.java <<'EOF'
package vn.masteva.invoice;

public class Main {
    public static void main(String[] args) {
        Invoice invoice = new Invoice();
        invoice.add(120_000);
        invoice.add(180_000);
        System.out.println("total=" + invoice.total());
    }
}
EOF
cat > src/test/java/vn/masteva/invoice/InvoiceTest.java <<'EOF'
package vn.masteva.invoice;

import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;

class InvoiceTest {
    @Test
    void totalIncludesTenPercentVat() {
        Invoice invoice = new Invoice();
        invoice.add(120_000);
        invoice.add(180_000);
        assertEquals(330_000, invoice.total());
    }
}
EOF
find . -type f | sort
```

Đây là bảng gắn mặc định của Maven 3.9.9 cho packaging `jar`. Để ý `maven-jar-plugin:3.4.1`: bảng này không đọc `pom.xml` của bạn, còn log ở bước 4 cho thấy build thật dùng `jar:3.5.0` như bạn đã khai báo. Phase `Not defined` vẫn tồn tại, chỉ là chưa có goal nào gắn vào.

### 6. Gọi goal thay vì phase

<Terminal where="mac">

```bash
mvn clean surefire:test
```

</Terminal>

<Predict question="Lệnh này chạy bao nhiêu test?">

```text
[INFO] --- clean:3.2.0:clean (default-clean) @ invoice ---
[INFO] Deleting /Users/<bạn>/masteva-j7/invoice/target
[INFO] 
[INFO] --- surefire:3.2.5:test (default-cli) @ invoice ---
[INFO] No tests to run.
[INFO] ------------------------------------------------------------------------
[INFO] BUILD SUCCESS
```

Không test nào. `clean` là phase của lifecycle `clean`, nó xoá `target/`. `surefire:test` là goal gọi trực tiếp (execution id `default-cli`), nên không kéo theo `compile` hay `test-compile`. Surefire tìm test trong `target/test-classes`, thư mục vừa bị xoá, và vẫn báo thành công. Trên CI, một lệnh như vậy cho cảm giác an toàn giả. Muốn chạy test thì gọi phase: `mvn test`.

</Predict>

<Check id="j7.1.lab-phase-vs-goal">Giải thích được vì sao `mvn clean surefire:test` báo `No tests to run` còn `mvn clean test` thì chạy test.</Check>

### 7. Test hỏng thì không có jar

Giả sử ai đó đổi VAT thành 8% mà quên sửa test:

<Terminal where="mac">

```bash

mvn package
ls target
```

</Terminal>

<Expected>

```text
[ERROR] Tests run: 1, Failures: 1, Errors: 0, Skipped: 0, Time elapsed: 0.031 s <<< FAILURE! -- in vn.masteva.invoice.InvoiceTest
```

</Expected>

Phase `test` thất bại nên Maven dừng, `package` không chạy và `target/` không có file `.jar`. Chi tiết từng test nằm trong `target/surefire-reports`. Trả công thức về 10% và build lại:

<Terminal where="mac">


<Check id="j7.1.lab-test-failure">Đọc được log khi test hỏng: test nào, giá trị mong đợi và thực tế, và vì sao không có file `.jar`.</Check>

### Khi gặp lỗi

<Callout kind="pitfall">

- `Fatal error compiling: error: release version 25 not supported`: Maven đang chạy trên JDK cũ hơn 25. Xem dòng `Java version` của `mvn -v` và sửa `JAVA_HOME` như bước 1.
- `no main manifest attribute, in target/...jar`: thiếu `<mainClass>` trong cấu hình `maven-jar-plugin`, hoặc bạn sửa `pom.xml` mà chưa build lại.
- `Tests run: 0` dù đã viết test: class test phải nằm dưới `src/test/java` và tên kết thúc bằng `Test` (hoặc bắt đầu bằng `Test`, hoặc kết thúc bằng `Tests`, `TestCase`) thì Surefire mới tìm thấy.
- `package org.junit.jupiter.api does not exist` khi biên dịch `src/main/java`: code chính đang import JUnit, thứ chỉ có ở scope `test`. Chuyển code đó sang `src/test/java`.

</Callout>


<DeepDive>

<Reveal title="Có nên luôn chạy mvn clean install?">

Không. `install` chép artifact vào `~/.m2/repository`, chỉ cần khi một project khác trên máy bạn, nằm ngoài build hiện tại, phụ thuộc vào nó. `clean` buộc biên dịch lại mọi thứ, làm mất lợi ích của biên dịch tăng dần. Trên CI, `mvn verify` là đủ: nó chạy mọi phase kiểm tra nhưng không cài artifact của bạn vào kho local. Dùng `clean` khi nghi `target/` còn kết quả cũ, ví dụ sau khi xoá hay đổi tên class.

</Reveal>

<Reveal title="-DskipTests khác -Dmaven.test.skip=true thế nào?">

`-DskipTests` vẫn biên dịch test nhưng không chạy. `-Dmaven.test.skip=true` bỏ cả biên dịch test, nên lỗi biên dịch trong test cũng bị che, và module nào đóng gói test để module khác dùng sẽ hỏng. Đây là tham số của plugin (Surefire, compiler, resources), không phải tuỳ chọn của bản thân Maven. Nếu phải dùng, chỉ dùng trên máy mình khi đang thử nhanh, không đưa vào CI.

</Reveal>

<Reveal title="Gradle nhanh hơn Maven nhờ đâu?">

Gradle ghi lại đầu vào và đầu ra của từng task; task nào không đổi được bỏ qua (`UP-TO-DATE`), và kết quả có thể lấy từ build cache, kể cả cache dùng chung giữa các máy. Gradle còn giữ một tiến trình nền (daemon) để khỏi khởi động JVM mỗi lần. Đổi lại, file build là code nên mỗi project có thể viết một kiểu, khó đọc hơn khi vào project lạ. Maven cũng biên dịch tăng dần (bạn đã thấy `Nothing to compile`), nhưng không bỏ qua cả phase như Gradle; muốn có cache kết quả build thì phải tự thêm extension build cache.

</Reveal>

<Reveal title="Phase verify dùng để làm gì khi chưa có goal nào?">

`verify` là chỗ để gắn các kiểm tra chạy sau khi đã có artifact: integration test qua Failsafe (chạy ở phase `integration-test`, kiểm kết quả ở `verify`), kiểm tra độ phủ test, quét bảo mật. Vì những kiểm tra đó gắn vào `verify`, lệnh `mvn verify` trên CI tự chạy chúng mà không đổi lệnh. J8 tách unit test (Surefire, phase `test`) khỏi integration test (Failsafe).

</Reveal>

<Callout kind="ai">

Nhờ AI viết nhanh một `pom.xml` có sẵn plugin và cấu hình, hoặc giải thích một đoạn log Maven. AI hay dùng version plugin cũ (ví dụ `maven-compiler-plugin` 3.8 với `<source>` và `<target>` thay vì `<release>`), hay trộn cú pháp Gradle Groovy (`build.gradle`) với Kotlin DSL (`build.gradle.kts`), và hay khuyên `-DskipTests` để "sửa" build đỏ. Kiểm tra lại bằng log thật: dòng `--- plugin:version:goal` cho biết plugin nào chạy, `Compiling ... [debug release 25]` cho biết tuỳ chọn tới tay `javac`.

</Callout>

<Callout kind="link">

J1 dạy `javac`, `--release` và classpath, những thứ Maven làm thay bạn ở đây. J7.2 thêm thư viện, scope và tách project thành nhiều module. J7.3 cố định phiên bản Maven và plugin. J8 dùng phase `test` và `verify` cho unit test và integration test; SB11 đóng gói file `.jar` vào image container.

</Callout>
