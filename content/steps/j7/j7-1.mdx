<Goal>

Thay chuỗi lệnh `javac`, `java -cp` thủ công bằng một build tool: đặt project theo cấu trúc chuẩn, chạy test, đóng gói file `.jar`, và đọc được log để biết build đã chạy những bước nào, bằng cả Maven lẫn Gradle. Học xong bài này, bạn giải thích được:

- Vì sao `mvn package` chạy cả test dù bạn chỉ muốn đóng gói, và vì sao test hỏng thì Maven không tạo file `.jar`.
- Vì sao `mvn clean surefire:test` báo `BUILD SUCCESS` mà không chạy test nào.
- Vì sao Maven báo `release version 25 not supported` trong khi `java -version` đang là 25.
- Vì sao `./gradlew build` lần thứ hai gần như không làm gì, và vì sao Gradle vẫn tạo file `.jar` khi test hỏng.

</Goal>

<Knowledge>

Ví dụ của cả chặng J7 là hoá đơn từ J1: cộng giá các dòng hàng, thêm VAT 10%, in tổng tiền. Ở chặng này, hoá đơn nằm trong package `vn.masteva.invoice` và có một unit test.

### Build tool giải quyết việc gì

Ở J1 bạn tự gõ `javac -d out src/*.java` rồi `java -cp out Main`. Cách đó hết dùng được khi project cần thư viện bên ngoài, có test, cần đóng gói, và cả nhóm phải build ra cùng một kết quả. Mỗi người gõ một chuỗi lệnh hơi khác nhau, và không ai nhớ đã ghép `-cp` thế nào.

**Build tool** (công cụ build) là chương trình đọc một file mô tả project rồi làm các việc đó theo một quy trình cố định:

| Việc | Làm tay | Build tool |
|---|---|---|
| Lấy thư viện | Tải file `.jar`, tự ghép `-cp` | Khai báo toạ độ, tự tải từ Maven Central, kho thư viện công khai mặc định của Maven |
| Biên dịch | `javac` với đúng classpath | Một bước có sẵn |
| Chạy test | Tự gọi JUnit | Chạy tự động trước hoặc cùng lúc đóng gói |
| Đóng gói | `jar cfe ...` | Sinh file `.jar` có manifest |

Hai build tool phổ biến của Java là **Maven** và **Gradle**. Chúng giải cùng một bài toán theo hai cách: Maven mô tả project bằng XML và chạy theo một chuỗi bước cố định; Gradle mô tả project bằng code Kotlin và chạy theo một đồ thị task. Bài này học Maven trước, vì file XML của nó ít cách viết khác nhau nên dễ đọc khi bạn vào một project lạ, rồi xem Gradle làm cùng việc đó thế nào. Các chặng sau của Masteva dùng Maven.

### POM và cấu trúc thư mục chuẩn

Bạn mở một project Maven lạ và cần biết mã nguồn ở đâu, test ở đâu, kết quả build nằm ở đâu. Câu trả lời giống nhau ở mọi project Maven, vì Maven theo nguyên tắc **convention over configuration** (quy ước thay cho cấu hình): đặt file đúng chỗ thì không phải khai báo gì thêm.

```text
invoice/
├── pom.xml
└── src/
    ├── main/java/vn/masteva/invoice/
    │   ├── Invoice.java
    │   └── Main.java
    └── test/java/vn/masteva/invoice/
        └── InvoiceTest.java
```

| Đường dẫn | Chứa |
|---|---|
| `pom.xml` | Mô tả project: toạ độ, thư viện phụ thuộc (dependency), plugin (phần mở rộng làm việc thật của build, mục "Lifecycle, phase và goal" giải thích) |
| `src/main/java` | Mã nguồn chính |
| `src/main/resources` | File cấu hình, template đi kèm ứng dụng |
| `src/test/java` | Test, không đóng vào `.jar` |
| `target/` | Mọi thứ Maven sinh ra; xoá đi lúc nào cũng được |

`Invoice` là lớp hoá đơn. Ví dụ này là một file trong project, không chạy riêng được; phần sau của bài build và chạy nó bằng Maven:

```java norun
package vn.masteva.invoice;

import java.util.ArrayList;
import java.util.List;

public class Invoice {
    private final List<Long> prices = new ArrayList<>();

    public void add(long price) {
        prices.add(price);
    }

    public long subtotal() {
        return prices.stream().mapToLong(Long::longValue).sum();
    }

    public long vat() {
        return subtotal() * 10 / 100;
    }

    public long total() {
        return subtotal() + vat();
    }
}
```

`Main` tạo hoá đơn hai món 120.000 và 180.000 đồng rồi in tổng tiền:

```java norun
package vn.masteva.invoice;

public class Main {
    public static void main(String[] args) {
        Invoice invoice = new Invoice();
        invoice.add(120_000);
        invoice.add(180_000);
        System.out.println("total=" + invoice.total());
    }
}
```

Tổng là 300.000 cộng 30.000 tiền VAT, nên chương trình in `total=330000`. `InvoiceTest` kiểm đúng con số đó bằng JUnit; J8 dạy viết test, ở bài này bạn đọc được `assertEquals(mong đợi, thực tế)`:

```java norun
package vn.masteva.invoice;

import static org.junit.jupiter.api.Assertions.assertEquals;

import org.junit.jupiter.api.Test;

class InvoiceTest {
    @Test
    void totalIncludesTenPercentVat() {
        Invoice invoice = new Invoice();
        invoice.add(120_000);
        invoice.add(180_000);
        assertEquals(330_000, invoice.total());
    }
}
```

**POM (Project Object Model)** là file `pom.xml` mô tả project cho Maven. Phần đầu của nó:

```xml
<project xmlns="http://maven.apache.org/POM/4.0.0"
         xmlns:xsi="http://www.w3.org/2001/XMLSchema-instance"
         xsi:schemaLocation="http://maven.apache.org/POM/4.0.0 https://maven.apache.org/xsd/maven-4.0.0.xsd">
  <modelVersion>4.0.0</modelVersion>

  <groupId>vn.masteva</groupId>
  <artifactId>invoice</artifactId>
  <version>1.0.0-SNAPSHOT</version>
  <packaging>jar</packaging>

  <properties>
    <maven.compiler.release>25</maven.compiler.release>
    <project.build.sourceEncoding>UTF-8</project.build.sourceEncoding>
  </properties>

  <dependencies>
    <dependency>
      <groupId>org.junit.jupiter</groupId>
      <artifactId>junit-jupiter</artifactId>
      <version>6.1.3</version>
      <scope>test</scope>
    </dependency>
  </dependencies>

  <!-- <build> với cấu hình plugin: xem mục "Plugin và cấu hình plugin" -->
</project>
```

- **Toạ độ** của project gồm `groupId` (thường là tên miền đảo ngược, ví dụ `vn.masteva`), `artifactId` (tên của project; J7.2 tách một project thành nhiều module, mỗi module một `artifactId`) và `version`. Ba giá trị này định danh duy nhất một artifact trên mọi kho Maven.
- `version` kết thúc bằng `-SNAPSHOT` là bản đang phát triển, có thể đổi nội dung mà giữ nguyên số. Bỏ `-SNAPSHOT` khi phát hành.
- `packaging` là loại artifact cần tạo: `jar` (mặc định), `war`, hoặc `pom` cho project chỉ gom module (J7.2).
- `maven.compiler.release` truyền `--release 25` cho `javac`, đúng tuỳ chọn bạn gặp ở J1.
- `project.build.sourceEncoding` bảo các plugin đọc mã nguồn theo UTF-8, để chữ có dấu trong code không phụ thuộc máy build.
- JUnit có `<scope>test</scope>`: nó chỉ có mặt khi biên dịch và chạy test, không đi vào ứng dụng. J7.2 dạy kỹ scope.

### Maven chạy trên JDK nào

Bạn đã cài JDK 25, `java -version` in 25, vậy mà `mvn compile` dừng với lỗi sau:

```text
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-compiler-plugin:3.13.0:compile (default-compile) on project invoice: Fatal error compiling: error: release version 25 not supported -> [Help 1]
```

Maven tự nó là một chương trình Java, và nó biên dịch project bằng chính JDK nó đang chạy trên đó, không phải bằng lệnh `java` bạn gõ trong Terminal. Lỗi trên nghĩa là JDK của Maven cũ hơn 25, nên `javac` của JDK đó không biết `--release 25`. Dòng `Java version` trong output của `mvn -v` cho biết JDK đó.

### Lifecycle, phase và goal

Bạn gõ `mvn package` để lấy file `.jar`, và Maven chạy cả test trước khi đóng gói. Để hiểu vì sao, bạn cần bốn khái niệm:

| Khái niệm | Vai trò |
|---|---|
| **Lifecycle** (vòng đời) | Một quy trình build có tên. Maven có ba: `clean` xoá `target/`, `default` build project, `site` sinh trang tài liệu |
| **Phase** (giai đoạn) | Một bước của lifecycle, theo thứ tự cố định. Phase tự nó không làm gì |
| **Plugin** | Thư viện chứa code làm việc thật, có toạ độ và version như mọi thư viện |
| **Goal** | Một việc cụ thể của plugin, viết `plugin:goal`, ví dụ `compiler:compile`. Goal được **gắn** (bind) vào phase |

Với project `jar`, Maven gắn sẵn goal vào phase như sau. Điều cần nhớ: gọi một phase là chạy mọi phase đứng trước nó.

```text
mvn package
   |
   v
phase (theo thứ tự)          goal gắn sẵn
validate                     (chưa có)
process-resources       ->   resources:resources
compile                 ->   compiler:compile
process-test-resources  ->   resources:testResources
test-compile            ->   compiler:testCompile
test                    ->   surefire:test
package                 ->   jar:jar            ◄ dừng ở đây
verify, install, deploy      không chạy
```

Sơ đồ lược bớt các phase chưa có goal nào, như `initialize` hay `generate-sources`. Gọi phase `compile` trước, rồi xem các file `.class` Maven sinh ra:

Phase `Not defined` vẫn tồn tại, chỉ là chưa có goal nào gắn vào. Để ý `maven-jar-plugin:3.4.1`: đây là version gắn sẵn trong Maven 3.9.9, còn build thật ở trên chạy `jar:3.5.0` vì `pom.xml` của bài ghi version đó (mục "Plugin và cấu hình plugin"). Bảng dưới là các lệnh dùng hằng ngày:

| Lệnh | Kết quả | Dùng khi |
|---|---|---|
| `mvn compile` | `target/classes` | Kiểm tra code biên dịch được |
| `mvn test` | Biên dịch và chạy unit test | Vòng lặp hằng ngày khi đang code |
| `mvn package` | Thêm file `.jar` trong `target/` | Cần artifact để chạy |
| `mvn verify` | Thêm các kiểm tra sau đóng gói | Lệnh chuẩn cho CI |
| `mvn install` | Chép artifact vào `~/.m2/repository` | Một project khác trên máy, nằm ngoài build hiện tại, cần dùng nó |
| `mvn clean package` | Xoá `target/` rồi build lại từ đầu | Nghi `target/` còn kết quả cũ, ví dụ sau khi xoá hay đổi tên class |

Phase `verify` đang `Not defined`, nhưng nó là chỗ để gắn các kiểm tra chạy sau khi đã có artifact: integration test, đo độ phủ test, quét bảo mật. Vì những kiểm tra đó gắn vào `verify`, lệnh `mvn verify` trên CI tự chạy chúng mà không phải đổi lệnh; J8 tách integration test sang phase này. Thói quen gõ `mvn clean install` cho mọi việc thì tốn hơn cần thiết: `clean` buộc biên dịch lại mọi thứ, còn `install` ghi vào kho local, thứ chỉ có ích khi một project khác trên máy phụ thuộc vào artifact của bạn.

### Gọi goal thay vì phase

Bạn có thể gọi thẳng một goal theo dạng `plugin:goal`, không qua phase. Lệnh dưới xoá `target/` rồi gọi goal chạy test của Surefire, thay vì gọi phase `test`:

<Terminal where="mac">

```bash
mvn clean surefire:test
```

</Terminal>

<Predict question="Lệnh này chạy bao nhiêu test, và build thành công hay thất bại?">

```text
[INFO] --- clean:3.2.0:clean (default-clean) @ invoice ---
[INFO] Deleting /Users/<bạn>/masteva-j7/invoice/target
[INFO] 
[INFO] --- surefire:3.2.5:test (default-cli) @ invoice ---
[INFO] No tests to run.
[INFO] ------------------------------------------------------------------------
[INFO] BUILD SUCCESS
```

Không test nào, và build vẫn báo thành công.

</Predict>

Thử tự trả lời trước khi đọc tiếp: Surefire tìm test ở đâu, và lúc nó chạy thì chỗ đó có gì?

`clean` là một phase, của lifecycle `clean`; nó xoá `target/`. `surefire:test` là một goal gọi trực tiếp, nên chỉ goal đó chạy (execution id `default-cli` cho biết nó đến từ dòng lệnh), không kéo theo `compile` hay `test-compile`. Surefire tìm class test trong `target/test-classes`, thư mục vừa bị xoá, không thấy gì và kết luận "không có test để chạy". 

Đây là quy tắc thứ hai: **gọi một goal thì chỉ goal đó chạy**. Trên CI, một lệnh như vậy cho cảm giác an toàn giả. Muốn chạy test thì gọi phase `mvn test`; khi đó cùng goal `surefire:test` chạy với execution id `default-test`, sau khi các phase trước đã biên dịch test.

### Test hỏng thì không có jar

Giả sử ai đó đổi VAT thành 8% trong `Invoice.vat()` (`subtotal() * 8 / 100`) mà quên sửa test, rồi build:

### Plugin và cấu hình plugin

Mọi việc trong Maven đều do plugin làm, kể cả biên dịch. Log ghi từng bước theo dạng `--- plugin:version:goal (execution id) @ module ---`, ví dụ `--- compiler:3.13.0:compile (default-compile) @ invoice ---`. Đọc được dòng này là biết plugin nào, version nào, goal nào đang chạy cho module nào.

Bạn cấu hình plugin trong `<build><plugins>` của `pom.xml`. File `.jar` ở trên chạy được bằng `java -jar` nhờ đoạn sau, bảo `maven-jar-plugin` ghi tên class chứa `main` vào manifest:

```xml
<build>
  <plugins>
    <plugin>
      <groupId>org.apache.maven.plugins</groupId>
      <artifactId>maven-jar-plugin</artifactId>
      <version>3.5.0</version>
      <configuration>
        <archive>
          <manifest>
            <mainClass>vn.masteva.invoice.Main</mainClass>
          </manifest>
        </archive>
      </configuration>
    </plugin>
  </plugins>
</build>
```

Manifest là file `META-INF/MANIFEST.MF` bên trong `.jar`. Đọc nó bằng `unzip -p`:

<Terminal where="mac">

```bash
unzip -p target/invoice-1.0.0-SNAPSHOT.jar META-INF/MANIFEST.MF
```

</Terminal>

```text

Created-By: Maven JAR Plugin 3.5.0
Java-Version: 25
Build-Jdk-Spec: 25
Main-Class: vn.masteva.invoice.Main
```

Dòng `Main-Class` đến từ `<configuration>`. Bỏ cấu hình đó, build lại bằng `mvn package`, rồi chạy file `.jar`:

<Terminal where="mac">

Không có `Main-Class`, JVM không biết gọi `main` của class nào trong file `.jar`, nên dừng ngay.

Ba điều cần biết về cấu hình plugin:

- `<configuration>` đặt tham số cho goal của plugin. Tên tham số tra ở trang tài liệu của plugin đó, ví dụ trang `jar:jar` của Maven JAR Plugin.
- `<executions>` gắn thêm một goal vào một phase, ví dụ chép thư viện vào `target/lib` ở phase `package`. J7.2 dùng cách này.
- Plugin gắn sẵn vào lifecycle mà không ghi version thì Maven dùng version gắn sẵn của **chính bản Maven đang chạy**, như `jar:3.4.1` ở bảng `help:describe`. Ghi `<version>` thì version đó thắng, như `jar:3.5.0` ở log build. J7.3 cho thấy để Maven tự chọn version thì hai máy có thể build bằng hai bộ plugin khác nhau.

Ví dụ gần thực tế hơn là cấu hình `javac`. Ở J4.2, `javac -Xdoclint:all,-missing` bắt được Javadoc ghi `@throws` một exception mà method không hề ném. Đưa cờ đó vào `maven-compiler-plugin` thì lỗi Javadoc làm build thất bại ở mọi máy, không phụ thuộc ai nhớ gõ cờ. Đây là ví dụ riêng của mục này: project của chặng không giữ cấu hình `maven-compiler-plugin`, và J7.3 dựa vào điều đó.

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-compiler-plugin</artifactId>
  <version>3.13.0</version>
  <configuration>
    <compilerArgs>
      <arg>-Xdoclint:all,-missing</arg>
    </compilerArgs>
  </configuration>
</plugin>
```

Với cấu hình này, thêm vào `Invoice.add` một Javadoc ghi sai, khai báo `@throws java.io.IOException` trong khi method không ném nó:

### Gradle: build script và task

Cùng project hoá đơn, viết cho Gradle. Gradle mô tả build bằng code Kotlin, trong hai file thay cho một `pom.xml`. Ví dụ dùng Gradle 9.8.2.

`settings.gradle.kts` đặt tên build và liệt kê các project con (J7.2 dùng phần này):

```kotlin
rootProject.name = "invoice"
```

`build.gradle.kts` là **build script**: code Kotlin mô tả project. Thư mục `src/` giữ nguyên như bản Maven, vì Gradle dùng cùng quy ước `src/main/java`, `src/test/java`.

```kotlin
plugins {
    application
}

group = "vn.masteva"
version = "1.0.0-SNAPSHOT"

java {
    toolchain {
        languageVersion = JavaLanguageVersion.of(25)
    }
}

repositories {
    mavenCentral()
}

dependencies {
    testImplementation("org.junit.jupiter:junit-jupiter:6.1.3")
    testRuntimeOnly("org.junit.platform:junit-platform-launcher")
}

application {
    mainClass = "vn.masteva.invoice.Main"
}

tasks.test {
    useJUnitPlatform()
}
```

Bạn chưa cần biết Kotlin để đọc file này. Mỗi khối `tên { ... }` là một lời gọi hàm nhận một lambda, giống lambda của J6 viết theo cú pháp Kotlin; `x = y` gán một thuộc tính; chuỗi viết trong nháy kép như Java. Mỗi khối có một phần tương ứng trong `pom.xml`:

| Khối | Việc | Tương ứng Maven |
|---|---|---|
| `plugins { application }` | Plugin `application` gồm plugin `java` (biên dịch, test, jar) cộng task `run` và gói phân phối | `<packaging>jar</packaging>` và các plugin gắn sẵn |
| `group`, `version` | Toạ độ; tên project lấy từ `settings.gradle.kts` | `groupId`, `version`, `artifactId` |
| `java { toolchain }` | Chọn JDK 25 để biên dịch và chạy test, kể cả khi Gradle chạy trên JDK khác | `maven.compiler.release` (Maven vẫn dùng JDK của `JAVA_HOME`) |
| `repositories` | Tải thư viện từ đâu; Gradle không có kho mặc định | Maven Central là kho mặc định |
| `dependencies` | `testImplementation` là thư viện cho test | `<scope>test</scope>` |
| `tasks.test { useJUnitPlatform() }` | Chạy test bằng JUnit Platform | Surefire tự phát hiện |

`testRuntimeOnly("org.junit.platform:junit-platform-launcher")` là thư viện Gradle cần để khởi chạy JUnit; nó không ghi version vì `junit-jupiter` đã kéo theo bộ phiên bản của JUnit. Mỗi tên như `testImplementation` là một **dependency configuration**, cách Gradle gọi scope; J7.2 dạy kỹ.

Các lệnh dưới chạy Gradle qua `./gradlew`, script **wrapper** nằm trong project, tự tải đúng bản Gradle mà project đã chốt. Wrapper được sinh một lần cho mỗi project bằng một bản Gradle cài trên máy: `brew install gradle`, rồi `gradle wrapper --gradle-version 9.8.2` trong thư mục project. Từ đó, máy nào clone project cũng gọi `./gradlew` mà không phải cài Gradle; J7.3 giải thích kỹ. `--console=plain` bảo Gradle in từng task thay vì thanh tiến độ:

### Đồ thị task thay cho chuỗi phase

Gradle không có chuỗi phase cố định. Mỗi task khai báo nó phụ thuộc task nào, và các quan hệ đó tạo thành một **đồ thị task**. Khi bạn gọi `build`, Gradle tìm mọi task mà `build` cần, sắp chúng theo quan hệ phụ thuộc, rồi chạy. Sơ đồ dưới là phần chính của đồ thị trên; điểm cần chú ý là nhánh `jar` và nhánh `test` không phụ thuộc nhau:

```text
                        build
                      /       \
               assemble        check
                  |              |
                 jar            test
                  |           /      \
               classes    classes   testClasses
                  |                     |
             compileJava         compileTestJava ──► classes
```

`build` cần `assemble` (đóng gói) và `check` (kiểm tra). `jar` cần class đã biên dịch, không cần kết quả test. Tuỳ chọn `--dry-run` in các task sẽ chạy mà không chạy chúng; với `jar`, đồ thị không có task test nào:

### Viết một task và ba pha của Gradle

Bạn cần một bước build mà plugin không có sẵn, ví dụ in tên file `.jar` cho script triển khai. Ở Maven, bạn tìm một plugin có goal làm việc đó. Ở Gradle, bạn viết task ngay trong build script:

```kotlin
tasks.register("printJar") {
    dependsOn(tasks.jar)
    val jarName = tasks.jar.flatMap { it.archiveFileName }
    println("cau hinh printJar")
    doLast {
        println("jar = " + jarName.get())
    }
}
```

- `tasks.register` khai báo task mới tên `printJar`. Khối lambda đi kèm cấu hình task.
- `dependsOn(tasks.jar)` thêm một cạnh vào đồ thị: `printJar` chỉ chạy sau `jar`.
- `doLast { }` là **action** của task, việc nó làm khi được chạy.
- `tasks.jar.flatMap { it.archiveFileName }` lấy tên file `.jar` dưới dạng một giá trị sẽ tính sau, để đọc đúng tên ngay cả khi cấu hình của `jar` đổi.

<Terminal where="mac">

```bash
./gradlew printJar --console=plain
```

</Terminal>

Kết quả:

```text
cau hinh printJar
> Task :compileJava UP-TO-DATE
> Task :processResources NO-SOURCE
> Task :classes UP-TO-DATE
> Task :jar UP-TO-DATE

> Task :printJar
jar = invoice-1.0.0-SNAPSHOT.jar

BUILD SUCCESSFUL in 506ms
3 actionable tasks: 1 executed, 2 up-to-date
```

Dòng `cau hinh printJar` in ra trước khi bất kỳ task nào chạy, còn dòng `jar = ...` in ra trong lúc task chạy. Đó là vì mỗi lần build, Gradle đi qua ba pha:

| Pha | Gradle làm gì | Code nào chạy |
|---|---|---|
| Initialization | Đọc `settings.gradle.kts`, biết build có những project nào | `settings.gradle.kts` |
| Configuration | Chạy build script, cấu hình các task cần cho lệnh này, dựng đồ thị task | Thân build script, khối cấu hình của task |
| Execution | Chạy các task trong đồ thị theo thứ tự phụ thuộc | Action trong `doLast`, `doFirst` |

Một lỗi hay gặp là đặt việc thật (đọc file, gọi lệnh ngoài) ngay trong khối cấu hình thay vì trong `doLast`. Việc đó chạy ở pha configuration, trước khi Gradle biết task có được chạy hay không, và chạy cả khi task `UP-TO-DATE`. Mọi việc của task đặt trong action.

Thêm một khác biệt cần biết: plugin `application` không ghi `Main-Class` vào manifest như cấu hình `maven-jar-plugin` ở trên, nên `java -jar build/libs/invoice-1.0.0-SNAPSHOT.jar` báo `no main manifest attribute`. Chạy ứng dụng bằng `./gradlew run`, hoặc cấu hình task `jar`:

```kotlin
tasks.jar {
    manifest {
        attributes["Main-Class"] = "vn.masteva.invoice.Main"
    }
}
```

Cờ `-Xdoclint` ở mục plugin cũng đi vào task: `tasks.compileJava { options.compilerArgs.add("-Xdoclint:all,-missing") }`. Javadoc ghi sai `@throws` khi đó làm task `compileJava` thất bại với cùng thông báo `exception not thrown: java.io.IOException`.

### Maven hay Gradle

Khái niệm của hai công cụ tương ứng với nhau gần như một đối một, nên học một cái thì đọc được cái kia:

| Maven | Gradle |
|---|---|
| `pom.xml` | `build.gradle.kts` và `settings.gradle.kts` |
| Phase (`compile`, `test`, `package`) | Task (`compileJava`, `test`, `jar`, `build`) |
| Goal của plugin (`compiler:compile`) | Action của task |
| `mvn package` | `./gradlew build` (có chạy test) hoặc `./gradlew assemble` (không chạy test) |
| `<scope>test</scope>` | `testImplementation(...)` |
| `maven.compiler.release` | `java { toolchain { ... } }` |
| `~/.m2/repository` | `~/.gradle/caches` |
| `target/` | `build/` |
| `mvnw` (J7.3) | `gradlew` (J7.3) |

Chỗ khác nhau thật nằm ở mô hình:

| Thuộc tính | Maven | Gradle |
|---|---|---|
| Mô tả build | XML khai báo, ít cách viết | Code Kotlin (hoặc Groovy), viết được logic tuỳ ý |
| Thứ tự bước | Chuỗi phase cố định | Đồ thị task |
| Test hỏng | Không có `.jar` | `.jar` vẫn có thể đã được tạo; lệnh `build` thất bại |
| Build lại khi không đổi gì | Đi lại mọi phase, chạy lại test | Task `UP-TO-DATE`, bỏ qua |
| Thêm bước mới | Tìm plugin, gắn goal vào phase | Viết task trong build script |

Chọn Maven khi muốn mọi project trông giống nhau và người mới đọc được ngay; đây là lựa chọn của các chặng sau trong Masteva. Chọn Gradle khi build lớn, nhiều module, cần tốc độ của kiểm tra cập nhật và build cache, hoặc khi hệ sinh thái đã mặc định nó, như Android.

<Callout kind="ai">

Nhờ AI viết nhanh một `pom.xml` hay `build.gradle.kts` có sẵn plugin và cấu hình, hoặc giải thích một đoạn log build. AI hay dùng version plugin cũ (ví dụ `maven-compiler-plugin` 3.8 với `<source>` và `<target>` thay vì `<release>`), hay trộn cú pháp Gradle Groovy (`build.gradle`) với Kotlin DSL (`build.gradle.kts`), hay đặt việc thật ngoài `doLast`, và hay khuyên `-DskipTests` để "sửa" build đỏ. Kiểm tra lại bằng log thật: dòng `--- plugin:version:goal` cho biết plugin nào chạy, `Compiling ... [debug release 25]` cho biết tuỳ chọn tới tay `javac`, `--dry-run` cho biết Gradle sẽ chạy task nào.

</Callout>

<Callout kind="link">

J1 dạy `javac`, `--release` và classpath, những thứ build tool làm thay bạn ở đây; J4.2 dùng `-Xdoclint` mà bài này đưa vào cấu hình build. J7.2 thêm thư viện, scope, dependency configuration của Gradle và tách project thành nhiều module. J7.3 cố định phiên bản Maven, Gradle và plugin bằng wrapper. J8 dùng phase `test` và `verify` cho unit test và integration test; SB11 đóng gói file `.jar` vào image container.

</Callout>
