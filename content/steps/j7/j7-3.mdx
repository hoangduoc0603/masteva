<Goal>

Làm cho project build giống nhau trên mọi máy và mọi lần build: cùng phiên bản build tool, cùng phiên bản plugin, cùng JDK, và cùng file `.jar` tới từng byte. Học xong bài này, bạn giải thích được:

- Vì sao cùng một commit, máy bạn và CI chạy hai phiên bản `maven-surefire-plugin` khác nhau mà không ai sửa `pom.xml`.
- Vì sao hai lần `mvn package` liên tiếp trên cùng một máy cho ra hai file `.jar` khác hash, còn Gradle 9 thì không.
- File nào của wrapper phải commit vào Git, và vì sao người mới clone repo không cần cài Maven hay Gradle.
- Vì sao Gradle biên dịch bằng JDK 25 dù chính nó đang chạy trên JDK 21, còn Maven thì báo lỗi.

</Goal>

<Knowledge>

Bài dùng project hai module `invoice` và `invoice-app` của J7.2, với POM cha ở thư mục gốc `masteva-j7`.

### Vì sao "chạy được trên máy tôi" chưa đủ

Build trên máy bạn xanh, trên CI đỏ, cùng một commit. Hai lần build cùng một mã nguồn có thể khác nhau vì những thứ không nằm trong mã nguồn:

| Nguồn khác biệt | Ví dụ | Cách chốt |
|---|---|---|
| Phiên bản build tool | Máy A có Maven 3.9.9, CI có 3.9.16 | Wrapper |
| Version plugin mặc định | Mỗi bản Maven gắn sẵn một bộ version plugin riêng | `<pluginManagement>` ghi đủ version |
| Version dependency | Version range `[2.0,)` (từ 2.0 trở lên, lấy bản mới nhất trên kho), `SNAPSHOT` của người khác | Version cố định, BOM (J7.2) |
| JDK | Build bằng 21 ở máy này, 25 ở máy kia | Enforcer (Maven), toolchain (Gradle) |
| Thời điểm build | Mỗi file trong `.jar` mang giờ build | `project.build.outputTimestamp` (Maven); Gradle 9 cố định sẵn |

**Build tái lập** (reproducible build) nghĩa là: cùng mã nguồn, cùng môi trường đã khai báo, thì ra artifact giống hệt từng byte. Khi đó bất kỳ ai build lại một commit cũng ra cùng hash, nên bạn chứng minh được file `.jar` trên production đúng là build từ commit nào, và so hai bản build để biết có gì thật sự thay đổi.

Build tái lập không thay cho việc lưu artifact. Build lại tốn thời gian và cần đúng môi trường, và cần mọi dependency vẫn còn trên kho. Quy trình thường gặp: CI build một lần, đẩy artifact lên kho (Nexus, Artifactory, GitHub Packages), mọi môi trường triển khai cùng file đó. Build tái lập dùng để đối chiếu: một máy độc lập build lại và so hash với file trên kho.

### Maven Wrapper

Người mới vào nhóm có Maven 3.9.9 từ Homebrew, CI dùng 3.9.16, còn bạn chưa nâng từ năm ngoái. **Wrapper** là một script nhỏ nằm trong repo, chạy thay cho lệnh `mvn` cài trên máy: nó đọc phiên bản Maven ghi trong repo, tải bản đó nếu máy chưa có, rồi chạy nó. Goal `wrapper:wrapper` sinh wrapper cho project; `-Dmaven=3.9.16` chọn bản Maven mà wrapper sẽ tải:

<Terminal where="mac">

```bash
mvn wrapper:wrapper -Dmaven=3.9.16
ls mvnw* .mvn/wrapper
cat .mvn/wrapper/maven-wrapper.properties
```

### Kiểm checksum của bản Maven tải về

Không có checksum, wrapper tin bất kỳ file zip nào tải về từ `distributionUrl`. Nếu URL trỏ tới một kho nội bộ bị chiếm quyền, mọi máy dev và CI sẽ chạy một bản Maven bị cài mã độc. Thuộc tính `distributionSha256Sum` trong `maven-wrapper.properties` bảo script so SHA-256 của file vừa tải với giá trị khai báo, và dừng nếu lệch.

Giá trị đó phải lấy từ nguồn tin cậy. Maven Central công bố SHA-512 của bản phân phối cạnh file zip; tải zip, so SHA-512 với giá trị công bố, rồi tính SHA-256 để ghi vào wrapper. Lệnh đầu chuyển sang một thư mục tạm do `mktemp -d` tạo, để file zip khoảng 9 MB không nằm lẫn trong repo:

<Terminal where="mac">

```bash
cd "$(mktemp -d)"
curl -sO https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.16/apache-maven-3.9.16-bin.zip
curl -s https://repo.maven.apache.org/maven2/org/apache/maven/apache-maven/3.9.16/apache-maven-3.9.16-bin.zip.sha512; echo
shasum -a 512 apache-maven-3.9.16-bin.zip
shasum -a 256 apache-maven-3.9.16-bin.zip
```

</Terminal>


Hai dòng đầu trùng nhau: file bạn tải đúng là file Maven Central công bố. `echo` chỉ để xuống dòng, vì file `.sha512` không kết thúc bằng dấu xuống dòng. Dòng cuối là giá trị cần thêm vào `.mvn/wrapper/maven-wrapper.properties`:


Khi giá trị không khớp file tải về, ví dụ một chuỗi toàn số 0, `./mvnw` trên máy chưa có bản 3.9.16 dừng ngay:

```text

If you updated your Maven version, you need to update the specified distributionSha256Sum property.
```

Script chỉ kiểm lúc tải. Máy đã có bản 3.9.16 trong `~/.m2/wrapper/dists` vẫn chạy bình thường với checksum sai, nên một checksum sai có thể nằm im trong repo cho tới khi một máy mới clone về. Cập nhật `distributionSha256Sum` trong cùng commit với `distributionUrl`.

### Version plugin đi theo bản Maven

J7.1 cho thấy plugin gắn sẵn mà không ghi version thì Maven dùng version gắn sẵn trong chính bản Maven đang chạy. Wrapper làm việc đó lộ ra rõ nhất. Build cùng project hai lần, lần đầu bằng `mvn` cài trên máy (3.9.9), lần sau bằng `./mvnw` (3.9.16); `grep` chỉ giữ các dòng ghi plugin, version và goal chạy trên module `invoice`:

<Terminal where="mac">

```bash

./mvnw clean package | grep -- '--- .* @ invoice ---'
```

</Terminal>

Một bản Maven mới gắn sẵn một bộ plugin mới, nên đổi bản Maven là đổi plugin, dù `pom.xml` không đổi một dòng. Plugin không nằm trong bảng gắn sẵn thì còn tệ hơn: thiếu version, Maven lấy bản mới nhất trên kho ở thời điểm build, như dòng `Downloading ... maven-wrapper-plugin/maven-metadata.xml` ở mục trước. Kết quả đó đổi theo ngày build.

Wrapper chốt bản Maven, nên chốt luôn bộ plugin gắn sẵn. Nhưng nâng wrapper vẫn đổi plugin, và plugin ngoài bảng gắn sẵn vẫn trôi theo kho. Vì vậy POM cha ghi version cho **mọi** plugin trong `<pluginManagement>`, kể cả những plugin bạn chưa từng cấu hình:

|---|---|---|

| `maven-resources-plugin` | 3.5.0 | Gắn sẵn: `process-resources`, `process-test-resources` |
| `maven-compiler-plugin` | 3.16.0 | Gắn sẵn: `compile`, `test-compile` |
| `maven-surefire-plugin` | 3.6.0 | Gắn sẵn: `test` |
| `maven-jar-plugin` | 3.5.0 | Gắn sẵn: `package` |
| `maven-install-plugin`, `maven-deploy-plugin` | 3.2.0 | Gắn sẵn: `install`, `deploy` |
| `maven-site-plugin` | 3.22.0 | Lifecycle `site` |

| `maven-enforcer-plugin` | 3.6.3 | Mục "Chặn môi trường sai bằng Enforcer" |
| `maven-artifact-plugin` | 3.7.0 | Goal `artifact:check-buildplan` ở mục dưới |
| `maven-wrapper-plugin` | 3.3.4 | Goal `wrapper:wrapper` gọi từ dòng lệnh |

Mỗi dòng trong bảng là một khối `<plugin>` trong `<pluginManagement>` của POM cha, như hai plugin ở J7.2:

```xml
<build>
  <pluginManagement>
    <plugins>
      <plugin>
        <groupId>org.apache.maven.plugins</groupId>
        <artifactId>maven-surefire-plugin</artifactId>
        <version>3.6.0</version>
      </plugin>
      <!-- một khối <plugin> như trên cho mỗi dòng còn lại của bảng -->
    </plugins>
  </pluginManagement>
</build>
```

<Callout kind="production">

Một nhóm không ghi version plugin. Agent CI được nâng Maven vào cuối tuần; sáng thứ Hai, build của nhánh `main` đỏ dù không ai commit gì. Bản Maven mới gắn sẵn một `maven-surefire-plugin` mới hơn, xử lý một tuỳ chọn cấu hình của nhóm khác với bản cũ. Mất nửa ngày mới tìm ra, vì `pom.xml` "không đổi". Wrapper cùng `<pluginManagement>` đầy đủ làm cho việc nâng Maven hay plugin trở thành một commit có review, không phải chuyện xảy ra ngoài repo.

</Callout>

### Thời điểm build nằm trong file jar

Build hai lần liên tiếp và so hash của file `.jar`. `shasum -a 256` in mã SHA-256 của file; khác một byte là khác hash. `unzip -l` liệt kê các mục trong file `.jar` kèm ngày giờ:

<Terminal where="mac">

```bash
./mvnw -q clean package && shasum -a 256 invoice/target/invoice-1.0.0-SNAPSHOT.jar
sleep 2
./mvnw -q clean package && shasum -a 256 invoice/target/invoice-1.0.0-SNAPSHOT.jar
unzip -l invoice/target/invoice-1.0.0-SNAPSHOT.jar | head -5
```

</Terminal>

```text
---------  ---------- -----   ----
        0  10-23-2026 16:56   META-INF/
```

Hash trên máy bạn sẽ khác; điều cần thấy là hai dòng khác nhau. File `.jar` là file zip, và mỗi mục trong zip ghi ngày giờ; mặc định đó là giờ build, như cột `Date` và `Time`. `sleep 2` có mặt vì zip chỉ ghi giờ chính xác tới 2 giây: hai lần build trong cùng 2 giây có thể trùng hash một cách tình cờ.

Thuộc tính `project.build.outputTimestamp` bảo các plugin đóng gói ghi một thời điểm cố định thay vì giờ hiện tại. Thêm nó vào `<properties>` của POM cha:

```xml
<project.build.outputTimestamp>2026-10-03T00:00:00Z</project.build.outputTimestamp>
```

Giá trị thường là thời điểm commit cuối; công cụ phát hành như `maven-release-plugin` có thể tự cập nhật nó mỗi lần phát hành. Plugin quá cũ không biết thuộc tính này, nên mục sau kiểm tra cả version plugin.

### Chặn môi trường sai bằng Enforcer

Wrapper chỉ có tác dụng khi người ta gọi `./mvnw`. Ai quen tay gõ `mvn`, hoặc build bằng một JDK khác, vẫn build được, với plugin và bytecode khác. `maven-enforcer-plugin` kiểm tra điều kiện ở phase `validate`, trước khi biên dịch, và dừng build nếu điều kiện sai:

| Rule | Chặn |
|---|---|
| `requireMavenVersion` | Ai đó gọi `mvn` cũ thay vì `./mvnw` |
| `requireJavaVersion` | Build bằng JDK không đúng phiên bản dự án chọn |
| `requirePluginVersions` | Plugin nào đó chưa ghi version |

Cấu hình trong `<build><plugins>` của POM cha, để mọi module kế thừa. `<pluginManagement>` chỉ chốt version và cấu hình cho plugin nào được dùng; `<build><plugins>` mới bật plugin cho build. Vì vậy khối dưới không ghi version, mà lấy 3.6.3 từ bảng ở mục "Version plugin đi theo bản Maven":

```xml
<plugin>
  <groupId>org.apache.maven.plugins</groupId>
  <artifactId>maven-enforcer-plugin</artifactId>
  <executions>
    <execution>
      <id>enforce-build-env</id>
      <goals>
        <goal>enforce</goal>
      </goals>
      <configuration>
        <rules>
          <requireMavenVersion>
            <version>[3.9.16,)</version>
          </requireMavenVersion>
          <requireJavaVersion>
            <version>[25,26)</version>
          </requireJavaVersion>
          <requirePluginVersions/>
        </rules>
      </configuration>
    </execution>
  </executions>
</plugin>
```

Version viết theo cú pháp khoảng của Maven: `[3.9.16,)` là từ 3.9.16 trở lên; `[25,26)` là từ 25 trở lên và nhỏ hơn 26, tức mọi bản vá 25.0.x. Goal `enforce` mặc định gắn vào phase `validate`, nên execution không cần ghi `<phase>`. Để thấy Enforcer bắt plugin thiếu version, tạm bỏ khối `maven-site-plugin` khỏi `<pluginManagement>` (bảng ở mục "Version plugin đi theo bản Maven"), rồi chạy phase `validate`:

<Terminal where="mac">

```bash
./mvnw validate
```

</Terminal>

### Gradle Wrapper

Gradle có wrapper với cùng ý tưởng, và đây là cách chạy Gradle phổ biến nhất: J7.1 và J7.2 đã gọi `./gradlew`. Như J7.1 nhắc, lần đầu tạo wrapper cho một project cần một bản Gradle cài trên máy (`brew install gradle` rồi `gradle wrapper --gradle-version 9.8.2`). Từ đó về sau, nâng phiên bản bằng chính wrapper. Lệnh dưới chốt Gradle 9.8.2 kèm checksum; giá trị SHA-256 lấy từ file `gradle-9.8.2-bin.zip.sha256` mà Gradle công bố trên services.gradle.org:

### Gradle: toolchain chọn JDK

Phần JDK thì Gradle giải theo cách khác Maven. Maven biên dịch bằng JDK đang chạy Maven, nên Enforcer chỉ kiểm và dừng build khi JDK sai. Gradle có **toolchain**: khối `java { toolchain { languageVersion = JavaLanguageVersion.of(25) } }` của J7.1 bảo Gradle tự tìm JDK 25 trên máy để biên dịch, chạy test và chạy ứng dụng, bất kể Gradle đang chạy trên JDK nào. Chạy Gradle bằng JDK 21, với `--rerun-tasks` để buộc chạy lại task dù đã `UP-TO-DATE` và `--info` để Gradle in thêm chi tiết, rồi lọc dòng cho biết JDK dùng để biên dịch:

<Terminal where="mac">

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./gradlew :invoice:compileJava --rerun-tasks --info | grep -E 'Compiling with toolchain|BUILD'
```

</Terminal>

Kết quả:

```text
Compiling with toolchain '/Library/Java/JavaVirtualMachines/jdk-25.jdk/Contents/Home'.
BUILD SUCCESSFUL in 4s
```

Gradle chạy trên JDK 21 nhưng biên dịch bằng JDK 25. Cùng tình huống, Maven không có Enforcer báo `release version 25 not supported` (J7.1); có Enforcer thì dừng ở `validate` như mục trên. Nếu máy không có JDK nào khớp, Gradle dừng với thông báo rõ ràng. Trên một máy không cài JDK 24, đặt `languageVersion` là 24 thì Gradle dừng:

```text
* What went wrong:
Could not determine the dependencies of task ':invoice:compileJava'.
> Could not resolve all dependencies for configuration ':invoice:compileClasspath'.
   > Failed to calculate the value of task ':invoice:compileJava' property 'javaCompiler'.
      > Cannot find a Java installation on your machine (Mac OS X 14.4.1 aarch64) matching: {languageVersion=24, vendor=any vendor, implementation=vendor-specific, nativeImageCapable=false}. Toolchain download repositories have not been configured.
```

`Toolchain download repositories have not been configured` cho biết Gradle còn tự tải được JDK nếu bạn khai báo kho tải toolchain trong `settings.gradle.kts`; bài này không đi vào phần đó. Tóm lại cách hai công cụ chốt từng nguồn khác biệt:

| Nguồn khác biệt | Maven | Gradle |
|---|---|---|
| Phiên bản build tool | `mvnw`, `maven-wrapper.properties` | `gradlew`, `gradle-wrapper.properties`, `gradle-wrapper.jar` |
| Checksum bản tải về | `distributionSha256Sum` | `distributionSha256Sum` |
| Version plugin | Ghi đủ trong `<pluginManagement>`, Enforcer `requirePluginVersions` | Plugin lõi theo bản Gradle; plugin ngoài bắt buộc ghi version |
| JDK | JDK của `JAVA_HOME`; Enforcer `requireJavaVersion` kiểm | Toolchain tự tìm đúng JDK |
| Thời điểm trong archive | `project.build.outputTimestamp` | Cố định sẵn từ Gradle 9 |

Cuối cùng, `.gitignore` của project bỏ qua thư mục kết quả build: `target/` với Maven, `build/` và `.gradle/` với Gradle. Mọi thứ khác ở trên, kể cả các file wrapper, đi vào Git; người clone repo cài JDK rồi gõ `./mvnw verify` hoặc `./gradlew build`.

<Callout kind="ai">

Nhờ AI liệt kê version mới nhất của các plugin Maven, viết cấu hình Enforcer, hoặc giải thích vì sao hai lần build khác hash. AI hay đưa version đã cũ hoặc không tồn tại, hay quên `maven-site-plugin` khi chốt version, hay đề xuất `<requireJavaVersion>` dạng `25` (nghĩa là từ 25 trở lên, kể cả 26, 27) thay vì khoảng `[25,26)`, và hay bịa checksum. Kiểm tra version trên Maven Central, lấy checksum từ trang phát hành chính thức, rồi để `requirePluginVersions` và hai lần `shasum` nói thay.

</Callout>
