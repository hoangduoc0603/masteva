<Goal>

Làm cho project build giống nhau trên mọi máy và mọi lần chạy: cùng phiên bản Maven, cùng phiên bản plugin, cùng JDK, và cùng file `.jar` tới từng byte. Học xong bài này, bạn giải thích được:

- Vì sao cùng một commit, máy bạn và CI chạy hai phiên bản `maven-surefire-plugin` khác nhau mà không ai sửa `pom.xml`.
- Vì sao hai lần `mvn package` liên tiếp trên cùng một máy cho ra hai file `.jar` khác hash.
- File nào của wrapper phải commit vào Git, và vì sao người mới clone repo không cần cài Maven.

</Goal>

<Knowledge>

### Vì sao "chạy được trên máy tôi" chưa đủ

Hai lần build cùng một mã nguồn có thể khác nhau vì những thứ không nằm trong mã nguồn:

| Nguồn khác biệt | Ví dụ | Cách chốt |
|---|---|---|
| Phiên bản Maven | Máy A có 3.9.9, CI có 3.9.16 | Maven Wrapper |
| Version plugin mặc định | Mỗi bản Maven gắn sẵn một bộ version plugin riêng; plugin ngoài bảng đó mà thiếu version thì lấy bản mới nhất trên kho | `<pluginManagement>` ghi đủ version |
| Version dependency | Version range `[2.0,)`, `SNAPSHOT` của người khác | Version cố định, BOM (J7.2) |
| JDK | Build bằng 21 ở máy này, 25 ở máy kia | Enforcer `requireJavaVersion` |
| Thời điểm build | Mỗi file trong `.jar` mang giờ build | `project.build.outputTimestamp` |

**Build tái lập** (reproducible build) nghĩa là: cùng mã nguồn, cùng môi trường đã khai báo, thì ra artifact giống hệt từng byte. Lợi ích thực tế: bạn chứng minh được file `.jar` trên production đúng là build từ commit nào (bất kỳ ai build lại cũng ra cùng hash), và so sánh hai bản build để biết có gì thật sự thay đổi.

### Maven Wrapper

**Wrapper** là một script nhỏ nằm trong repo, thay cho lệnh `mvn` cài trên máy:

```text
./mvnw package
   |
   |  đọc .mvn/wrapper/maven-wrapper.properties
   |  distributionUrl=.../apache-maven/3.9.16/apache-maven-3.9.16-bin.zip
   v
đã có ~/.m2/wrapper/dists/apache-maven-3.9.16/<hash>/ ?
   |-- chưa: tải zip, kiểm tra checksum nếu có khai báo, giải nén
   v
chạy Maven 3.9.16 vừa tìm được, với đúng tham số bạn gõ
```

| File | Commit vào Git | Vai trò |
|---|---|---|
| `mvnw` | Có | Script cho macOS, Linux |
| `mvnw.cmd` | Có | Script cho Windows |
| `.mvn/wrapper/maven-wrapper.properties` | Có | Phiên bản và URL tải Maven |
| `~/.m2/wrapper/dists/...` | Không | Bản Maven đã tải, nằm ngoài repo |

Với wrapper 3.3.4 dùng trong bài, kiểu mặc định là `only-script`: repo không cần file `maven-wrapper.jar`, script tự tải bằng `wget` hoặc `curl`. Gradle có cơ chế tương tự: `gradlew`, `gradlew.bat`, `gradle/wrapper/gradle-wrapper.properties` và một file `gradle-wrapper.jar` phải commit cùng.

<Check id="j7.3.wrapper-why">Giải thích được wrapper tìm và chạy đúng phiên bản Maven thế nào, và file nào của nó phải commit.</Check>

### Chốt version plugin

Plugin không ghi version thì lấy version gắn sẵn trong bản Maven đang chạy (bài J7.1 thấy `jar:3.4.1` trong bảng mặc định của 3.9.9). Plugin không nằm trong bảng gắn sẵn (ví dụ gọi `mvn wrapper:wrapper` từ dòng lệnh, hay khai báo trong `<plugins>` mà thiếu version) thì Maven lấy bản mới nhất trên kho, nên có thể đổi theo ngày build. Vì vậy POM cha ở bước 5 ghi cả `maven-wrapper-plugin` và `maven-artifact-plugin`. Với plugin gắn sẵn, đổi bản Maven là đổi plugin, dù `pom.xml` không đổi; nên POM cha cũng ghi version cho **mọi** plugin trong `<pluginManagement>`, kể cả những plugin bạn chưa từng cấu hình như `clean`, `resources`, `install`, `site`.

### Cố định thời điểm build

File `.jar` là file zip; mỗi mục trong zip ghi ngày giờ. Mặc định đó là giờ build, nên hai lần build cách nhau vài giây đã khác hash. Thuộc tính `project.build.outputTimestamp` bảo các plugin đóng gói ghi một thời điểm cố định thay vì giờ hiện tại. Giá trị thường là thời điểm commit cuối; công cụ phát hành như `maven-release-plugin` có thể tự cập nhật nó mỗi lần phát hành. Plugin quá cũ không biết thuộc tính này; goal `artifact:check-buildplan` của `maven-artifact-plugin` liệt kê plugin nào cần nâng.

### Chặn môi trường sai bằng Enforcer

`maven-enforcer-plugin` kiểm tra điều kiện ở phase `validate`, trước khi biên dịch:

| Rule | Chặn |
|---|---|
| `requireMavenVersion` | Ai đó gọi `mvn` cũ thay vì `./mvnw` |
| `requireJavaVersion` | Build bằng JDK không đúng phiên bản dự án chọn |
| `requirePluginVersions` | Plugin nào đó chưa ghi version |

<Callout kind="production">

Một nhóm không ghi version plugin. Agent CI được nâng Maven vào cuối tuần; sáng thứ Hai, build của nhánh `main` đỏ dù không ai commit gì. Bản Maven mới gắn sẵn một `maven-surefire-plugin` mới hơn, xử lý một tuỳ chọn cấu hình của nhóm khác với bản cũ. Mất nửa ngày mới tìm ra, vì `pom.xml` "không đổi". Wrapper cùng `<pluginManagement>` đầy đủ làm cho việc nâng Maven hay plugin trở thành một commit có review, không phải chuyện xảy ra ngoài repo.

</Callout>

</Knowledge>

Giống nhau. Mọi mục trong `.jar` mang thời điểm từ `project.build.outputTimestamp`, không còn giờ build. Hash trên máy bạn có thể khác máy kiểm chứng, vì bytecode và manifest còn phụ thuộc bản JDK; nhưng trên cùng một máy, hai lần build phải trùng nhau.

</Predict>

### 7. Enforcer chặn môi trường sai

<Terminal where="mac">

```bash
mvn -q validate
```

</Terminal>

<Expected>

```text
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-enforcer-plugin:3.6.3:enforce (enforce-build-env) on project masteva-j7: 
[ERROR] Rule 0: org.apache.maven.enforcer.rules.version.RequireMavenVersion failed with message:
[ERROR] Detected Maven Version: 3.9.9 is not in the allowed range [3.9.16,).
```

</Expected>

Ai quen tay gõ `mvn` thay vì `./mvnw` sẽ bị dừng ngay ở `validate`, kèm lý do rõ ràng. Nếu `mvn` trên máy bạn là 3.9.16 hoặc mới hơn (ví dụ 3.10.0 từ Homebrew), lệnh này qua được; thử đổi khoảng thành `[3.11,)` để thấy lỗi, rồi trả lại. Nếu máy bạn có thêm JDK 21, thử build bằng JDK đó:

<Terminal where="mac">

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) ./mvnw -q validate
```

</Terminal>

<Expected>

```text
[ERROR] Failed to execute goal org.apache.maven.plugins:maven-enforcer-plugin:3.6.3:enforce (enforce-build-env) on project masteva-j7: 
[ERROR] Rule 1: org.apache.maven.enforcer.rules.version.RequireJavaVersion failed with message:
[ERROR] Detected JDK /Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home is version 21.0.3 which is not in the allowed range [25,26).
```

</Expected>

Gán biến ngay trước lệnh như trên chỉ đổi `JAVA_HOME` cho đúng lệnh đó. Khoảng `[25,26)` nghĩa là từ 25 trở lên, nhỏ hơn 26: dự án chốt JDK 25, kể cả các bản vá 25.0.x.

```bash
printf 'target/\n' > .gitignore

```

</Terminal>

<Expected>

```text

A  invoice-app/pom.xml
A  invoice-app/src/main/java/vn/masteva/app/Main.java

A  invoice/src/main/java/vn/masteva/invoice/Invoice.java
```

`mvnw`, `mvnw.cmd` và `.mvn/wrapper/maven-wrapper.properties` nằm trong danh sách, còn `target/` của các module thì không. Người clone repo này chỉ cần JDK 25 và chạy `./mvnw verify`. Bài không yêu cầu commit; nếu muốn, chạy `git commit -m "..."` như ở J1.3.

### Khi gặp lỗi

<Callout kind="pitfall">

- `zsh: permission denied: ./mvnw`: file mất quyền chạy, thường do tải repo dạng zip hoặc commit từ Windows. Chạy `chmod +x mvnw`, và trên Git ghi lại quyền bằng `git update-index --chmod=+x mvnw`.
- `./mvnw` báo không tải được `distributionUrl`: mạng công ty chặn Maven Central. Đổi `distributionUrl` sang kho nội bộ của công ty, hoặc đặt biến `MVNW_REPOURL`.
- Hai lần build vẫn khác hash sau khi đặt `outputTimestamp`: chạy `./mvnw artifact:check-buildplan` để tìm plugin cũ, và kiểm tra có plugin nào ghi giờ build hay thông tin máy vào file trong `src/main/resources`.
- Checksum không khớp sau khi đổi version Maven: bạn đã khai báo `distributionSha256Sum` cho bản cũ. Cập nhật giá trị đó cùng lúc với `distributionUrl`.

</Callout>

<DeepDive>

<Reveal title="Build tái lập rồi thì có còn cần lưu artifact không?">

Vẫn cần. Build tái lập cho phép **kiểm chứng** một artifact đúng là từ commit nào, nhưng build lại tốn thời gian và cần đúng môi trường, kể cả mọi dependency vẫn còn trên kho. Quy trình thường gặp: CI build một lần, đẩy artifact lên kho (Nexus, Artifactory, GitHub Packages), mọi môi trường triển khai cùng file đó. Build tái lập dùng để đối chiếu: một máy độc lập build lại và so hash với file trên kho.

</Reveal>

<Reveal title="Vì sao nên khai báo distributionSha256Sum?">

Không có checksum, wrapper tin bất kỳ file zip nào tải về từ `distributionUrl`. Nếu URL trỏ tới một kho nội bộ bị chiếm quyền, mọi máy dev và CI sẽ chạy một bản Maven bị cài mã độc. Khi có `distributionSha256Sum`, script `mvnw` so SHA-256 của file vừa tải và dừng nếu lệch. Lấy giá trị từ nguồn tin cậy, và cập nhật nó trong cùng commit với `distributionUrl`. Gradle Wrapper có thuộc tính cùng tên.

</Reveal>

<Reveal title="Có nên chốt cả bản vá của JDK, ví dụ đúng 25.0.3?">

Thường là không. Bản vá JDK chủ yếu sửa lỗi bảo mật, chặn chúng làm dự án chậm nhận bản vá. Khoảng `[25,26)` chốt phiên bản chính, đủ để bytecode và API giống nhau. Phần còn lại chốt ở nơi build thật: image Docker của CI ghi rõ bản JDK, và bản đó được nâng qua một commit có review. Nếu cần hash giống hệt giữa nhiều máy, mọi máy phải dùng cùng bản JDK, nên khi đó hãy build trong cùng một image.

</Reveal>

<Reveal title="Gradle làm build tái lập thế nào?">

Gradle cũng có wrapper (`gradle wrapper --gradle-version <bản>` sinh ra `gradlew`), và toolchain chốt JDK như ở bài J7.1. Từ Gradle 9, file archive như `.jar` tái lập sẵn: mọi mục mang một thời điểm cố định năm 1980 và thứ tự file cố định. Bài đã thử với Gradle 9.8.0: hai lần `gradle clean jar` cho cùng hash mà không cần cấu hình gì. Plugin lõi như `java`, `application` đi theo bản Gradle mà wrapper đã chốt; plugin bên ngoài bắt buộc ghi version trong khối `plugins`.

</Reveal>

<Callout kind="ai">

Nhờ AI liệt kê version mới nhất của các plugin Maven, hoặc viết cấu hình Enforcer. AI hay đưa version đã cũ hoặc không tồn tại, hay quên `maven-site-plugin` khi chốt version, và hay đề xuất `<requireJavaVersion>` dạng `25` (nghĩa là từ 25 trở lên, kể cả 26, 27) thay vì khoảng `[25,26)`. Kiểm tra version trên Maven Central, rồi để `requirePluginVersions` và hai lần `shasum` nói thay.

</Callout>

<Callout kind="link">

</Callout>
