### OWASP Top 10:2025

OWASP Top 10 là danh sách mười nhóm rủi ro bảo mật web phổ biến nhất, xếp hạng từ dữ liệu kiểm thử thực tế của nhiều tổ chức cộng với khảo sát cộng đồng. Bản 2025 có hai nhóm mới (A03 mở rộng từ "thành phần lỗi thời" thành cả chuỗi cung ứng, và A10) và gộp SSRF (Server-Side Request Forgery) vào A01.

| Mã | Nhóm | Trong service Spring Boot trông như thế nào | Kiểm tra ở đâu |
|---|---|---|---|
| A01 | Broken Access Control | IDOR: `GET /api/orders/1` trả đơn của người khác; quên `denyAll`; SSRF khi server tải URL do người dùng gửi | Bước 1 tới 3 bài này, SB6.1 |
| A02 | Security Misconfiguration | Mở mọi endpoint Actuator, trả stack trace ra ngoài, CORS `*` | Bước 4, SB6.2 bước 7 |
| A03 | Software Supply Chain Failures | Thư viện có lỗ hổng, dependency không rõ nguồn, plugin build bị chiếm | Bước 4 (SBOM), J7 |
| A04 | Cryptographic Failures | Mật khẩu băm SHA-256, HTTP thay vì HTTPS, khoá ký yếu | SB6.1 bước 7 |
| A05 | Injection | Nối chuỗi vào SQL hay JPQL, log injection | SB3 (tham số bind) |
| A06 | Insecure Design | Không giới hạn số lần thử mã OTP, luồng hoàn tiền không có giới hạn | Thiết kế, review |
| A07 | Authentication Failures | Nhận JWT `alg: none`, không kiểm `aud`, session không đổi sau đăng nhập | SB6.2 bước 5 và 8 |
| A08 | Software or Data Integrity Failures | Deserialize dữ liệu không tin cậy, cập nhật không kiểm chữ ký | J9 (JSON có kiểu rõ ràng) |

### Broken Access Control và IDOR

**IDOR** (Insecure Direct Object Reference), trong danh sách riêng cho API gọi là **BOLA** (Broken Object Level Authorization, đứng đầu OWASP API Security Top 10 2023): API nhận mã đối tượng từ client rồi trả đối tượng mà không kiểm người gọi có quyền với **đối tượng đó** không.

```text
GET /api/orders/1   Authorization: Bearer <token của bob>
        |
 filter chain: token hợp lệ, bob có ROLE_USER, /api/** cần authenticated()   -> cho qua
        |
 controller: orders.findById(1)                                               -> đơn của alice
        |
 200 {"owner":"alice", ...}        lỗi nằm ở đây, không ở filter chain
```

Filter chain chỉ biết URL và role; nó không biết đơn số 1 của ai. Quyền theo dữ liệu phải kiểm ở tầng truy vấn: lấy đơn theo **cả** `id` **và** chủ sở hữu, ví dụ `findByIdAndOwner(id, auth.getName())` hoặc `WHERE id = ? AND owner_id = ?`. Không thấy thì trả **404** thay vì 403, để kẻ tấn công không dò được mã nào tồn tại. Đổi `id` từ số tăng dần sang UUID làm việc dò khó hơn nhưng không sửa được lỗi; nó chỉ giấu lỗi.

<Callout kind="production">

Một ứng dụng giao đồ ăn cho xem đơn qua `/api/orders/{id}` với `id` tăng dần. Một người dùng đổi số trong URL và đọc được địa chỉ, số điện thoại của hàng nghìn khách khác. Hệ thống có đăng nhập, có role, có HTTPS; chỉ thiếu một điều kiện `owner` trong câu truy vấn. Loại lỗi này không lộ ra trong test giao diện vì giao diện chỉ hiện đơn của chính người dùng. Nó chỉ lộ ra khi có test gọi API bằng **hai** user khác nhau.

</Callout>

### Secret: không nằm trong code, Git hay image

**Secret** là bất cứ thứ gì cho phép truy cập: mật khẩu database, API key của cổng thanh toán, `client_secret` OAuth2, khoá ký JWT, khoá riêng TLS. Nguyên tắc: code và image giống hệt nhau ở mọi môi trường, secret được **nạp lúc chạy**.

| Cách nạp | Ưu điểm | Cần biết |
|---|---|---|
| Biến môi trường | Đơn giản, mọi nền tảng đều hỗ trợ | Lộ qua `docker inspect`, `/proc/<pid>/environ`, process con, crash dump |
| File mount (Kubernetes Secret, Docker secret) | Phân quyền theo file, cập nhật không cần build lại | Spring Boot đọc bằng `configtree:`; quyền file phải chặt (`600`) |
| Vault, secret manager của cloud | Xoay vòng tự động, secret động sống ngắn, nhật ký truy cập | Thêm một dịch vụ phải vận hành; Spring Cloud Vault nạp vào `Environment` |

Spring Boot gộp nhiều **property source** theo thứ tự ưu tiên. Rút gọn, từ thấp lên cao: file `application.properties` và mọi thứ nó `import` (kể cả `configtree:`), rồi biến môi trường, rồi system property của JVM, rồi tham số dòng lệnh. Biến môi trường `PAYMENT_APIKEY` (dạng Spring Boot khuyến nghị: thay `.` bằng `_`, bỏ `-`, viết hoa) hoặc `PAYMENT_API_KEY` đều khớp với property `payment.api-key`, nên biến môi trường thắng mọi file cấu hình. Lab dùng `PAYMENT_API_KEY`.

Vòng đời một secret gồm tạo, phân phối, **xoay vòng** định kỳ, thu hồi, và phát hiện khi lộ. Khi một secret lọt vào Git, thứ tự đúng là: **thu hồi và đổi secret ngay**, kiểm tra nhật ký xem nó đã bị dùng chưa, rồi mới tính chuyện xoá khỏi lịch sử. Repo công khai bị bot quét trong vài phút; xoá lịch sử không thu hồi được bản ai đó đã clone.

<Check id="j13.3.secret-sources">So sánh được biến môi trường, file mount và vault, và nói được thứ tự ưu tiên giữa biến môi trường với file cấu hình trong Spring Boot.</Check>

</Knowledge>

### 1. Một endpoint đơn hàng có lỗ hổng

Thêm đơn hàng với kho trong bộ nhớ (SB3 làm việc này với PostgreSQL). Controller dưới đây **cố ý** có lỗi IDOR:

<Terminal where="mac" title="Tạo Order, OrderRepository, OrderController">

```bash

cat > $P/order/OrderRepository.java <<'EOF'
package dev.masteva.orders.order;

import java.util.Map;
import java.util.Optional;
import org.springframework.stereotype.Repository;

/** Kho trong bộ nhớ cho lab; SB3 thay bằng PostgreSQL. */
@Repository
public class OrderRepository {

    private final Map<Long, Order> orders = Map.of(
        1L, new Order(1, "alice", "Bàn phím", 1_200_000),
        2L, new Order(2, "bob", "Tai nghe", 850_000));

    public Optional<Order> findById(long id) {
        return Optional.ofNullable(orders.get(id));
    }

    public Optional<Order> findByIdAndOwner(long id, String owner) {
        return findById(id).filter(order -> order.owner().equals(owner));
    }
}
EOF
cat > $P/order/OrderController.java <<'EOF'
package dev.masteva.orders.order;

import org.springframework.http.ResponseEntity;
import org.springframework.security.core.Authentication;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class OrderController {

    private final OrderRepository orders;

    public OrderController(OrderRepository orders) {
        this.orders = orders;
    }

    @GetMapping("/api/orders/{id}")
    public ResponseEntity<Order> get(@PathVariable long id, Authentication auth) {
        return ResponseEntity.of(orders.findById(id));
    }
}
EOF
```

### 2. Viết test tái hiện lỗi

Trước khi sửa, viết test mô tả hành vi đúng. `jwt()` của `spring-security-test` dựng sẵn một `Authentication` kiểu JWT cho request MockMvc, không gọi Keycloak và không đi qua converter của ứng dụng; tên người dùng khi đó lấy từ claim `sub`, nên test đặt `subject`.

<Terminal where="mac" title="Tạo OrderAccessTest">

```bash

package dev.masteva.orders.order;

import static org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.jwt;
import static org.springframework.test.web.servlet.request.MockMvcRequestBuilders.get;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.jsonPath;
import static org.springframework.test.web.servlet.result.MockMvcResultMatchers.status;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.boot.webmvc.test.autoconfigure.AutoConfigureMockMvc;
import org.springframework.security.test.web.servlet.request.SecurityMockMvcRequestPostProcessors.JwtRequestPostProcessor;
import org.springframework.test.web.servlet.MockMvc;

@SpringBootTest
@AutoConfigureMockMvc
class OrderAccessTest {

    @Autowired
    MockMvc mvc;

    /** jwt() dựng sẵn Authentication, không gọi Keycloak; tên lấy từ claim sub. */
    static JwtRequestPostProcessor user(String name) {
        return jwt().jwt(token -> token.subject(name));
    }

    @Test
    void ownerReadsOwnOrder() throws Exception {
        mvc.perform(get("/api/orders/1").with(user("alice")))
            .andExpect(status().isOk())
            .andExpect(jsonPath("$.owner").value("alice"));

    @Test
    void otherUserCannotReadOrder() throws Exception {
        mvc.perform(get("/api/orders/1").with(user("bob")))
            .andExpect(status().isNotFound());
    }

    @Test
    void anonymousIsRejected() throws Exception {
        mvc.perform(get("/api/orders/1"))
            .andExpect(status().isUnauthorized());
    }
}
EOF
mvn -q test -Dtest=OrderAccessTest
```

### 4. Đi qua vài mục khác của Top 10 trong lab

**A09, ghi log sự kiện bảo mật.** Spring Security phát sự kiện mỗi khi xác thực thất bại hoặc bị từ chối quyền. Ghi chúng ra log có cấu trúc để hệ thống giám sát (SB8) đếm và cảnh báo được. Không bao giờ log token hay mật khẩu.

<Terminal where="mac" title="Tạo AuthFailureLogger">

```bash
cd ~/masteva-j13/orders
cat > src/main/java/dev/masteva/orders/security/AuthFailureLogger.java <<'EOF'
package dev.masteva.orders.security;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.context.event.EventListener;
import org.springframework.security.authentication.event.AuthenticationFailureBadCredentialsEvent;
import org.springframework.security.authorization.event.AuthorizationDeniedEvent;
import org.springframework.stereotype.Component;

/** Ghi log mọi lần xác thực thất bại hoặc bị từ chối quyền, để cảnh báo được (OWASP A09). */
@Component
public class AuthFailureLogger {

    private static final Logger log = LoggerFactory.getLogger(AuthFailureLogger.class);

    @EventListener
    public void onAuthenticationFailure(AuthenticationFailureBadCredentialsEvent event) {
        log.warn("security.authn.failure reason=\"{}\"", event.getException().getMessage());
    }

    @EventListener
    public void onAuthorizationDenied(AuthorizationDeniedEvent<?> event) {
        log.warn("security.authz.denied user={}", event.getAuthentication().get().getName());
    }
}
EOF
perl -ni -e 'print unless /^logging.level.org.springframework.security=DEBUG/' src/main/resources/application.properties
mvn -q spring-boot:run
```

### 8. Chặn từ trước khi commit

Một hook `pre-commit` của Git chạy trước mỗi commit và huỷ commit nếu thoát với mã khác 0. Viết một bản tối giản:

<Terminal where="mac">

```bash
cd ~/masteva-j13/orders
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/sh
# Chặn commit khi phần thay đổi đã stage trông giống secret.
PATTERN='(pay_live_[A-Za-z0-9]+|-----BEGIN [A-Z ]*PRIVATE KEY-----|(password|secret|api-key)=[^$[:space:]]{8,})'
if git diff --cached -U0 | grep -nE "^\+.*$PATTERN"; then
  echo "pre-commit: phát hiện chuỗi giống secret, commit bị chặn." >&2
  exit 1
fi
EOF
chmod +x .git/hooks/pre-commit
printf 'payment.api-key=pay_live_Rt5Wz8Kd3Nq1\n' > src/main/resources/application-staging.properties
git add src/main/resources/application-staging.properties
git commit -m "Cấu hình staging"; echo "exit=$?"
```

</Terminal>


<Reveal title="Vì sao không sửa IDOR bằng @PreAuthorize như SB6.1?">

Có thể: `@PostAuthorize("returnObject.body?.owner == authentication.name")` kiểm sau khi method trả về. Nhưng nó vẫn đọc đơn của người khác lên bộ nhớ, trả 403 (lộ rằng đơn tồn tại), và không dùng được cho danh sách có phân trang: lọc sau khi đã lấy một trang 20 đơn sẽ cho ra trang thiếu. Đưa điều kiện chủ sở hữu vào truy vấn thì database chỉ trả đúng dữ liệu được phép, kể cả với `findAll(pageable)`. Dùng `@PreAuthorize` cho quy tắc theo role hay theo tham số, còn quyền theo dòng dữ liệu thì đặt trong truy vấn.

</Reveal>

<Reveal title="Biến môi trường có thực sự an toàn để chứa secret không?">

An toàn hơn code và Git, nhưng không kín. Bất kỳ ai `docker inspect` được container hay đọc được `/proc/<pid>/environ` đều thấy chúng; process con thừa hưởng chúng; một số công cụ báo lỗi gửi toàn bộ biến môi trường kèm crash report. Actuator endpoint `/actuator/env` của Spring Boot 3 trở đi mặc định che giá trị (`management.endpoint.env.show-values=never`), nhưng nhiều người bật lại khi gỡ lỗi rồi quên. File mount với quyền `600` hoặc vault giảm các rủi ro này, đổi lại vận hành phức tạp hơn.

</Reveal>

<Reveal title="Vault mang lại gì mà biến môi trường không có?">

Ba thứ: **secret động**, ví dụ Vault tạo cho mỗi instance một user PostgreSQL riêng sống 1 giờ rồi tự xoá, nên lộ cũng chỉ hại trong thời gian ngắn; **nhật ký truy cập**, biết service nào đọc secret nào lúc nào; và **xoay vòng tự động** không cần deploy lại. Spring Cloud Vault nạp secret vào `Environment` nên code vẫn chỉ thấy `@Value` như bài này. Cái giá là một hệ thống quan trọng phải chạy với độ sẵn sàng cao, vì Vault chết thì service không khởi động được.

</Reveal>

Nó là danh sách nhận thức, không phải tiêu chuẩn kiểm định: qua hết mười mục không có nghĩa là ứng dụng an toàn. Với việc kiểm tra có hệ thống, OWASP có ASVS (Application Security Verification Standard) với yêu cầu chi tiết theo cấp độ. Cách dùng Top 10 hiệu quả là biến mỗi mục thành một câu hỏi trong checklist review và một loại test tự động, như test IDOR với hai user, test token sai audience, test lỗi không lộ stack trace.

</Reveal>
