### Session và JWT

Sau khi đăng nhập, mỗi request tiếp theo phải chứng minh "tôi là người vừa đăng nhập". Có hai cách chính:

| | Session | JWT (JSON Web Token) |
|---|---|---|
| Trạng thái nằm ở | Server: bộ nhớ, Redis, database | Trong chính token, client giữ |
| Client gửi gì | Cookie `JSESSIONID`, một chuỗi ngẫu nhiên vô nghĩa | Header `Authorization: Bearer eyJ...` |
| Server kiểm tra bằng | Tra session id trong kho | Kiểm chữ ký bằng khoá công khai, đọc claim |
| Thu hồi ngay | Dễ: xoá session | Khó: token còn hạn là còn dùng được |
| Scale nhiều instance | Cần kho session chung hoặc sticky session | Mỗi instance tự kiểm, không cần chia sẻ gì |
| Hợp với | Web app server-rendered, BFF | API gọi từ SPA, mobile, service khác |

Một JWT gồm ba phần base64url nối bằng dấu chấm: `header.payload.signature`. Header ghi thuật toán ký (`alg`, ví dụ `RS256`) và mã khoá (`kid`). Payload chứa **claim**:

| Claim | Ý nghĩa | Resource server phải |
|---|---|---|
| `iss` | Ai phát hành | So khớp với issuer tin cậy |
| `sub` | Token nói về ai | Dùng làm danh tính ổn định |
| `aud` | Token dành cho API nào | Kiểm tra có tên API của mình |
| `exp`, `iat`, `nbf` | Hết hạn, phát hành, có hiệu lực từ | Từ chối token hết hạn |
| `scope`, `roles` | Quyền | Ánh xạ thành `GrantedAuthority` |

Payload chỉ được **ký**, không được **mã hoá**: ai cầm token cũng đọc được nội dung. Đừng để dữ liệu nhạy cảm trong claim.

Vì không thu hồi được ngay, access token nên sống ngắn (5 tới 15 phút) và đi kèm **refresh token** sống lâu hơn. Refresh token chỉ gửi tới authorization server, và server đó kiểm tra session mỗi lần đổi token, nên đăng xuất sẽ chặn được ở lần làm mới kế tiếp. Trong trình duyệt, token để ở `localStorage` thì bất kỳ đoạn script XSS nào cũng đọc được; nhiều đội chọn mẫu **BFF** (backend for frontend): server của frontend giữ token, trình duyệt chỉ có cookie session `HttpOnly`.

<Check id="j13.2.session-vs-jwt">So sánh được session với JWT về nơi giữ trạng thái, cách thu hồi và cách scale, và nói được vì sao access token nên sống ngắn.</Check>

### OAuth2, OIDC và vai trò resource server

**OAuth 2.0** là khung cấp quyền: thay vì đưa mật khẩu cho mọi ứng dụng, người dùng đăng nhập ở một **authorization server** (Keycloak, Auth0, Okta, Entra ID) và ứng dụng nhận về **access token** để gọi API thay mặt họ. **OpenID Connect (OIDC)** xây trên OAuth2, thêm **ID token** cho việc đăng nhập, endpoint `userinfo` và trang khám phá `/.well-known/openid-configuration`.

```text
 client (SPA, mobile, job)         authorization server (Keycloak)        resource server (orders API)
        |                                   |                                       |
        |-- 1. xin token (grant) ---------->|                                       |
        |<-- 2. access token (JWT ký RS256)-|                                       |
        |                                   |<-- 0. lúc khởi động hoặc lần đầu:     |
        |                                   |       tải discovery và JWKS (khoá     |
        |                                   |       công khai), rồi cache ----------|
        |-- 3. GET /api/me  Authorization: Bearer <token> ------------------------->|
        |                                   |       4. kiểm chữ ký bằng khoá đã     |
        |                                   |          cache, iss, exp, aud;        |
        |                                   |          không gọi Keycloak           |
        |<-- 5. 200 hoặc 401/403 ---------------------------------------------------|
```

| Grant type | Ai dùng | Ghi chú |
|---|---|---|
| Authorization code + PKCE | Ứng dụng có người dùng: web, SPA, mobile | Mặc định cho mọi ứng dụng mới |
| Client credentials | Service gọi service, job chạy nền | Không có người dùng; token mang danh tính của client |
| Refresh token | Client đã có refresh token | Lấy access token mới mà không đăng nhập lại |
| Password (resource owner) | Không nên dùng | Client thấy mật khẩu; bị loại khỏi OAuth 2.1. Lab này chỉ dùng để lấy token bằng `curl` |

API của bạn là **resource server**: nó không cấp token, không giữ mật khẩu. Nó chỉ kiểm tra token. Với Spring Boot, một dòng `issuer-uri` đủ để Spring tự tìm JWKS, kiểm chữ ký và `iss`, `exp`. Phần còn lại bạn phải tự khai báo: `audiences` để chỉ nhận token dành cho mình, và claim nào chứa quyền.

<Callout kind="production">

Một nhân viên nghỉ việc, quản trị viên khoá tài khoản trong Keycloak lúc 9:00. Access token cấp lúc 8:55 có hạn 1 giờ, nên tới 9:55 người đó vẫn gọi được API nội bộ. Không có lỗi nào ở đây: resource server kiểm token bằng khoá công khai và không hỏi lại Keycloak. Cách giảm rủi ro là giữ access token ngắn (bài này dùng 5 phút), và với thao tác nhạy cảm như chuyển tiền, gọi thêm endpoint introspection của authorization server để hỏi token còn hiệu lực không.

</Callout>

<Check id="j13.2.resource-server">Kể được bốn vai trò của OAuth2, chọn đúng grant type cho SPA và cho service nền, liệt kê được những gì resource server kiểm tra trên một JWT, và nói được request `/api/me`, `/web/notes` đi qua filter chain nào của lab.</Check>

### CORS: trình duyệt hỏi trước khi gửi

**Same-origin policy** (chính sách cùng nguồn) của trình duyệt chặn script ở `https://app.masteva.test` đọc response từ `http://localhost:20131`, vì khác **origin** (scheme, host, port). **CORS** (Cross-Origin Resource Sharing) là cách server nói "origin này được phép".

- Request "phức tạp" (có header `Authorization`, method `PUT`, `DELETE`, `Content-Type: application/json`) khiến trình duyệt gửi **preflight** trước: `OPTIONS` kèm `Origin`, `Access-Control-Request-Method`, `Access-Control-Request-Headers`.
- Server trả `Access-Control-Allow-Origin` và các header liên quan nếu cho phép. Không có header đó, trình duyệt không gửi request thật, hoặc không cho script đọc response.
- `Access-Control-Max-Age` cho trình duyệt cache kết quả preflight, bớt một vòng request.

CORS do **trình duyệt** thực thi để bảo vệ **người dùng**. Nó không bảo vệ API của bạn: `curl`, Postman, service khác không gửi preflight và không quan tâm header CORS. Đừng coi danh sách origin là một lớp xác thực. Và không bao giờ dùng `*` cùng với `allowCredentials`.

### CSRF: lợi dụng thứ trình duyệt tự gửi

**CSRF** (Cross-Site Request Forgery, giả mạo request liên trang): người dùng đang đăng nhập `admin.masteva.test` bằng cookie, rồi mở một trang độc hại. Trang đó có một form ẩn tự gửi `POST https://admin.masteva.test/web/notes`. Trình duyệt tự đính kèm cookie session, server tưởng chính người dùng gửi.

Cách chống của Spring là **synchronizer token**: server sinh một CSRF token gắn với session, trang thật nhúng token vào form hoặc header, request thay đổi dữ liệu phải kèm token. Trang độc hại không đọc được token (same-origin policy chặn), nên không giả được. Từ Spring Security 6, token gửi ra được trộn XOR với chuỗi ngẫu nhiên mỗi lần, để chống tấn công BREACH; vì vậy mỗi lần đọc bạn thấy một chuỗi khác.

| API của bạn xác thực bằng | Trình duyệt tự đính kèm? | CSRF |
|---|---|---|
| Cookie session | Có | Bật |
| HTTP Basic trong trình duyệt | Có, sau lần đầu | Bật |
| `Authorization: Bearer` do code JavaScript tự thêm | Không | Tắt được |

Cookie `SameSite=Lax` chặn phần lớn CSRF từ site khác. Lax làm mặc định khi cookie không ghi thuộc tính này là hành vi của các trình duyệt nhân Chromium (Chrome, Edge), không phải của mọi trình duyệt. Nên coi nó là lớp bảo vệ thêm, không thay cho CSRF token, và nó không chặn được trang độc hại trên một subdomain cùng site.

<Check id="j13.2.cors-csrf">Giải thích được CORS bảo vệ ai và không bảo vệ ai, CSRF lợi dụng điều gì, và khi nào được tắt CSRF.</Check>

### 2. Lấy token và đọc bên trong

Lấy access token cho alice bằng password grant, rồi giải mã header và payload. `JwtPeek` chỉ đọc, không kiểm chữ ký; nó dùng Jackson có sẵn trong `cp.txt` của SB6.1.

<Terminal where="mac" title="Tab 2">

```bash
cd ~/masteva-j13
cat > JwtPeek.java <<'EOF'
import java.util.Base64;
import tools.jackson.databind.SerializationFeature;
import tools.jackson.databind.json.JsonMapper;

/** In header và payload của một JWT. Không kiểm tra chữ ký: chỉ để đọc. */
public class JwtPeek {
    public static void main(String[] args) {
        String[] parts = args[0].split("\\.");
        JsonMapper json = JsonMapper.builder().enable(SerializationFeature.INDENT_OUTPUT).build();
        for (int i = 0; i < 2; i++) {
            String decoded = new String(Base64.getUrlDecoder().decode(parts[i]));
            System.out.println(json.writeValueAsString(json.readTree(decoded)));
        }
    }
}
EOF
token() {
  curl -s $KC/protocol/openid-connect/token -d grant_type=password -d client_id=orders-cli \
    -d username=$1 -d password=$1-pass | sed -E 's/.*"access_token":"([^"]+)".*/\1/'
}
TOKEN=$(token alice)
java -cp "$(cat cp.txt)" JwtPeek.java "$TOKEN"
```

</Reveal>

<Reveal title="Keycloak xoay khoá ký thì API có phải khởi động lại không?">

Không. Mỗi token mang `kid` trong header. Khi gặp một `kid` chưa có trong cache, Spring tải lại JWKS từ `jwks_uri` rồi kiểm tiếp. Authorization server thường công bố khoá mới trước khi dùng, và giữ khoá cũ trong JWKS cho tới khi token ký bằng nó hết hạn, nên quá trình xoay vòng không làm rơi request nào.

</Reveal>

<Reveal title="Vì sao dùng preferred_username làm tên lại cần cẩn thận?">

`sub` là định danh ổn định do Keycloak cấp, không bao giờ đổi. `preferred_username` dễ đọc hơn nhưng có thể đổi nếu realm cho phép người dùng sửa username (realm `masteva` không cho, đây là mặc định). Nếu bạn lưu chủ sở hữu dữ liệu theo username rồi một người đổi username trùng với người cũ, dữ liệu của người cũ lộ sang người mới. Với hệ thống thật, lưu `sub` làm khoá; username chỉ để hiển thị.

</Reveal>

<Reveal title="SPA nên giữ access token ở đâu?">

Trong bộ nhớ JavaScript thì mất khi tải lại trang; trong `localStorage` thì script XSS đọc được; trong cookie thường thì quay lại bài toán CSRF. Hướng dẫn hiện tại của IETF cho ứng dụng trình duyệt (bản nháp "OAuth 2.0 for Browser-Based Applications") nghiêng về mẫu BFF: một server nhỏ cùng origin với SPA làm OAuth client, giữ token ở server, và trình duyệt chỉ có cookie session `HttpOnly`, `Secure`, `SameSite`. Khi đó bật lại CSRF cho các route của BFF.

</Reveal>

AI hay khuyên `allowedOrigins("*")` kèm `allowCredentials(true)` (Spring sẽ báo lỗi), hay tắt CSRF cho cả ứng dụng dùng session, hay bỏ qua kiểm tra audience, và thường dán JWT thật vào câu hỏi. Đừng dán token còn hạn vào bất kỳ công cụ nào; dùng `JwtPeek` của bài này. Kiểm tra lại cấu hình bằng các lệnh ở bước 5, 7 và 8.
