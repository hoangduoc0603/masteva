### Hai mô hình phục vụ request

Spring MVC (J11.3) theo mô hình **thread-per-request**: mỗi request chiếm một thread từ đầu tới cuối, kể cả lúc chờ database hay đối tác. Spring WebFlux theo mô hình **event loop**: vài thread cố định xử lý mọi kết nối; code không bao giờ chờ, mà đăng ký "khi có dữ liệu thì làm tiếp việc này".

```text
 Spring MVC + virtual thread                     Spring WebFlux (Netty)
 ---------------------------                     ----------------------
 request 1 -> VT#1: đọc DB ... chờ ... trả lời   reactor-http-nio-1 ┐ nhận req 1, gửi lời gọi đối tác, nhả thread
 request 2 -> VT#2: gọi đối tác ... chờ ...      reactor-http-nio-2 │ nhận req 2, ...
 ...                                             ...                │ (số event loop = số nhân CPU, tối thiểu 4)
 request N -> VT#N                               reactor-http-nio-10┘ đối tác trả lời req 1 -> ghi response
 chờ = virtual thread unmount, carrier rảnh       chờ = không có thread nào bị giữ
```

Cả hai đều phục vụ được hàng nghìn request đang chờ I/O. Khác nhau ở chỗ ai trả giá: virtual thread để JVM lo việc nhả thread (J14.3), code vẫn viết tuần tự; event loop bắt chính code của bạn không được chặn.

### Mono, Flux và quy tắc không chặn

WebFlux dựa trên **Project Reactor**. Handler không trả `Order` mà trả một **publisher**, lời hứa sẽ phát ra dữ liệu:

| Kiểu | Phát ra | Ví dụ trong lab |
|---|---|---|
| `Mono<T>` | 0 hoặc 1 phần tử, hoặc lỗi | `Mono<Order> get(id)`, rỗng thì thành `404` |
| `Flux<T>` | 0 tới N phần tử, có thể vô hạn | `Flux<Order> list()`, stream server-sent events |

Publisher **lười**: tạo `Mono` chưa làm gì cả; chỉ khi có người **subscribe** (ở đây là WebFlux, lúc ghi response) thì chuỗi `map`, `flatMap` mới chạy. `flatMap` nối một bước bất đồng bộ khác, như lời gọi `WebClient` tới đối tác.

Quy tắc sống còn: **không chặn thread event loop**. Chỉ có khoảng 10 thread cho mọi kết nối; một thread ngủ 200 ms là một phần mười năng lực của cả server đứng yên. Mọi thứ trên đường đi phải non-blocking: `WebClient` thay cho `RestClient`, R2DBC thay cho JDBC, driver reactive cho Redis, Kafka. Reactor tự phát hiện một trường hợp, `block()` trên event loop, và ném lỗi; các lời gọi chặn khác như JDBC thì nó không thấy.

<Callout kind="production">

Một đội viết API gateway bằng WebFlux, rồi thêm một bước kiểm tra quyền gọi thư viện JDBC có sẵn. Thử một người thì nhanh. Khi tải lên, độ trễ mọi endpoint tăng vọt dù CPU chỉ 15%: 10 event loop thread đều đang chờ database, và hàng nghìn kết nối khác xếp hàng sau chúng. Thread dump cho thấy toàn bộ thread `reactor-http-nio-*` nằm trong code JDBC. Cách sửa là đưa lời gọi chặn sang `Schedulers.boundedElastic()` hoặc đổi sang driver reactive, và chạy BlockHound trong test để bắt lỗi này trước khi lên production (trên JDK 13+, JVM chạy test cần thêm `-XX:+AllowRedefinitionToAddDeleteMethods`).

</Callout>

### Quarkus và Micronaut: làm DI lúc build

Spring nối bean **lúc chạy**: quét classpath, đọc annotation bằng reflection, tạo proxy (J11.1). Quarkus và Micronaut dời phần lớn việc đó về **lúc build**:

| | Spring Boot | Quarkus | Micronaut |
|---|---|---|---|
| Nối bean | Lúc chạy, reflection | Lúc build: plugin Maven phân tích và sinh bytecode (ArC, theo CDI) | Lúc biên dịch: annotation processor sinh sẵn định nghĩa bean; bean được tạo khi lần đầu cần |
| Thiếu bean lộ ra khi | Khởi động ứng dụng | `mvn package`: build hỏng với `UnsatisfiedResolutionException` | Chạy, lúc bean được cần lần đầu: `NoSuchBeanException` |
| API web | Spring MVC, WebFlux | Jakarta REST (`@Path`, `@GET`) trên Vert.x | API riêng giống Spring (`@Controller`, `@Get`) trên Netty |
| Chọn thread | MVC: thread-per-request; WebFlux: event loop | Theo kiểu trả về: kiểu thường chạy worker thread, `Uni`/`Multi` chạy event loop, `@RunOnVirtualThread` cho virtual thread | Event loop mặc định, `@ExecuteOn` để chuyển sang pool khác |
| Native image | Có, qua Spring AOT | Trọng tâm thiết kế từ đầu | Trọng tâm thiết kế từ đầu |
| Hệ sinh thái | Lớn nhất | Lớn, do Red Hat hậu thuẫn | Nhỏ hơn |

Lab dùng Quarkus vì có dịch vụ sinh project gọi được bằng `curl` như start.spring.io, và có module tương thích một phần API Spring (`quarkus-spring-web`, `quarkus-spring-di`) giúp chuyển dần. Micronaut có ý tưởng gần giống: annotation processor sinh sẵn định nghĩa bean khi `javac` chạy, nên không cần quét classpath hay reflection lúc khởi động; nhưng thiếu bean vẫn chỉ lộ ra lúc chạy (`NoSuchBeanException`), vì bean mặc định được tạo khi lần đầu cần. Quarkus thì kiểm mọi điểm inject lúc `mvn package`: thiếu bean là build hỏng với `UnsatisfiedResolutionException`.

Cái được: khởi động nhanh và tốn ít bộ nhớ hơn, vì công việc đã làm ở máy build. Cái mất: đội phải học API và cách gỡ lỗi mới; thư viện dựa vào reflection lúc chạy cần extension hoặc cấu hình riêng; tài liệu, câu trả lời trên mạng và người tuyển được ít hơn Spring.

### 2. Đối tác chậm và công cụ đo tải

`Downstream` giả lập một dịch vụ tính thuế mất 200 ms mỗi lời gọi. `Load` gửi nhiều request đồng thời và in thông lượng, độ trễ p50, p99. Cả hai chỉ dùng JDK.

<Terminal where="mac" title="Tạo tools/Downstream.java và tools/Load.java">

```bash
mkdir -p ~/masteva-j11/alt/tools && cd ~/masteva-j11/alt/tools
cat > Downstream.java <<'EOF'
import com.sun.net.httpserver.HttpServer;
import java.net.InetSocketAddress;
import java.util.concurrent.Executors;

/** Đối tác tính thuế giả lập: mỗi lời gọi mất 200 ms. */
public class Downstream {
    public static void main(String[] args) throws Exception {
        // Mặc định HttpServer chỉ giữ 200 kết nối keep-alive rảnh và đóng bớt phần dư.
        System.setProperty("sun.net.httpserver.maxIdleConnections", "1000");
        var server = HttpServer.create(new InetSocketAddress(20302), 1000);
        server.setExecutor(Executors.newVirtualThreadPerTaskExecutor());
        server.createContext("/tax", exchange -> {
            long amount = Long.parseLong(exchange.getRequestURI().getQuery().replace("amount=", ""));
            try { Thread.sleep(200); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
            byte[] body = ("{\"tax\":" + amount / 10 + "}").getBytes();
            exchange.getResponseHeaders().set("Content-Type", "application/json");
            exchange.sendResponseHeaders(200, body.length);
            try (var out = exchange.getResponseBody()) { out.write(body); }
        });
        server.start();
        System.out.println("Downstream chạy ở cổng 20302, mỗi lời gọi chậm 200 ms");
    }
}
EOF
cat > Load.java <<'EOF'
import java.net.URI;
import java.net.http.*;
import java.util.Arrays;
import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

/** java Load.java <url> <tổng số request> <số request đồng thời> */
public class Load {
    public static void main(String[] args) throws Exception {
        var request = HttpRequest.newBuilder(URI.create(args[0])).build();
        int total = Integer.parseInt(args[1]), concurrency = Integer.parseInt(args[2]);
        var client = HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1).build();
        var permits = new Semaphore(concurrency);
        var errors = new AtomicInteger();
        long[] latencies = new long[total];
        long start = System.nanoTime();
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < total; i++) {
                int n = i;
                permits.acquire();
                executor.submit(() -> {
                    long t = System.nanoTime();
                    try {
                        if (client.send(request, HttpResponse.BodyHandlers.discarding()).statusCode() != 200) errors.incrementAndGet();
                    } catch (Exception e) {
                        errors.incrementAndGet();
                    } finally {
                        latencies[n] = (System.nanoTime() - t) / 1_000_000;
                        permits.release();
                    }
                });
            }
        }
        double seconds = (System.nanoTime() - start) / 1e9;
        Arrays.sort(latencies);
        System.out.printf("%d request, %d đồng thời: %.2f s, %.0f req/s, p50 %d ms, p99 %d ms, lỗi %d%n", total, concurrency,
                seconds, total / seconds, latencies[total / 2], latencies[total * 99 / 100], errors.get());
    }
}
EOF
```

```bash
package dev.masteva.flux;

import java.net.URI;
import java.util.Comparator;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;
import org.slf4j.*;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.reactive.function.client.WebClient;
import org.springframework.web.server.ResponseStatusException;
import reactor.core.publisher.Flux;
import reactor.core.publisher.Mono;

@RestController
@RequestMapping("/v1/orders")
class OrderController {
    private static final Logger log = LoggerFactory.getLogger(OrderController.class);

    record Order(long id, String customer, long amount, String currency) {}
    record CreateOrder(String customer, long amount, String currency) {}
    record Tax(long tax) {}
    record Quote(long id, long amount, long tax, long total) {}

    private final Map<Long, Order> orders = new ConcurrentHashMap<>();
    private final AtomicLong nextId = new AtomicLong(1);
    private final WebClient partner;

    OrderController(@Value("${partner.url}") String partnerUrl) {
        this.partner = WebClient.create(partnerUrl);
    }

    @PostMapping
    Mono<ResponseEntity<Order>> create(@RequestBody Mono<CreateOrder> body) {
        return body.map(b -> {
            var order = new Order(nextId.getAndIncrement(), b.customer(), b.amount(), b.currency());
            orders.put(order.id(), order);
            return ResponseEntity.created(URI.create("/v1/orders/" + order.id())).body(order);
        });
    }

    @GetMapping
    Flux<Order> list() {
        return Flux.fromIterable(orders.values()).sort(Comparator.comparingLong(Order::id));
    }

    @GetMapping("/{id}")
    Mono<Order> get(@PathVariable long id) {
        return find(id);
    }

    /** Gọi đối tác chậm 200 ms mà không giữ thread nào trong lúc chờ. */
    @GetMapping("/{id}/quote")
    Mono<Quote> quote(@PathVariable long id) {
        log.info("quote {}: nhận request trên {}", id, Thread.currentThread().getName());
        return find(id)
                .flatMap(o -> partner.get().uri("/tax?amount={a}", o.amount())
                        .retrieve().bodyToMono(Tax.class)
                        .map(t -> new Quote(o.id(), o.amount(), t.tax(), o.amount() + t.tax())))
                .doOnNext(q -> log.info("quote {}: có thuế trên {}", id, Thread.currentThread().getName()));
    }

    /** SAI: block() trên event loop. */
    @GetMapping("/{id}/quote-block")
    Quote quoteBlock(@PathVariable long id) {
        return quote(id).block();
    }

    /** SAI: lời gọi chặn 200 ms trên event loop, như JDBC hay một HTTP client đồng bộ. */
    @GetMapping("/{id}/quote-sleep")
    Mono<Quote> quoteSleep(@PathVariable long id) throws InterruptedException {
        Order o = orders.get(id);
        Thread.sleep(200);
        return Mono.just(new Quote(o.id(), o.amount(), o.amount() / 10, o.amount() + o.amount() / 10));
    }

    private Mono<Order> find(long id) {
        return Mono.justOrEmpty(orders.get(id))
                .switchIfEmpty(Mono.error(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "Không có đơn hàng " + id)));
    }
}
EOF
```

```bash
package dev.masteva.mvc;

import java.net.URI;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;
import org.slf4j.*;
import org.springframework.beans.factory.annotation.Value;
import org.springframework.http.HttpStatus;
import org.springframework.http.ResponseEntity;
import org.springframework.web.bind.annotation.*;
import org.springframework.web.client.RestClient;
import org.springframework.web.server.ResponseStatusException;

@RestController
@RequestMapping("/v1/orders")
class OrderController {
    private static final Logger log = LoggerFactory.getLogger(OrderController.class);

    record Order(long id, String customer, long amount, String currency) {}
    record CreateOrder(String customer, long amount, String currency) {}
    record Tax(long tax) {}
    record Quote(long id, long amount, long tax, long total) {}

    private final Map<Long, Order> orders = new ConcurrentHashMap<>();
    private final AtomicLong nextId = new AtomicLong(1);
    private final RestClient partner;

    OrderController(@Value("${partner.url}") String partnerUrl) {
        this.partner = RestClient.create(partnerUrl);
    }

    @PostMapping
    ResponseEntity<Order> create(@RequestBody CreateOrder b) {
        var order = new Order(nextId.getAndIncrement(), b.customer(), b.amount(), b.currency());
        orders.put(order.id(), order);
        return ResponseEntity.created(URI.create("/v1/orders/" + order.id())).body(order);
    }

    /** Cùng việc như bản WebFlux, viết tuần tự: thread chờ là virtual thread nên rẻ. */
    @GetMapping("/{id}/quote")
    Quote quote(@PathVariable long id) {
        log.info("quote {}: nhận request trên {}", id, Thread.currentThread());
        Order o = orders.get(id);
        if (o == null) throw new ResponseStatusException(HttpStatus.NOT_FOUND, "Không có đơn hàng " + id);
        Tax t = partner.get().uri("/tax?amount={a}", o.amount()).retrieve().body(Tax.class);
        log.info("quote {}: có thuế trên {}", id, Thread.currentThread());
        return new Quote(o.id(), o.amount(), t.tax(), o.amount() + t.tax());
    }
}
```

<Reveal title="Thông lượng ngang nhau, vậy khi nào WebFlux thật sự đáng?">

Khi việc chính là giữ rất nhiều kết nối sống lâu và đẩy dữ liệu theo dòng: API gateway, server-sent events, WebSocket, proxy streaming file lớn, nơi `Flux` với backpressure (người nhận báo mình nhận được bao nhiêu) là mô hình tự nhiên. Ở đó, chi phí mỗi kết nối và việc kiểm soát luồng dữ liệu quan trọng hơn sự dễ đọc. Với service CRUD gọi database và vài đối tác, MVC trên virtual thread cho cùng thông lượng như lab đã đo, giữ được code tuần tự, stack trace đọc được, `ThreadLocal` (MDC của log, security context) chạy như cũ, và dùng được JDBC. Nếu đội đã có sẵn code WebFlux chạy tốt thì cũng không cần viết lại.

</Reveal>

<Reveal title="Bắt buộc phải gọi một thư viện chặn trong WebFlux thì làm sao?">

Bọc nó và chuyển sang scheduler dành cho việc chặn: `Mono.fromCallable(() -> jdbcRepo.find(id)).subscribeOn(Schedulers.boundedElastic())`. `boundedElastic` là pool có giới hạn số thread và hàng đợi, nên nó cũng là chỗ tải bị dồn lại; nếu phần lớn request đều cần nó, bạn đang trả giá của WebFlux mà không được lợi gì. Để không lọt lời gọi chặn lên event loop, thêm BlockHound (một Java agent của dự án Reactor) vào test: nó ném lỗi khi phát hiện `Thread.sleep` hay I/O chặn trên thread non-blocking, bắt được cả trường hợp `quote-sleep` mà Reactor không tự thấy. Trên JDK 13+, JVM chạy test cần thêm `-XX:+AllowRedefinitionToAddDeleteMethods`; bài này chưa chạy BlockHound.

</Reveal>

<Reveal title="125 thread HttpClient-* trong bản MVC từ đâu ra?">

`RestClient.create()` dùng `java.net.http.HttpClient` của JDK khi không có thư viện HTTP nào khác trên classpath. HttpClient đó mặc định có executor riêng là một cached thread pool gồm platform thread, dùng để hoàn tất các bước bất đồng bộ bên trong; dưới tải nó nở ra hàng trăm thread dù Tomcat đã chạy virtual thread. Truyền vào một HttpClient dùng virtual thread: `RestClient.builder().baseUrl(url).requestFactory(new JdkClientHttpRequestFactory(HttpClient.newBuilder().executor(Executors.newVirtualThreadPerTaskExecutor()).build())).build()`. Khi thử cách này với cùng hai lượt tải, số platform thread sau tải giảm từ khoảng 180 xuống 54, thông lượng không đổi. Bài học chung: bật virtual thread rồi vẫn phải xem thread dump (J14.3) để biết thư viện nào tự tạo pool.

</Reveal>

<Reveal title="WebClient có giới hạn số kết nối tới đối tác không?">

Có. `WebClient.create()` dùng pool kết nối chung của Reactor Netty; kiểm bằng `HttpResources.get().maxConnections()` trong jshell với classpath của project cho ra 500. Vượt quá 500 lời gọi đồng thời tới đối tác thì phần dư phải chờ kết nối rảnh, và độ trễ tăng theo. Theo mặc định của Reactor Netty, số lời gọi chờ kết nối có giới hạn (gấp đôi số kết nối tối đa, tức 1.000) và mỗi lời gọi chờ có timeout 45 giây; vượt nữa thì lỗi ngay. Giới hạn này là điều tốt: nó bảo vệ đối tác. Nhưng nó phải được chọn có chủ ý qua `ConnectionProvider`, cùng với thời gian giữ kết nối rảnh ngắn hơn timeout keep-alive của đối tác, để tránh lỗi `Connection reset` như phần gỡ lỗi. MVC trên virtual thread cần giới hạn tương tự bằng `Semaphore` hoặc pool của HTTP client.

</Reveal>

<Reveal title="Quarkus nhanh hơn 0,8 giây, có đáng đổi framework không?">

Với service chạy liên tục nhiều ngày trên Kubernetes, 0,8 giây lúc khởi động gần như không đáng kể, còn 80 MB mỗi pod chỉ đáng khi bạn chạy hàng trăm pod. Nó đáng khi khởi động nằm trên đường đi của người dùng: serverless scale từ 0, job ngắn chạy theo lịch, CLI, hoặc khi bộ nhớ là chi phí chính. Trước khi đổi, hãy đo trên ứng dụng thật của bạn với đủ dependency (database, security), vì khoảng cách trong lab đến từ một endpoint rỗng. Trong hệ Spring cũng có các hướng rút ngắn khởi động mà không đổi framework: Spring AOT với native image (J17.4), hoặc AOT cache của JDK. Đổi framework là quyết định về con người và hệ sinh thái nhiều hơn là về con số.

</Reveal>

<Callout kind="ai">

Kiểm tra bằng log tên thread như bước 3, bằng BlockHound trong test, và bằng phép đo của chính bạn như bước 5 và 7.
