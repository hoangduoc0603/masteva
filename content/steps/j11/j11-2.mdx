<Goal>

Chạy cùng một file jar ở máy bạn, ở staging và trên production, chỉ khác nhau ở cấu hình bên ngoài. Học xong bài này, bạn đọc cấu hình bằng một record có kiểu, biết giá trị nào thắng khi nhiều nguồn cùng đặt một khoá, và giải thích được:

- Vì sao sửa `application.properties` mà ứng dụng trên server vẫn dùng giá trị cũ.
- Vì sao gõ nhầm tên profile không làm ứng dụng báo lỗi, và vì sao đó là chuyện nguy hiểm.
- Vì sao cấu hình sai nên làm service chết ngay lúc khởi động thay vì chạy tiếp.

</Goal>

<Knowledge>

### Vì sao cấu hình nằm ngoài code

Cùng một bản build phải chạy được ở nhiều môi trường. Thứ khác nhau giữa chúng là **cấu hình**: địa chỉ database, hạn mức, mức log, khoá API. Nếu cấu hình nằm trong code, mỗi môi trường cần một bản build riêng, và bản bạn test không phải bản chạy trên production.

| Loại | Ví dụ | Đặt ở đâu |
|---|---|---|
| Mặc định hợp lý | Kích thước trang 20, timeout thanh toán 15 phút | Trong code (`@DefaultValue`) hoặc `application.properties` |
| Khác theo môi trường | Hạn mức đơn, mức log, URL dịch vụ khác | File theo profile, biến môi trường |
| Bí mật | Mật khẩu database, khoá API thanh toán | Biến môi trường hoặc secret manager, **không bao giờ** trong Git |

### Nguồn cấu hình và thứ tự ưu tiên

Spring Boot gom mọi nguồn vào một `Environment`. Khi nhiều nguồn cùng đặt một khoá, nguồn đứng cao hơn thắng. Các nguồn hay dùng, từ cao xuống thấp:

```text
  cao   --orders.max-amount=3000000            tham số dòng lệnh
   |    -Dorders.max-amount=...                Java system property
   |    ORDERS_MAXAMOUNT=2000000               biến môi trường của hệ điều hành
   |    application-dev.properties cạnh jar    file theo profile, ngoài jar
   |    application.properties cạnh jar        file chung, ngoài jar
   |    application-dev.properties trong jar   file theo profile, đóng gói sẵn
   |    application.properties trong jar       file chung, đóng gói sẵn
  thấp  @DefaultValue("20") trong code         giá trị mặc định
```

File cạnh jar, kể cả file chung, thắng mọi file trong jar. Trong cùng một vị trí (cùng cạnh jar hoặc cùng trong jar), file theo profile mới thắng file chung.

Quy tắc dễ nhớ: càng gần lúc chạy thì càng ưu tiên. File trong jar là mặc định của đội phát triển; biến môi trường do người vận hành đặt cho từng môi trường; tham số dòng lệnh dùng để ghi đè tạm thời.

<Callout kind="production">

Một đội sửa `orders.max-amount` trong `application.properties`, build, deploy, nhưng hạn mức trên production không đổi. Nguyên nhân: manifest Kubernetes đặt biến môi trường `ORDERS_MAXAMOUNT` từ nhiều tháng trước, và biến môi trường thắng file trong jar. Khi một giá trị "không chịu đổi", đừng đoán: hỏi chính ứng dụng xem giá trị đó đến từ nguồn nào, như bạn sẽ làm với `/actuator/configprops` trong lab.

</Callout>

<Check id="j11.2.precedence">Xếp được thứ tự ưu tiên giữa tham số dòng lệnh, biến môi trường, file theo profile, file chung và giá trị mặc định.</Check>

### Relaxed binding và định dạng file

Cùng một khoá được viết khác nhau tuỳ nguồn; Spring Boot gọi việc ánh xạ giữa chúng là **relaxed binding**:

| Nguồn | Cách viết `orders.max-amount` |
|---|---|
| `.properties`, `.yaml`, tham số dòng lệnh | `orders.max-amount` (kebab-case, dạng khuyên dùng) |
| Biến môi trường | `ORDERS_MAXAMOUNT`: thay `.` bằng `_`, bỏ `-`, viết hoa |
| Field trong Java | `maxAmount` |

`application.yaml` và `application.properties` tương đương nhau; YAML gom khoá theo cấp nên dễ đọc khi cấu hình dài:

```yaml
orders:
  currency: VND
  max-amount: 50000000
```

Chọn một định dạng cho cả project. Nếu cùng thư mục có cả hai file và cả hai đặt một khoá, file `.properties` thắng; khoá chỉ có trong file `.yaml` vẫn được dùng. Hai file trộn vào nhau như vậy rất khó đọc.

### Profile

**Profile** là tên một nhóm cấu hình, ví dụ `dev`, `staging`, `prod`. Khi profile `dev` bật:

- `application-dev.properties` được nạp thêm và ghi đè các khoá trùng trong `application.properties`.
- Bean gắn `@Profile("dev")` được tạo; khi profile tắt, bean đó không tồn tại.

Bật profile bằng `--spring.profiles.active=dev` hoặc biến môi trường `SPRING_PROFILES_ACTIVE=dev`. Không bật gì thì Spring Boot dùng profile `default`.

<Callout kind="pitfall">

Spring Boot không kiểm tra tên profile. `--spring.profiles.active=deev` vẫn khởi động bình thường, log ghi `The following 1 profile is active: "deev"`, và vì không có `application-deev.properties`, ứng dụng chạy bằng giá trị mặc định. Với `prod`, gõ nhầm có thể nghĩa là production chạy với hạn mức và mức log của máy phát triển. Đọc dòng log profile mỗi lần deploy, và đặt các giá trị bắt buộc của production sao cho thiếu là ứng dụng không khởi động.

</Callout>

<Check id="j11.2.profiles">Giải thích được profile ảnh hưởng tới file cấu hình và bean ra sao, và bật được một profile bằng tham số dòng lệnh hoặc biến môi trường.</Check>

### @ConfigurationProperties thay cho @Value rải rác

`@Value("${orders.max-amount}")` đọc một khoá vào một field. Khi có hàng chục khoá, chúng rải khắp các class, mỗi chỗ tự chuyển kiểu, và không ai biết service có những cấu hình nào. `@ConfigurationProperties` gom một nhóm khoá cùng tiền tố vào một class:

```java
@ConfigurationProperties("orders")
@Validated
public record OrdersProperties(
        @NotBlank @Pattern(regexp = "[A-Z]{3}") @DefaultValue("VND") String currency,
        @Positive long maxAmount,
        @Min(1) @Max(100) @DefaultValue("20") int pageSize,
        @NotNull @DefaultValue("15m") Duration paymentTimeout,
        @NotBlank @Email String supportEmail) {}
```

| | `@Value` | `@ConfigurationProperties` |
|---|---|---|
| Phạm vi | Một khoá | Một nhóm khoá cùng tiền tố |
| Chuyển kiểu | Có, cho từng chỗ | Có, kể cả `Duration` (`15m`), `DataSize` (`10MB`), list, map, object lồng nhau |
| Validation | Không | `@Validated` kèm annotation Jakarta Validation |
| Relaxed binding | Hạn chế; nên viết đúng dạng kebab-case | Đầy đủ |
| Xem được qua Actuator | Không | `/actuator/configprops` cho biết giá trị và nguồn của từng khoá |

Record là bất biến: cấu hình được đọc một lần lúc khởi động và không đổi sau đó, đúng với cách nó được dùng. Đăng ký record bằng `@EnableConfigurationProperties(OrdersProperties.class)` trên một class `@Configuration`, rồi inject `OrdersProperties` như mọi bean khác.

Với `@Validated`, cấu hình sai làm ứng dụng **không khởi động được** và in rõ khoá nào sai, giá trị gì, đến từ đâu. Đây là điều bạn muốn: một service chết ngay khi deploy thì Kubernetes giữ lại phiên bản cũ đang chạy tốt; một service chạy với hạn mức âm thì gây lỗi lúc nửa đêm.

<Callout kind="production">

Endpoint `/actuator/env` và `/actuator/configprops` cho thấy mọi khoá cấu hình, kể cả mật khẩu database nếu nó được truyền qua biến môi trường. Từ Spring Boot 3, giá trị mặc định bị che thành `******` (`show-values=never`), và chỉ `health` được mở qua HTTP. Lab này chỉ mở thêm endpoint và hiện giá trị trong profile `dev`. Trên production, chỉ mở những endpoint thật sự cần, đặt chúng sau xác thực hoặc trên một cổng quản trị riêng, và để `show-values` ở mặc định.

</Callout>

### 1. Record cấu hình, file chung và file dev

Tạo `OrdersProperties`, đăng ký nó trong `AppConfig`, và viết lại `StartupReport` để chỉ chạy ở profile `dev` và in cấu hình đang dùng. `application.properties` giờ chỉ mở `health`; các endpoint quan sát chuyển sang `application-dev.properties`.

<Terminal where="mac" title="Tạo OrdersProperties, sửa AppConfig, StartupReport và cấu hình">

```bash
cd ~/masteva-j11/orders
P=src/main/java/dev/masteva/orders
mkdir -p $P/config
cat > $P/config/OrdersProperties.java <<'EOF'
package dev.masteva.orders.config;

import jakarta.validation.constraints.Email;
import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import jakarta.validation.constraints.Pattern;
import jakarta.validation.constraints.Positive;
import java.time.Duration;
import org.springframework.boot.context.properties.ConfigurationProperties;
import org.springframework.boot.context.properties.bind.DefaultValue;
import org.springframework.validation.annotation.Validated;

/** Cấu hình nghiệp vụ của service, bind từ các khoá orders.* */
@ConfigurationProperties("orders")
@Validated
public record OrdersProperties(
        @NotBlank @Pattern(regexp = "[A-Z]{3}") @DefaultValue("VND") String currency,
        @Positive long maxAmount,
        @Min(1) @Max(100) @DefaultValue("20") int pageSize,
        @NotNull @DefaultValue("15m") Duration paymentTimeout,
        @NotBlank @Email String supportEmail) {
}
EOF
cat > $P/AppConfig.java <<'EOF'
package dev.masteva.orders;

import dev.masteva.orders.config.OrdersProperties;
import java.time.Clock;
import java.time.ZoneId;
import org.springframework.boot.context.properties.EnableConfigurationProperties;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
@EnableConfigurationProperties(OrdersProperties.class)
public class AppConfig {
    /** Clock là class của JDK, không gắn @Component được, nên khai báo bằng @Bean. */
    @Bean
    Clock clock() {
        return Clock.system(ZoneId.of("Asia/Ho_Chi_Minh"));
    }
}
EOF
cat > $P/StartupReport.java <<'EOF'
package dev.masteva.orders;

import dev.masteva.orders.config.OrdersProperties;
import dev.masteva.orders.order.OrderService;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.boot.ApplicationArguments;
import org.springframework.boot.ApplicationRunner;
import org.springframework.context.annotation.Profile;
import org.springframework.stereotype.Component;

/** Chỉ có ở profile dev: in cấu hình đang dùng để kiểm tra nhanh khi phát triển. */
@Component
@Profile("dev")
class StartupReport implements ApplicationRunner {
    private static final Logger log = LoggerFactory.getLogger(StartupReport.class);
    private final OrderService orderService;
    private final OrdersProperties props;

    StartupReport(OrderService orderService, OrdersProperties props) {
        this.orderService = orderService;
        this.props = props;
    }

    @Override
    public void run(ApplicationArguments args) {
        log.info("cấu hình: {}", props);
        log.info("quote(300000): {}", orderService.quote(300_000));
    }
}
EOF
cat > src/main/resources/application.properties <<'EOF'
spring.application.name=orders
server.port=20110
management.endpoints.web.exposure.include=health

orders.currency=VND
orders.max-amount=50000000
orders.support-email=support@example.com
EOF
cat > src/main/resources/application-dev.properties <<'EOF'
orders.max-amount=5000000
orders.payment-timeout=2m
logging.level.dev.masteva.orders=DEBUG
management.endpoints.web.exposure.include=health,beans,conditions,configprops,env
management.endpoint.configprops.show-values=always
management.endpoint.env.show-values=always
EOF
```

</Terminal>

`maxAmount` và `supportEmail` không có `@DefaultValue`: thiếu chúng thì ứng dụng không khởi động. `payment-timeout=2m` là một `Duration`; Spring Boot hiểu các đơn vị `ns`, `us`, `ms`, `s`, `m`, `h`, `d`. Ở profile `dev`, hạn mức đơn nhỏ hơn để dễ thử, và log của package `dev.masteva.orders` bật mức DEBUG.

### Khi gặp lỗi

<Callout kind="pitfall">

- `Binding to target ... failed ... Property: orders.maxAmount ... must be greater than 0` ngay cả khi không truyền gì: `application.properties` thiếu dòng `orders.max-amount`. Khoá này không có giá trị mặc định nên sẽ là `0`.
- `/actuator/configprops/orders` trả `404`: ứng dụng không chạy ở profile `dev`. Xem dòng log `The following 1 profile is active`.
- Mọi giá trị hiện `******`: thiếu `management.endpoint.configprops.show-values=always` trong file dev, hoặc file dev không được nạp.
- Biến môi trường không có tác dụng: tên sai quy tắc. `ORDERS_MAX_AMOUNT` cũng bind được, nhưng dạng chuẩn là `ORDERS_MAXAMOUNT`. Kiểm tra bằng `configprops` thay vì `/actuator/env/orders.max-amount`: ở Spring Boot 4.1.1, endpoint `env` tra theo tên từng nguồn nên không thấy biến `ORDERS_MAXAMOUNT`, và báo nhầm rằng giá trị đến từ file, dù ứng dụng thực ra dùng giá trị của biến môi trường.

</Callout>

<DeepDive>

<Reveal title="Mật khẩu database đặt ở đâu nếu không phải application.properties?">

Trong Git chỉ để tên khoá, không để giá trị. Lúc chạy, giá trị đến từ biến môi trường do hệ thống deploy đặt (Kubernetes Secret gắn vào pod dưới dạng biến môi trường hoặc file), hoặc từ một secret manager như Vault hay AWS Secrets Manager qua `spring.config.import`. Ở máy phát triển, dùng file `.env` hoặc `application-local.properties` đã có trong `.gitignore`. Kể cả khi đã làm đúng, secret vẫn có thể lộ qua log (in cả object cấu hình như `StartupReport` làm), qua `/actuator/env`, hoặc qua heap dump; đừng in record chứa secret, hoặc ghi đè `toString()` của nó.

</Reveal>

<Reveal title="Có nên có profile prod với đầy đủ cấu hình production trong repo?">

Có hai trường phái. Một là `application-prod.properties` nằm trong repo, chứa các giá trị không bí mật của production; ưu điểm là review được qua pull request. Hai là repo chỉ có mặc định an toàn, còn mọi khác biệt của môi trường nằm ở hạ tầng (Helm values, biến môi trường); ưu điểm là một bản build không biết gì về nơi nó chạy. Cách nào cũng được, miễn là nhất quán và giá trị bắt buộc không có mặc định nguy hiểm. Điều nên tránh là trộn cả hai, khiến không ai biết giá trị thật nằm ở đâu.

</Reveal>

<Reveal title="Đổi cấu hình mà không khởi động lại có được không?">

Record `OrdersProperties` cố ý bất biến: cấu hình đọc một lần lúc khởi động. Spring Cloud có cơ chế refresh bean khi cấu hình đổi, nhưng nó kéo theo câu hỏi khó: request đang chạy dùng giá trị cũ hay mới, hai instance có giá trị khác nhau trong bao lâu. Với service chạy trên Kubernetes, cách đơn giản và dễ kiểm soát hơn là đổi cấu hình rồi rolling restart. Thứ thật sự cần bật tắt lúc chạy, như feature flag, nên dùng công cụ dành riêng cho việc đó.

</Reveal>

<Reveal title="IDE gợi ý khoá orders.* thế nào?">

Thêm dependency `spring-boot-configuration-processor` (scope `optional` hoặc dùng làm annotation processor). Lúc biên dịch, nó đọc các class `@ConfigurationProperties` và sinh `META-INF/spring-configuration-metadata.json`. IDE dùng file này để gợi ý khoá, hiện Javadoc của từng field và cảnh báo khoá không tồn tại trong `application.properties`.

</Reveal>

<Callout kind="ai">

Nhờ AI chuyển một loạt `@Value` sang một record `@ConfigurationProperties`, hoặc viết file cấu hình cho một môi trường mới. AI hay viết tên biến môi trường sai quy tắc relaxed binding, quên `@Validated`, dùng `@ConstructorBinding` (không cần cho record có một constructor), hoặc đưa ra khoá đã đổi tên ở Spring Boot 4. Kiểm tra bằng cách chạy ứng dụng với profile tương ứng và đọc `/actuator/configprops` ở môi trường dev.

</Callout>
