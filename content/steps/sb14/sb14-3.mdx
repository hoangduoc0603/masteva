<Goal>

Nâng một service Spring thật qua một bản major theo cách có kiểm soát: biết trước công cụ sẽ đổi gì, biết chính xác phần nào công cụ bỏ sót, và tìm ra cả những thứ nằm ngoài repo mà không công cụ đọc mã nguồn nào thấy được. Học xong, bạn giải thích được:

- Vì sao `mvn test` ngay sau khi chạy recipe không báo lỗi biên dịch, dù code vẫn dùng class đã bị xoá khỏi Spring Security 7.
- Vì sao app mobile cũ gọi `/api/products/` nhận `401 Unauthorized` sau khi nâng cấp, dù endpoint đó công khai.
- Vì sao bản deploy đặt `SERVER_SERVLET_ENCODING_FORCE=true` mà Spring Boot 4 không còn gắn charset vào response, và vì sao `spring-boot-properties-migrator` cứu được khoá này nhưng không cứu được `SERVER_ERROR_INCLUDE_MESSAGE`.

</Goal>

<Knowledge>

### J14.2 đã làm gì, bài này đi tiếp ở đâu

J14.2 đã nâng một service nhỏ (Web, JPA trên H2) từ Spring Boot 3.5 lên 4.1 cùng Java 21 lên 25: chạy recipe `UpgradeSpringBoot_4_0` bằng goal `run`, đọc diff, sửa cấu hình Jackson recipe bỏ sót, lên 4.1 bằng tay. Lịch hỗ trợ của từng dòng Spring Boot, `@MockBean` thành `@MockitoBean`, Jackson 3 và `jdeps` đều đã có ở đó.

Bài này giữ nguyên Java, chỉ đổi Spring Boot, trên một service có đủ các mảng hay vỡ khi lên Boot 4: Spring Security 7, Hibernate 7, Spring Framework 7, Flyway, Actuator, Testcontainers 2. Ba điểm mới: xem trước bằng `dryRun` trước khi cho công cụ sửa file; đo chính xác phần recipe không làm và vì sao; và tìm khoá cấu hình nằm ngoài repo.

### Chiến lược: mỗi bước một thứ thay đổi

```text
 3.5.x bản patch mới nhất, test xanh, commit
   │  biên dịch với showDeprecation: danh sách API sẽ biến mất ở 4.0
   v
 (nên làm) thay API deprecated bằng API mới ngay trên 3.5, test xanh, commit
   │
   v
 4.0.x bản patch mới nhất: dryRun -> đọc patch -> run -> clean test -> sửa tay -> commit
   │
   v
 4.1.x: đọc release notes, đổi số phiên bản, recipe khoá cấu hình 4.1 -> clean test -> commit
   │
   v
 staging: thêm spring-boot-properties-migrator, chạy với cấu hình deploy thật, sửa cấu hình, gỡ migrator
```

Vì sao không nhảy thẳng từ 3.5 lên 4.1: mỗi bước có tài liệu riêng (Migration Guide của 4.0, Release Notes của 4.1), có recipe riêng, và khi test đỏ bạn biết nó đỏ vì bước nào. Hướng dẫn chính thức của Spring Boot 4.0 yêu cầu lên bản 3.5.x mới nhất và dọn mọi lời gọi tới API deprecated trước, vì thứ deprecated ở 3.x bị xoá ở 4.0.

Bước "nên làm" có thể làm trên 3.5 vì API thay thế đều đã có ở đó: `@SQLRestriction` có từ Hibernate 6.3, Spring Security 6.x nhận `requestMatchers(String...)`, `UrlHandlerFilter` có từ Spring Framework 6.2. Lab cố ý bỏ qua bước này để đo xem recipe tự xử lý được bao nhiêu.

<Check id="sb14.3.strategy">Kể được thứ tự các bước nâng từ 3.5 lên 4.1 và giải thích vì sao dọn deprecation trên bản cũ và đi từng bản minor làm việc tìm lỗi dễ hơn.</Check>

### Recipe làm được gì

`UpgradeSpringBoot_4_0` trong `rewrite-spring` là một recipe gộp: nó gọi lại chuỗi recipe 2.x và 3.x (để project cũ hơn cũng đi được), rồi các recipe cho Spring Framework 7, Spring Security 7, Hibernate 7.1, Testcontainers 2, khoá cấu hình 4.0, starter dạng module của Boot 4. Lab đo được trên service `catalog`:

| Thay đổi cần có | Recipe tự làm | Ai bắt được nếu recipe bỏ sót |
|---|---|---|
| Parent lên bản 4.0.x mới nhất lúc chạy (4.0.8 khi viết bài), `spring-boot-starter-web` thành `-webmvc`, `flyway-core` thành `spring-boot-starter-flyway` | Có | Lỗi biên dịch, hoặc Flyway lặng lẽ không chạy |
| Testcontainers 2: artifact `testcontainers-postgresql`, class `org.testcontainers.postgresql.PostgreSQLContainer` | Có | Lỗi biên dịch test |
| `TestRestTemplate`: package mới, `@AutoConfigureTestRestTemplate`, dependency `spring-boot-resttestclient` | Có | Lỗi biên dịch test |
| `management.endpoints.enabled-by-default` thành `management.endpoints.access.default` | Có | Không ai: khoá cũ còn chạy ở 4.1 nhưng sẽ bị xoá |
| Dependency `spring-boot-restclient` mà `TestRestTemplate` cần lúc chạy | **Không** | Test: context không dựng được |
| `@Where` (đã xoá ở Hibernate 7) thành `@SQLRestriction` | **Không** | Lỗi biên dịch |
| `AntPathRequestMatcher` (đã xoá ở Spring Security 7) | **Không** | Lỗi biên dịch |
| `setUseTrailingSlashMatch` (đã xoá ở Spring Framework 7) và hành vi URL có dấu `/` cuối | **Không** | Lỗi biên dịch; xoá dòng đó cho qua thì chỉ test bắt được hành vi |
| Khoá cấu hình đặt trong biến môi trường, Helm values, config server | **Không** (recipe chỉ đọc file trong repo) | `spring-boot-properties-migrator` lúc chạy |

Kết quả này đúng với phiên bản recipe được ghim (`rewrite-spring` 6.37.1). Recipe được phát hành thường xuyên; bản sau có thể làm thêm. Đó là lý do luôn ghim phiên bản và ghi nó vào commit message. Cũng vì thế, đừng hỏi "recipe có xử lý X không": chạy `dryRun` và đọc patch.

Với 4.1, `rewrite-spring` 6.37.1 chỉ có `SpringBootProperties_4_1` (đổi khoá cấu hình). Trang tài liệu của recipe gộp "Migrate to Spring Boot 4.1" ghi "has moved to Moderne docs", và recipe đó không có trong `rewrite-spring` 6.37.1. (Lõi OpenRewrite theo Apache 2.0, còn `rewrite-spring` theo Moderne Source Available License, J14.2 đã nhắc.) Bước 4.0 lên 4.1 vì vậy là đổi số phiên bản bằng tay, đọc Release Notes, và chạy recipe khoá cấu hình.

<Check id="sb14.3.recipe-coverage">Phân loại được một thay đổi khi nâng cấp vào nhóm recipe làm được hay không, và nói được thứ gì sẽ bắt nó nếu recipe bỏ sót: trình biên dịch, test, hay migrator lúc chạy.</Check>

### Xem trước rồi mới sửa

OpenRewrite đọc mã nguồn thành cây LST (J14.2), chạy recipe trên cây, rồi in lại file. Goal `dryRun` dừng ở bước cuối: không sửa file nào, ghi toàn bộ thay đổi vào `target/rewrite/rewrite.patch`, và log cho biết recipe con nào sửa file nào. Đọc patch trước có hai lợi ích: thấy thay đổi nào cần người review kỹ (khoá cấu hình đổi ngữ nghĩa, dependency bị thay), và thấy file nào **không** có trong patch dù bạn biết nó dùng API đã bị xoá. Goal `run` áp đúng patch đó.

### Khoá cấu hình ngoài repo

Recipe sửa được `application.properties` và `application.yml` trong repo. Nhưng cấu hình production thường nằm ở chỗ khác: biến môi trường trong manifest Kubernetes, Helm values, Spring Cloud Config, tham số dòng lệnh trong script deploy. Khi Boot 4 đổi tên `server.servlet.encoding.force` thành `spring.servlet.encoding.force`, biến `SERVER_SERVLET_ENCODING_FORCE=true` trong manifest không còn ai đọc: không lỗi, không cảnh báo.

**`spring-boot-properties-migrator`** là module Spring Boot dành cho việc này. Thêm nó với scope `runtime`, lúc khởi động nó:

```text
 đọc metadata của mọi jar   ->  các khoá có "deprecation" kèm "replacement"
                                (level warning hay error đều tính; SB14.2 bàn cách thư viện để lại dấu vết này)
 duyệt MỌI property source   ->  application.properties, biến môi trường, tham số dòng lệnh...
 với mỗi khoá cũ tìm thấy:
   kiểu của khoá mới tương thích   ->  WARN "renamed", tạm ánh xạ giá trị sang khoá mới
   không tương thích / không có thay thế  ->  ERROR "no longer supported", không ánh xạ
```

Nó là công cụ chuyển tiếp: thêm khi nâng cấp, chạy ở staging với cấu hình thật, sửa cấu hình theo báo cáo, rồi gỡ ra. Để nó lại thì nó che đi việc cấu hình đã cũ, và mỗi lần khởi động tốn thêm công duyệt metadata.

<Check id="sb14.3.properties-migrator">Giải thích được vì sao recipe không thấy khoá cấu hình trong biến môi trường, `spring-boot-properties-migrator` tìm chúng thế nào, khi nào nó ánh xạ tạm được và khi nào không.</Check>

<Callout kind="production">

Một đội nâng service lên Boot 4, test xanh, staging ổn, deploy. Hai ngày sau, đội mobile báo app Android bản cũ hiện tên sản phẩm tiếng Việt thành chuỗi ký tự lạ. Thư viện HTTP của bản app đó đoán charset là ISO-8859-1 khi header `Content-Type` không ghi charset; manifest Kubernetes của service có `SERVER_SERVLET_ENCODING_FORCE=true` từ ba năm trước chính vì lỗi này, và Boot 4 không còn đọc khoá đó. Staging không có app bản cũ nên không ai thấy. Chạy một lần với `spring-boot-properties-migrator` và cấu hình deploy thật đã in đúng tên khoá này.

</Callout>

package vn.masteva.catalog;

import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;
import org.hibernate.annotations.Where;

/** Xoá mềm: sản phẩm bị xoá vẫn nằm trong bảng, nhưng mọi truy vấn của Hibernate tự lọc đi. */
@Entity
@Where(clause = "deleted = false")
public class Product {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String sku;
    private String name;
    private long price;
    private boolean deleted;

    protected Product() {
    }

    public Product(String sku, String name, long price) {
        this.sku = sku;
        this.name = name;
        this.price = price;
    }

    public String getSku() { return sku; }
    public String getName() { return name; }
    public long getPrice() { return price; }

    void markDeleted() {
        this.deleted = true;
    }
}

package vn.masteva.catalog;

import java.util.List;
import org.springframework.http.HttpStatus;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.bind.annotation.DeleteMapping;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.PathVariable;
import org.springframework.web.bind.annotation.PostMapping;
import org.springframework.web.bind.annotation.RequestBody;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.ResponseStatus;
import org.springframework.web.bind.annotation.RestController;
import org.springframework.web.server.ResponseStatusException;

@RestController
@RequestMapping("/api/products")
class ProductController {
    record ProductDto(String sku, String name, long price) {
        static ProductDto of(Product p) {
            return new ProductDto(p.getSku(), p.getName(), p.getPrice());
        }
    }

    private final ProductRepository products;

    ProductController(ProductRepository products) {
        this.products = products;
    }

    @GetMapping
    List<ProductDto> list() {
        return products.findAll().stream().map(ProductDto::of).toList();
    }

    @PostMapping
    @ResponseStatus(HttpStatus.CREATED)
    ProductDto create(@RequestBody ProductDto request) {
        return ProductDto.of(products.save(new Product(request.sku(), request.name(), request.price())));
    }

    @DeleteMapping("/{sku}")
    @ResponseStatus(HttpStatus.NO_CONTENT)
    @Transactional
    void delete(@PathVariable String sku) {
        products.findBySku(sku)
                .orElseThrow(() -> new ResponseStatusException(HttpStatus.NOT_FOUND, "no product " + sku))
                .markDeleted();
    }
}

import org.springframework.security.config.annotation.web.builders.HttpSecurity;

import org.springframework.security.core.userdetails.UserDetailsService;
import org.springframework.security.provisioning.InMemoryUserDetailsManager;

@Configuration

    @Bean
    SecurityFilterChain api(HttpSecurity http) throws Exception {
        http.authorizeHttpRequests(auth -> auth
                        .requestMatchers(antMatcher("/actuator/health/**")).permitAll()
                        .requestMatchers(antMatcher(HttpMethod.GET, "/api/products/**")).permitAll()

    @Bean
    UserDetailsService users() {
        return new InMemoryUserDetailsManager(

    }
}

Lệnh `perl` khớp mọi bản `4.0.x` vì recipe lấy bản 4.0 mới nhất lúc chạy; `grep` ngay sau đó để chắc phiên bản thật sự đã đổi. Khi production có sự cố, bạn biết cần quay lại commit nào.

### 8. Cấu hình deploy cũ trên bản mới

Test xanh, nhưng chưa ai chạy bản mới với cấu hình deploy thật. Đóng gói và chạy lại kịch bản của bước 2:

<Terminal where="mac">

```bash
cd ~/masteva-sb14/catalog
./mvnw -q clean package -DskipTests && ./run.sh
```

</Terminal>

<Expected>

```text
Content-Type: application/json
{"status":404,"error":"Not Found","path":"/api/products/NOPE"}
```

</Expected>

Mất cả hai: không còn `charset`, không còn `message`. Không có dòng log nào báo. Thêm migrator, đóng gói, chạy lại:

<Terminal where="mac">

```bash
cd ~/masteva-sb14/catalog
perl -0pi -e 's#(    <dependency>\n      <groupId>org.springframework.boot</groupId>\n      <artifactId>spring-boot-starter-test</artifactId>)#    <dependency>\n      <groupId>org.springframework.boot</groupId>\n      <artifactId>spring-boot-properties-migrator</artifactId>\n      <scope>runtime</scope>\n    </dependency>\n$1#' pom.xml
./mvnw -q clean package -DskipTests && ./run.sh
grep -A8 "PropertiesMigrationListener" app.log | grep -vE "^$|^--$" | sed -E 's/^.*(WARN|ERROR).*PropertiesMigrationListener  : /\1/'
```

</Terminal>

<Expected>

```text
Content-Type: application/json;charset=UTF-8
{"status":404,"error":"Not Found","path":"/api/products/NOPE"}
WARN
The use of configuration keys that have been renamed was found in the environment:
Property source 'systemEnvironment':
	Key: server.servlet.encoding.force
		Replacement: spring.servlet.encoding.force
Each configuration key has been temporarily mapped to its replacement for your convenience. To silence this warning, please update your configuration to use the new keys.
ERROR

```

</Expected>

Migrator tìm thấy cả hai khoá trong `systemEnvironment`, nơi recipe không bao giờ nhìn tới, và xử lý chúng khác nhau:

- `server.servlet.encoding.force` sang `spring.servlet.encoding.force`: cùng kiểu boolean, migrator ánh xạ tạm, `charset=UTF-8` quay lại.
- `server.error.include-message` sang `spring.web.error.include-message`: mục deprecated của khoá cũ trong metadata của Boot 4 (`spring-boot-web-server-4.1.1.jar`) không ghi `type`. Migrator không kiểm được hai kiểu có tương thích không, nên coi là không tương thích, chỉ báo `ERROR` và không ánh xạ. `message` vẫn mất. Kiểu thật của khoá mới vẫn là enum `ErrorProperties$IncludeAttribute` như ở 3.5; chỉ dấu vết trong metadata là thiếu.

Migrator vì vậy là công cụ **phát hiện**, không phải công cụ sửa. Sửa ở gốc: cấu hình deploy dùng khoá mới, rồi gỡ migrator.

<Terminal where="mac">

```bash
cd ~/masteva-sb14/catalog
perl -pi -e 's/^SERVER_ERROR_INCLUDE_MESSAGE/SPRING_WEB_ERROR_INCLUDE_MESSAGE/; s/^SERVER_SERVLET_ENCODING_FORCE/SPRING_SERVLET_ENCODING_FORCE/' deploy.env
git checkout -q pom.xml
./mvnw -q clean package -DskipTests && ./run.sh
grep -c PropertiesMigrationListener app.log
```

</Terminal>

<Expected>

```text
Content-Type: application/json;charset=UTF-8
{"status":404,"error":"Not Found","message":"no product NOPE","path":"/api/products/NOPE"}
0
```

</Expected>

Hai hành vi của bước 2 trở lại, không còn migrator. Trên dự án thật, thay đổi ở `deploy.env` là một pull request vào repo chứa manifest, merge **cùng lúc** với bản nâng cấp: deploy bản 4.1 với manifest cũ thì mất hành vi, deploy manifest mới với bản 3.5 thì 3.5 không biết khoá mới.

### Khi gặp lỗi

- `Recipe(s) not found: org.openrewrite.java.spring.boot4.UpgradeSpringBoot_4_1`: recipe gộp cho 4.1 không có trong `rewrite-spring` 6.37.1. Dùng `UpgradeSpringBoot_4_0` rồi đổi số phiên bản như bước 7.
- Test lỗi `Could not find a valid Docker environment`: Docker chưa chạy. Testcontainers 1.21 ở bản 3.5 và 2.0 ở bản 4.x đều cần Docker.
- `./run.sh` treo ở vòng `until`: ứng dụng không khởi động, đọc `app.log`. Hay gặp nhất là container `sb14-pg` chưa chạy (`docker ps`) hoặc cổng 8194 đang bận.
- Test xanh nhưng lỗi khó hiểu kiểu `NoClassDefFoundError` cho class mà bạn đã sửa: thiếu `clean`, `target` còn class biên dịch với bản cũ (bước 5).
- Patch của `dryRun` khác bài: phiên bản recipe hoặc plugin khác. Kiểm lại hai số `6.46.1` và `6.37.1` trong lệnh.

<DeepDive>

<Reveal title="Có nên sửa ba API deprecated trên 3.5 trước khi chạy recipe không?">

Nên, trên dự án thật. Cả ba thay thế đều có trên 3.5: `@SQLRestriction`, matcher dạng chuỗi, `UrlHandlerFilter`. Sửa chúng thành một commit riêng trên 3.5, test xanh, deploy. Bản nâng cấp lên 4.0 sau đó chỉ còn phần cơ học của recipe và dependency, diff nhỏ và dễ review. Nếu có sự cố sau khi deploy bản 4.0, bạn đã loại được ba nghi phạm. Lab làm ngược lại để đo được recipe bỏ sót gì; đừng chép thứ tự đó vào dự án.

</Reveal>

<Reveal title="Service có 400 test và 60% độ phủ. Bao nhiêu là đủ để nâng cấp?">

Độ phủ trung bình không trả lời câu này. Câu hỏi đúng là: mỗi hành vi mà client phụ thuộc có test chạm tới nó không, qua đúng tầng mà nâng cấp có thể đổi. Bốn test của `catalog` không phủ nhiều code, nhưng mỗi cái chạm một mảng Boot 4 đổi (Hibernate, MVC, Security, Actuator) qua HTTP thật và database thật. Hai hành vi ở bước 2 đến từ cấu hình deploy nên không test nào bắt; đó là lý do cần chạy bản mới với cấu hình thật ở staging, kèm migrator. Trước khi nâng cấp, viết thêm test cho hành vi biên: URL lạ, lỗi, header, quyền.

</Reveal>

<Reveal title="Spring Boot 4.1 hết hỗ trợ OSS vào 07/2027. Nâng cấp bao lâu một lần?">

Theo bản minor, khoảng sáu tháng một lần, trong vòng vài tháng sau khi bản mới ra (J14.2 ghi chính sách này thành ADR). Mỗi bản minor thường là một lần đổi số và đọc Release Notes như bước 7. Bản major mới dồn việc như bước 4 tới 6, và dồn càng nhiều nếu bạn bỏ qua các bản minor ở giữa: API deprecated tích lại, recipe gộp phải chạy qua nhiều tầng hơn. Công cụ như Dependabot hoặc Renovate mở pull request đổi số phiên bản mỗi khi có bản patch; bộ test hợp đồng quyết định có merge được hay không.

</Reveal>

<Reveal title="Tự viết recipe OpenRewrite cho thư viện nội bộ được không?">

Được, và đó là cách đội platform giảm chi phí cho các đội dùng thư viện. Recipe đơn giản viết bằng YAML gộp các recipe có sẵn: `ChangeType` cho class đổi tên, `ChangeMethodName`, `ChangeSpringPropertyKey` cho khoá cấu hình. Với thư viện audit của SB14.2, một recipe YAML `MastevaAudit_2_0` đổi được `masteva.audit.timeout` thành `request-timeout` trong mọi `application.properties`; việc thêm tham số `Map.of()` vào lời gọi `record` hai tham số thường cần một recipe viết bằng Java (Refaster template hoặc recipe imperative). Đóng gói recipe thành jar, phát hành cùng bản 2.0.0, và changelog chỉ cần một dòng lệnh `rewrite:run`.

</Reveal>
