<Goal>

K7.4 dùng CloudNativePG và gặp ngay mười một `kind` mới: `Cluster`, `Backup`, `ScheduledBackup`… Chúng không có sẵn trong Kubernetes; operator thêm chúng vào API bằng **CRD**. Chặng K9 đi từ phía người viết operator: bài này thiết kế loại tài nguyên, K9.2 viết controller cho nó, K9.3 và K9.4 đóng gói thành operator, K9.5 quay lại phía người dùng operator của người khác. Học xong bài này, bạn giải thích được:

- Vì sao một `kind` mới lập tức dùng được với `kubectl`, RBAC, watch, server-side apply mà không cần viết dòng code nào.
- Vì sao `kubectl apply` từ chối một trường gõ sai, còn một công cụ khác lại bỏ nó đi, chỉ kèm một dòng cảnh báo dễ bị lờ đi, hoặc không báo gì.
- Vì sao sửa `status` bằng `kubectl patch` báo `no change`, và vì sao `metadata.generation` không tăng khi bạn thêm annotation.
- Vì sao nâng một CRD lên bản mới bị từ chối với lỗi `must remain in spec.versions until a storage migration…`, lỗi đã chặn việc nâng cấp Gateway API trên cụm thật.
- Vì sao một object hay một CRD đứng mãi sau lệnh `kubectl delete`.

</Goal>

### Hai cách thêm API: CRD và aggregated API

Mọi thứ trong Kubernetes là object đi qua API server (K1.1). Muốn thêm một loại object mới, có hai đường:

```text
 kubectl / controller
        |
        v
 +---------------------------------------------------------------+
 | kube-apiserver: xác thực -> RBAC -> admission -> kiểm hợp lệ  |
 |                                                               |
 |  /apis/apps/v1/...               (có sẵn)  ----------------+  |
 |  /apis/apps.masteva.example/...  (CRD)     ----------------+--+--> etcd
 |  /apis/metrics.k8s.io/...        (aggregated) --+          |  |
 +-------------------------------------------------+----------+--+
                                                   |
                                                   v
                                    API server riêng của bạn (Deployment
                                    trong cụm, tự lo lưu trữ, tự lo watch)
```

| | CRD (CustomResourceDefinition) | Aggregated API |
|---|---|---|
| Bạn viết gì | Một object YAML mô tả `kind` mới | Cả một API server, đăng ký bằng object `APIService` |
| Ai lưu dữ liệu | API server chính, vào etcd của cụm | API server của bạn, nơi nào cũng được (hoặc không lưu) |
| Có sẵn miễn phí | `kubectl`, RBAC, watch, server-side apply, audit, `kubectl explain`, kiểm hợp lệ bằng schema và CEL | Phải tự làm phần lớn |
| Dùng khi | Gần như mọi trường hợp: cấu hình khai báo mà controller đọc | Dữ liệu không nên nằm trong etcd hoặc phải tính khi được hỏi. Ví dụ `metrics.k8s.io` của metrics-server (K5.3): số đo CPU tính tại chỗ, không lưu |
| Rủi ro | Mọi object nằm trong etcd chung của cụm | API server của bạn chết thì mọi lệnh liệt kê nhóm API đó lỗi |

Bài này và cả chặng chỉ dùng CRD. Một CRD mới không làm gì cả: nó chỉ dạy API server nhận, kiểm và lưu một loại object. Phải có **controller** đọc object đó và làm việc thật (K9.2). CRD cộng controller, đóng gói kèm kiến thức vận hành, là **operator** (K7.4).

<Check id="k9.1.crd-va-aggregated">Phân biệt được CRD và aggregated API theo nơi lưu dữ liệu và những gì có sẵn, và giải thích được vì sao tạo xong CRD vẫn chưa có gì chạy.</Check>

### Cấu trúc một CRD

Bài thiết kế `WebApp`: đội nền tảng muốn đội ứng dụng chỉ khai image, số bản sao, cổng, rồi phần còn lại (Deployment, Service, chuẩn bảo mật) do operator lo. File CRD đầy đủ ở bước 1 của lab; các phần chính:

| Trường | Ví dụ | Ý nghĩa |
|---|---|---|
| `metadata.name` | `webapps.apps.masteva.example` | Bắt buộc đúng dạng `<plural>.<group>` |
| `spec.group` | `apps.masteva.example` | Tên miền bạn kiểm soát, để không đụng tên với operator khác (`.example` dành cho ví dụ). Nhóm kết thúc bằng `k8s.io` hay `kubernetes.io` dành cho dự án Kubernetes |
| `spec.scope` | `Namespaced` | Thứ thuộc về một đội, một ứng dụng. `Cluster` cho thứ toàn cụm (như Node, StorageClass). Không đổi được sau khi tạo |
| `spec.names` | `kind: WebApp`, `plural: webapps`, `shortNames: [wa]` | Tên dùng trong YAML, trong URL và trong `kubectl` |
| `spec.versions[]` | `v1alpha1` | Mỗi phiên bản có `served`, `storage`, `schema`, `subresources`, `additionalPrinterColumns`. Đúng một phiên bản có `storage: true` |

### Schema, mặc định và luật CEL

Từ `apiextensions.k8s.io/v1`, mọi CRD phải có **schema có cấu trúc** (structural schema): mỗi trường khai rõ kiểu. Schema làm ba việc, theo thứ tự một yêu cầu ghi đi qua API server:

```text
 YAML gửi lên
   |
   v
 (1) giải mã    trường không có trong schema: kubectl mặc định yêu cầu "strict" -> từ chối;
                client không yêu cầu strict -> trường đó bị cắt bỏ (pruning), kèm Warning;
                client yêu cầu Ignore (--validate=ignore) -> cắt bỏ, không báo gì
   |            điền giá trị mặc định (default) cho trường bị bỏ trống
   v
 mutating admission (webhook hoặc admission policy, chặng K8)
   |
   v
 (2) kiểm hợp lệ theo schema   kiểu, minimum/maximum, enum, maxLength, pattern, required
   |
   v
 (3) luật CEL                  x-kubernetes-validations: so trường này với trường kia,
   |                           so giá trị mới với giá trị cũ
   v
 validating admission -> ghi etcd
```

**CEL** (Common Expression Language) là ngôn ngữ biểu thức ngắn, chạy ngay trong API server. Ba luật của `WebApp`:

| Luật | Đặt ở | Biểu thức | Schema thường có làm được không |
|---|---|---|---|
| Image phải có tag, không phải `latest` | `spec.image` | `self.matches(':[A-Za-z0-9_][A-Za-z0-9._-]*$') && !self.endsWith(':latest')` | `pattern` làm được nửa đầu, không viết được thông báo lỗi dễ hiểu |
| Tier `prod` cần ít nhất 2 bản sao | `spec` | `self.tier != 'prod' \|\| self.replicas >= 2` | Không: liên quan hai trường |
| Tier không đổi sau khi tạo | `spec.tier` | `self == oldSelf` | Không: phải so với giá trị cũ |

- `self` là giá trị của trường đặt luật; `oldSelf` là giá trị trước khi sửa. Luật có `oldSelf` gọi là **transition rule**, chỉ chạy khi cập nhật.
- API server ước lượng **chi phí** của mỗi luật lúc bạn tạo CRD, và từ chối luật có thể chạy quá lâu (ví dụ duyệt một danh sách không có `maxItems`). Khai `maxLength`, `maxItems` để luật được nhận.
- **Ratcheting** (ổn định từ Kubernetes 1.33): khi bạn siết luật, object cũ đang vi phạm vẫn sửa được những trường khác; chỉ trường vi phạm mà bị đổi mới bị kiểm. Siết luật vì thế không làm hỏng object đang có, nhưng cũng không sửa chúng. Transition rule (luật có `oldSelf`) không được ratchet: nó luôn được kiểm khi cập nhật.
- Kiểm tra trong CRD chỉ nhìn thấy **chính object đang ghi**. Luật cần đọc object khác ("tên này đã có Service chưa") phải dùng webhook (K9.4) hoặc chính sách admission (K8).

<Check id="k9.1.schema-cel">Kể được thứ tự giải mã, mặc định, kiểm theo schema, luật CEL khi ghi một object, giải thích được pruning và strict, và viết được luật CEL so hai trường hoặc so giá trị mới với giá trị cũ.</Check>

### Cột in, subresource status và scale

**additionalPrinterColumns** quyết định `kubectl get webapps` in gì, bằng JSONPath vào object. Không có chúng, bạn chỉ thấy `NAME` và `AGE`.

**Subresource `status`** tách object thành hai cổng ghi:

| | `/webapps/web` | `/webapps/web/status` |
|---|---|---|
| Ai ghi | Người dùng, GitOps (D13) | Controller |
| Trường được đổi | Mọi thứ **trừ** `status` (status gửi kèm bị bỏ qua) | **Chỉ** `status` |
| `metadata.generation` | Tăng khi `spec` đổi; không tăng khi chỉ đổi label, annotation | Không tăng |
| Quyền RBAC | `webapps` | `webapps/status` |

Hai lợi ích. Người dùng không vô tình ghi đè trạng thái controller quan sát được, và controller không vô tình ghi đè `spec`. Và `generation` chỉ tăng khi ý định đổi: controller ghi `status.observedGeneration` bằng `generation` nó vừa xử lý, nên ai cũng biết status đang nói về bản `spec` nào (K9.2).

**Subresource `scale`** chỉ cho API server biết số bản sao nằm ở đâu (`specReplicasPath`, `statusReplicasPath`, `labelSelectorPath`). Đổi lại, `kubectl scale` và HorizontalPodAutoscaler (K5.3) dùng được với `WebApp` như với Deployment.

<Check id="k9.1.subresource">Giải thích được subresource `status` tách quyền ghi thế nào, khi nào `generation` tăng, và subresource `scale` cho phép công cụ nào làm việc với CRD.</Check>

### Nhiều phiên bản: phục vụ, lưu trữ, chuyển đổi

API ổn định thì không đổi tuỳ tiện: có người đang dùng `v1alpha1`. Một CRD vì thế phục vụ nhiều phiên bản cùng lúc, nhưng mỗi object trong etcd chỉ được ghi ở **một** phiên bản: phiên bản mang `storage: true` **tại lúc object được ghi**.

```text
 spec.versions: v1alpha1 (served)   v1 (served, storage)

 etcd:  /registry/apps.masteva.example/webapps/k9/web    {"apiVersion": ".../v1alpha1", ...}   ghi trước khi đổi
        /registry/apps.masteva.example/webapps/k9/web-2  {"apiVersion": ".../v1", ...}         ghi sau khi đổi

 status.storedVersions: [v1alpha1, v1]   <- mọi phiên bản TỪNG được dùng để ghi; API server chỉ thêm, không tự bớt

 GET .../v1/webapps/web  ->  đọc bản v1alpha1 trong etcd, chuyển sang v1 rồi trả về
```

**Conversion** là bước chuyển giữa các phiên bản khi đọc và ghi:

| `strategy` | Làm gì | Dùng khi |
|---|---|---|
| `None` (mặc định) | Chỉ thay chuỗi `apiVersion`, các trường giữ nguyên | Hai phiên bản có schema giống nhau, ví dụ nâng `v1alpha1` lên `v1` khi API đã ổn định |
| `Webhook` | API server gọi một HTTPS endpoint (thường nằm trong operator) để chuyển | Đổi tên, đổi cấu trúc trường. Webhook chết là mọi lệnh đọc, ghi object không cùng phiên bản lưu đều lỗi |

Đổi phiên bản lưu không ghi lại object cũ. Chúng nằm nguyên ở `v1alpha1` cho tới khi có ai ghi lại. Muốn gỡ hẳn `v1alpha1`, phải:

1. Ghi lại mọi object để chúng được lưu ở `v1`. Kubernetes có sẵn **StorageVersionMigration** (`storagemigration.k8s.io/v1`, bật sẵn trên cụm 1.37 của lab; cụm cũ hơn có thể phải bật feature gate `StorageVersionMigrator`): bạn tạo một object, controller trong `kube-controller-manager` ghi lại từng object rồi tự bỏ phiên bản cũ khỏi `storedVersions`.
2. Đặt `served: false` cho `v1alpha1` một thời gian, để client cũ lộ ra (lỗi 404) trong khi còn đường lui.
3. Xoá `v1alpha1` khỏi `spec.versions`. API server từ chối bước này chừng nào `v1alpha1` còn trong `storedVersions`.

Trong thời gian chuyển, đặt `deprecated: true` và `deprecationWarning` cho phiên bản cũ: mọi lệnh dùng nó nhận cảnh báo, kể cả `kubectl`.

<Callout kind="production">

Gateway API v1.2.0 (phát hành ngày 03/10/2024) ngừng phục vụ phiên bản `v1alpha2` của `GRPCRoute` và `ReferenceGrant`. [Release notes của dự án](https://github.com/kubernetes-sigs/gateway-api/releases/tag/v1.2.0) viết rằng nếu cài CRD mới gặp lỗi, nhiều khả năng là `v1alpha2` vẫn còn trong `storedVersions`, trường mà theo nguyên văn họ "không tự được dọn". Quy trình họ đưa ra: kiểm `storedVersions`, ghi lại từng `ReferenceGrant` và `GRPCRoute` (bằng cách patch một annotation) để chúng được lưu ở phiên bản mới, rồi mới patch `status.storedVersions` của CRD. Họ cũng nhắc một bẫy khác: manifest của bạn đã viết `v1` chưa đủ, controller của implementation vẫn có thể đang gọi `v1alpha2`.

[Bài trong kho kiến thức của Broadcom](https://knowledge.broadcom.com/external/article/433502/gateway-api-packageinstall-fails-reconci.html) ghi lại đúng lỗi này trên sản phẩm VMware vSphere Kubernetes Service: khi nâng cấp cụm, gói Gateway API không reconcile được, việc nâng cấp đứng lại, với thông báo `status.storedVersions[0]: Invalid value: "v1alpha2": missing from spec.versions`. Cách sửa trong bài là patch `storedVersions` chỉ còn `v1beta1` rồi để gói reconcile tiếp.

Điều bài này rút ra (của bài, không phải của hai nguồn): cách sửa của Broadcom bỏ qua bước ghi lại object mà release notes yêu cầu. Nếu còn object đang nằm ở `v1alpha2` trong etcd mà phiên bản đó bị xoá khỏi CRD, API server không còn cách đọc chúng. Bước 4 của lab gặp đúng lỗi này rồi đi đường đúng: migrate trước, xoá sau.

</Callout>

### Xoá: finalizer, và xoá CRD là xoá tất cả

Lệnh `delete` không xoá ngay một object có **finalizer**. Finalizer là một chuỗi trong `metadata.finalizers`, mang nghĩa "có người cần dọn việc trước khi object biến mất".

```text
 kubectl delete wa web
   |
   v
 finalizers rỗng?  -- có -->  xoá khỏi etcd
   | không
   v
 API server đặt metadata.deletionTimestamp, object vẫn còn, vẫn đọc được, vẫn sửa được spec,
 nhưng KHÔNG thêm được finalizer mới
   |
   v
 controller giữ finalizer thấy deletionTimestamp -> dọn việc của nó (xoá tài nguyên ngoài cụm,
 huỷ đăng ký...) -> gỡ tên mình khỏi finalizers
   |
   v
 finalizers rỗng -> xoá khỏi etcd
```

Controller giữ finalizer đã bị gỡ, đang chết, hoặc có lỗi, thì object đứng mãi. Gỡ finalizer bằng tay thì object biến mất, nhưng việc dọn dẹp mà finalizer bảo vệ **không** xảy ra. K1.3 đã nêu chuyện pod kẹt `Terminating` vì đúng lý do này.

Xoá **CRD** thì API server xoá **mọi object** của loại đó trong mọi namespace, rồi mới xoá CRD. Bản thân CRD mang finalizer `customresourcecleanup.apiextensions.k8s.io` để làm việc này; chỉ một object có finalizer chưa gỡ cũng giữ CRD ở trạng thái đang xoá. Nếu các object đó là chủ (owner) của Deployment, Service (K9.2), garbage collector xoá luôn những thứ đó. Vì thế Helm không nâng cấp và không xoá CRD trong thư mục `crds/` (K3.2), và K9.4 sẽ thấy lệnh gỡ operator mặc định của Kubebuilder kéo theo CRD.

<Check id="k9.1.finalizer">Kể được điều xảy ra khi xoá một object có finalizer, vì sao gỡ finalizer bằng tay là nguy hiểm, và điều xảy ra khi xoá một CRD còn object.</Check>

### Chuẩn bị

Bài dựng cụm kind `k9-lab` một node, dùng cho cả chặng K9. Cần Docker, kind 0.33, kubectl 1.37, `jq` và `yq` (D0.2).

**Profile máy.** Cuối bài, node kind dùng khoảng 0,65 tới 0,9 GiB RAM của Docker; bài không kéo image ứng dụng nào. Máy 8 GB chạy thoải mái. Các bài sau của chặng cần tối đa khoảng 1,4 GiB (K9.4).

Mọi terminal dùng cho chặng cần dòng `export KUBECONFIG=~/masteva-k9/kubeconfig`, để kind ghi cấu hình vào thư mục lab thay vì `~/.kube/config`. ### Gỡ lỗi

| Hiện tượng | Nguyên nhân thường gặp | Cách kiểm |
|---|---|---|
| Tạo CRD lỗi `metadata.name: Invalid value … must be spec.names.plural+"."+spec.group` | Tên CRD không khớp `plural.group` | Đặt `metadata.name` đúng `webapps.apps.masteva.example` |
| Tạo CRD lỗi về `structural schema` hoặc thiếu `type` | Một trường trong schema thiếu `type` | Khai `type` cho mọi trường; trường tự do thật thì thêm `x-kubernetes-preserve-unknown-fields: true` |
| Tạo CRD lỗi `estimated rule cost exceeds budget` | Luật CEL duyệt chuỗi hoặc danh sách không giới hạn độ dài | Thêm `maxLength`, `maxItems` cho trường mà luật dùng |
| `kubectl get wa` báo `the server doesn't have a resource type` ngay sau khi tạo CRD | Discovery chưa cập nhật, hoặc CRD chưa `Established` | `kubectl wait --for=condition=Established crd/…` rồi chạy lại |
| StorageVersionMigration không lên `Succeeded` | Một object không ghi lại được (ví dụ vi phạm luật mới) | `kubectl get storageversionmigration webapps-to-v1 -o yaml` xem `conditions` |

<Reveal title="Khi nào cần conversion webhook thay vì `None`?">

Khi hai phiên bản khác nhau về **cấu trúc**, không chỉ về tên phiên bản. Ví dụ `v2` đổi `message` thành `greeting`, hay gộp `image` thành `image.repository` và `image.tag`. Với `None`, API server chỉ thay `apiVersion`: object lưu ở `v1` có `message`, đọc qua `v2` thì trường đó không có trong schema `v2` và bị cắt bỏ, dữ liệu mất trên đường đi. Webhook chuyển đổi phải chạy được theo cả hai chiều và không mất thông tin (chuyển `v1 → v2 → v1` phải ra đúng bản gốc), nên các dự án thường cất trường không có chỗ ở phiên bản kia vào annotation. Cái giá vận hành: webhook là một service trong cụm; nó chết thì mọi lệnh đọc object không ở phiên bản lưu đều lỗi, kể cả lệnh của garbage collector và của `kubectl delete namespace`. Kubebuilder sinh khung cho việc này bằng `kubebuilder create webhook --conversion`; chặng này không dùng tới.

</Reveal>

<Reveal title="Có nên để mọi thứ vào CRD, kể cả dữ liệu lớn hay thay đổi liên tục?">

Không. Mỗi object nằm trong etcd chung với cả cụm. etcd đặt trần cho một yêu cầu ghi (mặc định khoảng 1,5 MiB) và cho tổng dung lượng của cả cơ sở dữ liệu. Mỗi lần ghi tạo một revision mới cho tới lần compaction kế tiếp, và mọi controller đang watch loại đó nhận một sự kiện. Kết quả quét, log, số đo theo giây thuộc về hệ thống lưu trữ khác; CRD giữ ý định và trạng thái tóm tắt. K9.3 có một sự cố thật vì đúng chuyện này.

</Reveal>

<Reveal title="`x-kubernetes-list-type: map` ở `conditions` để làm gì?">

Nó nói với API server rằng danh sách này là một tập phần tử phân biệt bằng khoá `type`, không phải một mảng nguyên khối. Server-side apply (K3.1) nhờ đó theo dõi quyền sở hữu **từng phần tử**: controller A sở hữu condition `Available`, controller B sở hữu `Degraded`, hai bên apply mà không ghi đè nhau. Không có nó, danh sách được coi là `atomic`: ai apply sau thay cả danh sách. API server cũng từ chối hai phần tử cùng `type`.

</Reveal>

<Callout kind="ai">

**Nên nhờ AI:** viết khung CRD từ một mô tả, viết luật CEL cho một ràng buộc giữa nhiều trường, giải thích một thông báo lỗi validation dài.

**AI hay sai ở đâu:** viết `apiextensions.k8s.io/v1beta1` (đã bị gỡ từ Kubernetes 1.22) với `validation` ở cấp CRD thay vì `schema` trong từng phiên bản; quên `type` làm schema không có cấu trúc; viết luật CEL dùng hàm không có trong thư viện của Kubernetes, hoặc dùng `oldSelf` ở trường có thể vắng mặt; khuyên "xoá phiên bản cũ khỏi CRD" hay "patch storedVersions" mà bỏ bước migrate; và gợi ý gỡ finalizer để "sửa" object kẹt mà không hỏi việc dọn dẹp nào đang bị bỏ.

**Cách kiểm tra:** `kubectl apply --dry-run=server -f crd.yaml` bắt lỗi schema và chi phí CEL ngay khi tạo CRD; với mỗi luật, viết một object hợp lệ và một object vi phạm rồi `kubectl apply --dry-run=server` cả hai; với mọi thay đổi phiên bản, kiểm `status.storedVersions` trước và sau.

</Callout>
