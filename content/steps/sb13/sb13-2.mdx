<Goal>

Dựng đủ ba mảnh của một hệ thống đăng nhập cho SPA: authorization server cấp token, resource server kiểm token, và một BFF (Backend for Frontend) đứng giữa để trình duyệt không bao giờ cầm token. Học xong bài này, bạn giải thích được:

- Vì sao tự dựng authorization server bằng Spring chỉ mất một file cấu hình, nhưng đưa nó lên production lại là việc khác hẳn.
- Vì sao một client có secret vẫn nên dùng PKCE, và authorization server trả lỗi gì khi client public quên nó.
- Vì sao chuyển token từ `localStorage` sang session của BFF lại đưa CSRF quay về, và SPA phải gửi thêm header gì.

</Goal>

<Knowledge>

### Authorization server: ai cấp token

SB6.2 đã dựng Keycloak, lấy token và cho API kiểm chữ ký, issuer, audience; bài này không nhắc lại phần resource server. Câu hỏi ở đây là phía bên kia: **authorization server** (máy chủ cấp quyền) chạy bằng gì. Nó giữ danh sách client, xác thực người dùng, cấp và thu hồi token, công bố khoá công khai qua JWKS. Hai lựa chọn tự host phổ biến trong hệ Spring:

| | Keycloak | Spring Authorization Server |
|---|---|---|
| Là gì | Sản phẩm hoàn chỉnh, chạy riêng (Docker, Kubernetes) | Thư viện; bạn viết một ứng dụng Spring Boot quanh nó |
| Từ Spring Security 7 | Không liên quan | Là module `spring-security-oauth2-authorization-server`, cùng phiên bản Spring Security |
| Có sẵn | Giao diện quản trị, đăng ký người dùng, quên mật khẩu, MFA, đăng nhập Google/GitHub, nối LDAP và Active Directory, theme | Các endpoint OAuth2/OIDC: authorize, token, JWKS, userinfo, introspect, revoke, logout |
| Phải tự làm | Gần như không phải code; tuỳ biến bằng SPI Java hoặc theme | Kho người dùng, trang đăng nhập, lưu client và token vào database, xoay khoá, MFA |
| Vận hành | Một hệ thống nữa: database riêng, nâng cấp theo lịch của Keycloak | Như mọi service Spring của bạn |
| Hợp với | Nhiều ứng dụng, nhiều loại người dùng, cần tính năng IAM đầy đủ | Luồng token đặc thù gắn chặt nghiệp vụ, đã có kho người dùng, đội quen Spring |

Còn lựa chọn thứ ba: dịch vụ có quản lý (Auth0, Amazon Cognito, Microsoft Entra ID…), đổi tiền lấy việc không phải vận hành. Vì cả ba đều nói OIDC chuẩn, phía client (BFF, resource server) chỉ cần `issuer-uri`, `client-id`, `client-secret`; bước 8 của lab đổi BFF từ Spring Authorization Server sang Keycloak mà không sửa một dòng Java.

Spring Boot 4.1 có starter `spring-boot-starter-security-oauth2-authorization-server`. Chỉ với property `spring.security.oauth2.authorizationserver.*`, nó dựng một authorization server chạy được. Nhưng mọi thứ đều nằm trong bộ nhớ:

| Thành phần | Mặc định của starter | Trên production |
|---|---|---|
| Danh sách client | Đọc từ property, giữ trong bộ nhớ | `JdbcRegisteredClientRepository` |
| Authorization, refresh token, consent | `InMemoryOAuth2AuthorizationService` | Bản JDBC, hoặc tự viết trên Redis |
| Khoá ký JWT | Một cặp RSA **sinh mới mỗi lần khởi động** | Khoá lưu bền, xoay vòng có kế hoạch, công bố cả khoá cũ lẫn mới trong JWKS |
| Người dùng | Bean `UserDetailsService` bạn tự khai báo | Database người dùng của bạn |

Khởi động lại bản mặc định nghĩa là mọi token đã cấp mất hiệu lực (khoá đổi) và mọi người phải đăng nhập lại.

<Check id="sb13.2.as-choice">Chọn được giữa Keycloak, Spring Authorization Server và dịch vụ có quản lý cho một tình huống cụ thể, và kể được những gì starter của Spring Boot giữ trong bộ nhớ.</Check>

### Client confidential, client public và PKCE

**Client** là ứng dụng xin token thay mặt người dùng. Khác nhau quan trọng nhất là nó có giữ được bí mật không:

| | Confidential | Public |
|---|---|---|
| Ví dụ | BFF, ứng dụng web chạy ở server | SPA tự giữ token, app mobile, CLI |
| Giữ được `client_secret`? | Có, nằm ở server | Không: ai tải app về cũng đọc được |
| Xác thực ở token endpoint | `client_secret_basic`, `private_key_jwt`… | `none` |

Với client public, kẻ nào chặn được `code` trên đường redirect (một app khác đăng ký cùng custom scheme trên điện thoại, log của proxy) có thể đổi nó lấy token. **PKCE** (Proof Key for Code Exchange, RFC 7636) chặn việc đó bằng một bí mật dùng một lần:

```text
 client                                           authorization server
 sinh code_verifier ngẫu nhiên (giữ kín)
 code_challenge = BASE64URL(SHA-256(code_verifier))
 GET /oauth2/authorize?...&code_challenge=..&code_challenge_method=S256  --->  lưu code_challenge cùng code
                                       <--- 302 redirect_uri?code=abc
 POST /oauth2/token code=abc&code_verifier=...                           --->  SHA-256(verifier) == challenge?
                                       <--- access token (chỉ khi khớp)
```

Kẻ chặn được `code=abc` không có `code_verifier`, nên không đổi được token. RFC 9700 (thực hành bảo mật tốt nhất cho OAuth 2.0, 2025) bắt buộc PKCE cho client public và khuyến nghị cho cả client confidential, vì nó còn chặn kiểu tấn công tiêm `code` của người khác vào phiên của nạn nhân. Spring Authorization Server bật yêu cầu này cho từng client bằng `require-proof-key=true`. Phía Spring Security client, `ClientRegistration.ClientSettings.requireProofKey` (có từ 6.5) mặc định là `true` trong Spring Security 7.1 của lab, nên mọi registration kiểu `authorization_code`, kể cả client confidential như BFF, tự gửi `code_challenge` S256 mà không cần cấu hình gì. Chỉ phải đụng tới nó khi một IdP cũ từ chối tham số PKCE.

<Check id="sb13.2.pkce">Vẽ lại được luồng authorization code có PKCE, và giải thích được vì sao client confidential cũng nên dùng nó.</Check>

### Vì sao SPA không nên giữ token

SPA giữ access token trong `localStorage`, `sessionStorage` hay biến JavaScript thì mọi script chạy trên trang đều đọc được nó. Chỉ cần một lỗ XSS (Cross-Site Scripting): một thư viện npm bị chiếm, một đoạn markdown người dùng nhập không được lọc, một script quảng cáo. Token bị gửi đi và dùng từ máy kẻ tấn công cho tới khi hết hạn; nếu refresh token cũng nằm đó, kẻ tấn công giữ quyền truy cập hàng tuần.

**BFF** (Backend for Frontend) là một server nhỏ cùng origin với SPA, đóng vai client confidential. Token nằm trong session của nó; trình duyệt chỉ có cookie phiên `HttpOnly`, thứ JavaScript không đọc được.

```text
 trình duyệt (SPA)            BFF :8093 (oauth2Login)          authorization server :8193    API :8293
 GET /oauth2/authorization/idp -->  tạo state, nonce, PKCE
            <-- 302 /oauth2/authorize?...  ---------------->   đăng nhập, cấp code
 GET /login/oauth2/code/idp?code=.. -->  POST /oauth2/token (secret + code_verifier) --->
                                    <--- access, refresh, id token: GIỮ TRONG SESSION
            <-- Set-Cookie: JSESSIONID; HttpOnly; SameSite=Lax
 GET /api/orders (cookie)      -->  lấy token từ session, hết hạn thì refresh
                                    GET /orders  Authorization: Bearer ... ------------------------>  kiểm JWT
            <-- JSON đơn hàng  <--------------------------------------------------------------------
```

| | SPA giữ token | BFF |
|---|---|---|
| XSS đọc được token | Có | Không: token không bao giờ tới trình duyệt |
| XSS vẫn gọi được API khi trang đang mở | Có | Có: XSS nào cũng làm được điều này; BFF không thay được CSP và lọc đầu vào |
| CSRF | Không (token gửi bằng header tự viết) | **Có**: cookie tự đi kèm, phải chống CSRF |
| CORS | SPA gọi thẳng API ở origin khác | Không cần: SPA và BFF cùng origin |
| Phải vận hành | Không thêm gì | BFF và nơi lưu session (Spring Session với Redis khi chạy nhiều instance) |

Bản nháp chuẩn "OAuth 2.0 for Browser-Based Applications" của IETF xếp BFF là kiến trúc an toàn nhất trong các cách cho SPA. Thuộc tính cookie phiên đáng đặt: `HttpOnly` (JavaScript không đọc), `Secure` (chỉ qua HTTPS), `SameSite=Lax` (không gửi kèm request khởi phát từ site khác, trừ điều hướng cấp cao nhất; `Strict` chỉ dùng được khi authorization server cùng site với BFF, vì callback `oauth2Login` là điều hướng từ site của authorization server và `Strict` làm mất cookie phiên ở bước đó), và tiền tố `__Host-` để cookie gắn chặt với đúng host.

<Check id="sb13.2.bff-why">Giải thích được BFF chặn được gì và không chặn được gì so với SPA tự giữ token, và kể được bốn thuộc tính cookie nên đặt cho cookie phiên.</Check>

### CSRF quay lại, và csrf.spa()

SB6.2 đã giải thích CSRF và lý do API dùng token trong header được tắt nó. BFF dùng cookie phiên, nên CSRF quay lại. Spring Security 7.0 thêm `csrf(c -> c.spa())`, gói cấu hình cho SPA:

1. Token CSRF lưu trong cookie `XSRF-TOKEN` **không** `HttpOnly`, để JavaScript của chính trang đọc được.
2. Mỗi request thay đổi dữ liệu, SPA đọc cookie đó và gửi lại trong header `X-XSRF-TOKEN`.
3. Trang của kẻ tấn công ở site khác không đọc được cookie của origin này, nên không dựng được header.

Request từ form HTML (tham số `_csrf`) vẫn phải dùng dạng token đã che (masked) như trang server-rendered; header thì nhận giá trị thô trong cookie. Lab sẽ gặp đúng chi tiết này ở bước đăng xuất.

<Check id="sb13.2.csrf-spa">Giải thích được vì sao BFF cần CSRF dù API phía sau không cần, và SPA lấy token CSRF từ đâu, gửi lại bằng gì.</Check>

### Token relay và đăng xuất

BFF nhận request có cookie, tìm access token của người dùng trong session, rồi gọi API kèm `Authorization: Bearer`. Việc đó gọi là **token relay**. Hai cách:

| Cách | Viết thế nào | Hợp với |
|---|---|---|
| `RestClient` + `OAuth2ClientHttpRequestInterceptor` (Spring Security 6.4+) | Interceptor lấy token qua `OAuth2AuthorizedClientManager`, tự refresh khi token sắp hết hạn | Vài endpoint, muốn kiểm soát từng lời gọi; lab dùng cách này |
| Spring Cloud Gateway Server MVC, filter `TokenRelay` | Khai báo route trong cấu hình | Nhiều route, BFF thuần proxy; start.spring.io ghép Boot 4.1.1 với Spring Cloud 2025.1.3 |

`OAuth2AuthorizedClientManager` mặc định refresh token khi còn dưới 60 giây là hết hạn (`clockSkew` của `RefreshTokenOAuth2AuthorizedClientProvider`), nên access token 5 phút của lab được làm mới sau khoảng 4 phút mà SPA không hay biết.

Đăng xuất có ba tầng: session của BFF, session đăng nhập ở authorization server (nếu chỉ xoá tầng đầu, bấm "Đăng nhập" là vào lại ngay không cần mật khẩu), và token đã cấp. **OIDC RP-initiated logout** xử lý tầng thứ hai: BFF chuyển trình duyệt tới `end_session_endpoint` kèm `id_token_hint` và `post_logout_redirect_uri`. Tầng thứ ba không ai lo: Spring Authorization Server không thu hồi token khi đăng xuất OIDC, và BFF chỉ quên token cùng session của nó. Access token vẫn sống tới khi hết hạn (SB6.2 đã chứng minh), refresh token cũng vậy. Trên production, thêm một `LogoutHandler` ở BFF gọi `/oauth2/revoke` (RFC 7009) cho refresh token trước khi xoá session, và giữ access token ngắn.

<Callout kind="production">

Một ứng dụng quản lý chi tiêu viết bằng React lưu access token và refresh token (sống 30 ngày) trong `localStorage`. Một thư viện hiển thị biểu đồ trong `package.json` bị chiếm quyền và phát hành bản vá chứa đoạn script gửi `localStorage` về một máy chủ lạ. Kẻ tấn công dùng refresh token lấy access token mới suốt nhiều tuần, kể cả sau khi đội gỡ thư viện, vì không ai thu hồi refresh token. Sau sự cố, đội chuyển sang BFF: script độc hại vẫn có thể gọi API khi người dùng mở trang, nhưng không mang được gì ra ngoài để dùng tiếp, và đăng xuất ở BFF chấm dứt mọi thứ.

</Callout>

### 2. Authorization server tối thiểu

<Terminal where="mac" title="Tab 4: cấu hình authserver">

```bash
cd ~/masteva-sb13/authserver
cat > src/main/resources/application.properties <<'EOF'
spring.application.name=authserver
server.port=8193
server.servlet.session.cookie.name=AS_SESSION
logging.pattern.console=%5p %logger{0} : %m%n

spring.security.oauth2.authorizationserver.issuer=http://localhost:8193

# BFF: confidential client, có secret, vẫn bắt PKCE
spring.security.oauth2.authorizationserver.client.bff.registration.client-id=bff
spring.security.oauth2.authorizationserver.client.bff.registration.client-secret={noop}lab-only-bff-secret
spring.security.oauth2.authorizationserver.client.bff.registration.client-authentication-methods=client_secret_basic
spring.security.oauth2.authorizationserver.client.bff.registration.authorization-grant-types=authorization_code,refresh_token
spring.security.oauth2.authorizationserver.client.bff.registration.redirect-uris=http://127.0.0.1:8093/login/oauth2/code/idp
spring.security.oauth2.authorizationserver.client.bff.registration.post-logout-redirect-uris=http://127.0.0.1:8093/
spring.security.oauth2.authorizationserver.client.bff.registration.scopes=openid,profile,orders.read,orders.write
spring.security.oauth2.authorizationserver.client.bff.require-proof-key=true
spring.security.oauth2.authorizationserver.client.bff.token.access-token-time-to-live=5m

spring.security.oauth2.authorizationserver.client.spa.registration.client-id=spa
spring.security.oauth2.authorizationserver.client.spa.registration.client-authentication-methods=none
spring.security.oauth2.authorizationserver.client.spa.registration.authorization-grant-types=authorization_code
spring.security.oauth2.authorizationserver.client.spa.registration.redirect-uris=http://127.0.0.1:5173/callback
spring.security.oauth2.authorizationserver.client.spa.registration.scopes=openid,orders.read
spring.security.oauth2.authorizationserver.client.spa.require-proof-key=true
EOF

import org.springframework.context.annotation.Configuration;

import org.springframework.security.core.userdetails.UserDetailsService;

@Configuration

    /** {noop}: mật khẩu thô, chỉ cho lab. */

    }
}
EOF
```

### 7. CSRF, rồi đăng xuất

<Terminal where="mac" title="Tab 4">


<Expected>

```text

{"owner":"alice","item":"Tai nghe"}

```

</Expected>

- POST có cookie phiên nhưng thiếu header: 403. Đây là đúng tình huống một trang ở site khác gửi form tới BFF.
- Thêm `X-XSRF-TOKEN` bằng giá trị đọc từ cookie: qua, và API nhận đơn mới.
- Gửi chính giá trị đó trong tham số form `_csrf`: 403. `spa()` chỉ nhận giá trị thô qua header; tham số form phải là bản đã che. Vì vậy SPA đăng xuất bằng `fetch` có header, như `index.html` làm.

```bash
c -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8093/api/orders
```

```bash
cd ~/masteva-sb13 && : > jar.txt
c -L -o kc-login.html http://127.0.0.1:8093/oauth2/authorization/idp
```


- Cùng BFF, cùng code, chỉ khác `issuer-uri`: đăng nhập qua Keycloak thành công. Spring đọc `.well-known/openid-configuration` của Keycloak và tự biết mọi endpoint.
- `sub` của Keycloak là UUID của user (khác trên máy bạn), không phải `alice`. Code nào dùng `sub` làm khoá dữ liệu sẽ "mất" toàn bộ dữ liệu cũ khi đổi nhà cung cấp; cần bảng ánh xạ hoặc migration.
- `/api/orders` trả 401: API vẫn chỉ tin khoá và issuer của Spring Authorization Server. Muốn API nhận token Keycloak, đổi `issuer-uri` và `audiences` của API như SB6.2.
- Keycloak từ chối scope `orders.read` mà realm chưa khai báo, nên profile `kc` chỉ xin `openid,profile`. Mỗi nhà cung cấp có cách định nghĩa scope riêng; đó là phần không đổi được chỉ bằng `issuer-uri`.

<Check id="sb13.2.lab-keycloak">Chuyển được BFF sang Keycloak chỉ bằng một file profile, và giải thích được ba khác biệt lộ ra: `sub`, scope và issuer mà API tin.</Check>

### Khi gặp lỗi

<Callout kind="pitfall">

- BFF dừng ngay với `Unable to resolve Configuration with the provided Issuer`: authorization server (hoặc Keycloak) chưa chạy xong khi BFF khởi động. Chờ discovery trả 200 rồi chạy lại BFF.
- `login` in `200 http://localhost:8193/login?error`: sai mật khẩu, hoặc `jar.txt` cũ lẫn cookie. Hàm `login` tự xoá jar; nếu gọi tay, chạy `: > jar.txt` trước.
- Callback trả `[invalid_request] OAuth 2.0 Parameter: redirect_uri`: `redirect-uris` ở authorization server không khớp từng ký tự với URL BFF gửi, thường do lẫn `localhost` với `127.0.0.1`.
- `[invalid_scope]` khi dùng Keycloak: thiếu file `application-kc.properties` hoặc quên `-Dspring-boot.run.profiles=kc`.
- `docker: Error response from daemon: Conflict. The container name "/sb13-kc" is already in use`: container từ lần chạy trước. Xoá theo mục Dọn dẹp rồi chạy lại.
- `Port 8093 was already in use`: BFF của bước trước chưa dừng; `lsof -i :8093` để tìm.

</Callout>

<DeepDive>

<Reveal title="BFF chạy ba instance sau load balancer thì session ở đâu?">

Session mặc định nằm trong bộ nhớ của từng instance, nên request sau rơi vào instance khác là mất đăng nhập. Hai cách: sticky session ở load balancer (đơn giản, nhưng instance chết là người dùng mất phiên), hoặc Spring Session lưu session trong Redis hay JDBC. Với BFF, session chứa access token và refresh token, nên kho session trở thành nơi chứa bí mật: bật mật khẩu và TLS cho Redis, giới hạn ai đọc được, và đặt thời gian sống của session không dài hơn refresh token. Kích thước session cũng lớn hơn ứng dụng thường vì có cả ID token.

</Reveal>

<Reveal title="ID token nằm trong URL đăng xuất. Vậy BFF có làm lộ token không?">

Có, nhưng là ID token, không phải access token. `id_token_hint` là tham số OIDC RP-initiated logout quy định, để authorization server biết phiên nào cần kết thúc và client nào yêu cầu. ID token chỉ là bằng chứng "người này đã đăng nhập ở client này", resource server không nhận nó làm access token (audience là client, không có scope API). Dù vậy URL đó có thể vào lịch sử trình duyệt và log của proxy; nếu authorization server hỗ trợ, gửi `client_id` thay cho `id_token_hint`, hoặc dùng back-channel logout để authorization server gọi thẳng BFF.

</Reveal>

<Reveal title="Khi nào vẫn để SPA giữ token?">

Khi không có server nào cùng origin để làm BFF, ví dụ SPA tĩnh trên CDN gọi API của bên thứ ba, hoặc ứng dụng mobile (không có cookie trình duyệt, nhưng có kho khoá an toàn của hệ điều hành). Khi đó dùng client public với PKCE, access token rất ngắn, giữ trong bộ nhớ thay vì `localStorage`, refresh token xoay vòng (mỗi lần dùng cấp cái mới, cái cũ hết hiệu lực) và Content Security Policy chặt. Bản nháp "OAuth 2.0 for Browser-Based Applications" mô tả mô hình này là kém an toàn hơn BFF, và nêu rõ rủi ro còn lại.

</Reveal>

<Reveal title="Spring Authorization Server cấp token cho service gọi service được không?">

Được, bằng grant `client_credentials`: service A xác thực bằng secret hoặc `private_key_jwt` và nhận token mang danh chính nó, không có người dùng. Discovery ở bước 2 liệt kê grant này, cùng với `urn:ietf:params:oauth:grant-type:token-exchange` (RFC 8693) để đổi token của người dùng lấy token hẹp hơn khi đi sâu qua nhiều service. Phía gọi dùng cùng `OAuth2ClientHttpRequestInterceptor` của bài này với một registration kiểu `client_credentials`.

</Reveal>

<Callout kind="ai">

Nhờ AI sinh realm JSON cho Keycloak, cấu hình client trong Spring Authorization Server, hay viết đoạn `fetch` gửi header CSRF. AI hay đề xuất lưu token vào `localStorage` "cho đơn giản", hay dùng implicit flow (đã bị loại khỏi OAuth 2.1), hay tắt CSRF ở BFF vì "đây là API", hay dùng chung tên máy cho BFF và authorization server khi chạy local, và hay viết `TokenRelay` cho Spring Cloud Gateway bản WebFlux trong một ứng dụng MVC. Kiểm tra lại bằng các bước của lab: đếm `eyJ` trong cookie jar, thử POST thiếu header CSRF, và đăng nhập lại sau khi đăng xuất xem có bị hỏi mật khẩu không.

</Callout>
