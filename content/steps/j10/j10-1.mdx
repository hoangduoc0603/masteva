<Goal>

Hiểu HTTP ở mức đủ để thiết kế và gỡ lỗi một API: phương thức nói gì về thao tác, status code nói gì về kết quả, header mang thông tin gì. Học xong bài này, bạn tự dựng được một API đơn hàng chỉ bằng JDK và giải thích được:

- Vì sao tạo đơn nên trả `201 Created` kèm header `Location`, không chỉ `200 OK`.
- Khi nào trả `400`, khi nào `422`, khi nào `409`, và vì sao `405` phải kèm header `Allow`.
- Vì sao `/getOrder?id=1` hay `/orders/1/delete` là URL nên tránh.

</Goal>

<Knowledge>

### Một lần trao đổi HTTP

HTTP là giao thức hỏi và đáp dạng văn bản: client gửi một **request**, server trả đúng một **response**. Với HTTP/1.1, những gì đi trên dây trông như sau:

```text
POST /v1/orders HTTP/1.1                 request line: phương thức, đường dẫn, phiên bản
Host: localhost:8765                     header: cặp tên và giá trị
Content-Type: application/json           body bên dưới là JSON
Accept: application/json                 client muốn nhận JSON
                                         dòng trống: hết phần header
{"customer":"An","total":120000}         body

HTTP/1.1 201 Created                     status line: phiên bản, status code, reason phrase
Location: /v1/orders/1                   resource vừa tạo nằm ở đâu
Content-Type: application/json

{"id":1,"customer":"An","total":120000,"status":"NEW"}
```

HTTP/2 và HTTP/3 đóng gói khác (nhị phân, nhiều request trên một kết nối) nhưng giữ nguyên **ngữ nghĩa**: vẫn phương thức, status code, header và body như trên. Mọi thứ trong bài này áp dụng cho cả ba. Lệnh `curl -i` in ra status line và header của response, nên nó là công cụ chính để quan sát.

### Phương thức: safe và idempotent

RFC 9110 gắn cho mỗi phương thức một ý nghĩa. Hai tính chất quan trọng nhất:

- **Safe** (an toàn): client không yêu cầu thay đổi gì trên server. Crawler, cache, trình duyệt được phép tự gửi lại request safe.
- **Idempotent** (lũy đẳng): gửi một lần hay nhiều lần, trạng thái trên server sau cùng như nhau. Client được phép tự gửi lại khi không biết lần trước đã tới server hay chưa. Bài J10.2 đi sâu vào tính chất này.

| Phương thức | Ý nghĩa | Safe | Idempotent | Ví dụ trong lab |
|---|---|---|---|---|
| `GET` | Đọc biểu diễn hiện tại của resource | Có | Có | `GET /v1/orders/1` |
| `HEAD` | Như GET nhưng chỉ lấy header | Có | Có | Kiểm tra resource có tồn tại |
| `POST` | Gửi dữ liệu để resource xử lý, thường là tạo mới trong collection | Không | Không | `POST /v1/orders` |
| `PUT` | Thay toàn bộ resource bằng biểu diễn gửi lên | Không | Có | Lab không dùng |
| `PATCH` | Sửa một phần resource | Không | Không bắt buộc | `PATCH /v1/orders/1` đổi trạng thái |
| `DELETE` | Xoá resource | Không | Có | `DELETE /v1/orders/2` |
| `OPTIONS` | Hỏi resource hỗ trợ những gì | Có | Có | Trình duyệt dùng cho CORS |

Đây là **hợp đồng**, không phải thứ framework tự đảm bảo. Bạn viết một `GET /orders/1/cancel` có huỷ đơn thì code vẫn chạy, nhưng proxy, crawler hay tính năng tải trước của trình duyệt có thể huỷ đơn thay người dùng.

<Check id="j10.1.method-semantics">Phân biệt được safe với idempotent, và kể được phương thức nào có tính chất nào.</Check>

### Status code

Status code là số ba chữ số; chữ số đầu cho biết nhóm. Client, proxy, công cụ giám sát và retry đều đọc số này trước khi đọc body.

| Nhóm | Nghĩa | Ai phải sửa |
|---|---|---|
| `2xx` | Thành công | Không ai |
| `3xx` | Đi nơi khác (redirect, dùng cache) | Client đi theo |
| `4xx` | Request sai | Client: gửi lại y hệt cũng sai y hệt (trừ vài mã như 408, 429) |
| `5xx` | Server lỗi | Server: client có thể thử lại sau |

Những mã bạn sẽ dùng thường xuyên:

| Mã | Khi nào |
|---|---|
| `200 OK` | Đọc hoặc sửa thành công, có body |
| `201 Created` | Đã tạo resource mới; kèm `Location` trỏ tới nó |
| `204 No Content` | Thành công, không có body (thường là DELETE) |
| `400 Bad Request` | Request hỏng về cú pháp: JSON sai, query không đọc được |
| `401` / `403` | Chưa xác thực / đã xác thực nhưng không có quyền |
| `404 Not Found` | Không có resource ở URL này |
| `405 Method Not Allowed` | URL có, phương thức không; bắt buộc kèm `Allow` |
| `406 Not Acceptable` | Không trả được định dạng mà `Accept` yêu cầu |
| `409 Conflict` | Xung đột với trạng thái hiện tại, ví dụ xoá đơn đã thanh toán |
| `415 Unsupported Media Type` | Server không đọc được `Content-Type` của body |
| `422 Unprocessable Content` | Cú pháp đúng nhưng dữ liệu vi phạm quy tắc, ví dụ tổng tiền âm |
| `429 Too Many Requests` | Gọi quá nhiều; thường kèm `Retry-After` |
| `500` / `503` | Lỗi không lường trước / tạm thời không phục vụ được |

Ranh giới `400` và `422`: JSON thiếu dấu ngoặc là `400`, vì server không đọc nổi. JSON đọc được nhưng `total` là `-5` là `422`, vì server hiểu nhưng không chấp nhận.

<Callout kind="production">

Một API trả `200 OK` cho mọi request, kể cả khi lỗi, kèm body `{"success": false}`. Dashboard giám sát chỉ đếm `5xx` nên luôn xanh trong lúc 30% đơn hàng thất bại. Load balancer không biết instance nào hỏng. Thư viện client không retry được vì không phân biệt được lỗi tạm thời với lỗi vĩnh viễn. Status code đúng là thứ cho phép cả hệ thống xung quanh API hiểu chuyện gì đang xảy ra.

</Callout>

<Check id="j10.1.status-choice">Chọn được status code cho tạo mới, xoá, JSON hỏng, dữ liệu sai quy tắc và xung đột trạng thái, kèm lý do.</Check>

### Header thường gặp

| Header | Chiều | Việc nó làm |
|---|---|---|
| `Content-Type` | Cả hai | Kiểu của body đang gửi, ví dụ `application/json` |
| `Accept` | Request | Kiểu body client muốn nhận; server không đáp ứng được thì có thể trả `406`, hoặc bỏ qua `Accept` và trả kiểu mặc định |
| `Location` | Response | URL của resource vừa tạo (`201`) hoặc nơi cần đi tới (`3xx`) |
| `Allow` | Response | Các phương thức URL này hỗ trợ, bắt buộc khi trả `405` |
| `Cache-Control` | Cả hai | Quy tắc cache; `no-store` nghĩa là không được lưu bản sao ở đâu cả |

Tên header **không phân biệt hoa thường**. `HttpServer` của JDK in `Content-type` còn Spring in `Content-Type`; cả hai đúng. Code đọc header phải so sánh không phân biệt hoa thường, và `HttpExchange.getRequestHeaders().getFirst(...)` đã làm điều đó.

Lab đặt `Cache-Control: no-store` cho mọi phản hồi, vì đơn hàng là dữ liệu riêng và thay đổi liên tục. Với dữ liệu công khai, ít đổi như danh mục sản phẩm, `Cache-Control: public, max-age=60` cho phép CDN giữ bản sao 60 giây và giảm tải cho server.

### Resource và URL

REST (Representational State Transfer) là phong cách kiến trúc do Roy Fielding mô tả. Ý chính dùng hằng ngày: hệ thống được mô hình hoá thành các **resource** (tài nguyên), mỗi resource có một URI, và thao tác lên nó bằng phương thức HTTP. URL là **danh từ**, phương thức là **động từ**.

| Nên | Tránh | Vì sao |
|---|---|---|
| `GET /v1/orders/42` | `GET /getOrder?id=42` | Động từ đã nằm ở phương thức |
| `POST /v1/orders` | `POST /v1/orders/create` | Tạo mới là POST vào collection |
| `DELETE /v1/orders/42` | `GET /v1/orders/42/delete` | GET phải safe |
| `GET /v1/orders?status=NEW` | `GET /v1/orders/status/NEW` | Lọc là tuỳ chọn, đặt ở query string |
| `GET /v1/customers/7/orders` | `GET /v1/customers/7/orders/42/items/3/notes` | Lồng một cấp là đủ; sâu hơn thì cho resource con URL riêng |
| `/v1/orders` | `/v1/OrderTable.php` | URL không lộ cách cài đặt; đổi PHP sang Java không được đổi URL |

Quy ước trong lab: collection là danh từ số nhiều `/v1/orders`, một phần tử là `/v1/orders/{id}`. Ký tự ngoài ASCII trong URL phải được **percent-encode** theo RFC 3986: chữ `ì` trong "Bình" là hai byte UTF-8 `C3 AC`, nên `Bình` trong query string thành `B%C3%ACnh`.

<Check id="j10.1.url-design">Sửa được một URL kiểu `/getOrder?id=42` hay `/orders/42/delete` thành URL theo resource và chọn đúng phương thức.</Check>

import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

/** JSON tối giản cho lab: ghi Map, List, String, Number, Boolean, null; chỉ đọc object phẳng. */
public final class Json {
    private Json() {}

    public static String write(Object value) {
        return switch (value) {
            case null -> "null";
            case String s -> "\"" + s.replace("\\", "\\\\").replace("\"", "\\\"").replace("\n", "\\n") + "\"";
            case Number n -> n.toString();
            case Boolean b -> b.toString();
            case Map<?, ?> map -> "{" + String.join(",", map.entrySet().stream()
                    .map(e -> write(e.getKey().toString()) + ":" + write(e.getValue())).toList()) + "}";
            case List<?> list -> "[" + String.join(",", list.stream().map(Json::write).toList()) + "]";
            default -> throw new IllegalArgumentException("Không ghi được " + value.getClass());
        };
    }

    /** Đọc {"a":"x","b":12,"c":true}. Sai cú pháp thì ném IllegalArgumentException. */
    public static Map<String, Object> parseObject(String text) {
        var p = new Parser(text);
        var result = new LinkedHashMap<String, Object>();
        p.expect('{');
        if (!p.tryRead('}')) {
            do {
                String key = p.string();
                p.expect(':');
                result.put(key, p.value());
            } while (p.tryRead(','));
            p.expect('}');
        }
        if (p.skip() != text.length()) throw new IllegalArgumentException("thừa ký tự ở vị trí " + p.pos);
        return result;
    }

    private static final class Parser {
        final String s;
        int pos;

        Parser(String s) { this.s = s; }

        int skip() {
            while (pos < s.length() && Character.isWhitespace(s.charAt(pos))) pos++;
            return pos;
        }

        char next() {
            if (pos >= s.length()) throw new IllegalArgumentException("hết dữ liệu giữa chừng");
            return s.charAt(pos++);
        }

        boolean tryRead(char c) {
            if (skip() < s.length() && s.charAt(pos) == c) { pos++; return true; }
            return false;
        }

        void expect(char c) {
            if (!tryRead(c)) throw new IllegalArgumentException("cần '" + c + "' ở vị trí " + pos);
        }

        String string() {
            expect('"');
            var sb = new StringBuilder();
            for (char c = next(); c != '"'; c = next()) {
                if (c != '\\') { sb.append(c); continue; }
                char e = next();
                if (e == 'u') sb.append((char) Integer.parseInt("" + next() + next() + next() + next(), 16));
                else sb.append(e == 'n' ? '\n' : e == 't' ? '\t' : e);
            }
            return sb.toString();
        }

        Object value() {
            if (skip() < s.length() && s.charAt(pos) == '"') return string();
            for (String word : List.of("true", "false", "null")) {
                if (s.startsWith(word, pos)) {
                    pos += word.length();
                    return word.equals("null") ? null : Boolean.valueOf(word);
                }
            }
            int start = pos;
            while (pos < s.length() && "+-0123456789.eE".indexOf(s.charAt(pos)) >= 0) pos++;
            String number = s.substring(start, pos);
            if (number.isEmpty()) throw new IllegalArgumentException("giá trị không hợp lệ ở vị trí " + start);
            if (number.matches("-?\\d+")) return Long.parseLong(number);
            return Double.parseDouble(number);
        }
    }
}

import com.sun.net.httpserver.HttpExchange;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.util.Map;

/** Gửi phản hồi và đọc request. */
public final class Http {
    private Http() {}

    public static void send(HttpExchange ex, int status, String contentType, String body) throws IOException {
        ex.getResponseHeaders().set("Cache-Control", "no-store");
        if (body == null) {
            ex.sendResponseHeaders(status, -1);
            return;
        }
        byte[] bytes = body.getBytes(StandardCharsets.UTF_8);
        ex.getResponseHeaders().set("Content-Type", contentType);
        ex.sendResponseHeaders(status, bytes.length);
        ex.getResponseBody().write(bytes);
    }

    public static void json(HttpExchange ex, int status, Object value) throws IOException {
        send(ex, status, "application/json", Json.write(value));
    }

    public static void requireAcceptJson(HttpExchange ex) {
        String accept = ex.getRequestHeaders().getFirst("Accept");
        if (accept == null) return;
        for (String range : accept.split(",")) {
            String type = range.split(";")[0].strip();
            if (type.equals("*/*") || type.equals("application/*") || type.equals("application/json")) return;
        }
        throw new ApiException(406, "not-acceptable", "API chỉ trả application/json");
    }

    public static Map<String, Object> readJson(HttpExchange ex) throws IOException {
        String type = ex.getRequestHeaders().getFirst("Content-Type");
        if (type == null || !type.toLowerCase().startsWith("application/json")) {
            throw new ApiException(415, "unsupported-media-type", "Content-Type phải là application/json");
        }
        String text = new String(ex.getRequestBody().readAllBytes(), StandardCharsets.UTF_8);
        try {
            return Json.parseObject(text);
        } catch (IllegalArgumentException e) {
            throw new ApiException(400, "invalid-json", "Body không phải JSON object hợp lệ: " + e.getMessage());
        }
    }
}

import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpHandler;
import java.io.IOException;
import java.util.LinkedHashMap;
import java.util.Map;

/** Nơi duy nhất đổi lỗi thành phản hồi HTTP. */
public final class Errors {
    private Errors() {}

    public interface Route {
        void handle(HttpExchange ex) throws IOException;
    }

    public static HttpHandler wrap(Route route) {
        return ex -> {
            try {
                route.handle(ex);
            } catch (ApiException e) {
                send(ex, e);
            } finally {
                ex.close();
            }
        };
    }

    static void send(HttpExchange ex, ApiException e) throws IOException {
        var body = new LinkedHashMap<String, Object>();
        body.put("error", e.code());
        body.put("message", e.getMessage());
        if (!e.errors().isEmpty()) body.put("errors", e.errors());
        Http.json(ex, e.status(), body);
    }

    public static Map<String, String> field(String name, String message) {
        var error = new LinkedHashMap<String, String>();
        error.put("field", name);
        error.put("message", message);
        return error;
    }
}

/** Resource /v1/orders (collection) và /v1/orders/{id} (một đơn). Dữ liệu chỉ nằm trong bộ nhớ. */
public class OrdersApi {
    private static final List<String> STATUSES = List.of("NEW", "PAID", "CANCELLED");
    private final Map<Long, Order> orders = new ConcurrentSkipListMap<>();
    private final AtomicLong nextId = new AtomicLong(1);

    public void handle(HttpExchange ex) throws IOException {
        Http.requireAcceptJson(ex);
        String path = ex.getRequestURI().getPath();
        String[] parts = path.split("/"); // "/v1/orders/7" -> ["", "v1", "orders", "7"]
        if (parts.length < 3 || parts.length > 4 || !parts[1].equals("v1") || !parts[2].equals("orders")) {
            throw new ApiException(404, "not-found", "Không có resource " + path);
        }
        String method = ex.getRequestMethod();
        if (parts.length == 3) {
            switch (method) {
                case "GET" -> Http.json(ex, 200, Map.of("items", orders.values().stream().map(this::toJson).toList()));
                case "POST" -> create(ex);
                default -> notAllowed(ex, "GET, POST");
            }
            return;
        }
        Order order = find(parts[3]);
        switch (method) {
            case "GET" -> Http.json(ex, 200, toJson(order));
            case "PATCH" -> changeStatus(ex, order);
            case "DELETE" -> delete(ex, order);
            default -> notAllowed(ex, "GET, PATCH, DELETE");
        }
    }

    private void create(HttpExchange ex) throws IOException {
        Map<String, Object> body = Http.readJson(ex);
        var errors = new ArrayList<Map<String, String>>();
        if (!(body.get("customer") instanceof String c) || c.isBlank()) {
            errors.add(Errors.field("customer", "bắt buộc, là chuỗi khác rỗng"));
        }
        if (!(body.get("total") instanceof Long t) || t <= 0) {
            errors.add(Errors.field("total", "bắt buộc, là số nguyên dương (đồng)"));
        }
        if (!errors.isEmpty()) {
            throw new ApiException(422, "validation-failed", "Dữ liệu đơn hàng không hợp lệ", errors);
        }
        var order = new Order(nextId.getAndIncrement(), (String) body.get("customer"), (Long) body.get("total"), "NEW");
        orders.put(order.id(), order);
        ex.getResponseHeaders().set("Location", "/v1/orders/" + order.id());
        Http.json(ex, 201, toJson(order));
    }

    private void changeStatus(HttpExchange ex, Order order) throws IOException {
        Map<String, Object> body = Http.readJson(ex);
        String status = (String) body.get("status");
        if (status == null || !STATUSES.contains(status)) {
            throw new ApiException(422, "validation-failed", "Trạng thái không hợp lệ",
                    List.of(Errors.field("status", "một trong NEW, PAID, CANCELLED")));
        }
        boolean allowed = status.equals(order.status()) || order.status().equals("NEW");
        if (!allowed) {
            throw new ApiException(409, "invalid-state",
                    "Không chuyển được đơn " + order.id() + " từ " + order.status() + " sang " + status);
        }
        Order updated = order.withStatus(status);
        orders.put(updated.id(), updated);
        Http.json(ex, 200, toJson(updated));
    }

    private void delete(HttpExchange ex, Order order) throws IOException {
        if (order.status().equals("PAID")) {
            throw new ApiException(409, "invalid-state", "Đơn " + order.id() + " đã thanh toán, không xoá được");
        }
        orders.remove(order.id());
        Http.send(ex, 204, null, null);
    }

    private Order find(String rawId) {
        Order order = rawId.matches("\\d{1,18}") ? orders.get(Long.parseLong(rawId)) : null;
        if (order == null) throw new ApiException(404, "not-found", "Không có đơn hàng " + rawId);
        return order;
    }

    private static void notAllowed(HttpExchange ex, String allow) {
        ex.getResponseHeaders().set("Allow", allow);
        throw new ApiException(405, "method-not-allowed", ex.getRequestMethod() + " không dùng được ở đây");
    }

    private Map<String, Object> toJson(Order o) {
        var json = new LinkedHashMap<String, Object>();
        json.put("id", o.id());
        json.put("customer", o.customer());
        json.put("total", o.total());
        json.put("status", o.status());
        return json;
    }
}

Vài chỗ đáng đọc kỹ:

- `Json.write` dùng `switch` theo pattern (Java 21) để chọn cách ghi cho từng kiểu. `parseObject` trả `Long` cho số nguyên và `Double` cho số thực, nên `instanceof Long` trong `create` loại được `"total": 1.5`.

- Mọi lỗi có chủ đích đều là `ApiException`; `Errors.wrap` bắt nó ở một chỗ và ghi phản hồi lỗi. Bài J10.3 chỉ cần thay `Errors.java` để đổi định dạng lỗi cho toàn API.

<Predict question="Lệnh thứ hai giống hệt lệnh tạo đơn ở bước 4, chỉ thiếu -H. Vì sao nó bị từ chối, và với mã nào?">

`415 Unsupported Media Type`. Khi có `-d` mà không có `-H 'Content-Type: ...'`, curl tự gửi `Content-Type: application/x-www-form-urlencoded`, kiểu của form HTML. Server chỉ đọc JSON nên từ chối, dù body trông giống JSON. Server không đoán kiểu body từ nội dung.

</Predict>

{"error":"method-not-allowed","message":"PUT không dùng được ở đây"}
HTTP/1.1 415 Unsupported Media Type
{"error":"unsupported-media-type","message":"Content-Type phải là application/json"}
HTTP/1.1 400 Bad Request
{"error":"invalid-json","message":"Body không phải JSON object hợp lệ: cần '\"' ở vị trí 17"}
HTTP/1.1 422 
{"error":"validation-failed","message":"Dữ liệu đơn hàng không hợp lệ","errors":[{"field":"customer","message":"bắt buộc, là chuỗi khác rỗng"},{"field":"total","message":"bắt buộc, là số nguyên dương (đồng)"}]}

HTTP/1.1 404 Not Found
{"error":"not-found","message":"Không có đơn hàng 99"}

Ở đây chỉ giữ status line, header `Allow` và body. Ba điều đáng chú ý:

- `405` kèm `Allow`, nên client biết ngay URL này nhận gì thay vì đoán.
- `422` báo **mọi** field sai trong một lần. Client sửa cả form một lượt, không phải gửi đi gửi lại.

<Reveal title="PUT hay PATCH để đổi trạng thái đơn?">

`PUT` thay **toàn bộ** resource: client phải gửi đủ mọi field, field nào thiếu bị coi là bỏ đi. Nó idempotent vì gửi lại cùng biểu diễn cho cùng kết quả. `PATCH` chỉ gửi phần thay đổi, hợp với "đổi trạng thái" khi đơn có hàng chục field. Định dạng chuẩn cho PATCH kiểu này là JSON Merge Patch (RFC 7396, `Content-Type: application/merge-patch+json`); lab chấp nhận `application/json` cho gọn. Nhiều API còn tách hành động nghiệp vụ thành resource riêng như `POST /orders/1/payments`, vì "thanh toán" là một sự kiện có dữ liệu riêng, không chỉ là đổi một field.

</Reveal>

<Reveal title="Người dùng không có quyền xem đơn 42: trả 403 hay 404?">

`403` nói thật "đơn có tồn tại nhưng bạn không được xem". Như vậy kẻ dò ID biết được đơn nào tồn tại. Với dữ liệu riêng tư, nhiều API trả `404` cho cả hai trường hợp để không lộ thông tin. Chọn cách nào là quyết định bảo mật; quan trọng là thống nhất trên toàn API.

</Reveal>

<Reveal title="Lồng URL tới đâu là vừa?">

`/customers/7/orders` hợp lý khi đơn luôn thuộc về một khách và bạn hay liệt kê theo khách. Nhưng mỗi đơn đã có ID riêng, nên `GET /orders/42` nên dùng được trực tiếp, không bắt client biết `customerId` trước. Quy tắc thực dụng: lồng tối đa một cấp, và mọi resource có ID duy nhất toàn cục đều có URL riêng ở cấp cao nhất. `GET /orders?customer=7` là cách khác cho cùng câu hỏi, linh hoạt hơn khi muốn lọc thêm theo trạng thái.

</Reveal>

<Reveal title="Sao không chạy server bằng java src/Main.java như ở J1?">

Chạy được, vì từ Java 22 trình chạy file nguồn tự tìm các file khác cùng thư mục. Nhưng mỗi lần khởi động nó biên dịch lại toàn bộ trong bộ nhớ và chỉ báo lỗi biên dịch khi chạy. `javac -d out` tách hai bước: lỗi biên dịch hiện ra trước, và `out/` là thứ bạn có thể đóng gói. Với project nhiều file như lab này, tách bước giúp đọc lỗi dễ hơn.

</Reveal>

<Callout kind="ai">

Nhờ AI sinh nhanh các lệnh `curl` cho từng trường hợp, hoặc rà một bảng endpoint xem phương thức và status code đã hợp lý chưa. AI hay trả `200` cho thao tác tạo mới, quên `Location`, dùng `400` cho mọi lỗi, đặt động từ vào URL, và viết code JSON tay có lỗi khó thấy. Ví dụ `s.matches("-?\\d+") ? Long.parseLong(s) : Double.parseDouble(s)` trông đúng nhưng luôn trả `Double`: hai nhánh của toán tử `?:` có kiểu `long` và `double` nên Java đổi cả hai về `double`. Cách kiểm tra là chạy `curl -i` cho từng trường hợp, như bước 5, và đối chiếu status code với bảng của RFC 9110.

</Callout>
