<Goal>

Biến API của lab thành thứ người khác dùng được mà không cần đọc code: lỗi nào cũng cùng một định dạng chuẩn, và có một đặc tả máy đọc được mô tả từng endpoint. Học xong bài này, bạn giải thích được:

<Knowledge>

### Vì sao cần một định dạng lỗi chung

Lỗi của lab đang có dạng `{"error": "...", "message": "..."}`, do chính ta nghĩ ra. API khác dùng `{"code": 4001, "msg": "..."}`, API khác nữa dùng `{"errors": [...]}`. Mỗi client phải viết code đọc lỗi riêng cho từng API, và API gateway hay thư viện dùng chung không làm được gì với chúng.

**Problem Details for HTTP APIs** (RFC 9457, thay cho RFC 7807) chuẩn hoá thân lỗi thành một object JSON có kiểu `application/problem+json`:

```json
{
  "type": "https://example.com/problems/validation-failed",
  "title": "Dữ liệu không hợp lệ",
  "status": 422,
  "detail": "Dữ liệu đơn hàng không hợp lệ",
  "instance": "/v2/orders",
  "errors": [{ "pointer": "#/amount", "detail": "bắt buộc, là số nguyên dương (đồng)" }]
}
```

| Trường | Ý nghĩa | Ai đọc |
|---|---|---|
| `type` | URI reference định danh **loại** lỗi; không có thì mặc định là `about:blank` | Code client: rẽ nhánh theo trường này |
| `title` | Tóm tắt ngắn của loại lỗi, giống nhau ở mọi lần xảy ra | Người đọc |
| `status` | Status code, lặp lại cho tiện; phải khớp status thật của response | Cả hai |
| `detail` | Giải thích **lần xảy ra này** | Người đọc; code không nên phân tích chuỗi này |
| `instance` | URI chỉ lần xảy ra cụ thể, ví dụ đường dẫn của request | Người tra log |
| Trường mở rộng | Thêm tuỳ ý, ví dụ `errors` liệt kê lỗi theo field | Code client |

Trường `errors` với `pointer` (JSON Pointer tới field sai) và `detail` theo đúng ví dụ trong RFC 9457. Client đọc `type` để biết phải làm gì, đọc `errors` để tô đỏ đúng ô trong form. `type` nên là URL dẫn tới trang mô tả lỗi; khi đã công bố thì không đổi, vì code client phụ thuộc vào nó.

<Check id="j10.3.problem-fields">Kể được năm trường chuẩn của Problem Details, trường nào cho code client và trường nào cho người đọc.</Check>

### Không lộ thông tin nội bộ

Lỗi có chủ đích (`ApiException`) mang thông điệp viết cho client. Lỗi **không** lường trước, như một `ClassCastException` hay mất kết nối database, thì khác: thông điệp và stack trace của nó chứa tên lớp, câu SQL, phiên bản thư viện, đường dẫn file. Đưa chúng ra response là cho kẻ tấn công bản đồ hệ thống của bạn.

```text
 Request -> Errors.wrap -> OrdersApi.handle
                |
                +-- ApiException (lỗi có chủ đích)
                |      -> problem: type, title, status, detail do ta viết
                |
                +-- RuntimeException khác (lỗi không lường trước)
                       -> sinh errorId
                       -> ghi errorId + method + URI + stack trace vào log server
                       -> problem 500, detail chỉ chứa errorId
```

Client nhận `500` kèm mã tra cứu; người vận hành dùng mã đó tìm đúng stack trace trong log. Hai phía đều có đủ thông tin, và không có gì nội bộ lọt ra ngoài.

<Callout kind="production">

Một API trả nguyên `e.getMessage()` của exception cho client. Khi database lỗi, response chứa câu SQL đầy đủ kèm tên bảng và cột; khi thư viện parse lỗi, response lộ tên và phiên bản thư viện, đủ để tra danh sách lỗ hổng đã biết. OWASP xếp việc này vào nhóm lỗi cấu hình bảo mật. Quy tắc: detail của `5xx` chỉ chứa thông điệp chung và mã tra cứu; mọi chi tiết vào log.

</Callout>

<Check id="j10.3.no-leak">Giải thích được vì sao không trả stack trace hay thông điệp exception cho client, và làm sao vẫn tra được lỗi nhờ mã tra cứu.</Check>

### OpenAPI

**OpenAPI** là đặc tả máy đọc được của một HTTP API, viết bằng YAML hoặc JSON: có những endpoint nào, nhận tham số và body gì, trả gì với từng status code. Từ một file OpenAPI, công cụ có thể sinh trang tài liệu, sinh code client cho nhiều ngôn ngữ, dựng mock server và kiểm tra response thật có đúng hợp đồng không.

| Phần | Chứa gì | Trong lab |
|---|---|---|
| `openapi` | Phiên bản của đặc tả OpenAPI | `3.1.0` |
| `info` | Tên, phiên bản **API của bạn**, mô tả, giấy phép | `Orders API`, `2.0.0` |
| `servers` | URL gốc | `http://localhost:8765/v2` |
| `paths` | Từng đường dẫn, từng phương thức: tham số, request body, responses | `/orders`, `/orders/{id}` |
| `components` | Phần dùng lại: `schemas`, `responses`, `parameters` | `Order`, `NewOrder`, `Problem` |
| `$ref` | Trỏ tới một phần trong `components` | `$ref: '#/components/schemas/Order'` |

Schema trong OpenAPI 3.1 là JSON Schema (bản 2020-12): `type`, `required`, `enum`, `minimum` mô tả đúng các quy tắc mà code kiểm tra. Bản mới nhất của đặc tả là 3.2; lab dùng 3.1 vì đã được hầu hết công cụ hỗ trợ. Trước khi dùng 3.2, kiểm tra công cụ của bạn đã đọc được nó chưa.

Có hai cách làm việc:

| | Design-first | Code-first |
|---|---|---|
| Thứ tự | Viết OpenAPI, review, rồi mới code | Viết code, sinh OpenAPI từ annotation |
| Hợp với | API công khai, nhiều đội cùng dùng | Service nội bộ, một đội tự làm cả hai phía |
| Rủi ro | Code lệch khỏi đặc tả nếu không kiểm tra tự động | Đặc tả chỉ tốt bằng annotation; thiết kế bị dẫn dắt bởi code |

Lab theo design-first ở quy mô nhỏ: viết tay `openapi.yaml`, kiểm tra bằng **Redocly CLI** (công cụ lint mã nguồn mở), rồi phục vụ nó ngay tại `GET /openapi.yaml` để đặc tả đi cùng service.

<Check id="j10.3.openapi-structure">Đọc được một file OpenAPI: tìm ra endpoint, tham số, schema của body và các response lỗi của nó.</Check>

</Knowledge>

### 2. Đổi Errors.java sang Problem Details

Thay `Errors.java` và `Main.java`. `Errors` mới ghi mọi lỗi theo RFC 9457, bắt thêm `RuntimeException` để trả `500` có mã tra cứu, và `field` sinh `pointer` và `detail` như ví dụ của RFC. `Main` thêm đường dẫn `/openapi.yaml`, dùng ở bước 5. `OrdersApi.java` không phải sửa dòng nào, vì mọi lỗi đều đi qua `Errors.wrap`.

<Terminal where="mac" title="Thay src/Errors.java và src/Main.java">

```bash
cd ~/masteva-j10
cat > src/Errors.java <<'EOF'
import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpHandler;
import java.io.IOException;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.UUID;

/** Nơi duy nhất đổi lỗi thành phản hồi HTTP, theo RFC 9457 (application/problem+json). */
public final class Errors {
    private Errors() {}

    /** title cố định cho từng loại lỗi; chi tiết của từng lần nằm ở detail. */
    private static final Map<String, String> TITLES = Map.ofEntries(
            Map.entry("not-found", "Không tìm thấy resource"),
            Map.entry("method-not-allowed", "Phương thức không được hỗ trợ"),
            Map.entry("not-acceptable", "Không có định dạng phản hồi phù hợp"),
            Map.entry("unsupported-media-type", "Content-Type không được hỗ trợ"),
            Map.entry("invalid-json", "Body không phải JSON hợp lệ"),
            Map.entry("invalid-query", "Tham số truy vấn không hợp lệ"),
            Map.entry("validation-failed", "Dữ liệu không hợp lệ"),
            Map.entry("invalid-state", "Trạng thái đơn không cho phép thao tác này"),
            Map.entry("idempotency-key-reused", "Idempotency-Key đã dùng cho request khác"),
            Map.entry("internal-error", "Lỗi máy chủ"));

    public interface Route {
        void handle(HttpExchange ex) throws IOException;
    }

    public static HttpHandler wrap(Route route) {
        return ex -> {
            try {
                route.handle(ex);
            } catch (ApiException e) {
                send(ex, e);
            } catch (RuntimeException e) {
                String errorId = UUID.randomUUID().toString();
                System.err.println("errorId=" + errorId + " " + ex.getRequestMethod() + " " + ex.getRequestURI());
                e.printStackTrace();
                send(ex, new ApiException(500, "internal-error", "Lỗi không mong muốn, mã tra cứu " + errorId));
            } finally {
                ex.close();
            }
        };
    }

    static void send(HttpExchange ex, ApiException e) throws IOException {
        var body = new LinkedHashMap<String, Object>();
        body.put("type", "https://example.com/problems/" + e.code());
        body.put("title", TITLES.getOrDefault(e.code(), "Lỗi"));
        body.put("status", e.status());
        body.put("detail", e.getMessage());
        body.put("instance", ex.getRequestURI().getPath());
        if (!e.errors().isEmpty()) body.put("errors", e.errors());
        Http.send(ex, e.status(), "application/problem+json", Json.write(body));
    }

    /** Lỗi theo field, cùng dạng với ví dụ trong RFC 9457: pointer là JSON Pointer tới field. */
    public static Map<String, String> field(String name, String message) {
        var error = new LinkedHashMap<String, String>();
        error.put("pointer", "#/" + name);
        error.put("detail", message);
        return error;
    }
}
EOF
cat > src/Main.java <<'EOF'
import com.sun.net.httpserver.HttpServer;
import java.net.InetAddress;
import java.net.InetSocketAddress;
import java.nio.file.Files;
import java.nio.file.Path;

public class Main {
    public static void main(String[] args) throws Exception {
        var address = new InetSocketAddress(InetAddress.getLoopbackAddress(), 8765);
        var server = HttpServer.create(address, 0);
        var api = new OrdersApi();
        server.createContext("/", Errors.wrap(api::handle));
        server.createContext("/openapi.yaml", Errors.wrap(ex ->
                Http.send(ex, 200, "application/yaml", Files.readString(Path.of("openapi.yaml")))));
        server.start();
        System.out.println("Orders API: http://localhost:8765/v1/orders");
    }
}
EOF
```

</Terminal>

### 5. Viết đặc tả OpenAPI

File dưới đây mô tả phiên bản `v2`. Các `parameters` viết gọn trên một dòng bằng cú pháp `{ ... }` của YAML; nó tương đương với cách viết nhiều dòng.

<Terminal where="mac" title="Tạo ~/masteva-j10/openapi.yaml">

```bash
cd ~/masteva-j10
cat > openapi.yaml <<'EOF'
openapi: 3.1.0
info:
  title: Orders API
  version: 2.0.0
  description: API đơn hàng của lab Masteva J10. Mọi số tiền tính bằng đồng.
  license: { name: MIT, identifier: MIT }
servers:
  - url: http://localhost:8765/v2
security: []
tags:
  - { name: orders, description: Đơn hàng }
paths:
  /orders:
    get:
      tags: [orders]
      operationId: listOrders
      summary: Liệt kê đơn hàng, phân trang theo cursor
      parameters:
        - { name: status, in: query, schema: { $ref: '#/components/schemas/Status' } }
        - { name: customer, in: query, schema: { type: string } }
        - { name: sort, in: query, schema: { type: string, enum: [id, -id, amount, -amount], default: id } }
        - { name: limit, in: query, schema: { type: integer, minimum: 1, maximum: 100, default: 20 } }
        - name: pageToken
          in: query
          description: Lấy từ nextPageToken của trang trước, giữ nguyên các tham số khác.
          schema: { type: string }
      responses:
        '200':
          description: Một trang đơn hàng
          headers:
            Link: { description: 'Trang sau, rel="next"', schema: { type: string } }
          content:
            application/json: { schema: { $ref: '#/components/schemas/OrderPage' } }
        '400': { $ref: '#/components/responses/Problem' }
    post:
```

### Khi gặp lỗi

<Callout kind="pitfall">

- `command not found: npx` hoặc Redocly báo phiên bản Node quá cũ: cài Node.js bản LTS từ nodejs.org, rồi kiểm tra `node -v`.
- `npx` treo hoặc báo lỗi mạng: máy cần truy cập registry của npm; ở mạng công ty có thể phải cấu hình proxy cho npm.
- Lint báo lỗi ở một dòng YAML trông đúng: YAML phân biệt thụt lề; một dấu cách lệch làm khoá rơi sang cấp khác. Dùng đúng heredoc của bài, hoặc bật hiển thị khoảng trắng trong editor.
- `curl /openapi.yaml` nhận `Empty reply from server`: server được chạy từ thư mục khác nên không thấy `openapi.yaml`. `NoSuchFileException` là `IOException`, không phải `RuntimeException`, nên `Errors.wrap` không bắt nó. Chạy server từ `~/masteva-j10`.
- Vẫn nhận lỗi dạng `{"error": ...}`: server chưa khởi động lại sau khi thay `Errors.java`.

</Callout>

<DeepDive>

<Reveal title="Sửa lỗi ClassCastException thế nào cho đúng?">

`500` cùng mã tra cứu là lưới an toàn, không phải đích đến: request gửi `"status": 1` là lỗi của client, nên phải nhận `422` và biết sửa field nào. Sửa trong `changeStatus` bằng `if (!(body.get("status") instanceof String status) || !STATUSES.contains(status))` rồi ném `ApiException` 422, đúng cách `create` đã làm. Nguyên tắc chung: mọi dữ liệu từ ngoài vào phải được kiểm tra kiểu trước khi dùng. J11 giao việc này cho Bean Validation.

</Reveal>

<Reveal title="Nên dùng type riêng hay about:blank?">

`about:blank` nghĩa là "không có gì thêm ngoài status code"; khi đó `title` nên đúng bằng reason phrase như "Not Found". Nó hợp với lỗi chung chung. Khi client cần phân biệt hai lỗi cùng status, ví dụ hai loại `409` là "đơn đã thanh toán" và "kho hết hàng", thì mỗi loại cần một `type` riêng. Trước khi tự đặt, xem danh mục IANA có loại nào trùng ý nghĩa để dùng lại.

</Reveal>

<Reveal title="Làm sao biết code còn khớp với openapi.yaml?">

Lint chỉ kiểm tra file đặc tả tự nó có hợp lệ không, không biết server trả gì. Để bắt độ lệch, viết test gọi API thật rồi kiểm response theo schema trong đặc tả, hoặc dùng công cụ sinh request từ đặc tả để thử hàng loạt đầu vào. Cách khác là đảo chiều: sinh đặc tả từ code (code-first), như springdoc làm với Spring Boot ở J11, rồi so đặc tả mới với bản đã công bố để phát hiện thay đổi phá vỡ.

</Reveal>

<Reveal title="detail và title có nên dịch theo ngôn ngữ người dùng?">

Có thể: RFC 9457 cho phép `title` và `detail` đổi theo `Accept-Language`. Vì vậy code client tuyệt đối không được so sánh chuỗi `title` hay `detail`; nó dựa vào `type`, `status` và các trường mở rộng như `errors[].pointer`. Văn bản hiển thị cho người dùng cuối thường do chính app client quyết định từ `type`, không lấy nguyên `detail`.

</Reveal>

<Callout kind="ai">

Nhờ AI viết nháp file OpenAPI từ một bảng endpoint hoặc từ code, sinh ví dụ cho từng schema, hay liệt kê các loại lỗi cần `type` riêng. AI hay bịa trường không có trong đặc tả (ví dụ đặt `required: true` bên trong schema của OpenAPI 3.1), trộn cú pháp 3.0 với 3.1 (`nullable: true` không còn trong 3.1), viết `$ref` tới schema không tồn tại, và để `detail` của lỗi 500 chứa `e.getMessage()`. Luôn chạy Redocly CLI trên mọi đặc tả AI viết, và tự gửi một request gây lỗi 500 để xem response có lộ gì không.

</Callout>

<Callout kind="link">

J11 dùng `ProblemDetail` có sẵn của Spring cùng `@ControllerAdvice` để làm đúng việc của `Errors.wrap`, và springdoc để sinh OpenAPI từ code. J13 đi sâu vào những gì không được lộ ra ngoài. J15 đưa mã tra cứu vào log có cấu trúc và trace, để tìm lỗi trên nhiều service.

</Callout>
