<Goal>

Nâng cấp một service thật qua một bản major của Spring Boot và một bản LTS của Java theo cách lặp lại được: build xanh trước, công cụ làm phần cơ học, người đọc diff và sửa phần còn lại, test quyết định khi nào xong. Ghi lại những gì chưa sửa thành nợ kỹ thuật có chủ. Học xong bài này, bạn giải thích được:

- Vì sao một thư viện chạy im lặng trên Java 21 lại in bốn dòng `WARNING` trên Java 25, và vì sao một ngày nó sẽ ném exception.
- Vì sao sau khi nâng cấp, code biên dịch được và gần hết test xanh vẫn chưa đủ: một cấu hình bị bỏ qua lặng lẽ làm API nhận dữ liệu sai.
- Vì sao nên trả nợ kỹ thuật ở file thay đổi nhiều nhất, không phải ở file xấu nhất.

<Knowledge>

### Vì sao nâng cấp đều đặn

Mỗi dòng phiên bản chỉ được vá trong một khoảng thời gian. Lịch hỗ trợ miễn phí (OSS) của Spring Boot, lấy từ `api.spring.io` ngày 04/10/2026:

| Dòng | Phát hành | Hết hỗ trợ OSS |
|---|---|---|
| 3.5.x | 05/2025 | 30/06/2026 |
| 4.0.x | 11/2025 | 31/12/2026 |
| 4.1.x | 06/2026 | 31/07/2027 |

Java đi theo nhịp LTS hai năm một lần (J1.1): 21, rồi 25. Hết hỗ trợ nghĩa là lỗ hổng bảo mật mới không được vá trong bản miễn phí. Nâng cấp mỗi bản minor tốn vài giờ; bỏ qua ba bản rồi nâng một lần thì mọi thay đổi phá vỡ dồn lại, không biết lỗi nào do bản nào, và thường rơi đúng lúc có CVE phải vá gấp.

### Nâng cấp từng bước, mỗi bước một commit

```text
 build xanh, test đủ ──> bản patch mới nhất của dòng đang dùng, dọn hết deprecation warning
        │
        v
 major: Spring Boot 3.5 -> 4.0 (công cụ + sửa tay) ──> test xanh, commit
        │
        v
 minor: 4.0 -> 4.1 (đọc release notes) ──> test xanh, commit
        │
        v
 Java 21 -> 25 (có thể làm cùng hoặc tách riêng) ──> test xanh, chạy thử, commit
```

Deprecation ở bản cũ chính là danh sách việc của bản mới: API bị đánh dấu deprecated ở 3.x thường bị xoá ở 4.0. Những gì có thể vỡ khi nâng cấp, và cái gì bắt được nó:

| Loại thay đổi | Ví dụ ở bài này | Ai bắt được |
|---|---|---|
| API bị xoá hoặc chuyển package | `@MockBean`, `Jackson2ObjectMapperBuilderCustomizer` | Trình biên dịch |
| Thuộc tính cấu hình đổi tên | `server.error.include-message` | Không ai, nếu không có công cụ: key cũ bị bỏ qua lặng lẽ |
| Hành vi mặc định thay đổi | Jackson 3 thay Jackson 2 | Chỉ có test |
| Dùng API nội bộ của JDK | `sun.misc.Unsafe` | `jdeps`, cảnh báo lúc chạy |

### Công cụ: OpenRewrite và jdeps

**OpenRewrite** đọc mã nguồn thành **LST (Lossless Semantic Tree)**, một cây cú pháp có đủ thông tin kiểu và giữ nguyên định dạng, rồi chạy **recipe**: một chuỗi phép biến đổi được đặt tên. Recipe `org.openrewrite.java.spring.boot4.UpgradeSpringBoot_4_0` nằm trong artifact `rewrite-spring`; nó gọi lại các recipe 3.x, đổi parent, đổi tên starter, chuyển package, đổi key cấu hình. Recipe `org.openrewrite.java.migrate.UpgradeToJava25` trong `rewrite-migrate-java` đổi phiên bản Java và thay API deprecated. Plugin Maven chạy chúng mà không cần sửa `pom.xml`: goal `dryRun` chỉ sinh file patch, goal `run` sửa thẳng file. Lõi OpenRewrite theo giấy phép Apache 2.0; recipe trong `rewrite-spring` và `rewrite-migrate-java` theo Moderne Source Available License, nên đọc điều khoản nếu công ty bạn có quy định về giấy phép.

**`jdeps`** là công cụ có sẵn trong JDK, phân tích bytecode trong jar để liệt kê phụ thuộc. `jdeps --jdk-internals` chỉ ra chỗ nào dùng API nội bộ của JDK, kèm gợi ý thay thế. Chạy nó trên mọi jar, kể cả thư viện bên thứ ba, trước khi đổi bản Java.

`sun.misc.Unsafe` là ví dụ điển hình. JEP 471 (Java 23) đánh dấu các method truy cập bộ nhớ của nó là deprecated để xoá; JEP 498 (Java 24) bắt đầu in cảnh báo ở lần gọi đầu tiên. Tuỳ chọn `--sun-misc-unsafe-memory-access=deny` cho bạn chạy thử trước hành vi của các bản JDK sau, khi những method này bị chặn rồi bị xoá.

<Check id="j20.2.upgrade-path">Kể được thứ tự nâng cấp an toàn và với mỗi loại thay đổi (API bị xoá, key cấu hình đổi tên, hành vi mặc định, API nội bộ JDK) nói được công cụ nào bắt nó.</Check>

<Callout kind="production">

Một service tắt tracing bằng `management.tracing.enabled=false` để tiết kiệm chi phí. Đội nâng lên Spring Boot 4 bằng tay, sửa hết lỗi biên dịch, test xanh, deploy. Ở Boot 4 key đó đổi thành `management.tracing.export.enabled`; key cũ không còn ai đọc, không có lỗi, không có cảnh báo. Tracing bật lại ở tỉ lệ mặc định, và hoá đơn của hệ thống quan sát tháng đó tăng gấp nhiều lần. Recipe OpenRewrite đổi key này tự động; nếu nâng cấp bằng tay, thêm dependency `spring-boot-properties-migrator` trong lúc chuyển đổi để nó in cảnh báo cho mọi key đã đổi tên lúc khởi động.

</Callout>

### Nợ kỹ thuật

**Nợ kỹ thuật** là ẩn dụ của Ward Cunningham (1992): đi tắt trong thiết kế giống vay tiền. **Tiền gốc** là công để sửa cho đúng. **Tiền lãi** là công thêm phải trả mỗi lần đụng vào phần code đó. Nợ không xấu tự thân; nợ không ai biết, không ai ghi, không ai trả mới xấu.

Martin Fowler chia nợ theo hai trục, gọi là **technical debt quadrant**:

| | Liều lĩnh (reckless) | Thận trọng (prudent) |
|---|---|---|
| **Cố ý** | "Không có thời gian cho thiết kế" | "Ra mắt trước, ghi lại và trả sau" |
| **Vô tình** | "Layering là gì?" | "Giờ mới hiểu lẽ ra nên thiết kế thế nào" |

Cách làm việc với nợ ở cấp Senior:

- **Ghi lại**: mỗi khoản một mã, nằm trong một file hoặc issue tracker, có quadrant, lãi phải trả và điều kiện bắt buộc trả. Comment trong code trỏ về mã đó.
- **Ưu tiên theo lãi**: nợ ở file hai năm không ai sửa gần như không tốn lãi. Nợ ở file thay đổi mỗi tuần thì tốn lãi mỗi tuần. `git log` cho biết file nào thay đổi nhiều.
- **Trả dần trong kế hoạch**: kèm việc trả nợ vào tính năng đi qua vùng đó, hoặc dành một phần cố định của mỗi sprint. Kế hoạch "viết lại toàn bộ" thường kéo dài và tạo ra nợ mới.

<Check id="j20.2.debt-quadrant">Xếp được một khoản nợ vào đúng ô của quadrant và nói được tiền gốc, tiền lãi của nó.</Check>

package vn.masteva.transfers;

import jakarta.persistence.Entity;
import jakarta.persistence.Id;

@Entity
public class Account {
    @Id
    private Long id;
    private String owner;
    private long balance;

    protected Account() {
    }

    public Long getId() { return id; }
    public String getOwner() { return owner; }
    public long getBalance() { return balance; }

    void debit(long amount) {
        if (amount > balance) {
            throw new InsufficientFundsException(id, amount);
        }
        balance -= amount;
    }

    void credit(long amount) {
        balance += amount;
    }
}

package vn.masteva.transfers;

import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

@Service
public class TransferService {
    private final AccountRepository accounts;
    private final PaymentOrderRepository orders;

    public TransferService(AccountRepository accounts, PaymentOrderRepository orders) {
        this.accounts = accounts;
        this.orders = orders;
    }

    @Transactional
    public PaymentOrder transfer(long sourceId, long targetId, long amount) {
        if (amount <= 0 || sourceId == targetId) {
            throw new IllegalArgumentException("invalid transfer");
        }
        Account source = accounts.findById(sourceId).orElseThrow();
        Account target = accounts.findById(targetId).orElseThrow();
        source.debit(amount);
        target.credit(amount);
        return orders.save(new PaymentOrder(source, target, amount));
    }
}
EOF

`legacy-util` là thư viện nội bộ do một đội khác viết từ lâu, dùng `sun.misc.Unsafe` để cấp phát bộ nhớ ngoài heap. Biên dịch nó cho Java 21 rồi đóng thành jar:

package vn.masteva.legacy;

import java.lang.reflect.Field;
import sun.misc.Unsafe;

/** Thư viện cũ: cấp phát bộ nhớ ngoài heap bằng Unsafe. DEBT-1 */
public class OffHeapBuffer {
    private static final Unsafe UNSAFE = loadUnsafe();

    public static long sumOfSquares(int n) {
        long address = UNSAFE.allocateMemory(8L * n);
        try {
            for (int i = 0; i < n; i++) {
                UNSAFE.putLong(address + 8L * i, (long) i * i);
            }
            long sum = 0;
            for (int i = 0; i < n; i++) {
                sum += UNSAFE.getLong(address + 8L * i);
            }
            return sum;
        } finally {
            UNSAFE.freeMemory(address);
        }
    }

    private static Unsafe loadUnsafe() {
        try {
            Field field = Unsafe.class.getDeclaredField("theUnsafe");
            field.setAccessible(true);
            return (Unsafe) field.get(null);
        } catch (ReflectiveOperationException e) {
            throw new IllegalStateException(e);
        }
    }

    public static void main(String[] args) {
        System.out.println("sum=" + sumOfSquares(1_000));
    }
}
EOF

<Reveal title="Nâng Java và Spring Boot cùng lúc hay tách hai lần?">

Bài này làm cùng lúc vì project nhỏ và test đủ. Với service lớn, tách ra: lên Java 25 trước trên Spring Boot 3.5 (Boot 3.5 chạy được trên Java 25), deploy, theo dõi một tuần; rồi mới lên Boot 4. Khi có sự cố, bạn biết ngay do bản nào. Quy tắc chung: mỗi lần chỉ đổi một thứ lớn, trừ khi hai thứ buộc phải đi cùng nhau.

</Reveal>

<Reveal title="Jackson 3 còn đổi mặc định nào khác có thể làm vỡ API?">

Có. Ví dụ `FAIL_ON_NULL_FOR_PRIMITIVES` bật sẵn ở Jackson 3: request thiếu field kiểu `long` như `amount` trước nhận giá trị 0, giờ bị trả 400. Ở API tiền đó là thay đổi tốt, nhưng client cũ có thể vỡ. Danh sách đầy đủ nằm trong mục Jackson của Spring Boot 4.0 Migration Guide và tài liệu phát hành Jackson 3.0. Cách an toàn là có test hợp đồng API cho các request biên: thiếu field, field lạ, kiểu sai. Nếu cần thêm thời gian, `spring.jackson.use-jackson2-defaults=true` tạm đưa các mặc định về như Spring Boot từng dùng với Jackson 2; coi nó là công tắc tạm thời và ghi thành một khoản DEBT có hạn trả.

</Reveal>

<Reveal title="Trả DEBT-1 thế nào khi Unsafe bị chặn?">

Thay bằng Foreign Function and Memory API (`java.lang.foreign`, chính thức từ Java 22). `Arena` quản lý vòng đời vùng nhớ, `MemorySegment` có kiểm tra biên nên ghi lố không làm hỏng bộ nhớ của JVM:

```java
try (Arena arena = Arena.ofConfined()) {
    MemorySegment buffer = arena.allocate(ValueLayout.JAVA_LONG, n);
    for (int i = 0; i < n; i++) {
        buffer.setAtIndex(ValueLayout.JAVA_LONG, i, (long) i * i);
    }
    long sum = 0;
    for (int i = 0; i < n; i++) {
        sum += buffer.getAtIndex(ValueLayout.JAVA_LONG, i);
    }
    return sum;
}
```

Đoạn này chạy được cả với `--sun-misc-unsafe-memory-access=deny`, và `jdeps --jdk-internals` không còn báo gì. Trả xong thì xoá dòng DEBT-1 khỏi bảng và comment trong code cùng một commit.

</Reveal>

<Reveal title="Đội không có thời gian trả nợ. Thuyết phục thế nào?">

Nói bằng tiền lãi, không bằng thẩm mỹ. "Code này xấu" không thuyết phục ai; "mỗi tính năng chạm vào phần tiền tốn thêm khoảng nửa ngày, quý trước có 6 tính năng như vậy" thì có. Đề xuất trả kèm tính năng sắp làm ở đúng vùng đó, với ước lượng gốc nhỏ. Nợ có ngưỡng cứng như DEBT-3 thì không phải chuyện thuyết phục: đó là điều kiện ra mắt, ghi vào kế hoạch như mọi yêu cầu khác.

</Reveal>
