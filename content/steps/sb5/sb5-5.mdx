<Goal>

Khi deploy kiểu rolling, phiên bản cũ và mới của ứng dụng cùng chạy trên một database trong vài phút. Bài này đổi schema trong đúng khoảng thời gian đó, với ứng dụng thật trên PostgreSQL. Học xong bài này, bạn giải thích được:

- Vì sao một migration `RENAME COLUMN` chạy thành công lại làm phiên bản ứng dụng đang chạy trả lỗi 500 ngay lập tức, và cách đổi tên cột qua ba bản phát hành.
- Vì sao thêm một cột `NOT NULL` có default lúc mất 3 ms, lúc mất hơn 4 giây khoá cả bảng.
- Vì sao `CREATE INDEX CONCURRENTLY` trong Flyway có thể treo mãi mãi, và vì sao một câu `SET lock_timeout` ở migration trước có thể làm nó thất bại.

</Goal>

<Knowledge>

### Migration không downtime

Khi deploy kiểu **rolling** (thay dần từng instance) hoặc blue-green, có một khoảng thời gian phiên bản cũ và mới **cùng chạy trên cùng database**. Flyway chạy migration khi instance mới đầu tiên khởi động, tức là trong lúc instance cũ vẫn đang nhận request:

```text
 thời gian ------------------------------------------------------------->
 instance v1  [=========== đang chạy =============]  (bị thay dần)
 instance v2                 [== khởi động: Flyway chạy V8 ==][===== chạy =====]
                             ^
                             từ đây schema là V8, nhưng v1 vẫn đang phục vụ
```

Quy tắc: **mỗi migration phải tương thích với cả phiên bản code đang chạy lẫn phiên bản sắp chạy.** Đổi tên cột thẳng bằng `RENAME COLUMN` vi phạm quy tắc này: v1 vẫn `select full_name` và nhận lỗi ngay khi migration commit. Cách làm là **expand/contract** (mở rộng rồi thu hẹp), trải qua nhiều bản phát hành:

```text
 Bản phát hành   Migration (expand -> contract)                    Code
 -------------   -----------------------------------------------   ------------------------------------
 v1              (schema cũ: full_name)                             đọc, ghi full_name
 v2  EXPAND      thêm display_name (nullable)                       đọc, ghi display_name
                 trigger đồng bộ hai cột khi v1 hoặc v2 ghi        (v1 vẫn chạy song song, vẫn đúng)
                 backfill: display_name = full_name
 v3  CONTRACT    bỏ trigger, display_name SET NOT NULL,             như v2
                 DROP COLUMN full_name                              (chỉ khi KHÔNG còn instance v1 nào)
```

Với thay đổi đơn giản hơn, quy tắc cụ thể trên PostgreSQL:

| Thay đổi | Cách an toàn | Vì sao |
|---|---|---|
| Thêm cột nullable | `ADD COLUMN` | Chỉ sửa metadata |
| Thêm cột `NOT NULL` có default | `ADD COLUMN ... NOT NULL DEFAULT 'web'` | Từ PostgreSQL 11, default **không volatile** chỉ ghi vào metadata. Default volatile như `gen_random_uuid()` thì ghi lại toàn bảng dưới khoá `ACCESS EXCLUSIVE` |
| Đặt `NOT NULL` cho cột có sẵn | PostgreSQL 18: `ADD CONSTRAINT c_nn NOT NULL c NOT VALID`, rồi `VALIDATE CONSTRAINT c_nn`. Bản cũ hơn: `ADD CONSTRAINT ... CHECK (c IS NOT NULL) NOT VALID`, rồi `VALIDATE CONSTRAINT`, rồi `SET NOT NULL` | `SET NOT NULL` trực tiếp quét cả bảng khi giữ khoá chặn mọi thứ; `VALIDATE` quét với khoá nhẹ, và `SET NOT NULL` dùng lại ràng buộc đã kiểm |
| Tạo index | `CREATE INDEX CONCURRENTLY` | `CREATE INDEX` thường giữ khoá `SHARE`, chặn mọi `INSERT`/`UPDATE`/`DELETE` tới khi xong |
| Đổi tên cột hoặc bảng | Expand/contract | Code cũ còn dùng tên cũ |
| Xoá cột | Bỏ khỏi code trước (một bản phát hành), xoá ở bản sau | Code cũ còn đọc cột đó; Hibernate `select` mọi cột có trong entity |
| Backfill bảng lớn | Chia lô vài nghìn dòng, ngoài migration hoặc nhiều migration | Một `UPDATE` cả bảng giữ khoá dòng lâu và sinh WAL lớn |

**Lock queue.** `ALTER TABLE` cần khoá `ACCESS EXCLUSIVE`. Nếu một truy vấn báo cáo dài đang đọc bảng, `ALTER` phải chờ, và **mọi truy vấn tới sau xếp hàng sau `ALTER`**, kể cả `SELECT` đơn giản. Đặt `SET LOCAL lock_timeout = '5s'` ở đầu migration: chờ quá 5 giây thì migration thất bại và deploy dừng, thay vì cả hệ thống đứng. Phải có `LOCAL`: Flyway chạy mỗi migration trong một transaction, và `SET LOCAL` chỉ sống tới hết transaction đó. `SET` thường đổi cả **session**: kết nối của Flyway giữ timeout đó cho mọi migration chạy sau trong cùng lượt, và nếu migration chạy qua kết nối của pool thì kết nối đó mang timeout về lại pool cho ứng dụng dùng.

**`CONCURRENTLY` trong Flyway.** `CREATE INDEX CONCURRENTLY` không chạy được trong transaction. Flyway 12 tự nhận ra và chạy migration đó ngoài transaction (log ghi `[non-transactional]`). Nhưng mặc định Flyway giữ một khoá advisory trong một **transaction đang mở** trên kết nối riêng (`postgresql.transactional.lock=true`), và `CONCURRENTLY` phải chờ mọi transaction đang mở kết thúc, gồm cả transaction đó của chính Flyway: migration treo mãi. Khi viết bài này, `pg_stat_activity` cho thấy đúng cảnh đó: một kết nối `idle in transaction` của Flyway và câu `CREATE INDEX CONCURRENTLY` chờ `virtualxid`. Đặt `spring.flyway.postgresql.transactional-lock=false` trước khi dùng `CONCURRENTLY`. Ngược lại, nếu một migration trước trong cùng lượt đã `SET lock_timeout` không có `LOCAL`, câu `CONCURRENTLY` kế thừa timeout đó: nó thất bại sau 5 giây với lỗi `55P03` khi phải chờ một transaction khác. Dù vì lý do gì, `CONCURRENTLY` thất bại giữa chừng để lại một index `INVALID` phải `DROP` rồi tạo lại.

<Callout kind="production">

Một migration thêm cột vào bảng `orders` lúc 10 giờ sáng. Câu `ALTER TABLE ... ADD COLUMN note text` chỉ sửa metadata, lẽ ra xong trong vài mili giây. Nhưng đúng lúc đó một truy vấn báo cáo chạy 4 phút đang đọc `orders`. `ALTER` xếp hàng chờ khoá `ACCESS EXCLUSIVE`, và trong 4 phút đó mọi request đọc hay ghi `orders` xếp hàng sau nó, pool kết nối cạn, health check thất bại, Kubernetes khởi động lại các pod. Sửa: `SET LOCAL lock_timeout = '5s'` trong migration, cho deploy thất bại sạch sẽ và thử lại, và đưa truy vấn báo cáo sang replica.

</Callout>

### 3. Expand: bản v2 chạy song song với v1

Migration `V8` thêm cột mới, dựng trigger giữ hai cột đồng bộ cho cả hai phiên bản, và backfill. Code v2 đổi ánh xạ sang `display_name`:

<Terminal where="mac" title="Tab 2: V8 và Customer của v2">

```bash
cd ~/masteva-sb5/shop
P=src/main/java/vn/masteva/shop
cat > src/main/resources/db/migration/V8__customers_display_name_expand.sql <<'EOF'
SET LOCAL lock_timeout = '5s';

ALTER TABLE customers ADD COLUMN display_name text;

CREATE FUNCTION customers_sync_name() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        NEW.display_name := coalesce(NEW.display_name, NEW.full_name);
        NEW.full_name := coalesce(NEW.full_name, NEW.display_name);
    ELSIF NEW.display_name IS DISTINCT FROM OLD.display_name THEN
        NEW.full_name := NEW.display_name;
    ELSIF NEW.full_name IS DISTINCT FROM OLD.full_name THEN
        NEW.display_name := NEW.full_name;
    END IF;
    RETURN NEW;
END
$$;

CREATE TRIGGER customers_sync_name
    BEFORE INSERT OR UPDATE ON customers
    FOR EACH ROW EXECUTE FUNCTION customers_sync_name();

UPDATE customers SET display_name = full_name WHERE display_name IS NULL;
EOF
perl -0pi -e 's/    private String fullName;/    \@Column(name = "display_name")\n    private String fullName;/; s/import jakarta.persistence.Entity;/import jakarta.persistence.Column;\nimport jakarta.persistence.Entity;/' $P/Customer.java
./mvnw -q package -DskipTests && cp target/shop-0.0.1-SNAPSHOT.jar ../shop-v2.jar
```

</Terminal>

- v1 ghi `full_name`, `display_name` để trống: trigger chép sang `display_name`. v2 ghi `display_name`, không biết `full_name`: trigger chép ngược lại, nên `full_name NOT NULL` vẫn thoả. Trigger `BEFORE` chạy trước khi PostgreSQL kiểm `NOT NULL`.
- Khi `UPDATE`, mỗi phiên bản chỉ gửi cột nó biết: v1 gửi `full_name`, v2 gửi `display_name`, và cột còn lại giữ giá trị cũ. Trigger nhìn cột nào vừa đổi so với `OLD` để chép theo đúng hướng.
- `display_name` để nullable ở bước này: v1 chưa biết cột này, đặt `NOT NULL` lúc này chỉ an toàn nhờ trigger, và bước contract sẽ làm điều đó.
- Backfill bằng một câu `UPDATE` được với bảng nhỏ. Với hàng triệu khách, chạy theo lô bên ngoài migration.

```text
Schema "public" is up to date. No migration necessary.
```

</Expected>

v1 chỉ biết tới V7 nhưng vẫn khởi động: Flyway mặc định bỏ qua migration "của tương lai" và chỉ cảnh báo. Điều đó chỉ an toàn vì V8 tương thích với code v1. Đây cũng là đường rollback: nếu v2 có lỗi, quay về v1 mà không phải đảo ngược migration.

<Check id="sb5.5.lab-expand">Tái hiện được việc `RENAME COLUMN` làm hỏng phiên bản đang chạy, viết được migration expand có trigger đồng bộ, và chứng minh được hai phiên bản cùng đọc ghi đúng.</Check>

### 4. Thêm cột và tạo index trên bảng lớn

Nạp 2 triệu đơn vào `orders` để thấy khác biệt. Lệnh mất khoảng nửa phút:

<Terminal where="mac" title="Tab 2">

```bash
shopsql -c '\timing on' -c "INSERT INTO orders (customer_id, status, created_at) SELECT 1 + g % 5, 'PAID', now() - g * interval '1 second' FROM generate_series(1, 2000000) AS g" -c 'ANALYZE orders'
shopsql -c '\timing on' -c "ALTER TABLE orders ADD COLUMN channel text NOT NULL DEFAULT 'web'" -c "ALTER TABLE orders ADD COLUMN ref uuid NOT NULL DEFAULT gen_random_uuid()"
```

</Terminal>

<Expected>

```text
Timing is on.
INSERT 0 2000000
Time: 26471.442 ms (00:26.471)
ANALYZE
Time: 425.904 ms
Timing is on.
ALTER TABLE
Time: 3.401 ms
ALTER TABLE
Time: 5140.510 ms (00:05.141)
```

</Expected>

Cùng là "thêm cột `NOT NULL` có default", nhưng 3 ms so với hơn 5 giây. `'web'` là hằng số: PostgreSQL ghi nó vào metadata và trả về cho mọi dòng cũ khi đọc. `gen_random_uuid()` là hàm volatile, mỗi dòng một giá trị, nên PostgreSQL phải ghi lại cả 2 triệu dòng, suốt thời gian đó giữ khoá `ACCESS EXCLUSIVE`: không ai đọc được bảng `orders`. Xoá hai cột thử:

<Callout kind="danger">

Lệnh sau xoá hai cột `channel` và `ref` cùng dữ liệu trong đó. Chỉ chạy trên `sb5-pg` của lab.

</Callout>

<Terminal where="mac" title="Tab 2">

```bash
shopsql -c 'ALTER TABLE orders DROP COLUMN channel, DROP COLUMN ref'
```

</Terminal>

Giờ tạo index trong một migration chạy trong transaction, như Flyway làm mặc định. Phần `pg_sleep(5)` đóng vai các câu lệnh khác của cùng migration. Trong lúc đó, một request của ứng dụng chèn đơn mới, với `lock_timeout` 2 giây:

<Terminal where="mac" title="Tab 2">

```bash
shopsql -c 'BEGIN' -c 'CREATE INDEX orders_created_idx ON orders (created_at)' -c 'SELECT pg_sleep(5)' -c 'COMMIT' > /dev/null &
sleep 2
shopsql -c '\timing on' -c "SET lock_timeout = '2s'" -c "INSERT INTO orders (customer_id, status, created_at) VALUES (1, 'NEW', now())"
wait
```

</Terminal>

<Expected>

```text
Timing is on.
SET
Time: 0.149 ms
Time: 2007.717 ms (00:02.008)
ERROR:  canceling statement due to lock timeout
LINE 1: INSERT INTO orders (customer_id, status, created_at) VALUES ...
                    ^
```

</Expected>

`CREATE INDEX` giữ khoá `SHARE` trên `orders` tới khi transaction commit. Khoá đó cho đọc nhưng chặn mọi ghi, nên `INSERT` chờ và bị huỷ sau 2 giây. Không có `lock_timeout`, nó sẽ chờ tới hết migration. Làm lại bằng `CONCURRENTLY` (không chạy được trong transaction):

<Terminal where="mac" title="Tab 2">

```bash
shopsql -c 'DROP INDEX orders_created_idx'
shopsql -c 'CREATE INDEX CONCURRENTLY orders_created_idx ON orders (created_at)' > /dev/null &
sleep 0.3
shopsql -c '\timing on' -c "SET lock_timeout = '2s'" -c "INSERT INTO orders (customer_id, status, created_at) VALUES (1, 'NEW', now())"
wait
shopsql -c 'DROP INDEX orders_created_idx'
```

</Terminal>

<Expected>

```text
DROP INDEX
Timing is on.
SET
Time: 0.107 ms
INSERT 0 1
Time: 14.098 ms
DROP INDEX
```

</Expected>

`INSERT` chạy xong trong khoảng 10 mili giây trong khi index đang được dựng. Cái giá: `CONCURRENTLY` quét bảng hai lần, lâu hơn, và nếu thất bại để lại index `INVALID`. Lệnh cuối xoá index thử để bước sau tạo nó bằng Flyway.

<Check id="sb5.5.lab-locks">Đo được khác biệt giữa default hằng số và default volatile khi thêm cột, và tái hiện được việc `CREATE INDEX` chặn ghi trong khi `CREATE INDEX CONCURRENTLY` thì không.</Check>

### 5. Contract: bản v3 bỏ cột cũ

Contract chỉ được chạy khi **không còn instance v1 nào**. Dừng v1 ở tab 1 bằng **Ctrl+C**. v2 ở tab 3 vẫn chạy. Bản v3 có cùng code với v2, thêm hai migration: `V9` bỏ cột cũ, `V10` tạo index bằng `CONCURRENTLY`, kèm cấu hình để Flyway không giữ transaction mở.

<Callout kind="danger">

`V9` xoá cột `full_name` cùng dữ liệu trong đó. Chỉ chạy khi chắc chắn mọi instance đã dùng `display_name` và backfill đã xong. Trên production, sao lưu hoặc giữ cột vài ngày trước khi xoá.

</Callout>

<Terminal where="mac" title="Tab 2: V9, V10 và bản v3">

```bash
cd ~/masteva-sb5/shop
cat > src/main/resources/db/migration/V9__customers_display_name_contract.sql <<'EOF'
SET LOCAL lock_timeout = '5s';

DROP TRIGGER customers_sync_name ON customers;
DROP FUNCTION customers_sync_name();
ALTER TABLE customers ALTER COLUMN display_name SET NOT NULL;
ALTER TABLE customers DROP COLUMN full_name;
EOF
cat > src/main/resources/db/migration/V10__orders_created_idx.sql <<'EOF'
CREATE INDEX CONCURRENTLY orders_created_idx ON orders (created_at);
EOF
echo 'spring.flyway.postgresql.transactional-lock=false' >> src/main/resources/application.properties
sed -i '' 's/INSERT INTO customers (email, full_name)/INSERT INTO customers (email, display_name)/' src/test/resources/db/testdata/V100__bulk_orders.sql
./mvnw test 2>&1 | grep -E 'Tests run:|BUILD' | tail -2
./mvnw -q package -DskipTests && cp target/shop-0.0.1-SNAPSHOT.jar ../shop-v3.jar
```

</Terminal>

<Expected>

```text
[INFO] Tests run: 25, Failures: 0, Errors: 0, Skipped: 0
[INFO] BUILD SUCCESS
```

</Expected>

- `SET NOT NULL` trực tiếp ở đây chấp nhận được vì `customers` nhỏ. Với bảng lớn, dùng ràng buộc `NOT VALID` rồi `VALIDATE` như mục Kiến thức.
- `SET LOCAL` giữ `lock_timeout` trong transaction của từng migration. Nếu `V9` dùng `SET` thường, timeout 5 giây sẽ đi theo kết nối của Flyway sang `V10`.
- `V10` chỉ có một câu `CONCURRENTLY`: Flyway không cho trộn câu cần transaction và câu không chạy được trong transaction trong cùng một file.
- Dữ liệu test `V100` của SB5.3 chèn vào `full_name`, cột mà `V9` vừa xoá. Migration test chạy lại từ đầu mỗi lần, nên sửa thẳng file đó là đúng; migration chính thì không bao giờ sửa (SB3.2). Chạy lại toàn bộ test của cả chặng để chắc không gì hỏng, kể cả `V10` chạy trong Testcontainers.

### Khi gặp lỗi

<Callout kind="pitfall">

- Migration có `CONCURRENTLY` treo mãi lúc khởi động: thiếu `spring.flyway.postgresql.transactional-lock=false`. Dừng ứng dụng, xem `shopsql -c "select pid, state, wait_event, left(query, 60) from pg_stat_activity where datname = 'shop'"`, thêm cấu hình rồi chạy lại.
- `V10` thất bại, ví dụ `canceling statement due to lock timeout` (mã `55P03`): `CONCURRENTLY` chạy ngoài transaction, nên Flyway ghi một dòng `success = false` vào `flyway_schema_history` và từ chối khởi động cho tới khi bạn dọn, còn PostgreSQL để lại index ở trạng thái `INVALID`. Dọn theo hai bước ở dưới.
- Migration chạy trong transaction (như `V8`, `V9`) thất bại: PostgreSQL rollback cả migration và Flyway 12 không ghi dòng nào vào lịch sử. Chỉ cần sửa file rồi khởi động lại.
- `Port 8085 was already in use`: một lần chạy trước chưa tắt. `lsof -ti tcp:8085` cho PID, dừng bằng `kill <PID>`.
- `Connection to localhost:5445 refused`: `sb5-pg` chưa chạy hoặc chưa sẵn sàng. `docker start sb5-pg` rồi đợi `pg_isready`.
- `curl` ở cổng 8085 trả `500` sau bước 5 với `column ... full_name does not exist`: tab 1 vẫn đang chạy v1, chưa phải v3.

</Callout>

Dọn sau khi `V10` thất bại. Bước 1, nếu `\d orders` ghi `orders_created_idx` là `INVALID`, xoá index đó để migration tạo lại từ đầu:

<Terminal where="mac" title="Tab 2">

```bash
shopsql -c '\d orders' | grep orders_created_idx
shopsql -c 'DROP INDEX IF EXISTS orders_created_idx'
```

</Terminal>

Bước 2, xoá dòng thất bại khỏi lịch sử của Flyway. `flyway repair` của Flyway CLI làm đúng việc này; không có CLI thì xoá bằng SQL:

<Callout kind="danger">

Lệnh dưới xoá dòng khỏi `flyway_schema_history`, bảng Flyway dựa vào để biết migration nào đã chạy. Chỉ xoá dòng `success = false` của migration bạn đã dọn xong, và chỉ khi không instance nào đang khởi động. Xoá nhầm dòng thành công làm Flyway chạy lại migration đó.

</Callout>

<Terminal where="mac" title="Tab 2">

```bash
shopsql -c 'DELETE FROM flyway_schema_history WHERE success = false'
```

</Terminal>

Rồi khởi động lại ứng dụng: Flyway chạy lại `V10`.

<DeepDive>

<Reveal title="Rollback một bản phát hành có migration thì sao?">

Flyway Community không có "down migration" chạy tự động, và kể cả có, đảo ngược một `DROP COLUMN` không lấy lại được dữ liệu. Expand/contract biến rollback thành việc chạy lại code cũ: vì mỗi migration tương thích với phiên bản trước, bạn quay về v(n-1) mà giữ nguyên schema, như bước 3. Đó là lý do contract luôn tách ra một bản phát hành sau, khi đã chắc không cần quay lại.

</Reveal>

<Reveal title="Chạy migration lúc ứng dụng khởi động hay tách thành bước riêng?">

Spring Boot chạy Flyway khi khởi động: đơn giản, nhưng với 20 instance, instance nào lên trước chạy migration (Flyway dùng khoá để chỉ một instance chạy), và migration lâu làm health check của instance đó thất bại. Nhiều team tách migration thành một bước riêng trong pipeline deploy (một job Kubernetes hoặc lệnh `flyway migrate`) chạy xong mới cuộn instance mới, và tắt `spring.flyway.enabled` ở ứng dụng. Chặng SB11 bàn cách đóng gói và phát hành.

</Reveal>

<Reveal title="Đổi kiểu một cột trên bảng lớn, ví dụ int sang bigint, thì sao?">

`ALTER COLUMN ... TYPE bigint` ghi lại toàn bảng và mọi index trên cột đó dưới khoá `ACCESS EXCLUSIVE`: với bảng trăm triệu dòng, đó là hàng chục phút không ai đọc ghi được. Chỉ vài đổi kiểu tương thích nhị phân được miễn, như nới `varchar(50)` thành `varchar(100)` hay `text`. Cách không downtime lại là expand/contract: thêm cột `bigint` mới, trigger chép giá trị khi ghi, backfill theo lô, tạo index `CONCURRENTLY`, chuyển code sang cột mới, rồi mới bỏ cột cũ. Với khoá chính, việc đổi còn kéo theo mọi khoá ngoại trỏ tới nó, nên chọn `bigint` ngay từ đầu rẻ hơn nhiều.

</Reveal>

<Callout kind="ai">

Nhờ AI viết kế hoạch expand/contract cho một thay đổi schema cụ thể, viết trigger đồng bộ hai cột, hoặc rà một file migration xem có khoá nặng không. AI hay viết `RENAME COLUMN` hay `ALTER COLUMN TYPE` thẳng trong một migration, hay quên `lock_timeout` hoặc viết `SET lock_timeout` không có `LOCAL`, và hay đặt `CREATE INDEX CONCURRENTLY` chung file với câu lệnh khác. Kiểm tra bằng cách chạy migration trên bản sao dữ liệu có kích thước thật trong khi một phiên bản cũ đang chạy, như bước 3 và 4.

</Callout>

<Callout kind="link">

SB3.2 giới thiệu Flyway và quy tắc không sửa migration đã chạy; bài này thêm quy tắc tương thích hai phiên bản. SB4.2 đo transaction dài giữ khoá dòng; bài này là phiên bản của cùng vấn đề ở mức khoá bảng. Chặng SB11 đưa migration vào pipeline phát hành.

</Callout>
