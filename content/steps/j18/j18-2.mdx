### Từ interpreter tới C2: tiered compilation

Bài J1.1 nói JIT dịch đoạn code chạy nhiều thành mã máy. Cụ thể, HotSpot có hai trình biên dịch JIT và dùng chúng theo **tầng (tier)**:

| Tier | Ai chạy | Đặc điểm |
|---|---|---|
| 0 | Interpreter | Chạy từng lệnh bytecode, chậm, đồng thời đếm số lần gọi |
| 1 | C1 | Biên dịch nhanh, mã tối ưu vừa phải, không thu profile; cho method quá đơn giản |
| 2 | C1 | Chỉ đếm lượt gọi và vòng lặp; dùng khi C2 đang quá tải |
| 3 | C1 | Như tier 1 nhưng chèn code thu **profile** đầy đủ: nhánh nào hay chạy, object thuộc kiểu gì |
| 4 | C2 | Biên dịch chậm, tối ưu mạnh dựa trên profile: inline, bỏ nhánh không bao giờ chạy, vector hoá vòng lặp |

```text
 method mới   tier 0 interpreter      gọi đủ nhiều     tier 3 C1 + profile
 -----------> đếm lượt gọi       -----------------> thu kiểu, nhánh
                                                        |  profile đủ
                                                        v
          uncommon trap                              tier 4 C2
 tier 0 <------------------------------------------ mã máy theo giả định
 (deoptimization: bỏ mã C2, quay lại interpreter,    "discount luôn là Percent"
  thu profile mới, biên dịch lại)
```

C2 tối ưu dựa trên **giả định** rút ra từ profile. Nếu tới giờ `discount.apply` chỉ gặp `Percent`, C2 inline thẳng code của `Percent.apply` và đặt một **uncommon trap** cho trường hợp khác. Khi một `Fixed` xuất hiện, trap kích hoạt: JVM bỏ mã C2 đó (**deoptimization**), chạy tiếp bằng interpreter, rồi biên dịch lại với profile mới.

**OSR (On-Stack Replacement)** xử lý một vòng lặp dài đang chạy trong interpreter: JVM biên dịch riêng thân vòng lặp và nhảy sang mã mới giữa chừng, không chờ method được gọi lần sau.

### Warm-up trên production

Mỗi lần khởi động, JVM bắt đầu lại từ interpreter. Service Spring Boot có hàng chục nghìn method; phải qua hàng nghìn request, các đường code nóng mới lên tới C2. Trong khoảng đó, độ trễ cao hơn bình thường nhiều lần và CPU tăng vọt vì các thread biên dịch cũng chạy.

| Cách giảm warm-up | Ý tưởng | Lưu ý |
|---|---|---|
| Gửi traffic giả trước khi báo ready | Chạy các API chính vài nghìn lần rồi mới bật readiness probe (J15) | Traffic giả phải giống traffic thật |
| Rolling deploy chậm | Mỗi lần chỉ thay một phần instance | Không rút ngắn warm-up, chỉ giảm tác động |
| AOT cache (JDK 24, 25) | Một lần chạy huấn luyện ghi lớp đã nạp, đã liên kết và profile method ra file; lần sau JVM dùng lại | Classpath phải là file JAR, giống hệt giữa hai lần chạy; profile chỉ tốt bằng lần huấn luyện |

AOT cache gom ba JEP: JEP 483 (nạp và liên kết lớp trước), JEP 514 (tạo cache bằng một cờ `-XX:AOTCacheOutput`), JEP 515 (lưu profile method để JIT biên dịch sớm hơn). Phần thực hành dùng cả ba.

<Callout kind="production">

Một team deploy service thanh toán lúc 10 giờ sáng. Readiness probe chỉ kiểm tra `/actuator/health`, nên instance mới nhận ngay 1/3 traffic. p99 tăng từ 80 ms lên 1,2 giây trong khoảng hai phút rồi tự hết, đủ để vài client timeout và retry, làm tải còn tăng thêm. Không có gì sai trong code; đó là warm-up. Cách sửa của họ: chạy một bộ request mẫu nội bộ trước khi bật readiness, và đo p99 riêng cho vài phút đầu sau deploy.

</Callout>

<Check id="j18.2.warm-up">Giải thích được vì sao service chậm sau khi khởi động và nêu được hai cách giảm warm-up.</Check>

### Microbenchmark và vì sao cần JMH

Muốn so sánh hai cách viết, bạn có thể bọc code trong vòng lặp và đo bằng `System.nanoTime()`. Cách đó sai theo nhiều kiểu, vì chính những tối ưu của C2 ở trên:

| Bẫy | Chuyện gì xảy ra |
|---|---|
| Không warm-up | Đo lẫn thời gian chạy interpreter và thời gian biên dịch |
| **Dead code elimination** (DCE) | Kết quả không được dùng, C2 xoá luôn phép tính; bạn đo một vòng lặp rỗng |
| **Constant folding** | Đầu vào là hằng số, C2 tính sẵn kết quả lúc biên dịch |
| Chỉ chạy một JVM | Thứ tự biên dịch và bố trí bộ nhớ của một lần chạy có thể khác hẳn lần sau |

**JMH (Java Microbenchmark Harness)** là harness của OpenJDK xử lý các bẫy này. Bạn viết method gắn `@Benchmark`, JMH sinh code đo quanh nó: chạy warm-up, chạy đo nhiều vòng, chạy trong JVM con riêng (**fork**), tính sai số.

| Annotation, lớp | Vai trò |
|---|---|
| `@Benchmark` | Method cần đo |
| `@State(Scope.Thread)` | Lớp giữ dữ liệu đầu vào; field của nó không bị coi là hằng số |
| `@Warmup`, `@Measurement` | Số vòng và thời lượng mỗi vòng warm-up, đo thật |
| `@Fork` | Số JVM con chạy benchmark |
| `@BenchmarkMode`, `@OutputTimeUnit` | Đo thời gian trung bình mỗi lần gọi, đơn vị ns |
| `Blackhole` | "Tiêu thụ" một giá trị để C2 không xoá được phép tính tạo ra nó |

Trả giá trị về từ method `@Benchmark` có tác dụng giống `Blackhole`: JMH tự tiêu thụ giá trị trả về.

<Callout kind="pitfall">

Microbenchmark chỉ trả lời câu hỏi rất hẹp: đoạn code này, với dữ liệu này, trên JVM này. Đừng benchmark trước khi profile (bài J18.3) chỉ ra đoạn đó thật sự nóng. Tối ưu một method chiếm 0,5% thời gian CPU không làm service nhanh hơn, dù JMH báo nó nhanh gấp đôi.

</Callout>

</Knowledge>

### 1. Một method nóng

`WarmUp` tính tổng tiền của giỏ 10.000 món sau giảm giá, 10 lần mỗi lô, 20 lô, và in thời gian từng lô. Cuối chương trình, một đơn hiếm gặp dùng kiểu giảm giá thứ hai, `Fixed`.

<Terminal where="mac" title="Tạo jit/src/WarmUp.java">

```bash
mkdir -p ~/masteva-j18/jit/src && cd ~/masteva-j18/jit
cat > src/WarmUp.java <<'EOF'
public class WarmUp {
    interface Discount {
        long apply(long price);
    }

    record Percent(int percent) implements Discount {
        public long apply(long price) {
            return price * (100 - percent) / 100;
        }
    }

    record Fixed(long amount) implements Discount {
        public long apply(long price) {
            return Math.max(0, price - amount);
        }
    }

    // Tổng tiền một giỏ hàng sau giảm giá: method "nóng" của bài.
    static long total(long[] prices, Discount discount) {
        long sum = 0;
        for (long price : prices) {
            sum += discount.apply(price);
        }
        return sum;
    }

    public static void main(String[] args) {
        boolean percentOnly = args.length > 0 && args[0].equals("percent-only");
        long[] prices = new long[10_000];
        for (int i = 0; i < prices.length; i++) {
            prices[i] = 10_000 + i * 7L;
        }
        Discount percent = new Percent(10);
        long checksum = 0;
        for (int batch = 1; batch <= 20; batch++) {
            long start = System.nanoTime();
            for (int i = 0; i < 10; i++) {
                checksum += total(prices, percent);
            }
            long micros = (System.nanoTime() - start) / 1_000;
            System.out.printf("batch %2d: %,5d µs%s", batch, micros, batch % 4 == 0 ? "\n" : "   ");
        }
        if (!percentOnly) {
            // Một đơn hiếm gặp dùng kiểu giảm giá thứ hai: giả định của JIT sai.
            checksum += total(prices, new Fixed(5_000));
        }
        System.out.println("checksum=" + checksum);
    }
}
EOF
javac -d out src/WarmUp.java && java -cp out WarmUp
```

</Terminal>


</Expected>

Mỗi dòng có: mã lần biên dịch, dấu `%` nếu là OSR, tier, tên method, `@ 13` là vị trí bytecode của vòng lặp được OSR. Mã biên dịch và thời điểm khác nhau giữa các lần chạy.

- `total @ 13` lên tier 3 rồi tier 4 bằng OSR: vòng lặp `for` bên trong chạy đủ lâu để JVM thay mã giữa chừng.
- `made not entrant: not used`: mã tier 3 cũ bị bỏ vì đã có mã tier 4 thay thế.
- Khi `Fixed` xuất hiện, mã C2 của `total` bị bỏ với lý do `uncommon trap`. Đó là deoptimization. JVM biên dịch lại `total` (mã 126) với profile biết cả hai kiểu. Có lần chạy còn thêm một dòng `blocked` ở cuối cho lần biên dịch này, vì chương trình kết thúc ngay sau đó.

### 4. Rút ngắn warm-up bằng AOT cache

AOT cache chỉ nhận classpath gồm file JAR, nên trước hết đóng gói `out` thành JAR. Lần chạy có `-XX:AOTCacheOutput` là **lần chạy huấn luyện**: chương trình chạy như thường, khi thoát thì JVM ghi cache.

<Terminal where="mac">

```bash

jar --create --file warmup.jar -C out .
java -XX:AOTCacheOutput=warmup.aot -cp warmup.jar WarmUp > /dev/null
java -XX:AOTCache=warmup.aot -cp warmup.jar WarmUp
```

### 5. Project JMH

Archetype chính thức của JMH 1.37 (`jmh-java-benchmark-archetype`) sinh pom nhắm Java 8 và khai báo bộ sinh code như một dependency `provided`. <Terminal where="mac" title="Tạo Loan.java và LoanBench.java">

```bash
cd ~/masteva-j18/bench
cat > src/main/java/dev/masteva/bench/Loan.java <<'EOF'
package dev.masteva.bench;

public final class Loan {
    private Loan() {
    }

    // Số dư sau 12 tháng, lãi 1,5%/tháng cộng phí: chỉ có phép tính, không có tác dụng phụ.
    public static double balanceAfterYear(double principal) {
        double balance = principal;
        for (int month = 0; month < 12; month++) {
            balance = balance * 1.015 + Math.sqrt(balance) / 100;
        }
        return balance;
    }
}
EOF
cat > src/main/java/dev/masteva/bench/LoanBench.java <<'EOF'
package dev.masteva.bench;

import java.util.concurrent.TimeUnit;
import org.openjdk.jmh.annotations.Benchmark;
import org.openjdk.jmh.annotations.BenchmarkMode;
import org.openjdk.jmh.annotations.Fork;
import org.openjdk.jmh.annotations.Measurement;
import org.openjdk.jmh.annotations.Mode;
import org.openjdk.jmh.annotations.OutputTimeUnit;
import org.openjdk.jmh.annotations.Scope;
import org.openjdk.jmh.annotations.State;
import org.openjdk.jmh.annotations.Warmup;
import org.openjdk.jmh.infra.Blackhole;

@State(Scope.Thread)
@BenchmarkMode(Mode.AverageTime)
@OutputTimeUnit(TimeUnit.NANOSECONDS)
@Warmup(iterations = 3, time = 1)
@Measurement(iterations = 5, time = 1)
@Fork(1)
public class LoanBench {
    // Field của @State, không phải hằng số, để JIT không tính trước được.
    double principal = 1_250_000;

    @Benchmark
    public void baseline() {
        // Không làm gì: chi phí tối thiểu của một lần gọi.
    }

    @Benchmark
    public void wrong() {
        Loan.balanceAfterYear(principal); // kết quả bị bỏ đi
    }

    @Benchmark
    public double constant() {
        return Loan.balanceAfterYear(1_250_000); // đầu vào là hằng số
    }

    @Benchmark
    public double returned() {
        return Loan.balanceAfterYear(principal);
    }

    @Benchmark
    public void blackhole(Blackhole bh) {
        bh.consume(Loan.balanceAfterYear(principal));
    }
}
EOF
```

### Khi gặp lỗi

<Callout kind="pitfall">

- `RuntimeException: ERROR: Unable to find the resource: /META-INF/BenchmarkList` khi chạy `benchmarks.jar`: annotation processor của JMH không chạy, nên không có benchmark nào được sinh. Thường do pom khai báo `jmh-generator-annprocess` như dependency `provided` (kiểu archetype 1.37) thay vì trong `annotationProcessorPaths`. Với JDK 25, cả project từ archetype lẫn pom của bài bỏ `annotationProcessorPaths` đều build thành công, chỉ lúc chạy mới báo lỗi này.
- `Error: non-empty directory 'out'` và `Cannot have non-empty directory in paths` khi tạo AOT cache: classpath có thư mục. Đóng gói thành JAR như bước 4.
- `An error has occurred while processing the AOT cache` khi chạy với `-XX:AOTCache`: file cache không có, hoặc tạo với classpath, phiên bản JDK khác lần chạy này. JVM vẫn chạy tiếp, chỉ không dùng cache; đọc stderr lúc khởi động để biết cache có được dùng không.
- `release version 25 not supported` khi `mvn package`: Maven chạy trên JDK cũ. Đặt lại `JAVA_HOME` như phần chuẩn bị.

</Callout>

<Reveal title="Vì sao không đơn giản là bỏ interpreter, biên dịch hết bằng C2 ngay từ đầu?">

C2 cần profile để tối ưu tốt: biết nhánh nào không bao giờ chạy, call site nào chỉ gặp một kiểu. Biên dịch trước khi có profile buộc C2 phải giả định mọi khả năng, mã sinh ra chậm hơn. Biên dịch C2 cũng tốn CPU và thời gian; làm cho mọi method, kể cả method chỉ chạy một lần lúc khởi động, sẽ làm khởi động chậm đi. Tiered compilation là cách trả chi phí biên dịch chỉ cho code đáng trả. GraalVM native image (phần Đào sâu của bài J17.3) chọn hướng ngược lại: biên dịch hết trước, đổi lấy khởi động nhanh và chấp nhận mất tối ưu dựa trên profile (trừ khi dùng PGO của Oracle GraalVM).

</Reveal>

<Reveal title="Deoptimization liên tục có thể làm service chậm không?">

Có. Nếu một call site lúc gặp kiểu này, lúc gặp kiểu khác theo từng đợt traffic, JVM có thể biên dịch, deoptimize, biên dịch lại nhiều lần; trong lúc đó CPU tăng và độ trễ dao động. Thường thì nó ổn định sau vài vòng, vì lần biên dịch sau dùng profile đã thấy cả kiểu mới, như mã 126 ở bước 3. JFR có sự kiện `jdk.Deoptimization` và view `deoptimizations-by-reason` để thấy điều này (bài J18.3).

</Reveal>

<Reveal title="Có nên đặt @Fork(0) để benchmark chạy nhanh hơn?">

Không cho kết quả bạn định tin. Không fork, benchmark chạy chung JVM với code của JMH và các benchmark trước nó: profile của call site đã bị "nhiễm" nhiều kiểu, giống hệt tình huống AOT cache ở bước 4. Mỗi benchmark nên có JVM riêng. Khi cần so sánh nghiêm túc, tăng `@Fork` lên 2 hoặc 3 để thấy độ lệch giữa các JVM.

</Reveal>

<Reveal title="JMH báo cách A nhanh hơn cách B 10 ns. Đưa vào service có nhanh hơn không?">

Chưa chắc. Benchmark chạy code trong vòng lặp nóng, dữ liệu nằm sẵn trong CPU cache, một kiểu dữ liệu duy nhất. Service thật gọi code đó lẫn với hàng nghìn đoạn khác, dữ liệu lạnh hơn, profile lẫn nhiều kiểu. Hãy hỏi: đoạn code này chiếm bao nhiêu phần trăm CPU trong profile của service? 10 ns nhân với số lần gọi mỗi giây là bao nhiêu? Nếu tổng là vài phần nghìn CPU, đừng đổi code chỉ vì benchmark.

</Reveal>
