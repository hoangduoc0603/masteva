<Goal>

Hiểu process JVM dùng bộ nhớ vào những vùng nào, JVM nạp một lớp ra sao, và hai GC chính G1, ZGC khác nhau thế nào. Học xong bài này, bạn giải thích được:

- Vì sao container đặt `-Xmx512m` vẫn bị kill vì vượt giới hạn 600 MB.
- `OutOfMemoryError: Java heap space`, `Metaspace` và `Cannot reserve ... direct buffer memory` khác nhau thế nào, và mỗi loại phải sửa ở đâu.
- Vì sao `NoClassDefFoundError` xuất hiện giữa lúc ứng dụng đang chạy, không phải lúc khởi động.
- Khi nào đổi từ G1 sang ZGC, và vì sao ZGC báo pause dưới 1 ms mà request vẫn chậm.

</Goal>

<Knowledge>

### Bản đồ bộ nhớ của một process JVM

`-Xmx` chỉ giới hạn **heap**. Process JVM còn nhiều vùng khác, phần lớn nằm ngoài heap, trong **native memory** (bộ nhớ do hệ điều hành cấp trực tiếp, không do GC quản lý):

```text
 Process java (RSS mà container, ps, top nhìn thấy)
 +---------------------------------------------------------------+
 | Heap (-Xmx)          object của bạn, do GC quản lý            |
 |   G1: chia thành region; young (eden, survivor) và old         |
 +---------------------------------------------------------------+
 | Thread stack (-Xss)  mỗi thread một stack, chứa frame method  |
 | Metaspace            metadata của lớp: method, field, bytecode |
 | Code cache           mã máy do JIT sinh ra (bài J18.2)         |
 | GC                   cấu trúc nội bộ của GC: card table, ...   |
 | Direct buffer        ByteBuffer.allocateDirect, Netty, NIO     |
 | Thư viện native, malloc của JVM, ...                           |
 +---------------------------------------------------------------+
```

| Vùng | Chứa gì | Giới hạn bằng | Khi đầy |
|---|---|---|---|
| Heap | Object, mảng | `-Xmx` | `OutOfMemoryError: Java heap space` |
| Thread stack | Frame của từng lời gọi method: biến cục bộ, tham số | `-Xss` cho mỗi thread | `StackOverflowError` |
| Metaspace | Metadata của mỗi lớp đã nạp | `-XX:MaxMetaspaceSize`, mặc định không giới hạn | `OutOfMemoryError: Metaspace` |
| Direct buffer | Vùng đệm I/O ngoài heap | `-XX:MaxDirectMemorySize`, mặc định bằng `-Xmx` | `OutOfMemoryError: Cannot reserve ... bytes of direct buffer memory` |

Vì vậy bộ nhớ thật của process luôn lớn hơn `-Xmx`. Muốn biết lớn hơn bao nhiêu, bật **NMT (Native Memory Tracking)** bằng `-XX:NativeMemoryTracking=summary` rồi hỏi bằng `jcmd <pid> VM.native_memory summary`. Bạn sẽ làm trong phần thực hành.

<Callout kind="production">

Pod giới hạn 600 MiB, JVM chạy `-Xmx512m`, 200 thread. Heap chưa đầy nhưng pod chết với exit code 137 (bị kernel kill vì vượt memory limit, xem bài D1.1). Thủ phạm là phần ngoài heap: metaspace, code cache, stack của 200 thread và direct buffer của thư viện HTTP. Quy tắc thực tế: để heap chiếm khoảng 60 tới 75% giới hạn container (bài J17.3 đặt bằng `-XX:MaxRAMPercentage` và tái hiện OOMKilled), rồi đo phần còn lại bằng NMT thay vì đoán.

</Callout>

### Class loading: từ file .class tới lớp dùng được

JVM không nạp mọi lớp lúc khởi động. Nó nạp **lười (lazy)**: lần đầu code thật sự dùng tới lớp nào thì mới nạp lớp đó. Mỗi lớp đi qua ba bước, theo JVMS chương 5:

```text
 loading          linking                                 initialization
 tìm bytes   ->   verify (bytecode hợp lệ?)          ->   chạy static initializer,
 tạo Class        prepare (cấp chỗ cho static field)      gán giá trị static
                  resolve (nối tham chiếu tới lớp khác)
```

Ai tìm bytes? Một **class loader**. JDK có ba loader xếp thành chuỗi cha con, và loader luôn hỏi cha trước khi tự tìm (**parent delegation**, uỷ quyền cho cha):

```text
 bootstrap        java.base: String, List, ...          (in ra là null)
     ^ cha
 platform         java.sql, java.net.http, ...
     ^ cha
 application      classpath của bạn: -cp out, file JAR
```

Một lớp được xác định bởi **tên và loader đã định nghĩa nó**. Hai loader nạp cùng file `Plugin.class` cho ra hai lớp khác nhau, mỗi lớp chiếm metaspace riêng. Đó là gốc của **rò rỉ class loader**: app server hay plugin system tạo loader mới mỗi lần redeploy, nhưng một tham chiếu cũ còn giữ loader cũ, nên metaspace tăng mãi.

| Lỗi | Nghĩa | Thường do |
|---|---|---|
| `ClassNotFoundException` | Code hỏi tên lớp một cách tường minh (`Class.forName`, `loadClass`) và không loader nào tìm thấy | Thiếu JAR, sai tên lớp trong cấu hình |
| `NoClassDefFoundError` | Lớp có lúc biên dịch nhưng lúc chạy không nạp được | JAR khác phiên bản giữa build và runtime, dependency bị loại khỏi fat JAR, static initializer ném exception |

**CDS (Class Data Sharing)** lưu sẵn các lớp của JDK đã được parse vào một file archive, nên JVM nạp chúng nhanh hơn. Log class loading ghi nguồn của các lớp này là `shared objects file`. AppCDS (từ JDK 10) đã archive được cả lớp của ứng dụng; từ JDK 24, **AOT cache** (JEP 483) đi xa hơn: lưu lớp ở trạng thái đã nạp và đã liên kết; bài J18.2 dùng nó để rút ngắn warm-up.

<Check id="j18.1.class-loading">Giải thích được parent delegation và phân biệt được `ClassNotFoundException` với `NoClassDefFoundError`.</Check>

### GC: G1 và ZGC

Hầu hết object chết trẻ: một request tạo DTO, chuỗi, list, rồi bỏ đi. GC thế hệ (generational) dựa vào đó: dọn vùng young thường xuyên và rẻ, chỉ thỉnh thoảng mới dọn vùng old. Mỗi lần dọn, GC có thể cần **pause**: dừng mọi thread của ứng dụng (stop-the-world).

| | G1 | ZGC |
|---|---|---|
| Mặc định | Có, từ JDK 9 | Bật bằng `-XX:+UseZGC` |
| Cách làm | Chia heap thành region; pause để sao chép object sống ra region khác | Làm gần như mọi việc song song với ứng dụng, kể cả di chuyển object |
| Pause | Mục tiêu `-XX:MaxGCPauseMillis`, mặc định 200 ms; thường vài ms tới vài chục ms | Dưới 1 ms, gần như không phụ thuộc kích thước heap |
| Cái giá | Pause tăng theo lượng object sống phải sao chép | Cần CPU cho các thread GC chạy song song, và cần heap dư; heap thiếu thì thread ứng dụng bị **allocation stall** (phải đứng chờ GC) |
| Chế độ | Generational | Chỉ còn generational từ JDK 24 |

Ngoài ra còn Serial GC (một thread, hợp container rất nhỏ) và Parallel GC (tối đa throughput, chấp nhận pause dài, hợp batch job).

**Chọn thế nào:** giữ G1 cho đa số service. Cân nhắc ZGC khi yêu cầu độ trễ p99 nhỏ hơn pause mà G1 đạt được, hoặc heap rất lớn (hàng chục GB trở lên), và bạn có CPU, bộ nhớ dư. Dù chọn gì, quyết định dựa trên **GC log** của workload thật, không dựa trên benchmark của người khác.

<Callout kind="pitfall">

Đừng chỉnh tham số GC trước khi đọc log. Phần lớn sự cố "GC chậm" thật ra là heap quá nhỏ so với lượng object sống, hoặc code tạo rác quá nhiều. Chỉnh `-XX:G1NewSizePercent` hay số thread GC khi chưa có số đo thường làm mọi thứ tệ hơn.

</Callout>

<Check id="j18.1.gc-choice">Nêu được khi nào giữ G1, khi nào cân nhắc ZGC, và cái giá phải trả của ZGC.</Check>

### 2. Chương trình tái hiện lỗi bộ nhớ

`OomLab` có sáu chế độ, mỗi chế độ làm đầy một vùng hoặc minh hoạ class loading. Danh sách `keep` giữ tham chiếu để GC không thu hồi được, giống một cache quên giới hạn. Khi bắt được `OutOfMemoryError`, chương trình xoá `keep` trước để còn bộ nhớ mà in thông báo.

<Terminal where="mac" title="Tạo mem/src">

```bash
mkdir -p ~/masteva-j18/mem/src && cd ~/masteva-j18/mem
cat > src/Plugin.java <<'EOF'
public class Plugin {
    public String name() {
        return "pricing-plugin v1";
    }
}
EOF
cat > src/OomLab.java <<'EOF'
import java.nio.ByteBuffer;
import java.util.ArrayList;
import java.util.List;

public class OomLab {
    // Giữ tham chiếu để GC không thu hồi được: đây là "rò rỉ" có chủ đích.
    static final List<Object> keep = new ArrayList<>();
    static int depth = 0;

    public static void main(String[] args) throws Exception {
        try {
            switch (args.length == 0 ? "" : args[0]) {
                case "loaders" -> loaders();
                case "plugin" -> System.out.println(new Plugin().name());
                case "heap" -> heap();
                case "stack" -> stack();
                case "meta" -> meta();
                case "direct" -> direct();
                default -> System.out.println("Dùng: loaders | plugin | heap | stack | meta | direct");
            }
        } catch (OutOfMemoryError e) {
            int kept = keep.size();
            keep.clear(); // nhả tham chiếu để còn bộ nhớ mà in thông báo
            System.out.println(e + " (đã giữ " + kept + " phần tử)");
        }
    }

    static void loaders() {
        System.out.println("String     -> " + String.class.getClassLoader());
        System.out.println("java.sql   -> " + java.sql.Connection.class.getClassLoader());
        System.out.println("OomLab     -> " + OomLab.class.getClassLoader());
        var app = OomLab.class.getClassLoader();
        System.out.println("parent     -> " + app.getParent());
    }

    static void heap() {
        // Cache không giới hạn: mỗi phần tử 1 MB, không bao giờ bị xoá.
        while (true) {
            keep.add(new byte[1024 * 1024]);
        }
    }

    static void stack() {
        try {
            recurse();
        } catch (StackOverflowError e) {
            System.out.println("StackOverflowError ở độ sâu " + depth);
        }
    }

    static void recurse() {
        depth++;
        recurse();
    }

    static void meta() throws Exception {
        byte[] bytes;
        try (var in = OomLab.class.getResourceAsStream("Plugin.class")) {
            bytes = in.readAllBytes();
        }
        while (true) {
            // Mỗi loader mới định nghĩa một bản Plugin riêng trong metaspace.
            var loader = new PluginLoader(bytes);
            keep.add(loader.loadClass("Plugin"));
        }
    }

    static void direct() {
        while (true) {
            // Buffer 1 MB nằm ngoài heap, trong bộ nhớ native.
            keep.add(ByteBuffer.allocateDirect(1024 * 1024));
        }
    }

    static final class PluginLoader extends ClassLoader {
        private final byte[] bytes;

        PluginLoader(byte[] bytes) {
            super(null); // cha là bootstrap, nên Plugin không được tìm thấy ở cha
            this.bytes = bytes;
        }

        @Override
        protected Class<?> findClass(String name) throws ClassNotFoundException {
            if (name.equals("Plugin")) {
                return defineClass(name, bytes, 0, bytes.length);
            }
            throw new ClassNotFoundException(name);
        }
    }
}
EOF
javac -d out src/*.java && ls out
```

</Terminal>

```text
OomLab.class
Plugin.class
```

### 5. Lazy loading và NoClassDefFoundError

Giả lập lỗi đóng gói: file `Plugin.class` không có mặt lúc chạy.

<Terminal where="mac">

```bash
cd ~/masteva-j18/mem
mv out/Plugin.class out/Plugin.class.bak
java -cp out OomLab loaders | head -1
java -cp out OomLab plugin
mv out/Plugin.class.bak out/Plugin.class
```

</Terminal>

<Expected>

```text
String     -> null
Exception in thread "main" java.lang.NoClassDefFoundError: Plugin
	at OomLab.main(OomLab.java:14)
Caused by: java.lang.ClassNotFoundException: Plugin
	at java.base/jdk.internal.loader.BuiltinClassLoader.loadClass(BuiltinClassLoader.java:580)
	at java.base/java.lang.ClassLoader.loadClass(ClassLoader.java:490)
	... 1 more
```

</Expected>

Chế độ `loaders` vẫn chạy bình thường dù `OomLab` có tham chiếu tới `Plugin`: JVM chưa cần `Plugin` nên chưa nạp. Chỉ khi nhánh `plugin` chạy tới `new Plugin()`, JVM mới đi tìm và thất bại. Lỗi bên ngoài là `NoClassDefFoundError` (lớp có lúc biên dịch), nguyên nhân bên trong là `ClassNotFoundException` của loader. Trên production, đó là lý do một service khởi động khoẻ mạnh rồi mới gãy khi request đầu tiên đi vào một nhánh code hiếm dùng.

<Terminal where="mac">

</Terminal>

<Expected>

```text
java.lang.OutOfMemoryError: Java heap space (đã giữ 31 phần tử)
java.lang.OutOfMemoryError: Metaspace (đã giữ 5391 phần tử)
java.lang.OutOfMemoryError: Cannot reserve 1048576 bytes of direct buffer memory (allocated: 67108864, limit: 67108864) (đã giữ 64 phần tử)
StackOverflowError ở độ sâu 43963
StackOverflowError ở độ sâu 1478
```

</Expected>

| Lỗi | Vùng | Sửa ở đâu |
|---|---|---|
| `Java heap space` | Heap | Tìm cái gì giữ object (bài J18.3), sau đó mới tính tăng `-Xmx` |
| `Metaspace` | Metaspace | Tìm nơi tạo class loader hay lớp động liên tục (proxy, script engine, redeploy) |
| `Cannot reserve ... direct buffer memory` | Direct buffer | Kiểm tra buffer có được trả lại không, đặt `-XX:MaxDirectMemorySize` có chủ đích |
| `StackOverflowError` | Stack của một thread | Gần như luôn là đệ quy không dừng; tăng `-Xss` chỉ hợp với đệ quy sâu có chủ đích |

Độ sâu stack thay đổi một chút giữa các lần chạy, vì JIT biên dịch `recurse` ở thời điểm khác nhau và frame đã biên dịch có kích thước khác frame thông dịch. Với `-Xss256k`, stack nhỏ hơn 8 lần nhưng độ sâu giảm khoảng 30 lần: stack tràn sau khoảng 1.500 lời gọi, trước khi JIT kịp biên dịch `recurse`, nên mọi frame là frame thông dịch, lớn hơn frame đã biên dịch. Chạy thêm `java -Xint -cp out OomLab stack` và `java -Xint -Xss256k -cp out OomLab stack` để so trên cùng loại frame: máy kiểm chứng được 20593 và 1478, vẫn chênh khoảng 14 lần chứ không phải 8, vì mỗi stack dành sẵn khoảng 110 KB cố định cho vùng bảo vệ (guard zone) mà JVM dùng để phát hiện tràn stack.

<Predict question="Heap 64 MB, mỗi phần tử 1 MB. Vì sao chỉ giữ được 31 phần tử chứ không phải khoảng 60?">

G1 chia heap 64 MB thành region 1 MB. Object lớn hơn hoặc bằng nửa region là **humongous object** và được cấp nguyên các region liền nhau. Mảng `byte[1048576]` cộng header lớn hơn 1 MB một chút, nên chiếm trọn 2 region: 31 phần tử là khoảng 62 MB. Thử `java -Xmx64m -XX:+UseParallelGC -cp out OomLab heap`, máy kiểm chứng giữ được 56 phần tử. Trên production, nhiều mảng lớn cỡ region (buffer, cache dạng mảng) làm G1 tốn heap hơn bạn tính; `-Xlog:gc` sẽ ghi `G1 Humongous Allocation`.

</Predict>

<Check id="j18.1.lab-oom-kinds">Tự tái hiện được bốn loại lỗi bộ nhớ và nói được mỗi loại phải sửa ở đâu.</Check>

### 7. Workload để so sánh GC

`GcLoad` giả lập một service giữ 150.000 phiên đăng nhập trong bộ nhớ. Mỗi request tạo một phiên mới, 0,5 tới 1,3 KB, thay cho phiên cũ nhất. Lượng object sống luôn khoảng 130 MB, còn tổng lượng cấp phát là hàng chục GB.

<Terminal where="mac" title="Tạo GcLoad.java và pauses.awk">

```bash
cd ~/masteva-j18/mem
cat > src/GcLoad.java <<'EOF'
public class GcLoad {
    public static void main(String[] args) {
        int live = args.length > 0 ? Integer.parseInt(args[0]) : 150_000; // số phiên đang hoạt động
        long requests = 30_000_000; // tổng số request giả lập
        byte[][] sessions = new byte[live][];
        long start = System.nanoTime();
        long checksum = 0;
        for (long i = 0; i < requests; i++) {
            // Mỗi request tạo một phiên mới (0,5 tới 1,3 KB) thay cho một phiên cũ.
            byte[] session = new byte[512 + (int) (i % 7) * 128];
            session[0] = (byte) i;
            sessions[(int) (i % live)] = session;
            checksum += sessions[(int) ((i * 31) % live)] == null ? 0 : 1;
        }
        long ms = (System.nanoTime() - start) / 1_000_000;
        System.out.println("requests=" + requests + " time=" + ms + "ms checksum=" + checksum);
    }
}
EOF
cat > pauses.awk <<'EOF'
# Cộng mọi dòng "Pause ... <số>ms" trong GC log của G1 hoặc ZGC.
/Pause.* [0-9.]+ms$/ { v = $NF; sub("ms", "", v); n++; total += v; if (v + 0 > max) max = v + 0 }
END { printf "%s: pauses=%d total=%.1fms max=%.3fms\n", FILENAME, n, total, max }
EOF
javac -d out src/GcLoad.java
```

</Terminal>

<Reveal title="Vì sao MaxMetaspaceSize mặc định không giới hạn lại nguy hiểm trong container?">

Metaspace nằm trong native memory. Không có giới hạn, một rò rỉ class loader không làm JVM ném `OutOfMemoryError: Metaspace` để bạn thấy stack trace; nó làm process phình dần cho tới khi kernel kill container với exit code 137, không để lại dấu vết trong log Java. Đặt `-XX:MaxMetaspaceSize` cao hơn mức dùng bình thường vài lần (đo bằng NMT, dòng `Class`) biến sự cố âm thầm thành lỗi rõ ràng.

</Reveal>

<Reveal title="Hai lớp cùng tên Plugin, do hai loader khác nhau nạp, có gán cho nhau được không?">

Không. Lớp được xác định bởi cặp (tên, loader định nghĩa). Ép object `Plugin` của loader A sang `Plugin` của loader B ném `ClassCastException`; với `Class.cast`, thông điệp là `Cannot cast Plugin to Plugin`, nhìn rất khó hiểu nếu bạn không biết về loader. Lỗi này hay gặp ở app server, plugin system, hoặc khi Spring Boot DevTools nạp lại code của bạn bằng một loader riêng.

</Reveal>

<Reveal title="ZGC pause rất nhỏ, vậy sao không dùng ZGC cho mọi service?">

ZGC làm việc song song với ứng dụng, nên nó lấy CPU của ứng dụng: khi máy đã chạy gần 100% CPU, các thread GC và thread ứng dụng tranh nhau, và GC chậm lại dẫn tới allocation stall. ZGC cũng cần heap dư để kịp dọn trước khi heap đầy. G1 với pause vài ms đã đủ cho phần lớn API có SLO hàng trăm ms. Chọn ZGC khi số đo cho thấy pause G1 là nguyên nhân vượt SLO, và bạn có CPU, bộ nhớ để trả cho nó.

</Reveal>

<Reveal title="Vì sao service hay tạo proxy hoặc lambda vẫn không rò metaspace?">

Lớp sinh động như lambda (hidden class) và proxy được nạp vào metaspace, nhưng chúng được thu hồi khi loader của chúng không còn được tham chiếu, và GC thực hiện **class unloading**. Rò rỉ chỉ xảy ra khi có thứ còn giữ loader: một static field, một thread còn chạy, một `ThreadLocal`. Bước 6 cố ý giữ mọi `Class` trong `keep`, nên không lớp nào được thu hồi.

</Reveal>
