<Goal>

Dùng Jackson để chuyển record Java sang JSON và ngược lại, điều khiển tên trường, trường bị bỏ qua và kiểu `java.time`. Dùng `HttpClient` của JDK để gọi API: đặt timeout, kiểm tra status code trước khi đọc body, gọi nhiều API song song. Học xong bài này, bạn giải thích được:

- Vì sao bên cung cấp API thêm một trường mới vào JSON mà client Jackson 2 của bạn chết, còn client Jackson 3 thì không.
- Vì sao `mapper.readValue(json, List.class)` biên dịch được nhưng ném `ClassCastException` ở một dòng khác.
- Vì sao một service gọi API chậm có thể treo hết thread nếu không đặt timeout, và vì sao response 404 không làm `HttpClient` ném exception.
- Vì sao code Jackson cũ không biên dịch được khi đổi dependency sang Jackson 3.

</Goal>

<Knowledge>

Ví dụ trong bài tiếp tục với đơn hàng của J9.1 và J9.2: cửa hàng gọi API của một hệ thống đặt hàng để lấy danh sách đơn và tạo đơn mới, dữ liệu trao đổi bằng JSON.

### Data binding: record thành JSON và ngược lại

API đơn hàng trả về `{"code":"DH-0001","customer":"Nguyễn Thị Hồng Nhung","amount":350000,"created_at":"2026-10-01T02:15:00Z"}`. Bạn muốn làm việc với một record `Order` có kiểu rõ ràng, không phải tự cắt chuỗi.

JSON là định dạng trao đổi dữ liệu phổ biến nhất giữa các service, nhưng JDK không có sẵn thư viện JSON. **Jackson** là thư viện được dùng nhiều nhất, và là mặc định của Spring Boot. Cách dùng chính của nó là **data binding**: ánh xạ thẳng giữa object Java và JSON, theo tên trường.

```text
record Order(code, customer, amount, createdAt)
        |   mapper.writeValueAsString(order)        ^
        v                                            |   mapper.readValue(json, Order.class)
{"code":"DH-0001","customer":"...","amount":350000,"created_at":"2026-10-01T02:15:00Z"}
```

Với Maven (J7), project khai báo một dependency. Bài dùng Jackson 3.2.3:

```xml
<dependency>
  <groupId>tools.jackson.core</groupId>
  <artifactId>jackson-databind</artifactId>
  <version>3.2.3</version>
</dependency>
```

`jackson-databind` kéo theo hai thư viện khác. Trong một project Maven `order-client` có dependency trên, lệnh `mvn dependency:tree` in cây dependency:

<Terminal where="mac">

```bash
mvn dependency:tree
```

</Terminal>

Phần giữa của kết quả là cây dependency:

```text
[INFO] vn.masteva:order-client:jar:1.0-SNAPSHOT
[INFO] \- tools.jackson.core:jackson-databind:jar:3.2.3:compile
[INFO]    +- com.fasterxml.jackson.core:jackson-annotations:jar:2.22:compile
[INFO]    \- tools.jackson.core:jackson-core:jar:3.2.3:compile
```

`jackson-core` đọc ghi JSON ở mức token, `jackson-databind` ánh xạ token thành object. `jackson-annotations` vẫn mang groupId cũ `com.fasterxml.jackson.core` và số phiên bản 2.x, kể cả trong Jackson 3; vì vậy annotation nằm ở package `com.fasterxml.jackson.annotation`. Các ví dụ Jackson trong bài cần ba thư viện này trên classpath. Trong project Maven, Maven tự thêm chúng khi biên dịch và chạy.

**`JsonMapper`** (lớp con của `ObjectMapper` dành cho JSON) là điểm vào của data binding. Đoạn sau ghi hai record ra JSON và đọc một chuỗi JSON ngược lại thành record:

```java norun
import com.fasterxml.jackson.annotation.JsonIgnore;
import com.fasterxml.jackson.annotation.JsonProperty;
import tools.jackson.databind.json.JsonMapper;

record Order(String code, String customer, long amount, @JsonProperty("created_at") Instant createdAt) {}

record NewOrder(String customer, long amount, @JsonIgnore String internalNote) {}

void main() {
    JsonMapper mapper = JsonMapper.builder().build();
    Order order = new Order("DH-0001", "Nguyễn Thị Hồng Nhung", 350_000, Instant.parse("2026-10-01T02:15:00Z"));
    String json = mapper.writeValueAsString(order);
    IO.println(json);
    IO.println(mapper.readValue(json, Order.class));
    IO.println(mapper.writeValueAsString(new NewOrder("Võ Thị Sáu", 99_000, "khach quen, giao gio hanh chinh")));
}
```

Kết quả:

```text
{"code":"DH-0001","customer":"Nguyễn Thị Hồng Nhung","amount":350000,"created_at":"2026-10-01T02:15:00Z"}
Order[code=DH-0001, customer=Nguyễn Thị Hồng Nhung, amount=350000, createdAt=2026-10-01T02:15:00Z]
{"customer":"Võ Thị Sáu","amount":99000}
```

Jackson hiểu record: tên component là tên trường JSON, và khi đọc, nó gọi constructor chính của record với các giá trị tìm thấy. Ba chỗ trong output đến từ cấu hình:

- `createdAt` thành `created_at` nhờ `@JsonProperty`, vì API dùng `snake_case` còn Java dùng `camelCase`.
- `Instant` được ghi thành chuỗi ISO-8601 mà không cần cấu hình hay module nào thêm.
- `internalNote` không xuất hiện trong JSON vì `@JsonIgnore`: ghi chú nội bộ ở lại trong service.

Các annotation hay dùng:

| Annotation | Đặt ở | Tác dụng |
|---|---|---|
| `@JsonProperty("created_at")` | Component, field | Đổi tên trường JSON |
| `@JsonIgnore` | Component, field | Không ghi ra JSON và không đọc vào |
| `@JsonIgnoreProperties(ignoreUnknown = true)` | Class | Bỏ qua trường lạ cho riêng class này |
| `@JsonFormat(pattern = "dd/MM/yyyy")` | Component, field | Định dạng riêng cho ngày giờ |

Tạo `JsonMapper` tốn kém: nó giữ cấu hình và bộ nhớ đệm về cấu trúc của mỗi class đã gặp. Sau khi tạo, nó thread-safe (nhiều thread dùng chung một đối tượng mà không hỏng, J11 dạy kỹ), nên một ứng dụng tạo một `JsonMapper` và dùng chung ở mọi nơi; trong Spring Boot, framework tạo sẵn và inject cho bạn.

### Trường lạ: bỏ qua hay báo lỗi

API đặt hàng trả về JSON có thêm trường `"channel":"pos"` mà record `Order` của bạn không có. Ở chiều ngược lại, một client gửi lên API của bạn trường gõ sai `"ammount"` thay cho `"amount"`. Hai tình huống cần hai phản ứng khác nhau.

Khi đọc một JSON có trường mà class không có, Jackson có hai cách: ném lỗi, hoặc bỏ qua. Cấu hình bằng `DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES`. Đoạn sau đọc cùng một JSON bằng mapper mặc định và bằng một mapper bật kiểm tra chặt:

```java norun
import tools.jackson.core.JacksonException;
import tools.jackson.databind.DeserializationFeature;
import tools.jackson.databind.json.JsonMapper;

record Order(String code, String customer, long amount) {}

void main() {
    String json = """
            {"code":"DH-0002","customer":"Trần Văn Đức","amount":1200000,"channel":"pos"}
            """;
    IO.println(JsonMapper.builder().build().readValue(json, Order.class));

    JsonMapper strict = JsonMapper.builder().enable(DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES).build();
    try {
        strict.readValue(json, Order.class);
    } catch (JacksonException e) {
        IO.println(e.getClass().getSimpleName() + ": " + e.getOriginalMessage());
    }
}
```

<Predict question="Mapper mặc định gặp trường channel thì làm gì?">

```text
Order[code=DH-0002, customer=Trần Văn Đức, amount=1200000]
UnrecognizedPropertyException: Unrecognized property "channel" (class Main$Order), not marked as ignorable
```

Mapper mặc định của Jackson 3 bỏ qua `channel` và đọc phần còn lại. Chỉ mapper `strict` mới ném `UnrecognizedPropertyException`; ném lỗi khi gặp trường lạ lại là mặc định của Jackson 2. `Main$Order` là tên đầy đủ của record `Order` khai báo bên trong chương trình `Main`. Khối `catch (JacksonException e)` là tuỳ chọn: `JacksonException` là unchecked exception, nên `main` không cần khai báo `throws`.

</Predict>

Bỏ qua trường lạ là mẫu **tolerant reader** (người đọc dễ tính): client chỉ đọc những trường nó cần, nên không chết khi bên cung cấp API thêm trường mới. Báo lỗi thì giúp phát hiện gõ sai tên trường. Chọn theo vai trò của code:

| Code của bạn | Nên | Vì sao |
|---|---|---|
| Client đọc API của bên khác | Bỏ qua trường lạ | Bên kia thêm trường bất cứ lúc nào, và đó là thay đổi tương thích |
| API của chính bạn đọc request | Có thể báo lỗi | Client gửi `"ammount"` gõ sai thì nên nhận lỗi rõ ràng, thay vì đơn hàng có số tiền 0 |

Dòng thứ hai của bảng dựa trên hành vi sau: mapper mặc định bỏ qua `"ammount"` như một trường lạ, và component `amount` kiểu `long` không có giá trị nào thì nhận 0:

```java norun
import tools.jackson.databind.json.JsonMapper;

record NewOrder(String customer, long amount) {}

void main() {
    String typo = "{\"customer\":\"Võ Thị Sáu\",\"ammount\":99000}";
    IO.println(JsonMapper.builder().build().readValue(typo, NewOrder.class));
}
```

Kết quả:

```text
NewOrder[customer=Võ Thị Sáu, amount=0]
```

Không có lỗi nào, và đơn hàng 99.000 đồng thành đơn 0 đồng. Với API nhận request, bật `FAIL_ON_UNKNOWN_PROPERTIES` để client gõ sai nhận lỗi ngay.

<Callout kind="production">

Một đối tác thanh toán thêm trường `"channel"` vào JSON trả về. Service dùng Jackson 2 với cấu hình mặc định bắt đầu ném `UnrecognizedPropertyException` ở mọi response, và mọi đơn hàng đều lỗi cho tới khi bản sửa được deploy. Client đọc API bên ngoài nên bỏ qua trường lạ, bằng cấu hình chung của mapper hoặc `@JsonIgnoreProperties(ignoreUnknown = true)` trên từng class.

</Callout>

### Jackson 2 và Jackson 3

Bạn nâng dependency từ Jackson 2 lên Jackson 3 và project không biên dịch được nữa, dù không đổi một dòng code nào.

Jackson 3.0 ra ngày 3/10/2025. Nhánh 2 vẫn được bảo trì song song, và phần lớn code hiện có, kể cả ứng dụng Spring Boot 3, dùng nhánh này. Hai nhánh khác nhau ở những điểm sau:

| | Jackson 2.x | Jackson 3.x |
|---|---|---|
| Maven groupId | `com.fasterxml.jackson.core` | `tools.jackson.core` |
| Package trong code | `com.fasterxml.jackson.databind` | `tools.jackson.databind` |
| Package annotation | `com.fasterxml.jackson.annotation` | Giữ nguyên `com.fasterxml.jackson.annotation` |
| Exception | `JsonProcessingException`, checked | `JacksonException`, unchecked |
| Kiểu `java.time` | Cần thêm module `jackson-datatype-jsr310` | Có sẵn trong databind |
| Trường lạ khi đọc | Mặc định ném lỗi | Mặc định bỏ qua |
| Ngày giờ khi ghi | Mặc định là số (timestamp) | Mặc định là chuỗi ISO-8601 |
| JDK tối thiểu | 8 | 17 |

Đoạn sau là code Jackson 2 điển hình, biên dịch với dependency Jackson 3 ở trên:

```java norun
import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;

void main() throws JsonProcessingException {
    IO.println(new ObjectMapper().writeValueAsString(List.of("DH-0001")));
}
```

Kết quả:

```text

import com.fasterxml.jackson.core.JsonProcessingException;
                                 ^
Main.java:2: error: package com.fasterxml.jackson.databind does not exist
import com.fasterxml.jackson.databind.ObjectMapper;
                                     ^
Main.java:4: error: cannot find symbol
void main() throws JsonProcessingException {
                   ^
  symbol:   class JsonProcessingException
  location: class Main
Main.java:5: error: cannot find symbol
    IO.println(new ObjectMapper().writeValueAsString(List.of("DH-0001")));
                   ^
  symbol:   class ObjectMapper
  location: class Main
4 errors

```

Đổi lên Jackson 3 không chỉ là đổi số phiên bản: mọi `import` của `databind` và `core` đổi sang `tools.jackson`, và mọi chỗ bắt `JsonProcessingException` phải sửa. Chỉ `import` của annotation giữ nguyên. Bài này dùng Jackson 3 vì đây là nhánh phát triển chính cho dự án mới trên Java 17 trở lên, có sẵn hỗ trợ `java.time` và mặc định an toàn hơn cho client. Bạn vẫn cần đọc được Jackson 2, vì sẽ gặp package `com.fasterxml.jackson` trong rất nhiều project đang chạy.

### Generic và TypeReference

API trả về một mảng đơn hàng `[{...}, {...}]`. Bạn viết `List<Order> orders = mapper.readValue(json, List.class)`; code biên dịch với một cảnh báo, rồi nổ ở dòng đọc đơn đầu tiên.

Java xoá thông tin kiểu generic khi biên dịch (type erasure, J5.2): `List.class` chỉ là "một list", không có `Order` nào trong đó. Jackson không biết phần tử là `Order`, nên đọc mỗi object JSON thành một `Map`. Đoạn sau đọc cùng một mảng bằng hai cách:

```java norun
import tools.jackson.core.type.TypeReference;
import tools.jackson.databind.json.JsonMapper;

record Order(String code, long amount) {}

@SuppressWarnings("unchecked")
void main() {
    JsonMapper mapper = JsonMapper.builder().build();
    String json = """
            [{"code":"DH-0001","amount":350000},{"code":"DH-0002","amount":1200000}]
            """;
    List<Order> raw = mapper.readValue(json, List.class);
    IO.println("List.class -> phan tu la " + ((Object) raw.get(0)).getClass().getName());
    try {
        Order first = raw.get(0);
    } catch (ClassCastException e) {
        IO.println("ClassCastException khi lay phan tu dau tien");
    }

    List<Order> orders = mapper.readValue(json, new TypeReference<List<Order>>() {});
    IO.println("TypeReference -> " + orders.get(0).code() + ", tong " + orders.stream().mapToLong(Order::amount).sum());
}
```

Kết quả:

```text
List.class -> phan tu la java.util.LinkedHashMap
ClassCastException khi lay phan tu dau tien
TypeReference -> DH-0001, tong 1550000
```

Với `List.class`, `raw` là `List<Order>` chỉ trên giấy: phần tử thật là `LinkedHashMap`. Ở chỗ code dùng một phần tử như `Order`, như dòng `Order first = raw.get(0)`, compiler tự chèn một phép ép kiểu sang `Order`, và chính phép ép đó ném `ClassCastException`, có thể cách chỗ đọc JSON rất xa. Dòng in kiểu ép phần tử sang `Object` trước để tránh phép ép ngầm này và in ra kiểu thật. **`TypeReference`** giữ lại kiểu đầy đủ: `new TypeReference<List<Order>>() {}` tạo một lớp con vô danh, và kiểu generic ghi trong khai báo lớp con thì không bị xoá, nên Jackson đọc được `List<Order>` từ đó. Gặp JSON là mảng hoặc map, luôn dùng `TypeReference`.

### Thiết kế record cho JSON: DTO và kiểu số

Một service để Jackson ghi thẳng entity `Customer` ra JSON (entity: class ánh xạ một bảng database, học ở SB3). Một hôm có người thêm cột `password_hash` vào bảng, và API bắt đầu trả mật khẩu đã băm của mọi khách.

Record `Order` và `NewOrder` ở các mục trên là **DTO** (data transfer object): class chỉ dùng để mang dữ liệu qua ranh giới API. Entity thay đổi theo database; API là hợp đồng với client. Gắn hai thứ vào nhau thì đổi tên một cột là vỡ API, thêm một cột nhạy cảm là lộ dữ liệu. Tạo record riêng cho request và response, rồi chuyển đổi giữa entity và DTO ở một chỗ.

Kiểu của từng trường cũng là một phần của hợp đồng. JSON chỉ có một kiểu số, và nhiều client, như JavaScript trong trình duyệt, đọc mọi số thành `double`. Đoạn sau mô phỏng điều đó trong Java:

```java
void main() {
    long amount = 9_007_199_254_740_993L;
    double asJavaScriptSees = amount;
    IO.println(amount + " -> " + (long) asJavaScriptSees);
    IO.println(0.1 + 0.2);
    IO.println(new BigDecimal("0.1").add(new BigDecimal("0.2")));
}
```

Kết quả:

```text
9007199254740993 -> 9007199254740992
0.30000000000000004
0.3
```

`double` giữ chính xác số nguyên chỉ tới khoảng 9 triệu tỷ (2^53); lớn hơn thì mất đơn vị cuối. Số lẻ thập phân như 0,1 thì không biểu diễn chính xác được ở hệ nhị phân. Bài dùng `long` theo đơn vị đồng, như J1. Với tiền có phần lẻ, nhiều API gửi dạng chuỗi (`"amount":"125000.50"`) hoặc số nguyên ở đơn vị nhỏ nhất, kèm mã tiền tệ; phía Java dùng `BigDecimal` hoặc `long`, không dùng `double`.

### HttpClient: client, request và response

Cửa hàng cần lấy danh sách đơn từ API đặt hàng, tạo đơn mới, và không muốn thêm thư viện HTTP nào vào project.

Từ Java 11 (JEP 321), gói `java.net.http` có một HTTP client hỗ trợ HTTP/1.1 và HTTP/2, gọi đồng bộ và bất đồng bộ. Ba thành phần chính:

```text
HttpClient   tạo một lần, dùng chung: connection pool, connectTimeout, HTTP/2
    |
    |  send(request, BodyHandler)        đồng bộ: thread chờ tới khi có response
    |  sendAsync(request, BodyHandler)   bất đồng bộ: trả CompletableFuture ngay
    v
HttpRequest      URI, method, header, body, timeout của riêng request; bất biến
    |
    v
HttpResponse<T>  statusCode(), headers(), body() kiểu T do BodyHandler quyết định
```

Sơ đồ có vài thuật ngữ được giải thích ở các mục sau: connection pool ở cuối mục này, `CompletableFuture` ở mục `sendAsync`. `BodyHandler` quyết định body được đọc thành gì:

- `BodyHandlers.ofString()`: thành chuỗi.
- `BodyHandlers.ofFile(path)`: ghi thẳng ra file.
- `BodyHandlers.discarding()`: bỏ qua body.

Chiều gửi đi dùng `BodyPublishers`, ví dụ `BodyPublishers.ofString(json)` mã hoá chuỗi bằng UTF-8. Gói `java.net.http` và `com.sun.net.httpserver` nằm ngoài module `java.base`, nên file `void main()` phải `import` chúng, khác với `URI` hay `Duration`.

Các ví dụ HTTP trong bài không gọi ra internet. Mỗi ví dụ tự chạy một server giả lập nhỏ ở đầu chương trình, viết bằng `com.sun.net.httpserver.HttpServer` có sẵn trong JDK (J10.1 dùng nó để dựng API), ở một cổng trống do hệ điều hành chọn. Phần đáng đọc là phần client phía sau. Đoạn sau lấy danh sách đơn và tạo một đơn mới:

```java
import com.sun.net.httpserver.HttpServer;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

void main() throws Exception {
    // server giả lập
    HttpServer server = HttpServer.create(new InetSocketAddress("localhost", 0), 0);
    server.createContext("/orders", exchange -> {
        String received = new String(exchange.getRequestBody().readAllBytes(), StandardCharsets.UTF_8);
        String reply = exchange.getRequestMethod().equals("POST") ? received : "[{\"code\":\"DH-0001\",\"customer\":\"Nguyễn Thị Hồng Nhung\"}]";
        byte[] bytes = reply.getBytes(StandardCharsets.UTF_8);
        exchange.getResponseHeaders().set("Content-Type", "application/json; charset=utf-8");
        exchange.sendResponseHeaders(exchange.getRequestMethod().equals("POST") ? 201 : 200, bytes.length);
        try (exchange) { exchange.getResponseBody().write(bytes); }
    });
    server.start();
    URI orders = URI.create("http://localhost:" + server.getAddress().getPort() + "/orders");

    // phía client
    try (HttpClient http = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build()) {
        HttpRequest list = HttpRequest.newBuilder(orders).header("Accept", "application/json").timeout(Duration.ofSeconds(5)).build();
        HttpResponse<String> response = http.send(list, HttpResponse.BodyHandlers.ofString());
        IO.println(response.statusCode() + " " + response.headers().firstValue("Content-Type").orElseThrow());
        IO.println(response.headers().firstValue("Content-Length").orElseThrow() + " byte, " + response.body().length() + " ky tu: " + response.body());

        HttpRequest create = HttpRequest.newBuilder(orders).header("Content-Type", "application/json").timeout(Duration.ofSeconds(5))
                .POST(HttpRequest.BodyPublishers.ofString("{\"customer\":\"Võ Thị Sáu\",\"amount\":99000}")).build();
        HttpResponse<String> created = http.send(create, HttpResponse.BodyHandlers.ofString());
        IO.println(created.statusCode() + " " + created.body());
    } finally {
        server.stop(0);
    }
}
```

Kết quả:

```text
200 application/json; charset=utf-8
61 byte, 55 ky tu: [{"code":"DH-0001","customer":"Nguyễn Thị Hồng Nhung"}]
201 {"customer":"Võ Thị Sáu","amount":99000}
```

Phần dưới comment `// phía client` là code client. Server giả lập trả danh sách cho `GET`, và trả lại nguyên body nó nhận được cho `POST`, nên dòng cuối cho thấy chuỗi tiếng Việt đi qua mạng mà không mất dấu. Để ý ba điểm:

- `Content-Length` là số **byte** (61), nhiều hơn số ký tự (55), vì chữ có dấu chiếm 2 tới 3 byte trong UTF-8 như ở J9.1. `BodyHandlers.ofString()` đọc charset từ header `Content-Type` để giải mã, mặc định UTF-8.
- `HttpRequest.newBuilder(...)...build()` tạo một request bất biến, dùng lại được nhiều lần. `HttpRequest` mặc định là `GET`; `POST(...)` đổi method và gắn body.
- Từ Java 21, `HttpClient` cài `AutoCloseable`, nên try-with-resources (J4) đóng nó và các kết nối của nó khi xong việc.

Trong ứng dụng thật, `HttpClient` được tạo một lần và dùng chung, giống `JsonMapper`. Client giữ một **connection pool**: request sau dùng lại kết nối TCP (và TLS, lớp mã hoá của HTTPS) đã mở, bỏ qua bước bắt tay (các lượt trao đổi để mở kết nối) tốn hàng chục mili giây. Tạo client mới cho mỗi request làm mất pool và có thể để lại kết nối chưa đóng. Javadoc của `HttpClient` ghi rằng client đã tạo xong là bất biến và gửi được nhiều request.

### Status code lỗi không phải exception

Code gọi API đơn hàng, rồi đưa thẳng body cho Jackson. Một hôm API trả 404 kèm một trang lỗi HTML, và log đầy lỗi parse JSON khó hiểu thay vì một dòng "không tìm thấy đơn".

Với `HttpClient`, response 404 hay 500 vẫn là một response hợp lệ: server đã trả lời, chỉ là câu trả lời là "lỗi". `send` chỉ ném exception khi không có response nào, ví dụ không kết nối được. Đoạn sau gọi một đường dẫn không tồn tại, rồi dừng server và gọi lại:

```java
import com.sun.net.httpserver.HttpServer;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

void main() throws Exception {
    // server giả lập
    HttpServer server = HttpServer.create(new InetSocketAddress("localhost", 0), 0);
    server.start(); // không khai báo đường dẫn nào: mọi request đều nhận 404
    URI missing = URI.create("http://localhost:" + server.getAddress().getPort() + "/orders/DH-9999");

    // phía client
    try (HttpClient http = HttpClient.newHttpClient()) {
        HttpRequest request = HttpRequest.newBuilder(missing).timeout(Duration.ofSeconds(5)).build();
        HttpResponse<String> response = http.send(request, HttpResponse.BodyHandlers.ofString());
        IO.println("status " + response.statusCode() + ", body: " + response.body());

        server.stop(0);
        try {
            http.send(request, HttpResponse.BodyHandlers.ofString());
        } catch (ConnectException e) {
            IO.println("server da dung -> " + e.getClass().getName());
        }
    }
}
```

Kết quả:

```text
status 404, body: <h1>404 Not Found</h1>No context found for request
server da dung -> java.net.ConnectException
```

Lần gọi đầu không có exception nào: bạn nhận status 404 và một body HTML. Nếu code đưa body này cho `mapper.readValue`, lỗi bạn thấy là lỗi parse JSON, không phải "đơn không tồn tại". Lần gọi thứ hai không có response, nên `send` ném `ConnectException`. Lỗi này đến gần như ngay lập tức: không có tiến trình nào nghe ở cổng đó, và hệ điều hành từ chối kết nối.

Quy tắc: kiểm `statusCode()` trước khi đọc body, và quyết định riêng cho từng nhóm status:

| Status | Ý nghĩa | Xử lý thường gặp |
|---|---|---|
| 2xx | Thành công | Parse body |
| 4xx | Request của bạn sai, hoặc dữ liệu không tồn tại | Báo lỗi nghiệp vụ, không thử lại; riêng 429 (Too Many Requests) thì thử lại sau thời gian server báo |
| 5xx | Server bên kia lỗi | Ghi log, thử lại có giới hạn |
| `ConnectException`, `HttpTimeoutException` | Không có response | Ghi log, thử lại có giới hạn hoặc trả lỗi cho người gọi |

`ConnectException` và `HttpTimeoutException` đều là `IOException`, nên một khối `catch (IOException e)` bắt được cả hai khi bạn xử lý chúng giống nhau.

### Timeout: connect timeout và request timeout

API của đối tác chậm lại, mỗi request mất 30 giây. Service của bạn không đặt timeout. Sau vài phút, mọi thread xử lý request đều đang chờ đối tác, và service ngừng trả lời cả những trang không liên quan gì tới đối tác, dù CPU gần như rảnh.

Lý do nằm ở cách server xử lý request: mỗi request chạy trên một **thread** (luồng thực thi; chương trình nào cũng có ít nhất thread `main`), và server chỉ có một số thread giới hạn, thường vài trăm. Thread đang chờ đối tác trả lời thì không phục vụ được request khác. J11 dạy kỹ về thread.

`HttpClient` có hai timeout, đặt ở hai chỗ khác nhau:

| Timeout | Đặt ở | Giới hạn điều gì |
|---|---|---|
| Connect timeout | `HttpClient.newBuilder().connectTimeout(...)` | Thời gian chờ mở một kết nối TCP mới |
| Request timeout | `HttpRequest.newBuilder().timeout(...)` | Thời gian chờ response của một request |

Mặc định không có timeout nào. [Javadoc của `HttpRequest.Builder.timeout`](https://docs.oracle.com/en/java/javase/25/docs/api/java.net.http/java/net/http/HttpRequest.Builder.html#timeout(java.time.Duration)) ghi rằng không đặt timeout thì giống đặt một khoảng vô hạn, tức chờ mãi. Đoạn sau gọi một đường dẫn mà server giả lập chờ 2 giây mới trả lời, với request timeout 500 mili giây:

```java
import com.sun.net.httpserver.HttpServer;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.net.http.HttpTimeoutException;

void main() throws Exception {
    // server giả lập
    HttpServer server = HttpServer.create(new InetSocketAddress("localhost", 0), 0);
    server.createContext("/slow", exchange -> {
        try { Thread.sleep(2_000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        exchange.sendResponseHeaders(200, -1);
        exchange.close();
    });
    server.start();
    URI slow = URI.create("http://localhost:" + server.getAddress().getPort() + "/slow");

    // phía client
    try (HttpClient http = HttpClient.newHttpClient()) {
        HttpRequest request = HttpRequest.newBuilder(slow).timeout(Duration.ofMillis(500)).build();
        long start = System.nanoTime();
        try {
            http.send(request, HttpResponse.BodyHandlers.discarding());
        } catch (HttpTimeoutException e) {
            long waited = (System.nanoTime() - start) / 1_000_000;
            IO.println(e.getMessage() + ", cho it hon 2 giay cua server? " + (waited < 2_000));
        }
    } finally {
        server.stop(0);
    }
}
```

Kết quả:

```text
request timed out, cho it hon 2 giay cua server? true
```

`send` ném `HttpTimeoutException` sau khoảng 500 mili giây, không chờ đủ 2 giây của server. Thread của bạn được trả lại để phục vụ việc khác, còn request chậm thành một lỗi bạn xử lý được.

Connect timeout chỉ có tác dụng khi phải mở kết nối mới và máy đích không trả lời gì, ví dụ khi firewall âm thầm bỏ gói tin. Khi máy đích từ chối thẳng, như lần gọi thứ hai ở mục trước, lỗi đến ngay mà không cần timeout. Nếu kết nối được dùng lại từ pool, connect timeout không áp dụng. Một client production đặt cả hai: connect timeout vài giây, request timeout theo thời gian trả lời chấp nhận được của từng API.

### Dùng chung client, send và sendAsync

Trang thanh toán cần giá giao hàng từ ba nhà vận chuyển. Mỗi API mất khoảng 1 giây; gọi lần lượt thì khách chờ 3 giây.

`send` là lời gọi **đồng bộ**: thread gọi nó dừng lại tới khi có response. `sendAsync` là lời gọi **bất đồng bộ**: nó trả ngay một `CompletableFuture<HttpResponse<T>>`, một đối tượng sẽ chứa response khi response về (J11 dạy kỹ `CompletableFuture`). Gửi ba request bằng `sendAsync` rồi chờ cả ba thì ba lời gọi chạy song song:

```java
import com.sun.net.httpserver.HttpServer;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

void main() throws Exception {
    // server giả lập
    HttpServer server = HttpServer.create(new InetSocketAddress("localhost", 0), 0);
    server.setExecutor(Executors.newVirtualThreadPerTaskExecutor()); // xử lý nhiều request cùng lúc
    AtomicInteger inFlight = new AtomicInteger();
    AtomicInteger maxInFlight = new AtomicInteger();
    server.createContext("/quote", exchange -> {
        maxInFlight.accumulateAndGet(inFlight.incrementAndGet(), Math::max); // đếm request đang xử lý cùng lúc
        try { Thread.sleep(1_000); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        inFlight.decrementAndGet();
        byte[] body = ("gia tu " + exchange.getRequestURI().getQuery()).getBytes(StandardCharsets.UTF_8);
        exchange.sendResponseHeaders(200, body.length);
        try (exchange) { exchange.getResponseBody().write(body); }
    });
    server.start();
    String base = "http://localhost:" + server.getAddress().getPort() + "/quote?";

    // phía client
    try (HttpClient http = HttpClient.newHttpClient()) {
        List<CompletableFuture<HttpResponse<String>>> futures = new ArrayList<>();
        for (String carrier : List.of("ghn", "ghtk", "viettelpost")) {
            HttpRequest request = HttpRequest.newBuilder(URI.create(base + carrier)).timeout(Duration.ofSeconds(3)).build();
            futures.add(http.sendAsync(request, HttpResponse.BodyHandlers.ofString()));
        }
        for (CompletableFuture<HttpResponse<String>> future : futures) {
            IO.println(future.join().body());
        }
        IO.println("server xu ly cung luc toi da " + maxInFlight.get() + " request");
    } finally {
        server.stop(0);
    }
}
```

Kết quả:

```text
gia tu ghn
gia tu ghtk
gia tu viettelpost
server xu ly cung luc toi da 3 request
```

Server giả lập đếm số request nó đang xử lý cùng lúc, và con số tối đa là 3: cả ba request cùng chờ trong một giây đó, nên tổng thời gian khoảng 1 giây thay vì 3. Vòng `for` đầu gửi cả ba mà không chờ, vòng sau mới chờ từng kết quả bằng `join()`. Kết quả in theo thứ tự trong list `futures`, không theo thứ tự response về. Timeout của request vẫn áp dụng với `sendAsync`: quá hạn thì future hoàn tất bằng `HttpTimeoutException` thay vì treo mãi.

`sendAsync` hữu ích khi cần gộp kết quả của vài lời gọi song song. Với một lời gọi đơn lẻ, `send` đồng bộ dễ đọc hơn: code chạy từ trên xuống, exception ném ra đúng chỗ. Cái giá của `send` là một thread bị giữ trong lúc chờ. Từ Java 21, **virtual thread** (thread nhẹ do JVM quản lý, J11) làm cái giá đó rất rẻ: mỗi request chạy trên một virtual thread, và một service giữ được hàng nghìn lời gọi `send` đang chờ cùng lúc.
