<Goal>

Đọc, ghi, sao chép file và duyệt thư mục bằng NIO.2 (`Path`, `Files`), đóng tài nguyên đúng cách; giữ đúng dấu tiếng Việt khi chuyển giữa ký tự và byte; và chọn đúng công cụ của JCA khi cần băm, ký hay mã hoá dữ liệu. Học xong bài này, bạn giải thích được:

- Vì sao file CSV mở ra thấy `Nguyá»…n` thay vì `Nguyễn`, khi nào sửa lại được, và vì sao hai tên trông giống hệt nhau lại không bằng nhau.

- Vì sao dùng lại IV với AES-GCM làm lộ dữ liệu, dù khoá vẫn được giữ bí mật.

<Knowledge>

Ví dụ trong bài dùng tình huống của cả chặng J9: một cửa hàng nhận file đơn hàng CSV mỗi ngày, mỗi dòng gồm mã đơn, tên khách, thành phố và số tiền tính bằng đồng.

### Luồng byte và luồng ký tự của java.io

Một thư viện đưa cho bạn file đơn hàng dưới dạng `InputStream`: đó có thể là resource trong file jar, body của một HTTP request, hay `System.in`. Bạn cần từng dòng chữ, còn thứ bạn đang cầm chỉ cho đọc từng byte.

Gói `java.io` có từ Java 1.0 và chia làm hai nhánh:

| Nhánh | Lớp gốc | Đơn vị | Dùng cho |
|---|---|---|---|
| Luồng byte (byte stream) | `InputStream`, `OutputStream` | `byte` | Ảnh, file zip, dữ liệu mạng thô |
| Luồng ký tự (character stream) | `Reader`, `Writer` | `char` | File văn bản, CSV, JSON |

Ổ đĩa và mạng chỉ chứa byte. Muốn có ký tự, bạn phải giải mã byte theo một **charset** (bảng quy ước chuyển ký tự thành byte và ngược lại, mục Charset bên dưới nói kỹ). Lớp làm cầu nối giữa hai nhánh là `InputStreamReader`. Đoạn sau ghi một file CSV nhỏ, rồi đọc lại bằng ba lớp `java.io` lồng vào nhau:

```java
void main() throws IOException {
    Files.writeString(Path.of("orders.csv"), """
            code,customer,city,amount
            DH-0001,Nguyễn Thị Hồng Nhung,Hà Nội,350000
            DH-0002,Trần Văn Đức,Đà Nẵng,1200000
            """);
    try (BufferedReader reader = new BufferedReader(
            new InputStreamReader(new FileInputStream("orders.csv"), StandardCharsets.UTF_8))) {
        reader.readLine(); // bỏ dòng tiêu đề
        String line;
        while ((line = reader.readLine()) != null) {
            IO.println(line);
        }
    }
}
```

Kết quả:

```text
DH-0001,Nguyễn Thị Hồng Nhung,Hà Nội,350000
DH-0002,Trần Văn Đức,Đà Nẵng,1200000
```

Mỗi lớp bọc lớp bên trong và thêm đúng một khả năng:

```text
file trên đĩa
   |  FileInputStream             đọc byte thô
   v
InputStreamReader(..., UTF_8)     giải mã byte thành char theo charset
   |
   v
BufferedReader                    gom vào bộ đệm, đọc từng dòng bằng readLine()
```

Cách ghép này là mẫu **decorator**: lớp ngoài giữ tham chiếu tới lớp trong và chuyển lời gọi xuống nó. Đóng lớp ngoài cùng thì cả chuỗi được đóng, nên khối try-with-resources (J4) khai báo mỗi `reader` là đủ. Dòng `Files.writeString` ở đầu thuộc NIO.2, phần ngay sau đây.

Code mới vẫn gặp `java.io` mỗi khi API bạn gọi chỉ nhận hoặc chỉ trả `InputStream`, `Reader`: thư viện parse, body HTTP, `System.in`, `getResourceAsStream`. Riêng lớp `java.io.File` thì nên tránh trong code mới; khi một API cũ đòi `File`, đổi qua lại bằng `path.toFile()` và `file.toPath()`.

### Path và Files của NIO.2

Code cũ xoá file tạm bằng `new File(...).delete()`. Một hôm method này trả `false`, và không ai biết vì sao: file không tồn tại, không có quyền, hay đang bị chương trình khác giữ.

Java 7 thêm gói `java.nio.file`, thường gọi là **NIO.2**. `Path` là một đường dẫn; `Files` là lớp tiện ích gồm các method tĩnh để đọc, ghi, sao chép và duyệt. Đoạn sau xoá cùng một file không tồn tại bằng hai API:

```java
void main() {
    IO.println("File.delete  -> " + new File("khong-co.csv").delete());
    try {
        Files.delete(Path.of("khong-co.csv"));
    } catch (IOException e) {
        IO.println("Files.delete -> " + e);
    }
}
```

Kết quả:

```text
File.delete  -> false
Files.delete -> java.nio.file.NoSuchFileException: khong-co.csv
```

`File.delete` chỉ báo thất bại. `Files.delete` ném một exception có tên nói đúng lý do. Các exception này (`NoSuchFileException`, `AccessDeniedException`, `FileAlreadyExistsException`) đều là con của `IOException`, nên bạn bắt riêng loại cần xử lý và để các lỗi khác đi tiếp.

Bảng dưới là các method của `Files` dùng nhiều nhất; danh sách đầy đủ ở Javadoc trong phần Tài liệu:

| Việc | Method | Ghi chú |
|---|---|---|
| Đọc cả file thành chuỗi | `Files.readString(path)` | Nạp cả file vào bộ nhớ, chỉ dùng cho file nhỏ |
| Đọc từng dòng, file lớn | `Files.lines(path)` | Trả `Stream<String>` đọc dần, phải đóng |
| Đọc kiểu `java.io` | `Files.newBufferedReader(path)` | Thay cho chuỗi ba lớp ở mục trước |
| Ghi chuỗi | `Files.writeString(path, text)` | Mặc định tạo mới hoặc ghi đè; thêm `StandardOpenOption.APPEND` để ghi nối |
| Tạo thư mục | `Files.createDirectories(dir)` | Tạo cả thư mục cha, không lỗi nếu đã có |
| Sao chép, di chuyển | `Files.copy`, `Files.move` | Đích đã tồn tại thì lỗi, trừ khi thêm `REPLACE_EXISTING` |
| Duyệt thư mục | `Files.list(dir)`, `Files.walk(dir)` | `walk` đi cả thư mục con; phải đóng |

Khi không truyền charset, các method đọc ghi chữ của `Files` luôn dùng UTF-8, bất kể máy chạy là gì. Đoạn sau tạo thư mục sao lưu và sao chép file đơn hàng vào đó hai lần:

```java
void main() throws IOException {
    Path orders = Path.of("data", "orders-2026-10-01.csv");
    Files.createDirectories(orders.getParent().resolve("backup"));
    Files.writeString(orders, "code,customer,city,amount\nDH-0003,Lê Thị Ánh,Hồ Chí Minh,89000\n");
    Path backup = orders.resolveSibling("backup").resolve(orders.getFileName());

    Files.copy(orders, backup);
    try {
        Files.copy(orders, backup);
    } catch (FileAlreadyExistsException e) {
        IO.println("copy lan 2 -> " + e);
    }
    Files.copy(orders, backup, StandardCopyOption.REPLACE_EXISTING);
    IO.println(backup + ": " + Files.size(backup) + " byte");
}
```

Kết quả:

```text
copy lan 2 -> java.nio.file.FileAlreadyExistsException: data/backup/orders-2026-10-01.csv
data/backup/orders-2026-10-01.csv: 70 byte
```

`resolve` nối thêm một phần vào cuối đường dẫn, `resolveSibling` thay phần cuối bằng tên khác. `Files.copy` từ chối ghi đè cho tới khi bạn nói rõ bằng `REPLACE_EXISTING`. File có 63 ký tự nhưng 70 byte; mục Charset bên dưới giải thích phần chênh.

Ghi đè có một rủi ro: nếu process chết giữa lúc `Files.writeString` đang ghi, file đích chỉ còn một nửa, và chương trình đọc nó sau đó nhận dữ liệu cụt. Với file quan trọng như báo cáo hay cấu hình, ghi ra một file tạm trong cùng thư mục rồi đổi tên nó thành file đích bằng `ATOMIC_MOVE`:

```java
void main() throws IOException {
    Path report = Path.of("report.txt");
    Files.writeString(report, "ban cu\n");

    Path tmp = Files.createTempFile(Path.of("."), "report-", ".tmp");
    Files.writeString(tmp, "ban moi, day du\n");
    Files.move(tmp, report, StandardCopyOption.ATOMIC_MOVE);

    IO.print(Files.readString(report));
    IO.println("file tam con khong? " + Files.exists(tmp));
}
```

Kết quả:

```text
ban moi, day du
file tam con khong? false
```

Đổi tên trong cùng một hệ thống file là một thao tác nguyên tử (atomic): người đọc chỉ thấy bản cũ hoặc bản mới hoàn chỉnh, không bao giờ thấy bản ghi dở. File tạm phải nằm cùng thư mục với file đích, vì `ATOMIC_MOVE` sang ổ khác ném `AtomicMoveNotSupportedException`. [Javadoc của `Files.move`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/file/Files.html#move(java.nio.file.Path,java.nio.file.Path,java.nio.file.CopyOption...)) để việc thay file đích đã tồn tại tuỳ hệ điều hành; trên Linux và macOS, nó được thay như output trên.

### Stream của Files phải được đóng

Một job tổng hợp doanh thu chạy ổn nhiều tháng. Rồi một hôm nó dừng với `Too many open files`, dù code không đổi gì.

`Files.lines`, `Files.list` và `Files.walk` trả về một `Stream` đọc dần (lazy): nó chỉ đọc file hay thư mục khi bạn duyệt tới, và giữ file hay thư mục đó mở cho tới khi stream được đóng. Javadoc của cả ba method ghi rằng chúng phải được dùng trong try-with-resources. Đoạn sau tạo thư mục `inbox` chứa hai file đơn hàng mới nhận, một nằm trong thư mục con `pos`, rồi cộng doanh thu theo khách từ mọi file `.csv`:

```java
void main() throws IOException {
    Path inbox = Path.of("inbox");
    Files.createDirectories(inbox.resolve("pos"));
    Files.writeString(inbox.resolve("orders-2026-10-01.csv"), "code,customer,city,amount\n"
            + "DH-0001,Nguyễn Thị Hồng Nhung,Hà Nội,350000\nDH-0002,Trần Văn Đức,Đà Nẵng,1200000\n");
    Files.writeString(inbox.resolve("pos/orders-pos.csv"), "code,customer,city,amount\n"
            + "DH-0006,Nguyễn Thị Hồng Nhung,Hà Nội,200000\n");

    List<Path> files;
    try (Stream<Path> paths = Files.walk(inbox)) {
        files = paths.filter(p -> p.toString().endsWith(".csv")).sorted().toList();
    }
    Map<String, Long> totals = new TreeMap<>();
    for (Path file : files) {
        try (Stream<String> lines = Files.lines(file)) {
            lines.skip(1).map(line -> line.split(","))
                    .forEach(cols -> totals.merge(cols[1], Long.parseLong(cols[3]), Long::sum));
        }
        IO.println("da doc " + file);
    }
    IO.println(totals);
}
```

Kết quả:

```text
da doc inbox/orders-2026-10-01.csv
da doc inbox/pos/orders-pos.csv
{Nguyễn Thị Hồng Nhung=550000, Trần Văn Đức=1200000}
```

Ba chỗ trong đoạn code là có chủ đích:

- Danh sách file được gom thành `List` ngay trong khối `try` của `Files.walk`, nên thư mục được đóng trước khi đọc từng file.
- `walk` đi vào cả thư mục con, nên tìm thấy `pos/orders-pos.csv`. Thứ tự nó trả các file tuỳ hệ thống file, nên `sorted()` giữ output giống nhau trên mọi máy.
- Mỗi `Files.lines` có khối `try` riêng: file trước được đóng trước khi mở file sau.

Bỏ khối `try` thì chương trình vẫn chạy đúng với vài file. Mỗi stream không đóng giữ lại một file descriptor (số hiệu hệ điều hành cấp cho một file đang mở), và không có gì bảo đảm garbage collector sẽ đóng hộ bạn kịp lúc. Hệ điều hành giới hạn số file một process được mở cùng lúc, và khi chạm giới hạn, mọi lần mở file mới đều ném `Too many open files`.

`IOException` là checked exception, nên bạn phải bắt hoặc khai báo `throws`. Stream của `Files.lines` đọc file dần dần bên trong các method như `forEach`, mà các method này và các interface hàm (`Consumer`, `Function`) không khai báo checked exception. Vì vậy lỗi đọc file xảy ra giữa chừng được bọc trong `UncheckedIOException`. Mục Mojibake bên dưới cho thấy exception đó.

<Callout kind="production">

Một job đọc log bằng `Files.readAllLines` chạy ổn nhiều tháng, tới ngày file log lên 3 GB thì JVM chết với `OutOfMemoryError`: method này nạp mọi dòng vào một `List` trước khi trả về. Với file không biết trước kích thước, đọc từng dòng bằng `Files.lines` hoặc `BufferedReader`, và luôn đặt chúng trong try-with-resources.

</Callout>

### Charset: ký tự thành byte

API của một đối tác giới hạn trường ghi chú tối đa 100 byte. Code kiểm `note.length() <= 100`, vậy mà một ghi chú tiếng Việt 60 ký tự vẫn bị từ chối.

Mỗi ký tự có một số hiệu trong bảng Unicode, gọi là **code point**: `ệ` là U+1EC7. **Charset** quy định code point đó được ghi thành những byte nào. Đoạn sau ghi chữ `Việt` bằng ba charset, in số byte và các byte dạng hex (hệ 16), rồi giải mã ngược lại:

```java
void main() {
    String word = "Việt";
    IO.println(word + ": length=" + word.length());
    HexFormat hex = HexFormat.ofDelimiter(" ");
    for (Charset cs : List.of(StandardCharsets.UTF_8, StandardCharsets.UTF_16BE, StandardCharsets.ISO_8859_1)) {
        byte[] bytes = word.getBytes(cs);
        IO.println("%-10s %d byte  %-23s -> %s".formatted(cs, bytes.length, hex.formatHex(bytes), new String(bytes, cs)));
    }
}
```

Kết quả:

```text
Việt: length=4
UTF-8      6 byte  56 69 e1 bb 87 74       -> Việt
UTF-16BE   8 byte  00 56 00 69 1e c7 00 74 -> Việt
ISO-8859-1 4 byte  56 69 3f 74             -> Vi?t
```

Cùng bốn ký tự, mỗi charset cho một dãy byte khác:

| Charset | `ệ` thành | Đặc điểm |
|---|---|---|
| UTF-8 | `e1 bb 87`, 3 byte | 1 byte cho ký tự ASCII, 2 tới 4 byte cho ký tự khác. Chuẩn của web, Linux, JSON |
| UTF-16 | `1e c7`, 2 byte | 2 hoặc 4 byte mỗi ký tự. `char` và `String.length()` của Java tính theo đơn vị 2 byte này |
| ISO-8859-1 | `3f`, tức dấu `?` | Chỉ có 256 ký tự Tây Âu, không có `ệ` |

Dòng ISO-8859-1 cho thấy một kiểu mất dữ liệu không quay lại được: charset không có `ệ`, nên `getBytes` thay nó bằng byte `3f` (dấu `?`) ngay lúc ghi. Giải mã lại chỉ ra `Vi?t`, vì byte của `ệ` chưa bao giờ được ghi.

`String.length()` đếm số `char`, tức số đơn vị 2 byte của UTF-16, không phải số byte khi ghi ra file và cũng không hẳn là số ký tự. Đoạn sau so ba cách đếm:

```java
void main() {
    for (String s : List.of("Viet", "Việt", "😀")) {
        IO.println(s + "  length=" + s.length() + "  codePoints=" + s.codePointCount(0, s.length())
                + "  utf8=" + s.getBytes(StandardCharsets.UTF_8).length);
    }
}
```

Kết quả:

```text
Viet  length=4  codePoints=4  utf8=4
Việt  length=4  codePoints=4  utf8=6
😀  length=2  codePoints=1  utf8=4
```

Emoji 😀 (U+1F600) nằm ngoài vùng 65.536 code point đầu tiên, nên UTF-16 cần hai `char` cho nó: `length()` là 2 dù chỉ có một ký tự. Khi giới hạn kích thước theo byte (cột database khai báo bằng byte, kích thước message, header HTTP), đo bằng `getBytes(StandardCharsets.UTF_8).length`. Khi giới hạn số ký tự người dùng nhập, đếm bằng `codePointCount`.

### Mojibake: ghi một charset, đọc bằng charset khác

Kế toán mở file đơn hàng bằng một phần mềm cũ và thấy `Nguyá»…n Thá»‹ Há»“ng Nhung`. File không hỏng; chỉ là nó được đọc sai.

**Mojibake** là chữ hỏng do giải mã byte bằng một charset khác với charset đã dùng khi ghi. Đoạn sau ghi file bằng UTF-8, rồi giải mã các byte đó bằng windows-1252, bảng mã Tây Âu mặc định của Windows:

```java
void main() throws IOException {
    Path file = Path.of("orders.csv");
    Files.writeString(file, "DH-0001,Nguyễn Thị Hồng Nhung,Hà Nội\nDH-0002,Trần Văn Đức,Đà Nẵng\n");
    byte[] bytes = Files.readAllBytes(file);
    IO.print(new String(bytes, Charset.forName("windows-1252")));
}
```

Kết quả:

```text
DH-0001,Nguyá»…n Thá»‹ Há»“ng Nhung,HÃ  Ná»™i
DH-0002,Tráº§n VÄƒn Ä�á»©c,Ä�Ã  Náºµng
```

Mỗi chữ có dấu là 2 hoặc 3 byte trong UTF-8, nhưng windows-1252 coi mỗi byte là một ký tự riêng:

```text
"ễ"  --ghi UTF-8-->  e1 bb 85  --đọc bằng windows-1252-->  "á" "»" "…"  =  "á»…"
```

Không byte nào bị mất, chỉ bị hiểu sai, nên phần lớn mojibake sửa ngược được: mã hoá chuỗi hỏng lại bằng chính charset đã đọc sai để lấy lại byte gốc, rồi giải mã đúng bằng UTF-8.

```java
void main() {
    Charset cp1252 = Charset.forName("windows-1252");
    for (String original : List.of("Nguyễn", "Đức")) {
        String broken = new String(original.getBytes(StandardCharsets.UTF_8), cp1252);
        String repaired = new String(broken.getBytes(cp1252), StandardCharsets.UTF_8);
        IO.println(broken + " -> " + repaired + "  khoi phuc dung? " + repaired.equals(original));
    }
}
```

<Predict question="Cả hai tên đều được khôi phục chứ? Để ý chữ Đ ở output của đoạn trước.">

```text
Nguyá»…n -> Nguyễn  khoi phuc dung? true
Ä�á»©c -> �?ức  khoi phuc dung? false
```

`Nguyễn` quay lại nguyên vẹn, còn `Đức` thì không. Chữ `Đ` trong UTF-8 là `c4 90`, và byte `90` không có nghĩa trong windows-1252. Lần giải mã sai đầu tiên thay nó bằng ký tự thay thế `�` (U+FFFD), nên byte `90` đã mất từ lúc đó, trước cả khi bạn thử sửa. Lúc sửa, windows-1252 không có `�` nên ghi nó thành `3f`, tức dấu `?` trong kết quả.

</Predict>

Vì vậy, khi mojibake đã lỡ lưu vào database:

1. Sửa trên một bản sao, không sửa thẳng dữ liệu gốc.
2. Đếm số dòng còn chứa `�` sau khi sửa.
3. Tìm lại dữ liệu gốc cho những dòng đó.

`new String(bytes, cs)` và `InputStreamReader` giải mã **dễ dãi** (lenient): gặp byte không hợp lệ thì thay bằng `�` rồi đi tiếp. Các method đọc chữ của `Files` thì giải mã **nghiêm ngặt** (strict): gặp byte không hợp lệ là ném exception. Đoạn sau đọc một file mà phần mềm bán hàng cũ xuất theo bảng mã windows-1258 (bảng mã tiếng Việt của Windows), bằng cả ba cách:

```java
void main() throws IOException {
    // "Nguyễn" theo windows-1258: chữ ê (ea) rồi dấu ngã đứng riêng (de)
    byte[] legacy = {'N', 'g', 'u', 'y', (byte) 0xea, (byte) 0xde, 'n'};
    Path file = Path.of("orders-pos.csv");
    Files.write(file, legacy);
    try {
        Files.readString(file);
    } catch (MalformedInputException e) {
        IO.println("readString -> " + e);
    }
    try (Stream<String> lines = Files.lines(file)) {
        lines.forEach(IO::println);
    } catch (UncheckedIOException e) {
        IO.println("lines      -> " + e);
    }
    IO.println("new String -> " + new String(legacy, StandardCharsets.UTF_8));
}
```

Kết quả:

```text
readString -> java.nio.charset.MalformedInputException: Input length = 3
lines      -> java.io.UncheckedIOException: java.nio.charset.MalformedInputException: Input length = 1
new String -> Nguy��n
```

Byte `ea de` không phải chuỗi UTF-8 hợp lệ. `Files.readString` ném `MalformedInputException` (một `IOException`); `Files.lines` gặp cùng loại lỗi nhưng bọc nó trong `UncheckedIOException`, vì lỗi xảy ra bên trong stream. `new String` không báo gì và trả về một chuỗi đã mất dữ liệu. Báo lỗi như hai cách đầu tốt hơn âm thầm sinh ra báo cáo sai: bạn biết ngay file không phải UTF-8 và đọc lại nó bằng đúng charset, `Charset.forName("windows-1258")`.

Gặp `MalformedInputException`, nhiều người đổi charset sang ISO-8859-1 cho hết lỗi. Lỗi biến mất thật, vì ISO-8859-1 gán một ký tự cho mọi giá trị byte từ `00` tới `ff`, nên không bao giờ có byte "không hợp lệ". Nhưng chương trình giờ chạy trên mojibake: mọi tên khách có dấu đều sai. Cách đúng là hỏi nguồn xuất file dùng bảng mã gì và đọc bằng đúng bảng mã đó.

Một trường hợp biên hay gặp với file CSV lưu từ Excel bằng tuỳ chọn "CSV UTF-8": đầu file có thêm ba byte `ef bb bf`, gọi là **BOM** (byte order mark). Java giải mã chúng thành ký tự U+FEFF và không tự bỏ đi:

```java
void main() throws IOException {
    byte[] bom = {(byte) 0xef, (byte) 0xbb, (byte) 0xbf};
    Path file = Path.of("excel.csv");
    Files.write(file, bom);
    Files.writeString(file, "code,customer\n", StandardOpenOption.APPEND);

    String header = Files.readAllLines(file).get(0);
    IO.println(header.length() + " ky tu, bat dau bang code? " + header.startsWith("code"));
    IO.println("bo BOM: " + header.replace("\uFEFF", "").startsWith("code"));
}
```

Kết quả:

```text
14 ky tu, bat dau bang code? false
bo BOM: true
```

Dòng tiêu đề trông như `code,customer` nhưng dài 14 ký tự thay vì 13, và so sánh với `"code"` thất bại. Kiểm tra và cắt ký tự U+FEFF ở đầu dòng đầu tiên trước khi parse.

### Charset mặc định, JEP 400 và stdout.encoding

Cùng một chương trình đọc file tiếng Việt đúng trên Mac nhưng hỏng trên Windows; một chương trình khác in log đúng trên laptop nhưng in `Nguy?n` trong container.

Khi bạn gọi `getBytes()`, `new String(bytes)` hay `new FileReader(file)` mà không truyền charset, Java dùng **charset mặc định**. Trước Java 18, charset mặc định lấy theo hệ điều hành: UTF-8 trên Mac và Linux, thường là windows-1252 trên Windows. **JEP 400** (Java 18) đổi charset mặc định thành UTF-8 trên mọi nền tảng. Từ đó, chuyện "đúng trên Mac, hỏng trên Windows" chỉ còn ở JDK cũ.

Còn hai chỗ vẫn phụ thuộc môi trường. Chỗ thứ nhất là `System.out` và `System.err`: chúng mã hoá chữ theo thuộc tính `stdout.encoding` (và `stderr.encoding`), lấy từ locale (thiết lập ngôn ngữ và bảng mã) của terminal. Chương trình sau in một chữ có dấu và hai thuộc tính đó. Nó được viết thành class có tên `EncodingInfo` để lệnh `java EncodingInfo.java` bên dưới khớp với tên file:

```java
import java.nio.charset.Charset;

public class EncodingInfo {
    public static void main(String[] args) {
        IO.println("Việt");
        IO.println("stdout.encoding=" + System.getProperty("stdout.encoding")
                + ", default charset=" + Charset.defaultCharset());
    }
}
```

Trên một terminal dùng UTF-8, như Terminal của macOS, kết quả sẽ giống thế này:

```text varies
Việt
stdout.encoding=UTF-8, default charset=UTF-8
```

Biến môi trường `LC_ALL=C` bảo chương trình rằng terminal chỉ hiểu ASCII, giống một container không đặt locale. Chạy lại chương trình với biến đó:


`stdout.encoding` thành US-ASCII, nên `ệ` thành `?` ở bước in ra màn hình. Chuỗi trong bộ nhớ vẫn đúng, và charset mặc định vẫn là UTF-8 nhờ JEP 400, nên nội dung file chương trình ghi ra không bị ảnh hưởng. Chỉ có chữ in ra màn hình hỏng.

Trên Linux, locale còn quyết định bảng mã của **tên** file (thuộc tính `sun.jnu.encoding` mà JEP 400 mô tả và không đổi), nên một container không đặt locale có thể hỏng cả tên file có dấu. Trong Dockerfile, sửa cả hai bằng `ENV LANG=C.UTF-8` để locale của container dùng UTF-8. Khi không đổi được locale, chạy `java -Dstdout.encoding=UTF-8`; [Javadoc của `System`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/System.html#getProperties()) chỉ bảo đảm hành vi khi đặt thuộc tính này thành UTF-8.

Chỗ thứ hai là file do hệ thống khác tạo ra, như file windows-1258 ở mục trước. Không thiết lập nào của Java đoán được bảng mã của một file; bạn phải biết nó từ nguồn xuất file. Bảng mã cũng phải có trong JDK đang chạy. Đoạn sau in module (đơn vị đóng gói của JDK, J3) chứa từng charset:

```java
void main() {
    for (String name : List.of("UTF-8", "windows-1252", "windows-1258")) {
        IO.println(name + " -> " + Charset.forName(name).getClass().getModule());
    }
}
```

Kết quả:

```text
UTF-8 -> module java.base
windows-1252 -> module java.base
windows-1258 -> module jdk.charsets
```

windows-1258 nằm trong module `jdk.charsets`, không nằm trong `java.base`. Một runtime rút gọn tạo bằng `jlink --add-modules java.base` (J3) không có module đó, và `Charset.forName("windows-1258")` ném `UnsupportedCharsetException` trên runtime ấy. Khi chương trình cần đọc file từ hệ thống Windows cũ, thêm `jdk.charsets` vào danh sách module lúc tạo runtime.

Quy tắc rút ra: **luôn truyền `StandardCharsets.UTF_8` tường minh** khi đọc ghi file và mạng (trừ các method của `Files`, vốn đã mặc định UTF-8). Code nói rõ ý định, và không đổi hành vi khi chạy trên JDK cũ hay máy khác.

### Chuẩn hoá Unicode: NFC và NFD

Báo cáo doanh thu theo khách có hai dòng `Nguyễn Thị Hồng Nhung` trông giống hệt nhau. Một dòng tính từ file của website, dòng kia từ file của phần mềm bán hàng cũ.

Một chữ có dấu trong Unicode ghi được theo nhiều cách. `ễ` có code point dựng sẵn U+1EC5, nhưng cũng ghi được bằng chữ `e` theo sau là dấu mũ và dấu ngã kết hợp (combining mark: ký tự dấu đứng sau và "gắn" vào chữ trước nó). Hai cách cho cùng hình dạng trên màn hình nhưng khác nhau từng `char`. Đoạn sau so ba cách ghi tên `Nguyễn`: gõ từ bàn phím, đọc từ file windows-1258, và tách hết dấu bằng `java.text.Normalizer`:

```java
void main() {
    String typed = "Nguyễn";
    byte[] legacy = {'N', 'g', 'u', 'y', (byte) 0xea, (byte) 0xde, 'n'};
    String fromPos = new String(legacy, Charset.forName("windows-1258"));
    String nfd = Normalizer.normalize(typed, Normalizer.Form.NFD);

    IO.println(typed + " " + fromPos + " " + nfd);
    IO.println("length: " + typed.length() + " " + fromPos.length() + " " + nfd.length());
    IO.println("equals: " + typed.equals(fromPos) + " " + typed.equals(nfd));
    IO.println("sau NFC: " + typed.equals(Normalizer.normalize(fromPos, Normalizer.Form.NFC)));
}
```

Kết quả:

```text
Nguyễn Nguyễn Nguyễn
length: 6 7 8
equals: false false
sau NFC: true
```

Ba chuỗi trông như nhau nhưng dài 6, 7 và 8 `char`, và `equals` coi chúng là khác nhau.

Unicode định nghĩa hai dạng chuẩn hoá hay gặp:

- **NFC** dùng chữ dựng sẵn: mỗi chữ có dấu là một code point. Bàn phím, web và hầu hết hệ thống tạo ra dạng này. `Nguyễn` dài 6.
- **NFD** tách mọi dấu khỏi chữ gốc, kể cả dấu mũ của `ê`: `ễ` thành `e`, dấu mũ, dấu ngã. `Nguyễn` dài 8.

windows-1258 có sẵn `ê`, `ô`, `ơ`, `ư` nhưng không có chữ mang dấu thanh, nên nó ghi `ễ` thành `ê` cộng dấu ngã kết hợp. Chuỗi đọc từ file đó dài 7, nằm giữa hai dạng chuẩn. `equals` và `TreeMap` so từng `char`, nên coi đây là hai khách khác nhau.

Cách sửa là chuẩn hoá về NFC mọi chuỗi đến từ bên ngoài trước khi dùng làm khoá hay so sánh: `Normalizer.normalize(name, Normalizer.Form.NFC)`. Tên file và dữ liệu nhập từ hệ thống khác cũng có thể ở dạng tách, nên khi so tên file bằng `equals`, chuẩn hoá cả hai vế.

### Mã hoá ký tự, Base64, băm và mã hoá bảo mật

Trang thanh toán đặt token `b3JkZXI9REgtMDAwMTthbW91bnQ9MzUwMDAw` vào URL, và đội phát triển gọi nó là token "đã mã hoá Base64". Một khách tò mò dán token vào một trang giải Base64, thấy `order=DH-0001;amount=350000`, sửa số tiền rồi mã hoá lại.

Tiếng Việt dùng chữ "mã hoá" cho nhiều việc khác hẳn nhau. Charset ở các mục trên là **mã hoá ký tự** (encoding): đổi chữ thành byte theo một bảng quy ước công khai. **Mã hoá bảo mật** (encryption) thì giữ bí mật: chỉ người có khoá mới đọc được. Bảng dưới đặt các việc hay bị nhầm cạnh nhau:

| Việc | Ví dụ | Cần khoá | Đảo ngược được | Dùng để |
|---|---|---|---|---|
| Mã hoá ký tự | UTF-8 | Không | Có, ai cũng làm được | Đổi chữ thành byte |
| Mã hoá nhị phân thành chữ | Base64, hex | Không | Có, ai cũng làm được | Đặt byte vào JSON, URL, header |
| Băm (hash) | SHA-256 | Không | Không | Dấu vân tay của dữ liệu, kiểm file có bị đổi |
| Mã xác thực (MAC) | HMAC-SHA256 | Một khoá bí mật dùng chung | Không | Chứng minh dữ liệu do bên có khoá tạo ra và không bị sửa |
| Chữ ký số | Ed25519 | Khoá riêng để ký, khoá công khai để kiểm | Không | Như MAC, nhưng ai có khoá công khai cũng kiểm được |
| Mã hoá bảo mật | AES-GCM | Một khoá bí mật | Có, chỉ khi có khoá | Giữ bí mật nội dung |

**JCA** (Java Cryptography Architecture) là bộ API mật mã có sẵn trong JDK, nằm ở `java.security` và `javax.crypto`. Mỗi việc trong bảng có một lớp riêng:

- `MessageDigest` để băm.
- `Mac` cho HMAC.
- `Signature` cho chữ ký số.
- `Cipher` để mã hoá và giải mã.

Bạn lấy đối tượng bằng `getInstance("tên thuật toán")`, và một **provider** (gói cài đặt thuật toán, như `SunJCE` có sẵn trong JDK) cung cấp phần chạy thật. Đoạn sau đưa cùng token qua Base64 và SHA-256:

```java
void main() throws Exception {
    String token = "order=DH-0001;amount=350000";
    String encoded = Base64.getEncoder().encodeToString(token.getBytes(StandardCharsets.UTF_8));
    IO.println("Base64:  " + encoded);
    IO.println("giai ra: " + new String(Base64.getDecoder().decode(encoded), StandardCharsets.UTF_8));

    MessageDigest sha256 = MessageDigest.getInstance("SHA-256");
    HexFormat hex = HexFormat.of();
    IO.println("SHA-256: " + hex.formatHex(sha256.digest(token.getBytes(StandardCharsets.UTF_8))));
    IO.println("SHA-256: " + hex.formatHex(sha256.digest("order=DH-0001;amount=350001".getBytes(StandardCharsets.UTF_8))));
}
```

Kết quả:

```text
Base64:  b3JkZXI9REgtMDAwMTthbW91bnQ9MzUwMDAw
giai ra: order=DH-0001;amount=350000
SHA-256: 5c0ef6623d3f56a3bf4bed962f319f8562de286151fb4fa61afe1db1699d9302
SHA-256: ae77a8162ed460a4a88a3880053f87c0226d13035d10d682efc8f661b1607a21
```

Base64 chỉ đổi byte thành chuỗi gồm 64 ký tự in được, đặt được vào JSON và header; ai cũng giải ngược được mà không cần gì. (Base64 chuẩn có dấu `+` và `/`; trong URL dùng biến thể ở mục SecureRandom.) SHA-256 luôn cho 32 byte (64 chữ số hex), bất kể đầu vào dài bao nhiêu. Đổi một chữ số trong số tiền làm thay đổi gần như toàn bộ kết quả, và không có cách nào tính ngược từ kết quả ra đầu vào. `digest` tự đặt lại trạng thái của `MessageDigest`, nên cùng một đối tượng băm tiếp được chuỗi thứ hai.

Băm cũng không ngăn được khách ở đầu mục. Thuật toán là công khai và không cần khoá, nên ai sửa token cũng tính lại được SHA-256 cho token mới. Hash chứng minh dữ liệu không đổi so với một giá trị bạn đã giữ an toàn từ trước, như checksum của file tải về. Muốn chứng minh dữ liệu do chính bạn tạo ra, bạn cần một bí mật: HMAC hoặc chữ ký số ở mục sau.

Mật khẩu cũng không lưu bằng SHA-256. SHA-256 được thiết kế để chạy nhanh, nên kẻ lấy được bảng chứa mật khẩu đã băm thử được hàng tỷ mật khẩu đoán mò mỗi giây bằng GPU. Mật khẩu cần thuật toán cố tình chậm như bcrypt hay Argon2, học ở SB6 (roadmap Spring Boot).

### HMAC và chữ ký số: chứng minh dữ liệu không bị sửa

Đối tác thanh toán gọi webhook `POST /payments/callback` của bạn với body `{"order":"DH-0001","status":"PAID","amount":350000}` mỗi khi khách trả tiền xong. Ai biết URL đó cũng gửi được đúng JSON như vậy, và đơn hàng sẽ được giao dù chưa ai trả tiền.

**HMAC** (hash-based message authentication code) băm dữ liệu cùng một khoá bí mật mà chỉ bạn và đối tác biết. Đối tác gửi kết quả trong một header, ví dụ `X-Signature`; bạn tính lại HMAC trên body nhận được bằng cùng khoá và so hai giá trị. Kẻ không có khoá không tạo được HMAC đúng cho một body đã sửa:

```java
byte[] hmac(byte[] key, String body) throws GeneralSecurityException {
    Mac mac = Mac.getInstance("HmacSHA256");
    mac.init(new SecretKeySpec(key, "HmacSHA256"));
    return mac.doFinal(body.getBytes(StandardCharsets.UTF_8));
}

void main() throws Exception {
    byte[] secret = "khoa-chung-voi-doi-tac-thanh-toan".getBytes(StandardCharsets.UTF_8);
    String body = "{\"order\":\"DH-0001\",\"status\":\"PAID\",\"amount\":350000}";
    byte[] signature = hmac(secret, body); // đối tác gửi kèm trong header X-Signature
    IO.println("X-Signature: " + HexFormat.of().formatHex(signature));

    String forged = body.replace("350000", "35000");
    IO.println("body goc hop le?    " + MessageDigest.isEqual(signature, hmac(secret, body)));
    IO.println("body bi sua hop le? " + MessageDigest.isEqual(signature, hmac(secret, forged)));
}
```

Kết quả:

```text
X-Signature: 66797028524d989c12a07d35aeb2904669aa82cfe2f3978047e337064e13ccd8
body goc hop le?    true
body bi sua hop le? false
```

Khoá viết thẳng trong code chỉ để ví dụ chạy được; trên production nó là một secret nạp từ môi trường (bài SB6 của roadmap Spring Boot). Hai chi tiết trong đoạn code là có chủ đích:

- So hai HMAC bằng `MessageDigest.isEqual`, không bằng `Arrays.equals`. `Arrays.equals` dừng ở byte khác nhau đầu tiên, nên thời gian so cho kẻ tấn công biết đoán đúng được bao nhiêu byte đầu. Javadoc của `isEqual` cam kết thời gian so không phụ thuộc nội dung hai mảng.
- HMAC tính trên đúng byte của body nhận được. Nếu bạn parse JSON rồi ghi lại thành chuỗi (J9.3), thứ tự trường hay khoảng trắng có thể khác bản gốc, và HMAC không còn khớp dù không ai sửa gì.

HMAC có một giới hạn: bên kiểm và bên tạo dùng chung một khoá, nên ai kiểm được cũng giả mạo được. Khi nhiều bên cần kiểm mà chỉ một bên được tạo, như hoá đơn điện tử do cửa hàng phát hành hay JWT do một server đăng nhập phát cho nhiều service, bạn dùng **chữ ký số** (digital signature). Chữ ký số dùng một **cặp khoá**: khoá riêng (private key) giữ bí mật để ký, khoá công khai (public key) phát cho mọi người để kiểm. Đoạn sau ký một hoá đơn bằng Ed25519 (thuật toán chữ ký có trong JDK từ Java 15), rồi kiểm chữ ký trước và sau khi sửa một chữ số:

```java
import java.security.Signature;

void main() throws Exception {
    KeyPair keys = KeyPairGenerator.getInstance("Ed25519").generateKeyPair();
    byte[] invoice = "{\"invoice\":\"HD-2026-0001\",\"total\":1550000}".getBytes(StandardCharsets.UTF_8);

    Signature signer = Signature.getInstance("Ed25519");
    signer.initSign(keys.getPrivate());
    signer.update(invoice);
    byte[] signature = signer.sign();
    IO.println("chu ky: " + signature.length + " byte");

    Signature verifier = Signature.getInstance("Ed25519");
    verifier.initVerify(keys.getPublic());
    verifier.update(invoice);
    IO.println("hop le? " + verifier.verify(signature));

    invoice[invoice.length - 2] = '1'; // tổng tiền thành 1550001
    verifier.initVerify(keys.getPublic());
    verifier.update(invoice);
    IO.println("sau khi sua, hop le? " + verifier.verify(signature));
}
```

Kết quả:

```text
chu ky: 64 byte
hop le? true
sau khi sua, hop le? false
```

Dòng `import java.security.Signature;` là bắt buộc. Một file chỉ có `void main()` tự import mọi package của module `java.base`, nên các ví dụ khác không cần `import` cho `KeyPair` hay `HexFormat`. Nhưng `java.base` có hai lớp tên `Signature`, một trong `java.security` và một trong `java.lang.classfile`; thiếu dòng import thì `javac` báo `reference to Signature is ambiguous`. Bên kiểm chữ ký dùng `keys.getPublic()`; nó không ký được hoá đơn mới vì không có khoá riêng. Mỗi lần chạy, `KeyPairGenerator` tạo một cặp khoá mới nên chữ ký cũng khác, nhưng ba dòng kết quả thì luôn như trên. Bảng dưới so hai cách:

| | HMAC | Chữ ký số |
|---|---|---|
| Khoá | Một khoá bí mật, hai bên cùng giữ | Khoá riêng để ký, khoá công khai để kiểm |
| Ai kiểm được | Chỉ bên có khoá, và bên đó cũng tạo được | Bất kỳ ai có khoá công khai |
| Tốc độ | Rất nhanh | Chậm hơn nhiều lần |
| Gặp ở đâu | Webhook thanh toán, JWT `HS256`, cursor phân trang | Hoá đơn điện tử, JWT `RS256`, `EdDSA`, chứng chỉ TLS |

### SecureRandom: số ngẫu nhiên không đoán được

Link đặt lại mật khẩu chứa một token sinh bằng `new Random().nextInt()`. Kẻ tấn công tự yêu cầu vài link cho tài khoản của mình, rồi đoán được token của người khác.

`java.util.Random` là một công thức: từ một số khởi đầu gọi là **seed**, nó tính ra dãy số tiếp theo. Cùng seed thì cùng dãy:

```java
void main() {
    Random a = new Random(20261023);
    Random b = new Random(20261023);
    IO.println("a: " + a.nextInt(1_000_000) + " " + a.nextInt(1_000_000) + " " + a.nextInt(1_000_000));
    IO.println("b: " + b.nextInt(1_000_000) + " " + b.nextInt(1_000_000) + " " + b.nextInt(1_000_000));
}
```

Kết quả:

```text
a: 738337 441580 561625
b: 738337 441580 561625
```

`new Random()` không seed chỉ chọn seed khác nhau mỗi lần, công thức vẫn vậy. [Javadoc của `Random`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Random.html) công bố công thức đó, với trạng thái bên trong chỉ 48 bit, và ghi rõ `Random` không an toàn về mật mã. Với công thức công khai và trạng thái nhỏ như vậy, từ vài giá trị liên tiếp người khác có thể tính lại trạng thái và đoán các giá trị sau.

**`SecureRandom`** lấy độ ngẫu nhiên từ nguồn của hệ điều hành (trên Linux và macOS, provider mặc định đọc `/dev/urandom`), nên giá trị sau không suy ra được từ giá trị trước. Mọi thứ cần bí mật đều sinh bằng nó: token, khoá, IV. Đoạn sau sinh một token 32 byte và đổi sang Base64 dạng an toàn cho URL:

```java
void main() {
    SecureRandom random = new SecureRandom();
    byte[] bytes = new byte[32];
    random.nextBytes(bytes);
    String token = Base64.getUrlEncoder().withoutPadding().encodeToString(bytes);
    IO.println(token + "  (" + token.length() + " ky tu)");
}
```

Kết quả sẽ giống thế này, nhưng token trên máy bạn sẽ khác ở mỗi lần chạy:

```text varies
q3vU0bJ8yQyKZf1c0m3s9W2PqT7NnE4hX_aLr6dGk1Y  (43 ky tu)
```

`getUrlEncoder` dùng `-` và `_` thay cho `+` và `/`, hai ký tự có nghĩa riêng trong URL; `withoutPadding` bỏ các dấu `=` ở cuối. Javadoc của `SecureRandom` cam kết đối tượng dùng chung an toàn cho nhiều thread, nên tạo một lần và dùng lại cho cả ứng dụng.

### Mã hoá với AES-GCM

Database lưu số tài khoản ngân hàng của khách để hoàn tiền. Một bản backup bị lộ ra ngoài; nếu cột đó là chữ thường, mọi số tài khoản lộ theo.

**AES** là thuật toán **mã hoá đối xứng** (symmetric encryption): cùng một khoá dùng để mã hoá và giải mã. AES chỉ mã hoá từng khối 16 byte; **chế độ** (mode) quyết định cách nối các khối thành một thông điệp dài. **GCM** là chế độ nên dùng: nó vừa giữ bí mật, vừa phát hiện bản mã bị sửa. Một lần mã hoá AES-GCM có bốn thành phần:

| Thành phần | Vai trò |
|---|---|
| Khoá (`SecretKey`, 256 bit) | Bí mật duy nhất; ai có khoá thì giải mã được |
| IV (initialization vector, còn gọi là nonce), 12 byte | Ngẫu nhiên và khác nhau ở mỗi lần mã hoá; không bí mật, lưu cạnh bản mã |
| Tag xác thực, 16 byte | GCM gắn vào cuối bản mã; lúc giải mã, sai tag thì từ chối |
| `Cipher` với `"AES/GCM/NoPadding"` | Tên đầy đủ gồm thuật toán, chế độ và padding (cách độn khối cuối; GCM không cần) |

Đoạn sau mã hoá cùng một số tài khoản hai lần, mỗi lần với một IV mới, và ghép IV vào trước bản mã để lưu chung một cột:

```java
final SecureRandom random = new SecureRandom();

byte[] encrypt(SecretKey key, String text) throws GeneralSecurityException {
    byte[] iv = new byte[12];
    random.nextBytes(iv);
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
    byte[] sealed = cipher.doFinal(text.getBytes(StandardCharsets.UTF_8));
    return ByteBuffer.allocate(iv.length + sealed.length).put(iv).put(sealed).array();
}

String decrypt(SecretKey key, byte[] data) throws GeneralSecurityException {
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.DECRYPT_MODE, key, new GCMParameterSpec(128, data, 0, 12));
    return new String(cipher.doFinal(data, 12, data.length - 12), StandardCharsets.UTF_8);
}

void main() throws Exception {
    KeyGenerator generator = KeyGenerator.getInstance("AES");
    generator.init(256);
    SecretKey key = generator.generateKey();

    byte[] first = encrypt(key, "0451000123456");
    byte[] second = encrypt(key, "0451000123456");
    IO.println("13 byte ban ro -> " + first.length + " byte luu xuong database");
    IO.println("hai lan ma hoa giong nhau? " + Arrays.equals(first, second));
    IO.println("giai ma: " + decrypt(key, first));
}
```

<Predict question="Mã hoá cùng một số tài khoản bằng cùng một khoá hai lần: hai bản mã có giống nhau không?">

```text
13 byte ban ro -> 41 byte luu xuong database
hai lan ma hoa giong nhau? false
giai ma: 0451000123456
```

Không. Mỗi lần mã hoá dùng một IV ngẫu nhiên mới, nên cùng một bản rõ cho ra hai bản mã khác hẳn nhau. 41 byte gồm 12 byte IV, 13 byte bản mã và 16 byte tag.

</Predict>

Bản mã khác nhau ở mỗi lần là tính chất bạn cần: nhìn vào cột đã mã hoá, không ai biết hai khách có cùng số tài khoản hay không. `GCMParameterSpec(128, iv)` đặt độ dài tag là 128 bit. `GCMParameterSpec(128, data, 0, 12)` đọc lại IV từ 12 byte đầu của dữ liệu đã lưu.

Tag là thứ giúp GCM phát hiện bản mã bị sửa. Đoạn sau đổi một bit của bản mã bằng toán tử `^` (XOR, "hoặc loại trừ" từng bit: bit nào gặp 1 thì bị đảo, gặp 0 thì giữ nguyên; vì vậy `a ^ k ^ k` luôn bằng `a`), rồi giải mã:

```java
void main() throws Exception {
    SecretKey key = KeyGenerator.getInstance("AES").generateKey();
    byte[] iv = new byte[12];
    new SecureRandom().nextBytes(iv);
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
    byte[] sealed = cipher.doFinal("amount=350000".getBytes(StandardCharsets.UTF_8));

    sealed[0] ^= 1; // một bit bị đổi trên đường truyền hoặc trong database
    cipher.init(Cipher.DECRYPT_MODE, key, new GCMParameterSpec(128, iv));
    try {
        cipher.doFinal(sealed);
    } catch (AEADBadTagException e) {
        IO.println(e);
    }
}
```

Kết quả:

```text
javax.crypto.AEADBadTagException: Tag mismatch
```

`doFinal` từ chối trả bất kỳ byte nào khi tag không khớp. Bạn không bao giờ nhận về một số tài khoản "gần đúng" đã bị sửa.

Tên `"AES"` trần cũng là một tên hợp lệ cho `Cipher.getInstance`, nhưng nó không chọn GCM. Đoạn sau mã hoá hai khối 16 byte giống hệt nhau bằng `Cipher.getInstance("AES")`:

```java
void main() throws Exception {
    SecretKey key = KeyGenerator.getInstance("AES").generateKey();
    Cipher cipher = Cipher.getInstance("AES");
    cipher.init(Cipher.ENCRYPT_MODE, key);
    // hai khối 16 byte giống hệt nhau, như hai dòng cùng trạng thái trong một file
    byte[] sealed = cipher.doFinal("status=PAID;;;;;status=PAID;;;;;".getBytes(StandardCharsets.UTF_8));
    IO.println("IV: " + cipher.getIV());
    IO.println("khoi 1 == khoi 2? " + Arrays.equals(sealed, 0, 16, sealed, 16, 32));
}
```

Kết quả:

```text
IV: null
khoi 1 == khoi 2? true
```

Không có IV, và hai khối rõ giống nhau cho hai khối mã giống nhau. Provider `SunJCE` hiểu `"AES"` là `"AES/ECB/PKCS5Padding"`. Chế độ **ECB** mã hoá từng khối 16 byte riêng rẽ với cùng một khoá, nên mọi khuôn mẫu lặp lại của dữ liệu hiện nguyên trên bản mã, và không có tag để phát hiện sửa đổi. Luôn ghi tên đầy đủ `"AES/GCM/NoPadding"`.

IV ngẫu nhiên không phải chi tiết trang trí. [Javadoc của `Cipher`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/javax/crypto/Cipher.html) ghi rằng GCM đòi IV không lặp lại với cùng một khoá. Nếu bạn gọi lại `init` với đúng khoá và IV cũ trên cùng một đối tượng `Cipher` để mã hoá, nó ném `InvalidAlgorithmParameterException: Cannot reuse iv for GCM encryption`. Nhưng nó chỉ chặn được trên cùng một đối tượng. Code tạo `Cipher` mới cho mỗi lần mã hoá với một IV cố định thì không ai chặn. Đoạn sau mã hoá hai số tài khoản với cùng khoá và cùng IV, rồi đóng vai kẻ tấn công không có khoá:

```java
byte[] seal(SecretKey key, byte[] iv, String text) throws GeneralSecurityException {
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
    return cipher.doFinal(text.getBytes(StandardCharsets.UTF_8));
}

void main() throws Exception {
    SecretKey key = KeyGenerator.getInstance("AES").generateKey();
    byte[] fixedIv = new byte[12]; // IV cố định: đây là lỗi đang được minh hoạ
    byte[] a = seal(key, fixedIv, "0451000123456");
    byte[] b = seal(key, fixedIv, "0987000654321");

    // kẻ tấn công biết số tài khoản thứ nhất và có cả hai bản mã, nhưng không có khoá
    byte[] known = "0451000123456".getBytes(StandardCharsets.UTF_8);
    byte[] recovered = new byte[known.length];
    for (int i = 0; i < known.length; i++) {
        recovered[i] = (byte) (a[i] ^ b[i] ^ known[i]);
    }
    IO.println("tai khoan thu hai: " + new String(recovered, StandardCharsets.UTF_8));
}
```

Thử tự trả lời trước khi xem kết quả: không có khoá, làm sao phép XOR ba mảng byte lấy lại được số tài khoản thứ hai? Kết quả:

```text
tai khoan thu hai: 0987000654321
```

Bên trong, GCM sinh một dãy byte giả ngẫu nhiên (keystream) từ khoá và IV, rồi XOR dãy đó với bản rõ: bản mã = bản rõ `^` keystream. Cùng khoá và cùng IV cho cùng keystream, nên XOR hai bản mã với nhau thì keystream triệt tiêu (`k ^ k` bằng 0) và còn lại XOR của hai bản rõ. Biết một bản rõ, kẻ tấn công lấy ra bản kia. Theo Javadoc của `Cipher`, IV lặp lại còn cho phép giả mạo bản mã hợp lệ, tức tag cũng mất tác dụng.

<Callout kind="production">

Một service mã hoá số điện thoại khách bằng AES-GCM, với IV là mảng 12 byte 0 chép từ một đoạn code mẫu. Bản backup database bị lộ. Kẻ có bản backup đăng ký một tài khoản bằng số điện thoại của chính mình, tìm bản mã của nó trong backup, và giải được số điện thoại của mọi khách khác bằng đúng phép XOR ở trên, dù khoá chưa bao giờ rời khỏi server. Sinh IV bằng `SecureRandom` cho mỗi lần mã hoá và lưu nó cạnh bản mã.

</Callout>

IV ngẫu nhiên cũng có giới hạn. IV dài 96 bit được chọn ngẫu nhiên, nên sau đủ nhiều lần mã hoá với cùng một khoá, hai IV có thể tình cờ trùng nhau và đưa bạn về đúng lỗi ở trên. [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final) (mục 8.3) vì vậy giới hạn số lần mã hoá dùng IV ngẫu nhiên ở 2^32, khoảng 4,3 tỷ lần, cho mỗi khoá. Một cột số tài khoản hiếm khi chạm mức đó, nhưng một service mã hoá từng message trong một luồng dữ liệu lớn thì có thể; khi đó phải thay khoá mới định kỳ (**xoay khoá**, key rotation) trước khi chạm giới hạn.

Tag còn một giới hạn khác: nó chứng minh bản mã không bị sửa, nhưng không chứng minh bản mã nằm đúng chỗ. Người ghi được vào database mà không có khoá vẫn chép được nguyên bản mã ở dòng của khách A sang dòng của khách B. Bản mã đó còn nguyên vẹn nên tag khớp, và dòng của B giải mã ra số tài khoản của A; tiền hoàn cho B sẽ chuyển vào tài khoản của A. GCM có cách chặn: **AAD** (additional authenticated data, dữ liệu xác thực kèm theo) là dữ liệu không được mã hoá nhưng được tính vào tag. Bạn nạp AAD bằng `cipher.updateAAD(...)` trước `doFinal`, ở cả lúc mã hoá lẫn lúc giải mã. Đoạn sau dùng mã khách hàng làm AAD, rồi thử giải mã bản mã của `KH-001` như thể nó nằm ở dòng `KH-002`:

```java
byte[] seal(SecretKey key, byte[] iv, String customerId, String text) throws GeneralSecurityException {
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.ENCRYPT_MODE, key, new GCMParameterSpec(128, iv));
    cipher.updateAAD(customerId.getBytes(StandardCharsets.UTF_8));
    return cipher.doFinal(text.getBytes(StandardCharsets.UTF_8));
}

String open(SecretKey key, byte[] iv, String customerId, byte[] sealed) throws GeneralSecurityException {
    Cipher cipher = Cipher.getInstance("AES/GCM/NoPadding");
    cipher.init(Cipher.DECRYPT_MODE, key, new GCMParameterSpec(128, iv));
    cipher.updateAAD(customerId.getBytes(StandardCharsets.UTF_8));
    return new String(cipher.doFinal(sealed), StandardCharsets.UTF_8);
}

void main() throws Exception {
    SecretKey key = KeyGenerator.getInstance("AES").generateKey();
    byte[] iv = new byte[12];
    new SecureRandom().nextBytes(iv);
    byte[] ofA = seal(key, iv, "KH-001", "0451000123456");

    IO.println("dong KH-001: " + open(key, iv, "KH-001", ofA));
    try {
        open(key, iv, "KH-002", ofA); // bản mã của KH-001 bị chép sang dòng KH-002
    } catch (AEADBadTagException e) {
        IO.println("dong KH-002: " + e);
    }
}
```

Kết quả:

```text
dong KH-001: 0451000123456
dong KH-002: javax.crypto.AEADBadTagException: Tag mismatch
```

Ở đúng dòng của nó, bản mã giải ra số tài khoản. Chép sang dòng `KH-002`, AAD lúc giải mã là `KH-002`, khác AAD lúc mã hoá, nên tag không khớp và `doFinal` từ chối. Mã khách hàng không cần giữ bí mật, nên lưu ở cột thường như mọi khi; điều kiện là lúc giải mã bạn lấy AAD từ chính dòng đang đọc.

### KeyStore: cất khoá trong file có mật khẩu

Khoá mà `KeyGenerator` vừa tạo chỉ nằm trong bộ nhớ. Service khởi động lại thì khoá mất, và dữ liệu mã hoá hôm qua không giải mã được nữa. Viết khoá thẳng vào code thì nó nằm trong Git, ai đọc được repo cũng có khoá.

**KeyStore** là file chứa khoá và chứng chỉ, mỗi mục có một tên gọi là **alias**, cả file được bảo vệ bằng mật khẩu. **Chứng chỉ** (certificate) là một tài liệu chứa khoá công khai và tên chủ sở hữu, có chữ ký của bên phát hành; đó là cách khoá công khai được phát cho người khác. Định dạng keystore chuẩn là **PKCS12** (đuôi `.p12`), mặc định của JDK từ Java 9. Một keystore có ba loại mục:

| Loại mục | Chứa gì | Dùng khi |
|---|---|---|
| `PrivateKeyEntry` | Khoá riêng kèm chứng chỉ chứa khoá công khai | Ký dữ liệu, chạy HTTPS |
| `SecretKeyEntry` | Khoá đối xứng, như khoá AES | Mã hoá dữ liệu, tính HMAC |
| `TrustedCertificateEntry` | Chứng chỉ của bên khác mà bạn tin | Kiểm chữ ký hay kết nối HTTPS tới bên đó |

Đoạn sau cất khoá AES vào file `app-keys.p12`, đọc lại, rồi thử mở bằng mật khẩu sai:

```java
void main() throws Exception {
    char[] password = "doi-mat-khau-nay".toCharArray();
    SecretKey key = KeyGenerator.getInstance("AES").generateKey();

    KeyStore store = KeyStore.getInstance("PKCS12");
    store.load(null, null); // keystore rỗng
    store.setEntry("orders-aes", new KeyStore.SecretKeyEntry(key), new KeyStore.PasswordProtection(password));
    try (OutputStream out = Files.newOutputStream(Path.of("app-keys.p12"))) {
        store.store(out, password);
    }

    KeyStore loaded = KeyStore.getInstance(Path.of("app-keys.p12").toFile(), password);
    Key again = loaded.getKey("orders-aes", password);
    IO.println(loaded.getType() + " " + Collections.list(loaded.aliases()) + ", cung khoa? " + again.equals(key));
    try {
        KeyStore.getInstance(Path.of("app-keys.p12").toFile(), "sai-mat-khau".toCharArray());
    } catch (IOException e) {
        IO.println(e.getMessage());
    }
}
```

Kết quả:

```text
PKCS12 [orders-aes], cung khoa? true
Integrity check failed: java.security.UnrecoverableKeyException: Failed PKCS12 integrity checking
```

Khoá đọc lại từ file giống hệt khoá ban đầu, nên dữ liệu mã hoá trước khi khởi động lại vẫn giải mã được. Mật khẩu sai thì `KeyStore.getInstance` ném `IOException` ngay lúc mở file. API keystore nhận mật khẩu dạng `char[]` thay cho `String`, để code có thể ghi đè mảng sau khi dùng; `String` thì bất biến và nằm trong bộ nhớ tới khi bị dọn.

JDK có sẵn công cụ dòng lệnh `keytool` để xem và tạo keystore. Lệnh sau liệt kê các mục trong file vừa tạo:

<Terminal where="mac">

```bash
keytool -list -keystore app-keys.p12 -storepass doi-mat-khau-nay
```

</Terminal>

Kết quả sẽ giống thế này, với ngày là ngày bạn tạo file. Bỏ `-storepass` khỏi lệnh thì `keytool` hỏi mật khẩu, và mật khẩu không bị lưu vào lịch sử của shell:

```text varies
Keystore type: PKCS12
Keystore provider: SUN

Your keystore contains 1 entry

orders-aes, Oct 23, 2026, SecretKeyEntry,
```

Cặp khoá để ký thường được tạo bằng `keytool` chứ không bằng code, vì `keytool` tạo luôn chứng chỉ chứa khoá công khai để phát cho bên kiểm. Lệnh sau tạo một cặp khoá Ed25519 cho việc ký hoá đơn:

<Terminal where="mac">

```bash
keytool -genkeypair -alias invoice-signer -keyalg Ed25519 -dname "CN=masteva-shop" -validity 365 -keystore signer.p12 -storepass doi-mat-khau-nay
```

</Terminal>

Kết quả:

```text
Generating Ed25519 key pair and self-signed certificate (Ed25519) with a validity of 365 days
	for: CN=masteva-shop
```

Trong code, `store.getKey("invoice-signer", password)` trả khoá riêng để truyền cho `Signature.initSign`, còn `store.getCertificate("invoice-signer").getPublicKey()` trả khoá công khai cho bên kiểm. Spring Boot cũng đọc keystore PKCS12 để bật HTTPS, qua thuộc tính `server.ssl.key-store`.

Keystore chuyển bài toán từ "giấu khoá" sang "giấu mật khẩu của keystore". Mật khẩu đó không nằm trong code hay trong Git; nó được nạp từ biến môi trường hoặc một kho secret lúc service khởi động (bài SB6 của roadmap Spring Boot).

<Callout kind="ai">

Nhờ AI viết code đọc ghi file, giải thích một stack trace về charset, hay viết đoạn mã hoá và kiểm chữ ký. AI hay sai ở những chỗ sau:

- Viết `new FileReader(file)` hay `getBytes()` không truyền charset, dùng `Files.readAllLines` cho file lớn, quên đóng stream của `Files.lines` và `Files.walk`.
- Gặp mojibake thì đề xuất đổi sang ISO-8859-1 cho "hết lỗi".
- Gọi `Cipher.getInstance("AES")` (tức ECB), dùng IV cố định hoặc sinh bằng `Random`, so HMAC bằng `Arrays.equals`.
- Gọi Base64 là "mã hoá", lưu mật khẩu bằng SHA-256.

Kiểm tra lại: tìm mọi chỗ tạo `Reader`, `Writer`, `getBytes`, `new String(bytes)` và xem có charset tường minh không; chạy thử với file chứa chữ có dấu. Với code mật mã, kiểm tên transformation đầy đủ, nguồn của IV và khoá, và mã hoá cùng một chuỗi hai lần để chắc hai bản mã khác nhau.

</Callout>
