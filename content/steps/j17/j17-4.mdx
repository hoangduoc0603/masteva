<Goal>

Biết khi nào nên đóng gói một ứng dụng Java thành **native image** thay vì chạy trên JVM, và trả giá gì cho lựa chọn đó. Bạn tự build, tự đo, rồi tự làm hỏng ứng dụng theo đúng những cách native image hay hỏng. Học xong bài này, bạn giải thích được:

- Vì sao cùng một service khởi động mất 1 giây trên JVM nhưng chưa tới 0,1 giây khi là native, và vì sao với cờ build mặc định điều đó không làm nó xử lý nhanh hơn khi đã chạy lâu (cờ `-O3` thì khác).
- Vì sao code chạy tốt trên JVM lại ném `ClassNotFoundException` trong native image, dù class nằm ngay trong project.
- Vì sao bật một property lúc chạy không tạo ra bean như trên JVM.

</Goal>

<Knowledge>

### Native image là gì

Trên JVM, file JAR chứa bytecode. Lúc chạy, HotSpot nạp class, kiểm tra, thông dịch rồi mới dần biên dịch phần nóng bằng JIT (J12.2 sẽ đi sâu). **Native image** làm hết việc đó **trước khi chạy** (AOT, ahead-of-time): công cụ `native-image` của GraalVM phân tích toàn bộ ứng dụng lúc build và sinh ra một file thực thi của hệ điều hành, chạy được mà không cần cài JRE.

```text
 mvn -Pnative native:compile
   |
   |  1. Spring AOT (goal process-aot): refresh ApplicationContext ở chế độ AOT
   |     lúc build (chỉ tạo bean definition, chưa tạo bean), sinh code Java
   |     đăng ký bean thay cho reflection, và file hint (reflection, resource, proxy)
   v
 target/classes + target/spring-aot + các JAR dependency
   |
   |  2. native-image: phân tích từ main(), giữ class, method, field "tới được",
   |     bỏ toàn bộ phần còn lại
   |  3. chụp các object tạo lúc build vào image heap
   |  4. biên dịch AOT toàn bộ bằng Graal compiler, liên kết bằng trình biên dịch C
   v
 target/catalog-native    file thực thi (Mach-O trên macOS, ELF trên Linux)
                          = mã máy + image heap + Substrate VM
```

**Substrate VM** là runtime thu gọn đi kèm file thực thi: GC, thread, xử lý exception. Nó không có JIT và không có trình thông dịch bytecode. Vì thế native image khởi động gần như tức thì: không phải nạp class, không có giai đoạn thông dịch, bean Spring đã được sinh sẵn thành code. Cái giá là mọi thứ phải được biết **lúc build**.

<Check id="j17.4.native-pipeline">Kể được bốn bước từ `mvn -Pnative native:compile` tới file thực thi, và giải thích được vì sao native image khởi động nhanh.</Check>

### Giả định closed world

Để biết cái gì "tới được", `native-image` giả định **closed world** (thế giới đóng): mọi code sẽ chạy đều đã có mặt lúc build, và đường đi tới nó thấy được qua phân tích tĩnh. Những gì Java vẫn quyết định lúc chạy thì phân tích tĩnh không thấy:

| Tính năng | Trên JVM | Trong native image | Cách xử lý |
|---|---|---|---|
| Reflection với tên động (`Class.forName(tênTừCấuHình)`) | Tìm class lúc chạy | Class không đăng ký thì như không tồn tại | Đăng ký bằng `RuntimeHints` hoặc `@RegisterReflection` |
| Resource (`getResource("x.json")`) | Đọc từ classpath | Chỉ file đã khai báo mới được nhúng | `hints.resources()` |
| JDK dynamic proxy | Tạo lúc chạy | Bộ interface phải khai báo trước | `hints.proxies()` |
| Nạp class mới (plugin JAR, sinh bytecode lúc chạy) | Được | Không làm được | Không có cách; mọi plugin phải có lúc build |
| Bean theo `@ConditionalOnProperty`, `@Profile` | Quyết định lúc khởi động | Chốt lúc build | Đặt property lúc build, hoặc đừng dùng điều kiện cho thứ đổi theo môi trường |

Bạn không phải tự khai báo phần lớn những thứ này. **Spring AOT** chạy lúc build, sinh code tạo bean thay cho reflection và ghi hint cho controller, Jackson, `@ConfigurationProperties`. Với thư viện ngoài, plugin Maven của GraalVM tải **GraalVM Reachability Metadata Repository**, kho metadata do cộng đồng duy trì cho logback, Tomcat, Jackson. Phần còn lại là code của chính bạn dùng reflection theo cách không ai đoán trước được, và đó là chỗ bạn phải viết hint.

<Check id="j17.4.closed-world">Giải thích được closed world, kể được ba thứ native image không tự thấy, và cách khai báo từng thứ.</Check>

### Đánh đổi: khi nào chọn native

JDK 25 còn một cách khác rút ngắn khởi động, J12.2 sẽ đi sâu: **AOT cache**. Chạy ứng dụng một lần để JVM ghi class đã nạp, đã liên kết và profile method vào một file; các lần sau đọc lại file đó. Ba lựa chọn đặt cạnh nhau (con số đo trong lab của bài này, trên Mac M1 Pro):

| | JVM thường | JVM + Spring AOT + AOT cache | Native image |
|---|---|---|---|
| Thời gian build | Vài giây (`package`) | Thêm vài giây giải nén và chạy huấn luyện | 1 tới 1,5 phút, đỉnh 2,8 tới 3,5 GB RAM trên máy 16 GB |
| Artifact | JAR 19 MB, cần JRE | JAR và cache 50 MB, cần đúng JDK đã tạo cache | File 65 MB cho đúng một hệ điều hành và kiến trúc CPU |
| Khởi động | Khoảng 1 giây | Khoảng 0,25 giây | 0,03 tới 0,07 giây |
| RSS sau 500 request | 150 tới 230 MB | 150 tới 185 MB | 64 MB |
| Mã chạy lâu, nặng CPU | Nhanh nhất nhờ JIT | Như JVM thường | Với cờ mặc định, chậm hơn JVM sau warm-up khoảng 20% trong lab; `-O3` cho native vượt lên ở bước 8 |
| GC | G1 mặc định, nhiều lựa chọn | Như JVM thường | Serial GC; G1 chỉ có ở Oracle GraalVM trên Linux |
| Chẩn đoán | JFR, jcmd, heap dump đầy đủ | Như JVM thường | Phải bật lúc build bằng `--enable-monitoring`, một phần còn experimental |
| Đổi hành vi lúc chạy | Tự do | Tập bean bị khoá lúc build | Tập bean và class bị khoá lúc build |

Chọn native khi khởi động và bộ nhớ quyết định chi phí: CLI, function serverless, service scale từ 0, sidecar chạy hàng trăm bản. Giữ JVM khi service chạy lâu với tải đều: throughput đỉnh, công cụ chẩn đoán và vòng build nhanh đáng giá hơn vài trăm mili giây khởi động. AOT cache nằm giữa: không đổi gì trong code, lấy lại phần lớn thời gian khởi động, nhưng bộ nhớ chỉ giảm ít (RSS 150 tới 185 MB so với 150 tới 230 MB trong bảng trên), xa mức của native image.

<Callout kind="production">

Một đội chuyển service tính giá sang native image để giảm bộ nhớ trên Kubernetes. Thời gian CI tăng từ 2 lên 9 phút. Hai tuần sau, một nhánh code hiếm khi chạy, dùng thư viện đọc file cấu hình bằng reflection, ném `ClassNotFoundException` trên production: test chỉ chạy trên JVM nên không bắt được. Bài học của họ: nếu ship native, chạy test trong native (`mvn -PnativeTest test`), và đo lại throughput dưới tải thật trước khi quyết định. Service đó cuối cùng quay về JVM với AOT cache; còn các job batch chạy 30 giây mỗi lần thì giữ native.

</Callout>

### 1. Tải GraalVM vào thư mục lab

Bài không cài GraalVM vào hệ thống: chỉ tải và giải nén vào `~/masteva-j17/tools`, xoá thư mục là gỡ xong. Bản dùng ở đây là **GraalVM Community 25.4.4.1.1**, bản mới nhất ngày kiểm chứng, giấy phép GPLv2 kèm Classpath Exception. Nếu mở tab mới, chạy lại hai dòng `export` và khối hàm ở bước 3.

### 2. Tạo ứng dụng

Dependency `native` của start.spring.io thêm `native-maven-plugin` vào `pom.xml`; profile `native` có sẵn trong `spring-boot-starter-parent`. Ngoài `/api/products` quen thuộc từ SB11.1, ứng dụng có hai chỗ cố ý "động": `/api/prices` nạp chính sách giảm giá theo **tên class đọc từ cấu hình**, và `AuditLog` chỉ được tạo khi `app.audit.enabled=true`.

<Terminal where="mac" title="Tạo project và code">

```bash
cd ~/masteva-j17
curl -s https://start.spring.io/starter.tgz \
  -d type=maven-project -d language=java -d bootVersion=4.1.1 -d javaVersion=25 \
  -d groupId=dev.masteva -d artifactId=catalog-native -d baseDir=catalog-native \
  -d packageName=dev.masteva.catalog -d dependencies=web,native | tar -xzf -
cd catalog-native
PKG=src/main/java/dev/masteva/catalog
cat >> src/main/resources/application.properties <<'EOF'
server.port=20330
app.discount-policy=dev.masteva.catalog.HolidayDiscount
EOF
cat > $PKG/ProductController.java <<'EOF'
package dev.masteva.catalog;

import java.util.List;
import java.util.function.LongUnaryOperator;

import org.springframework.beans.factory.annotation.Value;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
public class ProductController {

    record Product(String sku, String name, long price) {
    }

    private static final List<Product> PRODUCTS = List.of(
            new Product("SKU-1", "Bàn phím cơ", 1_250_000),
            new Product("SKU-2", "Chuột không dây", 450_000));

    private final String policyClass;

    ProductController(@Value("${app.discount-policy}") String policyClass) {
        this.policyClass = policyClass;
    }

    @GetMapping("/api/products")
    List<Product> products() {
        return PRODUCTS;
    }

    // Tên class đến từ cấu hình: kiểu "plugin" hay gặp, và là reflection thật sự.
    @GetMapping("/api/prices")
    List<Product> prices() throws ReflectiveOperationException {
        var policy = (LongUnaryOperator) Class.forName(policyClass).getDeclaredConstructor().newInstance();
        return PRODUCTS.stream()
                .map(p -> new Product(p.sku(), p.name(), policy.applyAsLong(p.price())))
                .toList();
    }
}
EOF
cat > $PKG/HolidayDiscount.java <<'EOF'
package dev.masteva.catalog;

import java.util.function.LongUnaryOperator;

public class HolidayDiscount implements LongUnaryOperator {
    @Override
    public long applyAsLong(long price) {
        return price * 90 / 100;
    }
}
EOF
cat > $PKG/AuditLog.java <<'EOF'
package dev.masteva.catalog;

import org.springframework.boot.autoconfigure.condition.ConditionalOnProperty;
import org.springframework.stereotype.Component;

@Component
@ConditionalOnProperty(name = "app.audit.enabled", havingValue = "true")
class AuditLog {
    AuditLog() {
        System.out.println(">>> AuditLog: đang bật");
    }
}
EOF
```

</Terminal>

### 3. Build JAR và đo trên JVM

Ba hàm shell dưới đây dùng cho mọi phép đo: `app_start` chạy ứng dụng ở nền và chờ tới khi `/api/products` trả lời; `app_stop` dừng nó; `measure` in dòng `Started` của Spring Boot, gửi 500 request rồi đọc **RSS** (resident set size, bộ nhớ thật tiến trình đang chiếm) bằng `ps`. Nếu mở tab mới, chạy lại hai dòng `export` và khối hàm ở bước 3.

<Terminal where="mac">

```bash
app_start() {
  "$@" > app.log 2>&1 & APP=$!
  for i in {1..300}; do curl -sf localhost:20330/api/products >/dev/null && return 0; sleep 0.05; done
  echo "app không lên được, xem app.log"; return 1
}
app_stop() { kill $APP; wait $APP 2>/dev/null; return 0; }
measure() {
  app_start "$@" || return 1
  grep -o 'Started .* in .*)' app.log
  for i in {1..500}; do curl -s localhost:20330/api/products >/dev/null; done
  echo "RSS sau 500 request: $(( $(ps -o rss= -p $APP) / 1024 )) MB"
  app_stop
}
time mvn -q -DskipTests package
ls -lh target/*.jar | awk '{print $5, $9}'
measure java -jar target/catalog-native-0.0.1-SNAPSHOT.jar
```

</Terminal>

<Expected>

```text
mvn -q -DskipTests package  5.89s user 0.29s system 306% cpu 2.012 total
19M target/catalog-native-0.0.1-SNAPSHOT.jar
Started CatalogNativeApplication in 0.847 seconds (process running for 1.073)
RSS sau 500 request: 212 MB

</Expected>

Dòng `time` có dạng của zsh (mặc định trên macOS); bash in `real 0m2.012s`. Lần build đầu lâu hơn vì Maven tải dependency. Maven chạy trên JDK 25 in thêm vài dòng `WARNING:` về `restricted method` và `sun.misc.Unsafe`, còn shell tương tác có thể in `[1] 12345` hay `terminated` khi chạy và dừng tiến trình nền; các khối kết quả đã lược chúng. Con số trên máy bạn sẽ khác. RSS của JVM dao động mạnh giữa các lần chạy (150 tới 230 MB trên máy kiểm chứng) vì heap tối đa mặc định là 1/4 RAM máy (SB11.3), JVM không vội thu gom.

Trước khi `native-image` chạy, Maven chạy goal `process-aot` (log Spring Boot khởi động **lúc build**) và tải kho reachability metadata (các dòng `[graalvm reachability metadata repository for ...]` trong log). Log có 8 bước; bước 2 là phân tích closed world: 18.762 kiểu tới được, 1.403 kiểu được đăng ký cho reflection, phần lớn nhờ Spring AOT và kho metadata. Bước 6 biên dịch AOT mọi method tới được. Tổng cộng khoảng 1 phút 15 giây, 8 phút CPU (`user`); `package` chỉ mất vài giây. Trên máy 16 GB, builder được dùng khoảng 70% RAM nên đỉnh lên 2,8 tới 3,5 GB; với ít RAM hơn nó vẫn chạy nhưng GC nhiều hơn, chậm hơn. ### 8. JIT và AOT trên một tác vụ nặng CPU

Không cần Spring để dùng `native-image`. `PriceStats` chạy 10 lô, mỗi lô gom doanh thu của 1 triệu đơn hàng theo SKU, rồi in thời gian từng lô. Biến `sink` cộng dồn doanh thu của mọi lô và được in ra cuối cùng, để trình biên dịch không thể coi vòng lặp là vô dụng mà bỏ đi; hai bản phải in cùng một tổng kiểm tra:

<Terminal where="mac">

```bash

import java.util.HashMap;
import java.util.Random;

public class PriceStats {
    public static void main(String[] args) {
        Random rnd = new Random(42);
        StringBuilder out = new StringBuilder("ms mỗi lô:");

        for (int round = 1; round <= 10; round++) {

        System.out.println(out);
        System.out.println("tổng kiểm tra: " + sink);
    }
}
EOF

Vậy khoảng cách ở trên một phần do cờ mặc định, và mọi so sánh JIT với AOT phải ghi rõ cờ build. Oracle GraalVM còn có PGO (profile-guided optimization, tối ưu theo profile thu từ lần chạy thật); bản Community thì không.

### 9. Còn container image thì sao?

Lệnh `file` ở bước 4 đã trả lời: `Mach-O 64-bit executable arm64` chỉ chạy trên macOS chip Apple. Container Linux cần file ELF build **trên Linux**, đúng kiến trúc CPU của server; GraalVM không biên dịch chéo sang hệ điều hành khác. Có hai đường: `mvn -Pnative spring-boot:build-image` để Buildpacks build native image trong một container Linux, hoặc Dockerfile multi-stage với stage build dùng image `ghcr.io/graalvm/native-image-community:25i4-25.0.4.1.1` (ghim đúng bản đã dùng ở bước 1; thẻ `:25` vẫn trỏ về 25.0.2 cũ) và stage cuối là một base nhỏ. Lưu ý đường Buildpacks không dùng GraalVM bạn vừa tải: theo tài liệu Paketo, buildpack Java Native Image mặc định dùng Liberica Native Image Kit của BellSoft. Bài không chạy bước này: build native trong container cần Docker VM có vài GB RAM rảnh (đỉnh ở bước 4 là 2,8 tới 3,5 GB; ít hơn thì vẫn chạy nhưng chậm hơn), và chạy lâu hơn nhiều trên Mac. Trong CI, hãy build trên runner Linux cùng kiến trúc với cụm.

<Callout kind="pitfall">

- `native-image is not installed in your JAVA_HOME`: chưa đặt `GRAALVM_HOME` trong tab Terminal hiện tại. Chạy lại hai dòng `export` ở bước 1.

<Reveal title="Thư viện ngoài thiếu metadata thì tìm hint bằng cách nào?">

Chạy ứng dụng trên JVM với **tracing agent** của GraalVM: `java -agentlib:native-image-agent=config-output-dir=src/main/resources/META-INF/native-image -jar app.jar`. Agent ghi lại mọi lời gọi reflection, resource, proxy thật sự xảy ra rồi xuất ra `reachability-metadata.json`. Giới hạn của nó nằm ngay trong cách hoạt động: chỉ những đường code đã chạy mới được ghi. Nhánh lỗi, nhánh hiếm gặp như bước 6 sẽ thiếu nếu bạn không chạy tới. Vì vậy agent thường được chạy cùng bộ test, và metadata sinh ra phải được review như code, trước khi đóng góp ngược lên kho reachability metadata.

</Reveal>

<Reveal title="Làm sao biết hint của mình đúng mà không phải build native mỗi lần?">

Spring có `RuntimeHintsPredicates` để kiểm tra hint bằng unit test thường trên JVM: tạo `RuntimeHints`, gọi `new CatalogRuntimeHints().registerHints(hints, getClass().getClassLoader())`, rồi assert `RuntimeHintsPredicates.reflection().onType(HolidayDiscount.class)` khớp. Test chạy trong mili giây và bắt được việc ai đó xoá hay đổi tên class. Nó không thay được việc chạy test trong native (`mvn -PnativeTest test`), vì không biết code nào khác cần hint; nhưng nó giữ cho các hint đã biết không âm thầm hỏng.

</Reveal>

<Reveal title="Native image trong container giới hạn 256 MB thì heap tính thế nào?">

Với Serial GC, nếu không đặt gì, heap tối đa của native image là 80% bộ nhớ vật lý mà nó thấy (khác 25% của JVM ở SB11.3). Trong container 256 MB, như vậy chỉ còn khoảng 50 MB cho mọi thứ khác (stack thread, metaspace của image, bộ đệm mạng), nên hãy đặt `-Xmx`. File thực thi nhận tham số heap lúc chạy như JVM: `./catalog-native -Xmx128m`. Image heap đã có sẵn trong file, nên ứng dụng cần ít heap hơn JVM cho cùng việc. Nhưng Serial GC dừng toàn bộ ứng dụng mỗi lần thu gom, chỉ dùng một thread; với heap lớn và nhiều request đồng thời, pause dài hơn G1. Đó là một lý do Oracle GraalVM có G1 cho native image trên Linux.

</Reveal>

<Callout kind="ai">

Nhờ AI giải thích một lỗi build của `native-image`, hoặc viết nháp `RuntimeHintsRegistrar` cho một thư viện.
