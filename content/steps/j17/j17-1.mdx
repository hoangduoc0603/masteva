<Goal>

Hiểu bên trong file JAR mà Spring Boot tạo ra, tách nó thành các layer và đóng gói thành container image bằng một Dockerfile đủ tốt cho production: multi-stage, base JRE, user không phải root, cache tốt. Học xong bài này, bạn giải thích được:

- Vì sao `java -jar app.jar` chạy được, còn `java -cp app.jar <MainClass>` báo `ClassNotFoundException` với chính class đó.
- Vì sao sửa một dòng code mà CI vẫn đẩy lại 20 MB lên registry, và layered JAR giảm con số đó xuống vài chục KB như thế nào.
- Vì sao image nên chạy bằng user thường, và `java` phải là PID 1.

</Goal>

<Knowledge>

### Executable fat JAR

JAR thường chỉ chứa class của chính bạn; dependency phải nằm trên classpath lúc chạy. Spring Boot Maven plugin tạo **fat JAR** (còn gọi là uber JAR): một file chứa cả code của bạn lẫn mọi dependency, chạy được bằng `java -jar`. Bên trong nó có cấu trúc riêng:

```text
catalog-0.0.1-SNAPSHOT.jar
├── META-INF/MANIFEST.MF          Main-Class: ...JarLauncher, Start-Class: ...CatalogApplication
├── org/springframework/boot/loader/   launcher: đọc được JAR lồng trong JAR
└── BOOT-INF/
    ├── classes/                  class và resource của bạn
    ├── lib/                      42 JAR dependency, để nguyên dạng JAR
    ├── classpath.idx             thứ tự classpath
    └── layers.idx                file nào thuộc layer nào
```

Classloader của JDK không đọc được một JAR nằm bên trong JAR khác, và chỉ tìm class ở gốc file. Vì vậy Spring Boot đặt một **launcher** nhỏ ở gốc:

```text
java -jar app.jar
   |  JVM đọc MANIFEST.MF, gọi Main-Class
   v
JarLauncher (org/springframework/boot/loader/launch)
   |  đọc classpath.idx, mở từng JAR trong BOOT-INF/lib bằng NestedJarFile
   |  tạo classloader gồm BOOT-INF/classes + BOOT-INF/lib/*.jar
   v
Start-Class: dev.masteva.catalog.CatalogApplication.main()
```

| Mục trong JAR | Vai trò | Thay đổi khi nào |
|---|---|---|
| `BOOT-INF/lib/` | Dependency: Spring, Tomcat, Jackson | Khi nâng phiên bản dependency |
| `org/springframework/boot/loader/` | Launcher | Khi nâng Spring Boot |
| `BOOT-INF/classes/` | Code và cấu hình của bạn | Mỗi commit |

<Check id="j17.1.fat-jar-anatomy">Giải thích được vai trò của `Main-Class`, `Start-Class`, `BOOT-INF/classes`, `BOOT-INF/lib` và vì sao fat JAR cần launcher riêng.</Check>

### Layered JAR

Container image là chồng các **layer** (lớp file chỉ đọc). Docker và registry nhận diện layer bằng hash nội dung: layer nào không đổi thì không build lại, không đẩy lại, node không tải lại. Nếu Dockerfile chỉ `COPY app.jar`, cả 21 MB nằm trong một layer, và mỗi commit đổi hash của cả layer đó.

**Layered JAR** ghi sẵn trong `BOOT-INF/layers.idx` cách chia file thành bốn layer, xếp từ ít đổi tới hay đổi:

| Layer | Nội dung | Kích thước trong lab |
|---|---|---|
| `dependencies` | JAR dependency có phiên bản cố định | 21 MB |
| `spring-boot-loader` | Launcher | 0, vì lab giải nén không kèm launcher |
| `snapshot-dependencies` | Dependency `-SNAPSHOT`, đổi thường xuyên hơn | 0 |
| `application` | Code và resource của bạn | 8 KB |

Công cụ **jarmode tools** chạy ngay từ JAR: `java -Djarmode=tools -jar app.jar list-layers` liệt kê layer, `extract --layers` giải nén mỗi layer ra một thư mục. Không có `--launcher`, `extract` tạo một JAR nhỏ cùng tên với JAR gốc (trong Dockerfile là `application.jar`) cùng thư mục `lib/`, manifest dùng `Class-Path` trỏ vào `lib/`. JVM tự nạp classpath đó, không cần launcher, nên khởi động nhanh hơn một chút so với đọc JAR lồng nhau. Cách giải nén này cũng là điều kiện cho CDS và AOT cache trong tài liệu "Efficient Deployments".

<Check id="j17.1.layers">Kể được bốn layer mặc định, thứ tự của chúng và vì sao thứ tự đó quyết định hiệu quả của cache.</Check>

### Dockerfile multi-stage

```text
stage builder (eclipse-temurin:25-jre)        stage cuối (eclipse-temurin:25-jre)
  COPY target/*.jar application.jar             useradd app
  java -Djarmode=tools ... extract    ------>   COPY dependencies/            21.9 MB, hầu như không đổi
                                                COPY spring-boot-loader/
                                                COPY snapshot-dependencies/
                                                COPY application/             16 KB, đổi mỗi commit
                                                USER app
                                                ENTRYPOINT ["java","-jar","application.jar"]
```

- **Multi-stage:** stage `builder` chỉ để giải nén; image cuối không chứa file JAR gốc hay thư mục tạm.
- **Base JRE, không phải JDK:** image chạy không cần `javac`. Eclipse Temurin có cả hai biến thể; bản JRE nhỏ hơn và ít công cụ cho kẻ tấn công dùng lại.
- **User thường:** mặc định container chạy bằng `root`. Nếu ứng dụng bị khai thác lỗ hổng thực thi mã, kẻ tấn công có quyền root trong container. `USER app` giới hạn điều đó.
- **ENTRYPOINT dạng exec** (mảng JSON): `java` là PID 1 và nhận `SIGTERM` trực tiếp khi `docker stop`. Dạng shell (`ENTRYPOINT java -jar ...`) chạy qua `/bin/sh -c`: tuỳ shell, `sh` có thể giữ PID 1 và không chuyển `SIGTERM` (lỗi "dừng mất 10 giây, exit 137" ở bài D1.1), và mọi tham số sau tên image bị bỏ qua.
- **`.dockerignore`:** chỉ gửi `target/*.jar` cho Docker, không gửi `src`, `.git` hay `target/classes`.

<Callout kind="production">

Một service deploy 30 lần mỗi ngày, chạy 12 pod. Với `COPY app.jar` một khối, mỗi lần deploy registry nhận 21 MB và mỗi node kéo lại 21 MB, kể cả khi commit chỉ sửa một câu log. Chuyển sang layered, phần thay đổi giảm còn khoảng 16 KB; layer dependency chỉ đổi khi ai đó nâng phiên bản thư viện. Ngoài băng thông, thời gian rollout cũng ngắn lại vì pod mới khởi động ngay khi layer nhỏ tải xong.

</Callout>

<Check id="j17.1.dockerfile-rules">Giải thích được bốn quyết định trong Dockerfile: multi-stage, base JRE, `USER` không phải root, `ENTRYPOINT` dạng exec.</Check>

</Knowledge>

### 5. Dockerfile multi-stage

<Terminal where="mac">

```bash
cat > Dockerfile <<'EOF'
FROM eclipse-temurin:25-jre AS builder
WORKDIR /builder
COPY target/*.jar application.jar
RUN java -Djarmode=tools -jar application.jar extract --layers --destination extracted

FROM eclipse-temurin:25-jre
RUN groupadd --system app && useradd --system --gid app --no-create-home app
WORKDIR /application
COPY --from=builder /builder/extracted/dependencies/ ./
COPY --from=builder /builder/extracted/spring-boot-loader/ ./
COPY --from=builder /builder/extracted/snapshot-dependencies/ ./
COPY --from=builder /builder/extracted/application/ ./
USER app
EXPOSE 20170
ENTRYPOINT ["java", "-jar", "application.jar"]
EOF
printf '*\n!target/*.jar\n' > .dockerignore
docker pull eclipse-temurin:25-jre
docker build -t masteva-j17/catalog:dockerfile .
docker image ls masteva-j17/catalog
docker history --format 'table {{.Size}}\t{{.CreatedBy}}' masteva-j17/catalog:dockerfile | head -9
```

</Terminal>

### Khi gặp lỗi

<Callout kind="pitfall">

- `Cannot connect to the Docker daemon`: Docker Desktop chưa chạy. Mở nó và chờ biểu tượng chuyển sang trạng thái running.
- `ERROR: failed to build: failed to solve: lstat /target: no such file or directory` ở `COPY target/*.jar`: không có file nào khớp, do chưa chạy `mvn package` hoặc `.dockerignore` loại mất file JAR. BuildKit chỉ gửi các file khớp `target/*.jar`, nên khi không có JAR thì thư mục `target` cũng không có trong build context. Kiểm tra `ls target/*.jar`.
- `target` có hơn một JAR, thường do đổi `version` trong `pom.xml` mà không `mvn clean`: BuildKit **không báo lỗi**. Nó chép lần lượt mọi JAR khớp vào cùng file `application.jar`, file đứng sau cùng theo thứ tự tên thắng, nên image có thể chứa JAR cũ (`catalog-0.0.9` đứng sau `catalog-0.0.10`). Chạy `mvn -q clean package -DskipTests` để `target` chỉ còn một JAR.
- `UnsupportedClassVersionError ... class file version 69.0`: base image là Java 24 trở xuống (thường gặp là 17 hoặc 21) trong khi code build bằng JDK 25 (J1.1). Dùng cùng phiên bản Java cho build và runtime.
- `Bind for 0.0.0.0:20170 failed: port is already allocated`: còn container hoặc tiến trình `java -jar` cũ giữ cổng. Xem bằng `docker ps` và `lsof -i :20170`.

</Callout>

<DeepDive>

<Reveal title="Sao không chạy luôn mvn package trong Dockerfile?">

Được, bằng một stage dùng image Maven. Ưu điểm: máy build chỉ cần Docker, kết quả không phụ thuộc JDK trên máy. Nhược điểm: mỗi lần build Docker phải tải lại dependency Maven, trừ khi bạn dùng cache mount của BuildKit (`RUN --mount=type=cache,target=/root/.m2 mvn package`), và test chạy bên trong `docker build` khó đọc báo cáo hơn. Phần lớn pipeline CI chạy `mvn verify` ở một bước riêng, giữ lại JAR làm artifact, rồi Dockerfile chỉ đóng gói JAR đó như bài này. Cách đó cũng đảm bảo JAR đã qua test chính là JAR trong image.

</Reveal>

<Reveal title="Có nên dùng image alpine để nhỏ hơn?">

Image alpine dùng thư viện C `musl` thay cho `glibc`. Temurin có phát hành bản alpine riêng cho Java 25, nhưng thư viện native của bên thứ ba (driver, nén, crypto) đôi khi chỉ được build và kiểm thử với `glibc`, và lỗi chỉ lộ ra lúc chạy. Phần nặng nhất của image là JRE (khoảng 200 MB chưa nén), không phải hệ điều hành. Muốn nhỏ hơn đáng kể, hãy dùng `jlink` tạo JRE chỉ gồm các module ứng dụng cần, hoặc base distroless; đo lại kích thước và chạy test tích hợp trên chính image đó trước khi đổi.

</Reveal>

<Reveal title="Tag 25-jre tự trỏ tới bản vá mới. Đó là ưu hay nhược điểm?">

Ưu điểm: mỗi lần build lại, bạn nhận bản vá bảo mật của JRE và hệ điều hành. Nhược điểm: hai lần build cùng một commit có thể cho hai image khác nhau, và một bản vá có thể đổi hành vi. Nhiều đội ghim base image theo digest (`FROM eclipse-temurin:25-jre@sha256:...`) để build tái lập, rồi dùng công cụ tự mở pull request khi digest mới xuất hiện. Như vậy việc nâng base image có review và có test, thay vì xảy ra ngầm.

</Reveal>

<Reveal title="Ngoài layer, làm sao để container Java khởi động nhanh hơn nữa?">

JAR đã giải nén là điều kiện để dùng CDS (Class Data Sharing) và AOT cache của JDK 25: bạn chạy ứng dụng một lần để "huấn luyện", JVM ghi lại class đã nạp và đã liên kết vào một file cache, và các lần khởi động sau đọc file đó thay vì làm lại. Tài liệu "Efficient Deployments" của Spring Boot có lệnh cụ thể. Đánh đổi là thêm một bước build, và file cache chỉ dùng được với đúng JVM và đúng classpath đã tạo ra nó. J12 đo thời gian khởi động và warm-up kỹ hơn.

</Reveal>

<Callout kind="ai">

Nhờ AI viết nháp Dockerfile hay giải thích một dòng lỗi của `docker build`. AI hay đưa cú pháp cũ: `java -Djarmode=layertools -jar app.jar extract` (Spring Boot 4 báo `Unsupported jarmode 'layertools'`; cú pháp đúng là `-Djarmode=tools` với `extract --layers`), class `org.springframework.boot.loader.JarLauncher` (từ Spring Boot 3.2 nằm ở package `launch`), base `openjdk:...` (không còn được cập nhật). AI cũng hay quên `USER`. Kiểm tra lại bằng `java -Djarmode=tools -jar app.jar help`, `docker history` và `docker exec ... id`.
