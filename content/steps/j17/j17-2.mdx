<Goal>

Tạo image cho ứng dụng catalog bằng hai công cụ không cần Dockerfile: Jib và Cloud Native Buildpacks. Đo và so sánh trung thực ba cách ở kích thước, thời gian build, khả năng tái lập và mức kiểm soát. Học xong bài này, bạn giải thích được:

- Vì sao `docker image ls` báo image Jib được tạo từ năm 1970, và đó là tính năng chứ không phải lỗi.
- Vì sao image build trên Mac chip M có thể chạy chậm bất thường, hoặc chết với `exec format error` trên server.
- Vì sao image Buildpacks không khởi động nổi trong container 512 MB, trong khi image Dockerfile thì có.

</Goal>

<Knowledge>

### Jib: build image từ Maven, không cần Dockerfile

**Jib** là plugin Maven và Gradle của Google. Nó đọc project Maven, biết đâu là dependency, resource, class, rồi tự xếp chúng thành layer trên một base image. Jib không chạy lệnh nào bên trong container, nên không cần Dockerfile và không cần Docker daemon khi đẩy thẳng lên registry.

```text
mvn compile jib:...
   |  đọc pom.xml: dependency, resources, target/classes, main class
   v
layer: dependencies | snapshot dependencies | resources | classes | jvm arg files
   |  ghép lên base image (tải từ registry, cache ở máy)
   +--> jib:build         đẩy thẳng lên registry, không cần Docker
   +--> jib:dockerBuild   nạp vào Docker daemon ở máy
   +--> jib:buildTar      ghi ra file .tar
```

- Jib không dùng fat JAR. Nó chép class và JAR dependency vào `/app` rồi chạy `java -cp @/app/jib-classpath-file <MainClass>`.
- Mọi file trong image có thời điểm cố định và thứ tự cố định; thời điểm tạo image mặc định là epoch (1/1/1970). Cùng mã nguồn và cùng base image cho ra đúng cùng một image ID: đó là **build tái lập** (reproducible build).
- Jib không có `RUN`. Cần cài gói hệ điều hành thì bạn phải chuẩn bị một base image riêng.
- Mặc định Jib build cho `linux/amd64`. Trên Mac chip M, image đó chạy qua giả lập Rosetta, chậm hơn nhiều. Khai báo `platforms` gồm cả `amd64` và `arm64`: `jib:build` đẩy lên registry một image đa nền tảng, còn `jib:dockerBuild` chọn đúng kiến trúc của Docker ở máy.

### Cloud Native Buildpacks: image từ mã nguồn, theo quy ước

**Buildpacks** (chuẩn của CNCF, bản cài đặt phổ biến là Paketo) biến ứng dụng thành image mà không cần bạn mô tả từng bước. Spring Boot tích hợp sẵn qua `spring-boot:build-image`.

```text
spring-boot:build-image
   |  gửi fat JAR cho Docker, chạy container builder (paketobuildpacks/builder-noble-java-tiny)
   v
lifecycle bên trong builder:
   DETECT   6 trong 26 buildpack nhận việc: ca-certificates, bellsoft-liberica, syft,
            executable-jar, dist-zip, spring-boot
   BUILD    tải Liberica JRE theo Java version trong MANIFEST.MF, chia layer theo layers.idx,
            thêm memory calculator, SBOM, Spring Cloud Bindings
   EXPORT   ghép lên run image ubuntu-noble-run-tiny (không có shell),
            chạy bằng user không phải root (uid do builder đặt)
   v
masteva-j17/catalog:buildpacks
```

Buildpacks quyết định thay bạn nhiều thứ: JRE nào, user nào, tham số bộ nhớ nào. Quan trọng nhất với vận hành là **memory calculator**: lúc container khởi động, nó đọc giới hạn bộ nhớ rồi tính `-Xmx` sao cho heap cộng các vùng cố định (metaspace, code cache 240 MB, mỗi thread 1 MB stack nhân 250 thread) vừa đúng giới hạn. Nếu các vùng cố định đã vượt giới hạn, nó từ chối khởi động. Mặc định headroom là 0%: phần bộ nhớ native của GC, malloc không được tính, nên container vẫn có thể bị OOMKilled; đặt `BPL_JVM_HEAD_ROOM` (ví dụ 10) khi sát giới hạn.

### So sánh ba cách

Số đo trên máy kiểm chứng (Mac M, Docker Desktop), ứng dụng catalog của chặng này:

| | Dockerfile (SB11.1) | Jib | Buildpacks |
|---|---|---|---|
| Cần viết | Dockerfile, `.dockerignore` | Khối plugin trong `pom.xml` | Không gì |
| Cần Docker daemon | Có | Không, trừ `dockerBuild` | Có |
| Base | Temurin 25 JRE trên Ubuntu | Temurin 25 JRE trên Ubuntu | Liberica 25 JRE trên Ubuntu tiny |
| Tổng layer chưa nén | 407 MB | 407 MB | 354 MB |
| Build lần đầu | `mvn package` cộng khoảng 2 giây | 16 giây | 41 giây, gồm tải builder 338 MB nén |
| Build lại | Vài giây | Vài giây tới 15 giây | 14 giây |
| Cùng mã nguồn cho cùng image ID | Không | Có | Có |
| User | `app` (bạn tự viết) | `1000` (bạn tự khai báo) | Không phải root, uid do builder đặt |
| Shell trong image | Có | Có | Không |
| Tự đặt tham số JVM theo container | Không | Không | Có, memory calculator |

Không có cách nào thắng tuyệt đối. Dockerfile cho toàn quyền kiểm soát và ai cũng đọc được. Jib nhanh, tái lập, hợp với CI không có Docker. Buildpacks hợp với tổ chức muốn một quy chuẩn image chung và vá JRE, hệ điều hành đồng loạt.

<Callout kind="production">

Một đội chuyển từ Dockerfile sang `spring-boot:build-image` vì "không phải bảo trì Dockerfile". Manifest Kubernetes giữ nguyên `limits.memory: 512Mi`. Sau deploy, mọi pod `CrashLoopBackOff`, log chỉ có dòng `fixed memory regions require 591391K which is greater than 512M`. Memory calculator giả định 250 thread và code cache 240 MB, đã hết chỗ trước khi tính tới heap. Sửa bằng cách tăng limit, hoặc đặt `BPL_JVM_THREAD_COUNT` sát với số thread thật của service, đồng thời giới hạn số thread đó thật sự, ví dụ `server.tomcat.threads.max`; Tomcat mặc định tới 200 thread. Đổi công cụ đóng gói là đổi cả cách JVM được cấu hình lúc chạy.

</Callout>

### 1. Thêm plugin Jib

Mở `pom.xml`, dán khối sau vào trong `<plugins>`, ngay sau thẻ `</plugin>` của `spring-boot-maven-plugin`:

```xml
<plugin>
    <groupId>com.google.cloud.tools</groupId>
    <artifactId>jib-maven-plugin</artifactId>
    <version>3.5.2</version>
    <configuration>
        <from>
            <image>eclipse-temurin:25-jre</image>
            <platforms>
                <platform><architecture>amd64</architecture><os>linux</os></platform>
                <platform><architecture>arm64</architecture><os>linux</os></platform>
            </platforms>
        </from>
        <to>
            <image>masteva-j17/catalog:jib</image>
        </to>
        <container>
            <ports><port>20170</port></ports>
            <user>1000</user>
        </container>
    </configuration>
</plugin>
```

`eclipse-temurin:25-jre` có sẵn user `ubuntu` với uid 1000, nên `<user>1000</user>` cho ứng dụng chạy bằng user thường mà không cần tạo user mới. 3.5.2 là bản mới nhất trên Maven Central ngày kiểm chứng.

### 4. Tái lập: Jib và Dockerfile

Xoá `target`, build lại từ đầu, so sánh image ID trước và sau:

<Terminal where="mac">

```bash

mvn -q clean compile jib:dockerBuild
docker image inspect -f '{{.Id}}' masteva-j17/catalog:jib
docker image inspect -f '{{.Id}}' masteva-j17/catalog:dockerfile
mvn -q clean package -DskipTests
docker build -q -t masteva-j17/catalog:dockerfile .
```

</Terminal>

```text

Image Jib giữ nguyên ID. Spring Boot đọc `DOCKER_CONFIG` trước `~/.docker`.

<Check id="j17.2.lab-buildpacks">Build được image bằng `spring-boot:build-image`, giải thích được vì sao nó không khởi động với 512 MB và sửa bằng `BPL_JVM_THREAD_COUNT` hoặc tăng giới hạn.</Check>

### 7. So sánh kích thước

<Terminal where="mac">

```bash
docker image ls masteva-j17/catalog
for t in dockerfile jib buildpacks; do
  docker history --format '{{.Size}}' masteva-j17/catalog:$t |
    awk -v t=$t '/kB$/ {s+=$1/1000} /MB$/ {s+=$1} /GB$/ {s+=$1*1000} END {printf "%-11s %4.0f MB\n", t, s}'
done
```

</Terminal>

<Expected>

```text
IMAGE                            ID             DISK USAGE   CONTENT SIZE   EXTRA
masteva-j17/catalog:buildpacks   0bea4677d199        679MB          325MB
masteva-j17/catalog:dockerfile   5adaacd10b61        544MB          138MB
masteva-j17/catalog:jib          9682f5bccfcb        544MB          138MB
dockerfile   407 MB
jib          407 MB
buildpacks   354 MB
```

</Expected>

Đừng so cột CONTENT SIZE giữa ba image: Buildpacks nạp các layer nó tạo vào Docker ở dạng chưa nén, nên 325 MB gần bằng kích thước chưa nén, còn hai image kia là dung lượng nén. Vòng lặp `awk` cộng kích thước chưa nén của mọi layer theo `docker history`, cho một thước đo chung. Buildpacks nhỏ hơn nhờ run image tiny (khoảng 38 MB so với khoảng 185 MB của Ubuntu đầy đủ), dù JRE Liberica của nó lớn hơn (276 MB so với 200 MB).

### Khi gặp lỗi

<Callout kind="pitfall">

- `429 Too Many Requests` khi tải base image hay builder: Docker Hub giới hạn lượt tải ẩn danh, chạy `docker login`.
- `401 Unauthorized` khi tải base image hay builder: credential đã lưu sai hoặc hết hạn, `docker logout` rồi `docker login` lại.
- `Cannot connect to the Docker daemon` ở `jib:dockerBuild` hay `build-image`: hai lệnh này cần Docker đang chạy. `jib:build` đẩy thẳng lên registry thì không cần.
- `docker run` cảnh báo `The requested image's platform (linux/amd64) does not match the detected host platform`: thiếu khối `platforms` trong cấu hình Jib (bước 3).
- `exec format error` khi deploy image Dockerfile của SB11.1 lên node x86: image build trên Mac M là arm64. Build cho cả hai kiến trúc bằng `docker buildx build --platform linux/amd64,linux/arm64 ...`.
- Build Buildpacks đứng rất lâu ở `Pulling builder image`: builder chiếm hơn 1 GB trên đĩa. Chờ lần đầu; các lần sau dùng lại.

</Callout>

<DeepDive>

<Reveal title="Khi nào Jib không phải lựa chọn tốt?">

Khi image cần thứ mà chỉ `RUN` làm được: cài font cho xuất PDF, cài `curl` cho health check, thư viện native. Jib chỉ xếp file lên base image, nên bạn phải duy trì một base image riêng có sẵn những thứ đó, và lúc ấy bạn vẫn quay về viết Dockerfile, chỉ là ở một repo khác. Jib cũng chỉ hiểu Maven và Gradle; monorepo nhiều ngôn ngữ thường thống nhất bằng Dockerfile.

</Reveal>

<Reveal title="Buildpacks vá lỗ hổng hệ điều hành mà không build lại ứng dụng bằng cách nào?">

Image Buildpacks tách bạch phần run image (hệ điều hành) với các layer ứng dụng, và ghi metadata về ranh giới đó. Thao tác **rebase** (`pack rebase`) thay các layer hệ điều hành bằng bản mới chỉ bằng cách sửa manifest, không chạy lại build, không đụng layer ứng dụng. Với hàng trăm service, việc vá một CVE của OpenSSL chuyển từ hàng trăm pipeline thành một thao tác hàng loạt. Dockerfile không có cơ chế này: mọi layer sau `FROM` phải build lại.

</Reveal>

<Reveal title="Ngày tạo cố định làm mất thông tin. Lấy lại ở đâu?">

`Created: 1970-01-01` đổi lấy việc cùng đầu vào cho cùng ID. Thông tin build nên nằm ở chỗ không phá tính tái lập: tag theo commit (`catalog:3f2a9c1`), label `org.opencontainers.image.revision` chứa mã commit, và metadata của registry ghi thời điểm push. Nếu bạn gắn label chứa thời điểm build, ID sẽ đổi mỗi lần và mất tính tái lập. Jib có `creationTime` để đặt `USE_CURRENT_TIMESTAMP` khi thật sự cần.

</Reveal>

<Reveal title="Image không có shell thì gỡ lỗi production thế nào?">

Không `exec` vào được, nhưng bạn vẫn có các công cụ gắn từ ngoài. Kubernetes có ephemeral container: `kubectl debug -it <pod> --image=busybox --target=<container>` gắn một container có shell vào cùng namespace tiến trình. Docker Desktop có `docker debug`. Cho JVM, bật sẵn JFR và để Actuator phơi `/actuator/threaddump`, `/actuator/heapdump` sau xác thực (SB8) thường hữu ích hơn một shell.

</Reveal>

<Callout kind="ai">

Nhờ AI viết cấu hình Jib hay giải thích một biến `BP_*`, `BPL_*` của Paketo. AI hay đưa tên builder cũ (`paketobuildpacks/builder:base`, `builder-jammy-base`), goal `spring-boot:build-image` với tham số Spring Boot 2, và quên `platforms` khiến image amd64 chạy giả lập trên Mac chip M. Kiểm tra lại bằng log `Pulled builder image`, `docker image inspect -f '{{.Architecture}}'` và log `Calculated JVM Memory Configuration` của chính container.

</Callout>
