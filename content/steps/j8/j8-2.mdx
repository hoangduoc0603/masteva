<Goal>

<Knowledge>

### Vì sao cần test double

`CheckoutService` tính tổng tiền, gọi cổng thanh toán để trừ tiền khách, rồi lưu biên nhận. Nếu unit test gọi cổng thanh toán thật, mỗi lần chạy test là một lần trừ tiền thật, test chậm theo mạng, và đỏ mỗi khi ngân hàng bảo trì. **Test double** (bản thế thân, như diễn viên đóng thế) là object thay cho phụ thuộc thật trong lúc test:

```text
                      ┌──────────────────────┐
  CheckoutServiceTest │   CheckoutService    │ code thật, đang được test
  ──────────────────▶ │  checkout(order, z)  │
                      └───┬──────────────┬───┘
                          │              │
                 charge() │              │ save(), findByOrderId()
                          ▼              ▼
              PaymentGateway        ReceiptRepository
              mock của Mockito      fake: HashMap trong bộ nhớ
              (thay API ngân hàng)  (thay PostgreSQL)
```

| Loại | Là gì | Ví dụ trong bài |
|---|---|---|
| **Dummy** | Chỉ để điền tham số, không bao giờ được dùng | Một `Order` truyền vào nhưng không đọc tới |
| **Stub** | Trả kết quả định sẵn cho một lời gọi | `when(payments.charge(...)).thenReturn("pay-42")` |
| **Mock** | Ghi lại lời gọi để test kiểm tra tương tác | `verify(payments).charge("c-1", 260_000)` |
| **Spy** | Bọc object thật, ghi lại lời gọi | `Mockito.spy(...)`, ít khi cần |
| **Fake** | Cài đặt thật nhưng đơn giản, chạy được | `InMemoryReceiptRepository` dùng `HashMap` |

Với Mockito, một object tạo bằng `mock()` vừa là stub (khi bạn `when`) vừa là mock (khi bạn `verify`). Chọn theo câu hỏi test cần trả lời: "kết quả cuối cùng là gì" thì kiểm tra **trạng thái**, thường bằng fake; "service có gọi ra ngoài đúng cách không" thì kiểm tra **tương tác**, bằng mock.

<Check id="j8.2.double-types">Phân biệt được stub, mock và fake, và chọn được loại phù hợp cho cổng thanh toán và kho dữ liệu.</Check>

### Mockito trong một phút

| Việc | Code |
|---|---|
| Tạo mock | `@Mock PaymentGateway payments;` với `@ExtendWith(MockitoExtension.class)`, hoặc `mock(PaymentGateway.class)` |
| Định sẵn kết quả | `when(payments.charge("c-1", 260_000)).thenReturn("pay-42")` |
| Định sẵn exception | `when(...).thenThrow(new PaymentDeclinedException("..."))` |
| Khớp mọi tham số | `anyString()`, `anyLong()`, `any()`; đã dùng matcher thì mọi tham số đều phải là matcher |
| Kiểm tra đã gọi đúng một lần | `verify(payments).charge("c-1", 260_000)` |
| Kiểm tra không gọi | `verify(payments, never()).charge(anyString(), anyLong())` |

Method chưa được `when` trả giá trị mặc định: `null`, `0`, `false`, list rỗng. `MockitoExtension` còn bật chế độ **strict stubs**: nếu bạn `when` một lời gọi mà test không dùng tới, test đỏ với `UnnecessaryStubbingException`. Quy tắc này giữ test gọn và lộ ra test đang kiểm tra sai thứ.

Ba quy tắc giữ cho mock không biến test thành vô nghĩa:

- **Chỉ mock kiểu mình sở hữu.** `PaymentGateway` là interface của bạn, bọc API ngân hàng. Đừng mock thẳng HTTP client hay SDK của bên thứ ba: hành vi thật của chúng phức tạp hơn bạn đoán, và mock của bạn sẽ sai theo cách bạn đoán.
- **Không mock kiểu dữ liệu đơn giản.** `Order`, `OrderLine`, `String`, `List` rẻ và chạy được, cứ dùng bản thật.
- **Không mock thứ đang test.** Mock chỉ nằm ở rìa: những gì ra khỏi process.

### Mockito trên Java 21 trở lên

Để mock được cả class `final`, Mockito 5 dùng **inline mock maker**: nó sửa bytecode của class lúc đang chạy, việc cần một **Java agent** (chương trình được JVM nạp kèm, có quyền sửa class). Trước đây Mockito tự gắn agent vào JVM đang chạy. Từ Java 21 (JEP 451), JVM cảnh báo mỗi khi có agent được gắn động như vậy và sẽ mặc định cấm ở một bản sau (khi đó phải bật lại bằng `-XX:+EnableDynamicAgentLoading`). Cách đúng là khai báo agent khi khởi động JVM chạy test, bằng tham số `-javaagent:<đường dẫn tới mockito-core.jar>`. Phần thực hành làm việc này bằng `maven-dependency-plugin` và `argLine` của Surefire.

### Kim tự tháp test

```text
                 /\
                /  \       End-to-end: cả hệ thống qua UI hay API
               / E2E\      rất ít, chậm (phút), dễ đỏ vì lý do ngoài code
              /------\
             /        \    Integration: code thật + hạ tầng thật hoặc nhiều module ghép
            /Integrat. \   vừa phải, chậm hơn (giây), cần Docker, database
           /------------\
          /              \  Unit: một class, phụ thuộc là test double
         /      Unit      \ nhiều nhất, nhanh (mili giây), chạy mỗi lần lưu file
        /------------------\
```

Ý chính của kim tự tháp: càng lên cao test càng chậm, càng đắt để viết và sửa, nên càng phải ít. Lỗi logic như phí giao hàng nên bị bắt ở tầng unit; tầng integration chỉ để kiểm những thứ unit test không thấy được, như SQL có chạy trên PostgreSQL thật không.

Maven tách hai tầng dưới bằng hai plugin gần như giống nhau:

| | Surefire | Failsafe |
|---|---|---|
| Tên file mặc định | `*Test`, `Test*`, `*Tests`, `*TestCase` | `*IT`, `IT*`, `*ITCase` |
| Chạy ở phase | `test` | `integration-test`, rồi `verify` |
| Khi có test đỏ | Dừng build ngay | Ghi lại, chỉ báo đỏ ở phase `verify` |
| Lệnh | `mvn test` | `mvn verify` (chạy cả hai) |

Failsafe không dừng ngay ở phase `integration-test`, để phase `post-integration-test` vẫn kịp dọn dẹp (tắt server, xoá container) trước khi build báo đỏ. Với Gradle, plugin JVM Test Suite cho phép khai báo một bộ `integrationTest` riêng theo cùng ý tưởng.

<Callout kind="production">

Một team đặt mọi test là `*Test`, kể cả test cần database. `mvn test` mất 8 phút, nên lập trình viên thôi chạy test trước khi push và chỉ chờ CI. Tách test cần hạ tầng sang `*IT` đưa `mvn test` về vài giây để chạy liên tục khi code; CI chạy `mvn verify` để không bỏ sót integration test. Đừng đi xa theo hướng ngược lại: CI chỉ chạy `mvn test` thì file `*IT` không bao giờ được chạy.

</Callout>

```bash
package com.masteva.shop;

import java.util.Optional;

public class CheckoutService {
    private final PaymentGateway payments;
    private final ReceiptRepository receipts;

    public CheckoutService(PaymentGateway payments, ReceiptRepository receipts) {
        this.payments = payments;
        this.receipts = receipts;
    }

    public Receipt checkout(Order order, Zone zone) {
        if (order.lines().isEmpty()) {
            throw new IllegalStateException("order " + order.id() + " is empty");
        }
        Optional<Receipt> existing = receipts.findByOrderId(order.id());
        if (existing.isPresent()) {
            return existing.get(); // khách bấm "Thanh toán" lần hai: không trừ tiền lại
        }
        long fee = ShippingFee.of(order.subtotal(), zone);
        long total = order.subtotal() + fee;
        String paymentId = payments.charge(order.customerId(), total);
        Receipt receipt = new Receipt(order.id(), order.customerId(), order.subtotal(), fee, total, paymentId);
        receipts.save(receipt);
        return receipt;
    }
}
EOF
```

- `mockito-junit-jupiter` kéo theo `mockito-core` và thêm `MockitoExtension` để dùng `@Mock`.
- Goal `properties` của `maven-dependency-plugin` tạo một property cho mỗi dependency, dạng `groupId:artifactId:type`, có giá trị là đường dẫn tới file jar trong `~/.m2`. `-javaagent:${org.mockito:mockito-core:jar}` nhờ đó trỏ đúng tới jar của Mockito trên mọi máy.
- `@{argLine}` (dấu `@`, không phải `$`) được Surefire thay **muộn**, lúc chuẩn bị chạy test, nên giữ được tham số mà plugin khác như JaCoCo ghi vào `argLine`. Nếu property `argLine` không tồn tại, chuỗi `@{argLine}` được truyền nguyên văn cho JVM và JVM chết ngay; vì vậy có dòng `<argLine></argLine>` rỗng trong `properties`.
- Failsafe cần khai báo `executions` với hai goal. Thiếu phần này, plugin có mặt nhưng không chạy gì, và không báo lỗi.

### 3. Fake, stub và mock trong một test

<Terminal where="mac" title="Tạo fake và CheckoutServiceTest trong src/test/java/com/masteva/shop">

```bash
cd ~/masteva-j8
cat > src/test/java/com/masteva/shop/InMemoryReceiptRepository.java <<'EOF'
package com.masteva.shop;

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

/** Fake: cài đặt thật nhưng đơn giản, giữ dữ liệu trong một HashMap. */
class InMemoryReceiptRepository implements ReceiptRepository {
    private final Map<String, Receipt> byOrderId = new HashMap<>();

    @Override
    public void save(Receipt receipt) {
        byOrderId.put(receipt.orderId(), receipt);
    }

    @Override
    public Optional<Receipt> findByOrderId(String orderId) {
        return Optional.ofNullable(byOrderId.get(orderId));
    }
}
EOF
cat > src/test/java/com/masteva/shop/CheckoutServiceTest.java <<'EOF'
package com.masteva.shop;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;
import static org.mockito.ArgumentMatchers.anyLong;
import static org.mockito.ArgumentMatchers.anyString;
import static org.mockito.Mockito.never;
import static org.mockito.Mockito.verify;
import static org.mockito.Mockito.when;

import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.junit.jupiter.api.extension.ExtendWith;
import org.mockito.Mock;
import org.mockito.junit.jupiter.MockitoExtension;

@ExtendWith(MockitoExtension.class)
class CheckoutServiceTest {

    @Mock
    PaymentGateway payments;

    InMemoryReceiptRepository receipts = new InMemoryReceiptRepository();
    CheckoutService service;
    Order order = new Order("o-1", "c-1");

    @BeforeEach
    void setUp() {
        service = new CheckoutService(payments, receipts);
        order.add(new OrderLine("BOOK", 2, 120_000));
    }

    @Test
    void chargesSubtotalPlusShippingAndSavesReceipt() {
        when(payments.charge("c-1", 260_000)).thenReturn("pay-42");

        Receipt receipt = service.checkout(order, Zone.HANOI);

        assertThat(receipt.total()).isEqualTo(260_000);
        assertThat(receipt.paymentId()).isEqualTo("pay-42");
        assertThat(receipts.findByOrderId("o-1")).contains(receipt);
    }

    @Test
    void doesNotChargeTwiceForTheSameOrder() {
        when(payments.charge("c-1", 260_000)).thenReturn("pay-42");
        service.checkout(order, Zone.HANOI);

        Receipt second = service.checkout(order, Zone.HANOI);

        assertThat(second.paymentId()).isEqualTo("pay-42");
        verify(payments).charge("c-1", 260_000);
    }

    @Test
    void savesNothingWhenPaymentIsDeclined() {
        when(payments.charge(anyString(), anyLong()))
                .thenThrow(new PaymentDeclinedException("insufficient funds"));

        assertThatThrownBy(() -> service.checkout(order, Zone.HANOI))
                .isInstanceOf(PaymentDeclinedException.class);
        assertThat(receipts.findByOrderId("o-1")).isEmpty();
    }

    @Test
    void rejectsEmptyOrderWithoutCallingTheGateway() {
        Order empty = new Order("o-2", "c-1");

        assertThatThrownBy(() -> service.checkout(empty, Zone.HANOI))
                .isInstanceOf(IllegalStateException.class);
        verify(payments, never()).charge(anyString(), anyLong());
    }
}
EOF
mvn test -Dtest=CheckoutServiceTest
```

Dòng `Sharing is only supported...` xuất hiện vì agent của Mockito thêm class vào bootstrap classpath, nên JVM tắt bớt CDS (Class Data Sharing, bộ nhớ đệm class giúp JVM khởi động nhanh hơn) cho các class đó. Nó vô hại; không còn cảnh báo "self-attaching" nữa là cấu hình agent đã đúng. Với OpenJDK, chữ `Java HotSpot(TM)` có thể là `OpenJDK`.

Đọc lại bốn test:

- `receipts` là **fake**: test kiểm tra trạng thái cuối, "biên nhận đã nằm trong kho", thay vì hỏi `save` có được gọi không.
- `when(...).thenReturn("pay-42")` dùng `payments` như **stub**; `thenThrow` giả lập ngân hàng từ chối.
- `verify(payments).charge("c-1", 260_000)` và `verify(payments, never())` dùng `payments` như **mock**: tiền là thứ chỉ quan sát được qua lời gọi ra ngoài.
- `Order` và `OrderLine` là bản thật. 260.000 là 240.000 tiền sách cộng 20.000 phí giao hàng ở Hà Nội, tính bằng `ShippingFee` thật.

<Check id="j8.2.lab-mockito">Viết được test dùng `@Mock`, `when(...).thenReturn`, `thenThrow`, `verify` và `never()`, chạy xanh mà không có cảnh báo self-attaching.</Check>

### 5. Integration test với Failsafe

Unit test ở bước 3 thay cổng thanh toán bằng mock. Integration test dưới đây ghép các class thật lại với nhau qua một tình huống trọn vẹn: khách bị từ chối vì vượt hạn mức, đặt đơn nhỏ hơn, rồi bấm "Thanh toán" hai lần. Cổng thanh toán lần này là một fake có hạn mức, viết tay:

<Terminal where="mac" title="Tạo FakePaymentGateway và CheckoutFlowIT">

```bash
cd ~/masteva-j8
cat > src/test/java/com/masteva/shop/FakePaymentGateway.java <<'EOF'
package com.masteva.shop;

import java.util.ArrayList;
import java.util.List;

/** Fake: cổng thanh toán chạy trong bộ nhớ, từ chối giao dịch vượt hạn mức. */
class FakePaymentGateway implements PaymentGateway {
    private final long limit;
    final List<Long> charges = new ArrayList<>();

    FakePaymentGateway(long limit) {
        this.limit = limit;
    }

    @Override
    public String charge(String customerId, long amount) {
        if (amount > limit) {
            throw new PaymentDeclinedException("over limit: " + amount);
        }
        charges.add(amount);
        return "pay-" + charges.size();
    }
}
EOF
cat > src/test/java/com/masteva/shop/CheckoutFlowIT.java <<'EOF'
package com.masteva.shop;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import org.junit.jupiter.api.Test;

/** Ghép các class thật với nhau; chỉ thay những gì nằm ngoài process. */
class CheckoutFlowIT {

    FakePaymentGateway payments = new FakePaymentGateway(1_000_000);
    InMemoryReceiptRepository receipts = new InMemoryReceiptRepository();
    CheckoutService service = new CheckoutService(payments, receipts);

    @Test
    void customerRetriesAfterADeclinedPayment() {
        Order order = new Order("o-9", "c-7");
        order.add(new OrderLine("LAPTOP", 1, 1_500_000));
        assertThatThrownBy(() -> service.checkout(order, Zone.OTHER))
                .isInstanceOf(PaymentDeclinedException.class);

        Order smaller = new Order("o-10", "c-7");
        smaller.add(new OrderLine("BOOK", 3, 120_000));
        Receipt receipt = service.checkout(smaller, Zone.OTHER);
        service.checkout(smaller, Zone.OTHER);

        assertThat(receipt.total()).isEqualTo(395_000);
        assertThat(payments.charges).containsExactly(395_000L);
        assertThat(receipts.findByOrderId("o-9")).isEmpty();
    }
}
EOF
mvn test 2>&1 | grep -E 'Tests run:.*Skipped: 0$|BUILD'
```

</Terminal>

<Expected>

```text

[INFO] BUILD SUCCESS
```

</Expected>

`grep` chỉ giữ dòng tổng kết. 26 là 22 test của bài J8.1 cộng 4 test của `CheckoutServiceTest`; `CheckoutFlowIT` không chạy vì tên không khớp mẫu của Surefire. Giờ chạy tới phase `verify`:

<Terminal where="mac">


```text
[INFO] Tests run: 26, Failures: 0, Errors: 0, Skipped: 0

[INFO] Tests run: 1, Failures: 0, Errors: 0, Skipped: 0
```

Thứ tự trên là vòng đời của Maven: Surefire chạy unit test ở phase `test`, Maven đóng gói jar ở phase `package`, rồi Failsafe chạy `*IT` ở `integration-test` và báo kết quả ở `verify`. Unit test đỏ thì build dừng trước khi tới integration test, đúng tinh thần của kim tự tháp: tầng rẻ chặn lỗi trước tầng đắt.

<Check id="j8.2.lab-failsafe">Cấu hình được Failsafe, đặt tên integration test là `*IT`, và chứng minh được `mvn test` bỏ qua nó còn `mvn verify` chạy nó.</Check>

### Khi gặp lỗi

<Callout kind="pitfall">

- `UnnecessaryStubbingException ... Unnecessary stubbings detected`: test `when` một lời gọi mà code không gọi tới, ví dụ stub `charge` trong test đơn rỗng, nơi service ném exception trước khi gọi cổng thanh toán. Xoá stub đó; đừng vội tắt strict stubs bằng `lenient()`, vì stub thừa thường cho thấy test đang hiểu sai luồng code.
- `Error: could not open` kèm chữ `{argLine}`, rồi `The forked VM terminated without properly saying goodbye`: JVM nhận nguyên văn `@{argLine}` hoặc `${org.mockito:mockito-core:jar}` như một tham số. Kiểm tra dòng `<argLine></argLine>` trong `properties` và khối `maven-dependency-plugin` có goal `properties`.
- `CheckoutFlowIT` không bao giờ chạy: bạn chạy `mvn test` thay vì `mvn verify`, hoặc khối Failsafe thiếu `executions`.
- `Invalid use of argument matchers! 2 matchers expected, 1 recorded`: bạn trộn matcher với giá trị thật, ví dụ `charge(anyString(), 260_000)`. Dùng `eq(260_000L)` cho giá trị thật, hoặc bỏ matcher hẳn.

</Callout>

<DeepDive>

<Reveal title="Kho dữ liệu: dùng fake hay mock?">

Với `ReceiptRepository`, fake thường tốt hơn. Test viết bằng mock sẽ là `verify(repository).save(receipt)`: nó gắn chặt vào cách service gọi kho. Đổi `save` thành `saveAll` là test đỏ dù hành vi không đổi. Test với fake hỏi "sau khi checkout, kho có biên nhận không", và vẫn đúng sau khi refactor. Giữ mock cho những tác dụng ra ngoài mà chỉ quan sát được qua lời gọi: trừ tiền, gửi email, đẩy message lên Kafka.

</Reveal>

<Reveal title="Vì sao không mock Order cho nhanh?">

Mock `Order` nghĩa là bạn tự định nghĩa `subtotal()` trả gì. Khi `Order` có lỗi tính tiền, test của `CheckoutService` vẫn xanh vì nó không còn chạy code thật của `Order`. Nó cũng bắt bạn viết lại hành vi của `Order` trong từng test. Object dữ liệu rẻ, chạy được và không ra khỏi process, nên dùng bản thật. Mock nhiều tới mức test chỉ còn kiểm tra "method A gọi method B" là dấu hiệu nên lùi lại.

</Reveal>

<Reveal title="ArgumentCaptor dùng khi nào?">

Khi tham số truyền cho mock là một object được tạo bên trong service, và bạn muốn kiểm tra nội dung của nó. Ví dụ nếu kho dữ liệu là mock, `ArgumentCaptor<Receipt> captor = ArgumentCaptor.forClass(Receipt.class); verify(repository).save(captor.capture());` rồi `assertThat(captor.getValue().total()).isEqualTo(260_000)`. Nếu dùng được fake, đọc thẳng dữ liệu từ fake thường dễ hiểu hơn.

</Reveal>

<Reveal title="Kim tự tháp có phải luật cứng không?">

Không. Nó là lời khuyên về chi phí: test càng rộng càng chậm và càng khó tìm nguyên nhân khi đỏ. Một service gần như chỉ đọc ghi database có ít logic để unit test, và phần lớn giá trị nằm ở integration test với database thật; một số team gọi hình dạng đó là "tổ ong" hay "chiếc cúp". Điều không đổi: lỗi nào bắt được ở tầng rẻ hơn thì bắt ở đó, và tầng end-to-end chỉ nên giữ vài hành trình quan trọng nhất như đặt hàng và thanh toán.

</Reveal>
