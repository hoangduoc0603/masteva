<Goal>

Viết integration test cho một repository JDBC chạy với PostgreSQL thật, do Testcontainers khởi động trong Docker ngay trong lúc test, và đọc được báo cáo độ phủ của JaCoCo mà không hiểu nhầm nó. Học xong bài này, bạn giải thích được:

- Vì sao test repository bằng H2 xanh mà lên production với PostgreSQL vẫn lỗi.
- Vì sao mỗi lần chạy, database trong test có một cổng khác, và vì sao điều đó an toàn hơn cổng 5432 cố định.
- Vì sao độ phủ 100% vẫn để lọt lỗi `>` thay vì `>=` ở bài J8.1.

</Goal>

<Knowledge>

### Vì sao cần database thật trong test

Repository là nơi code Java gặp SQL. Unit test với fake ở bài J8.2 không chạy một câu SQL nào, nên không bắt được lỗi cú pháp, sai tên cột hay vi phạm ràng buộc. Cách cũ là chạy test với **H2**, một database viết bằng Java chạy trong bộ nhớ. H2 nhanh, nhưng nó là một database khác: kiểu dữ liệu, hàm, thông báo lỗi và cách khoá đều khác PostgreSQL; chế độ tương thích chỉ giả lập một phần cú pháp. Test xanh trên H2 chứng minh code chạy trên H2.

**Testcontainers** là thư viện Java khởi động container Docker từ trong test: PostgreSQL, Kafka, Redis hay bất kỳ image nào. Test chạy với đúng phiên bản database của production, rồi container bị xoá khi test xong.

### Testcontainers chạy thế nào

```text
mvn verify
  └─ Failsafe chạy JdbcReceiptRepositoryIT
       └─ @Testcontainers (JUnit extension) tìm các field @Container
            1. Gọi Docker API: tạo container ryuk (người dọn dẹp) cho lần chạy này
            2. Tạo container postgres:18-alpine, cổng 5432 bên trong
               được map ra một cổng ngẫu nhiên trên máy, ví dụ 51022
            3. Chờ tới khi PostgreSQL in "ready to accept connections"
            4. Chạy db/schema.sql (withInitScript)
            5. Chạy các test; test lấy URL bằng postgres.getJdbcUrl()
               -> jdbc:postgresql://localhost:51022/test
            6. Hết class: dừng và xoá container
  JVM thoát (kể cả bị kill): ryuk thấy mất kết nối, xoá mọi container còn sót
```

- **Cổng động.** Mặc định Testcontainers map ra một cổng ngẫu nhiên trên máy. Hai bộ test chạy song song trên cùng máy CI không đụng nhau, và test không vô tình kết nối vào PostgreSQL bạn cài sẵn ở cổng 5432. Vì vậy test phải lấy URL, user, password từ container thay vì ghi cứng.
- **Ryuk** là một container nhỏ chạy kèm. Nếu JVM chết giữa chừng, Ryuk vẫn dọn container, nên máy bạn không đầy container mồ côi.

<Callout kind="production">

Integration test của một team kết nối tới `localhost:5432` ghi cứng, và mỗi test bắt đầu bằng `TRUNCATE`. Trên máy CI không sao. Trên máy một lập trình viên, PostgreSQL cài sẵn đang chạy ở cổng 5432, chứa dữ liệu anh ấy đã nhập tay suốt hai tuần để thử tính năng; chạy test là xoá sạch bảng. Với Testcontainers, URL luôn trỏ tới một container vừa tạo và sẽ bị xoá, nên `TRUNCATE` trong test chỉ chạm vào dữ liệu của test.

</Callout>

### Vòng đời container và tốc độ

Khởi động PostgreSQL mất khoảng một giây; kéo image lần đầu mất lâu hơn nhiều. Cách khai báo field quyết định số lần khởi động:

| Khai báo | Container | Dùng khi |
|---|---|---|
| `@Container static PostgreSQLContainer postgres` | Một cho cả class, dùng chung cho mọi test | Mặc định nên dùng; dọn dữ liệu giữa các test bằng `TRUNCATE` |
| `@Container PostgreSQLContainer postgres` (không `static`) | Một container mới cho **mỗi** test | Test cần database hoàn toàn mới, ví dụ test migration |
| Field `static` trong một class cha, khởi động trong khối `static` | Một cho cả lần chạy, dùng chung giữa nhiều class | Nhiều class `*IT` cùng cần PostgreSQL |

Mẫu thứ ba gọi là **singleton container**: không dùng `@Container`, gọi `postgres.start()` trong khối `static { }` của class cha, và để Ryuk xoá container khi JVM thoát.

<Check id="j8.3.lifecycle">Giải thích được field `@Container` có `static` và không có `static` khác nhau thế nào về số container và thời gian chạy.</Check>

### Độ phủ và mutation testing

**JaCoCo** đo xem test đã chạy qua những dòng và nhánh nào. Nó gắn một Java agent vào JVM chạy test (lại dùng `argLine`, như Mockito ở bài J8.2), ghi kết quả vào `target/jacoco.exec`, rồi goal `report` sinh báo cáo HTML, CSV và XML trong `target/site/jacoco`.

| Bộ đếm | Ý nghĩa |
|---|---|
| Line | Dòng có ít nhất một lệnh bytecode đã chạy |
| Branch | Mỗi hướng của `if`, `switch`, `?:` đã đi qua chưa |
| Instruction | Số lệnh bytecode đã chạy, đơn vị nhỏ nhất |

Độ phủ trả lời "test **đã chạy qua** đoạn code này chưa", không trả lời "test **có kiểm tra** đoạn code này không". Một test gọi `ShippingFee.of(...)` mà không có assertion nào vẫn cho độ phủ 100%. **Mutation testing** (công cụ PIT cho Java) đo chất lượng test bằng cách cố ý sửa code, ví dụ đổi `>=` thành `>`, rồi chạy lại test: nếu test vẫn xanh, "mutant" đó sống sót và bạn biết assertion còn lỗ hổng. Nó chậm vì chạy test nhiều lần, nên hợp với logic lõi như tính tiền hơn là cả dự án.

<Check id="j8.3.coverage-meaning">Giải thích được vì sao độ phủ cao không chứng minh test tốt, và mutation testing đo thêm được điều gì.</Check>

</Knowledge>

### 3. Bảng và repository JDBC

<Terminal where="mac" title="Tạo schema.sql và JdbcReceiptRepository.java">

```bash
cd ~/masteva-j8
mkdir -p src/main/resources/db
cat > src/main/resources/db/schema.sql <<'EOF'
CREATE TABLE receipts (
    order_id     TEXT PRIMARY KEY,
    customer_id  TEXT NOT NULL,
    subtotal     BIGINT NOT NULL CHECK (subtotal >= 0),
    shipping_fee BIGINT NOT NULL CHECK (shipping_fee >= 0),
    total        BIGINT NOT NULL,
    payment_id   TEXT NOT NULL,
    created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
EOF
cat > src/main/java/com/masteva/shop/JdbcReceiptRepository.java <<'EOF'
package com.masteva.shop;

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.PreparedStatement;
import java.sql.ResultSet;
import java.sql.SQLException;
import java.util.Optional;

public class JdbcReceiptRepository implements ReceiptRepository {
    private final String url;
    private final String user;
    private final String password;

    public JdbcReceiptRepository(String url, String user, String password) {
        this.url = url;
        this.user = user;
        this.password = password;
    }

    /** Lưu biên nhận; đơn đã có biên nhận thì giữ bản cũ (ON CONFLICT DO NOTHING). */
    @Override
    public void save(Receipt r) {
        String sql = """
                INSERT INTO receipts (order_id, customer_id, subtotal, shipping_fee, total, payment_id)
                VALUES (?, ?, ?, ?, ?, ?)
                ON CONFLICT (order_id) DO NOTHING
                """;
        try (Connection c = DriverManager.getConnection(url, user, password);
             PreparedStatement ps = c.prepareStatement(sql)) {
            ps.setString(1, r.orderId());
            ps.setString(2, r.customerId());
            ps.setLong(3, r.subtotal());
            ps.setLong(4, r.shippingFee());
            ps.setLong(5, r.total());
            ps.setString(6, r.paymentId());
            ps.executeUpdate();
        } catch (SQLException e) {
            throw new IllegalStateException("cannot save receipt " + r.orderId(), e);
        }
    }

    @Override
    public Optional<Receipt> findByOrderId(String orderId) {
        String sql = """
                SELECT order_id, customer_id, subtotal, shipping_fee, total, payment_id
                FROM receipts WHERE order_id = ?
                """;
        try (Connection c = DriverManager.getConnection(url, user, password);
             PreparedStatement ps = c.prepareStatement(sql)) {
            ps.setString(1, orderId);
            try (ResultSet rs = ps.executeQuery()) {
                if (!rs.next()) {
                    return Optional.empty();
                }
                return Optional.of(new Receipt(rs.getString("order_id"), rs.getString("customer_id"),
                        rs.getLong("subtotal"), rs.getLong("shipping_fee"), rs.getLong("total"),
                        rs.getString("payment_id")));
            }
        } catch (SQLException e) {
            throw new IllegalStateException("cannot read receipt " + orderId, e);
        }
    }
}
EOF
```

</Terminal>

JDBC là API chuẩn của Java để nói chuyện với database; bài SB3 đi sâu vào nó cùng connection pool. Ở đây bạn chỉ cần ba ý:

- `DriverManager.getConnection(url, user, password)` mở kết nối; driver PostgreSQL nhận URL bắt đầu bằng `jdbc:postgresql://`.
- `PreparedStatement` với dấu `?` truyền tham số an toàn, không ghép chuỗi SQL.
- `try (...)` (try-with-resources, bài J4) đóng kết nối kể cả khi có exception.

`ON CONFLICT (order_id) DO NOTHING` là cú pháp của PostgreSQL: lưu lại biên nhận cho cùng một đơn sẽ không ghi đè biên nhận đầu tiên. Đây chính là loại SQL mà chỉ database thật mới kiểm được.

### 4. Integration test với PostgreSQL thật

<Terminal where="mac" title="Tạo JdbcReceiptRepositoryIT và chạy mvn verify">

```bash
cd ~/masteva-j8
cat > src/test/java/com/masteva/shop/JdbcReceiptRepositoryIT.java <<'EOF'
package com.masteva.shop;

import static org.assertj.core.api.Assertions.assertThat;
import static org.assertj.core.api.Assertions.assertThatThrownBy;

import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.sql.Statement;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;
import org.testcontainers.junit.jupiter.Container;
import org.testcontainers.junit.jupiter.Testcontainers;
import org.testcontainers.postgresql.PostgreSQLContainer;

@Testcontainers
class JdbcReceiptRepositoryIT {

    @Container
    static PostgreSQLContainer postgres = new PostgreSQLContainer("postgres:18-alpine")
            .withInitScript("db/schema.sql");

    JdbcReceiptRepository repository;

    @BeforeEach
    void cleanTable() throws SQLException {
        System.out.println("JDBC URL: " + postgres.getJdbcUrl());
        repository = new JdbcReceiptRepository(
                postgres.getJdbcUrl(), postgres.getUsername(), postgres.getPassword());
        try (Connection c = DriverManager.getConnection(
                postgres.getJdbcUrl(), postgres.getUsername(), postgres.getPassword());
             Statement s = c.createStatement()) {
            s.execute("TRUNCATE receipts");
        }
    }

    @Test
    void savesAndReadsBack() {
        Receipt receipt = new Receipt("o-1", "c-1", 240_000, 20_000, 260_000, "pay-1");

        repository.save(receipt);

        assertThat(repository.findByOrderId("o-1")).contains(receipt);
        assertThat(repository.findByOrderId("o-404")).isEmpty();
    }

    @Test
    void keepsTheFirstReceiptOfAnOrder() {
        repository.save(new Receipt("o-1", "c-1", 240_000, 20_000, 260_000, "pay-1"));
        repository.save(new Receipt("o-1", "c-1", 240_000, 20_000, 260_000, "pay-2"));

        assertThat(repository.findByOrderId("o-1"))
                .get().extracting(Receipt::paymentId).isEqualTo("pay-1");
    }

    @Test
    void databaseRejectsNegativeSubtotal() {
        Receipt broken = new Receipt("o-2", "c-1", -1, 0, -1, "pay-3");

        assertThatThrownBy(() -> repository.save(broken))
                .isInstanceOf(IllegalStateException.class)
                .cause().hasMessageContaining("receipts_subtotal_check");
    }

    @Test
    void checkoutWithARealDatabase() {
        FakePaymentGateway payments = new FakePaymentGateway(1_000_000);
        CheckoutService service = new CheckoutService(payments, repository);
        Order order = new Order("o-3", "c-2");
        order.add(new OrderLine("BOOK", 5, 120_000));

        service.checkout(order, Zone.HCMC);
        service.checkout(order, Zone.HCMC);

        assertThat(payments.charges).containsExactly(600_000L);
        assertThat(repository.findByOrderId("o-3")).get()
                .extracting(Receipt::shippingFee).isEqualTo(0L);
    }
}
EOF
mvn verify
```

### Khi gặp lỗi

<Callout kind="pitfall">

- `Could not find a valid Docker environment`: Docker chưa chạy, hoặc Testcontainers không tìm thấy socket. Chạy lại bước 1. Nếu log có thêm `BadRequestException (Status 400: ...)` dù Docker đang chạy, bạn đang dùng Testcontainers quá cũ với Docker 29: bản 1.21.3 trở về trước, 2.0.0 và 2.0.1 báo lỗi này, bản 1.21.4 trở lên (nhánh 1.x) hoặc 2.0.2 trở lên chạy được.
- `relation "receipts" does not exist`: `withInitScript` không tìm thấy hoặc không chạy được `db/schema.sql`. File phải nằm trong `src/main/resources` hoặc `src/test/resources`, đường dẫn tính từ gốc classpath.
- `No suitable driver found for jdbc:postgresql://...`: thiếu dependency `org.postgresql:postgresql`.
- Test treo lâu ở `Pulling docker image`: lần đầu cần tải image; mạng công ty có proxy thì cấu hình proxy cho Docker Desktop trước.
- Báo cáo JaCoCo không có hoặc ghi `Skipping JaCoCo execution due to missing execution data file`: cấu hình `argLine` của Surefire đã ghi đè agent của JaCoCo. Kiểm tra `argLine` bắt đầu bằng `@{argLine}`.

</Callout>

<DeepDive>

<Reveal title="Nhiều class *IT cùng cần PostgreSQL thì làm sao để chỉ khởi động một lần?">

Dùng mẫu singleton container: một class cha trừu tượng có `static final PostgreSQLContainer POSTGRES = new PostgreSQLContainer("postgres:18-alpine");` và khối `static { POSTGRES.start(); }`, không dùng `@Testcontainers` hay `@Container`. Mọi class `*IT` kế thừa nó dùng chung container trong suốt lần chạy, và Ryuk xoá container khi JVM thoát. Cái giá là dữ liệu bị chia sẻ giữa các class, nên mỗi test phải tự dọn hoặc dùng dữ liệu không trùng nhau.

</Reveal>

<Reveal title="withReuse(true) có nên dùng không?">

`withReuse(true)` giữ container sống qua nhiều lần chạy `mvn verify`, nên lần sau test bắt đầu ngay. Nó chỉ bật khi máy có `testcontainers.reuse.enable=true` trong file `~/.testcontainers.properties`, và tài liệu ghi rõ đây là tính năng thử nghiệm. Container được giữ lại không bị Ryuk xoá, nên dữ liệu của lần chạy trước còn đó. Hợp cho máy dev muốn vòng phản hồi nhanh; không dùng trên CI, nơi mỗi lần build phải sạch.

</Reveal>

<Reveal title="Vì sao không mở sẵn một PostgreSQL bằng docker compose rồi cho test kết nối vào?">

Được, nhưng bạn phải tự lo: khởi động trước khi test, chờ database sẵn sàng, tránh cổng trùng, dọn dữ liệu, tắt sau khi xong, và giữ phiên bản image khớp giữa máy dev và CI. Testcontainers gói những việc đó vào code test: ai clone repo về chỉ cần Docker và `mvn verify`. Docker Compose vẫn hợp khi bạn chạy cả hệ thống để test end-to-end bằng tay; Testcontainers cũng có module dựng một file Compose từ trong test.

</Reveal>

<Reveal title="Có nên đặt ngưỡng độ phủ bắt buộc, ví dụ 80%, trên CI không?">

Ngưỡng chặn được việc độ phủ tụt mạnh mà không ai để ý, nhưng con số dễ bị chạy theo: người ta viết test không assertion cho đủ phần trăm. Cách hợp lý hơn là dùng goal `check` của JaCoCo với ngưỡng vừa phải cho các package logic lõi, đọc báo cáo để tìm vùng chưa test có rủi ro cao, và chạy PIT định kỳ cho phần tính tiền. Độ phủ thấp là tín hiệu chắc chắn có vấn đề; độ phủ cao chưa nói được gì.

</Reveal>
