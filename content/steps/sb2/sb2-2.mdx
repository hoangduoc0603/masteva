<Goal>

Đưa service đơn hàng của SB2.1 lên PostgreSQL thật ở cả ba nơi: trong test (Testcontainers), khi chạy trên máy dev (Docker Compose), và trong test qua HTTP thật (`RestTestClient`), rồi sắp các loại test thành một chiến lược rõ ràng. Học xong bài này, bạn giải thích được:

- Vì sao test lịch sử đơn hàng xanh trên H2 nhưng đỏ trên PostgreSQL, dù câu SQL giống hệt nhau.
- Vì sao một test `@Transactional` gọi API qua `RestTestClient` để lại dữ liệu trong database, trong khi cùng test đó với MockMvc thì không.
- Vì sao chạy `spring-boot:test-run` trong project có `compose.yaml` lại khởi động hai PostgreSQL và ứng dụng chỉ dùng một.

</Goal>

<Knowledge>

### Vì sao bỏ H2

J8.3 đã nói: test trên H2 chứng minh code chạy trên H2. SB2.1 có một ví dụ cụ thể. Luật nghiệp vụ "đơn chưa thanh toán nằm cuối danh sách" được kiểm bằng `order by paid_at desc` trên H2, và test xanh. Nhưng hai database xử lý `NULL` khi sắp xếp khác nhau:

| Database | `NULL` được coi là | `ORDER BY paid_at DESC` | `ORDER BY paid_at ASC` |
|---|---|---|---|
| H2 (mặc định) | Nhỏ hơn mọi giá trị | `NULL` ở cuối | `NULL` ở đầu |
| PostgreSQL | Lớn hơn mọi giá trị | `NULL` ở **đầu** | `NULL` ở cuối |

Cùng một câu SQL, hai thứ tự khác nhau. Trên production, trang "lịch sử đơn" sẽ đẩy đơn chưa thanh toán lên trên cùng, và bộ test xanh không báo gì. Lỗi loại này còn nhiều: kiểu cột (`status enum(...)` mà Hibernate tạo trên H2 không có trên PostgreSQL), schema do Hibernate sinh thay vì migration thật, cú pháp riêng như `ON CONFLICT`, `DISTINCT ON`, `interval '7 days'` mà H2 không hiểu. Cách chắc chắn là test trên đúng database và đúng phiên bản của production.

### @ServiceConnection: Testcontainers trong Spring Boot

J8.3 dùng Testcontainers thuần: lấy `getJdbcUrl()` từ container rồi tự truyền cho repository. Trong Spring Boot, URL đó phải tới được `DataSource` mà auto-configuration tạo. Có ba cách, cách mới nhất gọn nhất:

| Cách | Viết | Ai quản lý vòng đời container |
|---|---|---|
| `@DynamicPropertySource` | Method static thêm `spring.datasource.url`, `username`, `password` từ container | JUnit (`@Container`) |
| `@ServiceConnection` trên field `@Container static` | Annotation trên field | JUnit, có rủi ro với context cache (xem Đào sâu) |
| `@ServiceConnection` trên `@Bean` trong `@TestConfiguration` | Một method trả container | **Spring**: container là một bean |

Lab dùng cách thứ ba, cũng là cách start.spring.io sinh ra khi chọn Testcontainers. Bên dưới:

```text
@Import(TestcontainersConfiguration.class)  trên class test
   |
   v
TestcontainersConfiguration
   @Bean @ServiceConnection PostgreSQLContainer postgres()
   |
   |  1. Spring Boot đọc KIỂU trả về (PostgreSQLContainer), chưa cần gọi method,
   |     tìm ContainerConnectionDetailsFactory phù hợp
   |  2. Đăng ký bean JdbcConnectionDetails trỏ tới container
   |  3. Bean container được tạo và start() trước bean cần kết nối (DataSource)
   |     -> Docker: postgres:18-alpine, cổng 5432 map ra cổng ngẫu nhiên
   v
DataSourceAutoConfiguration
   có JdbcConnectionDetails -> dùng nó, BỎ QUA spring.datasource.url/username/password
   |
   v
HikariCP -> Flyway chạy V1__orders.sql -> Hibernate validate schema -> repository, service...

Context đóng (thường là khi JVM test kết thúc): bean khác bị huỷ trước, container stop sau cùng
```

Ba hệ quả cần nhớ:

- **Không cần `spring.datasource.*` cho test.** `JdbcConnectionDetails` thắng mọi property kết nối. Cùng cơ chế "connection details" được Docker Compose dùng ở phần sau.
- **`@DataJpaTest` không thay `DataSource` này bằng H2.** Mặc định `@AutoConfigureTestDatabase(replace = Replace.NON_TEST)` chỉ thay `DataSource` không do test khai báo; connection details từ `@ServiceConnection` được coi là của test. Bản Spring Boot cũ phải viết thêm `replace = Replace.NONE`.
- **Mỗi context một container.** Container là bean, nên hai context khác nhau (một `@DataJpaTest`, một `@SpringBootTest`) mỗi cái có PostgreSQL riêng. Context nằm trong cache thì container cũng sống theo. Đây là thêm một lý do để giữ số context nhỏ như SB2.1.

<Check id="sb2.2.service-connection">Giải thích được chuỗi từ `@Bean @ServiceConnection` tới `DataSource`, vì sao không cần `spring.datasource.url` trong test, và vì sao số container bằng số context dùng nó.</Check>

### Docker Compose khi phát triển

Test đã có PostgreSQL. Còn khi bạn chạy ứng dụng trên máy để thử bằng `curl` hay frontend? Cách cũ: README ghi "chạy `docker compose up -d` trước", và `application.properties` ghi cứng URL, user, password khớp với file compose. Hai nơi phải sửa cùng nhau, và người mới hay quên bước đầu.

Module **`spring-boot-docker-compose`** gộp hai việc đó vào lúc khởi động:

```text
./mvnw spring-boot:run
  |
  1. Tìm compose.yaml (compose.yml, docker-compose.yaml...) trong thư mục làm việc
  2. Chạy "docker compose up" (bỏ qua nếu các service đã chạy sẵn)
  3. Chờ sẵn sàng: mặc định là mở được kết nối TCP tới cổng đã map
  4. Đọc từng container đang chạy: image "postgres" -> tạo JdbcConnectionDetails
     từ cổng map ra máy và POSTGRES_USER, POSTGRES_PASSWORD, POSTGRES_DB
  5. Khởi động ứng dụng như bình thường; DataSource dùng connection details đó
  ...
Ctrl+C
  6. Ứng dụng tắt -> "docker compose stop": container dừng nhưng KHÔNG bị xoá
```

| Thuộc tính | Mặc định | Ý nghĩa |
|---|---|---|
| `spring.docker.compose.enabled` | `true` | Tắt hẳn hỗ trợ Compose |
| `spring.docker.compose.lifecycle-management` | `start-and-stop` | `start-only` để container chạy tiếp sau khi app tắt; `none` để tự quản lý |
| `spring.docker.compose.stop.command` | `stop` | Đổi thành `down` để xoá container khi tắt (mất dữ liệu nếu không có volume) |
| `spring.docker.compose.skip.in-tests` | `true` | Không chạy Compose khi test; test dùng Testcontainers |

Dependency được khai báo `<optional>true</optional>`, và plugin Maven của Spring Boot loại nó khỏi file jar đóng gói (SB11): production không bao giờ tự chạy `docker compose`.

Spring Boot còn một cách khác cho máy dev: **Testcontainers lúc phát triển**. Một class `main` trong `src/test` gọi `SpringApplication.from(OrdersApplication::main).with(TestcontainersConfiguration.class)`, chạy bằng `./mvnw spring-boot:test-run`. Ứng dụng dùng đúng container bean của test.

| | Docker Compose | Testcontainers lúc phát triển |
|---|---|---|
| Khai báo service | `compose.yaml`, ai cũng đọc được, dùng được cả ngoài Java | Code Java trong `src/test` |
| Dữ liệu sau khi tắt app | Còn (container chỉ bị `stop`) | Mất (container bị xoá) |
| Cổng | Cố định, ví dụ 5442, nối `psql` hay DBeaver dễ | Ngẫu nhiên mỗi lần |
| Hợp với | Làm việc hằng ngày, có dữ liệu thử lâu dài, nhiều service (PostgreSQL, Redis, Kafka) | Muốn môi trường sạch mỗi lần, dùng lại đúng cấu hình của test |

Chọn một cho mỗi project. Lab sẽ cho thấy dùng cả hai cùng lúc sinh ra chuyện gì.

<Check id="sb2.2.docker-compose">Kể được Spring Boot làm gì với `compose.yaml` lúc khởi động và lúc tắt, vì sao Compose không chạy trong test, và so sánh được nó với `spring-boot:test-run`.</Check>

### MockMvc và RestTestClient

SB1.3 và SB2.1 gọi API bằng `MockMvcTester`: request không qua mạng, không có Tomcat, `DispatcherServlet` được gọi thẳng trên một servlet giả. Spring Framework 7 thêm **`RestTestClient`**, một client test có cùng API cho mọi "đích":

| Cách dựng | Đích | Khi nào |
|---|---|---|
| `@SpringBootTest` (MOCK) + `@AutoConfigureRestTestClient` | MockMvc bên dưới | Muốn API kiểu client nhưng không cần Tomcat |
| `@SpringBootTest(webEnvironment = RANDOM_PORT)` + `@AutoConfigureRestTestClient` | Tomcat thật, cổng ngẫu nhiên | Test qua HTTP thật |
| `RestTestClient.bindToController(...)` | Một controller, không có Spring Boot | Test rất nhỏ |
| `RestTestClient.bindToServer().baseUrl(...)` | Server bất kỳ đang chạy | Smoke test sau khi deploy |

Khác biệt quan trọng nhất không nằm ở API mà ở **thread**:

```text
MOCK (MockMvc)                                 RANDOM_PORT (Tomcat thật)
-----------------------------------------      ------------------------------------------------
thread main                                    thread main             thread http-nio-xxx-exec-1
  @Transactional test: BEGIN                     @Transactional test:    (Tomcat)
  mvc.post("/orders")                            BEGIN
    -> DispatcherServlet                         client.post("/orders") --HTTP--> DispatcherServlet
    -> OrderService.create (@Transactional:                                        OrderService.create
       THAM GIA transaction của test)                                              BEGIN ... COMMIT
  ROLLBACK -> đơn biến mất                       ROLLBACK (không có gì để huỷ)    đơn ĐÃ nằm trong DB
```

Với MockMvc, service tham gia transaction của test, nên rollback cuối test xoá mọi thứ. Với Tomcat thật, server xử lý request trong thread của nó, transaction riêng, commit thật; `@Transactional` trên test không có tác dụng gì với dữ liệu đó. Tài liệu Spring Boot ghi rõ điều này, và lab sẽ cho thấy nó.

| | `MockMvcTester` / `RestTestClient` trên MOCK | `RestTestClient` trên RANDOM_PORT |
|---|---|---|
| Đi qua | `DispatcherServlet`, filter Spring, Jackson, advice | Thêm Tomcat, socket HTTP, header thật |
| Exception không ai xử lý | Bay thẳng vào test dưới dạng `ServletException` | Thành `500` với body do `/error` của Spring Boot sinh: `timestamp`, `status`, `error`, `path` |
| Rollback bằng `@Transactional` | Có | Không, phải tự dọn dữ liệu |
| Persistence context mở suốt test | Có, nếu test `@Transactional` (che lỗi lazy loading) | Không, giống production |
| Tốc độ | Nhanh hơn | Chậm hơn, thêm một context nếu cấu hình khác |

<Callout kind="production">

Một quan hệ **lazy** giữa hai entity chỉ được tải khi code chạm vào nó, và chỉ tải được khi persistence context còn mở; `spring.jpa.open-in-view=false` (đã đặt trong lab) đóng nó ngay khi transaction của service kết thúc, thay vì giữ tới hết request. SB3.2 sẽ đi sâu vào hai cơ chế này. Một controller trả entity có quan hệ lazy. Bộ test tích hợp đặt `@Transactional` trên mọi class "để tự rollback" và gọi API qua MockMvc. Vì request chạy trong transaction của test, persistence context còn mở khi Jackson ghi JSON, nên quan hệ lazy được tải bình thường và test xanh. Trên production, transaction của service đã đóng trước khi Jackson chạy (`open-in-view=false`), và endpoint trả `500` với `LazyInitializationException`. Test qua `RANDOM_PORT`, không `@Transactional`, tái hiện đúng điều kiện production và bắt được lỗi này. Đây là lý do chiến lược bên dưới giữ ít nhất một nhóm test HTTP thật cho các endpoint quan trọng.

</Callout>

<Check id="sb2.2.mockmvc-vs-resttestclient">Giải thích được vì sao `@Transactional` rollback được với MockMvc nhưng không với `RANDOM_PORT`, và nêu được loại lỗi chỉ test HTTP thật mới bắt được.</Check>

### Chiến lược test cho một service Spring

J8.2 đã dựng kim tự tháp test (unit, integration, E2E) và tách test cần hạ tầng sang Failsafe. Đây là bản cụ thể cho một service Spring, với hai tầng giữa được chia nhỏ theo những gì SB2.1 và bài này dạy:

```text
                 /\        E2E: nhiều service, ngoài repo này
                /--\
               /HTTP\      @SpringBootTest(RANDOM_PORT) + RestTestClient: vài test cho đường chính
              /------\
             /Tích hợp\    @SpringBootTest (MOCK) + MockMvc: luồng qua nhiều tầng, MỘT lớp cha chung
            /----------\
           /   Slice    \  @WebMvcTest (hợp đồng HTTP), @DataJpaTest (truy vấn, mapping, ràng buộc)
          /--------------\
         /Unit test thuần \  domain, luật nghiệp vụ: không Spring, không Docker, phần lớn số test
        /__________________\
```

| Cần kiểm | Tầng | Lý do |
|---|---|---|
| `PurchaseOrder.pay()` từ chối đơn đã thanh toán | Unit | Logic thuần, không cần gì khác |
| Body thiếu `customer` trả `422`, không gọi service | `@WebMvcTest` | Chỉ tầng web liên quan; mock service |
| Lịch sử đơn sắp xếp đúng | `@DataJpaTest` + PostgreSQL thật | Hành vi phụ thuộc database |
| Migration chạy được, entity khớp schema | Mọi test có database (Flyway + `ddl-auto=validate`) | Tự động có khi context khởi động |
| Tạo, thanh toán, thanh toán lại trả `409` | Tích hợp (MOCK) | Qua controller, service, transaction, database |
| Hệ thống ngoài lỗi: client nhận `500` từ `/error`, đơn không được lưu | HTTP thật (`RANDOM_PORT`) | MockMvc không có trang lỗi của servlet container |
| Gọi service khác (SB7), gửi Kafka (SB9) | Mock ở tích hợp; test hợp đồng riêng | Không phụ thuộc hệ thống ngoài khi chạy CI |

Năm quy tắc giữ bộ test nhanh và đáng tin khi nó lớn lên:

1. **Một cấu hình cho mỗi tầng.** Một lớp cha cho test tích hợp, một cho test HTTP thật; mock hệ thống ngoài khai báo ở đó (SB2.1).
2. **Database thật cho mọi thứ chạm tới SQL.** Không H2, không mock repository trong test tích hợp.
3. **Tách test cần Docker như J8.2.** Đặt tên `*IT` (ví dụ `OrderHttpIT`) để Failsafe chạy chúng ở `./mvnw verify`, còn `./mvnw test` chỉ chạy unit test và `@WebMvcTest` trong vài giây. `spring-boot-starter-parent` đã cấu hình sẵn Failsafe, chỉ cần khai báo `maven-failsafe-plugin` trong `<build><plugins>`. Surefire và Failsafe chạy ở hai JVM khác nhau, nên mỗi bên có context cache riêng. Lab của bài giữ mọi class là `*Test` để một lệnh `./mvnw test` chạy hết và đếm context trong một log; project thật nên tách.
4. **Không dựa vào thứ tự hay rollback để cô lập dữ liệu.** Mỗi test tạo dữ liệu riêng (khách hàng riêng, id lấy từ response) hoặc tự dọn.
5. **Đo.** Thời gian bộ test và số context là chỉ số cần theo dõi như độ phủ (J8.3).

<Check id="sb2.2.test-strategy">Xếp được một yêu cầu kiểm thử bất kỳ của service Spring vào đúng tầng của kim tự tháp và giải thích vì sao không đặt nó ở tầng thấp hơn hay cao hơn.</Check>

### Khi gặp lỗi

<Callout kind="pitfall">

- `Could not find a valid Docker environment`: Docker Desktop chưa chạy. Mở nó rồi chạy lại.
- `Schema-validation: missing table [orders]`: Flyway chưa chạy. Thường do thiếu `spring-boot-starter-flyway`: chỉ có `flyway-core` thì Spring Boot 4 không bật auto-configuration của Flyway. Cũng kiểm tra file migration nằm trong `src/main/resources/db/migration`.

<Reveal title="Ba container cho một bộ test nhỏ là nhiều. Dùng chung một container cho mọi context được không?">

Được, bằng cách cho mọi context trỏ tới cùng một đối tượng container: khai báo nó là field `static` trong một interface, đánh dấu `@Container @ServiceConnection`, rồi đưa vào context bằng `@ImportTestcontainers` thay vì `@Bean`. Container khởi động một lần và dùng cho mọi context. Cái giá: các context giờ chia sẻ dữ liệu, nên việc dọn dữ liệu phải chặt hơn (`deleteAll` ở bước 8 sẽ xoá dữ liệu của context khác). Tài liệu Spring Boot cảnh báo thêm: nếu dùng `@Testcontainers` của JUnit để quản lý container, JUnit dừng container sau class, trong khi context vẫn nằm trong cache và lần sau dùng lại sẽ lỗi kết nối. Với bộ test cỡ vừa, gom số context (SB2.1) thường được lợi nhiều hơn và ít rủi ro hơn.

</Reveal>

<Reveal title="Có nên bật withReuse(true) để container sống qua nhiều lần chạy test?">

J8.3 đã nêu cái giá chung: dữ liệu của lần trước còn đó và Ryuk không dọn container. Với Spring Boot có thêm một bẫy: Flyway thấy `flyway_schema_history` đã ghi các migration, nên không chạy lại, và nếu bạn vừa sửa một file migration cũ trên máy, test chạy trên schema mà bộ migration hiện tại không còn tạo ra được. Muốn nhanh hơn trên máy dev, giảm số context trước, rồi cân nhắc `spring.testcontainers.beans.startup=parallel` khi có nhiều container.

</Reveal>

<Reveal title="Khi nào cần test HTTP thật nếu MockMvc đã đi qua controller?">

Khi điều bạn muốn kiểm nằm ngoài `DispatcherServlet`: cấu hình Tomcat (giới hạn kích thước body, nén), filter của servlet container, trang lỗi `/error` cho exception không được xử lý, serialization thật qua mạng, và quan trọng nhất là điều kiện transaction giống production như callout ở phần Kiến thức. Quy tắc gọn: mỗi endpoint quan trọng có một test HTTP thật cho đường chính; các nhánh lỗi chi tiết để ở `@WebMvcTest`.

</Reveal>

<Reveal title="Compose cho nhiều service (PostgreSQL, Redis, Kafka) thì cấu hình thế nào?">

Thêm service vào `compose.yaml`; Spring Boot nhận diện theo tên image (`redis`, `apache/kafka`...) và tạo connection details tương ứng. Image tự build hay qua registry riêng thì thêm nhãn `org.springframework.boot.service-connection: redis` cho container đó. Container không liên quan tới ứng dụng (ví dụ pgAdmin) thì gắn `org.springframework.boot.ignore: true`. Nếu một service khởi động lâu và cổng TCP mở trước khi nó thật sự sẵn sàng, khai báo `healthcheck` trong compose: `docker compose up --wait` mà Spring Boot gọi sẽ chờ tới khi container healthy.

</Reveal>
