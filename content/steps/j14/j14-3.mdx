### Virtual thread

**Virtual thread** (chính thức từ Java 21, JEP 444) là thread do JVM quản lý thay vì hệ điều hành. Nó vẫn là `java.lang.Thread`, có stack, có `ThreadLocal`, chạy code chặn bình thường. Khác biệt nằm ở cách chạy:

```text
 virtual thread:  VT1   VT2   VT3   VT4 ... VT10000      (hàng nghìn, mỗi cái vài trăm byte tới vài KB stack trên heap)
                   |     |                                 mount: chép stack lên carrier để chạy
                   v     v                                 unmount: khi chặn (sleep, đọc socket, lock),
 carrier thread:  [ForkJoinPool-1-worker-1] [worker-2] ... [worker-N]   N = số nhân CPU
                   |                         |
 OS thread:       thread hệ điều hành       thread hệ điều hành
```

Khi virtual thread gặp thao tác chặn như `Thread.sleep`, đọc socket, chờ `ReentrantLock` hay `BlockingQueue`, JVM **unmount** nó khỏi carrier thread và cho virtual thread khác chạy. Khi dữ liệu về, nó được mount lại, có thể trên một carrier khác. Một carrier phục vụ được rất nhiều virtual thread đang chờ I/O.

| | Platform thread | Virtual thread |
|---|---|---|
| Ánh xạ | 1:1 với thread hệ điều hành | M:N lên vài carrier thread |
| Tạo ra | Đắt, nên gom vào pool | Rẻ, tạo mới cho mỗi task, **không gom pool** |
| Số lượng thực tế | Vài trăm tới vài nghìn | Hàng triệu |
| Hợp với | Việc dùng CPU, số lượng ít | Nhiều việc chờ I/O đồng thời |
| Giới hạn đồng thời | Kích thước pool | Tự đặt bằng `Semaphore` nếu cần |

Virtual thread làm **tăng thông lượng** (số việc xử lý cùng lúc) chứ không làm từng việc nhanh hơn. Việc dùng CPU vẫn bị giới hạn bởi số nhân. Và giới hạn bây giờ chuyển xuống tài nguyên phía sau: 10.000 virtual thread cùng gọi database với pool 10 kết nối thì 9.990 thread chờ kết nối. Muốn giới hạn số lời gọi tới một hệ thống chậm, dùng `Semaphore`, không dùng pool thread.

**Pinning** (ghim) là khi virtual thread chặn nhưng không unmount được, giữ luôn carrier. Trên JDK 21 tới 23, chặn bên trong `synchronized` gây pinning, nên lời khuyên khi đó là đổi `synchronized` sang `ReentrantLock`. Từ JDK 24 (JEP 491), `synchronized` và `Object.wait()` không còn ghim. Các trường hợp còn ghim trên JDK 25: chặn khi đang ở trong code native (method `native` hoặc hàm ngoại gọi ngược vào Java), và chặn trong lúc nạp hay khởi tạo class. JFR vẫn có sự kiện `jdk.VirtualThreadPinned` cho các trường hợp này; thuộc tính `-Djdk.tracePinnedThreads` của JDK 21 đã bị bỏ.

Trong Spring Boot 3.2 trở lên, `spring.threads.virtual.enabled=true` cho Tomcat xử lý mỗi request trên một virtual thread thay vì pool mặc định 200 thread. Bài J9.3 đã hỏi nên dùng `HttpClient.sendAsync` hay `send`: với virtual thread, `send` đồng bộ chạy trên mỗi request một thread là đủ rẻ, và code đọc từ trên xuống; `sendAsync` vẫn hữu ích khi cần gộp kết quả của vài lời gọi song song.

Thông lượng tăng, nhưng database bắt đầu báo hết kết nối và độ trễ p99 tăng vọt: trước đây pool 200 thread của Tomcat vô tình giới hạn số truy vấn đồng thời, giờ giới hạn đó biến mất. ### Structured concurrency, vẫn là preview

Với executor, một task con có thể sống lâu hơn method đã tạo ra nó: method lỗi và trả về, nhưng task con vẫn chạy, không ai huỷ. **Structured concurrency** gắn vòng đời các task con vào một khối code: khối kết thúc thì mọi task con đã kết thúc.

```text
try (var scope = StructuredTaskScope.open()) {      mở scope
    fork(price)  ---- 1.000 ms ----------x  bị huỷ (interrupt)
    fork(stock)  -- 100 ms --> lỗi  -----'  scope huỷ các nhánh còn lại
    scope.join()                             ném FailedException sau ~100 ms
}                                            close(): chắc chắn không còn task con nào chạy
```

**Trạng thái, kiểm tra ngày 03/10/2026:**

| JDK | JEP | Trạng thái | Thay đổi đáng chú ý |
|---|---|---|---|
| 21 tới 24 | 453, 462, 480, 499 | Preview | API cũ, tạo scope bằng constructor như `ShutdownOnFailure` |
| 25 | 505 | Preview lần 5 | `StructuredTaskScope.open()`, `Joiner`; `join()` ném `StructuredTaskScope.FailedException` |
| 26 | 525 | Preview lần 6 | `allSuccessfulOrThrow()` trả list; đổi tên `anySuccessfulResultOrThrow` thành `anySuccessfulOrThrow` |
| 27 | 533 | Preview lần 7 | Thêm tham số kiểu thứ ba cho exception; `join()` mặc định ném `ExecutionException`; bỏ `FailedException`, `awaitAll()` |

Bài này chạy trên JDK 25. Theo Javadoc của JDK 27 và JEP 533, code của lab **không biên dịch được trên JDK 27** vì `FailedException` đã bị bỏ; điều này chưa được chạy thử trên máy kiểm chứng, vốn không có JDK 27. API còn đổi qua mỗi phiên bản, nên đừng dùng nó trong code production. Hiểu ý tưởng ngay bây giờ vẫn có ích: cùng một cấu trúc (mở scope, fork, join, huỷ khi lỗi) bạn viết được bằng executor và `CompletableFuture` ở J11.2, chỉ dài hơn và dễ sót việc huỷ.

Code dùng preview phải biên dịch và chạy với `--enable-preview`. File `.class` sinh ra mang minor version `65535` và chỉ chạy được trên đúng JDK feature release đã biên dịch nó.

### Deadlock

**Deadlock** xảy ra khi các thread chờ khoá của nhau theo một vòng tròn. Cần đủ bốn điều kiện cùng lúc: khoá độc quyền, giữ khoá này trong khi chờ khoá khác, không ai bị cướp khoá, và có vòng chờ. Phá một điều kiện là hết deadlock.

```text
transfer-A-to-B: giữ khoá A ----chờ khoá B---->\
                      ^                         \
                      |                          v
                 chờ khoá A <---- giữ khoá B : transfer-B-to-A
```

| Cách phòng | Phá điều kiện nào | Ghi chú |
|---|---|---|
| Thứ tự lấy khoá cố định, ví dụ theo id tài khoản | Vòng chờ | Đơn giản, hiệu quả nhất khi biết trước các khoá |
| `tryLock(timeout)`, không được thì nhả hết và thử lại | Không cướp được khoá (tự nhả) | Cần thêm thời gian chờ ngẫu nhiên để hai bên không thử lại cùng nhịp |
| Không gọi code lạ (callback, listener, service khác) khi đang giữ khoá | Giữ và chờ | Code lạ có thể lấy khoá bạn không biết |
| Giảm số khoá, dùng atomic hoặc collection đồng thời | Khoá độc quyền | |

JVM tự phát hiện được vòng chờ giữa các monitor (`synchronized`) và các khoá trong `java.util.concurrent.locks`. Bạn lấy kết quả bằng **thread dump**: `jcmd <pid> Thread.print`, hoặc `jstack <pid>` (công cụ cũ hơn, cùng nội dung). Từ trong code, `ThreadMXBean.findDeadlockedThreads()` trả về id các thread đang deadlock. JVM **không** phát hiện được: deadlock với khoá dòng trong database, task chờ một task khác trong cùng một pool đã đầy (thread starvation deadlock), và vòng chờ qua mạng giữa hai service.

<Check id="j14.3.deadlock-conditions">Kể được bốn điều kiện của deadlock, hai cách phòng, và những loại deadlock mà thread dump không tự báo được.</Check>

</Knowledge>

### 1. Virtual thread với việc chờ I/O và việc dùng CPU

10.000 task, mỗi task `sleep(100)` đóng vai một lời gọi database. Pool 200 platform thread bằng đúng mặc định của Tomcat. Sau đó 200 task tính toán thuần CPU.

<Terminal where="mac" title="Tạo src/VirtualDemo.java">

```bash
cd ~/masteva-j14
cat > src/VirtualDemo.java <<'EOF'
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.stream.IntStream;

public class VirtualDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread.ofVirtual().start(() -> System.out.println("virtual: " + Thread.currentThread())).join();

        int tasks = 10_000;
        time("I/O, pool 200 platform", tasks, Executors.newFixedThreadPool(200), VirtualDemo::io);
        time("I/O, virtual mỗi task", tasks, Executors.newVirtualThreadPerTaskExecutor(), VirtualDemo::io);

        int cores = Runtime.getRuntime().availableProcessors();
        time("CPU, pool " + cores + " platform", 200, Executors.newFixedThreadPool(cores), VirtualDemo::cpu);
        time("CPU, virtual mỗi task", 200, Executors.newVirtualThreadPerTaskExecutor(), VirtualDemo::cpu);
    }

    static void time(String label, int tasks, ExecutorService executor, Runnable work) {
        long t0 = System.nanoTime();
        try (executor) {   // close() chờ mọi task xong
            IntStream.range(0, tasks).forEach(i -> executor.submit(work));
        }
        long ms = (System.nanoTime() - t0) / 1_000_000;
        System.out.printf("%-26s %,6d task  %,6d ms%n", label, tasks, ms);
    }

    static void io() {
        try {
            Thread.sleep(100);   // đóng vai một lời gọi database hay HTTP mất 100 ms
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    static long sink;

    static void cpu() {
        long x = 0;
        for (int i = 0; i < 20_000_000; i++) {
            x += i % 7;
        }
        sink += x;
    }
}
EOF
javac -d out src/*.java && java -cp out VirtualDemo
```

### 2. Pinning: JDK 21 và JDK 25

100 virtual thread, mỗi cái giữ một khoá riêng (không ai tranh khoá) và `sleep(100)` bên trong `synchronized`.

<Terminal where="mac" title="Tạo src/Pinning.java">

```bash
cd ~/masteva-j14
cat > src/Pinning.java <<'EOF'
import java.util.concurrent.Executors;

public class Pinning {
    public static void main(String[] args) {
        int tasks = 100;
        long t0 = System.nanoTime();
        try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
            for (int i = 0; i < tasks; i++) {
                Object lock = new Object();   // mỗi task một khoá riêng: không ai tranh khoá
                executor.submit(() -> {
                    synchronized (lock) {
                        sleep(100);           // blocking khi đang giữ monitor
                    }
                });
            }
        }
        long ms = (System.nanoTime() - t0) / 1_000_000;
        System.out.printf("Java %s: %d virtual thread, mỗi cái sleep 100 ms trong synchronized: %,d ms%n",
                Runtime.version().feature(), tasks, ms);
    }

    static void sleep(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
EOF
javac -d out src/*.java && java -cp out Pinning
```

### 3. Structured concurrency với --enable-preview

Code preview nằm riêng trong thư mục `preview`, để lệnh `javac -d out src/*.java` của các bước khác không cần cờ preview.

<Terminal where="mac" title="Tạo preview/StructuredCheckout.java">

```bash
mkdir -p ~/masteva-j14/preview && cd ~/masteva-j14
cat > preview/StructuredCheckout.java <<'EOF'
import java.util.concurrent.StructuredTaskScope;
import java.util.concurrent.StructuredTaskScope.Subtask;

public class StructuredCheckout {
    record Quote(long price, int stock) {}

    static long price(String sku) throws InterruptedException {
        try {
            Thread.sleep(1_000);
            return 250_000;
        } catch (InterruptedException e) {
            System.out.println("price: bị huỷ sau khi stock lỗi");
            throw e;
        }
    }

    static int stock(String sku) throws InterruptedException {
        Thread.sleep(100);
        if (sku.equals("SKU-HET")) {
            throw new IllegalStateException("kho không phản hồi");
        }
        return 7;
    }

    static Quote quote(String sku) throws InterruptedException {
        try (var scope = StructuredTaskScope.open()) {
            Subtask<Long> price = scope.fork(() -> price(sku));
            Subtask<Integer> stock = scope.fork(() -> stock(sku));
            scope.join();   // chờ cả hai; một nhánh lỗi thì huỷ nhánh kia và ném FailedException
            return new Quote(price.get(), stock.get());
        }
    }

    public static void main(String[] args) throws InterruptedException {
        for (String sku : new String[] {"SKU-1", "SKU-HET"}) {
            long t0 = System.nanoTime();
            try {
                System.out.println(sku + ": " + quote(sku));
            } catch (StructuredTaskScope.FailedException e) {
                System.out.println(sku + ": lỗi " + e.getCause());
            }
            System.out.printf("%s: ~%d ms%n", sku, Math.round((System.nanoTime() - t0) / 1e8) * 100);
        }
    }
}
EOF
java preview/StructuredCheckout.java 2>&1 | head -4
```

### 4. Tạo một deadlock và tìm nó

Hai lệnh chuyển tiền chạy cùng lúc theo hai chiều ngược nhau, mỗi lệnh khoá tài khoản nguồn trước rồi tới tài khoản đích. Chương trình có thêm một thread `deadlock-watchdog` dùng `ThreadMXBean` để tự phát hiện, và hai chế độ đã sửa: `ordered` và `trylock`.

<Terminal where="mac" title="Tạo src/Deadlock.java">

```bash

cat > src/Deadlock.java <<'EOF'
import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class Deadlock {
    static final class Account {
        final String id;
        long balance;
        final ReentrantLock lock = new ReentrantLock();

        Account(String id, long balance) {
            this.id = id;
            this.balance = balance;
        }
    }

    // Cách 1: khoá theo thứ tự tham số. Hai chiều chuyển ngược nhau là đủ để kẹt.
    static void transferNaive(Account from, Account to, long amount) {
        synchronized (from) {
            pause(50);
            synchronized (to) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }

    // Cách 2: luôn khoá tài khoản có id nhỏ hơn trước. Không có vòng chờ.
    static void transferOrdered(Account from, Account to, long amount) {
        Account first = from.id.compareTo(to.id) < 0 ? from : to;
        Account second = first == from ? to : from;
        synchronized (first) {
            pause(50);
            synchronized (second) {
                from.balance -= amount;
                to.balance += amount;
            }
        }
    }

    // Cách 3: tryLock có timeout. Không lấy được khoá thứ hai thì nhả khoá đầu và thử lại.
    static void transferTryLock(Account from, Account to, long amount) throws InterruptedException {
        while (true) {
            if (from.lock.tryLock(100, TimeUnit.MILLISECONDS)) {
                try {
                    pause(50);
                    if (to.lock.tryLock(100, TimeUnit.MILLISECONDS)) {
                        try {
                            from.balance -= amount;
                            to.balance += amount;
                            return;
                        } finally {
                            to.lock.unlock();
                        }
                    }
                } finally {
                    from.lock.unlock();
                }
            }
            System.out.println(Thread.currentThread().getName() + ": không lấy được khoá, thử lại");
            pause((long) (Math.random() * 100));
        }
    }

    public static void main(String[] args) throws InterruptedException {
        String mode = args.length > 0 ? args[0] : "naive";
        Account a = new Account("A", 1_000_000);
        Account b = new Account("B", 1_000_000);
        System.out.println("PID " + ProcessHandle.current().pid() + ", mode=" + mode);

        Thread t1 = Thread.ofPlatform().name("transfer-A-to-B").start(() -> transfer(mode, a, b, 100_000));
        Thread t2 = Thread.ofPlatform().name("transfer-B-to-A").start(() -> transfer(mode, b, a, 200_000));
        startWatchdog();
        t1.join();
        t2.join();
        System.out.println("xong: A=" + a.balance + ", B=" + b.balance);
    }

    static void transfer(String mode, Account from, Account to, long amount) {
        try {
            switch (mode) {
                case "ordered" -> transferOrdered(from, to, amount);
                case "trylock" -> transferTryLock(from, to, amount);
                default -> transferNaive(from, to, amount);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    // Tự phát hiện deadlock từ trong ứng dụng, giống điều jcmd Thread.print làm từ bên ngoài.
    static void startWatchdog() {
        Thread.ofPlatform().name("deadlock-watchdog").daemon().start(() -> {
            ThreadMXBean mx = ManagementFactory.getThreadMXBean();
            while (true) {
                pause(1_000);
                long[] ids = mx.findDeadlockedThreads();
                if (ids != null) {
                    for (ThreadInfo info : mx.getThreadInfo(ids)) {
                        System.out.println("watchdog: " + info.getThreadName()
                                + " chờ " + info.getLockName() + " do " + info.getLockOwnerName() + " giữ");
                    }
                    return;
                }
            }
        });
    }

    static void pause(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}
EOF
javac -d out src/*.java
```

<DeepDive>

<Reveal title="Thread dump của service dùng virtual thread không thấy request nào đang chạy. Chúng đi đâu?">

`jcmd <pid> Thread.print` chỉ in platform thread, gồm cả carrier; virtual thread đang chờ I/O không nằm trên carrier nào nên không xuất hiện. Dùng `jcmd <pid> Thread.dump_to_file -format=json /tmp/threads.json`: file này liệt kê cả virtual thread, nhóm theo executor hoặc scope tạo ra chúng. Trên máy kiểm chứng, một chương trình có ba virtual thread đang ngủ cho 0 dòng trong `Thread.print` và đủ 3 trong file JSON.

</Reveal>

<Reveal title="Có nên dùng ThreadLocal để cache object đắt (như SimpleDateFormat) trên virtual thread?">

Không. Cache trong `ThreadLocal` có lợi vì platform thread trong pool sống lâu và được dùng lại. Virtual thread được tạo mới cho mỗi task, nên mỗi task tạo một object mới, rồi giữ nó tới khi thread kết thúc; một triệu virtual thread là một triệu bản. Dùng object bất biến và thread-safe như `DateTimeFormatter`, hoặc một pool object riêng. `ThreadLocal` để truyền ngữ cảnh ngắn (request id cho log, như MDC ở SB8) thì vẫn ổn.

</Reveal>

<Reveal title="Task trong pool chờ một task khác cùng pool: vì sao treo mà thread dump không báo deadlock?">

Pool 4 thread, mỗi task `submit` thêm một task con rồi `get()` kết quả. Khi 4 task cha chiếm đủ 4 thread, task con nằm trong hàng đợi mãi, task cha chờ mãi. Không thread nào giữ khoá của thread nào, chúng chỉ ở `WAITING` trên `FutureTask.get`, nên JVM không thấy vòng khoá. Dấu hiệu trong thread dump: mọi thread của pool cùng chờ ở một chỗ. Sửa bằng cách không chờ task con trong cùng pool: dùng pool riêng, `thenCompose`, hoặc virtual thread.

</Reveal>

<Reveal title="Vì sao service treo trên production thường không phải deadlock khoá Java?">

Phần lớn "treo" là chờ bên ngoài: lời gọi HTTP không có timeout, pool kết nối database cạn, khoá dòng trong database (SB3). Thread dump vẫn là công cụ đầu tiên: lấy ba bản cách nhau vài giây. Thread `RUNNABLE` trong `SocketInputStream.read` ở cả ba bản là chờ mạng; `TIMED_WAITING` trong `HikariPool.getConnection` là cạn kết nối; `BLOCKED` thành vòng là deadlock. So các bản với nhau để thấy cái gì đứng yên.

</Reveal>

<Callout kind="ai">

Nhờ AI đọc một thread dump dài: dán phần liên quan và hỏi thread nào giữ khoá nào, nhóm thread nào cùng chờ một chỗ. AI hay khẳng định virtual thread làm mọi thứ nhanh hơn, vẫn khuyên đổi `synchronized` sang `ReentrantLock` vì pinning dù bạn đã ở JDK 24 trở lên, và viết code `StructuredTaskScope` theo API của một bản preview khác (`ShutdownOnFailure` của JDK 21, hay `ExecutionException` của JDK 27). Kiểm tra lại: hỏi rõ JDK nào, biên dịch thử với đúng JDK đó, và đo trên tải giống thật.
