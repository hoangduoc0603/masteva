<Goal>

D20.1 sao lưu một database đứng một mình. Một ứng dụng trên Kubernetes còn có manifest, Secret, ConfigMap, volume, và một cụm database do operator quản lý. Bài này sao lưu cả thứ đó theo cách khôi phục được ở một cụm khác; D20.3 khôi phục nó. Học xong, bạn giải thích được:

- etcd snapshot, Velero và backup của database mỗi cái trả lời câu hỏi nào, và vì sao một hệ thống thật cần cả ba.
- Velero lấy dữ liệu volume bằng snapshot hay bằng file-system backup, và vì sao trên cụm không có driver CSI hỗ trợ snapshot thì chỉ còn cách thứ hai.
- Vì sao database có operator không đi qua Velero, và bản Velero phải loại những gì của nó.
- Vì sao "bản backup nằm ở đâu" phải là một con số kỹ thuật, không phải một lời hứa.

</Goal>

### Ba loại backup, ba câu hỏi

K4.5 đã chụp etcd snapshot và chỉ ra nó chứa mọi object nhưng không chứa dữ liệu trong volume. K7.4 và D20.1 đã sao lưu PostgreSQL. Thứ còn thiếu là một công cụ sao lưu **theo namespace**, lấy được cả object lẫn dữ liệu volume, và khôi phục được sang **cụm khác**. Đó là Velero.

| | etcd snapshot (K4.5) | Velero | Backup của database (CNPG, D20.1) |
|---|---|---|---|
| Lấy gì | Toàn bộ kho của một cụm tại một revision | Object Kubernetes đã chọn (theo namespace, loại, label), cộng dữ liệu volume nếu yêu cầu | Dữ liệu của database: base backup cộng WAL |
| Khôi phục về đâu | Đúng cụm đó (hoặc một cụm dựng lại y hệt), cả cụm một lúc | Cụm bất kỳ có Velero trỏ cùng object storage; chọn được namespace, đổi được tên namespace | Một cụm database mới, ở bất kỳ đâu đọc được object storage |
| Nhất quán | Nhất quán cho mọi object | Mỗi object một thời điểm; volume đọc khi đang chạy | Nhất quán theo giao dịch, tới từng thời điểm (PITR) |
| Trả lời câu hỏi | "etcd hỏng, quorum mất, cụm chết vì control plane" | "Mất một namespace, mất cả cụm, cần dựng lại ứng dụng ở cụm khác" | "Mất database, xoá nhầm dữ liệu, cần quay về 10:42" |
| Không dùng cho | Xoá nhầm một namespace (quay cả cụm về quá khứ là quá tay) | Database đang ghi (bản chép file của PostgreSQL đang chạy chưa chắc khởi động được) | Manifest, Secret, volume của phần còn lại |

Ba loại không thay nhau. Một kế hoạch DR cho cụm Kubernetes thường gồm: manifest trong Git (D13) để dựng lại phần stateless, Velero cho thứ không nằm trong Git (Secret sinh ra lúc chạy, volume của ứng dụng, object do người tạo bằng tay), backup của database cho database, và etcd snapshot cho chính control plane của cụm tự dựng.

<Check id="d17.2.ba-loai-backup">So sánh được etcd snapshot, Velero và backup của database theo thứ được lấy, nơi khôi phục được, mức nhất quán và câu hỏi mỗi loại trả lời, và chọn đúng loại cho ba tình huống: mất quorum etcd, xoá nhầm một namespace, xoá nhầm một bảng.</Check>

### Velero hoạt động thế nào

Velero là một controller chạy trong cụm (namespace `velero`), cộng một CLI `velero` trên máy bạn. Bài dùng bản 1.18; Velero 1.18 mới được thử tới Kubernetes 1.35 (README của dự án), lab chạy Kubernetes 1.37 nằm ngoài dải đã thử, và các bước của bài chạy được trên 1.37. Dự án chuyển từ `vmware-tanzu/velero` sang tổ chức `velero-io` trên GitHub, nhiều tài liệu và câu trả lời cũ còn trỏ về tên cũ.

```text
  velero backup create shop-1 --include-namespaces shop
        │  (tạo object Backup)
        ▼
  ┌─────────────── cụm A ───────────────┐            ┌──── object storage (site khác) ────┐
  │ velero server                        │  tarball   │ velero/backups/shop-1/             │
  │  1. liệt kê object qua API server    ├──────────► │   shop-1.tar.gz  (mọi object JSON) │
  │  2. ghi từng object ra JSON          │            │   shop-1-logs.gz, ...              │
  │ node-agent (DaemonSet, mỗi node)     │  Kopia     │ velero/kopia/shop/                 │
  │  3. đọc file trong volume của pod    ├──────────► │   (kho dữ liệu volume, khử trùng   │
  │     qua /var/lib/kubelet/pods        │            │    lặp, mã hoá)                    │
  └──────────────────────────────────────┘            └──────────────┬─────────────────────┘
                                                                     │ đồng bộ mỗi phút
  ┌─────────────── cụm B ───────────────┐                            │
  │ velero server (BSL chỉ đọc)          │ ◄──────────────────────────┘
  │  velero restore create --from-backup shop-1
  │  4. tạo lại object theo thứ tự: CRD, Namespace, StorageClass, PV, PVC, Role,
  │     ServiceAccount, RoleBinding, Secret, ConfigMap, Pod, ReplicaSet, Service,
  │     rồi mọi loại còn lại theo thứ tự chữ cái
  │  5. pod có volume cần khôi phục: chèn init container chờ node-agent chép dữ liệu xong
  └──────────────────────────────────────┘
```

Các khái niệm cần cho lab:

- **BackupStorageLocation** (BSL): bucket mà Velero ghi backup vào. Hai cụm trỏ cùng một BSL thì cụm B thấy được backup của cụm A sau lần đồng bộ kế tiếp (mặc định mỗi phút). BSL ở cụm khôi phục nên đặt `accessMode: ReadOnly`, để không có thao tác nào ở đó xoá nhầm backup của cụm A.
- **Dữ liệu volume** có hai đường. **Snapshot**: Velero gọi driver CSI hoặc API của cloud chụp ổ đĩa; nhanh và nhất quán ở mức đĩa, nhưng snapshot thường chỉ dùng được trong cùng nhà cung cấp, cùng vùng. **File-system backup** (FSB): node-agent đọc từng file trong volume đang mount và đẩy lên object storage bằng **Kopia** (công cụ sao lưu có khử trùng lặp và mã hoá); chậm hơn, không nhất quán tại một thời điểm, nhưng khôi phục được sang bất kỳ cụm nào. Cụm kind dùng `local-path` không có snapshot, nên lab dùng FSB. Tài liệu Velero cũng khuyên FSB khi chuyển giữa vùng hoặc giữa nhà cung cấp.
- **Chọn volume nào**: mặc định FSB là opt-in, pod phải có annotation `backup.velero.io/backup-volumes: <tên volume>`. Cờ `--default-volumes-to-fs-backup` đảo thành opt-out.
- **Hook**: lệnh chạy trong pod trước hoặc sau khi sao lưu (`pre.hook.backup.velero.io/command`), ví dụ đóng băng file system hay flush ứng dụng để bản FSB nhất quán hơn. Có cả hook khi khôi phục.
- **Khôi phục không phá huỷ**: object đã tồn tại ở cụm đích thì bị bỏ qua (trừ ServiceAccount được gộp), trừ khi đặt `--existing-resource-policy update`.

Một chi tiết bảo mật: Kopia mã hoá dữ liệu volume bằng một mật khẩu kho mà Velero sinh mặc định trong Secret `velero-repo-credentials`. Tài liệu ghi rõ khoá này giống nhau cho mọi kho, nên ai đọc được bucket là giải mã được; production đặt mật khẩu riêng trước lần backup đầu, và cất mật khẩu đó ở nơi cụm DR lấy được.

<Check id="d17.2.velero-co-che">Mô tả được đường đi của một lần Velero sao lưu và khôi phục (tarball object, Kopia cho volume, đồng bộ BSL, thứ tự khôi phục, init container chờ dữ liệu), phân biệt được snapshot với file-system backup và nói được khi nào chỉ dùng được cái sau.</Check>

### Database đi đường riêng

Velero lấy được file trong PVC của PostgreSQL, nhưng đó là bản chép file của một database **đang ghi**: không nhất quán tại một thời điểm, không có WAL đi kèm, có thể không khởi động được, và không có PITR. Với database có operator, đường đúng là backup của chính operator (K7.4), và lúc khôi phục là một object `Cluster` mới với `bootstrap.recovery`. Vì vậy bản Velero của bài **loại trừ** mọi thứ CNPG quản lý:

- Object `Cluster`, `Backup`, `ScheduledBackup` bị loại bằng `--exclude-resources`. Nếu để Velero khôi phục object `Cluster` cũ, operator ở cụm B thấy một Cluster chưa có PVC nào và dựng nó theo `bootstrap.initdb` của bản gốc: một database **trống** mang đúng tên database cũ. D20.3 cho thấy Cluster đó vẫn báo sẵn sàng.
- Object mà operator và plugin sinh ra (pod, PVC, Service, các Secret chứng chỉ, Role của plugin) mang label `app.kubernetes.io/managed-by` là `cloudnative-pg` hoặc `plugin-barman-cloud`; bộ chọn `--selector 'app.kubernetes.io/managed-by notin (cloudnative-pg,plugin-barman-cloud)'` bỏ chúng. Lease mà instance manager dùng để chọn primary chỉ mang label `cnpg.io/cluster`, nên được loại riêng bằng `--exclude-resources`. Operator ở cụm B sẽ tự tạo lại những thứ nó cần.
- Object `ObjectStore` của plugin Barman Cloud và Secret chứa khoá S3 **được** sao lưu: cụm B cần chúng để đọc backup.

Bên database cũng có hai chỗ phải tính trước, cả hai đều nằm trong tài liệu "Recovery" của CNPG:

- **Secret mật khẩu ứng dụng.** Operator không sao lưu Secret. Database khôi phục mang theo role `shop` với mật khẩu cũ; nếu cụm B sinh một Secret mới với mật khẩu ngẫu nhiên, ứng dụng không đăng nhập được. Lab đặt mật khẩu trong một Secret do bạn quản lý (`shop-db`), khai nó ở `bootstrap.initdb.secret` lúc tạo và ở `bootstrap.recovery.secret` lúc khôi phục; Velero mang Secret đó sang.
- **Thư mục WAL của cụm mới.** Cụm khôi phục tiếp tục đẩy WAL vào cùng bucket thì phải dùng `serverName` khác; trùng thư mục của cụm gốc thì operator dừng với lỗi `Expected empty archive`, vì ghi chồng lên sẽ làm hỏng chính bản backup vừa dùng.

<Check id="d17.2.database-duong-rieng">Giải thích được vì sao không khôi phục database bằng bản chép file của Velero, vì sao phải loại object `Cluster` khỏi bản Velero và điều gì xảy ra nếu không loại, và kể được hai chỗ phải tính trước khi khôi phục CNPG sang cụm khác (Secret mật khẩu, `serverName`).</Check>

### Chuẩn bị

Bài dựng từ đầu hai cụm kind một node, `d20-a` (cụm chính) và `d20-b` (cụm DR), cùng một **SeaweedFS** chạy ngoài cả hai cụm làm object storage ở "site khác". D20.3, D20.4 và D20.5 dùng tiếp hai cụm này. Cần Docker Desktop, `kind`, `kubectl` (1.36 hay 1.37 đều được), `curl`. Cổng dùng, chỉ nghe trên `127.0.0.1`: **9902** (S3 của SeaweedFS), **9910** và **9911** (API server của hai cụm).

**Profile máy.** Hai cụm kind một node cùng cert-manager, CloudNativePG, plugin Barman Cloud, Velero với node-agent, một instance PostgreSQL (giới hạn 256 MiB) và ứng dụng: theo `docker stats` ở cuối bài, node cụm A khoảng 1,9 GiB, node cụm B khoảng 1,1 GiB, SeaweedFS khoảng 300 MiB, tổng khoảng 3,3 GiB; một phần là page cache của các node nên con số dao động vài trăm MiB giữa các lần chạy. Đĩa của Docker cần khoảng 6 GB trống. Lần đầu, mỗi node kéo khoảng 600 MB image (cert-manager, operator, plugin, PostgreSQL, Velero), nên bước 2 và 3 mất 5 tới 15 phút tuỳ mạng. Máy 8 GB: đặt Docker 5 GB, dừng mọi VM và cụm khác, đóng trình duyệt và ứng dụng nặng trong lúc làm; macOS chỉ còn khoảng 3 GB nên máy sẽ chậm.

Ba điều lab làm cho gọn mà production không làm: hai "site" là hai container trên cùng một máy, chung một mạng Docker; một SeaweedFS dùng chung cho cả hai cụm, không nhân bản; và khoá S3 nằm trong một file trên máy bạn.

- Danh sách có object Namespace của mọi namespace: Velero áp `--selector` lên cả object Namespace, và `notin` khớp mọi namespace không mang label đó. Chỉ object Namespace được lấy, không kèm tài nguyên bên trong; D20.3 khôi phục với `--include-namespaces shop` nên các namespace đó không được tạo ở cụm B.
- `Pod Volume Backups - kopia` có đúng một volume, `uploads`, đã `Completed`. Nếu dòng này ghi `<none included>`, mở phần `Warnings` của `velero backup describe`: lý do thường gặp là volume kiểu `hostPath` hoặc pod thiếu annotation.

<DeepDive>

<Reveal title="Velero có thay được etcd snapshot cho cụm tự dựng không?">

Không. Velero đọc object qua API server, nên cần một API server đang chạy; khi etcd mất quorum hay hỏng dữ liệu, không có API server nào để Velero hỏi, và cũng không có API server nào để khôi phục vào. Velero cũng không lấy được những thứ nằm ngoài API mà một cụm cần để tự đứng được, như chứng chỉ trong `/etc/kubernetes/pki` và cấu hình kubelet trên từng node (K4.5). Hai công cụ bổ sung cho nhau: etcd snapshot cứu control plane, Velero cứu ứng dụng; với cụm do cloud quản lý, bạn không chạm được etcd, nên Velero cùng Git là đường còn lại.

</Reveal>

<Reveal title="File-system backup đọc volume đang ghi. Dữ liệu có nhất quán không?">

Không nhất quán tại một thời điểm: Kopia đọc từng file theo thứ tự, ứng dụng vẫn ghi trong lúc đó, nên bản backup có thể chứa file A của giây thứ 1 và file B của giây thứ 5. Với file độc lập như ảnh tải lên, điều đó chấp nhận được. Với dữ liệu mà nhiều file phải khớp nhau (database, chỉ mục tìm kiếm), dùng hook trước khi sao lưu để đóng băng ghi (`fsfreeze`, lệnh flush của ứng dụng), dùng snapshot CSI nếu hạ tầng có, hoặc tốt hơn là công cụ sao lưu riêng của phần mềm đó, như bài đã làm với PostgreSQL.

</Reveal>
