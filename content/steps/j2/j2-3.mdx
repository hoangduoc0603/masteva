<Goal>

Dùng các tính năng Java hiện đại (từ Java 14 tới 21) để viết code mô hình dữ liệu ngắn và an toàn hơn: record cho dữ liệu bất biến, enum cho tập giá trị cố định, switch expression và pattern matching để rẽ nhánh theo kiểu và nội dung, text block cho chuỗi nhiều dòng. Học xong bài này, bạn giải thích được:

- Một record tự có những gì, và kiểm tra dữ liệu đầu vào của nó ở đâu.
- Vì sao lưu `ordinal()` của enum vào database làm dữ liệu cũ đổi nghĩa khi ai đó thêm một hằng.
- Vì sao thêm một hằng vào enum làm code ở nơi khác **không biên dịch được nữa**, và vì sao đó là điều tốt.
- Vì sao một switch trên sealed interface không cần `default`.

</Goal>

<Knowledge>

J2.2 đọc log truy cập bằng mảng `String[]` và chỉ số: `parts[1]` là method, `parts[3]` là status. Bài này mô hình hoá cùng dữ liệu đó bằng kiểu, để trình biên dịch bắt lỗi thay cho bạn. Mỗi dòng log vẫn có dạng `2026-10-03T09:00:01Z GET /api/orders 200 35`.

### Record: lớp dữ liệu bất biến trong một dòng

Để giữ một dòng log đã tách, cách cũ là viết một class với bốn field `private final`, một constructor, bốn getter, rồi `equals`, `hashCode` và `toString`: khoảng 50 dòng mà mọi dòng đều đoán được. Sửa thêm một field là phải nhớ sửa cả năm chỗ.

**Record** (chính thức từ Java 16) khai báo một lớp dữ liệu bất biến bằng danh sách **thành phần** (component) của nó. Trình biên dịch sinh phần còn lại:

| Bạn viết | Trình biên dịch sinh |
|---|---|
| `record LogEntry(String method, String path, int status, int millis) {}` | 4 field `private final` cùng tên |
| | **Canonical constructor** nhận đủ 4 tham số theo đúng thứ tự |
| | Accessor `method()`, `path()`, `status()`, `millis()`, không có tiền tố `get` |
| | `equals` và `hashCode` tính theo mọi thành phần |
| | `toString` dạng `LogEntry[method=GET, path=/api/orders, status=200, millis=35]` |

`hashCode` là mã băm mà `HashMap` dùng để tìm khoá; J3 học kỹ cặp `equals` và `hashCode`. Đoạn sau tạo hai `LogEntry` cùng nội dung:

```java
record LogEntry(String method, String path, int status, int millis) {}

void main() {
    LogEntry a = new LogEntry("GET", "/api/orders", 200, 35);
    LogEntry b = new LogEntry("GET", "/api/orders", 200, 35);

    IO.println(a);
    IO.println("status = " + a.status());
    IO.println("a == b      " + (a == b));
    IO.println("a.equals(b) " + a.equals(b));
}
```

Kết quả:

```text
LogEntry[method=GET, path=/api/orders, status=200, millis=35]
status = 200
a == b      false
a.equals(b) true
```

`a` và `b` là hai đối tượng, nên `==` ra `false`; `equals` do trình biên dịch sinh so từng thành phần nên ra `true`. Với một class thường không tự viết `equals`, dòng cuối cũng ra `false`, vì `equals` mặc định so tham chiếu như `==`.

Record tự sinh constructor, nhưng bạn vẫn kiểm tra được dữ liệu đầu vào bằng **compact constructor**: viết tên record rồi thân `{ }`, không có danh sách tham số. Thân này chạy trước khi các field được gán, và các tham số dùng được với đúng tên thành phần:

```java
record LogEntry(String method, String path, int status, int millis) {
    LogEntry {
        if (status < 100 || status > 599) {
            throw new IllegalArgumentException("status out of range: " + status);
        }
        path = path.strip();
    }
}

void main() {
    IO.println(new LogEntry("GET", " /api/orders ", 200, 35));
    IO.println(new LogEntry("GET", "/api/orders", 2000, 35));
}
```

Kết quả:

```text
LogEntry[method=GET, path=/api/orders, status=200, millis=35]
Exception in thread "main" java.lang.IllegalArgumentException: status out of range: 2000
	at Compact$LogEntry.<init>(Compact.java:4)
	at Compact.main(Compact.java:12)
```

Dòng đầu cho thấy compact constructor gán lại được tham số (`path = path.strip()`), và field nhận giá trị đã sửa. Dòng sau bị chặn ngay lúc tạo, nên trong chương trình không bao giờ tồn tại một `LogEntry` có status `2000`. `throw new IllegalArgumentException(...)` ném một exception để báo đầu vào sai; J4 học kỹ cách ném và bắt exception.

Record có ba giới hạn, đều xuất phát từ mục đích "chỉ chở dữ liệu":

- **Không thêm được field instance.** Mọi trạng thái phải là thành phần, để `equals`, `hashCode`, `toString` phản ánh đủ dữ liệu. Thêm `int retries;` vào thân record báo lỗi `field declaration must be static`. Field `static` và method thì thêm được.
- **Không kế thừa được lớp khác**, vì record ngầm kế thừa `java.lang.Record`. Record implement được interface; kế thừa và interface học ở J3.
- **Chỉ bất biến nông.** Field là `final` nên không gán lại được, nhưng nếu một thành phần là `List` hay mảng, nội dung bên trong vẫn sửa được. J5.3 dùng `List.copyOf` trong compact constructor để chặn việc này.

Đoạn sau thử giới hạn đầu tiên: thêm một field instance để đếm số lần thử lại.

```java
record LogEntry(String method, int status) {
    int retries;
}

void main() {
}
```

Kết quả:

```text
FieldInRecord.java:2: error: field declaration must be static
    int retries;
        ^
  (consider replacing field with record component)
1 error
error: compilation failed
```

Gợi ý trong ngoặc của `javac` nói đúng cách sửa: đưa `retries` vào danh sách thành phần. Giới hạn thứ ba cần chạy mới thấy. Record dưới có thành phần là một mảng, và bên ngoài sửa phần tử của mảng sau khi đã tạo record:

```java
record Batch(String service, int[] latencies) {}

void main() {
    int[] latencies = {35, 41};
    Batch batch = new Batch("orders", latencies);
    latencies[0] = 9999;
    IO.println(batch.latencies()[0]);
}
```

Kết quả:

```text
9999
```

Record giữ tham chiếu tới cùng mảng mà bên gọi đang giữ, như mục truyền tham số của J2.1, nên sửa mảng từ bên ngoài thì dữ liệu của record đổi theo. Record bất biến ở tầng field, không bất biến ở các đối tượng mà field trỏ tới.

Dùng record cho DTO (data transfer object, đối tượng chỉ để chở dữ liệu giữa các phần của chương trình), cho giá trị trả về gồm nhiều phần, và cho khoá trong `Map`. Không dùng record cho đối tượng có trạng thái thay đổi theo thời gian, như một giỏ hàng.

Nhiều dự án Java cũ dùng thư viện Lombok với annotation `@Data` hay `@Value` để sinh getter, `equals`, `toString`. Lombok sinh code bằng annotation processor (công cụ chạy trong lúc biên dịch), cần plugin trong IDE và trong công cụ build. Record là tính năng của ngôn ngữ: JVM biết một class là record, nên thư viện chuyển đối tượng sang JSON như Jackson đọc được các thành phần mà không cần setter. `@Data` còn sinh setter, tức đối tượng sửa được. Với dữ liệu mang qua lại giữa các lớp, record là lựa chọn mặc định; Lombok vẫn có chỗ cho lớp cần sửa được hoặc cần kế thừa.

### Enum: tập hằng có kiểu

Code cũ lưu method HTTP bằng `String`. Một chỗ gõ nhầm `"GTE"`, chương trình biên dịch bình thường, và dòng log đó lặng lẽ rơi vào nhánh "method lạ".

**Enum** định nghĩa một kiểu có tập giá trị cố định, liệt kê hết lúc khai báo, ví dụ `enum HttpMethod { GET, POST, PUT, DELETE }`. Một method nhận `HttpMethod` không thể nhận `"GTE"` hay số `7`: trình biên dịch chặn ngay. Mỗi hằng là **một đối tượng duy nhất** trong JVM, nên so hai giá trị enum bằng `==` là đúng, khác với `String` và `Long`.

Enum có thể có field, constructor và method như một class. Đoạn sau khai báo nhóm status có nhãn riêng cho từng hằng, và thử các method có sẵn của mọi enum:

```java
enum StatusClass {
    SUCCESS("2xx"), REDIRECT("3xx"), CLIENT_ERROR("4xx"), SERVER_ERROR("5xx");

    private final String label;

    StatusClass(String label) {
        this.label = label;
    }

    String label() {
        return label;
    }
}

void main() {
    for (StatusClass c : StatusClass.values()) {
        IO.println(c.ordinal() + " " + c.name() + " " + c.label());
    }
    IO.println(StatusClass.valueOf("REDIRECT") == StatusClass.REDIRECT);
    IO.println(StatusClass.valueOf("redirect"));
}
```

Kết quả:

```text
0 SUCCESS 2xx
1 REDIRECT 3xx
2 CLIENT_ERROR 4xx
3 SERVER_ERROR 5xx
true
Exception in thread "main" java.lang.IllegalArgumentException: No enum constant Enums.StatusClass.redirect
	at java.base/java.lang.Enum.valueOf(Enum.java:293)
	at Enums$StatusClass.valueOf(Enums.java:1)
	at Enums.main(Enums.java:20)
```

`SUCCESS("2xx")` gọi constructor `StatusClass(String label)`, nên mỗi hằng mang nhãn của nó. Bảng dưới đọc output theo từng method:

| Method | Trả về | Output cho thấy |
|---|---|---|
| `values()` | Mảng mọi hằng, theo thứ tự khai báo | Vòng lặp in đủ bốn hằng, đúng thứ tự |
| `name()` | Tên hằng như trong code | `SUCCESS`, không phải nhãn `2xx` |
| `ordinal()` | Vị trí khai báo, tính từ 0 | `REDIRECT` là `1` |
| `valueOf(String)` | Hằng có đúng tên đó | Tên sai, kể cả sai hoa thường, ném `IllegalArgumentException` |

Khi đọc dữ liệu từ bên ngoài, như một dòng log, `valueOf` với tên lạ làm chương trình dừng. Muốn coi tên lạ là một trường hợp bình thường, tự viết method tra cứu duyệt `values()` và so `name().equals(s)`, như `HttpMethod.parse` ở mục cuối bài.

<Callout kind="production">

Một bảng `orders` lưu trạng thái đơn bằng `ordinal()`: `NEW` là 0, `PAID` là 1, `SHIPPED` là 2. Đây cũng là mặc định của JPA (chuẩn lưu đối tượng Java vào database, học ở SB3) khi bạn không ghi `@Enumerated(EnumType.STRING)`. Một năm sau, ai đó thêm `CONFIRMED` vào giữa `NEW` và `PAID`. Từ đó mọi đơn cũ đang là `PAID` (1) được đọc lên thành `CONFIRMED`, `SHIPPED` (2) thành `PAID`. Không có lỗi nào được báo. Lưu enum bằng `name()`, hoặc bằng một mã riêng đặt trong field của enum, không bao giờ bằng `ordinal()`.

</Callout>

Đoạn sau mô phỏng đúng sự cố đó: `stored` là con số đã lưu trong database từ phiên bản cũ, và phiên bản mới đọc nó lên bằng `values()[stored]`:

```java
enum OrderStatusV1 { NEW, PAID, SHIPPED }
enum OrderStatusV2 { NEW, CONFIRMED, PAID, SHIPPED }

void main() {
    int stored = OrderStatusV1.PAID.ordinal();
    IO.println("luu xuong: " + stored);
    IO.println("doc len:   " + OrderStatusV2.values()[stored]);

    String storedName = OrderStatusV1.PAID.name();
    IO.println("luu bang name, doc len: " + OrderStatusV2.valueOf(storedName));
}
```

Kết quả:

```text
luu xuong: 1
doc len:   CONFIRMED
luu bang name, doc len: PAID
```

Lưu bằng `ordinal`, đơn đã thanh toán đọc lên thành `CONFIRMED`. Lưu bằng `name`, thứ tự khai báo không còn ảnh hưởng. Đổi tên một hằng thì vẫn làm hỏng dữ liệu cũ, nên khi tên có thể đổi, dùng một mã riêng trong field như `label` của `StatusClass`.

JDK có hai collection dành riêng cho enum. Collection nói chung học ở J5; ở bài này, bạn biết chúng tồn tại và vì sao chúng nhanh là đủ:

- `EnumMap`: map (bảng tra từ khoá sang giá trị) có khoá là enum. Bên trong nó là một mảng đánh chỉ số theo `ordinal`, nên tra cứu nhanh và duyệt theo thứ tự khai báo.
- `EnumSet`: tập các hằng, ví dụ `EnumSet.of(GET, PUT, DELETE)` cho các method idempotent (gọi nhiều lần để lại trên server cùng trạng thái như gọi một lần; J10.2 học kỹ).

### Switch expression

J2.1 cho thấy `switch` dạng cũ rơi xuống case sau khi thiếu `break`, và bạn phải gán biến trong từng case. Code chọn mức log theo status cần một biến khởi tạo trước, rồi một lệnh gán và một `break` cho mỗi case; quên một `break` là có lỗi.

**Switch expression** (từ Java 14) là một biểu thức: nó trả về một giá trị, nên gán thẳng được vào biến. Với nhãn `case ->`, chỉ đúng một nhánh chạy, không bao giờ rơi xuống case sau. Đoạn sau chọn mức log cho ba status:

```java
String level(int status) {
    return switch (status / 100) {
        case 2, 3 -> "INFO";
        case 4 -> "WARN";
        case 5 -> {
            boolean retryable = status == 502 || status == 503;
            yield retryable ? "RETRY" : "ERROR";
        }
        default -> "UNKNOWN";
    };
}

void main() {
    for (int status : new int[] {200, 404, 502, 500, 99}) {
        IO.println(status + " -> " + level(status));
    }
}
```

Kết quả:

```text
200 -> INFO
404 -> WARN
502 -> RETRY
500 -> ERROR
99 -> UNKNOWN
```

Ba điểm mới của cú pháp:

- `case 2, 3 ->` gom nhiều nhãn vào một nhánh.
- Nhánh cần nhiều lệnh thì viết trong khối `{ }` và trả giá trị bằng `yield`. `return` ở đó sẽ thoát khỏi cả method, nên Java dùng một từ khoá riêng.
- Switch expression phải **đầy đủ** (exhaustive): mọi giá trị đầu vào đều phải khớp một nhánh, vì biểu thức nào cũng phải có giá trị. Với `int`, chỉ `default` mới phủ hết, nên bỏ `default` ở trên thì `javac` báo `the switch expression does not cover all possible input values`.

Tính đầy đủ thể hiện sức mạnh khi switch trên enum. Một enum có tập hằng cố định, nên liệt kê đủ các hằng là đã đầy đủ, không cần `default`. Giả sử ứng dụng bắt đầu ghi cả status 1xx và ai đó thêm `INFORMATIONAL` vào đầu `StatusClass` (ví dụ dưới bỏ phần nhãn cho gọn), trong khi method `alertLevel` ở nơi khác vẫn chỉ liệt kê bốn hằng cũ:

```java
enum StatusClass { INFORMATIONAL, SUCCESS, REDIRECT, CLIENT_ERROR, SERVER_ERROR }

String alertLevel(StatusClass c) {
    return switch (c) {
        case SUCCESS, REDIRECT -> "ok";
        case CLIENT_ERROR -> "watch";
        case SERVER_ERROR -> "page";
    };
}

void main() {
    IO.println(alertLevel(StatusClass.SUCCESS));
}
```

<Predict question="Chương trình in ok, hay không chạy được? Nếu lỗi, lỗi báo ở dòng nào?">

```text
Exhaustive.java:4: error: the switch expression does not cover all possible input values
    return switch (c) {
           ^
1 error
error: compilation failed
```

Chương trình không biên dịch. Lỗi chỉ đúng vào switch của `alertLevel`, chỗ còn thiếu `INFORMATIONAL`.

</Predict>

Lỗi biên dịch này là điều bạn muốn. Trình biên dịch chỉ ra mọi switch cần quyết định "1xx thì cảnh báo mức nào", trước khi code chạy. Nếu `alertLevel` có `default -> "ok"`, nó biên dịch bình thường và status 1xx lặng lẽ đi vào `default`, dù có thể nó cần một mức cảnh báo khác. Vì vậy, khi switch trên enum của chính bạn, đừng thêm `default`.

`default` vẫn có chỗ khi đầu vào không phải tập đóng: `int`, `String`, hay enum của một thư viện khác mà bạn không kiểm soát việc thêm hằng. Có một trường hợp biên: enum nằm trong một JAR được biên dịch riêng, được thêm hằng sau khi code của bạn đã biên dịch. Lúc đó trình biên dịch không thấy hằng mới, và theo [JEP 441](https://openjdk.org/jeps/441), switch expression không có `default` ném `MatchException` lúc chạy khi gặp hằng lạ, chứ không lặng lẽ bỏ qua.

### Pattern matching: kiểm tra kiểu và tách dữ liệu cùng lúc

Khi đọc một dòng log, kết quả có hai loại: dòng hợp lệ, hoặc dòng hỏng kèm lý do. Trả `null` cho dòng hỏng thì mất lý do, và bên gọi có thể quên kiểm tra `null`. Bạn cần một kiểu nói được "một trong hai thứ này", và một cách rẽ nhánh theo từng thứ.

**Pattern matching** vừa kiểm tra một giá trị có khớp một mẫu (pattern) không, vừa gán các phần của nó vào biến trong cùng một bước. Java có ba dạng:

| Dạng | Từ Java | Ví dụ |
|---|---|---|
| `instanceof` pattern | 16 | `if (input instanceof String s && !s.isBlank())`, bên trong `if` dùng thẳng `s` |
| Type pattern trong switch | 21 | `case String s ->`, `case Integer i when i > 0 ->` |
| Record pattern | 21 | `case Parsed(LogEntry e) ->`, tách thành phần của record ra biến |

`when` là **guard**: điều kiện thêm, case chỉ khớp khi kiểu khớp **và** điều kiện đúng. `case null ->` xử lý giá trị `null`; thiếu nó thì switch trên `null` ném `NullPointerException`. Đoạn sau mô tả một giá trị bất kỳ đọc từ cấu hình:

```java
String describe(Object value) {
    return switch (value) {
        case null -> "thieu gia tri";
        case Integer i when i > 0 -> "so duong " + i;
        case Integer i -> "so khong duong " + i;
        case String s -> "chuoi dai " + s.length();
        default -> "kieu khac: " + value.getClass().getSimpleName();
    };
}

void main() {
    IO.println(describe(3000));
    IO.println(describe(-1));
    IO.println(describe("orders"));
    IO.println(describe(null));
    IO.println(describe(2.5));
}
```

Kết quả:

```text
so duong 3000
so khong duong -1
chuoi dai 6
thieu gia tri
kieu khac: Double
```

Switch thử các case từ trên xuống và chọn case đầu tiên khớp. `-1` là `Integer` nhưng không qua guard `i > 0`, nên rơi xuống `case Integer i`. `2.5` là `Double`, không khớp case nào phía trên, nên vào `default`. Trên `Object`, `default` là bắt buộc: kiểu nào cũng có thể là một `Object`, trình biên dịch không thể biết bạn đã phủ hết.

Thứ tự case quan trọng. Đoạn sau đặt case không có guard lên trước case có guard của cùng kiểu `Rejected`:

```java
record Rejected(String line, String reason) {}

String describe(Rejected r) {
    return switch (r) {
        case Rejected rej -> "rejected";
        case Rejected rej when rej.line().isBlank() -> "blank";
    };
}

void main() {
}
```

Kết quả:

```text
Dominance.java:6: error: this case label is dominated by a preceding case label
        case Rejected rej when rej.line().isBlank() -> "blank";
             ^
1 error
error: compilation failed
```

Thử tự trả lời trước khi đọc tiếp: điều kiện `rej.line().isBlank()` hoàn toàn hợp lệ, vậy vì sao `javac` từ chối case thứ hai?

Case `Rejected rej` không có guard nên khớp mọi `Rejected`. Mọi giá trị đi tới case thứ hai đều đã được case thứ nhất nhận, nên case có guard không bao giờ chạy, và `javac` báo lỗi thay vì để bạn giữ một nhánh chết. "Dominated" nghĩa là bị một case phía trên "che" hết. Quy tắc rút ra: case có guard phải đứng **trước** case cùng kiểu không có guard. Đổi chỗ hai case là hết lỗi.

Để trình biên dịch biết hết mọi khả năng, như với enum, bạn dùng **sealed interface**: một interface tự liệt kê danh sách cố định các lớp được implement nó, bằng từ khoá `permits`. J3 học kỹ interface và sealed; ở bài này, bạn đọc được dòng khai báo là đủ. Kết quả đọc một dòng log là một `ParseResult`, chỉ có thể là `Parsed` hoặc `Rejected`:

```text
 sealed interface ParseResult permits Parsed, Rejected
   +-- record Parsed(LogEntry entry)                  dòng log hợp lệ
   +-- record Rejected(String line, String reason)    dòng hỏng, kèm lý do

 switch (parse(line)) {
     case Parsed(LogEntry e) when e.millis() >= 1000 -> chậm
     case Parsed(LogEntry e)                         -> bình thường
     case Rejected(var line, var reason)             -> ghi lý do
 }   không cần default: chỉ có hai lớp con, và cả hai đã có case
```

`case Parsed(LogEntry e)` là record pattern: nó kiểm tra giá trị là `Parsed`, rồi gán thành phần `entry` vào biến `e`. `var` trong record pattern để trình biên dịch tự suy kiểu thành phần. Kiểu `ParseResult` buộc bên gọi xử lý cả hai trường hợp: quên case `Rejected` thì switch không biên dịch, giống enum thiếu hằng. Mục cuối bài dùng đúng sơ đồ này.

### Text block

Test của bạn cần một chuỗi JSON hay một câu SQL nhiều dòng. Viết bằng `"..." + "\n" +` thì đầy dấu nháy và `\n`, khó đọc và dễ sai.

**Text block** (từ Java 15) viết chuỗi nhiều dòng giữa hai cặp ba dấu nháy kép `"""`. Nội dung bắt đầu từ dòng ngay sau `"""` mở; viết nội dung trên cùng dòng với `"""` mở là lỗi `illegal text block open delimiter sequence, missing line terminator`. Đoạn sau in một câu SQL, đổi mỗi ký tự xuống dòng thành hai ký tự `\n` để bạn thấy chính xác chuỗi chứa gì:

```java
void main() {
    String sql = """
        SELECT id, total
          FROM orders
        WHERE status = 'PAID'
        """;
    IO.println(sql.replace("\n", "\\n"));
}
```

<Predict question="Dòng FROM giữ lại mấy dấu cách đầu dòng? Chuỗi có kết thúc bằng xuống dòng không?">

```text
SELECT id, total\n  FROM orders\nWHERE status = 'PAID'\n
```

`FROM` giữ 2 dấu cách, các dòng khác không có dấu cách đầu dòng, và chuỗi kết thúc bằng `\n`.

</Predict>

Trình biên dịch bỏ phần thụt lề chung của mọi dòng, gọi là **incidental whitespace** (khoảng trắng ngẫu nhiên, do thụt lề code chứ không thuộc nội dung). Phần bị bỏ tính theo dòng thụt ít nhất, **kể cả dòng chứa `"""` đóng**. Ở đây dòng ít nhất thụt 8 dấu cách; `FROM` thụt 10 nên giữ lại 2. `"""` đóng nằm trên dòng riêng nên chuỗi kết thúc bằng `\n`; đặt `"""` ngay sau ký tự cuối thì không có `\n` ở cuối. Đẩy `"""` đóng sang trái là cách giữ thêm thụt lề cho mọi dòng.

Hai quy tắc khác về khoảng trắng và hai escape mới đi kèm:

- Khoảng trắng cuối mỗi dòng bị cắt. Muốn giữ, kết thúc dòng bằng `\s`, escape cho một dấu cách và chặn việc cắt các dấu cách đứng trước nó.
- Dấu `\` ở cuối dòng nối dòng đó với dòng sau, không chèn `\n`. Dùng nó để viết một chuỗi dài trên nhiều dòng code.

Text block thường đi với `formatted` để chèn giá trị. Nhưng `formatted` chỉ thay `%s`, `%d` theo thứ tự, không escape gì cả. Đoạn sau chèn một đường dẫn có dấu nháy kép vào JSON:

```java
void main() {
    String path = "/api/orders?name=\"KB-02\"";
    String json = """
        {"path": "%s", "millis": %d}""".formatted(path, 35);
    IO.println(json);
}
```

Kết quả:

```text
{"path": "/api/orders?name="KB-02"", "millis": 35}
```

Dấu `"` trong `path` đóng chuỗi JSON quá sớm, và output không còn là JSON hợp lệ. Với SQL, chèn giá trị người dùng nhập vào kiểu này tạo lỗ hổng SQL injection. Text block hợp với chuỗi cố định và dữ liệu test. Để tạo JSON, dùng thư viện như Jackson; để chạy SQL có tham số, dùng `PreparedStatement` (SB3).

### Ghép lại: đọc log bằng record, enum và sealed interface

Chương trình dưới đọc lại log của J2.2, lần này bằng kiểu: in các request chậm từ 1000 ms, các dòng bị bỏ kèm lý do, và request chậm nhất. Log có thêm một dòng viết method bằng chữ thường, `get`. Theo đặc tả HTTP ([RFC 9110](https://www.rfc-editor.org/rfc/rfc9110#section-9.1)), tên method phân biệt hoa thường, nên dòng đó phải bị từ chối. `HttpMethod.parse` so bằng `name().equals` thay vì `valueOf`, nên tên lạ cho ra `null` để `parse` biến thành một `Rejected`, thay vì một exception làm dừng chương trình:

```java
enum HttpMethod {
    GET, POST, PUT, DELETE;

    static HttpMethod parse(String s) {
        for (HttpMethod m : values()) {
            if (m.name().equals(s)) return m;
        }
        return null;
    }
}

record LogEntry(HttpMethod method, String path, int status, int millis) {}

sealed interface ParseResult permits Parsed, Rejected {}
record Parsed(LogEntry entry) implements ParseResult {}
record Rejected(String line, String reason) implements ParseResult {}

ParseResult parse(String raw) {
    String[] parts = raw.strip().split("\\s+");
    if (parts.length != 5) return new Rejected(raw, "expected 5 fields");
    HttpMethod method = HttpMethod.parse(parts[1]);
    if (method == null) return new Rejected(raw, "unknown method");
    return new Parsed(new LogEntry(method, parts[2],
            Integer.parseInt(parts[3]), Integer.parseInt(parts[4])));
}

void main() {
    String log = """
        2026-10-03T09:00:01Z GET /api/orders 200 35
        2026-10-03T09:00:05Z POST /api/payments 502 3012

        upstream timed out
        2026-10-03T09:00:09Z GET /api/products 500 1290
        2026-10-03T09:00:11Z get /api/orders 200 12
        """;
    LogEntry slowest = null;
    for (String line : log.split("\n")) {
        switch (parse(line)) {
            case Parsed(LogEntry e) when e.millis() >= 1000 -> {
                IO.println("slow: " + e.method() + " " + e.path() + " " + e.millis() + "ms");
                slowest = (slowest == null || e.millis() > slowest.millis()) ? e : slowest;
            }
            case Parsed(LogEntry e) -> { }
            case Rejected r when r.line().isBlank() -> { }
            case Rejected(String raw, String reason) -> IO.println("skip (" + reason + "): " + raw);
        }
    }
    IO.println("slowest = " + slowest);
}
```

Kết quả:

```text
slow: POST /api/payments 3012ms
skip (expected 5 fields): upstream timed out
slow: GET /api/products 1290ms
skip (unknown method): 2026-10-03T09:00:11Z get /api/orders 200 12
slowest = LogEntry[method=POST, path=/api/payments, status=502, millis=3012]
```

Đọc output theo các phần của bài:

- Log viết bằng text block, nên mỗi dòng không cần `\n` và dấu nháy riêng. Dòng trống trong text block thành một dòng rỗng khi `split("\n")`.
- Dòng `get` bị từ chối với lý do `unknown method`, còn `upstream timed out` bị từ chối vì thiếu trường. Cả hai mang lý do của mình nhờ record `Rejected`.
- Switch trên `parse(line)` không có `default`: `ParseResult` chỉ có `Parsed` và `Rejected`, và cả hai đều có case không guard. Case có guard đứng trước case cùng kiểu không guard, đúng quy tắc ở mục pattern matching. Dòng trống thành `Rejected` có `line` rỗng, và case `when r.line().isBlank()` bỏ qua nó.
- `slowest` in bằng `toString` do record sinh, và thành phần `method` in tên hằng enum `POST`.

<Callout kind="ai">

Nhờ AI chuyển một lớp DTO dài thành record, hoặc chuyển chuỗi `if-else` thành switch expression. AI hay thêm `default` vào switch trên enum hay sealed type (tắt mất kiểm tra đầy đủ), viết getter `getName()` cho record, dùng `ordinal()` để lưu hay so sánh, và ghép giá trị vào text block JSON hay SQL bằng `formatted`. Kiểm tra bằng cách thêm thử một hằng enum hay một lớp con vào sealed interface và xem trình biên dịch có báo mọi switch cần sửa không.

</Callout>

<Callout kind="link">

J3 dạy interface, sealed type, kế thừa, cặp `equals` và `hashCode`, và đối tượng bất biến đầy đủ. J4 dạy cách ném và bắt exception, như `IllegalArgumentException` của compact constructor. J5 dùng record làm khoá `Map`, dạy `EnumSet`, `EnumMap` cùng các collection khác, và J5.3 dùng `List.copyOf` để record bất biến sâu. SB3 lưu enum vào database bằng JPA với `EnumType.STRING`.
