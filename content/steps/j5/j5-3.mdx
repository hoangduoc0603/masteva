<Goal>

Duyệt, sắp xếp và trả dữ liệu từ collection một cách an toàn: không hỏng khi xoá trong lúc duyệt, không mất phần tử khi sắp xếp, không `NullPointerException` vì quên kiểm tra `null`, không bị sửa ngầm từ bên ngoài. Học xong bài này, bạn giải thích được:

- Vì sao xoá phần tử trong vòng for-each ném `ConcurrentModificationException`, dù chỉ có một thread, và vì sao có lúc nó không ném gì mà lặng lẽ bỏ sót phần tử.
- Vì sao một `TreeSet` sắp theo giá "nuốt mất" một sản phẩm mà không báo lỗi gì.
- Vì sao `orElse` vẫn chạy hàm tạo giá trị mặc định dù `Optional` đã có giá trị.
- Vì sao `Collections.unmodifiableList` không ngăn được dữ liệu thay đổi, còn `List.copyOf` thì có.

</Goal>

### Xoá trong lúc duyệt và fail-fast

Món `HD-07` vừa ngừng bán và bạn cần bỏ nó khỏi giỏ hàng. Cách viết đầu tiên ai cũng nghĩ tới là duyệt giỏ bằng for-each và gọi `cart.remove` khi gặp nó. Chương trình chỉ có một thread, vậy mà nó ném một exception có chữ "concurrent" trong tên.

**Iterator** là đối tượng đi qua từng phần tử của collection, với ba method: `hasNext()`, `next()` và `remove()` (xoá phần tử mà `next()` vừa trả về). Vòng for-each không có cơ chế riêng: `javac` dịch nó thành một iterator. Đoạn code sau xoá `HD-07`, phần tử thứ hai trong giỏ bốn món. `Product` ghi đè `toString` để khi in giỏ hàng chỉ thấy SKU.

```java
record Product(String sku, long price) {
    public String toString() { return sku; }
}

void main() {
    List<Product> cart = new ArrayList<>(List.of(
            new Product("KB-02", 1_290_000), new Product("HD-07", 890_000),
            new Product("SP-03", 1_150_000), new Product("CB-05", 120_000)));
    for (Product p : cart) {
        if (p.sku().equals("HD-07")) {
            cart.remove(p);
        }
    }
    IO.println(cart);
}
```

<Predict question="Exception nổ ở dòng nào: dòng cart.remove(p), hay chỗ khác? Dòng IO.println cuối có chạy không?">

```text
Exception in thread "main" java.util.ConcurrentModificationException
	at java.base/java.util.ArrayList$Itr.checkForComodification(ArrayList.java:1096)
	at java.base/java.util.ArrayList$Itr.next(ArrayList.java:1050)
	at RemoveInLoop.main(RemoveInLoop.java:9)
```

Không có dòng nào được in. Exception nổ ở dòng 9, dòng `for`, tức lúc vòng lặp gọi `next()` để lấy phần tử kế tiếp, không phải lúc gọi `remove`. Số dòng trong `ArrayList.java` có thể khác giữa các bản JDK.

</Predict>

Để hiểu vì sao lỗi nổ ở `next()`, bạn cần ba thành phần:

| Thành phần | Vai trò |
|---|---|
| `modCount` của `ArrayList` | Số lần list bị sửa cấu trúc (thêm, xoá); tăng ở mỗi `add`, `remove` |
| `expectedModCount` của iterator | Giá trị `modCount` mà iterator ghi nhớ lúc được tạo |
| `cursor` của iterator | Vị trí phần tử kế tiếp; `hasNext()` trả `true` khi `cursor != size` |

Iterator so số nó nhớ với `modCount` ở mỗi lần `next()`:

```text
for (Product p : cart) { ... cart.remove(p); }

   javac dịch thành                          ArrayList bên trong
   Iterator<Product> it = cart.iterator();   modCount = 0, it.expected = 0
   while (it.hasNext()) {
       Product p = it.next();  ◄──────────── next() so it.expected với modCount
       cart.remove(p);         ────────────► modCount = 1, iterator không hay biết
   }                                         lần next() sau: 0 != 1 -> ConcurrentModificationException
```

`cart.remove(p)` sửa list trực tiếp, không qua iterator, nên iterator không biết các phần tử phía sau đã dời lên một ô. Nếu duyệt tiếp, nó sẽ trả sai phần tử. Vì vậy, ngay khi thấy số đếm lệch, `ArrayList` ném exception thay vì duyệt tiếp trên dữ liệu đã xê dịch. Cách thiết kế này gọi là **fail-fast**: báo lỗi sớm nhất có thể, tại chỗ gần nguyên nhân nhất.

Bạn có thể nghĩ chữ "concurrent" trong `ConcurrentModificationException` nghĩa là lỗi chỉ xảy ra khi nhiều thread cùng sửa một collection. Không phải vậy. "Concurrent" ở đây là việc sửa collection trong lúc một iterator đang duyệt nó, và một thread làm được cả hai việc như ví dụ trên. Collection cho nhiều thread là chủ đề của J11.

Fail-fast cũng không phải lúc nào cũng xảy ra. Đoạn sau xoá hai món `CB-05` và `PD-04` nằm ở cuối giỏ, và in ra từng phần tử vòng lặp xét tới:

```java
record Product(String sku, long price) {
    public String toString() { return sku; }
}

void main() {
    List<Product> cart = new ArrayList<>(List.of(
            new Product("KB-02", 1_290_000), new Product("HD-07", 890_000),
            new Product("CB-05", 120_000), new Product("PD-04", 120_000)));
    Set<String> discontinued = Set.of("CB-05", "PD-04");
    for (Product p : cart) {
        IO.println("xet " + p);
        if (discontinued.contains(p.sku())) {
            cart.remove(p);
        }
    }
    IO.println("con lai " + cart);
}
```

Kết quả:

```text
xet KB-02
xet HD-07
xet CB-05
con lai [KB-02, HD-07, PD-04]
```

Không có exception, nhưng `PD-04` không bao giờ được xét và vẫn nằm trong giỏ. Thử tự trả lời trước khi đọc tiếp: vì sao `hasNext()` trả `false` ngay sau khi xoá `CB-05`?

`CB-05` là phần tử áp chót. Sau khi xét nó, `cursor` bằng 3; xoá nó làm `size` giảm từ 4 xuống 3. `hasNext()` chỉ so `cursor != size`, thấy 3 bằng 3 nên trả `false`, và vòng lặp kết thúc mà không gọi `next()` lần nào nữa. [Javadoc của `ArrayList`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/ArrayList.html) gọi fail-fast là "best-effort": nó chỉ giúp phát hiện lỗi, bạn không được dựa vào nó để biết code của mình đúng.

Có hai cách xoá đúng trong lúc duyệt. `it.remove()` xoá qua chính iterator, nên iterator cập nhật số đếm và `cursor` của nó. `removeIf` (Java 8) nhận một điều kiện, tự duyệt và xoá. Điều kiện viết bằng một **lambda**: `p -> discontinued.contains(p.sku())` là một hàm nhận `p` và trả `true` nếu cần xoá. J6 học kỹ lambda, ở bài này bạn đọc được nó là đủ.

```java
record Product(String sku, long price) {
    public String toString() { return sku; }
}

void main() {
    Set<String> discontinued = Set.of("CB-05", "PD-04");
    List<Product> cart = List.of(
            new Product("KB-02", 1_290_000), new Product("HD-07", 890_000),
            new Product("CB-05", 120_000), new Product("PD-04", 120_000));

    List<Product> byIterator = new ArrayList<>(cart);
    Iterator<Product> it = byIterator.iterator();
    while (it.hasNext()) {
        if (discontinued.contains(it.next().sku())) {
            it.remove();
        }
    }
    List<Product> byRemoveIf = new ArrayList<>(cart);
    byRemoveIf.removeIf(p -> discontinued.contains(p.sku()));

    IO.println("it.remove " + byIterator);
    IO.println("removeIf  " + byRemoveIf);
}
```

Kết quả:

```text
it.remove [KB-02, HD-07]
removeIf  [KB-02, HD-07]
```

Cả hai cách đều bỏ đủ hai món, kể cả `PD-04` mà vòng for-each bỏ sót. Tóm lại ba cách xoá trong lúc duyệt:

| Cách xoá trong lúc duyệt | Kết quả |
|---|---|
| `cart.remove(p)` trong for-each | `ConcurrentModificationException`, hoặc lặng lẽ bỏ sót phần tử |
| `it.remove()` với iterator tường minh | Đúng; iterator tự cập nhật số đếm |
| `cart.removeIf(điều kiện)` | Đúng và ngắn nhất |

Gặp `ConcurrentModificationException` trong code một thread, hãy tìm lời gọi `add`, `remove`, `clear` nằm bên trong vòng lặp đang duyệt chính collection đó.

### Comparable: thứ tự tự nhiên

Khi in danh mục ra file đối chiếu với kho, bạn muốn sản phẩm luôn xếp theo SKU. Đây là thứ tự "mặc định" của sản phẩm, đúng ở hầu hết mọi chỗ cần sắp.

Một lớp cài `Comparable<T>` thì có **thứ tự tự nhiên** (natural ordering). Method `compareTo(other)` trả số âm nếu `this` đứng trước `other`, `0` nếu ngang nhau, số dương nếu đứng sau. `Collections.sort(list)`, `TreeSet` và `TreeMap` dùng thứ tự này khi bạn không đưa cách sắp nào khác.

```java
record Product(String sku, String category, long price) implements Comparable<Product> {
    @Override
    public int compareTo(Product other) {
        return sku.compareTo(other.sku);
    }
}

void main() {
    List<Product> products = new ArrayList<>(List.of(
            new Product("MS-01", "phu-kien", 450_000),
            new Product("CB-05", "phu-kien", 120_000),
            new Product("KB-02", "phu-kien", 1_290_000)));
    Collections.sort(products);
    for (Product p : products) {
        IO.println(p.sku() + " " + p.price());
    }
}
```

Kết quả:

```text
CB-05 120000
KB-02 1290000
MS-01 450000
```

Ba sản phẩm xếp theo SKU, còn giá không ảnh hưởng gì: `MS-01` giá 450.000 đồng vẫn đứng sau `KB-02` giá 1.290.000 đồng. `compareTo` của `Product` chuyển việc so sánh cho `String.compareTo`, vốn so theo thứ tự từ điển. Chỉ chọn thứ tự tự nhiên khi cả lớp có một thứ tự mà ai cũng nghĩ tới đầu tiên, như theo mã hay theo ngày. Các cách sắp khác dùng `Comparator` ở mục sau.

[Javadoc của `Comparable`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Comparable.html) khuyến nghị mạnh rằng thứ tự tự nhiên **nhất quán với equals**: `a.compareTo(b) == 0` đúng khi và chỉ khi `a.equals(b)`. Nói chính xác, thứ tự theo SKU ở trên không nhất quán với `equals` của record, vì `equals` so cả ba field. Nó vẫn an toàn vì SKU là duy nhất trong danh mục: không có hai `Product` khác nhau mà cùng SKU. Mục TreeSet bên dưới cho thấy chuyện gì xảy ra khi điều kiện này bị phá.

Khi so số, nhiều người viết `compareTo` bằng phép trừ, ví dụ `return (int) (total - other.total);`, vì nó ngắn và có vẻ trả đúng dấu. Cách viết này sai khi hai số cách nhau quá xa: phép trừ vượt giới hạn của `int`, và ép kiểu cắt mất bit cao làm đổi dấu. Đoạn sau so một đơn sỉ 2,2 tỷ đồng với một đơn lẻ 100.000 đồng:

```java
record Order(String id, long total) {}

void main() {
    Order wholesale = new Order("DH-9001", 2_200_000_000L);
    Order retail = new Order("DH-1001", 100_000);

    int bySubtraction = (int) (wholesale.total() - retail.total());
    int byCompare = Long.compare(wholesale.total(), retail.total());

    IO.println("(int) (a - b)   = " + bySubtraction);
    IO.println("Long.compare    = " + byCompare);
}
```

Kết quả:

```text
(int) (a - b)   = -2095067296
Long.compare    = 1
```

Hiệu số 2.199.900.000 lớn hơn giới hạn 2.147.483.647 của `int`, nên sau khi ép kiểu nó thành số âm, và đơn 2,2 tỷ bị xếp trước đơn 100.000 đồng. `Long.compare` (và `Integer.compare` cho `int`) so trực tiếp, không trừ, nên luôn đúng dấu.

### Comparator: thứ tự bên ngoài

Trang danh mục cần sắp theo nhóm hàng, trong cùng nhóm thì giá giảm dần. Đó không phải thứ tự tự nhiên của `Product`, và một trang khác có thể cần cách sắp khác nữa.

**Comparator** (`Comparator<T>`) là một đối tượng mô tả một cách sắp xếp, nằm ngoài lớp được sắp. Method `compare(a, b)` của nó trả số âm, `0` hoặc số dương theo cùng quy ước với `compareTo`. Từ Java 8, bạn ghép các comparator có sẵn thay vì tự viết `compare`. Đoạn sau dùng **method reference** `Product::category`, cách viết gọn của lambda `p -> p.category()`: một hàm nhận `Product` và trả nhóm hàng.

```java
record Product(String sku, String category, long price) {}

void main() {
    List<Product> products = new ArrayList<>(List.of(
            new Product("CB-05", "phu-kien", 120_000),
            new Product("HD-07", "am-thanh", 890_000),
            new Product("KB-02", "phu-kien", 1_290_000),
            new Product("MS-01", "phu-kien", 450_000),
            new Product("PD-04", "phu-kien", 120_000),
            new Product("SP-03", "am-thanh", 1_150_000)));

    products.sort(Comparator.comparing(Product::category)
            .thenComparing(Product::price, Comparator.reverseOrder()));
    for (Product p : products) {
        IO.println(p.category() + " " + p.sku() + " " + p.price());
    }
}
```

Kết quả:

```text
am-thanh SP-03 1150000
am-thanh HD-07 890000
phu-kien KB-02 1290000
phu-kien MS-01 450000
phu-kien CB-05 120000
phu-kien PD-04 120000
```

Nhóm `am-thanh` đứng trước `phu-kien`, trong mỗi nhóm giá giảm dần. `CB-05` và `PD-04` cùng nhóm, cùng giá, nên comparator coi chúng bằng nhau; chúng giữ nguyên thứ tự trong list ban đầu vì `List.sort` và `Collections.sort` là sắp xếp **ổn định** (stable), như [Javadoc của `Collections.sort`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Collections.html) cam kết.

Bảng dưới là các method bài này dùng; các method khác có trong bài "Writing and Combining Comparators" ở phần Tài liệu.

| Method | Việc nó làm |
|---|---|
| `Comparator.comparing(f)` | So theo giá trị `f` trích ra. Bản `comparingLong` và `thenComparingLong` so số `long` mà không bọc thành đối tượng |
| `thenComparing(g)` | Nếu bằng nhau theo tiêu chí trước, so tiếp theo `g`. Bản `thenComparing(g, c)` so `g` bằng comparator `c` |
| `reversed()` | Đảo chiều sắp xếp; xem bẫy ngay dưới bảng |
| `Comparator.reverseOrder()` | Thứ tự tự nhiên đảo ngược |

Nhìn chuỗi trên, nhiều người nghĩ có thể viết "giá giảm dần" bằng cách gắn `.reversed()` vào cuối chuỗi. Nhưng `reversed()` không chỉ đảo tiêu chí liền trước nó. Đoạn sau sắp cùng một danh sách theo hai cách: gắn `.reversed()` vào cuối chuỗi, và truyền `Comparator.reverseOrder()` cho riêng tiêu chí giá:

```java
record Product(String sku, String category, long price) {}

List<Product> products = new ArrayList<>(List.of(
        new Product("HD-07", "am-thanh", 890_000), new Product("SP-03", "am-thanh", 1_150_000),
        new Product("MS-01", "phu-kien", 450_000), new Product("KB-02", "phu-kien", 1_290_000)));

void print(String title, Comparator<Product> order) {
    products.sort(order);
    IO.println(title);
    for (Product p : products) {
        IO.println("  " + p.category() + " " + p.sku() + " " + p.price());
    }
}

void main() {
    print("reversed() o cuoi:", Comparator.comparing(Product::category)
            .thenComparingLong(Product::price).reversed());
    print("reverseOrder() cho rieng gia:", Comparator.comparing(Product::category)
            .thenComparing(Product::price, Comparator.reverseOrder()));
}
```

Kết quả:

```text
reversed() o cuoi:
  phu-kien KB-02 1290000
  phu-kien MS-01 450000
  am-thanh SP-03 1150000
  am-thanh HD-07 890000
reverseOrder() cho rieng gia:
  am-thanh SP-03 1150000
  am-thanh HD-07 890000
  phu-kien KB-02 1290000
  phu-kien MS-01 450000
```

Cả hai cách đều cho giá giảm dần, nhưng cách đầu đảo luôn nhóm hàng: `phu-kien` đứng trước `am-thanh`. Mỗi lần gọi `thenComparing...` hay `reversed()`, Java không sửa comparator cũ mà bọc nó trong một comparator mới. `comparing(...).thenComparingLong(...)` là một comparator so nhóm rồi so giá; `reversed()` bọc nguyên comparator đó và đổi chiều kết quả của nó, nên cả hai tiêu chí cùng bị đảo. Muốn đảo riêng một tiêu chí, đưa comparator đảo vào đúng chỗ của tiêu chí đó: `thenComparing(Product::price, Comparator.reverseOrder())`, hoặc `thenComparing(Comparator.comparing(Product::price).reversed())`.

<Callout kind="pitfall">

`Comparator.comparing(p -> p.price()).reversed()` không biên dịch: `error: cannot find symbol ... method price() ... location: variable p of type Object`. Gọi thêm `.reversed()` làm trình biên dịch không suy được kiểu của `p` từ chỗ dùng nữa, nên coi nó là `Object`. Dùng method reference `Product::price`, hoặc ghi kiểu `(Product p) -> p.price()`.

</Callout>

### TreeSet tin vào compare, không tin equals

Danh mục có bốn sản phẩm, trong đó `CB-05` và `PD-04` cùng giá 120.000 đồng. Bạn bỏ cả bốn vào một `TreeSet` sắp theo giá để lấy danh sách từ rẻ tới đắt, và danh sách in ra chỉ có ba món.

**`TreeSet`** là một `Set` giữ phần tử theo thứ tự sắp xếp, dựa trên thứ tự tự nhiên hoặc một comparator bạn đưa vào. `TreeMap` làm điều tương tự với khoá của map. Đoạn sau in kết quả của từng lần `add`:

```java
record Product(String sku, long price) {}

void main() {
    Product cb05 = new Product("CB-05", 120_000);
    Product pd04 = new Product("PD-04", 120_000);
    List<Product> catalog = List.of(
            new Product("KB-02", 1_290_000), new Product("MS-01", 450_000), cb05, pd04);

    Set<Product> byPrice = new TreeSet<>(Comparator.comparingLong(Product::price));
    for (Product p : catalog) {
        boolean added = byPrice.add(p);
        IO.println("add " + p.sku() + " -> " + added);
    }
    IO.println("size = " + byPrice.size());
    IO.println("PD-04 equals CB-05? " + pd04.equals(cb05));
}
```

<Predict question="Món nào bị mất, lần add của nó trả gì, và equals nói hai sản phẩm cùng giá có bằng nhau không?">

```text
add KB-02 -> true
add MS-01 -> true
add CB-05 -> true
add PD-04 -> false
size = 3
PD-04 equals CB-05? false
```

`add` của `PD-04` trả `false`: `TreeSet` coi nó đã có mặt, dù `equals` nói hai sản phẩm khác nhau.

</Predict>

`TreeSet` lưu phần tử trong một cây nhị phân tìm kiếm (red-black tree). Để biết đặt phần tử mới ở đâu và phần tử đó đã có chưa, cây chỉ dùng comparator: nhỏ hơn thì rẽ trái, lớn hơn thì rẽ phải, bằng 0 thì "đã có rồi". Ở cả hai việc này, nó không gọi `equals`. [Javadoc của `TreeSet`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/TreeSet.html) nói rõ điều này: set dùng `compare` cho mọi phép so sánh, nên chỉ tuân đúng hợp đồng của `Set` khi thứ tự nhất quán với `equals`. [`TreeMap`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/TreeMap.html) cũng vậy: hai khoá có `compare` bằng 0 là cùng một khoá, nên `put` khoá thứ hai thay giá trị đã gắn với khoá thứ nhất.

Cách sửa là thêm một tiêu chí phân định cuối cùng, là một khoá duy nhất như SKU, để comparator chỉ trả 0 khi hai phần tử thật sự là một:

```java
record Product(String sku, long price) {}

void main() {
    List<Product> catalog = List.of(
            new Product("KB-02", 1_290_000), new Product("MS-01", 450_000),
            new Product("CB-05", 120_000), new Product("PD-04", 120_000));

    Set<Product> byPrice = new TreeSet<>(Comparator.comparingLong(Product::price)
            .thenComparing(Product::sku));
    byPrice.addAll(catalog);
    for (Product p : byPrice) {
        IO.println(p.sku() + " " + p.price());
    }
}
```

Kết quả:

```text
CB-05 120000
PD-04 120000
MS-01 450000
KB-02 1290000
```

Đủ bốn món, cùng giá thì xếp theo SKU.

<Callout kind="production">

Trang "Hàng bán chạy" giữ top sản phẩm trong một `TreeSet<Product>` với comparator theo doanh số. Hai sản phẩm có cùng doanh số, nên `add` sản phẩm thứ hai trả `false` và nó biến mất khỏi trang. Không exception, không log; chỉ có nhà cung cấp gọi điện hỏi vì sao hàng của họ không hiện.

</Callout>

Comparator dùng cho `TreeSet` hay `TreeMap` phải phân biệt được mọi phần tử khác nhau; với `List.sort` thì không cần, vì list không bỏ phần tử nào.

### Optional: kết quả có thể vắng mặt

`Map.get` trả `null` khi không có khoá. Ở J5.1, bên gọi quên kiểm tra `null` và nhận `NullPointerException` ở một dòng cách xa chỗ gây ra nó. Chữ ký `Product find(String sku)` không cho bên gọi biết rằng có thể không có kết quả.

**Optional** (`Optional<T>`, từ Java 8) là một hộp chứa 0 hoặc 1 giá trị. Trả `Optional<Product>` thay cho `Product` đưa trường hợp "không có" vào ngay chữ ký của method. Đoạn sau tra hai SKU, một có và một không, rồi đòi bắt buộc phải có một SKU. `map(f)` của `Optional` (không liên quan tới `Map`) áp hàm `f` lên giá trị bên trong nếu có. `() -> new IllegalArgumentException(...)` là lambda không có tham số: một hàm tạo exception, chỉ được gọi khi cần.

```java
record Product(String sku, String name, long price) {}

Map<String, Product> bySku = Map.of(
        "KB-02", new Product("KB-02", "Ban phim co", 1_290_000),
        "MS-01", new Product("MS-01", "Chuot khong day", 450_000));

Optional<Product> find(String sku) {
    return Optional.ofNullable(bySku.get(sku));
}

void main() {
    for (String sku : List.of("MS-01", "XX-99")) {
        String label = find(sku).map(Product::name).orElse("(khong co)");
        IO.println(sku + " -> " + label);
    }
    find("XX-99").orElseThrow(() -> new IllegalArgumentException("unknown sku: XX-99"));
}
```

Kết quả:

```text
MS-01 -> Chuot khong day
XX-99 -> (khong co)
Exception in thread "main" java.lang.IllegalArgumentException: unknown sku: XX-99
	at FindOptional.lambda$main$0(FindOptional.java:16)
	at java.base/java.util.Optional.orElseThrow(Optional.java:403)
	at FindOptional.main(FindOptional.java:16)
```

Khi "không có" là chuyện bình thường, như SKU người dùng gõ vào ô tìm kiếm, `map` và `orElse` cho ra một giá trị thay thế mà không cần dòng `if (x != null)` nào. Khi kết quả bắt buộc phải có, như SKU trong một đơn đã thanh toán, `orElseThrow` nổ ngay tại chỗ với thông báo do bạn viết. Exception ở cuối output là cố ý; dòng `lambda$main$0` trong stack trace là lambda bạn truyền cho `orElseThrow`. J4 bàn chuyện chọn loại exception cho trường hợp này.

Một lợi ích quan trọng của `Optional` đến từ trình biên dịch. Khi bạn đổi `find` từ trả `Product` sang trả `Optional<Product>`, mọi chỗ gọi cũ đang dùng kết quả như một `Product` đều không biên dịch nữa:

```java
record Product(String sku, long price) {}

Optional<Product> find(String sku) {
    return Optional.empty();
}

void main() {
    Product product = find("KB-02");
}
```

Kết quả:

```text
CompileGuard.java:8: error: incompatible types: Optional<Product> cannot be converted to Product
    Product product = find("KB-02");
                          ^
1 error
error: compilation failed
```

Với một project nhiều file, `javac` liệt kê từng chỗ gọi như vậy. Bạn phải quyết định ở mỗi chỗ: kết quả ở đây chắc chắn có (`orElseThrow()`) hay có thể vắng (`orElse`, `map`). Với `null`, quyết định đó không có ai nhắc. Trình biên dịch không bắt được một trường hợp: chỗ gọi cũ viết `if (find(sku) == null)` vẫn biên dịch, vì so một `Optional` với `null` là hợp lệ, nhưng giờ điều kiện luôn sai. Khi đổi sang `Optional`, tìm thêm các phép so với `null` như vậy.

Bảng dưới là các method của `Optional` mà bài này dùng:

| Method | Khi rỗng | Khi có giá trị `v` |
|---|---|---|
| `map(f)` | Rỗng | `Optional` chứa `f(v)` |
| `orElse(x)` | `x` | `v`; xem bên dưới về lúc `x` được tính |
| `orElseGet(() -> ...)` | Gọi hàm để tạo giá trị | `v`; hàm không được gọi |
| `orElseThrow()` | `NoSuchElementException: No value present` | `v` |
| `orElseThrow(() -> new ...)` | Ném exception bạn tạo | `v` |
| `isPresent()` | `false` | `true` |
| `get()` | `NoSuchElementException` | `v`; tránh dùng, tên nó không nói lên rủi ro |

Một hiểu lầm hay gặp là `orElse(x)` chỉ tính `x` khi `Optional` rỗng. `orElse` là một method bình thường, nên Java tính đối số trước khi gọi nó, dù kết quả có được dùng hay không. Đoạn sau gọi một hàm tạo sản phẩm mặc định, có in ra mỗi lần được gọi:

```java
record Product(String sku, String name) {}

Product loadDefault() {
    IO.println("  (goi loadDefault)");
    return new Product("??", "San pham mac dinh");
}

void main() {
    Optional<Product> found = Optional.of(new Product("KB-02", "Ban phim co"));

    IO.println("orElse:");
    IO.println("  " + found.orElse(loadDefault()).name());
    IO.println("orElseGet:");
    IO.println("  " + found.orElseGet(() -> loadDefault()).name());
}
```

Kết quả:

```text
orElse:
  (goi loadDefault)
  Ban phim co
orElseGet:
  Ban phim co
```

`Optional` đã có giá trị, vậy mà `orElse` vẫn chạy `loadDefault()`. Nếu hàm đó gọi database hay tạo đối tượng tốn kém, bạn trả chi phí đó ở mọi lần gọi. `orElseGet` nhận một hàm và chỉ gọi nó khi rỗng. Dùng `orElse` cho hằng số hoặc giá trị đã có sẵn, `orElseGet` cho giá trị phải tính.

Tạo `Optional` cũng có bẫy: `Optional.of(null)` ném `NullPointerException`. Khi giá trị có thể là `null`, như kết quả của `Map.get`, dùng `Optional.ofNullable`, như `find` ở trên.

API Note trong [Javadoc của `Optional`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Optional.html) nói nó chủ yếu dùng làm **kiểu trả về** của method, khi cần biểu diễn "không có kết quả". Dùng nó cho field, tham số hay phần tử của collection không bị cấm, nhưng là cách viết nên tránh theo quy ước phổ biến. Làm tham số, `Optional` bắt mọi bên gọi phải bọc giá trị, và vẫn có người truyền `null` thay cho `Optional.empty()`; hai method overload, một có và một không có tham số, rõ hơn. Làm field, nó tốn thêm một đối tượng cho mỗi giá trị; bên trong lớp, một field có thể `null` cộng với getter trả `Optional` là đủ. Với collection, trả về list rỗng thay cho `Optional<List<...>>`.

### Collection không sửa được: view khác bản sao

Lớp danh mục sản phẩm đưa danh sách sản phẩm ra ngoài bằng `Collections.unmodifiableList`, để bên gọi không sửa được. Bên gọi đúng là không sửa được, nhưng danh sách họ đang cầm vẫn thay đổi mỗi khi danh mục thêm hàng.

Một collection **không sửa được** (unmodifiable) là collection không cho thêm, xoá hay thay phần tử: mọi thao tác thay đổi ném `UnsupportedOperationException`. Nếu thêm điều kiện là các phần tử cũng không đổi được, collection đó **bất biến** (immutable). Từ Java 9, `List.of`, `Set.of`, `Map.of` tạo collection không sửa được; từ Java 10 có thêm `List.copyOf`, `Set.copyOf`, `Map.copyOf`. `Collections.unmodifiableList` thì khác: nó tạo một **view** (lớp nhìn) lên list gốc, chặn sửa qua view nhưng không chép dữ liệu. Đoạn sau tạo cả hai từ cùng một `source`, rồi sửa `source`:

```java
void main() {
    List<String> source = new ArrayList<>(List.of("KB-02", "MS-01"));
    List<String> view = Collections.unmodifiableList(source);
    List<String> copy = List.copyOf(source);

    source.add("HD-07");
    IO.println("view = " + view);
    IO.println("copy = " + copy);
    view.add("SP-03");
}
```

<Predict question='Sau source.add("HD-07"), copy có thấy HD-07 không? Dòng view.add cuối cùng có chạy được không?'>

```text
view = [KB-02, MS-01, HD-07]
copy = [KB-02, MS-01]
Exception in thread "main" java.lang.UnsupportedOperationException
	at java.base/java.util.Collections$UnmodifiableCollection.add(Collections.java:1093)
	at ViewVsCopy.main(ViewVsCopy.java:9)
```

`view` thấy `HD-07` dù không ai sửa qua `view`. `copy` giữ nguyên hai phần tử. Sửa qua `view` thì bị chặn.

</Predict>

`view` và `copy` đều chặn sửa, nhưng chỉ `copy` tách khỏi dữ liệu gốc:

```text
 source ──► [KB-02, MS-01, HD-07]     ArrayList, ai giữ source vẫn sửa được
               ▲
 view ─────────┘                       unmodifiableList: chặn sửa qua view,
                                       nhưng vẫn thấy mọi thay đổi của source

 copy ──► [KB-02, MS-01]               List.copyOf: bản sao riêng, không ai sửa được
```

Điểm cần chú ý là `unmodifiableList` chỉ bảo vệ được khi không còn ai giữ tham chiếu tới `source`, vì `view` đọc thẳng từ đó ở mỗi lần đọc. Bảng dưới so bốn cách tạo list từ một list có sẵn:

| Cách tạo | Sửa được | Thấy thay đổi của nguồn | Nhận `null` |
|---|---|---|---|
| `new ArrayList<>(src)` | Có | Không, là bản sao | Có |
| `Collections.unmodifiableList(src)` | Không, qua view | Có | Có |
| `List.copyOf(src)` | Không | Không | Không, ném `NullPointerException` |
| `List.of(a, b)` | Không | Không áp dụng | Không, ném `NullPointerException` |

Collection tạo bởi `List.of`, `Set.of`, `Map.of` và các bản `copyOf` còn vài hành vi cần biết, nhất là khi dữ liệu đến từ người dùng. Mục [Unmodifiable Lists](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html#unmodifiable) trong Javadoc của `List` mô tả đủ các hành vi này:

| Đầu vào | Hành vi |
|---|---|
| `add`, `remove`, `sort` trên list tạo bởi `List.of`, `List.copyOf` | `UnsupportedOperationException`; cần sửa thì chép sang `new ArrayList<>(...)` |
| `Map.of("KB-02", 1, "KB-02", 2)` | `IllegalArgumentException: duplicate key: KB-02` |
| `Set.of("KB-02", "KB-02")` | `IllegalArgumentException: duplicate element: KB-02` |
| `List.copyOf` một list có phần tử `null` | `NullPointerException` |
| Duyệt `Set.of(...)` hoặc `Map.of(...)` | Thứ tự không xác định, đổi giữa các lần chạy chương trình |

Dòng cuối dễ bị bỏ qua vì trong một lần chạy, thứ tự trông ổn định. Chạy đoạn sau vài lần:

```java
void main() {
    IO.println(Set.of("KB-02", "MS-01", "HD-07", "SP-03", "CB-05"));
}
```

Kết quả sẽ giống thế này, nhưng thứ tự trên máy bạn sẽ khác, và có thể đổi sau mỗi lần chạy:

```text
[MS-01, CB-05, HD-07, SP-03, KB-02]
```

Đừng viết code hay test dựa vào thứ tự đó. Cần thứ tự cố định thì dùng `List.of` khi không cần loại phần tử trùng, hoặc `LinkedHashSet`, `LinkedHashMap` để giữ thứ tự thêm vào.

Cuối cùng, "không sửa được" chỉ áp cho bản thân collection, không áp cho phần tử bên trong. Collection không sửa được chưa chắc đã bất biến:

```java
void main() {
    List<StringBuilder> notes = List.of(new StringBuilder("Giao gio hanh chinh"));
    notes.get(0).append(", goi truoc 30 phut");
    IO.println(notes);
}
```

Kết quả:

```text
[Giao gio hanh chinh, goi truoc 30 phut]
```

List vẫn một phần tử, nhưng phần tử đó là một `StringBuilder` sửa được nên nội dung đã đổi. Với record mà mọi field đều bất biến, như `Product` ở trên, list không sửa được của nó cũng là list bất biến.

### Sao chép phòng thủ trong constructor

Một đơn hàng đã thanh toán bỗng có 0 dòng hàng. Không ai gọi method nào của đơn hàng; code ở nơi khác chỉ dọn sạch list tạm đã dùng để tạo nó.

Đoạn sau tái hiện lỗi đó. Record `Order` nhận thẳng list mà bên gọi đưa vào:

```java
record Product(String sku, long price) {}

record Order(String id, List<Product> lines) {}

void main() {
    List<Product> lines = new ArrayList<>();
    lines.add(new Product("KB-02", 1_290_000));
    lines.add(new Product("MS-01", 450_000));
    Order order = new Order("DH-1001", lines);

    lines.clear();
    IO.println("order lines = " + order.lines().size());
}
```

Kết quả:

```text
order lines = 0
```

Record không chép gì: field `lines` của `order` và biến `lines` của bên gọi là cùng một đối tượng, nên `lines.clear()` xoá luôn dòng hàng của đơn. **Sao chép phòng thủ** (defensive copy) là chép dữ liệu đầu vào thành bản riêng ngay khi nhận, để đối tượng không phụ thuộc vào thứ bên gọi còn giữ. Với record, chỗ làm việc này là compact constructor:

```java
record Product(String sku, long price) {}

record Order(String id, List<Product> lines) {
    Order {
        lines = List.copyOf(lines);
    }
}

void main() {
    List<Product> lines = new ArrayList<>();
    lines.add(new Product("KB-02", 1_290_000));
    lines.add(new Product("MS-01", 450_000));
    Order order = new Order("DH-1001", lines);

    lines.clear();
    IO.println("order lines = " + order.lines().size());
}
```

Kết quả:

```text
order lines = 2
```

Hai chương trình chỉ khác nhau ở dòng `lines = List.copyOf(lines);`. `List.copyOf` vừa tách đơn hàng khỏi list của bên gọi, vừa làm `order.lines()` không sửa được, nên cả bên gọi lẫn người nhận đơn hàng đều không đổi được dòng hàng của nó.

Bạn có thể lo rằng chép list ở mọi constructor tốn kém, nhất là khi một list đi qua nhiều tầng và tầng nào cũng gọi `List.copyOf`. Đoạn sau gọi `List.copyOf` trên một list đã chép, và trên một view, rồi so tham chiếu bằng `==`:

```java
void main() {
    List<String> first = List.copyOf(new ArrayList<>(List.of("KB-02", "MS-01")));
    List<String> second = List.copyOf(first);
    List<String> view = Collections.unmodifiableList(new ArrayList<>(first));

    IO.println("copyOf(first) == first? " + (second == first));
    IO.println("copyOf(view) == view?   " + (List.copyOf(view) == view));
}
```

Kết quả:

```text
copyOf(first) == first? true
copyOf(view) == view?   false
```

Với list tạo bởi `List.of` hay `List.copyOf`, lần gọi sau trả lại chính list đó, không chép. Với view, nó vẫn chép, vì dữ liệu sau view còn có thể đổi. [Javadoc của `List.copyOf`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/List.html#copyOf(java.util.Collection)) chỉ hứa rằng thường không tạo bản sao, nên bạn không viết code dựa vào việc `==` trả `true`; nhưng bạn có thể yên tâm rằng chỉ tầng đầu tiên tốn chi phí chép.

<Callout kind="ai">

AI hay gọi `optional.get()` ngay sau `isPresent()` thay vì `map` hay `orElse`, hay dùng `orElse` với một lời gọi tốn kém, hay dùng Optional cho field và tham số, hay quên tiêu chí phân định cuối cùng cho comparator dùng trong `TreeSet`, và hay nói `Collections.unmodifiableList` là "bất biến". Kiểm tra lại bằng một test nhỏ: hai phần tử bằng nhau theo tiêu chí chính, một SKU không tồn tại, và một lần sửa list nguồn sau khi tạo đối tượng.

</Callout>
