<Goal>

Viết được lớp và method generic cho code thật, đọc được chữ ký generic trong Javadoc của JDK, và chọn đúng wildcard cho tham số. Học xong bài này, bạn giải thích được:

- Vì sao `List<Product>` không truyền được vào method nhận `List<Priced>`, dù `Product` cài `Priced`.
- Vì sao một `ClassCastException` nổ ở dòng `tags.get(0)` trong khi lỗi thật nằm ở một phép ép kiểu phía trên.
- Vì sao `Collections.max` khai báo `<T extends Object & Comparable<? super T>>` thay vì `<T extends Comparable<T>>`.

</Goal>

<Knowledge>

Ví dụ trong bài dùng tiếp cửa hàng của J5.1. Hoá đơn có hai loại dòng: sản phẩm (`Product`) và phí giao hàng (`ShippingFee`). Cả hai cài interface `Priced`, nghĩa là "thứ có giá và được tính vào hoá đơn".

### Raw type: lỗi kiểu chỉ lộ ra lúc chạy

Giỏ hàng chứa các SKU, và một dòng code thêm nhầm giá tiền vào giỏ thay cho SKU. Chương trình biên dịch được, in món đầu tiên, rồi nổ `ClassCastException` khi gặp món thứ hai.

Trước Java 5, `List` chứa `Object`: thêm gì cũng được, và lấy ra thì bạn phải tự ép kiểu. Kiểu `List` viết trần như vậy, không kèm tham số kiểu, gọi là **raw type**. Đoạn sau viết theo cách đó:

```java
void main() {
    List cart = new ArrayList();
    cart.add("KB-02");
    cart.add(450_000L);
    for (Object item : cart) {
        String sku = (String) item;
        IO.println(sku.toLowerCase());
    }
}
```

Kết quả:

```text
RawCart.java:3: warning: [unchecked] unchecked call to add(E) as a member of the raw type List
    cart.add("KB-02");
            ^
  where E is a type-variable:
    E extends Object declared in interface List
RawCart.java:4: warning: [unchecked] unchecked call to add(E) as a member of the raw type List
    cart.add(450_000L);
            ^
  where E is a type-variable:
    E extends Object declared in interface List
2 warnings
kb-02
Exception in thread "main" java.lang.ClassCastException: class java.lang.Long cannot be cast to class java.lang.String (java.lang.Long and java.lang.String are in module java.base of loader 'bootstrap')
	at RawCart.main(RawCart.java:6)
```

Các dòng từ đầu tới `2 warnings` là cảnh báo của trình biên dịch, in ra trước khi chương trình chạy: nó cảnh báo hai lần nhưng vẫn cho chạy. Món đầu in ra bình thường; lỗi chỉ lộ khi vòng lặp gặp phần tử thứ hai, ở dòng 6 (dòng ép kiểu), không phải ở dòng 4, dòng thêm nhầm. Trong một hệ thống thật, hai dòng đó có thể nằm ở hai lớp khác nhau.

**Generics** cho lớp và method nhận **tham số kiểu** (type parameter). `List<String>` nói với trình biên dịch "list này chỉ chứa `String`". Đoạn sau chỉ khác đoạn trên ở khai báo `cart`, và vòng lặp không còn phải ép kiểu:

```java
void main() {
    List<String> cart = new ArrayList<>();
    cart.add("KB-02");
    cart.add(450_000L);
    for (String sku : cart) {
        IO.println(sku.toLowerCase());
    }
}
```

Kết quả:

```text
TypedCart.java:4: error: no suitable method found for add(long)
    cart.add(450_000L);
        ^
    method List.add(String) is not applicable
      (argument mismatch; long cannot be converted to String)
    method List.add(int,String) is not applicable
      (actual and formal argument lists differ in length)
1 error
error: compilation failed
```

Cùng một lỗi, nhưng giờ chương trình không chạy được, và thông báo chỉ đúng dòng 4, dòng thêm nhầm. Generics dời lỗi kiểu từ lúc chạy, có khi trên production, về lúc biên dịch trên máy bạn. Raw type chỉ còn để tương thích với code viết trước Java 5; trong code mới, gặp raw type là gặp một lỗi tiềm ẩn.

### Lớp và method generic

Trang danh mục chia sản phẩm thành từng trang, và trang tìm đơn hàng cũng chia mã đơn thành từng trang. Logic chia trang giống hệt nhau, chỉ khác kiểu phần tử. Bạn không muốn viết hai lớp `ProductPage` và `OrderPage`.

Một **lớp generic** khai báo tham số kiểu sau tên lớp, ví dụ `record Page<T>`: `T` là tên đặt chỗ cho một kiểu mà bên dùng sẽ chọn. Một **method generic** khai báo tham số kiểu riêng, đặt trước kiểu trả về, ví dụ `static <T> Page<T> of(...)`. Đoạn sau dùng cùng một `Page` cho sản phẩm và cho mã đơn. `subList(from, to)` là phần của list từ vị trí `from` tới trước `to`; `Page` chép phần đó sang một `ArrayList` riêng.

```java
record Product(String sku, long price) {
    public String toString() { return sku; }
}

record Page<T>(List<T> items, int number, int totalPages) {
    static <T> Page<T> of(List<T> all, int number, int size) {
        int from = Math.min((number - 1) * size, all.size());
        int to = Math.min(from + size, all.size());
        int totalPages = (all.size() + size - 1) / size;
        return new Page<>(new ArrayList<>(all.subList(from, to)), number, totalPages);
    }
}

void main() {
    List<Product> catalog = List.of(
            new Product("KB-02", 1_290_000), new Product("MS-01", 450_000), new Product("HD-07", 890_000),
            new Product("SP-03", 1_150_000), new Product("CB-05", 120_000), new Product("PD-04", 120_000));
    Page<Product> second = Page.of(catalog, 2, 4);
    IO.println("san pham, trang " + second.number() + "/" + second.totalPages() + ": " + second.items());

    Page<String> orders = Page.of(List.of("DH-1001", "DH-1002", "DH-1003"), 1, 2);
    String first = orders.items().get(0);
    IO.println("don hang, trang 1/" + orders.totalPages() + ": " + orders.items() + ", dau tien " + first);
}
```

Kết quả:

```text
san pham, trang 2/2: [CB-05, PD-04]
don hang, trang 1/2: [DH-1001, DH-1002], dau tien DH-1001
```

Một `Page` phục vụ cả hai kiểu. `orders.items().get(0)` trả thẳng `String`, không cần ép kiểu, vì kiểu của `orders` là `Page<String>`. Bạn cũng không phải viết `Page.<Product>of(...)`: trình biên dịch **suy ra** (infer) `T` từ đối số và từ kiểu biến nhận kết quả. `of` là method `static`, không thuộc về một `Page` cụ thể nào, nên nó không dùng được `T` của lớp và phải khai báo `<T>` của riêng mình. Bảng dưới gom các thuật ngữ vừa gặp:

| Thuật ngữ | Ví dụ | Ý nghĩa |
|---|---|---|
| Type parameter | `T` trong `record Page<T>` | Tên đặt chỗ cho một kiểu, do bên dùng chọn |
| Type argument | `Product` trong `Page<Product>` | Kiểu cụ thể thay vào `T` |
| Diamond | `new Page<>(...)`, `new ArrayList<>()` | Để trình biên dịch tự suy ra type argument |
| Generic method | `static <T> Page<T> of(...)` | Method có type parameter riêng, khai báo trước kiểu trả về |

Quy ước đặt tên type parameter là một chữ in hoa: `T` (type), `E` (element), `K`, `V` (key, value), `R` (result). Javadoc của JDK dùng đúng các tên này, ví dụ `List<E>`, `Map<K, V>`.

### Bounded type: khi cần gọi method của T

Hoá đơn cần SKU lớn nhất theo thứ tự chữ cái để in mã tham chiếu, và báo cáo cần giá cao nhất. Bạn viết một method `max` dùng cho mọi kiểu, và trình biên dịch từ chối dòng so sánh.

Với một `T` bất kỳ, trình biên dịch chỉ biết `T` là một `Object`, nên chỉ cho gọi các method của `Object`. Để so hai phần tử, `max` cần `compareTo` của interface **`Comparable<T>`**: `a.compareTo(b)` trả số âm, `0` hoặc số dương khi `a` đứng trước, ngang hoặc sau `b`. `String`, `Long` và `LocalDate` đều cài `Comparable`; J5.3 học kỹ interface này. Đoạn sau viết `max` không nói gì về `T`:

```java
static <T> T max(Collection<T> items) {
    T best = null;
    for (T item : items) {
        if (best == null || item.compareTo(best) > 0) {
            best = item;
        }
    }
    return best;
}

void main() {
    IO.println(max(List.of("KB-02", "SP-03", "MS-01")));
}
```

Kết quả:

```text
NoBound.java:4: error: cannot find symbol
        if (best == null || item.compareTo(best) > 0) {
                                ^
  symbol:   method compareTo(T)
  location: variable item of type T
  where T is a type-variable:
    T extends Object declared in method <T>max(Collection<T>)
1 error
error: compilation failed
```

Dòng cuối của thông báo nói đúng điều trình biên dịch biết: `T extends Object`. Một **bounded type** (tham số kiểu có giới hạn) nói thêm `T` phải là kiểu con của một kiểu khác: `<T extends Comparable<T>>` nghĩa là "`T` so được với chính `T`". Trong bound, `extends` dùng cho cả lớp lẫn interface. Đoạn sau chỉ thêm bound vào chữ ký, thân method giữ nguyên, kèm một exception khi collection rỗng:

```java
static <T extends Comparable<T>> T max(Collection<T> items) {
    T best = null;
    for (T item : items) {
        if (best == null || item.compareTo(best) > 0) {
            best = item;
        }
    }
    if (best == null) {
        throw new NoSuchElementException("max of empty collection");
    }
    return best;
}

void main() {
    IO.println("SKU lon nhat: " + max(List.of("KB-02", "SP-03", "MS-01")));
    IO.println("gia cao nhat: " + max(List.of(1_290_000L, 450_000L, 890_000L)));
}
```

Kết quả:

```text
SKU lon nhat: SP-03
gia cao nhat: 1290000
```

Cùng một `max` chạy với `String` và `Long`, và bên gọi nhận lại đúng kiểu đã đưa vào. Đổi lại, `max` từ chối mọi kiểu không cài `Comparable`, ngay lúc biên dịch. Bound `Comparable<T>` này còn chặt hơn mức cần; mục cuối bài cho thấy nó từ chối cả `LocalDate` và cách nới nó ra.

### Type erasure: generics chỉ có lúc biên dịch

`List<String>` và `List<Long>` trông như hai kiểu khác nhau. Vậy mà lúc chạy, JVM không phân biệt được chúng, và một `List<String>` có thể chứa số nguyên mà không ai báo lỗi.

**Type erasure** (xoá kiểu) là cách Java cài generics: sau khi kiểm tra kiểu, `javac` xoá tham số kiểu khỏi bytecode, thay mỗi `T` bằng bound của nó (`Object` nếu không có bound), và chèn phép ép kiểu ở chỗ lấy giá trị ra. Đoạn sau kiểm điều đó bằng **reflection**, API để chương trình đọc thông tin về lớp và method của chính nó lúc chạy. `getClass()` trả lớp của một đối tượng lúc chạy; `getClass().getDeclaredMethod("max", Collection.class)` tìm trong lớp của chương trình method `max` có một tham số kiểu `Collection`. `throws Exception` có mặt vì `getDeclaredMethod` khai báo checked exception (J4).

```java
static <T extends Comparable<T>> T max(Collection<T> items) {
    T best = null;
    for (T item : items) {
        if (best == null || item.compareTo(best) > 0) {
            best = item;
        }
    }
    return best;
}

void main() throws Exception {
    List<String> skus = new ArrayList<>();
    List<Long> prices = new ArrayList<>();
    IO.println("cung mot lop? " + (skus.getClass() == prices.getClass()));

    var method = getClass().getDeclaredMethod("max", Collection.class);
    IO.println("khai bao: tra ve " + method.getGenericReturnType() + ", tham so " + method.getGenericParameterTypes()[0]);
    IO.println("JVM chay: tra ve " + method.getReturnType().getName() + ", tham so " + method.getParameterTypes()[0].getName());
}
```

Kết quả:

```text
cung mot lop? true
khai bao: tra ve T, tham so java.util.Collection<T>
JVM chay: tra ve java.lang.Comparable, tham so java.util.Collection
```

Lúc chạy, `ArrayList<String>` và `ArrayList<Long>` là cùng một lớp `ArrayList`. Method `max` mà JVM chạy nhận một `Collection` trơn và trả về `Comparable`, tức bound của `T`. Phần generic (`T`, `Collection<T>`) vẫn được lưu trong file `.class`, nhưng chỉ làm thông tin cho trình biên dịch và reflection; nó không tham gia kiểm tra kiểu lúc chạy. Sơ đồ dưới tóm tắt `javac` biến đổi code thế nào:

```text
 Mã nguồn                         javac kiểm tra kiểu        Bytecode (đã xoá kiểu)
 List<String> tags = ...;   ──►   tags.add(42) -> lỗi   ──►  List tags
 String s = tags.get(0);                                     String s = (String) tags.get(0)
                                                                        └ checkcast chèn tự động
 <T extends Comparable<T>>                                   T thay bằng bound: Comparable
 T max(Collection<T>)                                        Comparable max(Collection)
```

`checkcast` là lệnh bytecode kiểm tra ép kiểu. Điểm cần nhớ là nó nằm ở chỗ **lấy phần tử ra**, không ở chỗ phần tử được đưa vào. Hệ quả hiện ra khi dữ liệu đến từ bên ngoài, ví dụ JSON đã parse thành `Map<String, Object>`, nơi bên gửi đưa số thay cho chuỗi:

```java
void main() {
    Map<String, Object> json = new HashMap<>();
    json.put("tags", new ArrayList<>(List.of(101, 102)));

    List<String> tags = (List<String>) json.get("tags");
    IO.println("tags = " + tags);
    String first = tags.get(0);
    IO.println(first.toUpperCase());
}
```

Kết quả:

```text
Erasure.java:5: warning: [unchecked] unchecked cast
    List<String> tags = (List<String>) json.get("tags");
                                               ^
  required: List<String>
  found:    Object
1 warning
tags = [101, 102]
Exception in thread "main" java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')
	at Erasure.main(Erasure.java:7)
```

Thử tự trả lời trước khi đọc tiếp: vì sao dòng 5 ép một list số thành `List<String>` mà không lỗi, còn exception nổ ở dòng 7?

Lúc chạy, phép ép `(List<String>)` chỉ còn là ép sang `List`, và đối tượng đúng là một `List`, nên dòng 5 qua. Phần `<String>` không kiểm tra được vì nó đã bị xoá; `javac` biết vậy nên báo **unchecked warning** ("unchecked cast") ở đúng dòng này. In cả list ở dòng 6 cũng không cần ép phần tử nào. Phép ép sang `String` do `javac` chèn nằm ở `tags.get(0)`, dòng 7, nên lỗi nổ ở đó. Tình trạng một `List<String>` thực ra chứa `Integer` gọi là **heap pollution**: kiểu khai báo của biến nói một đằng, dữ liệu trong bộ nhớ là một nẻo.

<Callout kind="production">

Một service đọc JSON thành `Map<String, Object>`, viết `List<String> tags = (List<String>) json.get("tags");` và thêm `@SuppressWarnings("unchecked")` để tắt cảnh báo. Một ngày đối tác gửi `"tags": [101, 102]`. Dòng ép kiểu chạy êm, list được truyền qua ba lớp code, và `ClassCastException` nổ ở một nơi chẳng liên quan gì tới JSON. Cách đúng là kiểm tra kiểu từng phần tử ngay ở biên (boundary), nơi dữ liệu đi vào hệ thống, hoặc để thư viện JSON map thẳng vào một `record` có kiểu rõ ràng.

</Callout>

Erasure còn kéo theo một số việc không làm được với generics. Bảng dưới là những giới hạn hay gặp; danh sách đầy đủ ở bài "Restriction on Generics" trong phần Tài liệu.

| Không làm được | Lý do | Cách thay |
|---|---|---|
| `new T()`, `new T[10]` | Lúc chạy không biết `T` là gì | Nhận `Class<T>` hoặc dùng `List<T>` |
| `x instanceof List<String>` | Lúc chạy chỉ còn `List` | `x instanceof List<?>` rồi kiểm tra từng phần tử |
| `List<int>` | Tham số kiểu phải là kiểu tham chiếu | `List<Integer>`, kèm bẫy `remove(int)` ở J5.1 |
| Hai overload `m(List<String>)` và `m(List<Long>)` | Sau khi xoá, hai chữ ký giống hệt | Đặt tên method khác nhau |

### Generics bất biến

Method `total` cộng giá mọi dòng của một hoá đơn, nhận `Collection<Priced>`. Gọi nó với danh sách dòng hoá đơn thì chạy, nhưng gọi với giỏ hàng chỉ có sản phẩm thì không biên dịch, dù mọi `Product` đều là một `Priced`. `Collection` là interface cha của `List` và `Set` (J5.1), nên `total` nhận được cả hai.

```java
interface Priced {
    long price();
}

record Product(String sku, long price) implements Priced {}

record ShippingFee(String zone, long price) implements Priced {}

long total(Collection<Priced> items) {
    long sum = 0;
    for (Priced item : items) {
        sum += item.price();
    }
    return sum;
}

void main() {
    List<Priced> lines = List.of(new Product("KB-02", 1_290_000), new ShippingFee("noi-thanh", 30_000));
    List<Product> cart = List.of(new Product("KB-02", 1_290_000), new Product("MS-01", 450_000));
    IO.println("lines = " + total(lines));
    IO.println("cart  = " + total(cart));
}
```

<Predict question="Lời gọi nào không biên dịch: total(lines), total(cart), hay cả hai?">

```text
InvoiceTotal.java:21: error: method total in class InvoiceTotal cannot be applied to given types;
    IO.println("cart  = " + total(cart));
                            ^
  required: Collection<Priced>
  found:    List<Product>
  reason: argument mismatch; List<Product> cannot be converted to Collection<Priced>
1 error
error: compilation failed
```

Chỉ `total(cart)`. `lines` đúng là `List<Priced>` nên được nhận; `cart` là `List<Product>` thì không.

</Predict>

`Product` là kiểu con của `Priced`, nhưng `List<Product>` **không** phải kiểu con của `List<Priced>`. Generics là **bất biến** (invariant): `A<X>` và `A<Y>` không có quan hệ cha con, dù `X` và `Y` có. Lý do nằm ở thao tác ghi. Nếu Java cho gán `List<Product>` vào `List<Priced>`, code sau sẽ biên dịch được:

```java
interface Priced {
    long price();
}

record Product(String sku, long price) implements Priced {}

record ShippingFee(String zone, long price) implements Priced {}

void main() {
    List<Product> products = new ArrayList<>();
    List<Priced> lines = products;
    lines.add(new ShippingFee("noi-thanh", 30_000));
}
```

Kết quả:

```text
Invariance.java:11: error: incompatible types: List<Product> cannot be converted to List<Priced>
    List<Priced> lines = products;
                         ^
1 error
error: compilation failed
```

`lines` và `products` là cùng một list. Nếu dòng 11 được phép, dòng 12 sẽ đưa một `ShippingFee` vào list mà mọi chỗ khác tin là chỉ chứa `Product`, và ai lấy phần tử đó ra dưới dạng `Product` sẽ nhận `ClassCastException`. Vì erasure, lúc chạy JVM không biết list này là `List<Product>` để chặn lần `add`, nên Java chặn từ phép gán, lúc biên dịch.

Mảng thì khác: `String[]` là một `Object[]`, tức mảng **hiệp biến** (covariant). Đoạn sau đi đúng con đường vừa bị generics chặn, nhưng với mảng:

```java
void main() {
    String[] skus = new String[2];
    Object[] items = skus;
    items[0] = "KB-02";
    IO.println("ghi String: ok");
    items[1] = 450_000L;
}
```

Kết quả:

```text
ghi String: ok
Exception in thread "main" java.lang.ArrayStoreException: java.lang.Long
	at ArrayStore.main(ArrayStore.java:6)
```

Phép gán biên dịch được, và lỗi chỉ bị bắt lúc chạy, ở lần ghi sai kiểu. Mảng làm được vậy vì mỗi mảng nhớ kiểu phần tử của nó lúc chạy và kiểm tra từng lần ghi. Generics đã bị xoá kiểu nên không kiểm tra được lúc chạy; cách an toàn duy nhất là cấm ngay lúc biên dịch. Đó cũng là lý do Java không cho tạo mảng generic như `new List<String>[10]`: mảng đó không biết kiểm tra phần `<String>` khi ghi.

### Wildcard và PECS

`total` chỉ đọc phần tử ra để lấy giá, không ghi gì vào. Với một method chỉ đọc, chuyện `ShippingFee` lọt vào list sản phẩm không thể xảy ra, nên lẽ ra nó phải nhận được cả `List<Product>`.

**Wildcard** `?` là "một kiểu nào đó". `Collection<? extends Priced>` nghĩa là "collection của một kiểu con nào đó của `Priced`": nó nhận `List<Priced>`, `List<Product>`, `List<ShippingFee>`. Đoạn sau chỉ đổi kiểu tham số của `total` so với ví dụ ở mục trước:

```java
interface Priced {
    long price();
}

record Product(String sku, long price) implements Priced {}

record ShippingFee(String zone, long price) implements Priced {}

long total(Collection<? extends Priced> items) {
    long sum = 0;
    for (Priced item : items) {
        sum += item.price();
    }
    return sum;
}

void main() {
    List<Priced> lines = List.of(new Product("KB-02", 1_290_000), new ShippingFee("noi-thanh", 30_000));
    List<Product> cart = List.of(new Product("KB-02", 1_290_000), new Product("MS-01", 450_000));
    IO.println("lines = " + total(lines));
    IO.println("cart  = " + total(cart));
}
```

Kết quả:

```text
lines = 1320000
cart  = 1740000
```

Cả hai lời gọi đều chạy, thân method không đổi. Cái giá phải trả là không ghi được vào một `? extends`. Đoạn sau thử thêm phí giao hàng qua một biến `List<? extends Priced>`:

```java
interface Priced {
    long price();
}

record Product(String sku, long price) implements Priced {}

record ShippingFee(String zone, long price) implements Priced {}

void main() {
    List<Product> products = new ArrayList<>();
    List<? extends Priced> readable = products;
    readable.add(new ShippingFee("noi-thanh", 30_000));
}
```

Kết quả:

```text
Capture.java:12: error: no suitable method found for add(ShippingFee)
    readable.add(new ShippingFee("noi-thanh", 30_000));
            ^
    method List.add(CAP#1) is not applicable
      (argument mismatch; ShippingFee cannot be converted to CAP#1)
    method List.add(int,CAP#1) is not applicable
      (actual and formal argument lists differ in length)
  where CAP#1 is a fresh type-variable:
    CAP#1 extends Priced from capture of ? extends Priced
1 error
error: compilation failed
```

Dòng 11 hợp lệ: gán `List<Product>` vào `List<? extends Priced>` được phép. Dòng 12 bị chặn, vì `readable` có thể đang là `List<Product>`, và trình biên dịch không biết chính xác là kiểu nào. `CAP#1` là tên tạm nó đặt cho "kiểu con nào đó của `Priced`" mà biến đang giữ (**capture**); không giá trị nào ngoài `null` chắc chắn thuộc kiểu đó. Đây chính là kịch bản phá kiểu ở mục trước, bị chặn đúng chỗ.

Chiều ngược lại là `? super T`: "một kiểu cha nào đó của `T`". Bạn ghi được `T` vào nó, vì kiểu cha nào cũng chứa được `T`, nhưng đọc ra chỉ chắc chắn là `Object`. Đoạn sau chép dòng hoá đơn từ giỏ hàng sang danh sách `Priced`, rồi từ đó sang một nhật ký kiểu `Object`:

```java
interface Priced {
    long price();
}

record Product(String sku, long price) implements Priced {}

record ShippingFee(String zone, long price) implements Priced {}

static <T> void copyInto(Collection<? extends T> source, Collection<? super T> target) {
    for (T item : source) {
        target.add(item);
    }
}

void main() {
    List<Product> cart = List.of(new Product("KB-02", 1_290_000), new Product("MS-01", 450_000));
    List<Priced> lines = new ArrayList<>();
    copyInto(cart, lines);
    lines.add(new ShippingFee("noi-thanh", 30_000));

    List<Object> audit = new ArrayList<>();
    copyInto(lines, audit);
    IO.println("lines: " + lines.size() + " dong");
    IO.println("audit: " + audit.size() + " dong, dong cuoi " + audit.get(2));
}
```

Kết quả:

```text
lines: 3 dong
audit: 3 dong, dong cuoi ShippingFee[zone=noi-thanh, price=30000]
```

Một `copyInto` chép `Product` vào `List<Priced>`, rồi chép `Priced` vào `List<Object>`. `source` chỉ cung cấp phần tử nên dùng `? extends T`; `target` chỉ nhận phần tử nên dùng `? super T`. Bảng dưới so các cách khai báo tham số:

| Khai báo | Nhận được | Đọc ra | Ghi vào |
|---|---|---|---|
| `List<Priced>` | Chỉ `List<Priced>` | `Priced` | `Priced` |
| `List<? extends Priced>` | `List<Priced>`, `List<Product>`, `List<ShippingFee>` | `Priced` | Không được (trừ `null`) |
| `List<? super Product>` | `List<Product>`, `List<Priced>`, `List<Object>` | `Object` | `Product` |
| `List<?>` | Mọi `List` | `Object` | Không được (trừ `null`) |
| `List<Object>` | Chỉ `List<Object>` | `Object` | Mọi thứ |

Hai dòng cuối hay bị nhầm. `List<Object>` là list chứa mọi thứ, nhưng chỉ nhận đúng `List<Object>`, không nhận `List<String>`. `List<?>` nhận mọi list, đổi lại chỉ đọc ra `Object`: dùng nó khi method không quan tâm kiểu phần tử, như đếm hay in. Raw `List` khác cả hai: nó tắt hẳn kiểm tra kiểu, như mục đầu bài.

Quy tắc **PECS (Producer Extends, Consumer Super)** chọn wildcard theo vai trò của tham số đối với method:

```text
          đọc T ra                                ghi T vào
 source ───────────►  method của bạn  ───────────►  target
 producer: ? extends T                      consumer: ? super T
```

- Tham số **cung cấp** phần tử cho method (method chỉ đọc từ nó): `? extends T`.
- Tham số **nhận** phần tử từ method (method chỉ ghi vào nó): `? super T`.
- Vừa đọc vừa ghi: không wildcard, dùng đúng `T`.

JDK theo quy tắc này khắp nơi. `Collections.copy(List<? super T> dest, List<? extends T> src)` có `src` cung cấp, `dest` nhận. `List.sort(Comparator<? super E> c)` có comparator "tiêu thụ" phần tử để so sánh, nên một `Comparator<Priced>` sắp được một `List<Product>`. Chỉ dùng wildcard cho **tham số**: kiểu trả về có wildcard bắt mọi bên gọi phải xử lý nó.

Khi chọn giữa method generic và wildcard, đếm số lần type parameter xuất hiện trong chữ ký. Xuất hiện một lần thì thay bằng wildcard cho gọn: `long total(Collection<? extends Priced> items)` thay vì `<T extends Priced> long total(Collection<T> items)`. Cần nối hai chỗ với nhau thì phải dùng type parameter: tham số với kiểu trả về như trong `<T> T max(...)`, hoặc hai tham số như trong `copyInto`, nơi `T` bảo đảm thứ đọc từ `source` ghi được vào `target`.

### Bound chặt quá và `Comparable<? super T>`

Báo cáo giao hàng cần ngày giao muộn nhất của một đơn. `LocalDate` so sánh được với nhau, vậy mà `max` ở mục Bounded type không nhận một `List<LocalDate>`.

```java
static <T extends Comparable<T>> T max(Collection<T> items) {
    T best = null;
    for (T item : items) {
        if (best == null || item.compareTo(best) > 0) {
            best = item;
        }
    }
    return best;
}

void main() {
    List<LocalDate> deliveries = List.of(
            LocalDate.of(2026, 10, 6), LocalDate.of(2026, 10, 9), LocalDate.of(2026, 10, 7));
    IO.println("giao muon nhat: " + max(deliveries));
}
```

<Predict question="LocalDate cài Comparable. Lời gọi max(deliveries) có biên dịch được không?">

```text
LatestDelivery.java:14: error: method max in class LatestDelivery cannot be applied to given types;
    IO.println("giao muon nhat: " + max(deliveries));
                                    ^
  required: Collection<T>
  found:    List<LocalDate>
  reason: inference variable T has incompatible equality constraints ChronoLocalDate,LocalDate
  where T is a type-variable:
    T extends Comparable<T> declared in method <T>max(Collection<T>)
1 error
error: compilation failed
```

Không biên dịch. Trình biên dịch không tìm được `T` nào thoả mọi điều kiện.

</Predict>

Dòng `reason` nói `T` vừa phải là `LocalDate` (từ đối số) vừa phải là `ChronoLocalDate`. [Javadoc của `LocalDate`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/time/LocalDate.html) cho thấy lý do: `LocalDate` cài `Comparable<ChronoLocalDate>`, với `ChronoLocalDate` là một interface cha của nó, chứ không cài `Comparable<LocalDate>`. Bound `T extends Comparable<T>` đòi `T` so được với **đúng** `T`, nên không có `T` nào thoả.

`compareTo` "tiêu thụ" một `T` để so sánh, nên theo PECS, `Comparable` ở đây là consumer: `Comparable<? super T>`, tức "so được với `T` hoặc một kiểu cha của `T`". Còn `items` chỉ cung cấp phần tử: `Collection<? extends T>`. Đoạn sau chỉ sửa chữ ký:

```java
static <T extends Comparable<? super T>> T max(Collection<? extends T> items) {
    T best = null;
    for (T item : items) {
        if (best == null || item.compareTo(best) > 0) {
            best = item;
        }
    }
    return best;
}

void main() {
    List<LocalDate> deliveries = List.of(
            LocalDate.of(2026, 10, 6), LocalDate.of(2026, 10, 9), LocalDate.of(2026, 10, 7));
    IO.println("giao muon nhat: " + max(deliveries));
    IO.println("SKU lon nhat:   " + max(List.of("KB-02", "SP-03", "MS-01")));
}
```

Kết quả:

```text
giao muon nhat: 2026-10-09
SKU lon nhat:   SP-03
```

Thân method không đổi một ký tự nào; chỉ chữ ký rộng hơn, và lời gọi cũ với `String` vẫn chạy. `LocalDate` giờ thoả bound vì `ChronoLocalDate` là một kiểu cha của `LocalDate`. [`Collections.max`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Collections.html#max(java.util.Collection)) của JDK khai báo đúng như vậy, thêm `Object &`: `<T extends Object & Comparable<? super T>> T max(Collection<? extends T> coll)`. Dấu `&` ghép nhiều bound, và erasure thay `T` bằng bound **đầu tiên**. Nhờ `Object` đứng đầu, sau khi xoá kiểu `Collections.max` trả về `Object`, đúng chữ ký của nó từ trước khi Java có generics, nên code cũ đã biên dịch với bản đó vẫn chạy.

<Callout kind="ai">

Nhờ AI viết chữ ký generic cho một method tiện ích, hoặc giải thích một thông báo lỗi có `CAP#1` hay `inference variable T`. AI hay đặt wildcard sai chiều (dùng `? extends` cho tham số cần ghi), hay trả về kiểu có wildcard, hay viết bound `T extends Comparable<T>` quá chặt, và hay "sửa" cảnh báo unchecked bằng `@SuppressWarnings` thay vì kiểm tra kiểu. Kiểm tra lại bằng cách áp PECS cho từng tham số, rồi viết một lời gọi với kiểu con và một với kiểu cha, như `List<Product>` và `List<Priced>`, để chắc chữ ký đủ linh hoạt.

</Callout>
