<Goal>

Mở rộng mô hình đơn hàng của J3.1 bằng kế thừa, interface và sealed type, và biết vì sao trong đa số trường hợp nên kết hợp (composition) thay vì kế thừa. Học xong bài này, bạn giải thích được:

- Vì sao cùng một biến `ebook`, lời gọi `ebook.requiresShipping()` đi vào lớp con, còn `label(ebook)` lại chọn method viết cho lớp cha.
- Vì sao lớp con của `HashSet` đếm 3 phần tử thêm vào thành 6.
- Vì sao method của lớp con, khi được gọi từ constructor lớp cha, thấy field của chính nó là `null`.
- Vì sao thêm một phương thức thanh toán mới làm `javac` báo lỗi đúng ở chỗ quên xử lý, nếu bạn dùng `sealed` và `switch` không có `default`.

</Goal>

<Knowledge>

Ví dụ trong bài tiếp tục cửa hàng cà phê của J3.1, với thêm sản phẩm số (ebook pha chế), chính sách giảm giá và phương thức thanh toán. Để ví dụ ngắn, các lớp trong bài viết trong file dùng `void main()` và không ghi access modifier, trừ chỗ cần.

### Kế thừa và override

Cửa hàng bán thêm ebook hướng dẫn pha chế. Ebook không cần giao hàng, nhưng `Product.requiresShipping()` luôn trả `true`, nên đơn chỉ có ebook vẫn bị tính phí ship.

**Kế thừa (inheritance)**: `class DigitalProduct extends Product` nghĩa là `DigitalProduct` **là một** `Product` (quan hệ is-a). Nó có mọi field và method của `Product`, và được dùng ở mọi chỗ cần một `Product`. `Product` gọi là lớp cha (superclass), `DigitalProduct` là lớp con (subclass). Lớp con **override** (ghi đè) một method của lớp cha bằng cách viết lại method đó với cùng tên và cùng danh sách tham số:

```java
class Product {
    final String sku;
    final long price;

    Product(String sku, long price) {
        this.sku = sku;
        this.price = price;
    }

    boolean requiresShipping() {
        return true;
    }
}

class DigitalProduct extends Product {
    final String downloadUrl;

    DigitalProduct(String sku, long price, String downloadUrl) {
        super(sku, price);
        this.downloadUrl = downloadUrl;
    }

    @Override
    boolean requiresShipping() {
        return false;
    }
}

void main() {
    List<Product> cart = List.of(new Product("CF-01", 185_000),
            new DigitalProduct("EB-01", 99_000, "https://example.com/eb-01"));
    for (Product p : cart) {
        IO.println(p.sku + " shipping=" + p.requiresShipping());
    }
}
```

Kết quả:

```text
CF-01 shipping=true
EB-01 shipping=false
```

Cả hai phần tử đều nằm trong một `List<Product>` và được gọi cùng một dòng `p.requiresShipping()`, nhưng ebook chạy bản của `DigitalProduct`. Ba điểm trong code:

- `super(sku, price)` gọi constructor của lớp cha để lớp cha tự gán field của nó. Nếu bạn không viết, `javac` tự chèn `super()` không tham số, và báo lỗi vì `Product` không có constructor không tham số ([JLS §8.8.7](https://docs.oracle.com/javase/specs/jls/se25/html/jls-8.html#jls-8.8.7)).
- Một lớp chỉ `extends` được một lớp. Lớp không ghi `extends` thì ngầm kế thừa `java.lang.Object`, nên mọi đối tượng đều có `equals`, `hashCode`, `toString` (J3.3).
- `@Override` là một annotation (chú thích cho trình biên dịch) nói rằng method này phải override một method của lớp cha.

Cây kế thừa của ví dụ:

```text
        Object            equals, hashCode, toString (J3.3)
          ^
       Product            sku, price, requiresShipping() = true
          ^
    DigitalProduct        downloadUrl, requiresShipping() = false
```

`@Override` không bắt buộc, nhưng thiếu nó thì một lỗi gõ phím biến override thành method mới. Đoạn sau gõ thiếu chữ `s` trong tên method:

```java
class Product {
    boolean requiresShipping() {
        return true;
    }
}

class DigitalProduct extends Product {
    @Override
    boolean requireShipping() {
        return false;
    }
}

void main() {
    IO.println(new DigitalProduct().requiresShipping());
}
```

Kết quả:

```text
Main.java:8: error: method does not override or implement a method from a supertype
    @Override
    ^
1 error
error: compilation failed
```

Bỏ dòng `@Override` đi thì chương trình biên dịch được và in `true`: `requireShipping` là một method mới không ai gọi, còn `requiresShipping` vẫn là bản của lớp cha, và mọi ebook bị tính phí ship mà không ai hay. Luôn gắn `@Override` khi override.

### Override chọn lúc chạy, overload chọn lúc biên dịch

Bạn viết hai method `label`, một nhận `Product`, một nhận `DigitalProduct`, để in nhãn khác nhau cho từng loại. Rồi bạn gọi `label` với một ebook, và nhận nhãn của sản phẩm thường.

Cùng tên method có hai cơ chế khác nhau. **Override** là lớp con viết lại method của lớp cha. **Overload** là nhiều method cùng tên trong một lớp nhưng khác danh sách tham số, ví dụ `Order` có thể có cả `add(String sku)` lẫn `add(String sku, int quantity)`. Đoạn sau dùng cả hai trên cùng một biến `ebook`, khai báo kiểu `Product` nhưng trỏ tới một `DigitalProduct`:

```java
class Product {
    boolean requiresShipping() {
        return true;
    }
}

class DigitalProduct extends Product {
    @Override
    boolean requiresShipping() {
        return false;
    }
}

String label(Product product) {
    return "Product";
}

String label(DigitalProduct product) {
    return "DigitalProduct";
}

void main() {
    Product ebook = new DigitalProduct();
    IO.println("overload: " + label(ebook));
    IO.println("override: requiresShipping=" + ebook.requiresShipping());
}
```

<Predict question="ebook thật ra là một DigitalProduct. Hai dòng in ra là gì?">

```text
overload: Product
override: requiresShipping=false
```

Overload chọn `label(Product)`, override chọn bản của `DigitalProduct`.

</Predict>

Mỗi lời gọi qua biến tham chiếu liên quan tới hai kiểu. **Kiểu khai báo** (static type) là kiểu viết ở khai báo biến, ở đây là `Product`. **Kiểu thật** (runtime type) là lớp của đối tượng mà biến đang trỏ tới, ở đây là `DigitalProduct`. `javac` chọn overload lúc biên dịch, khi nó chỉ biết kiểu khai báo, nên `label(ebook)` luôn là `label(Product)`. Override thì JVM chọn lúc chạy, theo kiểu thật của đối tượng. Khả năng một biến kiểu `Product` chạy code của nhiều lớp con khác nhau gọi là **đa hình (polymorphism)**.

| | Override | Overload |
|---|---|---|
| Là gì | Lớp con viết lại method cùng chữ ký của lớp cha | Nhiều method cùng tên, khác tham số |
| Chọn lúc | Chạy, theo kiểu thật của đối tượng | Biên dịch, theo kiểu khai báo của đối số |
| Ví dụ | `DigitalProduct.requiresShipping()` | `label(Product)` và `label(DigitalProduct)` |

Đừng dùng overload để phân nhánh theo kiểu con. Hành vi khác nhau theo kiểu con thì đặt vào method override, hoặc dùng `switch` trên kiểu sealed ở cuối bài.

### Constructor lớp cha gọi method bị override

`Product` muốn in một dòng log mỗi khi tạo sản phẩm, nên constructor của nó gọi method `label()`. `DigitalProduct` override `label()` để kèm đường dẫn tải. Dòng log của ebook lại in đường dẫn là `null`:

```java
class Product {
    final String sku;

    Product(String sku) {
        this.sku = sku;
        IO.println("tao " + label());
    }

    String label() {
        return sku;
    }
}

class DigitalProduct extends Product {
    final String downloadUrl;

    DigitalProduct(String sku, String downloadUrl) {
        super(sku);
        this.downloadUrl = downloadUrl;
    }

    @Override
    String label() {
        return sku + " link=" + downloadUrl;
    }
}

void main() {
    new DigitalProduct("EB-01", "https://example.com/eb-01");
}
```

Kết quả:

```text
tao EB-01 link=null
```

Thử tự trả lời trước khi đọc tiếp: `downloadUrl` là field `final`, được gán ngay trong constructor, vậy vì sao `label()` thấy `null`?

Thứ tự chạy quyết định kết quả. `new DigitalProduct(...)` chạy constructor lớp con, và dòng đầu của nó là `super(sku)`, nên constructor lớp cha chạy trước khi lớp con kịp gán `downloadUrl`. Constructor lớp cha gọi `label()`, và vì đối tượng thật là `DigitalProduct`, override của lớp con chạy, đọc `downloadUrl` khi nó còn ở giá trị mặc định `null`:

```text
 new DigitalProduct("EB-01", url)
   DigitalProduct(...)
     super("EB-01")  ─────────►  Product(...)
                                   this.sku = "EB-01"
                                   label()  ──► DigitalProduct.label()  ◄ downloadUrl vẫn null
     this.downloadUrl = url      ◄ chỉ được gán sau khi super(...) xong
```

Từ Java 25 (JEP 513), constructor được đặt lệnh trước `super(...)`, miễn là các lệnh đó không đọc đối tượng đang tạo; gán field của chính lớp con là được phép. Đổi thứ tự hai dòng trong constructor của `DigitalProduct`:

```java
class Product {
    final String sku;

    Product(String sku) {
        this.sku = sku;
        IO.println("tao " + label());
    }

    String label() {
        return sku;
    }
}

class DigitalProduct extends Product {
    final String downloadUrl;

    DigitalProduct(String sku, String downloadUrl) {
        this.downloadUrl = downloadUrl;
        super(sku);
    }

    @Override
    String label() {
        return sku + " link=" + downloadUrl;
    }
}

void main() {
    new DigitalProduct("EB-01", "https://example.com/eb-01");
}
```

Kết quả:

```text
tao EB-01 link=https://example.com/eb-01
```

Cách này chữa được lớp con bạn viết, nhưng lớp cha không biết lớp con nào sẽ override nó và chúng có gán field trước `super(...)` hay không. Quy tắc an toàn vẫn là: constructor không gọi method mà lớp con override được. Cần gọi thì đánh dấu method đó `private` hoặc `final`.

### Kế thừa dễ vỡ

Bộ phận phân tích muốn đếm số lượt thêm SKU vào danh sách theo dõi. `HashSet` là collection không chứa phần tử trùng, J5.1 học kỹ; `add` thêm một phần tử, `addAll` thêm cả một collection. Cách thứ nhất kế thừa `HashSet` và override hai method đó. Cách thứ hai bọc một `HashSet` làm field. Hai method override phải là `public`, vì method override không được có mức truy cập hẹp hơn bản của lớp cha, và `HashSet.add`, `HashSet.addAll` là `public`. `Collection<? extends String>` là kiểu tham số của `addAll`, học ở J5.2; ở bài này, đọc nó là "một collection chuỗi" là đủ.

```java
class CountingSkus extends HashSet<String> {
    int added = 0;

    @Override
    public boolean add(String sku) {
        added++;
        return super.add(sku);
    }

    @Override
    public boolean addAll(Collection<? extends String> skus) {
        added += skus.size();
        return super.addAll(skus);
    }
}

class SkuCounter {
    private final Set<String> skus = new HashSet<>();
    private int added = 0;

    void addAll(List<String> list) {
        added += list.size();
        skus.addAll(list);
    }

    int added() {
        return added;
    }
}

void main() {
    CountingSkus inherited = new CountingSkus();
    inherited.addAll(List.of("CF-01", "FL-01", "EB-01"));
    IO.println("extends HashSet: added=" + inherited.added);

    SkuCounter composed = new SkuCounter();
    composed.addAll(List.of("CF-01", "FL-01", "EB-01"));
    IO.println("composition:     added=" + composed.added());
}
```

<Predict question="Cả hai cùng thêm 3 SKU. Mỗi dòng in ra added bằng bao nhiêu?">

```text
extends HashSet: added=6
composition:     added=3
```

Lớp con của `HashSet` đếm mỗi SKU hai lần.

</Predict>

`super.addAll(skus)` chạy `addAll` mà `HashSet` thừa hưởng từ `AbstractCollection`, và cài đặt đó gọi `add` cho từng phần tử. `add` đã bị override, nên mỗi SKU được đếm một lần trong `addAll` của lớp con và một lần nữa trong `add`. Hành vi "`addAll` gọi `add`" chỉ được ghi ở mục Implementation Requirements của [`AbstractCollection.addAll`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/AbstractCollection.html#addAll(java.util.Collection)), không thuộc hợp đồng của `Set`. Lớp con đã phụ thuộc vào cách lớp cha tự gọi chính nó, và một phiên bản JDK đổi cách cài là lớp con hỏng theo mà không có dòng code nào của nó thay đổi. Hiện tượng này gọi là **fragile base class** (lớp cha dễ vỡ).

`SkuCounter` không kế thừa gì. Nó chỉ gọi `addAll` trên một set nằm bên trong, nên chi tiết bên trong `HashSet` không ảnh hưởng tới nó. Kế thừa buộc lớp con vào **chi tiết cài đặt** của lớp cha; bọc làm field chỉ buộc vào **hợp đồng** công khai.

Kế thừa là lựa chọn đúng khi đủ hai điều kiện:

1. Quan hệ thật sự là is-a, và lớp con dùng được ở **mọi** chỗ lớp cha được dùng mà không làm sai kỳ vọng của bên gọi. Điều kiện này gọi là nguyên lý thay thế Liskov (Liskov substitution principle).
2. Lớp cha được thiết kế để kế thừa: tài liệu của nó nói method nào gọi method nào, như `AbstractCollection` ghi ở mục Implementation Requirements.

Joshua Bloch tóm lại trong *Effective Java* (mục 19): hoặc thiết kế và viết tài liệu cho kế thừa, hoặc cấm nó. Lớp không định cho kế thừa thì khai báo `final`.

Một dạng lớp cha được thiết kế để kế thừa là **abstract class**: lớp khai báo `abstract`, không tạo trực tiếp bằng `new` được, và có thể có method `abstract` không thân mà lớp con bắt buộc cài. Đoạn sau giữ phần định dạng hoá đơn chung trong lớp cha, khoá nó bằng `final`, và để lớp con chỉ cài phần khác nhau:

```java
abstract class Receipt {
    final String render(String orderNumber, long total) {
        return header() + " | " + orderNumber + " | " + total + " dong";
    }

    abstract String header();
}

class EmailReceipt extends Receipt {
    @Override
    String header() {
        return "Email";
    }
}

class PrintedReceipt extends Receipt {
    @Override
    String header() {
        return "Ban in";
    }
}

void main() {
    for (Receipt receipt : List.of(new EmailReceipt(), new PrintedReceipt())) {
        IO.println(receipt.render("DH-1", 455_000));
    }
}
```

Kết quả:

```text
Email | DH-1 | 455000 dong
Ban in | DH-1 | 455000 dong
```

`render` là `final`, nên lớp con không đổi được cách lớp cha ghép hoá đơn; nó chỉ được cài `header()`, đúng điểm mở mà lớp cha dành cho nó. Viết `new Receipt()` thì `javac` báo `Receipt is abstract; cannot be instantiated`.

### Kết hợp qua interface

Chính sách giảm giá của cửa hàng đổi theo chiến dịch: tuần này giảm 10% cho đơn từ 300.000 đồng, tuần sau giảm cố định cho đơn nhiều món. Nếu mỗi chính sách là một lớp con của `Order`, bạn có `PercentOffOrder`, `BulkOrder`, rồi `PercentOffBulkOrder` khi cần cả hai, và số lớp tăng theo số tổ hợp.

**Kết hợp (composition)** là giữ một đối tượng khác làm field và **uỷ quyền (delegate)** việc cho nó, như `SkuCounter` ở mục trước. Kết hợp mạnh nhất khi field có kiểu là một **interface**: một kiểu chủ yếu khai báo các method mà lớp cài đặt (`implements`) phải có, và không có field trạng thái (từ Java 8 interface có thêm method có thân, mục sau). `Checkout` dưới đây không kế thừa gì; nó có một `DiscountPolicy`:

```java
record Order(String number, long subtotal) {}

interface DiscountPolicy {
    long discountFor(Order order);
}

final class PercentOff implements DiscountPolicy {
    private final int percent;
    private final long minSubtotal;

    PercentOff(int percent, long minSubtotal) {
        this.percent = percent;
        this.minSubtotal = minSubtotal;
    }

    @Override
    public long discountFor(Order order) {
        return order.subtotal() >= minSubtotal ? order.subtotal() * percent / 100 : 0;
    }
}

class Checkout {
    private final DiscountPolicy discountPolicy;

    Checkout(DiscountPolicy discountPolicy) {
        this.discountPolicy = discountPolicy;
    }

    long amountDue(Order order) {
        return order.subtotal() - discountPolicy.discountFor(order);
    }
}

void main() {
    Order order = new Order("DH-1", 435_000);
    IO.println("giam 10%:   " + new Checkout(new PercentOff(10, 300_000)).amountDue(order));
    IO.println("khong giam: " + new Checkout(o -> 0).amountDue(order));
}
```

Kết quả:

```text
giam 10%:   391500
khong giam: 435000
```

`Checkout` chỉ biết hợp đồng `discountFor`, không biết chính sách nào đang được truyền vào. Method trong interface ngầm là `public`, nên `PercentOff` phải cài nó là `public`. `o -> 0` ở dòng cuối là một **lambda**: cách viết ngắn một cài đặt của interface có đúng một method, ở đây là chính sách luôn giảm 0 đồng. Interface có đúng một method trừu tượng như `DiscountPolicy` gọi là **functional interface**; J6 học lambda kỹ hơn.

```text
  Checkout ──has-a──► DiscountPolicy (interface)
                         ▲               ▲                  ▲
                    PercentOff   lớp vô danh (cuối bài)   lambda o -> 0

                    cài đặt nào cũng thay vào được
```

Đổi chiến dịch chỉ là đổi đối tượng truyền vào constructor của `Checkout`. Trong test, bạn truyền một chính sách cố định như `o -> 0` để kiểm phần còn lại của `Checkout` mà không phụ thuộc chiến dịch đang chạy. Đây cũng là cách thay thứ J3.1 khuyên không gọi `static`: đồng hồ hay bộ sinh mã thành một interface truyền vào, và test truyền bản giả.

<Callout kind="production">

Chính sách giảm giá của một cửa hàng là một cây lớp con của `Order`. Mỗi lần marketing ra chiến dịch mới, team phải thêm lớp con, sửa mọi chỗ `new` đơn hàng cho đúng loại, và kiểm thử lại toàn bộ luồng tạo đơn; một nhánh tạo đơn quên đổi loại là khách ở nhánh đó nhận sai mức giảm. Khi `Checkout` nhận một `DiscountPolicy` qua constructor, chiến dịch mới là một lớp hoặc một lambda mới, không đụng vào `Order`. Spring làm đúng việc này ở SB1: nó tạo đối tượng và truyền dependency (đối tượng mà lớp cần dùng) vào constructor, gọi là dependency injection.

</Callout>

### Interface: default method, static method và xung đột

Bạn muốn mọi chính sách giảm giá có thêm khả năng "giảm tối đa 30.000 đồng", kể cả các lambda đã viết. Thêm một method trừu tượng vào interface thì mọi lớp cài đặt cũ không biên dịch nữa.

Từ Java 8, interface có thể chứa method có thân. **Default method** là method có thân mà mọi lớp cài đặt nhận luôn, hoặc override nếu muốn. **Static method** của interface gọi qua tên interface, thường là factory method:

```java
record Order(String number, long subtotal) {}

interface DiscountPolicy {
    long discountFor(Order order);

    default DiscountPolicy capAt(long max) {
        return order -> Math.min(discountFor(order), max);
    }

    static DiscountPolicy none() {
        return order -> 0;
    }
}

void main() {
    Order order = new Order("DH-1", 435_000);
    DiscountPolicy tenPercent = o -> o.subtotal() / 10;
    IO.println("10%:         " + tenPercent.discountFor(order));
    IO.println("10%, toi da: " + tenPercent.capAt(30_000).discountFor(order));
    IO.println("none:        " + DiscountPolicy.none().discountFor(order));
}
```

Kết quả:

```text
10%:         43500
10%, toi da: 30000
none:        0
```

Lambda `tenPercent` có sẵn `capAt` dù nó không cài gì ngoài `discountFor`. `capAt` không sửa chính sách cũ mà bọc nó trong một chính sách mới, cũng là kết hợp. Bảng dưới là các thành phần của interface theo phiên bản Java:

| Thành phần trong interface | Từ Java | Ghi chú |
|---|---|---|
| Method trừu tượng | 1.0 | Ngầm `public abstract` |
| Hằng số | 1.0 | Ngầm `public static final`; interface không có field trạng thái |
| `default` method | 8 | Có thân; lớp cài đặt dùng luôn hoặc override |
| `static` method | 8 | Gọi qua tên interface, như `DiscountPolicy.none()` |
| `private` method | 9 | Code dùng chung giữa các default method, không lộ ra ngoài |

Một lớp cài được nhiều interface, nên có thể nhận hai default method trùng tên. Java không đoán bạn muốn bản nào:

```java
interface Taxable {
    default String describe() {
        return "co VAT";
    }
}

interface Giftable {
    default String describe() {
        return "goi qua duoc";
    }
}

class GiftBox implements Taxable, Giftable {
}

void main() {
    IO.println(new GiftBox().describe());
}
```

Kết quả:

```text
Main.java:13: error: types Taxable and Giftable are incompatible;
class GiftBox implements Taxable, Giftable {
^
  class Main.GiftBox inherits unrelated defaults for describe() from types Taxable and Giftable
1 error
error: compilation failed
```

Lớp phải tự override method đó. Trong thân override, cú pháp `Taxable.super.describe()` gọi bản của một interface cụ thể:

```java
interface Taxable {
    default String describe() {
        return "co VAT";
    }
}

interface Giftable {
    default String describe() {
        return "goi qua duoc";
    }
}

class GiftBox implements Taxable, Giftable {
    @Override
    public String describe() {
        return Taxable.super.describe() + ", " + Giftable.super.describe();
    }
}

void main() {
    IO.println(new GiftBox().describe());
}
```

Kết quả:

```text
co VAT, goi qua duoc
```

Vì xung đột kiểu này, default method hợp cho hành vi tiện ích nhỏ dựng trên method trừu tượng, như `capAt`, chứ không phải để nhồi logic nghiệp vụ vào interface. Bảng sau giúp chọn giữa interface và abstract class:

| | Interface | Abstract class |
|---|---|---|
| Field trạng thái | Không, chỉ hằng số | Có |
| Constructor | Không | Có |
| Một lớp dùng được bao nhiêu | Nhiều | Một |
| Dùng khi | Mô tả một khả năng, một vai trò mà nhiều lớp không liên quan cùng có | Các lớp con chung code và trạng thái, lớp cha thiết kế để kế thừa |

Mặc định chọn interface. Chọn abstract class khi các lớp con thật sự chung field và cần lớp cha giữ một phần quy trình, như `Receipt.render`.

### sealed: tập kiểu đóng và switch kiểm tra đủ

Cửa hàng nhận ba phương thức thanh toán: tiền mặt khi nhận hàng, thẻ (phí 2%), ví điện tử (phí 1.000 đồng). Mọi chỗ tính phí cần xử lý đủ ba. Rồi cửa hàng nhận thêm chuyển khoản, và bạn phải tìm hết những chỗ đó.

**Sealed** (chính thức từ Java 17) giới hạn những kiểu được phép kế thừa một lớp hay interface. J2.3 đã dùng nó với `switch`; ở đây là cách nó giúp khi tập kiểu thay đổi. Mỗi phương thức thanh toán mang dữ liệu khác nhau, nên mỗi cái là một record:

```java
sealed interface Payment {
    record Cash() implements Payment {}
    record Card(String last4) implements Payment {}
    record EWallet(String provider) implements Payment {}
}

long paymentFee(Payment payment, long amount) {
    return switch (payment) {
        case Payment.Cash cash -> 0;
        case Payment.Card card -> amount * 2 / 100;
        case Payment.EWallet wallet -> 1_000;
    };
}

void main() {
    List<Payment> payments = List.of(new Payment.Cash(), new Payment.Card("4242"), new Payment.EWallet("demo"));
    for (Payment payment : payments) {
        IO.println(payment + " fee=" + paymentFee(payment, 459_000));
    }
}
```

Kết quả:

```text
Cash[] fee=0
Card[last4=4242] fee=9180
EWallet[provider=demo] fee=1000
```

`switch` không có nhánh `default`, và `javac` vẫn chấp nhận vì nó biết `Payment` chỉ có đúng ba kiểu con. Giờ thêm `BankTransfer` vào `Payment` mà chưa sửa `paymentFee`:

```java
sealed interface Payment {
    record Cash() implements Payment {}
    record Card(String last4) implements Payment {}
    record EWallet(String provider) implements Payment {}
    record BankTransfer(String reference) implements Payment {}
}

long paymentFee(Payment payment, long amount) {
    return switch (payment) {
        case Payment.Cash cash -> 0;
        case Payment.Card card -> amount * 2 / 100;
        case Payment.EWallet wallet -> 1_000;
    };
}

void main() {
    IO.println(paymentFee(new Payment.BankTransfer("FT-1001"), 459_000));
}
```

Kết quả:

```text
Main.java:9: error: the switch expression does not cover all possible input values
    return switch (payment) {
           ^
1 error
error: compilation failed
```

`javac` chỉ ra đúng chỗ quên xử lý, ở mọi `switch` trên `Payment` trong cả codebase. Nếu `switch` có `default -> 0`, chương trình biên dịch được và chuyển khoản lặng lẽ được miễn phí. Với kiểu sealed, đừng viết `default`: nó nuốt mất trường hợp mới mà bạn muốn `javac` báo.

Ba quy tắc của sealed:

- Kiểu con trực tiếp của một kiểu sealed phải là `final`, `sealed` hoặc `non-sealed` (mở lại cho kế thừa tự do). Record ngầm là `final`.
- Khi các kiểu con nằm cùng file với kiểu sealed, có thể bỏ mệnh đề `permits`, như ví dụ trên. Nằm ở file khác thì liệt kê: `sealed interface Payment permits Cash, Card, EWallet`.
- Kiểu con không có trong danh sách được phép thì `javac` báo lỗi khi nó `implements` hay `extends`.

**Enum** (J2.3) cũng cho `switch` kiểm tra đủ trường hợp. Chọn giữa hai cách theo dữ liệu của từng trường hợp:

| | Enum | Sealed interface với record |
|---|---|---|
| Dữ liệu của mỗi trường hợp | Cùng hình dạng, thường là hằng số | Khác nhau: `Card` có `last4`, `Cash` không có gì |
| Số đối tượng | Mỗi trường hợp đúng một đối tượng | Tạo bao nhiêu cũng được |
| Ví dụ | Trạng thái đơn `NEW`, `PAID`, `SHIPPED` | Phương thức thanh toán |

### Lớp lồng, lớp vô danh và lambda

Một màn hình quản trị đăng ký một đối tượng lắng nghe sự kiện "có đơn mới" vào một danh sách toàn cục. Màn hình đóng, nhưng bộ nhớ của nó không bao giờ được thu hồi.

Java cho khai báo lớp bên trong lớp khác. **Lớp lồng static** (`static class X` bên trong lớp khác, hay một record lồng) là một lớp bình thường đặt trong không gian tên của lớp ngoài. **Inner class** (`class X` không `static`) thì khác: mỗi đối tượng của nó gắn với một đối tượng của lớp bao ngoài, và đọc được field của đối tượng đó. Đoạn sau khai báo cả hai loại trong `Order`, rồi dùng **reflection** (API để chương trình xem cấu trúc của một lớp lúc chạy) để liệt kê các field mà `javac` sinh cho chúng. `X.class` là đối tượng mô tả lớp `X`, `Class<?>` đọc là "một lớp bất kỳ", `getDeclaredFields()` trả mảng các field của lớp, và `Arrays.toString` in mảng đó:

```java
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;

public class Nesting {
    public static void main(String[] args) {
        Order order = new Order();
        Order.LineCounter counter = order.new LineCounter();
        IO.println("count = " + counter.count());
        for (Class<?> type : List.of(Order.LineCounter.class, Order.Title.class, Order.Summary.class)) {
            IO.println(type.getSimpleName() + ": " + Arrays.toString(type.getDeclaredFields()));
        }
    }
}

class Order {
    private final List<String> lines = new ArrayList<>(List.of("CF-01", "FL-01"));

    class LineCounter {
        int count() {
            return lines.size();
        }
    }

    class Title {
        String text() {
            return "Don hang";
        }
    }

    static class Summary {
        String text() {
            return "Tom tat";
        }
    }
}
```

Kết quả:

```text
count = 2
LineCounter: [final Order Order$LineCounter.this$0]
Title: []
Summary: []
```

Ví dụ này khai báo `Order` là lớp cấp cao nhất, không dùng `void main()`, để tên lớp không bị lồng thêm một tầng trong lớp ngầm `Main` (J3.1). `order.new LineCounter()` là cú pháp tạo inner class gắn với `order`. `javac` thêm vào `LineCounter` một field ẩn `this$0` trỏ tới đơn hàng bao ngoài; đó là cách `lines.size()` trong `count()` tìm được đúng đơn. `Title` cũng là inner class nhưng không đọc gì của `Order`, và `javac` của JDK 25 bỏ field ẩn trong trường hợp này, như output cho thấy. `Summary` là lớp lồng static nên không bao giờ có nó.

Field ẩn này là nguồn rò bộ nhớ hay gặp. Một đối tượng inner sống lâu, như listener (đối tượng được gọi lại mỗi khi có sự kiện) đăng ký vào danh sách toàn cục, giữ luôn đối tượng ngoài qua `this$0`. GC không thu hồi được đối tượng ngoài, vì vẫn còn tham chiếu trỏ tới nó; đó là chuyện của màn hình quản trị ở đầu mục. Mặc định viết lớp lồng `static`. Chỉ bỏ `static` khi lớp thật sự cần đối tượng ngoài; kể cả khi `javac` bỏ được field ẩn như `Title`, bạn vẫn phải có một `Order` mới tạo được nó.

**Lớp vô danh** (anonymous class) là lớp không tên, khai báo và tạo đối tượng trong cùng một biểu thức `new Interface() { ... }`. Trước Java 8, đây là cách gọn nhất để truyền một đoạn hành vi. Lambda viết cùng việc đó ngắn hơn, cho functional interface:

```java
interface DiscountPolicy {
    long discountFor(long subtotal);
}

void main() {
    DiscountPolicy bulk = new DiscountPolicy() {
        @Override
        public long discountFor(long subtotal) {
            return subtotal >= 400_000 ? 15_000 : 0;
        }
    };
    DiscountPolicy bulkLambda = subtotal -> subtotal >= 400_000 ? 15_000 : 0;

    IO.println(bulk.discountFor(435_000) + " " + bulkLambda.discountFor(435_000));
    IO.println("lop vo danh: " + bulk.getClass().getName());
    IO.println("lambda la hidden class? " + bulkLambda.getClass().isHidden());
}
```

Kết quả:

```text
15000 15000
lop vo danh: Main$1
lambda la hidden class? true
```

Hai cách cho cùng kết quả. Lớp vô danh là một lớp thật mà `javac` sinh ra file `Main$1.class`. Lambda không có file `.class` riêng: JVM tạo lớp cho nó lúc chạy, dưới dạng hidden class (lớp không tìm được qua tên). Bảng dưới tóm tắt khi nào dùng loại nào:

| Loại | Khai báo | Giữ tham chiếu tới đối tượng ngoài | Dùng khi |
|---|---|---|---|
| Lớp lồng static | `static class X` trong lớp khác, hoặc record lồng | Không | Kiểu phụ chỉ có nghĩa cùng lớp ngoài, như `Payment.Card` |
| Inner class | `class X` không `static` | Có, nếu thân lớp dùng tới đối tượng ngoài | Cần đọc field của đối tượng ngoài, như `LineCounter` ở trên |
| Lớp cục bộ | Khai báo trong thân method | Có, nếu method không static và thân lớp dùng tới đối tượng ngoài | Hiếm dùng |
| Lớp vô danh | `new DiscountPolicy() { ... }` | Có, nếu thân lớp dùng tới đối tượng ngoài | Cài interface nhiều method, hoặc kế thừa một lớp |
| Lambda | `o -> ...` | Chỉ khi thân lambda dùng `this`, kể cả ngầm qua field hay method instance | Cài functional interface |

<Callout kind="ai">

Nhờ AI phác thảo cây kiểu cho một nghiệp vụ, hoặc chuyển lớp vô danh sang lambda. AI hay đề xuất cây kế thừa sâu cho thứ nên là kết hợp, thêm `default ->` vào `switch` trên kiểu sealed, gọi method override được từ constructor, và quên `@Override`. Kiểm tra: mỗi `extends` có đúng là is-a và lớp cha có được thiết kế để kế thừa không, mỗi `switch` trên kiểu sealed có `default` không, mỗi lớp lồng không cần đối tượng ngoài đã là `static` chưa; rồi thêm thử một kiểu con mới và cho `javac` biên dịch lại.

</Callout>

<Callout kind="link">

J6 dùng lambda và các functional interface có sẵn. J8 tận dụng interface để thay cài đặt thật bằng cài đặt giả trong test. SB1 dùng constructor injection của Spring, chính là kết hợp ở bài này.
