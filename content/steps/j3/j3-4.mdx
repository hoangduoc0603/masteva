<Goal>

Hiểu module system của Java (JPMS, Java Platform Module System) giải quyết điều gì mà package và access modifier ở J3.1 không làm được, và nó tốn gì. Đây là chủ đề tuỳ chọn: ứng dụng bạn viết ở các chặng sau vẫn chạy trên classpath, nhưng bạn sẽ gặp module mỗi ngày qua thông báo lỗi của JDK. Học xong bài này, bạn giải thích được:

- Vì sao một lớp `public` trong package `internal` vẫn bị code khác gọi, và module chặn việc đó ngay lúc biên dịch thế nào.
- Vì sao một thư viện cũ chạy tốt trên Java 11 lại báo `InaccessibleObjectException` khi lên Java 17, và `--add-opens` sửa tạm ra sao.
- Vì sao ứng dụng Spring Boot thường vẫn chạy trên classpath, dù Java có module từ phiên bản 9.

</Goal>

<Knowledge>

### Điều package không làm được

Ở J3.1 bạn chọn mức truy cập hẹp nhất. Nhưng package-private chỉ có tác dụng trong **một** package. Thư viện catalog dưới đây có hai package:

```text
shop.catalog            Catalog, Product        API cho người dùng
shop.catalog.internal   PriceRules              chi tiết cài đặt
```

`Catalog` cần gọi `PriceRules.withVat(...)`. Vì hai lớp nằm ở hai package khác nhau, `PriceRules` buộc phải `public`, và khi đã `public` thì **mọi** đoạn code trên classpath đều gọi được nó. Chữ `internal` trong tên package chỉ là lời nhắn, không phải rào chắn. Sau vài năm, team khác dùng `PriceRules` trực tiếp, và bạn không đổi được nó mà không làm vỡ code của họ.

Classpath còn hai điểm yếu khác. Thứ nhất, nó là một danh sách jar phẳng, không ghi jar nào cần jar nào. Thiếu một jar thì JVM vẫn khởi động bình thường, rồi chết với `NoClassDefFoundError` ở lần đầu tiên code chạm vào lớp bị thiếu, có thể sau vài giờ chạy. Thứ hai, khi hai jar chứa cùng một lớp (thường là hai phiên bản của một thư viện), JVM lấy bản tìm thấy trước theo thứ tự classpath; lỗi kiểu này hay được gọi là **JAR hell**.

### Module và module-info.java

**Module** là một nhóm package có tên, kèm một file mô tả `module-info.java` đặt ở gốc thư mục nguồn. File này nói module cần module nào và cho bên ngoài dùng package nào:

```java
module shop.catalog {
    exports shop.catalog;          // shop.catalog.internal không được nhắc tới: bị giấu
}

module shop.app {
    requires shop.catalog;         // cần module catalog
    requires java.logging;         // java.util.logging nằm ở module riêng của JDK
}
```

| Chỉ thị | Nghĩa |
|---|---|
| `requires M` | Module này **đọc** (read) module `M`: dùng được các package mà `M` export |
| `requires transitive M` | Như trên, và ai `requires` module này thì cũng tự đọc `M` |
| `exports p` | Lớp `public` trong package `p` dùng được từ module khác, lúc biên dịch và lúc chạy |
| `opens p` | Cho reflection truy cập cả thành viên `private` của package `p`, chỉ lúc chạy |

Mọi module tự động `requires java.base`, module chứa `java.lang`, `java.util`. Bản thân JDK 25 được chia thành khoảng 70 module (69 trên máy kiểm chứng, đếm bằng `java --list-modules`); `java.util.logging` nằm ở `java.logging`, JDBC ở `java.sql`.

Một lớp ở module A dùng được lớp `T` ở module B khi đủ **cả ba** điều kiện:

```text
 module shop.app                         module shop.catalog
 +------------------------+              +-----------------------------------+
 | requires shop.catalog -|--(1) đọc --->| exports shop.catalog   (2)        |
 |                        |              |   public class Catalog (3)  OK    |
 | Main dùng Catalog      |              |                                   |
 | Main dùng PriceRules --|---- X ------>| shop.catalog.internal  không export |
 +------------------------+              |   public class PriceRules   CHẶN  |
                                         +-----------------------------------+
 (1) A requires B     (2) B exports package của T     (3) T là public
```

`public` giờ nghĩa là "public cho những module được phép", không còn là "public cho mọi nơi". Đó là **đóng gói mạnh (strong encapsulation)**.

<Check id="j3.4.module-descriptor">Đọc được một `module-info.java` và nói ra module đó cần gì, lộ package nào; kể được ba điều kiện để module A dùng được một lớp của module B.</Check>

### Module path và classpath

Từ Java 9, `java` và `javac` có hai nơi tìm code. Một jar chỉ được coi là module khi nằm trên **module path** (`--module-path`, viết tắt `-p`). Cùng jar đó đặt trên classpath thì `module-info.class` bị bỏ qua.

| | Classpath (`-cp`) | Module path (`-p`) |
|---|---|---|
| Đơn vị | Lớp, tìm theo thứ tự jar | Module có tên, phụ thuộc khai báo rõ |
| Thiếu phụ thuộc | Phát hiện khi lớp được dùng lần đầu: `NoClassDefFoundError` | Phát hiện khi JVM khởi động: `FindException`, chưa chạy dòng code nào |
| `public` | Dùng được từ mọi nơi | Chỉ khi package được export |
| Cùng package ở hai jar | Được, bản đứng trước thắng | Lỗi khi khởi động (split package) |
| Code nằm ở | **Unnamed module**: đọc mọi module, export mọi package | Module có tên (named module) |

Jar chưa có `module-info.class` mà đặt trên module path thì thành **automatic module**: nó export mọi package và đọc mọi module khác; nó cũng đọc unnamed module, nên dùng được lớp trên classpath, và `opens` mọi package. Tên của nó lấy từ thuộc tính `Automatic-Module-Name` trong file `META-INF/MANIFEST.MF` nếu có, nếu không thì suy ra từ tên file (`acme-tax-1.4.0.jar` thành `acme.tax`). Tên suy từ tên file dễ đổi khi tác giả đổi tên artifact, nên thư viện nghiêm túc ghi sẵn `Automatic-Module-Name` để người dùng `requires` một cái tên ổn định.

<Check id="j3.4.classpath-vs-modulepath">Giải thích được cùng một jar chạy trên classpath và trên module path khác nhau thế nào, và named, automatic, unnamed module là gì.</Check>

### Đóng gói mạnh của chính JDK

Module của JDK chỉ export API chính thức. Package nội bộ như `jdk.internal.misc` và các field `private` trong `java.util` không còn mở cho reflection. Thay đổi này đến dần: Java 8 cho reflection tự do; Java 9 tới 15 vẫn cho nhưng in cảnh báo `Illegal reflective access`; Java 16 (JEP 396) chặn mặc định nhưng còn mở lại được bằng `--illegal-access=permit`; từ Java 17 (JEP 403), tuỳ chọn đó bị bỏ hẳn.

Lối thoát còn lại là **`--add-opens <module>/<package>=<module nhận>`**, mở một package cụ thể cho reflection. Code trên classpath có tên module nhận là `ALL-UNNAMED`. `--add-exports` tương tự nhưng chỉ mở lớp `public` cho biên dịch và gọi trực tiếp. Với jar chạy bằng `java -jar`, có thể ghi thuộc tính `Add-Opens:` vào manifest thay cho tham số dòng lệnh.

`exports` và `opens` tách riêng có chủ ý. Framework như Jackson, Hibernate, Spring đọc và ghi field `private` của lớp bạn bằng reflection. Nếu ứng dụng của bạn là module, package chứa entity hay DTO cần `opens` (hoặc `opens ... to` đúng module framework), dù không cần `exports`: framework được nhìn vào bên trong lúc chạy, nhưng không module nào viết được `import` tới package đó. `open module` mở mọi package cho reflection một lần, tiện nhưng bỏ phần lớn lợi ích của đóng gói mạnh.

<Callout kind="production">

Một team nâng service từ Java 11 lên 17. Build xanh, nhưng service chết ngay khi khởi động với `InaccessibleObjectException: Unable to make field ... accessible: module java.base does not "opens java.util" to unnamed module`. Trên Java 11, thư viện đó vẫn reflection được vào `java.util`, chỉ in một dòng cảnh báo mà không ai đọc. Cách sửa đúng là nâng thư viện lên bản hỗ trợ Java 17. Thêm `--add-opens java.base/java.util=ALL-UNNAMED` chỉ là cách chữa cháy: ghi lại lý do ngay cạnh tham số và gỡ nó khi đã nâng thư viện.

</Callout>

### JPMS trên thực tế: có từ Java 9 (2017), nhưng ai dùng?

- **JDK:** dùng hoàn toàn. Mọi thông báo về `module java.base does not "opens"` đến từ đây, kể cả khi ứng dụng của bạn không có module nào.
- **Thư viện:** nhiều thư viện chỉ ghi `Automatic-Module-Name` để có tên ổn định. Kiểm tra trên máy kiểm chứng: `spring-core` 7.0.9 và `spring-boot` 4.1.1 chỉ có `Automatic-Module-Name: spring.core`, `spring.boot`, không có `module-info`; `jackson-databind` 3.1.5 (Jackson 3, đi cùng Boot 4) có `module-info.class` ở gốc jar.
- **Ứng dụng:** phần lớn ứng dụng server, đặc biệt Spring Boot, chạy trên classpath. Jar thực thi của Spring Boot (J17) tự nạp các jar trong `BOOT-INF/lib` bằng classloader riêng, nên mọi thứ nằm trong unnamed module. Ranh giới giữa các phần của ứng dụng thường được giữ bằng Maven multi-module (J7) hoặc test kiến trúc như Spring Modulith (J19).
- **Công cụ phân phối kèm runtime:** ứng dụng desktop, CLI dùng `jlink` để đóng gói một JVM chỉ chứa module cần thiết. `jlink` đòi mọi module phải có `module-info` thật; automatic module bị từ chối.

| | Classpath và package (mặc định) | JPMS |
|---|---|---|
| Giấu lớp `public` nội bộ, thiếu phụ thuộc | Không giấu được; thiếu jar lộ ra muộn | `javac` báo lỗi; thiếu module lộ ra khi khởi động |
| Chi phí build | Thấp; mọi công cụ hỗ trợ sẵn | Mỗi module cần `module-info`; plugin, IDE, test phải hiểu module path |
| Framework dùng reflection | Chạy luôn | Phải `opens` đúng package, lỗi thường lộ lúc chạy |
| Thư viện cũ | Chạy | Có thể vướng split package hoặc tên automatic module không ổn định |
| `jlink` runtime gồm cả code của bạn | Không | Có |

Chọn JPMS khi bạn viết **thư viện** dùng chung cho nhiều team và cần giấu phần cài đặt, hoặc phân phối một công cụ kèm runtime riêng. Với ứng dụng Spring Boot thông thường, chi phí thường lớn hơn lợi ích; hãy giữ classpath và dùng ranh giới ở mức build hoặc test.

<Practice>

**Chuẩn bị:** JDK 25. Lab này độc lập với code J3.1 tới J3.3, nên không sao nếu bạn đã xoá `~/masteva-j3` ở cuối J3.3. Chỉ dùng `javac`, `java`, `jar`, `jdeps`, `jlink`, đều có sẵn trong JDK. Mọi lệnh giống nhau trên Mac và Linux, trừ chỗ ghi chú ở bước 7.

### 1. Hai module: shop.catalog và shop.app

<Terminal where="mac" title="Tạo mã nguồn hai module">

```bash
mkdir -p ~/masteva-j3/jpms && cd ~/masteva-j3/jpms
mkdir -p catalog/src/shop/catalog/internal app/src/shop/app
cat > catalog/src/module-info.java <<'EOF'
module shop.catalog {
    exports shop.catalog;
}
EOF
cat > catalog/src/shop/catalog/Product.java <<'EOF'
package shop.catalog;

public record Product(String sku, String name, long price) {}
EOF
cat > catalog/src/shop/catalog/Catalog.java <<'EOF'
package shop.catalog;

import java.util.List;
import shop.catalog.internal.PriceRules;

public final class Catalog {
    public List<Product> all() {
        return List.of(new Product("CF-01", "Ca phe hat 500g", 185_000),
                new Product("TR-01", "Tra o long 200g", 120_000));
    }

    public long priceWithVat(Product product) {
        return PriceRules.withVat(product.price());
    }
}
EOF
cat > catalog/src/shop/catalog/internal/PriceRules.java <<'EOF'
package shop.catalog.internal;

public final class PriceRules {
    public static long withVat(long price) {
        return price + price * 10 / 100;
    }
}
EOF
cat > app/src/module-info.java <<'EOF'
module shop.app {
    requires shop.catalog;
    requires java.logging;
}
EOF
cat > app/src/shop/app/Main.java <<'EOF'
package shop.app;

import java.util.logging.Logger;
import shop.catalog.Catalog;
import shop.catalog.Product;

public class Main {
    private static final Logger LOG = Logger.getLogger("shop.app");

    public static void main(String[] args) {
        System.out.println("app module: " + Main.class.getModule());
        Catalog catalog = new Catalog();
        for (Product p : catalog.all()) {
            System.out.println(p.sku() + " " + catalog.priceWithVat(p));
        }
        System.out.println("catalog module: " + Catalog.class.getModule());
        LOG.fine("listed " + catalog.all().size() + " products");
    }
}
EOF
```

</Terminal>

`PriceRules` phải `public` vì `Catalog` ở package khác gọi nó. `LOG.fine(...)` ở mức FINE, thấp hơn mức INFO mặc định nên không in gì; nó ở đó để `shop.app` thật sự dùng module `java.logging`.

### 2. Build và chạy trên module path

<Terminal where="mac">

```bash
cd ~/masteva-j3/jpms
javac -d out/shop.catalog $(find catalog/src -name '*.java')
mkdir -p mods && jar --create --file mods/shop.catalog.jar -C out/shop.catalog .
javac --module-path mods -d out/shop.app $(find app/src -name '*.java')
jar --create --file mods/shop.app.jar --main-class shop.app.Main -C out/shop.app .
java --module-path mods --describe-module shop.catalog
java --module-path mods --module shop.app
```

</Terminal>

<Expected>

```text

exports shop.catalog
requires java.base mandated
contains shop.catalog.internal
app module: module shop.app
CF-01 203500
TR-01 132000

```

</Expected>

- `jar` gói thư mục `.class` thành file `.jar`; `-C out/shop.catalog .` nghĩa là lấy mọi thứ trong thư mục đó. `javac --module-path mods` (viết tắt `-p`) tìm module `shop.catalog` trong `mods` để biên dịch `shop.app`. `--main-class` ghi lớp chính vào jar, nên `java --module shop.app` (viết tắt `-m shop.app`) không cần tên lớp.
- `--describe-module` đọc `module-info.class`. Phần `...` là thư mục home của bạn. `mandated` nghĩa là `java.base` được thêm tự động; `contains` liệt kê package có trong module mà không export.

### 3. Gọi package không được export

Một đồng nghiệp viết chương trình khuyến mãi và gọi thẳng `PriceRules`. File nằm ở thư mục `promo` riêng để không lẫn vào mã nguồn chính:

<Terminal where="mac" title="Tạo promo/shop/app/Promo.java">

```bash
cd ~/masteva-j3/jpms
mkdir -p promo/shop/app
cat > promo/shop/app/Promo.java <<'EOF'
package shop.app;

import shop.catalog.internal.PriceRules;

public class Promo {
    public static void main(String[] args) {
        System.out.println("flash sale: " + PriceRules.withVat(99_000));
    }

EOF
javac --module-path mods -d out/promo $(find app/src promo -name '*.java')
javac --class-path mods/shop.catalog.jar -d out/promo-cp promo/shop/app/Promo.java && java --class-path mods/shop.catalog.jar:out/promo-cp shop.app.Promo
```

</Terminal>

Lệnh `javac` đầu biên dịch `Promo` như một phần của module `shop.app`. Dòng cuối biên dịch và chạy đúng file đó trên classpath, với cùng jar `shop.catalog.jar`.

Trên classpath, `module-info.class` trong jar bị bỏ qua và `PriceRules` chỉ là một lớp `public` bình thường. Đóng gói mạnh chỉ có tác dụng khi **cả hai bên** là module trên module path.

### 4. Thiếu module: lỗi lúc khởi động hay lỗi lúc chạy

Chạy hai jar trên classpath, rồi bỏ jar catalog đi trên cả hai đường. Cuối cùng, hỏi `jdeps` xem `shop.app` thật sự cần những module nào:

<Terminal where="mac">

```bash
cd ~/masteva-j3/jpms
java --class-path mods/shop.catalog.jar:mods/shop.app.jar shop.app.Main
java --module-path mods/shop.app.jar --module shop.app
java --class-path mods/shop.app.jar shop.app.Main
jdeps --module-path mods --list-deps mods/shop.app.jar
```

</Terminal>

<Predict question="Lệnh 2 và 3 đều thiếu shop.catalog.jar. Lệnh nào kịp in dòng app module trước khi chết?">

	at shop.app.Main.main(Main.java:12)

Chỉ lệnh 3, bản classpath. Trên module path, JVM giải quyết mọi `requires` **trước** khi chạy `main`, nên thiếu module là dừng ngay. Trên classpath, JVM chỉ đi tìm `Catalog` khi dòng 12 dùng tới nó; với một service thật, đó có thể là lúc một request hiếm gặp chạy vào nhánh code đó. Lệnh 1 cho thấy trên classpath cả hai lớp nằm chung một unnamed module; số sau `@` là identity hash của đối tượng module, trên máy bạn có thể khác. `jdeps` đọc bytecode và liệt kê đúng ba module mà `module-info.java` khai báo.

</Predict>

<Check id="j3.4.lab-missing-module">Chỉ ra được trong output: thiếu module trên module path báo `FindException` trước khi chạy `main`, còn trên classpath báo `NoClassDefFoundError` khi lớp được dùng lần đầu.</Check>

### 5. Đóng gói mạnh của JDK và --add-opens

Chương trình dưới đây làm điều nhiều thư viện cũ từng làm: đọc field `private` bên trong `ArrayList` bằng reflection để biết dung lượng mảng.

<Terminal where="mac" title="Tạo peek/Peek.java và chạy">

```bash
cd ~/masteva-j3/jpms
mkdir -p peek
cat > peek/Peek.java <<'EOF'
import java.lang.reflect.Field;
import java.util.ArrayList;
import java.util.List;

public class Peek {
    public static void main(String[] args) throws Exception {
        List<String> cart = new ArrayList<>(List.of("CF-01"));
        Field field = ArrayList.class.getDeclaredField("elementData");
        field.setAccessible(true);
        Object[] data = (Object[]) field.get(cart);
        System.out.println("size=" + cart.size() + " capacity=" + data.length);
    }
}
EOF
java peek/Peek.java
java --illegal-access=permit peek/Peek.java
java --add-opens java.base/java.util=ALL-UNNAMED peek/Peek.java
```

</Terminal>

### 6. Jar chưa có module-info: automatic module

Phần lớn thư viện bạn dùng chưa có `module-info`. Tạo một jar như vậy, xem module system đặt tên cho nó, rồi thêm `Automatic-Module-Name` vào manifest:

<Terminal where="mac" title="Thư viện acme-tax không có module-info">

```bash
cd ~/masteva-j3/jpms
mkdir -p legacy/src/com/acme/tax libs
cat > legacy/src/com/acme/tax/TaxTable.java <<'EOF'
package com.acme.tax;

public class TaxTable {
    public static int vatPercent(String category) {
        return category.equals("book") ? 5 : 10;
    }
}
EOF
javac -d out/legacy legacy/src/com/acme/tax/TaxTable.java
jar --create --file libs/acme-tax-1.4.0.jar -C out/legacy .
jar --describe-module --file libs/acme-tax-1.4.0.jar
printf 'Automatic-Module-Name: com.acme.tax\n' > legacy/manifest.txt
jar --update --file libs/acme-tax-1.4.0.jar --manifest legacy/manifest.txt
jar --describe-module --file libs/acme-tax-1.4.0.jar
```

</Terminal>

<Expected>

```text
No module descriptor found. Derived automatic module.

acme.tax@1.4.0 automatic
requires java.base mandated
contains com.acme.tax

No module descriptor found. Derived automatic module.

com.acme.tax@1.4.0 automatic
requires java.base mandated
contains com.acme.tax
```

</Expected>

Lần đầu, tên `acme.tax` suy ra từ tên file: bỏ `-1.4.0` làm phiên bản, đổi `-` thành `.`. Nếu tác giả đổi artifact thành `acme-taxes`, mọi `requires acme.tax` sẽ gãy. Sau khi thêm `Automatic-Module-Name`, tên là `com.acme.tax` dù file tên gì. Nó vẫn là automatic module, export mọi package và không giấu gì, nhưng tên giờ ổn định. Spring Framework và Spring Boot làm đúng như vậy.

### 7. jlink: runtime chỉ gồm module cần thiết

Vì mọi module đều khai báo rõ phụ thuộc, `jlink` tính được tập module tối thiểu và tạo một thư mục runtime riêng, có lệnh chạy `bin/shop`. Trên Linux, thay `$(/usr/libexec/java_home -v 25)` bằng `$JAVA_HOME`:

<Terminal where="mac">

```bash
cd ~/masteva-j3/jpms
jlink --module-path mods --add-modules shop.app --launcher shop=shop.app --strip-debug --no-header-files --no-man-pages --output image
du -sh image "$(/usr/libexec/java_home -v 25)"
image/bin/java --list-modules
image/bin/shop
jlink --module-path mods:libs --add-modules shop.app,com.acme.tax --output image-tax
```

</Terminal>

<Expected>

```text

363M	/Library/Java/JavaVirtualMachines/jdk-25.jdk/Contents/Home
java.base@25.0.3
java.logging@25.0.3
shop.app
shop.catalog
app module: module shop.app
CF-01 203500
TR-01 132000
catalog module: module shop.catalog
Error: automatic module cannot be used with jlink: com.acme.tax from file:///.../masteva-j3/jpms/libs/acme-tax-1.4.0.jar
```

</Expected>

Kích thước phụ thuộc hệ điều hành và bản phân phối JDK. Trên máy kiểm chứng, runtime chỉ có 4 module và 43 MB so với 363 MB của JDK đầy đủ; phần lớn là `lib/modules` (24 MB) và thư viện JVM (17 MB). Thêm `--compress zip-6` thì còn khoảng 30 MB, đổi lại khởi động có thể chậm hơn một chút vì phải giải nén.

Lệnh `jlink` cuối thử đưa thêm thư viện `acme-tax` của bước 6 và bị từ chối. Automatic module không có danh sách `requires` thật, nên `jlink` không tính được nó cần gì. Một ứng dụng có hàng chục thư viện chỉ có `Automatic-Module-Name`, như ứng dụng Spring, không đóng được trọn vào `jlink` theo cách này.

<Check id="j3.4.lab-jlink">Tạo được runtime bằng `jlink`, đọc được kích thước và danh sách module của nó, và giải thích vì sao automatic module bị từ chối.</Check>

### Khi gặp lỗi

<Callout kind="pitfall">

- `error: module not found: shop.catalog` khi biên dịch `shop.app`: thiếu `--module-path mods`, hoặc chưa build `mods/shop.catalog.jar` ở bước 1.
- `error: package java.util.logging is not visible ... but module shop.app does not read it`: package có export, nhưng `module-info.java` của bạn thiếu `requires java.logging`. Chữ "does not read it" luôn nghĩa là thiếu `requires`; chữ "does not export it" nghĩa là module kia giấu package đó.
- `module shop.catalog does not have a ModuleMainClass attribute, use -m <module>/<main-class>`: bạn chạy `-m` với module không có lớp chính. Ghi rõ `-m shop.app/shop.app.Main`, hoặc tạo jar với `--main-class`.
- `java.lang.LayerInstantiationException: Package shop.catalog in both module shop.catalog and module shop.extra`: hai module chứa cùng một package (split package). Trên classpath điều này được phép, trên module path thì không; gộp package hoặc đổi tên.
- `InaccessibleObjectException ... does not "opens" ...`: reflection bị chặn. Với package của JDK, nâng thư viện gây lỗi hoặc tạm thêm `--add-opens`. Với module của bạn, thêm `opens <package>` vào `module-info.java`.

</Callout>

<Reveal title="Ứng dụng Spring Boot mới có nên viết module-info.java không?">

Thường là không. Jar thực thi của Spring Boot nạp thư viện qua classloader riêng, tức classpath, nên `module-info` của bạn không được dùng tới khi chạy. Nếu chạy trên module path, bạn phải `opens` mọi package mà Spring, Jackson, Hibernate cần reflection vào, và xử lý thư viện chỉ là automatic module. Lợi ích chính của JPMS cho ứng dụng là ranh giới giữa các phần, và Maven multi-module (J7) hoặc Spring Modulith (J19) cho ranh giới đó với ít ma sát hơn.

</Reveal>

<Reveal title="Ứng dụng chạy trên classpath có dùng được jlink không?">

Được, nhưng chỉ cho phần JDK. `jdeps --print-module-deps` liệt kê module JDK mà các jar cần, ví dụ `java.base,java.logging,java.sql`; đưa danh sách đó cho `jlink --add-modules` để có một JRE nhỏ, rồi vẫn chạy ứng dụng bằng `-cp` hay `-jar` trên JRE đó. Cách này hay dùng để làm image container nhỏ hơn (J17). Rủi ro: code nạp module qua reflection hoặc `ServiceLoader`, như driver JDBC hay charset trong `jdk.charsets` (J9), không hiện trong `jdeps`, và chỉ lộ ra lúc chạy.

</Reveal>

<Reveal title="jdeps có tìm ra chỗ Peek đụng vào bên trong java.util không?">

Không. Biên dịch `Peek` rồi chạy `jdeps --jdk-internals` trên thư mục `.class`, kết quả rỗng. `jdeps` thấy được lời gọi **trực tiếp** tới lớp nội bộ như `sun.misc.Unsafe`, vì lời gọi đó nằm trong bytecode. Reflection dùng tên field là chuỗi `"elementData"`, nên phân tích tĩnh không thấy. Lỗi loại này chỉ lộ ra khi chạy, vì vậy hãy chạy test trên đúng phiên bản Java của production trước khi nâng cấp.

</Reveal>
