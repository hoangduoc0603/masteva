<Goal>

Hiểu module system của Java (JPMS, Java Platform Module System) giải quyết điều gì mà package và access modifier ở J3.1 không làm được, và nó tốn gì. Đây là chủ đề tuỳ chọn: ứng dụng bạn viết ở các chặng sau vẫn chạy trên classpath (danh sách nơi JVM tìm lớp, chính là `-cp` ở J1.1), nhưng bạn sẽ gặp module mỗi ngày qua thông báo lỗi của JDK. Học xong bài này, bạn giải thích được:

- Vì sao một lớp `public` trong package `internal` vẫn bị code khác gọi, và module chặn việc đó ngay lúc biên dịch thế nào.
- Vì sao thiếu một thư viện trên classpath chỉ lộ ra khi code chạm tới nó, còn trên module path thì JVM không khởi động.
- Vì sao một thư viện cũ chạy tốt trên Java 11 lại báo `InaccessibleObjectException` khi lên Java 17, và `--add-opens` sửa tạm ra sao.
- Vì sao ứng dụng Spring Boot thường vẫn chạy trên classpath, dù Java có module từ phiên bản 9.

</Goal>

<Knowledge>

Bài này dùng nhiều lệnh của JDK (`javac`, `java`, `jar`, `jdeps`, `jlink`), vì module là chuyện của cách biên dịch và chạy chương trình chứ không chỉ của mã nguồn. Mọi lệnh chạy ở thư mục gốc `jpms` của ví dụ, trên Mac và Linux như nhau trừ chỗ có ghi chú.

### Điều package không làm được

Thư viện catalog của cửa hàng có hai package: một package là API cho người dùng, một package chứa chi tiết cài đặt mà bạn muốn đổi tự do.

```text
shop.catalog            Catalog, Product        API cho người dùng
shop.catalog.internal   PriceRules              chi tiết cài đặt
```

`Catalog` cần gọi `PriceRules.withVat(...)`. Vì hai lớp nằm ở hai package khác nhau, `PriceRules` buộc phải `public` (J3.1), và khi đã `public` thì **mọi** đoạn code trên classpath đều gọi được nó. Chữ `internal` trong tên package chỉ là lời nhắn, không phải rào chắn. Sau vài năm, team khác dùng `PriceRules` trực tiếp, và bạn không đổi được nó mà không làm vỡ code của họ.

Thư viện thường được phát hành dưới dạng **jar**: một file nén chứa các file `.class`. Classpath còn hai điểm yếu khác:

- Classpath là một danh sách jar phẳng, không ghi jar nào cần jar nào. Thiếu một jar thì JVM vẫn khởi động bình thường, rồi chết với `NoClassDefFoundError` ở lần đầu code chạm vào lớp bị thiếu, có thể sau vài giờ chạy.
- Khi hai jar chứa cùng một lớp (thường là hai phiên bản của một thư viện), JVM lấy bản tìm thấy trước theo thứ tự classpath. Lỗi kiểu này hay được gọi là **JAR hell**.

### Module và module-info.java

**Module** là một nhóm package có tên, kèm một file mô tả `module-info.java` đặt ở gốc thư mục nguồn. File này nói module cần module nào và cho bên ngoài dùng package nào. Ví dụ có hai module, mỗi module một thư mục nguồn:

```text
jpms/
├── catalog/src/
│   ├── module-info.java                      module shop.catalog
│   └── shop/catalog/
│       ├── Product.java
│       ├── Catalog.java
│       └── internal/PriceRules.java
└── app/src/
    ├── module-info.java                      module shop.app
    └── shop/app/Main.java
```

Module `shop.catalog` chỉ export package API; `shop.catalog.internal` không được nhắc tới, nên nó bị giấu:

```java norun
module shop.catalog {
    exports shop.catalog;
}
```

Ba lớp của `shop.catalog` là lớp Java bình thường. `PriceRules` vẫn `public`, vì `Catalog` ở package khác cần gọi nó:

```java norun
package shop.catalog;

public record Product(String sku, String name, long price) {}
```

```java norun
package shop.catalog;

import java.util.List;
import shop.catalog.internal.PriceRules;

public final class Catalog {
    public List<Product> all() {
        return List.of(new Product("CF-01", "Ca phe hat 500g", 185_000),
                new Product("TR-01", "Tra o long 200g", 120_000));
    }

    public long priceWithVat(Product product) {
        return PriceRules.withVat(product.price());
    }
}
```

```java norun
package shop.catalog.internal;

public final class PriceRules {
    public static long withVat(long price) {
        return price + price * 10 / 100;
    }
}
```

Module `shop.app` khai báo hai module nó cần. `java.util.logging` nằm ở module `java.logging` của JDK, nên dùng logger cũng phải `requires`:

```java norun
module shop.app {
    requires shop.catalog;
    requires java.logging;
}
```

```java norun
package shop.app;

import java.util.logging.Logger;
import shop.catalog.Catalog;
import shop.catalog.Product;

public class Main {
    private static final Logger LOG = Logger.getLogger("shop.app");

    public static void main(String[] args) {
        IO.println("app module: " + Main.class.getModule());
        Catalog catalog = new Catalog();
        for (Product p : catalog.all()) {
            IO.println(p.sku() + " " + catalog.priceWithVat(p));
        }
        IO.println("catalog module: " + Catalog.class.getModule());
        LOG.fine("listed " + catalog.all().size() + " products");
    }
}
```

`Main` in tên module của chính nó và của `Catalog`, để bạn thấy mỗi lớp nằm ở module nào. `LOG.fine(...)` ở mức FINE, thấp hơn mức INFO mặc định nên không in gì; nó ở đó để `shop.app` thật sự dùng `java.logging`. Bảng dưới là các chỉ thị hay gặp trong `module-info.java`:

| Chỉ thị | Nghĩa |
|---|---|
| `requires M` | Module này **đọc** (read) module `M`: dùng được các package mà `M` export |
| `requires transitive M` | Như trên, và ai `requires` module này thì cũng tự đọc `M` |
| `exports p` | Lớp `public` trong package `p` dùng được từ module khác, lúc biên dịch và lúc chạy |
| `opens p` | Cho reflection (API đọc, ghi field và gọi method của lớp khác lúc chạy, theo tên dạng chuỗi) truy cập cả thành viên `private` của package `p`, chỉ lúc chạy |

Mọi module tự động `requires java.base`, module chứa `java.lang`, `java.util`. Bản thân JDK được chia thành nhiều module; JDBC (API kết nối database) ở `java.sql`, logger ở `java.logging`. `java --list-modules` liệt kê các module của JDK đang cài.

Build hai module theo thứ tự phụ thuộc: `shop.catalog` trước, gói thành jar trong thư mục `mods`, vì `shop.app` cần nó lúc biên dịch. Hai lệnh cuối đọc mô tả của module catalog rồi chạy ứng dụng:

<Terminal where="mac">

```bash
javac -d out/shop.catalog $(find catalog/src -name '*.java')
mkdir -p mods && jar --create --file mods/shop.catalog.jar -C out/shop.catalog .
javac --module-path mods -d out/shop.app $(find app/src -name '*.java')
jar --create --file mods/shop.app.jar --main-class shop.app.Main -C out/shop.app .
java --module-path mods --describe-module shop.catalog
java --module-path mods --module shop.app
```

</Terminal>

Kết quả:

```text
shop.catalog file:///.../jpms/mods/shop.catalog.jar
exports shop.catalog
requires java.base mandated
contains shop.catalog.internal
app module: module shop.app
CF-01 203500
TR-01 132000
catalog module: module shop.catalog
```

Phần `...` là đường dẫn trên máy bạn. Các tuỳ chọn trong lệnh:

- `jar --create` gói thư mục `.class` thành file `.jar`; `-C out/shop.catalog .` nghĩa là lấy mọi thứ trong thư mục đó. `--main-class` ghi lớp chính vào jar, nên `java --module shop.app` (viết tắt `-m`) không cần tên lớp.
- `--module-path mods` (viết tắt `-p`) bảo `javac` và `java` tìm module trong thư mục `mods`.
- `--describe-module` đọc `module-info.class`. `mandated` nghĩa là `java.base` được thêm tự động; `contains` liệt kê package có trong module mà không export.

Dòng `app module: module shop.app` xác nhận `Main` chạy trong một module có tên. Một lớp ở module A dùng được lớp `T` ở module B khi đủ **cả ba** điều kiện:

```text
 module shop.app                         module shop.catalog
 +------------------------+              +-------------------------------------+
 | requires shop.catalog -|--(1) đọc --->| exports shop.catalog   (2)          |
 |                        |              |   public class Catalog (3)   OK     |
 | Main dùng Catalog      |              |                                     |
 | Main dùng PriceRules --|---- X ------>| shop.catalog.internal  không export |
 +------------------------+              |   public class PriceRules   ◄ CHẶN  |
                                         +-------------------------------------+
 (1) A requires B     (2) B exports package của T     (3) T là public
```

`public` giờ nghĩa là "public cho những module được phép", không còn là "public cho mọi nơi". Đó là **đóng gói mạnh (strong encapsulation)**.

### public không còn đủ: package không export

Một đồng nghiệp viết chương trình khuyến mãi và gọi thẳng `PriceRules`. File nằm ở thư mục `promo/shop/app/Promo.java`, cùng package với `Main`:

```java norun
package shop.app;

import shop.catalog.internal.PriceRules;

public class Promo {
    public static void main(String[] args) {
        IO.println("flash sale: " + PriceRules.withVat(99_000));
    }
}
```

Lệnh `javac` đầu biên dịch `Promo` như một phần của module `shop.app`, trên module path. Dòng thứ hai biên dịch và chạy đúng file đó trên classpath, với cùng jar `shop.catalog.jar`:

<Terminal where="mac">

```bash
javac --module-path mods -d out/promo $(find app/src promo -name '*.java')
javac --class-path mods/shop.catalog.jar -d out/promo-cp promo/shop/app/Promo.java && java --class-path mods/shop.catalog.jar:out/promo-cp shop.app.Promo
```

</Terminal>

<Predict question="PriceRules là lớp public, có method public static. Hai cách biên dịch cho kết quả gì?">

```text
promo/shop/app/Promo.java:3: error: package shop.catalog.internal is not visible
import shop.catalog.internal.PriceRules;
                   ^
  (package shop.catalog.internal is declared in module shop.catalog, which does not export it)
1 error
flash sale: 108900
```

Trên module path, `javac` báo lỗi ngay ở dòng `import`. Trên classpath, chương trình biên dịch và chạy bình thường.

</Predict>

Trên module path, `public` không còn đủ: package phải được export. Đây đúng là thứ J3.1 không chặn được bằng access modifier. Trên classpath, `module-info.class` trong jar bị bỏ qua, và `PriceRules` chỉ là một lớp `public` bình thường. Đóng gói mạnh chỉ có tác dụng khi **cả hai bên** là module trên module path.

Thông báo lỗi của module có hai dạng hay bị nhầm. "does not export it" nghĩa là module kia giấu package đó. "does not read it" nghĩa là package có export, nhưng `module-info.java` của bạn thiếu `requires` tới module chứa nó; ví dụ bỏ dòng `requires java.logging;` thì `javac` báo `package java.util.logging is not visible` kèm `module shop.app does not read it`.

### Module path và classpath

Từ Java 9, `java` và `javac` có hai nơi tìm code. Một jar chỉ được coi là module khi nằm trên **module path** (`--module-path`). Cùng jar đó đặt trên classpath thì `module-info.class` bị bỏ qua, như `Promo` ở mục trước. Lệnh dưới chạy ứng dụng trên classpath, với đủ hai jar:

<Terminal where="mac">

```bash
java --class-path mods/shop.catalog.jar:mods/shop.app.jar shop.app.Main
```

</Terminal>

Kết quả sẽ giống thế này; số sau `@` là mã băm của đối tượng module, trên máy bạn sẽ khác:

```text varies
app module: unnamed module @659e0bfd
CF-01 203500
TR-01 132000
catalog module: unnamed module @659e0bfd
```

Trên classpath, cả hai lớp nằm chung một **unnamed module**: module không tên chứa mọi thứ trên classpath. Khác biệt giữa hai đường lộ rõ nhất khi thiếu một jar. Hai lệnh dưới bỏ `shop.catalog.jar`, lần lượt trên module path và trên classpath:

<Terminal where="mac">

```bash
java --module-path mods/shop.app.jar --module shop.app
java --class-path mods/shop.app.jar shop.app.Main
```

</Terminal>


Chỉ lệnh thứ hai, bản classpath, in được dòng đầu tiên. Hai dòng đầu của output là của lệnh trên module path.

Trên module path, JVM giải quyết mọi `requires` **trước** khi chạy `main`, nên thiếu module là dừng ngay, chưa chạy dòng code nào. Trên classpath, JVM chỉ đi tìm `Catalog` khi dòng 12 của `Main` dùng tới nó; với một service thật, đó có thể là lúc một request hiếm gặp chạy vào nhánh code đó.

Bạn cũng hỏi được `jdeps` (công cụ phân tích phụ thuộc của JDK) xem một module cần những module nào:

<Terminal where="mac">

```bash
jdeps --module-path mods --list-deps mods/shop.app.jar
```

</Terminal>

Kết quả:

```text
   java.base
   java.logging
   shop.catalog
```

`jdeps` đọc bytecode và liệt kê hai module khai báo trong `module-info.java`, cộng `java.base` mà mọi module luôn có. Hai module cùng chứa một package thì gọi là **split package**: trên classpath điều này được phép, trên module path thì JVM từ chối khởi động. Bảng dưới tóm tắt hai đường:

| | Classpath (`-cp`) | Module path (`-p`) |
|---|---|---|
| Đơn vị | Lớp, tìm theo thứ tự jar | Module có tên, phụ thuộc khai báo rõ |
| Thiếu phụ thuộc | Phát hiện khi lớp được dùng lần đầu: `NoClassDefFoundError` | Phát hiện khi JVM khởi động: `FindException` |
| `public` | Dùng được từ mọi nơi | Chỉ khi package được export |
| Cùng package ở hai jar | Được, bản đứng trước thắng | Lỗi khi khởi động (split package) |
| Code nằm ở | Unnamed module: đọc mọi module, export mọi package | Module có tên (named module) |

Phần lớn thư viện bạn dùng chưa có `module-info`. Jar như vậy đặt trên module path thì thành **automatic module**:

- Nó export và `opens` mọi package, đọc mọi module khác.
- Nó cũng đọc unnamed module, nên dùng được lớp trên classpath.
- Tên của nó lấy từ thuộc tính `Automatic-Module-Name` trong file `META-INF/MANIFEST.MF` (file mô tả nằm trong jar) nếu có; nếu không, tên suy ra từ tên file.

Thư viện thuế `acme-tax` dưới đây chỉ có một lớp, nằm ở `legacy/src/com/acme/tax/TaxTable.java`, và không có `module-info.java`:

```java norun
package com.acme.tax;

public class TaxTable {
    public static int vatPercent(String category) {
        return category.equals("book") ? 5 : 10;
    }
}
```

Các lệnh dưới biên dịch và đóng gói nó thành `libs/acme-tax-1.4.0.jar`, rồi xem module system đặt tên cho jar trước và sau khi thêm `Automatic-Module-Name` vào manifest:

<Terminal where="mac">

```bash
javac -d out/legacy legacy/src/com/acme/tax/TaxTable.java
mkdir -p libs && jar --create --file libs/acme-tax-1.4.0.jar -C out/legacy .
jar --describe-module --file libs/acme-tax-1.4.0.jar
printf 'Automatic-Module-Name: com.acme.tax\n' > legacy/manifest.txt
jar --update --file libs/acme-tax-1.4.0.jar --manifest legacy/manifest.txt
jar --describe-module --file libs/acme-tax-1.4.0.jar
```

</Terminal>

Kết quả:

```text
No module descriptor found. Derived automatic module.

acme.tax@1.4.0 automatic
requires java.base mandated
contains com.acme.tax

No module descriptor found. Derived automatic module.

com.acme.tax@1.4.0 automatic
requires java.base mandated
contains com.acme.tax
```

Lần đầu, tên `acme.tax` suy ra từ tên file: bỏ `-1.4.0` làm phiên bản, đổi `-` thành `.`. Nếu người phát hành đổi tên file thành `acme-taxes`, mọi `requires acme.tax` sẽ gãy. Sau khi thêm `Automatic-Module-Name`, tên là `com.acme.tax` dù file tên gì. Nó vẫn là automatic module, export mọi package và không giấu gì, nhưng tên giờ ổn định. Vì vậy thư viện nghiêm túc ghi sẵn `Automatic-Module-Name`, để người dùng `requires` một cái tên không đổi.

### Đóng gói mạnh của chính JDK

Một thư viện chạy tốt trên Java 11 ném `InaccessibleObjectException` ngay khi chạy trên Java 17, dù không dòng code nào của nó thay đổi.

Module của JDK chỉ export API chính thức; field `private` bên trong `java.util` không còn mở cho reflection. Chương trình dưới làm điều nhiều thư viện cũ từng làm: đọc field `private` `elementData` (mảng chứa phần tử) bên trong `ArrayList` để biết dung lượng thật. `Field`, `getDeclaredField` và `setAccessible(true)` là API reflection: tìm một field theo tên rồi xin quyền đọc nó dù nó là `private`.

```java
import java.lang.reflect.Field;
import java.util.ArrayList;
import java.util.List;

public class Peek {
    public static void main(String[] args) throws Exception {
        List<String> cart = new ArrayList<>(List.of("CF-01"));
        Field field = ArrayList.class.getDeclaredField("elementData");
        field.setAccessible(true);
        Object[] data = (Object[]) field.get(cart);
        IO.println("size=" + cart.size() + " capacity=" + data.length);
    }
}
```

Kết quả sẽ giống thế này; số sau `@` trên máy bạn sẽ khác:

```text varies
Exception in thread "main" java.lang.reflect.InaccessibleObjectException: Unable to make field transient java.lang.Object[] java.util.ArrayList.elementData accessible: module java.base does not "opens java.util" to unnamed module @29f69090
	at java.base/java.lang.reflect.AccessibleObject.throwInaccessibleObjectException(AccessibleObject.java:353)
	at java.base/java.lang.reflect.AccessibleObject.checkCanSetAccessible(AccessibleObject.java:329)
	at java.base/java.lang.reflect.AccessibleObject.checkCanSetAccessible(AccessibleObject.java:277)
	at java.base/java.lang.reflect.Field.checkCanSetAccessible(Field.java:179)
	at java.base/java.lang.reflect.Field.setAccessible(Field.java:173)
	at Peek.main(Peek.java:9)
```

Đọc thông báo theo đúng cấu trúc của nó: module nào (`java.base`) không mở package nào (`java.util`) cho ai (`unnamed module`, tức code trên classpath). Lỗi nổ ở `setAccessible(true)`, dòng 9, không phải ở `getDeclaredField`: tìm field theo tên vẫn được, xin quyền đọc field `private` thì bị chặn.

Thay đổi này đến dần qua các phiên bản. Java 8 cho reflection tự do. Java 9 tới 15 vẫn cho nhưng in cảnh báo `Illegal reflective access`. Java 16 ([JEP 396](https://openjdk.org/jeps/396)) chặn mặc định nhưng còn mở lại được bằng `--illegal-access=permit`. Từ Java 17 ([JEP 403](https://openjdk.org/jeps/403)), tuỳ chọn đó bị bỏ hẳn. Lối thoát còn lại là **`--add-opens <module>/<package>=<module nhận>`**, mở một package cụ thể cho reflection; code trên classpath có tên module nhận là `ALL-UNNAMED`. Hai lệnh dưới chạy lại `Peek.java` với từng tuỳ chọn:

<Terminal where="mac">

```bash
java --illegal-access=permit Peek.java
java --add-opens java.base/java.util=ALL-UNNAMED Peek.java
```

</Terminal>

Kết quả sẽ giống thế này; phần stack trace của lệnh đầu giống hệt output ở trên nên được lược bớt, và số sau `@` trên máy bạn sẽ khác:

```text varies
Java HotSpot(TM) 64-Bit Server VM warning: Ignoring option --illegal-access=permit; support was removed in 17.0
Exception in thread "main" java.lang.reflect.InaccessibleObjectException: Unable to make field transient java.lang.Object[] java.util.ArrayList.elementData accessible: module java.base does not "opens java.util" to unnamed module @29f69090
size=1 capacity=1
```

`--illegal-access=permit`, cách sửa quen thuộc trên Java 9 tới 16, giờ chỉ còn một dòng cảnh báo. Với bản JDK khác như Temurin, dòng đó bắt đầu bằng `OpenJDK 64-Bit Server VM`. Chỉ `--add-opens` mở được đúng package đó, và chương trình in dung lượng mảng. `--add-exports` tương tự nhưng chỉ mở lớp `public` của một package không export, cho biên dịch và gọi trực tiếp, không cho đọc `private`. Với jar chạy bằng `java -jar`, có thể ghi thuộc tính `Add-Opens:` vào manifest thay cho tham số dòng lệnh.

Bạn có thể mong `jdeps` tìm ra những chỗ như thế này trước khi nâng cấp Java. `jdeps --jdk-internals` liệt kê code dùng API nội bộ của JDK. Chạy nó trên `Peek` đã biên dịch:

<Terminal where="mac">

```bash
javac -d out/peek Peek.java
jdeps --jdk-internals out/peek
```

</Terminal>

Kết quả: lệnh chạy xong mà không in gì. Thử tự trả lời trước khi đọc tiếp: `Peek` đọc thẳng vào bên trong `java.util`, vì sao `jdeps` không thấy?

`jdeps` thấy được lời gọi **trực tiếp** tới lớp nội bộ như `sun.misc.Unsafe`, vì lời gọi đó nằm trong bytecode. Reflection dùng tên field là chuỗi `"elementData"`, nên phân tích tĩnh không thấy. Lỗi loại này chỉ lộ ra khi chạy, vì vậy hãy chạy test trên đúng phiên bản Java của production trước khi nâng cấp.

<Callout kind="production">

Một team nâng service từ Java 11 lên 17. Build xanh, nhưng service chết ngay khi khởi động với `InaccessibleObjectException: Unable to make field ... accessible: module java.base does not "opens java.util" to unnamed module`. Trên Java 11, thư viện đó vẫn reflection được vào `java.util`, chỉ in một dòng cảnh báo mà không ai đọc. Cách sửa đúng là nâng thư viện lên bản hỗ trợ Java 17. Thêm `--add-opens java.base/java.util=ALL-UNNAMED` chỉ là cách chữa cháy: ghi lại lý do ngay cạnh tham số và gỡ nó khi đã nâng thư viện.

</Callout>

`exports` và `opens` tách riêng có chủ ý. Framework như Jackson, Hibernate, Spring đọc và ghi field `private` của lớp bạn bằng reflection. Nếu ứng dụng của bạn là module, package chứa entity hay DTO (đối tượng chỉ chở dữ liệu giữa các phần của chương trình) cần `opens` (hoặc `opens ... to` đúng module framework), dù không cần `exports`: framework được nhìn vào bên trong lúc chạy, nhưng không module nào viết được `import` tới package đó. `open module` mở mọi package cho reflection một lần, tiện nhưng bỏ phần lớn lợi ích của đóng gói mạnh.

### jlink: runtime chỉ gồm module cần thiết

Một công cụ dòng lệnh nội bộ cần chạy trên máy không cài JDK. Đóng kèm cả JDK thì nặng vài trăm MB, trong khi công cụ chỉ dùng vài module.

Vì mọi module đều khai báo rõ phụ thuộc, **`jlink`** tính được tập module tối thiểu và tạo một thư mục runtime riêng: một JVM chỉ chứa các module đó, kèm lệnh chạy `bin/shop`. Lệnh `du -sh` so kích thước runtime với JDK đầy đủ; trên Linux, thay `$(/usr/libexec/java_home -v 25)` bằng `$JAVA_HOME`. Lệnh `jlink` cuối thử đưa thêm thư viện `acme-tax` ở mục trước:

<Terminal where="mac">

```bash
jlink --module-path mods --add-modules shop.app --launcher shop=shop.app --strip-debug --no-header-files --no-man-pages --output image
du -sh image "$(/usr/libexec/java_home -v 25)"
image/bin/java --list-modules
image/bin/shop
jlink --module-path mods:libs --add-modules shop.app,com.acme.tax --output image-tax
```

</Terminal>

Kết quả:

```text
 43M	image
363M	/Library/Java/JavaVirtualMachines/jdk-25.jdk/Contents/Home
java.base@25.0.3
java.logging@25.0.3
shop.app
shop.catalog
app module: module shop.app
CF-01 203500
TR-01 132000
catalog module: module shop.catalog
Error: automatic module cannot be used with jlink: com.acme.tax from file:///.../jpms/libs/acme-tax-1.4.0.jar
```

Kích thước trên máy bạn phụ thuộc hệ điều hành và bản phân phối JDK, nhưng tỉ lệ thì giống nhau: runtime chỉ có 4 module và nặng vài chục MB, so với vài trăm MB của JDK đầy đủ. `--strip-debug` bỏ thông tin debug, `--no-header-files` và `--no-man-pages` bỏ file header C và trang hướng dẫn. Lệnh `jlink` cuối bị từ chối: automatic module không có danh sách `requires` thật, nên `jlink` không tính được nó cần gì. Một ứng dụng có hàng chục thư viện chỉ có `Automatic-Module-Name`, như ứng dụng Spring, không đóng được trọn vào `jlink` theo cách này.

Ứng dụng chạy trên classpath vẫn dùng được `jlink` cho phần JDK. `jdeps --print-module-deps` liệt kê module JDK mà các jar cần, ở dạng đưa thẳng được cho `jlink --add-modules`:

<Terminal where="mac">

```bash
jdeps --print-module-deps --class-path mods/shop.catalog.jar out/shop.app/shop/app/Main.class
```

</Terminal>

Kết quả:

```text
java.base,java.logging
```

Đưa danh sách đó cho `jlink --add-modules java.base,java.logging` là có một JRE nhỏ, rồi vẫn chạy ứng dụng bằng `-cp` hay `-jar` trên JRE đó. Cách này hay dùng để làm image container nhỏ hơn (SB11). Rủi ro là code nạp module qua reflection hoặc `ServiceLoader` (cơ chế tìm cài đặt của một interface lúc chạy), như driver JDBC hay charset trong `jdk.charsets` (J9), không hiện trong `jdeps` và chỉ lộ ra lúc chạy.

### JPMS trên thực tế: có từ Java 9, nhưng ai dùng

Java có module từ năm 2017, nhưng phần lớn ứng dụng bạn sẽ viết không có `module-info.java`. Mỗi nhóm người dùng Java dùng JPMS ở một mức khác nhau:

- **JDK:** dùng hoàn toàn. Mọi thông báo `module java.base does not "opens"` đến từ đây, kể cả khi ứng dụng của bạn không có module nào.
- **Thư viện:** nhiều thư viện chỉ ghi `Automatic-Module-Name` để có tên ổn định. `jar --describe-module --file <jar>` cho bạn biết một jar thuộc loại nào; kết quả với ba jar phổ biến được liệt kê ngay dưới danh sách này.
- **Ứng dụng:** phần lớn ứng dụng server, đặc biệt Spring Boot, chạy trên classpath. Jar thực thi của Spring Boot (SB11) tự nạp các jar trong `BOOT-INF/lib` bằng classloader riêng (thành phần nạp lớp vào JVM), nên mọi thứ nằm trong unnamed module. Ranh giới giữa các phần của ứng dụng thường được giữ bằng Maven multi-module (J7) hoặc test kiến trúc như Spring Modulith (J13).
- **Công cụ phân phối kèm runtime:** ứng dụng desktop, CLI dùng `jlink` như mục trước, và cần mọi module có `module-info` thật.

Ba lệnh dưới kiểm `spring-core` 7.0.9, `spring-boot` 4.1.1 và `jackson-databind` 3.1.5 (Jackson 3, đi cùng Spring Boot 4) trong kho Maven cục bộ `~/.m2` (J7 giải thích kho này; máy bạn chỉ có các jar đó sau khi đã build một project dùng chúng). `unzip -p` in một file nằm trong jar, ở đây là manifest:

<Terminal where="mac">

```bash
unzip -p ~/.m2/repository/org/springframework/spring-core/7.0.9/spring-core-7.0.9.jar META-INF/MANIFEST.MF | grep Automatic-Module-Name
unzip -p ~/.m2/repository/org/springframework/boot/spring-boot/4.1.1/spring-boot-4.1.1.jar META-INF/MANIFEST.MF | grep Automatic-Module-Name
jar --describe-module --file ~/.m2/repository/tools/jackson/core/jackson-databind/3.1.5/jackson-databind-3.1.5.jar | head -3
```

</Terminal>

Kết quả:

```text
Automatic-Module-Name: spring.core
Automatic-Module-Name: spring.boot
tools.jackson.databind@3.1.5 jar:file:///.../jackson-databind-3.1.5.jar!/module-info.class
exports tools.jackson.databind
exports tools.jackson.databind.annotation
```

Hai jar Spring không có `module-info.class`, chỉ ghi `Automatic-Module-Name` trong manifest: trên module path chúng là automatic module có tên ổn định `spring.core`, `spring.boot`. `jackson-databind` thì có `module-info.class` thật. Ứng dụng Spring Boot vì vậy không thể là một tập module trọn vẹn cho `jlink`, kể cả khi chính code của bạn có `module-info.java`. Bảng dưới so hai cách tổ chức:

| | Classpath và package (mặc định) | JPMS |
|---|---|---|
| Giấu lớp `public` nội bộ | Không giấu được | `javac` báo lỗi |
| Thiếu phụ thuộc | Lộ ra muộn, khi lớp được dùng | Lộ ra khi khởi động |
| Chi phí build | Thấp; mọi công cụ hỗ trợ sẵn | Mỗi module cần `module-info`; plugin, IDE, test phải hiểu module path |
| Framework dùng reflection | Chạy luôn | Phải `opens` đúng package, lỗi thường lộ lúc chạy |
| Thư viện cũ | Chạy | Có thể vướng split package hoặc tên automatic module không ổn định |
| `jlink` runtime gồm cả code của bạn | Không | Có |

Chọn JPMS khi bạn viết **thư viện** dùng chung cho nhiều team và cần giấu phần cài đặt, hoặc phân phối một công cụ kèm runtime riêng. Với ứng dụng Spring Boot thông thường, chi phí thường lớn hơn lợi ích. Nếu ép ứng dụng chạy trên module path, bạn phải `opens` mọi package mà Spring, Jackson, Hibernate cần reflection vào. Hãy giữ classpath và dùng ranh giới ở mức build (Maven multi-module) hoặc test (Spring Modulith).

<Callout kind="ai">

Nhờ AI giải thích một thông báo `InaccessibleObjectException`, `FindException` hay "is not visible", hoặc phác thảo `module-info.java` cho một thư viện. AI hay đề xuất `--illegal-access=permit` (đã bị bỏ từ Java 17), nhầm `exports` với `opens`, và viết `requires` theo tên artifact Maven thay vì tên module thật. Kiểm tra: chạy lệnh trên đúng JDK của bạn, đọc tên module bằng `jar --describe-module --file <jar>`, và với `--add-opens` hãy ghi rõ module, package, module nhận thay vì mở rộng hết.

</Callout>

<Callout kind="link">

J3.1 dạy access modifier và package, nền của `exports`. J7 dựng Maven multi-module, cách phổ biến hơn để tách ranh giới trong ứng dụng. J9 gặp lại module `jdk.charsets` khi runtime rút gọn thiếu charset. SB11 làm image container cho Java, nơi `jlink` và `jdeps --print-module-deps` giúp giảm kích thước. J13 dùng Spring Modulith để kiểm ranh giới module bằng test.

</Callout>
