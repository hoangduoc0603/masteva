<Goal>

Viết được một lớp Java có field, constructor và method, chia các lớp vào package, và chọn mức truy cập để không đoạn code nào đưa được đối tượng vào trạng thái sai. Học xong bài này, bạn giải thích được:

- Vì sao gán `Order alias = order` rồi thêm hàng vào `alias` thì `order` cũng có thêm hàng.
- Vì sao một getter trả thẳng `List` nội bộ làm mọi kiểm tra trong method `add` trở nên vô nghĩa.
- Vì sao khối `static` của một lớp chạy giữa chừng chương trình chứ không chạy lúc khởi động, và vì sao có lúc đọc một field `static` của lớp mà khối đó vẫn chưa chạy.
- Vì sao field `final` vẫn có thể bị sửa nội dung, và vì sao sinh mã đơn hàng bằng bộ đếm `static` là lỗi trên production.

</Goal>

<Knowledge>

Ví dụ trong chặng J3 là mô hình đơn hàng của một cửa hàng cà phê online: `Product` (sản phẩm), `Order` (đơn hàng), `OrderLine` (một dòng hàng trong đơn). Tiền tính bằng đồng, kiểu `long`.

### Lớp, đối tượng và tham chiếu

Bạn gán `Order alias = order;`, thêm một túi lọc cà phê vào `alias`, rồi in `order`: túi lọc cũng nằm trong `order`. Không có dòng code nào sửa `order` trực tiếp.

**Lớp (class)** là bản mô tả gồm **field** (trạng thái) và **method** (hành vi). **Đối tượng (object)** là một thể hiện cụ thể của lớp, tạo bằng `new` và nằm trên heap. Như J2.1 đã nói về mảng, biến có kiểu là một lớp không chứa đối tượng; nó chứa **tham chiếu (reference)** trỏ tới đối tượng. Đoạn sau khai báo lớp `Order` có hai field, tạo hai đơn có cùng nội dung và một biến `alias`:

```java
class Order {
    String number;
    List<String> lines = new ArrayList<>();
}

void main() {
    Order order = new Order();
    order.number = "DH-1";
    order.lines.add("CF-01");

    Order alias = order;
    alias.lines.add("FL-01");

    Order other = new Order();
    other.number = "DH-1";
    other.lines.add("CF-01");
    other.lines.add("FL-01");

    IO.println("order.lines = " + order.lines);
    IO.println("alias == order? " + (alias == order));
    IO.println("other == order? " + (other == order));
}
```

Kết quả:

```text
order.lines = [CF-01, FL-01]
alias == order? true
other == order? false
```

Chỉ có hai lần `new Order()`, nên trên heap chỉ có hai đơn hàng. `alias` và `order` trỏ cùng một đơn, còn `other` là đơn thứ hai, dù nội dung giống hệt:

```text
 biến cục bộ trong main               heap
 order  ----------------+
                        +--->  Order { number="DH-1", lines=[CF-01, FL-01] }
 alias  ----------------+
 other  ---------------------> Order { number="DH-1", lines=[CF-01, FL-01] }
```

- `Order alias = order;` chép tham chiếu, không chép đối tượng. Sửa qua biến nào cũng là sửa cùng một đơn.
- `==` giữa hai biến tham chiếu hỏi "có phải cùng một đối tượng không", nên `other == order` là `false` dù hai đơn giống nhau. So nội dung là việc của `equals`, học ở J3.3.
- Khi không còn tham chiếu nào trỏ tới một đối tượng, **GC (garbage collector**, bộ thu gom rác) thu hồi nó vào một lúc nào đó. Bạn không tự giải phóng bộ nhớ như trong C.

Quy tắc đó áp dụng cả khi truyền đối tượng vào method. Java luôn truyền **theo giá trị** (J2.1), và giá trị của một biến kiểu lớp là tham chiếu. Method nhận được bản sao của tham chiếu, nên nó sửa được đối tượng mà bên gọi đang trỏ tới, nhưng gán tham số sang đối tượng khác thì bên gọi không hay biết:

```java
class Order {
    List<String> lines = new ArrayList<>();
}

void addFreeGift(Order order) {
    order.lines.add("GIFT-01");
}

void replace(Order order) {
    order = new Order();
    order.lines.add("XX-99");
}

void main() {
    Order order = new Order();
    order.lines.add("CF-01");
    addFreeGift(order);
    replace(order);
    IO.println(order.lines);
}
```

Kết quả:

```text
[CF-01, GIFT-01]
```

Thử tự trả lời trước khi đọc tiếp: cả hai method đều nhận đơn của `main`, vì sao chỉ quà tặng còn lại?

`addFreeGift` đi theo tham chiếu tới đúng đơn của `main` và thêm quà tặng. `replace` gán tham số `order` của riêng nó sang một đơn mới, nên `XX-99` nằm trong đơn mới đó, còn đơn của `main` không đổi.

### Constructor: đối tượng hợp lệ ngay từ đầu

Lớp `Order` ở trên có một vấn đề: ai quên gán `number` thì đơn hàng không có mã, và lỗi chỉ lộ ra ở nơi khác, khi in hoá đơn. Đoạn sau tạo một đơn và dùng ngay:

```java
class Order {
    String number;
    int lineCount;
    boolean paid;
}

void main() {
    Order order = new Order();
    IO.println(order.number + " " + order.lineCount + " " + order.paid);
    IO.println("Hoa don " + order.number.toUpperCase());
}
```

Kết quả:

```text
null 0 false
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.toUpperCase()" because "<local1>.number" is null
	at Main.main(Main.java:10)
```

`new` gán cho mọi field giá trị mặc định: `null` cho kiểu tham chiếu, `0` cho số, `false` cho `boolean`. Đối tượng tồn tại nhưng ở trạng thái vô nghĩa, và `NullPointerException` nổ ở dòng dùng mã đơn, cách xa chỗ quên gán. (`<local1>` là cách JVM gọi biến `order` khi chương trình được biên dịch không kèm tên biến cục bộ.)

**Constructor** là đoạn code chạy đúng một lần khi `new` tạo đối tượng. Nó có tên trùng tên lớp và không có kiểu trả về. Việc của nó là đưa đối tượng vào trạng thái hợp lệ ngay từ đầu: kiểm tra tham số, ném `IllegalArgumentException` nếu sai, gán mọi field. Một lớp có thể có nhiều constructor:

```java
class Product {
    String sku;
    String name;
    long price;

    Product(String sku, String name, long price) {
        if (sku == null || sku.isBlank()) {
            throw new IllegalArgumentException("sku is required");
        }
        if (price <= 0) {
            throw new IllegalArgumentException("price must be positive: " + price);
        }
        this.sku = sku;
        this.name = name;
        this.price = price;
    }

    Product(String sku, long price) {
        this(sku, sku, price);   // chưa có tên thì tạm dùng sku làm tên
    }
}

void main() {
    Product coffee = new Product("CF-01", "Ca phe hat 500g", 185_000);
    Product filter = new Product("FL-01", 65_000);
    IO.println(coffee.name + " | " + filter.name);
    new Product("TR-01", "Tra o long 200g", 0);
}
```

Kết quả:

```text
Ca phe hat 500g | FL-01
Exception in thread "main" java.lang.IllegalArgumentException: price must be positive: 0
	at Main$Product.<init>(Main.java:11)
	at Main.main(Main.java:27)
```

Sản phẩm giá 0 không bao giờ được tạo ra: exception nổ ngay trong constructor (`<init>` trong stack trace là tên JVM đặt cho constructor), tại đúng dòng tạo sai. Ba điểm trong code:

- `this.sku` là field, `sku` là tham số. Khi trùng tên, `this.` chỉ rõ bạn gán vào field; `this` là tham chiếu tới chính đối tượng đang được tạo.
- `this(sku, sku, price)` gọi constructor ba tham số của cùng lớp. Nhờ vậy mọi cách tạo `Product` đều đi qua một chỗ kiểm tra duy nhất. Tới Java 24, `this(...)` phải là câu lệnh đầu tiên; từ Java 25 (JEP 513), bạn được đặt trước nó các lệnh không đụng tới đối tượng đang tạo, ví dụ kiểm tra tham số.
- `Main$Product` trong stack trace: lớp `Product` được viết trong file dùng `void main()`, nên nó thành lớp lồng của lớp `Main` mà Java tạo ngầm cho file. Mục đóng gói bên dưới cho thấy điều này ảnh hưởng tới `private` thế nào.

Khi lớp không khai báo constructor nào, `javac` tự sinh một **constructor mặc định**: không tham số, không làm gì. `Order` ở đầu mục dùng chính constructor đó. Khai báo một constructor bất kỳ là constructor mặc định biến mất:

```java
class Product {
    String sku;
    long price;

    Product(String sku, long price) {
        this.sku = sku;
        this.price = price;
    }
}

void main() {
    Product product = new Product();
}
```

Kết quả:

```text
Main.java:12: error: constructor Product in class Main.Product cannot be applied to given types;
    Product product = new Product();
                      ^
  required: String,long
  found:    no arguments
  reason: actual and formal argument lists differ in length
1 error
error: compilation failed
```

Đây là điều bạn muốn: không ai tạo được sản phẩm thiếu mã và giá. Một số framework như JPA hay Jackson cần constructor không tham số để tạo đối tượng; khi đó bạn thêm nó, với mức truy cập hẹp nhất mà framework cho phép (mục sau).

### Đóng gói và access modifier

`Order` kiểm tra số lượng trong method `add`: số lượng phải dương. Nhưng field `lines` để ngỏ, nên một đoạn code ở nơi khác thêm thẳng vào list, không qua `add`:

```java
record OrderLine(String sku, int quantity, long unitPrice) {}

class Order {
    List<OrderLine> lines = new ArrayList<>();

    void add(String sku, int quantity, long unitPrice) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive: " + quantity);
        }
        lines.add(new OrderLine(sku, quantity, unitPrice));
    }

    long total() {
        long sum = 0;
        for (OrderLine line : lines) {
            sum += line.quantity() * line.unitPrice();
        }
        return sum;
    }
}

void main() {
    Order order = new Order();
    order.add("CF-01", 2, 185_000);
    order.lines.add(new OrderLine("CF-01", -5, 185_000));
    IO.println("total = " + order.total());
}
```

Kết quả:

```text
total = -555000
```

Đơn hàng có tổng tiền âm, và kiểm tra trong `add` không giúp gì vì không ai bắt buộc phải đi qua `add`. (`OrderLine` là record, học ở J2.3.) **Đóng gói (encapsulation)** nghĩa là giấu field, chỉ mở ra những thao tác giữ được **bất biến (invariant)** của đối tượng, tức điều kiện luôn đúng trong suốt vòng đời của nó. Với đơn hàng, bất biến là: mọi dòng có số lượng dương, nên tổng tiền không bao giờ âm.

Công cụ để giấu là **access modifier**, từ khoá đặt trước field, method, constructor hay lớp để quy định ai được dùng nó. Đánh dấu `lines` là `private` thì chỉ code bên trong lớp `Order` đụng được vào nó:

```java
import java.util.ArrayList;
import java.util.List;

public class Shop {
    public static void main(String[] args) {
        Order order = new Order();
        order.lines.add("CF-01");
    }
}

class Order {
    private List<String> lines = new ArrayList<>();
}
```

Kết quả:

```text
Shop.java:7: error: lines has private access in Order
        order.lines.add("CF-01");
             ^
1 error
error: compilation failed
```

`javac` chặn ngay lúc biên dịch, trước khi chương trình kịp chạy. Ví dụ này khai báo lớp `Shop` có `main` theo cách viết truyền thống, không dùng `void main()`, và có lý do.

File dùng `void main()` biến mọi lớp trong file thành lớp lồng, nên `private` không chặn gì giữa chúng. Khi file không khai báo lớp chứa `main`, Java tạo ngầm một lớp cho cả file, và mọi lớp bạn viết trong file thành **lớp lồng** (lớp khai báo bên trong lớp khác, J3.2) của lớp ngầm đó. Java cho mọi code nằm trong cùng một lớp cấp cao nhất dùng thành viên `private` của nhau ([JLS §6.6.1](https://docs.oracle.com/javase/specs/jls/se25/html/jls-6.html#jls-6.6.1)). `Order.class` dưới đây là đối tượng mô tả lớp `Order`, và `getName()` trả tên của lớp:

```java
class Order {
    private String secret = "noi bo";
}

void main() {
    Order order = new Order();
    IO.println(order.secret);
    IO.println(Order.class.getName());
}
```

Kết quả:

```text
noi bo
Main$Order
```

Tên `Main$Order` cho thấy `Order` nằm bên trong lớp `Main`. Cách viết `void main()` hợp cho ví dụ ngắn; để thấy access modifier có tác dụng, các lớp phải là lớp cấp cao nhất (top-level) như ví dụ `Shop`.

Java có bốn mức truy cập. Cột "lớp con" nói về kế thừa, học ở J3.2:

| Modifier | Trong cùng lớp | Cùng package | Lớp con ở package khác | Mọi nơi |
|---|---|---|---|---|
| `private` | có | không | không | không |
| không ghi gì (package-private) | có | có | không | không |
| `protected` | có | có | có, qua kế thừa | không |
| `public` | có | có | có | có |

### Package và package-private

Một đồng nghiệp ở phần khác của codebase muốn "đi tắt": tự tạo một dòng hàng số lượng âm thay vì gọi `Order.add`. `private` chỉ chặn được ngoài một lớp; ranh giới lớn hơn là package.

**Package** gom các lớp liên quan dưới một tên và là ranh giới của mức package-private. Dòng `package shop.order;` ở đầu file khai báo package; theo quy ước, file nằm trong thư mục `shop/order/`. `javac` không bắt thư mục khớp package với những file bạn truyền thẳng vào lệnh, nhưng khi tự tìm mã nguồn của một lớp chưa được truyền vào, nó tìm theo đúng đường dẫn đó; Maven và Gradle cũng dùng bố cục này làm mặc định. Tên đầy đủ của lớp là `shop.order.Order`, và lớp ở package khác dùng nó qua `import shop.order.Order;`. Ví dụ sau có ba file trong hai package:

```text
src/shop/
├── Peek.java              package shop
└── order/
    ├── Order.java         package shop.order
    └── OrderLine.java     package shop.order
```

`OrderLine` là lớp `public`, nhưng constructor của nó không ghi modifier, tức package-private. (`final` trên field nghĩa là field chỉ được gán một lần, mục cuối bài giải thích.)

```java norun
package shop.order;

public class OrderLine {
    private final String sku;
    private final int quantity;

    OrderLine(String sku, int quantity) {
        this.sku = sku;
        this.quantity = quantity;
    }

    public int quantity() {
        return quantity;
    }
}
```

`Order` cùng package nên gọi được constructor đó, sau khi đã kiểm tra số lượng:

```java norun
package shop.order;

import java.util.ArrayList;
import java.util.List;

public class Order {
    private final List<OrderLine> lines = new ArrayList<>();

    public void add(String sku, int quantity) {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive: " + quantity);
        }
        lines.add(new OrderLine(sku, quantity));
    }
}
```

`Peek` ở package `shop` thử tự tạo một dòng hàng số lượng âm:

```java norun
package shop;

import shop.order.Order;
import shop.order.OrderLine;

public class Peek {
    public static void main(String[] args) {
        Order order = new Order();
        order.add("CF-01", 2);
        OrderLine line = new OrderLine("CF-01", -5);
    }
}
```

Code nằm trong nhiều thư mục, nên lệnh `javac` dưới đây nhận mọi file `.java` do `find` liệt kê, và `-d out` đặt file `.class` vào thư mục `out` theo đúng cây package:

<Terminal where="mac">

```bash
javac -d out $(find src -name '*.java')
```

</Terminal>

Kết quả:

```text
src/shop/Peek.java:10: error: OrderLine(String,int) is not public in OrderLine; cannot be accessed from outside package
        OrderLine line = new OrderLine("CF-01", -5);
                         ^
1 error
```

Dòng `order.add("CF-01", 2)` biên dịch được, vì `add` là `public`. Dòng tạo `OrderLine` thì không: `Peek` dùng được kiểu `OrderLine` (lớp `public`) nhưng không tạo được nó. Muốn có dòng hàng, code bên ngoài `shop.order` phải đi qua `Order.add`, nơi giữ bất biến. Bỏ dòng đó đi thì `javac` biên dịch xong, và bạn chạy bằng tên đầy đủ của lớp: `java -cp out shop.Peek`.

Quy tắc chọn mức truy cập là chọn mức **hẹp nhất** còn làm được việc:

- Field gần như luôn `private`.
- Lớp, method và constructor chỉ dùng trong package thì không ghi modifier.
- `protected` mở cho cả package lẫn mọi lớp con ở bất kỳ đâu. Nó không bảo vệ nhiều như cái tên: với người kế thừa, nó là một phần API công khai, và đổi nó có thể làm hỏng lớp con mà bạn không biết. Chỉ dùng khi bạn thiết kế lớp để kế thừa (J3.2).
- `public` là lời hứa với mọi nơi khác trong codebase. Rút lại lời hứa đó tốn kém hơn nhiều so với mở thêm khi cần.

### Getter làm lộ trạng thái nội bộ

Field `lines` đã `private`, mọi thay đổi phải qua `add`. Vậy mà một màn hình ở nơi khác xoá sạch dòng hàng của đơn bằng một dòng code, không qua method nào của `Order`.

Đoạn sau trả thẳng list nội bộ qua getter `getLines()`:

```java
class Order {
    private List<String> lines = new ArrayList<>();

    void add(String sku) {
        lines.add(sku);
    }

    List<String> getLines() {
        return lines;
    }
}

void main() {
    Order order = new Order();
    order.add("CF-01");
    order.add("FL-01");
    order.getLines().clear();
    IO.println("lines = " + order.getLines());
}
```

Kết quả:

```text
lines = []
```

Bên gọi xoá sạch đơn hàng mà không qua method nào của `Order`. Getter trả về chính list nội bộ, nên ai cầm list đó cũng sửa được nó, và `private` trên field không còn tác dụng. Sửa bằng cách trả về một bản sao không sửa được: `List.copyOf` (từ Java 10) tạo list mới chứa cùng phần tử, và mọi thao tác thêm, xoá trên list đó ném exception.

```java
class Order {
    private List<String> lines = new ArrayList<>();

    void add(String sku) {
        lines.add(sku);
    }

    List<String> getLines() {
        return List.copyOf(lines);
    }
}

void main() {
    Order order = new Order();
    order.add("CF-01");
    order.getLines().clear();
}
```

Kết quả:

```text
Exception in thread "main" java.lang.UnsupportedOperationException
	at java.base/java.util.ImmutableCollections.uoe(ImmutableCollections.java:159)
	at java.base/java.util.ImmutableCollections$AbstractImmutableCollection.clear(ImmutableCollections.java:166)
	at Main.main(Main.java:16)
```

Lần này `clear()` ném `UnsupportedOperationException` ngay tại dòng gọi nó, thay vì lặng lẽ xoá hàng. Số dòng trong `ImmutableCollections.java` có thể khác giữa các bản JDK. Mọi getter trả `List`, `Map` hay mảng đều phải trả bản sao (mảng thì dùng `clone()`); J5.3 so sánh `List.copyOf` với các cách khác.

Cũng vì đóng gói, đừng sinh getter và setter cho mọi field. Getter cho mọi field lộ cấu trúc bên trong; setter cho mọi field cho phép đặt đối tượng vào trạng thái sai từ bất kỳ đâu. Thay cho `setPrice(long)`, viết `changePrice(long newPrice)` kiểm tra khoảng giá trước khi gán: đặt tên method theo việc nghiệp vụ và để nó giữ bất biến.

### static: thuộc về lớp, không thuộc từng đối tượng

Mỗi đơn hàng cần một mã riêng: `DH-1`, `DH-2`, và cứ thế. Bộ đếm sinh mã không thể là field của từng đơn, vì mỗi đơn có một bản riêng và bản nào cũng bắt đầu từ 1. Nó phải là thứ mọi đơn dùng chung.

Field hay method khai báo **`static`** thuộc về lớp, không thuộc từng đối tượng: cả chương trình chỉ có một bản. Đoạn sau dùng field `static nextNumber` để sinh mã đơn:

```java
class Order {
    static int nextNumber = 1;

    String number;

    Order() {
        number = "DH-" + nextNumber++;
    }
}

void main() {
    Order first = new Order();
    Order second = new Order();
    IO.println(first.number + " " + second.number + " next=" + Order.nextNumber);
}
```

Kết quả:

```text
DH-1 DH-2 next=3
```

Hai đơn có hai mã khác nhau vì cùng tăng một bộ đếm. Bạn đọc nó qua tên lớp, `Order.nextNumber`, không qua một đơn cụ thể. Bảng dưới so hai loại thành viên:

| | Thành viên thường (instance) | Thành viên `static` |
|---|---|---|
| Thuộc về | Từng đối tượng | Lớp, một bản duy nhất |
| Gọi bằng | `order.total()` | `Order.nextNumber`, `Math.max(a, b)` |
| Có `this` không | Có | Không |
| Dùng cho | Trạng thái và hành vi của đối tượng | Hằng số, hàm tiện ích, factory method (method tạo đối tượng thay cho `new`, như `List.of`) |

Method `static` không có `this`, nên không đọc được field của đối tượng nào, vì nó không biết đối tượng nào:

```java
class Order {
    long subtotal = 435_000;

    static long totalWithShipping() {
        return subtotal + 20_000;
    }
}

void main() {
    IO.println(Order.totalWithShipping());
}
```

Kết quả:

```text
Main.java:5: error: non-static variable subtotal cannot be referenced from a static context
        return subtotal + 20_000;
               ^
1 error
error: compilation failed
```

**Hằng số** khai báo `static final`, đặt tên chữ hoa có gạch dưới: `static final int MAX_LINES = 20;`. Mục `final` ở dưới giải thích phần `final`.

Lớp có thể có **khối khởi tạo static** `static { ... }` để chuẩn bị field `static` cần nhiều bước, như nạp một bảng phí giao hàng. Khối này chạy đúng một lần, khi lớp được **khởi tạo**. Câu hỏi là lúc nào. Đoạn sau có lớp `ShippingFees` với một hằng số, một bảng phí theo thành phố nạp trong khối `static`, và một dòng in để bạn thấy lúc khối đó chạy. `Map` là bảng tra từ khoá sang giá trị, J5 học kỹ.

```java
class ShippingFees {
    static final long DEFAULT_FEE = 35_000;
    static final Map<String, Long> FEE_BY_CITY = new HashMap<>();

    static {
        FEE_BY_CITY.put("HN", 20_000L);
        FEE_BY_CITY.put("HCM", 20_000L);
        IO.println("[ShippingFees] loaded " + FEE_BY_CITY.size() + " cities");
    }

    static long feeFor(String city) {
        return FEE_BY_CITY.getOrDefault(city, DEFAULT_FEE);
    }
}

void main() {
    IO.println("start");
    IO.println("default fee = " + ShippingFees.DEFAULT_FEE);
    IO.println("HN fee = " + ShippingFees.feeFor("HN"));
    IO.println("Da Nang fee = " + ShippingFees.feeFor("Da Nang"));
}
```

<Predict question="Dòng [ShippingFees] loaded in ra ở vị trí nào: đầu tiên, trước dòng default fee, hay ở chỗ khác? Nó in mấy lần?">

```text
start
default fee = 35000
[ShippingFees] loaded 2 cities
HN fee = 20000
Da Nang fee = 35000
```

Khối `static` chạy sau `start` và sau cả dòng `default fee`, ngay trước lần gọi `feeFor` đầu tiên, và chỉ chạy một lần.

</Predict>

JVM khởi tạo lớp **lười** (lazy): ở lần đầu code thật sự cần lớp, như gọi method `static`, `new`, hay đọc một field `static`, chứ không phải lúc chương trình bắt đầu. Đọc `DEFAULT_FEE` lại không tính, vì nó là **hằng số lúc biên dịch** (compile-time constant): field `static final` kiểu nguyên thuỷ hoặc `String`, khởi tạo bằng một biểu thức hằng. `javac` chép thẳng giá trị `35000` vào nơi dùng, nên dòng đó không chạm tới lớp `ShippingFees`. `FEE_BY_CITY` cũng là `static final` nhưng không phải hằng số lúc biên dịch, vì giá trị của nó tạo bằng `new` lúc chạy.

Việc chép giá trị hằng có một hệ quả khi làm thư viện. Đổi giá trị của một hằng số lúc biên dịch trong thư viện mà không biên dịch lại code dùng nó, thì code đó vẫn giữ giá trị cũ ([JLS §13.4.9](https://docs.oracle.com/javase/specs/jls/se25/html/jls-13.html#jls-13.4.9)). Thứ có thể đổi giữa các phiên bản thì đừng khai báo thành hằng số công khai.

Field `static` không `final`, như `nextNumber`, là **trạng thái toàn cục**: mọi đối tượng và mọi đoạn code trong cùng JVM dùng chung nó, nhưng chỉ trong JVM đó. Trong test, test trước để lại giá trị cho test sau, nên kết quả phụ thuộc thứ tự chạy.

Cũng vì chỉ sống trong một JVM, bộ đếm `static` như `nextNumber` không sinh được mã đơn hàng duy nhất. Mỗi tiến trình JVM chạy service có bộ đếm riêng, nên hai tiến trình chạy song song cùng sinh `DH-1`, `DH-2`. Mỗi lần khởi động lại, bộ đếm quay về 1 và trùng với mã đã lưu trong database. Thêm vào đó, `nextNumber++` không an toàn khi nhiều thread cùng gọi. Mã định danh phải đến từ một nguồn chung, như sequence của database (bộ đếm do database giữ, SB3) hoặc UUID (chuỗi ngẫu nhiên gần như không thể trùng).

<Callout kind="production">

Một service sinh mã đơn bằng `"DH-" + nextNumber++` với `nextNumber` là field `static`, như ví dụ trên. Chạy một instance (một tiến trình JVM của service) thì ổn, và test trên máy cũng không lộ ra gì. Ngày đội vận hành tăng lên hai instance đứng sau load balancer (bộ chia request), đơn mới của hai instance bắt đầu trùng mã nhau; sau lần deploy kế tiếp, mã mới còn trùng cả với đơn cũ trong database.

</Callout>

Viết method `static` khi method không cần trạng thái của đối tượng: hàm tiện ích như `Math.max`, factory method như `List.of`, hàm tra cứu như `ShippingFees.feeFor`. Tránh `static` cho thứ cần thay thế khi test, như đồng hồ, kết nối database hay bộ sinh mã: code gọi thẳng method `static` `LocalDateTime.now()` thì test không chen được một đồng hồ giả vào. J3.2 giải quyết chuyện này bằng interface.

### final: gán một lần, không khoá đối tượng

Field `lines` của `Order` khai báo `private final List<String> lines`. Có người đọc chữ `final` và nghĩ đơn hàng không bị đổi dòng hàng được nữa. Đoạn sau thêm rồi xoá dòng trên chính field đó:

```java
class Order {
    final String number;
    final List<String> lines = new ArrayList<>();

    Order(String number) {
        this.number = number;
    }
}

void main() {
    Order order = new Order("DH-1");
    order.lines.add("CF-01");
    order.lines.clear();
    IO.println(order.number + " lines=" + order.lines);
}
```

Kết quả:

```text
DH-1 lines=[]
```

Không có lỗi nào. **`final`** ở biến hay field nghĩa là biến chỉ được gán đúng một lần. Nó khoá **tham chiếu**, không khoá **đối tượng**: `lines` luôn trỏ tới cùng một list, nhưng list đó vẫn thêm, xoá được. Thứ `final` cấm là gán lại tham chiếu:

```java
class Order {
    final List<String> lines = new ArrayList<>();
}

void main() {
    Order order = new Order();
    order.lines = new ArrayList<>();
}
```

Kết quả:

```text
Main.java:7: error: cannot assign a value to final variable lines
    order.lines = new ArrayList<>();
         ^
1 error
error: compilation failed
```

`final` còn cấm gán thiếu. Field `final` phải được gán xong khi constructor kết thúc, và `javac` kiểm tra điều đó ở mọi constructor. Constructor dưới đây quên gán `number`:

```java
class Order {
    final String number;

    Order() {
    }
}

void main() {
    new Order();
}
```

Kết quả:

```text
Main.java:5: error: variable number might not have been initialized
    }
    ^
1 error
error: compilation failed
```

Lỗi nằm ở dấu `}` đóng constructor, chỗ constructor kết thúc mà `number` vẫn chưa có giá trị. Vì vậy `final` cho field là mặc định tốt: `javac` bảo đảm field được gán đúng một lần, ngay trong constructor, nên không còn đối tượng nào nằm ở giá trị mặc định `null` như ví dụ ở mục Constructor.

`final` còn đặt được ở hai chỗ khác, cả hai liên quan tới kế thừa ở J3.2:

| `final` đặt ở | Nghĩa là |
|---|---|
| Biến cục bộ, tham số, field | Chỉ được gán đúng một lần |
| Method | Lớp con không được override method này |
| Lớp | Không lớp nào được kế thừa, ví dụ `String` |

Muốn đối tượng thật sự không đổi được, `final` chưa đủ; J3.3 dạy cách làm đối tượng bất biến.

Đọc lại từng `public` và hỏi "ai ngoài lớp này cần nó?"; tìm mọi getter trả `List`, `Map` hay mảng và kiểm tra chúng có trả bản sao không; tìm mọi field `static` không `final` và hỏi nó có cần dùng chung cho cả JVM không.

<Callout kind="link">
