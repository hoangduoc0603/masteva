### == và equals: entity và value object

Bạn đọc danh mục sản phẩm từ database hai lần và bỏ cả hai kết quả vào một `HashSet`. Set có hai "cà phê CF-01", và `contains` một sản phẩm `CF-01` vừa đọc lên trả `false`.

`==` giữa hai tham chiếu hỏi "có phải cùng một đối tượng không" (J3.1). **`equals`** hỏi "có cùng giá trị không", và lớp của bạn quyết định giá trị nghĩa là gì. Mọi lớp kế thừa `equals` từ `Object` (J3.2), và bản đó chỉ làm đúng việc của `==`. Đoạn sau tạo hai đối tượng cùng mã `CF-01`. `HashSet` là tập không chứa phần tử trùng, học kỹ ở J5.1:

```java
class Product {
    final String sku;
    final String name;

    Product(String sku, String name) {
        this.sku = sku;
        this.name = name;
    }
}

void main() {
    Product a = new Product("CF-01", "Ca phe hat 500g");
    Product b = new Product("CF-01", "Ca phe hat 500g");
    IO.println("a == b: " + (a == b));
    IO.println("a.equals(b): " + a.equals(b));

    Set<Product> catalog = new HashSet<>();
    catalog.add(a);
    IO.println("catalog.contains(b): " + catalog.contains(b));
}
```

Kết quả:

```text
a == b: false
a.equals(b): false
catalog.contains(b): false
```

Không override gì, `equals` chính là `==`, nên hai bản ghi cùng mã là hai sản phẩm khác nhau. Với một cửa hàng, điều đó sai. Trước khi viết `equals`, bạn cần quyết định lớp của mình thuộc loại nào:

| | Entity | Value object |
|---|---|---|
| Bằng nhau khi | Cùng định danh, dù các field khác đổi | Mọi field bằng nhau |
| Ví dụ | `Product`: cùng `sku` là cùng sản phẩm, kể cả sau khi đổi giá | `OrderLine`, `Payment.Card`, số tiền |
| Thường viết bằng | Lớp, `equals` theo định danh | Record |

**Entity** là đối tượng có định danh và trạng thái đổi theo thời gian: sản phẩm đổi giá vẫn là sản phẩm đó. **Value object** là đối tượng chỉ được định nghĩa bằng giá trị của nó: hai dòng hàng "2 túi CF-01 giá 185.000" là như nhau, không cần phân biệt cái nào.

### Hợp đồng của equals và hashCode

Bạn override `equals` cho `Product`, so cả mã và tên. Giờ `a.equals(b)` là `true`, nhưng `catalog.contains(b)` vẫn là `false`.

[Javadoc của `Object`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Object.html#equals(java.lang.Object)) đặt ra hợp đồng mà mọi collection dựa vào:

- `equals` phải **phản xạ** (`x.equals(x)`), **đối xứng** (`x.equals(y)` thì `y.equals(x)`), **bắc cầu** (`x` bằng `y`, `y` bằng `z` thì `x` bằng `z`), **nhất quán** (gọi nhiều lần cho cùng kết quả nếu không ai sửa đối tượng), và `x.equals(null)` là `false`.
- Hai đối tượng `equals` nhau thì **bắt buộc** có cùng **`hashCode`**, con số `int` đại diện cho đối tượng. Chiều ngược lại không bắt buộc: hai đối tượng khác nhau có thể trùng `hashCode`, gọi là va chạm (collision).

Đoạn sau override `equals` mà không override `hashCode`:

```java
class Product {
    final String sku;
    final String name;

    Product(String sku, String name) {
        this.sku = sku;
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) {
            return true;
        }
        if (!(o instanceof Product other)) {
            return false;
        }
        return sku.equals(other.sku) && name.equals(other.name);
    }
}

void main() {
    Product a = new Product("CF-01", "Ca phe hat 500g");
    Product b = new Product("CF-01", "Ca phe hat 500g");
    IO.println("a.equals(b): " + a.equals(b));

    Set<Product> catalog = new HashSet<>();
    catalog.add(a);
    IO.println("catalog.contains(b): " + catalog.contains(b));
}
```

<Predict question="a.equals(b) giờ là true. catalog.contains(b) là gì?">

```text
a.equals(b): true
catalog.contains(b): false
```

`contains` vẫn trả `false`, và `equals` của `Product` không hề được gọi.

</Predict>

`equals` nhận `Object` vì phải so được với bất kỳ đối tượng nào. `o instanceof Product other` là pattern matching của J2.3: nếu `o` là `Product` thì gán nó vào biến `other`. Phần đáng chú ý là cách `HashSet` tìm phần tử. Nó không duyệt mọi phần tử; nó dùng `hashCode` để chọn một **ngăn** (bucket), rồi chỉ gọi `equals` với các phần tử trong ngăn đó:

```text
 catalog.contains(b)
    1. h = b.hashCode()          -> tính ngăn từ h
    2. trong ngăn đó, với mỗi phần tử e:
          e.hashCode() == h  &&  (e == b || e.equals(b))   -> tìm thấy

 ngăn 3: [a]          a.hashCode() = 9341207
 ngăn 7: []           b.hashCode() = 1882355   ◄ tìm ở ngăn 7, không bao giờ so với a
                      (số và ngăn chỉ để minh hoạ)
```

`hashCode` kế thừa từ `Object` thường khác nhau cho mỗi đối tượng, nên `a` và `b` gần như chắc chắn rơi vào hai ngăn khác nhau, và `equals` không bao giờ được gọi. Hợp đồng đã bị vi phạm: `a.equals(b)` mà `hashCode` khác nhau. `HashMap` dùng cùng cơ chế với khoá của nó. Override `equals` thì phải override `hashCode`, tính từ đúng các field mà `equals` so:

```java
class Product {
    final String sku;
    final String name;

    Product(String sku, String name) {
        this.sku = sku;
        this.name = name;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) {
            return true;
        }
        if (!(o instanceof Product other)) {
            return false;
        }
        return sku.equals(other.sku) && name.equals(other.name);
    }

    @Override
    public int hashCode() {
        return Objects.hash(sku, name);
    }
}

void main() {
    Product a = new Product("CF-01", "Ca phe hat 500g");
    Product b = new Product("CF-01", "Ca phe hat 500g");
    Set<Product> catalog = new HashSet<>();
    catalog.add(a);
    IO.println("catalog.contains(b): " + catalog.contains(b));
}
```

Kết quả:

```text
catalog.contains(b): true
```

`Objects.hash(a, b, c)` tính `hashCode` từ nhiều giá trị, và `Objects.equals(x, y)` so hai giá trị có thể là `null` mà không ném `NullPointerException`; cả hai nằm trong lớp tiện ích `java.util.Objects`.

### hashCode không được dựa trên field thay đổi được

Kho lưu số tồn theo sản phẩm trong một `HashMap<Product, Integer>` (bảng tra từ khoá sang giá trị, J5.1). Sau khi đổi giá cà phê, `stock.get(coffee)` trả `null`, dù không ai xoá gì khỏi map.

Đoạn sau dùng cách IDE hay sinh: `equals` và `hashCode` theo mọi field, kể cả `price` là field đổi được. Dòng in cuối lấy khoá duy nhất của map (`keySet()` là tập các khoá, `iterator().next()` lấy phần tử đầu tiên của tập) để chứng tỏ `coffee` vẫn nằm trong map:

```java
class Product {
    final String sku;
    long price;

    Product(String sku, long price) {
        this.sku = sku;
        this.price = price;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Product other && sku.equals(other.sku) && price == other.price;
    }

    @Override
    public int hashCode() {
        return Objects.hash(sku, price);
    }
}

void main() {
    Product coffee = new Product("CF-01", 185_000);
    Map<Product, Integer> stock = new HashMap<>();
    stock.put(coffee, 40);

    coffee.price = 199_000;
    IO.println("get: " + stock.get(coffee));
    IO.println("size: " + stock.size());
    IO.println("keys: " + stock.keySet().iterator().next().sku);
}
```

<Predict question="coffee vẫn là cùng một đối tượng, vẫn nằm trong map. stock.get(coffee) trả gì?">

```text
get: null
size: 1
keys: CF-01
```

Map vẫn có một khoá, đúng là `coffee`, nhưng `get` không tìm thấy nó.

</Predict>

Map đặt `coffee` vào ngăn tính từ `hashCode` lúc `put`, khi giá là 185.000. Đổi giá làm `hashCode` đổi, nên `get` tìm ở một ngăn mới, nơi không có gì. Số tồn kho 40 vẫn chiếm bộ nhớ nhưng không lấy ra được bằng `get` nữa. [Javadoc của `Map`](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/Map.html) cảnh báo đúng điều này: hành vi của map không được quy định nếu một khoá đang nằm trong map bị đổi theo cách làm thay đổi kết quả `equals`.

`Product` là entity: cùng `sku` là cùng sản phẩm, dù giá đổi. Vậy `equals` và `hashCode` chỉ dùng `sku`, một field `final` không bao giờ đổi:

```java
class Product {
    final String sku;
    long price;

    Product(String sku, long price) {
        this.sku = sku;
        this.price = price;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) {
            return true;
        }
        if (!(o instanceof Product other)) {
            return false;
        }
        return sku.equals(other.sku);
    }

    @Override
    public int hashCode() {
        return sku.hashCode();
    }
}

void main() {
    Product coffee = new Product("CF-01", 185_000);
    Map<Product, Integer> stock = new HashMap<>();
    stock.put(coffee, 40);

    coffee.price = 199_000;
    IO.println("get: " + stock.get(coffee));
    IO.println("get ban ghi khac cung sku: " + stock.get(new Product("CF-01", 199_000)));
}
```

Kết quả:

```text
get: 40
get ban ghi khac cung sku: 40
```

Đây là mẫu viết `equals` cho entity: so `this == o` trước cho nhanh, kiểm tra kiểu bằng `instanceof`, rồi so đúng các field định danh. `hashCode` dùng cùng các field đó, không thêm, không bớt.

Entity lưu trong database thì định danh nên là một mã nghiệp vụ không đổi như `sku`, nếu có. Khoá chính do database sinh thường chưa có trước khi lưu: một đối tượng mới có `id` là `null`, được lưu, rồi có `id`. Nếu `hashCode` tính từ `id`, đối tượng đó "đổi" `hashCode` sau khi lưu và biến mất khỏi `HashSet` đang chứa nó, cùng cơ chế với ví dụ đổi giá ở trên. SB3 bàn chi tiết cách viết `equals` cho entity JPA.

### Lớp con và tính đối xứng: instanceof hay getClass()

J3.2 có `DigitalProduct extends Product`. Ebook có thêm `downloadUrl`, và ai đó override `equals` ở lớp con để so thêm field này. Từ lúc đó, kết quả của `equals` phụ thuộc vào việc bạn gọi nó trên đối tượng nào:

```java
class Product {
    final String sku;

    Product(String sku) {
        this.sku = sku;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof Product other && sku.equals(other.sku);
    }

    @Override
    public int hashCode() {
        return sku.hashCode();
    }
}

class DigitalProduct extends Product {
    final String downloadUrl;

    DigitalProduct(String sku, String downloadUrl) {
        super(sku);
        this.downloadUrl = downloadUrl;
    }

    @Override
    public boolean equals(Object o) {
        return o instanceof DigitalProduct other && sku.equals(other.sku)
                && downloadUrl.equals(other.downloadUrl);
    }
}

void main() {
    Product product = new Product("EB-01");
    Product ebook = new DigitalProduct("EB-01", "https://example.com/eb-01");
    IO.println("product.equals(ebook): " + product.equals(ebook));
    IO.println("ebook.equals(product): " + ebook.equals(product));
    IO.println("set chua product, contains(ebook): " + new HashSet<>(List.of(product)).contains(ebook));
}
```

Kết quả:

```text
product.equals(ebook): true
ebook.equals(product): false
set chua product, contains(ebook): false
```

Thử tự trả lời trước khi đọc tiếp: cùng hai đối tượng, vì sao hai chiều cho hai kết quả khác nhau?

`equals` của `Product` dùng `instanceof Product`, và một ebook cũng là `Product`, nên `product.equals(ebook)` là `true`. `equals` của `DigitalProduct` đòi đối số là `DigitalProduct`, mà `product` thì không, nên chiều ngược lại là `false`. Tính đối xứng bị phá, và collection không hứa sẽ gọi `x.equals(y)` hay `y.equals(x)`. `HashSet` hiện gọi `equals` trên đối số, tức `ebook.equals(product)`, nên dòng cuối là `false` dù `product.equals(ebook)` là `true`; một collection khác, hay một phiên bản JDK khác, có thể cho kết quả ngược lại.

Có hai cách giữ hợp đồng:

- Dùng `instanceof` ở lớp cha và khai báo `equals`, `hashCode` là `final`, để lớp con không thêm field vào phép so. Ebook và sản phẩm thường cùng `sku` thì bằng nhau; vì `sku` là duy nhất trong cửa hàng, điều đó hợp lý.
- Dùng `getClass() != o.getClass()`, để chỉ đối tượng cùng đúng một lớp mới có thể bằng nhau.

Đoạn sau dùng cách thứ hai ở lớp cha. `getClass()` trả lớp thật của đối tượng lúc chạy:

```java
class Product {
    final String sku;

    Product(String sku) {
        this.sku = sku;
    }

    @Override
    public boolean equals(Object o) {
        if (o == null || getClass() != o.getClass()) {
            return false;
        }
        return sku.equals(((Product) o).sku);
    }

    @Override
    public int hashCode() {
        return sku.hashCode();
    }
}

class DigitalProduct extends Product {
    DigitalProduct(String sku) {
        super(sku);
    }
}

void main() {
    Product product = new Product("EB-01");
    Product ebook = new DigitalProduct("EB-01");
    IO.println("product.equals(ebook): " + product.equals(ebook));
    IO.println("ebook.equals(product): " + ebook.equals(product));
    IO.println("ebook.equals(new DigitalProduct): " + ebook.equals(new DigitalProduct("EB-01")));
}
```

Kết quả:

```text
product.equals(ebook): false
ebook.equals(product): false
ebook.equals(new DigitalProduct): true
```

Hai chiều giờ cho cùng kết quả. Cái giá là một `DigitalProduct` không bao giờ bằng một `Product`, kể cả khi lớp con không thêm field nào. Record và lớp `final` không gặp vấn đề này vì không có lớp con.

### equals(Product) là overload, không phải override

Nhiều người viết `public boolean equals(Product other)` vì thấy nó gọn hơn: khỏi kiểm tra kiểu, khỏi ép kiểu. Gọi `a.equals(b)` trực tiếp thì đúng, nhưng collection không bao giờ gọi method này:

```java
class Product {
    final String sku;

    Product(String sku) {
        this.sku = sku;
    }

    public boolean equals(Product other) {
        return sku.equals(other.sku);
    }

    @Override
    public int hashCode() {
        return sku.hashCode();
    }
}

void main() {
    Product a = new Product("CF-01");
    Product b = new Product("CF-01");
    IO.println("a.equals(b): " + a.equals(b));

    Set<Product> catalog = new HashSet<>(List.of(a));
    IO.println("catalog.contains(b): " + catalog.contains(b));
}
```

Kết quả:

```text
a.equals(b): true
catalog.contains(b): false
```

`equals(Product)` có tham số khác `equals(Object)`, nên nó là một overload mới, không phải override (J3.2). `HashSet` được viết cho mọi kiểu phần tử nên gọi `equals(Object)`, và bản đó vẫn là của `Object`. `hashCode` đã đúng, nên `b` rơi đúng ngăn của `a`, nhưng phép so trong ngăn dùng `equals(Object)` và trả `false`. Gắn `@Override` lên `equals(Product)` thì `javac` báo `method does not override or implement a method from a supertype` ngay lúc biên dịch. Luôn viết `equals(Object o)` kèm `@Override`.

### toString cho log và cho dữ liệu nhạy cảm

Một dòng log ghi "không tìm thấy sản phẩm" kèm đối tượng sản phẩm, và bạn đọc được `Product@51931956`. Dòng đó không cho bạn biết sản phẩm nào.

**`toString`** trả một chuỗi mô tả đối tượng; Java gọi nó mỗi khi bạn nối đối tượng vào chuỗi hay in nó ra. Bản kế thừa từ `Object` in tên lớp, `@` và `hashCode` dạng hex. Record thì tự sinh `toString` liệt kê mọi thành phần:

```java
class Product {
    final String sku;

    Product(String sku) {
        this.sku = sku;
    }
}

record OrderLine(String sku, int quantity, long unitPrice) {}

void main() {
    IO.println(new Product("CF-01"));
    IO.println(new OrderLine("CF-01", 2, 185_000));
}
```

Kết quả sẽ giống thế này; phần sau `@` trên máy bạn sẽ khác, và có thể đổi sau mỗi lần chạy:

```text varies
Main$Product@51931956
OrderLine[sku=CF-01, quantity=2, unitPrice=185000]
```

Viết `toString` cho những lớp hay xuất hiện trong log và thông báo lỗi. Đừng viết code đọc lại chuỗi đó: `toString` dành cho người đọc, định dạng của nó không phải hợp đồng.

`toString` tự sinh của record in **mọi** thành phần, kể cả thứ không được phép nằm trong log. Với dữ liệu nhạy cảm, override `toString` để che đi:

```java
record PaymentRequest(String orderNumber, String cardNumber, String cvv) {
    @Override
    public String toString() {
        return "PaymentRequest[orderNumber=" + orderNumber
                + ", card=****" + cardNumber.substring(cardNumber.length() - 4) + "]";
    }
}

void main() {
    IO.println("charging " + new PaymentRequest("DH-1", "4242424242424242", "123"));
}
```

Kết quả:

```text
charging PaymentRequest[orderNumber=DH-1, card=****4242]
```

<Callout kind="production">

Một service ghi log bằng `log.info("charging {}", request)`, với `request` là record `PaymentRequest(String orderNumber, String cardNumber, String cvv)` không override `toString`. `{}` được thay bằng `toString` của `request`, nên số thẻ và CVV nằm nguyên trong log, rồi chảy sang hệ thống gom log mà cả công ty đọc được. Đây là vi phạm chuẩn bảo mật thẻ thanh toán, và log đã gom thì khó xoá sạch. Với mật khẩu, token, số thẻ, số căn cước: override `toString` để che, và rà lại mọi chỗ log đối tượng.

</Callout>

### Đối tượng bất biến

Khi khách bấm thanh toán, hệ thống chốt một ảnh chụp (snapshot) của đơn: số đơn, các dòng hàng, tổng tiền. Biên nhận là record với các field `final`. Sau đó đơn hàng thêm một dòng, và biên nhận đã chốt cũng có thêm dòng đó.

Đối tượng **bất biến (immutable)** không đổi trạng thái sau khi tạo. `String`, `Integer`, `LocalDate` đều bất biến. Lợi ích:

- Chia sẻ giữa nhiều thread mà không cần khoá (lock, cơ chế cho từng thread lần lượt đụng vào dữ liệu; J11).
- Làm khoá của `HashMap` an toàn, vì `hashCode` không đổi; mục trước cho thấy điều gì xảy ra khi khoá đổi.
- Dễ suy luận: đã kiểm tra hợp lệ trong constructor thì hợp lệ mãi.

Record (J2.3) có field `private final` và không có setter, nên trông như đã bất biến. Đoạn sau chốt biên nhận khi đơn có một dòng, rồi thêm dòng thứ hai vào đơn:

```java
record OrderLine(String sku, int quantity, long unitPrice) {}

record OrderSnapshot(String number, List<OrderLine> lines, long total) {}

void main() {
    List<OrderLine> lines = new ArrayList<>();
    lines.add(new OrderLine("CF-01", 2, 185_000));
    OrderSnapshot confirmed = new OrderSnapshot("DH-1", lines, 390_000);

    lines.add(new OrderLine("FL-01", 1, 65_000));
    IO.println("confirmed lines=" + confirmed.lines().size() + " total=" + confirmed.total());

    confirmed.lines().clear();
    IO.println("order lines=" + lines.size());
}
```

<Predict question="Biên nhận được chốt khi đơn có 1 dòng. Sau khi đơn thêm dòng thứ hai, biên nhận báo bao nhiêu dòng? clear() trên biên nhận làm gì với đơn?">

```text
confirmed lines=2 total=390000
order lines=0
```

Biên nhận báo 2 dòng nhưng tổng tiền vẫn của 1 dòng: nó tự mâu thuẫn. `clear()` trên biên nhận xoá luôn các dòng của đơn.

</Predict>

Record không chép gì: field `lines` của `confirmed` và biến `lines` của bên gọi là cùng một list. `final` chỉ khoá tham chiếu tới list (J3.1), nên record chỉ bất biến **nông** (shallow): không gán lại được field, nhưng đối tượng mà field trỏ tới vẫn sửa được. Bảng dưới là các quy tắc để một lớp thật sự bất biến:

| Quy tắc | Vì sao |
|---|---|
| Mọi field `private final` | Không ai gán lại được |
| Không có method sửa trạng thái; cần "đổi" thì trả đối tượng mới | Như `String.toUpperCase()` trả chuỗi mới |
| Lớp `final`, hoặc dùng record | Lớp con không thêm được trạng thái thay đổi được |
| **Sao chép phòng thủ (defensive copy)** collection, mảng nhận vào và trả ra | Không ai khác còn giữ tham chiếu tới dữ liệu bên trong |

Với record, chỗ sao chép phòng thủ là **compact constructor** (J2.3), chạy trước khi field được gán:

```java
record OrderLine(String sku, int quantity, long unitPrice) {}

record OrderSnapshot(String number, List<OrderLine> lines, long total) {
    OrderSnapshot {
        lines = List.copyOf(lines);
    }
}

void main() {
    List<OrderLine> lines = new ArrayList<>();
    lines.add(new OrderLine("CF-01", 2, 185_000));
    OrderSnapshot confirmed = new OrderSnapshot("DH-1", lines, 390_000);

    lines.add(new OrderLine("FL-01", 1, 65_000));
    IO.println("confirmed lines=" + confirmed.lines().size() + " total=" + confirmed.total());

    confirmed.lines().clear();
}
```

Kết quả:

```text
confirmed lines=1 total=390000
Exception in thread "main" java.lang.UnsupportedOperationException
	at java.base/java.util.ImmutableCollections.uoe(ImmutableCollections.java:159)
	at java.base/java.util.ImmutableCollections$AbstractImmutableCollection.clear(ImmutableCollections.java:166)
	at Main.main(Main.java:17)
```

Khác biệt quyết định giữa hai chương trình là compact constructor. `List.copyOf` vừa tách biên nhận khỏi list của bên gọi, vừa làm `confirmed.lines()` không sửa được. Sửa ở record, không phải ở nơi tạo biên nhận: mọi nơi tạo `OrderSnapshot`, kể cả code viết sau này, đều được bảo vệ. Bất biến còn phụ thuộc vào phần tử: list không sửa được của `OrderLine` là bất biến vì `OrderLine` là record chỉ có field bất biến. J5.3 so `List.copyOf` với `Collections.unmodifiableList` và các cách khác.

Mảng không có bản "không sửa được", và `equals` của mảng là `equals` của `Object`. Record có thành phần là mảng vì vậy so tham chiếu, không so nội dung:

```java
record Bundle(String name, String[] skus) {}

void main() {
    Bundle a = new Bundle("Combo sang", new String[] {"CF-01", "FL-01"});
    Bundle b = new Bundle("Combo sang", new String[] {"CF-01", "FL-01"});
    IO.println("a.equals(b): " + a.equals(b));

    a.skus()[0] = "TR-01";
    IO.println("a.skus()[0]: " + a.skus()[0]);
}
```

Kết quả:

```text
a.equals(b): false
a.skus()[0]: TR-01
```

Hai combo giống hệt nhau không bằng nhau, và bên ngoài sửa được nội dung của combo qua accessor. Dùng `List` thay cho mảng trong record. Buộc phải dùng mảng thì override `equals`, `hashCode` bằng `Arrays.equals`, `Arrays.hashCode`, và chép mảng bằng `clone()` cả khi nhận vào lẫn khi trả ra.

Record còn một giới hạn khi bạn muốn kiểm soát ai được tạo đối tượng. J3.1 giữ constructor của `OrderLine` là package-private để chỉ `Order.add` tạo được dòng hàng. Constructor ghi đủ mọi thành phần của record (canonical constructor) không được hẹp hơn chính record:

```java
record OrderLine(String sku, int quantity, long unitPrice) {
    private OrderLine {
        if (quantity <= 0) {
            throw new IllegalArgumentException("quantity must be positive: " + quantity);
        }
    }
}

void main() {
    IO.println(new OrderLine("CF-01", 2, 185_000));
}
```

Kết quả:

```text
Main.java:2: error: invalid canonical constructor in record OrderLine
    private OrderLine {
            ^
  (attempting to assign stronger access privileges; was package)
1 error
error: compilation failed
```

Compact constructor là một dạng canonical constructor, và `was package` cho biết record đang ở mức package-private nên constructor của nó không được là `private`. Hệ quả: ai thấy được record là tạo được nó, với bất kỳ giá trị nào qua được kiểm tra trong compact constructor. Vì vậy hãy đặt mọi bất biến của dòng hàng vào compact constructor; cần chặn hẳn việc tạo từ bên ngoài thì giữ nó là lớp thường.

Đối tượng bất biến có làm chương trình chậm vì phải tạo đối tượng mới mỗi lần "đổi" không? Thường là không đáng kể. GC của JVM được tối ưu cho đối tượng sống ngắn, và đổi lại bạn bỏ được chi phí sao chép phòng thủ ở mọi nơi dùng, cùng chi phí khoá khi chia sẻ giữa thread. Chỉ cân nhắc kiểu thay đổi được khi đo đạc cho thấy đó là điểm nghẽn, như ghép chuỗi trong vòng lặp lớn, nơi `StringBuilder` (J2.2) tồn tại vì đúng lý do này.

<Callout kind="ai">

Nhờ AI sinh `equals`, `hashCode`, `toString` hoặc chuyển một lớp dữ liệu sang record. AI và IDE hay dùng mọi field, kể cả field thay đổi được, cho entity; hay viết `equals(Product)` thay vì `equals(Object)`; hay quên sao chép phòng thủ cho `List` hay mảng trong record; và sinh `toString` in cả mật khẩu, token. Kiểm tra: `equals` và `hashCode` dùng đúng cùng tập field và các field đó không đổi; `equals` có `@Override` và nhận `Object`; mọi thành phần collection của record đi qua `List.copyOf`; đọc `toString` như thể nó sẽ nằm trong log.

</Callout>

<Callout kind="link">

J5.1 đi sâu vào `HashMap` và giải thích ngăn, va chạm. J5.3 dùng `TreeSet`, `TreeMap` (dựa vào `compareTo` thay cho `hashCode`) và so các cách tạo collection không sửa được. J8 dùng `equals` của record trong assertion của test. SB3 viết `equals` cho entity JPA. J11 dựa vào đối tượng bất biến để chia sẻ dữ liệu giữa các thread mà không cần khoá.

</Callout>
