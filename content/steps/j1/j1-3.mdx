<Goal>

Hiểu Git lưu lịch sử thế nào để làm chủ vòng làm việc hằng ngày: commit, branch, merge, gỡ xung đột, push và pull. Đọc được trang Javadoc của JDK và tự viết Javadoc cho lớp của mình. Học xong bài này, bạn giải thích được:

- Vì sao xoá một file chứa mật khẩu bằng một commit mới không làm mật khẩu biến mất khỏi Git.
- Hai người cùng sửa một dòng thì Git làm gì, và vì sao những dòng khác trong cùng file vẫn được gộp tự động.
- Vì sao `git push` bị từ chối với `fetch first`, và vì sao `--force` không phải cách sửa.
- Vì sao `List.of(...).add(x)` ném exception, và bạn biết điều đó từ đâu mà không cần chạy thử.

</Goal>

<Knowledge>

Ví dụ trong bài là project hoá đơn đã sửa lỗi ở J1.2, tách lại thành hai file như J1.1: `src/Invoice.java` (các method để `public`) và `src/Main.java` (hoá đơn ba món, giảm 10%). Project nằm trong thư mục `invoice`.

### Ba vùng của Git

Bạn sửa ba file, nhưng chỉ muốn lưu hai file thành một mốc "đã xong tính giảm giá"; file thứ ba còn đang viết dở. Git cho làm đúng việc đó, vì giữa file bạn đang sửa và lịch sử có một vùng trung gian.

**Git** là hệ thống quản lý phiên bản: nó lưu lịch sử thay đổi của một thư mục thành chuỗi ảnh chụp, gọi là **commit**. Thư mục được Git quản lý là một **repository** (repo); lịch sử nằm trong thư mục con `.git`. Git chia công việc thành ba vùng:

| Vùng | Vai trò |
|---|---|
| Working tree | Các file bạn đang thấy và sửa trong thư mục |
| Staging area (index) | Ảnh chụp đang chuẩn bị cho commit kế tiếp; `git add` đưa thay đổi vào đây |
| Repository (`.git`) | Lịch sử các commit; `git commit` biến staging area thành một commit mới |

```text
 working tree          staging area (index)              repository (.git)
 file bạn đang sửa  -- git add -->  ảnh chụp sẽ commit  -- git commit -->  lịch sử commit
```

Mỗi commit ghi tên và email của người tạo nó. Khai báo một lần cho cả máy bằng `git config --global user.name "Nguyễn Văn A"` và `git config --global user.email "a@example.com"`, thay bằng tên và email của bạn; email nên trùng với email tài khoản GitHub hay GitLab để commit được gắn đúng người. Xem Git đã biết hai thông tin này chưa:

<Terminal where="mac">

```bash
git config --global user.name; git config --global user.email
```

</Terminal>

Kết quả:

```text
Nguyễn Văn A
a@example.com
```

Nếu lệnh không in gì, bạn chưa khai báo. Trên macOS, Git khi đó tự đoán danh tính từ tên tài khoản và tên máy, rồi vẫn commit kèm lời nhắc `Your name and email address were configured automatically based on your username and hostname`. Email đoán ra có dạng `ten@ten-may.local`, không thuộc tài khoản nào của bạn.

Một số file không bao giờ nên vào lịch sử: file `.class` sinh ra khi build, tài liệu sinh ra, cấu hình riêng của IDE. File **`.gitignore`** ở gốc repo liệt kê chúng, mỗi dòng một mẫu. `.gitignore` của project hoá đơn:

```text
out/
docs/
.idea/
.vscode/
*.iml
```

Thư mục `invoice` đã có `out/` (từ lần build ở J1.1) và `.idea/` (IntelliJ tạo khi mở project). Lệnh dưới biến thư mục thành repo với branch đầu tiên tên `main`, xem trạng thái, đưa `.gitignore` và `src` vào staging area, xem trạng thái lần nữa rồi commit:

<Terminal where="mac">

```bash
git init -b main
git status --short
git add .gitignore src
git status --short
git commit -m "Hoá đơn có giảm giá và VAT"
```

</Terminal>

Kết quả:

```text

?? .gitignore
?? src/
A  .gitignore
A  src/Invoice.java
A  src/Main.java

 create mode 100644 src/Invoice.java

```

Đường dẫn ở dòng đầu là thư mục của bạn. `git status --short` in hai cột trạng thái trước tên file: cột trái cho staging area, cột phải cho working tree. `??` là file chưa được theo dõi. Sau `git add`, cột trái thành `A` (added): ba file đã nằm trong staging area. `out/` và `.idea/` không xuất hiện ở lần nào vì đã nằm trong `.gitignore`.

Dòng `[main (root-commit) 1cd10dc]` báo commit đầu tiên đã tạo trên `main`. `1cd10dc` là bảy ký tự đầu của **mã commit**, một hash tính từ toàn bộ nội dung commit: ảnh chụp các file, tên người tạo, thời gian, lời nhắn và commit cha. Nội dung khác một chút là hash khác hẳn, nên mã commit trên máy bạn sẽ khác.

Hai lỗi hay gặp ở bước này:

- `fatal: not a git repository (or any of the parent directories): .git`: bạn chạy lệnh Git ở một thư mục không thuộc repo nào. Kiểm tra bằng `pwd` và `ls -a`, phải thấy thư mục `.git`.
- `git add .` khi chưa có `.gitignore` đưa luôn `out/` và cấu hình IDE vào commit. Đọc `git status --short` trước mỗi lần `git add`.

### Branch, HEAD và merge fast-forward

Bạn bắt đầu viết Javadoc cho `Invoice` (mục cuối bài), một việc mất vài buổi. Trong lúc đó, `main` phải luôn chạy được, để ai cần sửa gấp một lỗi vẫn làm được ngay.

**Branch** là một cái tên trỏ vào một commit. Tạo commit mới trên một branch làm tên đó dịch sang commit mới; các branch khác đứng yên. **HEAD** cho biết bạn đang đứng ở branch nào, tức commit mới sẽ được gắn vào đâu. Tạo branch không chép file nào, nên rẻ tới mức bạn tạo một branch cho mỗi việc:

```text
            C---D        javadoc  <- HEAD
           /
  A---B---E              main
```

Lệnh dưới tạo branch `javadoc` và chuyển sang đó. Sau khi viết Javadoc vào `src/Invoice.java`, xem trạng thái rồi commit. `-a` trong `git commit -am` tự đưa vào staging area mọi file đang được theo dõi đã sửa, thay cho một lệnh `git add` riêng:

<Terminal where="mac">

```bash
git switch -c javadoc
git status --short
git commit -am "Viết Javadoc cho Invoice"
```

</Terminal>

Kết quả:

```text
Switched to a new branch 'javadoc'
 M src/Invoice.java
[javadoc adc0f36] Viết Javadoc cho Invoice
 1 file changed, 40 insertions(+)
```

` M` có chữ `M` (modified) ở cột phải: file đã sửa trong working tree, chưa vào staging area. Commit mới nằm trên `javadoc`, còn `main` vẫn ở `1cd10dc`. Việc xong thì quay về `main` và **merge** (gộp) branch `javadoc` vào:

<Terminal where="mac">

```bash
git switch main
git merge javadoc
git log --oneline --graph
```

</Terminal>

Kết quả:

```text
Switched to branch 'main'
Updating 1cd10dc..adc0f36
Fast-forward
 src/Invoice.java | 40 ++++++++++++++++++++++++++++++++++++++++
 1 file changed, 40 insertions(+)
* adc0f36 Viết Javadoc cho Invoice
* 1cd10dc Hoá đơn có giảm giá và VAT
```

`main` không có commit nào mới kể từ lúc tách branch, nên Git chỉ việc dịch con trỏ `main` từ `1cd10dc` lên `adc0f36`. Đó là **fast-forward**: không tạo commit gộp, lịch sử vẫn là một đường thẳng, như `git log --graph` vẽ.

### Merge khi hai branch cùng sửa một dòng

Nhà nước giảm VAT còn 8%. Bạn sửa trên branch `vat-8`; cùng lúc, một đồng nghiệp tách thuế suất thành hằng số trên `main`. Lần này cả hai branch đều có commit mới, nên không fast-forward được nữa.

Trên `vat-8`, `git diff` trước khi commit cho thấy bạn sửa hai dòng: dòng Javadoc của `vat()` và dòng tính VAT. Bốn dòng đầu cho biết file nào được so; mỗi đoạn bắt đầu bằng `@@` ghi vị trí dòng; dòng bắt đầu bằng `-` là bản cũ, `+` là bản mới:

Chỉ dòng tính VAT bị cả hai bên sửa theo hai cách khác nhau. Git không đoán ý bạn ở dòng đó: nó dừng lại, đánh dấu chỗ xung đột trong file, và chờ bạn quyết. Xem trạng thái và đoạn bị đánh dấu:

`UU` nghĩa là file đang xung đột, cả hai phía đều sửa. Phần giữa `<<<<<<< HEAD` và `=======` là bản của branch bạn đang đứng (`main`), phần sau là bản của `vat-8`. `sed -n` chỉ in đoạn từ dòng `<<<<<<<` tới dòng `>>>>>>>`; trong IDE, đoạn này được tô màu và có nút chọn từng phía.

Gỡ xung đột không phải là chọn một phía. Kết quả đúng cần ý của cả hai: giữ hằng số của đồng nghiệp, và đổi giá trị của nó thành 8. Trong file, bạn xoá ba dòng đánh dấu cùng dòng `* 8 / 100`, rồi đổi `VAT_PERCENT = 10` thành `VAT_PERCENT = 8`. Chạy lại chương trình trước khi đánh dấu đã gỡ xong:

<Terminal where="mac">

Đọc đồ thị từ dưới lên: hai commit đầu nằm trên một đường thẳng, rồi lịch sử tách làm hai nhánh và gặp lại ở **commit gộp** (merge commit) `f2e107b`, commit có hai commit cha.

Phần Git gộp tự động không có nghĩa là đúng. Git chỉ so từng dòng chữ, không hiểu code: nếu một bên đổi tên method còn bên kia thêm một lời gọi tới tên cũ ở dòng khác, Git gộp êm và code không biên dịch. Sau mọi merge, kể cả merge không xung đột, hãy biên dịch và chạy test.

### Rebase: chép commit lên đỉnh nhánh khác

Bạn có branch `readme` với một commit thêm file `README.md`. Trong lúc đó `main` có thêm một commit mới. Merge sẽ tạo thêm một commit gộp chỉ để nối hai đường; nhiều nhóm muốn lịch sử thẳng hơn.

**Rebase** lấy các commit của branch bạn đang đứng và chép lại chúng, từng cái một, lên đỉnh của branch kia. Trước khi rebase, `git log --oneline --graph --all -3` cho thấy hai branch tách nhau từ commit gộp ở mục trước:

```text
* 655adc4 Thêm món thứ tư vào ví dụ
| * f2acdc2 Thêm README
|/
*   f2e107b Merge branch 'vat-8'
|\
```

Dòng `|\` cuối là phần đầu của hai nhánh đã gộp ở mục trước; `-3` chỉ in ba commit nên nó bị cắt ở đó.

Đứng trên `readme`, rebase lên `main`, rồi vẽ lại đồ thị:

<Terminal where="mac">

```bash
git rebase main
git log --oneline --graph --all -3
```

</Terminal>

Kết quả:

```text
Successfully rebased and updated refs/heads/readme.
* 042677d Thêm README
* 655adc4 Thêm món thứ tư vào ví dụ
*   f2e107b Merge branch 'vat-8'
|\
```

Commit "Thêm README" giờ nằm ngay trên `655adc4`, nên `git merge readme` từ `main` là fast-forward, không cần commit gộp. Nhưng mã của nó đã đổi, từ `f2acdc2` thành `042677d`. Rebase không di chuyển commit cũ; nó tạo commit mới có cùng thay đổi và cùng lời nhắn nhưng cha khác, và mã commit tính từ cả commit cha, nên mã mới khác.

Vì rebase thay commit cũ bằng commit mới, nó chỉ an toàn với commit chưa ai khác có. Nếu đồng nghiệp đã kéo `f2acdc2` về và làm tiếp trên đó, rebase của bạn để lại hai bản của cùng một thay đổi, và lần gộp sau sẽ rối. Quy tắc: không rebase commit đã push lên branch dùng chung.

| | Merge | Rebase |
|---|---|---|
| Lịch sử | Giữ đúng những gì đã xảy ra, có commit gộp | Thẳng, không có commit gộp |
| Mã commit cũ | Giữ nguyên | Thay bằng commit mới |
| An toàn với branch dùng chung | Có | Không |

Cách làm phổ biến: rebase branch cá nhân lên `main` mới nhất trước khi mở pull request (yêu cầu nhóm review và gộp branch của bạn), còn gộp vào `main` thì dùng merge.

### Remote: push, pull và khi cả hai bên có commit mới

Repo trên máy bạn chỉ có bạn thấy. Để làm việc cùng người khác, nhóm đặt một bản repo chung ở một nơi như GitHub, và mỗi người đồng bộ với nó.

**Remote** là một bản repo ở nơi khác mà repo của bạn biết tới qua một cái tên, thường là `origin`. `git push` đẩy commit của bạn lên remote, `git pull` kéo commit mới từ remote về và gộp vào branch hiện tại. Ví dụ dưới dùng một **repo bare** (chỉ có lịch sử, không có working tree) nằm cạnh thư mục project để đóng vai GitHub. `main` lúc này đã gộp `readme` ở mục trước. Với GitHub, lệnh giống hệt, chỉ địa chỉ remote là khác:

<Terminal where="mac">

```bash
git init --bare -b main ../invoice-remote.git
git remote add origin ../invoice-remote.git
git push -u origin main
```

</Terminal>

Kết quả (dòng đầu, đường dẫn tới repo bare, sẽ khác trên máy bạn):

```text
Initialized empty Git repository in /Users/<bạn>/invoice-remote.git/
To ../invoice-remote.git
 * [new branch]      main -> main
branch 'main' set up to track 'origin/main'.
```

`-u` ghi nhớ `origin/main` là branch đi kèm của `main`, nên từ giờ chỉ gõ `git push` và `git pull` là đủ. Trong Terminal, `git push` còn in vài dòng tiến độ như `Enumerating objects` trước các dòng trên.

Sau đó, một đồng nghiệp clone repo, sửa `README.md` và push commit `c53a5fa`. Cùng lúc, bạn commit một thay đổi trên máy mình và push:

<Terminal where="mac">

```bash
git push
```

</Terminal>

Kết quả:

```text
To ../invoice-remote.git
 ! [rejected]        main -> main (fetch first)
error: failed to push some refs to '../invoice-remote.git'
hint: Updates were rejected because the remote contains work that you do
hint: not have locally. This is usually caused by another repository pushing
hint: to the same ref. You may want to first integrate the remote changes
hint: (e.g., 'git pull ...') before pushing again.
```

Remote chỉ nhận push khi nó là fast-forward: commit của bạn phải nằm nối tiếp commit mới nhất trên remote. Ở đây remote có `c53a5fa` mà máy bạn chưa có, nên push bị từ chối để không xoá mất commit của đồng nghiệp. `git push --force` ép remote nhận bản của bạn và làm đúng điều đó: commit `c53a5fa` biến khỏi `main` trên remote. Cách sửa đúng là kéo commit của đồng nghiệp về trước:

<Terminal where="mac">

```bash

```

| Cách | Khi có commit ở cả hai bên |

| `pull.rebase false`, hoặc `git pull --no-rebase` | Merge, tạo commit gộp |
| `pull.rebase true`, hoặc `git pull --rebase` | Rebase commit của bạn lên commit mới của remote |
| `pull.ff only`, hoặc `git pull --ff-only` | Từ chối, để bạn tự xử lý |

Commit của bạn chưa push nên rebase an toàn, và lịch sử sẽ gọn hơn. Với branch nhiều người cùng đẩy, merge giữ đúng những gì đã xảy ra. Lần này chọn merge:

### Lịch sử không quên: commit nhầm mật khẩu

Một lập trình viên commit nhầm file `.env` chứa mật khẩu database, nhận ra, rồi tạo commit mới xoá file đó. File không còn trong thư mục, nhưng mật khẩu vẫn còn trong Git.

Repo dưới có đúng hai commit như vậy: commit trước thêm `.env`, commit sau xoá nó. `HEAD~1` nghĩa là commit ngay trước HEAD, và `git show <commit>:<file>` in nội dung một file trong commit đó:

<Terminal where="mac">

```bash
git log --oneline -3
ls -a
git show HEAD~1:.env
```

</Terminal>

Kết quả:

```text

1c8d7fd Cấu hình kết nối database
877e2d2 Merge branch 'main' of ../invoice-remote
.
..

```

`ls -a` không còn thấy `.env`, nhưng `git show` vẫn in nguyên mật khẩu. Một commit là ảnh chụp không đổi được: commit sau chỉ ghi "từ đây không còn file `.env`", còn commit trước vẫn giữ nguyên ảnh chụp có file. Ai clone repo cũng có cả hai commit, và đọc được mật khẩu bằng đúng lệnh trên.

<Callout kind="production">

Mật khẩu database nằm trong một commit đã push lên GitHub được vài giờ. Việc đầu tiên là coi như mật khẩu đã lộ: đổi mật khẩu ngay, vì bản clone, fork hay cache của người khác vẫn giữ commit cũ. Sau đó mới dọn lịch sử bằng công cụ chuyên dụng như `git filter-repo`, force push, và báo mọi người clone lại. Thứ tự ngược lại để lộ mật khẩu trong suốt thời gian dọn.

</Callout>

Phòng từ đầu thì rẻ hơn nhiều: đưa file chứa secret vào `.gitignore` trước commit đầu tiên, đọc secret từ biến môi trường, và đọc `git status --short` trước mỗi lần `git add`.

### Đọc Javadoc của JDK

`List.of("An", "Binh").add("Chi")` làm gì? Câu trả lời trên diễn đàn có thể đúng với Java 8 mà sai với Java 25, hoặc chỉ đúng với một bản cài đặt. Câu trả lời chính xác nằm ở Javadoc của đúng phiên bản bạn dùng.

**Javadoc** của JDK là **hợp đồng** của mỗi API: nó nói class dùng để làm gì, method nhận gì, trả gì và ném exception nào. Một trang class trả lời các câu hỏi sau ở những chỗ cố định:

| Câu hỏi | Tìm ở đâu | Ví dụ |
|---|---|---|
| Class này dùng để làm gì, có giới hạn gì? | Đoạn mô tả đầu trang | Javadoc của `ArrayList` ghi nó không được đồng bộ hoá (not synchronized) |
| Method nhận gì, trả gì? | Method Details: Parameters, Returns | `String.substring(begin, end)` không lấy ký tự ở vị trí `end` |
| Ném exception nào? | Method Details: Throws | `List.of(...)` ném `NullPointerException` nếu có phần tử `null` |
| Có từ phiên bản nào? | Since | `List.of` có từ Java 9 |

Interface `List` có thêm mục "Unmodifiable Lists", nói rằng list tạo bằng `List.of` không thêm, xoá hay đổi phần tử được: mọi method thay đổi đều ném `UnsupportedOperationException`. Đoạn sau kiểm chứng điều Javadoc nói. Nó chép list sang `ArrayList` để thêm được phần tử, rồi thử thêm thẳng vào list gốc:

```java
import java.util.ArrayList;
import java.util.List;

public class Main {
    public static void main(String[] args) {
        List<Long> prices = List.of(120_000L, 180_000L);
        List<Long> editable = new ArrayList<>(prices);
        editable.add(250_000L);
        System.out.println("editable = " + editable);
        prices.add(250_000L);
    }
}
```

Kết quả:

```text
editable = [120000, 180000, 250000]
Exception in thread "main" java.lang.UnsupportedOperationException
	at java.base/java.util.ImmutableCollections.uoe(ImmutableCollections.java:159)
	at java.base/java.util.ImmutableCollections$AbstractImmutableCollection.add(ImmutableCollections.java:164)
	at Main.main(Main.java:10)
```

Bản chép thêm được, list gốc thì ném exception ở dòng 10, đúng như mục "Unmodifiable Lists". Phần Throws của `List.of` nói thêm một điều:

```java
import java.util.List;

public class Nulls {
    public static void main(String[] args) {
        Long missing = null;
        List<Long> prices = List.of(120_000L, missing);
        System.out.println(prices);
    }
}
```

Kết quả:

```text
Exception in thread "main" java.lang.NullPointerException
	at java.base/java.util.Objects.requireNonNull(Objects.java:220)
	at java.base/java.util.ImmutableCollections$List12.<init>(ImmutableCollections.java:591)
	at java.base/java.util.List.of(List.java:952)
	at Nulls.main(Nulls.java:6)
```

`List.of` từ chối `null` ngay lúc tạo list, ở dòng 6, chứ không đợi tới lúc dùng. Số dòng trong các file của JDK (`ImmutableCollections.java:159`…) có thể khác giữa các bản JDK. Cả hai hành vi đều có trong Javadoc, nên bạn biết trước mà không cần chạy thử; chạy thử chỉ để thấy chúng xảy ra.

Đoạn mô tả đầu trang đáng đọc nhất khi code chạy trên nhiều thread. Javadoc của `ArrayList` ghi nó không được đồng bộ hoá: nhiều thread cùng sửa một `ArrayList` mà không có cơ chế đồng bộ bên ngoài có thể làm hỏng dữ liệu. Gặp dòng như vậy, đừng dùng chung một instance giữa các thread; chọn class được thiết kế cho việc đó, như `CopyOnWriteArrayList` hay `ConcurrentHashMap`, rồi đọc Javadoc của chúng để biết chúng đảm bảo điều gì. J5 và J11 đi sâu vào chuyện này.

### Viết Javadoc cho code của bạn

Đồng nghiệp gọi `new Invoice(150)` và không ai biết đó có phải giá trị hợp lệ không, vì không có chỗ nào nói `discountPercent` được phép nằm trong khoảng nào.

Javadoc là chú thích bắt đầu bằng `/**`, đặt ngay trên class, constructor hay method. Công cụ `javadoc` đọc chúng và sinh trang HTML cùng bố cục với tài liệu của JDK. Chạy `javadoc` trên `Invoice` chưa có chú thích nào, ghi kết quả vào thư mục `docs`:

<Terminal where="mac">

```bash
javadoc -quiet -d docs src/Invoice.java
```

</Terminal>

Kết quả:

```text

       ^

    public Invoice(int discountPercent) {
           ^
src/Invoice.java:12: warning: no comment

                ^
```

`javadoc` vẫn sinh tài liệu, nhưng cảnh báo bảy thành phần `public` chưa có chú thích: class, constructor và năm method. Phần kiểm tra này gọi là **doclint**. Dưới đây là Javadoc của class, constructor và `discount()`; bốn method còn lại viết theo cùng mẫu. Constructor có thêm đoạn kiểm tra, để dòng `@throws` là sự thật:

```java norun
/**
 * Hoá đơn bán hàng: cộng giá các món, giảm giá cho đơn lớn và tính VAT.
 *
 * <p>Mọi số tiền tính bằng đồng, kiểu {@code long}; phép chia làm tròn xuống.
 * Lớp này không an toàn khi nhiều thread cùng gọi {@link #add(long)}.
 */
public class Invoice {
    // field prices và discountPercent như trước

    /**
     * Tạo một hoá đơn chưa có món nào.
     *
     * @param discountPercent phần trăm giảm cho đơn từ 500.000 đồng, từ 0 đến 100
     * @throws IllegalArgumentException nếu {@code discountPercent} nằm ngoài khoảng 0 đến 100
     */
    public Invoice(int discountPercent) {
        if (discountPercent < 0 || discountPercent > 100) {
            throw new IllegalArgumentException("discountPercent: " + discountPercent);
        }
        this.discountPercent = discountPercent;
    }

    /**
     * Số tiền được giảm. Chỉ áp dụng khi {@link #subtotal()} từ 500.000 đồng.
     *
     * @return số tiền giảm, tính bằng đồng; {@code 0} nếu đơn chưa đủ 500.000 đồng
     */
    public long discount() {
        if (subtotal() < 500_000) {
            return 0;
        }
        return subtotal() * discountPercent / 100;
    }

    // add, subtotal, vat, total, mỗi method có Javadoc như discount()
}
```

Cách viết một chú thích Javadoc tốt:

- Câu đầu tiên là tóm tắt; nó xuất hiện trong bảng Method Summary. Viết nó như câu trả lời cho "method này cho tôi cái gì".
- `@param`, `@return`, `@throws` mô tả hợp đồng: đơn vị, khoảng giá trị hợp lệ, khi nào ném lỗi. Không kể lại từng dòng code; người đọc Javadoc thường không mở code.
- `{@code ...}` viết một tên trong code, `{@link ...}` tạo link tới class hay method khác. `<p>` mở một đoạn mới.
- Điều kiện quan trọng với người gọi, như "không an toàn khi nhiều thread cùng gọi", đặt ở đoạn mô tả class, đúng chỗ bạn vừa tìm nó trong Javadoc của JDK.

Doclint kiểm cả các tag còn thiếu. Nếu Javadoc của `add` quên dòng `@param price`, `javadoc` báo:

```text
src/Invoice.java:30: warning: no @param for price
    public void add(long price) {
                ^
1 warning
```

Khi đủ chú thích cho mọi thành phần `public`, cùng lệnh `javadoc -quiet -d docs src/Invoice.java` không in gì, và `docs/Invoice.html` là trang tài liệu của class. Doclint chỉ kiểm cấu trúc, không kiểm nội dung: nó không biết constructor có thật sự ném `IllegalArgumentException` như `@throws` hứa hay không. Với mỗi `@throws`, đối chiếu với code, như đoạn kiểm tra trong constructor ở trên.

<Callout kind="ai">

Nhờ AI giải thích output của `git status` hay một thông báo lỗi của Git, gợi ý lời nhắn commit, hoặc viết nháp Javadoc cho một method. AI hay đưa lệnh "cứu nguy" như `git push --force` hay `git reset --hard` mà không nói chúng xoá mất commit, của bạn hoặc của người khác. Nó cũng hay viết Javadoc kể lại code thay vì mô tả hợp đồng, hoặc bịa `@throws` mà code không ném. Trước khi chạy một lệnh Git lạ, đọc `git help <lệnh>`; với Javadoc, đối chiếu từng `@throws` với code và chạy `javadoc` tới khi không còn cảnh báo.

</Callout>
