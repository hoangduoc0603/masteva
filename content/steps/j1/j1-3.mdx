<Goal>

Quản lý project bằng Git theo vòng làm việc hằng ngày: commit, branch, merge, gỡ xung đột, push và pull. Đọc được trang Javadoc của JDK và tự viết Javadoc cho lớp của mình. Học xong bài này, bạn giải thích được:

- Vì sao xoá một file chứa secret trong commit mới không làm secret biến mất khỏi Git.
- Hai người cùng sửa một dòng thì Git làm gì, và bạn gỡ xung đột ra sao.
- Vì sao `List.of(...).add(x)` ném exception, và bạn biết điều đó từ đâu mà không cần chạy thử.

</Goal>

<Knowledge>

### Ba vùng của Git

```text
 working tree          staging area (index)        repository (.git)
 file bạn đang sửa  -- git add -->  ảnh chụp sẽ commit  -- git commit -->  lịch sử commit
                    <---------------- git restore / git switch ---------------
```

- **Commit** là ảnh chụp toàn bộ file đã stage, kèm tác giả, thời gian, lời nhắn và con trỏ tới commit cha. Mã commit (ví dụ `5462a11`) là hash của nội dung đó.
- **Branch** chỉ là một cái tên trỏ vào một commit. Commit mới trên branch làm tên đó dịch sang commit mới.
- **HEAD** cho biết bạn đang đứng ở branch nào.

```text
            C---D        vat-8
           /
  A---B---E              main  <- HEAD
```

| Lệnh | Việc nó làm |
|---|---|
| `git status` | Xem file nào đã sửa, đã stage, chưa theo dõi |
| `git add <file>` | Đưa thay đổi vào staging area |
| `git commit -m "..."` | Tạo commit từ staging area |
| `git switch -c <tên>` | Tạo branch mới và chuyển sang |
| `git merge <branch>` | Gộp branch khác vào branch hiện tại |
| `git push`, `git pull` | Đẩy commit lên remote, kéo commit mới về |

**Merge** giữ nguyên lịch sử hai nhánh và tạo một commit gộp. **Rebase** chép lại commit của bạn lên đỉnh nhánh kia, cho lịch sử thẳng hơn nhưng đổi mã commit. Quy tắc an toàn: chỉ rebase commit chưa push lên branch dùng chung.

<Callout kind="production">

Một lập trình viên commit nhầm file `.env` chứa mật khẩu database và push lên GitHub, rồi tạo commit mới xoá file đó. Mật khẩu vẫn nằm trong commit cũ, ai clone repo cũng đọc được. Việc đúng là đổi mật khẩu ngay, sau đó mới tính chuyện xoá khỏi lịch sử. Phòng từ đầu bằng `.gitignore` và đọc `git status` trước mỗi lần `git add`.

</Callout>

### Đọc Javadoc của JDK

Javadoc của JDK là **hợp đồng** của mỗi API: nó nói method làm gì, nhận gì, trả gì và ném exception nào. Câu trả lời trên diễn đàn có thể cũ hoặc sai; Javadoc của đúng phiên bản bạn dùng thì không. Một trang lớp có các phần:

| Câu hỏi | Tìm ở đâu | Ví dụ |
|---|---|---|
| Lớp này dùng để làm gì, có giới hạn gì? | Đoạn mô tả đầu trang | Javadoc của `ArrayList` ghi rõ nó không được đồng bộ hoá, nên không an toàn khi nhiều thread cùng sửa |
| Method nhận gì, trả gì? | Method Details: Parameters, Returns | `String.substring(begin, end)` không lấy ký tự ở vị trí `end` |
| Ném exception nào? | Method Details: Throws | `List.of(...)` ném `NullPointerException` nếu có phần tử `null` |
| Có từ phiên bản nào? | Since | `List.of` có từ Java 9 |

Interface `List` có một mục riêng tên "Unmodifiable Lists", nói rằng list tạo bằng `List.of` không thêm, xoá hay đổi phần tử được. Bạn sẽ kiểm chứng điều này trong phần thực hành.

### Viết Javadoc cho code của bạn

Javadoc là chú thích bắt đầu bằng `/**`, đặt ngay trên class, constructor hay method `public`. Công cụ `javadoc` đọc chúng và sinh ra trang HTML giống tài liệu của JDK.

```java
/**
 * Số tiền được giảm. Chỉ áp dụng khi {@link #subtotal()} từ 500.000 đồng.
 *
 * @return số tiền giảm, tính bằng đồng
 */
public long discount() { ... }
```

- Câu đầu tiên là tóm tắt, xuất hiện trong bảng Method Summary. Viết nó như một câu trả lời cho "method này cho tôi cái gì".
- `@param`, `@return`, `@throws` mô tả hợp đồng: đơn vị, khoảng giá trị hợp lệ, khi nào ném lỗi. Đừng kể lại từng dòng code.
- `{@code ...}` để viết tên trong code, `{@link ...}` để tạo link tới class hay method khác.

</Knowledge>

Làm việc mới trên branch riêng, để `main` luôn ở trạng thái chạy được:

`javadoc` vẫn sinh tài liệu vào `docs/`, nhưng cảnh báo 7 chỗ chưa có chú thích: class, constructor và 5 method `public`. Mở `src/Invoice.java` trong IDE và viết Javadoc cho cả 7. Gõ `/**` rồi Enter ngay trên một method, IDE tự sinh khung `@param`, `@return`. Mẫu cho class và constructor; thêm luôn đoạn kiểm tra để dòng `@throws` là sự thật:

```java
/**
 * Hoá đơn bán hàng: cộng giá các món, giảm giá cho đơn lớn và tính VAT.
 *
 * <p>Mọi số tiền tính bằng đồng, kiểu {@code long}; phép chia làm tròn xuống.
 * Lớp này không an toàn khi nhiều thread cùng gọi {@link #add(long)}.
 */
public class Invoice {
    ...
    /**
     * Tạo một hoá đơn rỗng.
     *
     * @param discountPercent phần trăm giảm cho đơn từ 500.000 đồng, từ 0 đến 100
     * @throws IllegalArgumentException nếu {@code discountPercent} nằm ngoài khoảng 0 đến 100
     */
    public Invoice(int discountPercent) {
        if (discountPercent < 0 || discountPercent > 100) {
            throw new IllegalArgumentException("discountPercent: " + discountPercent);
        }
        this.discountPercent = discountPercent;
    }
```

Mẫu cho `discount()` nằm ở phần Kiến thức. Chạy lại cho tới khi `javadoc` không in cảnh báo nào:

### 4. Tạo và gỡ một xung đột

Nhà nước giảm VAT còn 8%. Bạn sửa trên branch `vat-8`; cùng lúc, một đồng nghiệp tách thuế suất thành hằng số trên `main`. Hai thay đổi chạm vào cùng một dòng. Lệnh `perl -pi -e` dưới đây sửa file tại chỗ, chạy được cả trên Mac và Linux:

<Terminal where="mac">

```bash
git switch -c vat-8
perl -pi -e 's#\* 10 / 100#* 8 / 100#' src/Invoice.java
git commit -am "Giảm VAT còn 8%"
git switch main
perl -0pi -e 's#\* 10 / 100#* VAT_PERCENT / 100#; s#public class Invoice \{\n#$&    static final int VAT_PERCENT = 10;\n#' src/Invoice.java
git commit -am "Tách thuế suất VAT thành hằng số"
git merge vat-8
```

</Terminal>

### Khi gặp lỗi

<Callout kind="pitfall">

- `Author identity unknown`: Git chưa biết bạn là ai. Chạy lại hai lệnh `git config --global user.name` và `user.email` ở bước 1.
- `fatal: not a git repository`: bạn đang đứng sai thư mục, hoặc đường dẫn sau `git -C` sai. Kiểm tra bằng `pwd` và `ls -a` (phải thấy thư mục `.git`).
- `! [rejected] main -> main (fetch first)` khi push: remote có commit mà máy bạn chưa có. Chạy `git pull` trước, gỡ xung đột nếu có, rồi push lại. Đừng dùng `--force` để "sửa" lỗi này.
- `javadoc` báo `error: unknown tag` hoặc `warning: no comment`: sửa đúng tên tag (`@param`, `@return`, `@throws`) và viết Javadoc cho mọi thành phần `public`.

</Callout>

<DeepDive>

<Reveal title="Khi nào merge, khi nào rebase?">

Merge giữ đúng lịch sử đã xảy ra và an toàn với branch dùng chung. Rebase cho lịch sử thẳng, dễ đọc với `git log`, nhưng tạo commit mới thay cho commit cũ. Cách làm phổ biến: rebase branch cá nhân lên `main` mới nhất trước khi mở pull request (`git pull --rebase` hoặc `git rebase main`), còn gộp vào `main` thì merge. Không bao giờ rebase commit người khác đã kéo về.

</Reveal>

<Reveal title="git pull báo divergent branches và hỏi merge hay rebase, chọn gì?">

Thông báo này xuất hiện khi cả máy bạn và remote đều có commit mới mà máy kia chưa có. Các bản Git mới không tự chọn nữa mà dừng lại, bắt bạn khai báo một lần: `git config --global pull.rebase false` để luôn merge, `true` để luôn rebase, hoặc `pull.ff only` để chỉ nhận khi tua thẳng được và tự xử lý phần còn lại. Với branch cá nhân, rebase cho lịch sử gọn; với branch nhiều người cùng đẩy, merge an toàn hơn.

</Reveal>

<Reveal title="Lỡ commit mật khẩu hoặc token thì xoá thế nào?">

Coi như secret đã lộ: thu hồi và tạo secret mới trước tiên, vì bản clone, fork hay cache của người khác vẫn giữ commit cũ. Sau đó mới dọn lịch sử bằng công cụ chuyên dụng như `git filter-repo`, rồi force push và báo mọi người clone lại. Một commit "xoá file" mới không đủ, vì secret vẫn nằm trong commit trước đó. Để tránh lặp lại, đưa file cấu hình chứa secret vào `.gitignore` và dùng biến môi trường.

</Reveal>

<Reveal title="Javadoc nói lớp không thread-safe thì làm gì?">

Không dùng chung một instance giữa nhiều thread mà không đồng bộ. Chọn lớp được thiết kế cho việc đó, như `CopyOnWriteArrayList` hay `ConcurrentHashMap`, và đọc Javadoc của chúng để biết chúng đảm bảo điều gì. J5 và J14 đi sâu vào chuyện này.

</Reveal>

<Callout kind="ai">

Nhờ AI giải thích output của `git status`, gợi ý lời nhắn commit, hoặc viết nháp Javadoc cho một method. AI hay đưa lệnh "cứu nguy" như `git push --force` hay `git reset --hard` mà không nói chúng xoá mất commit. Nó cũng hay viết Javadoc kể lại code thay vì mô tả hợp đồng, hoặc bịa `@throws` mà code không ném. Trước khi chạy lệnh Git lạ, đọc `git help <lệnh>`; với Javadoc, đối chiếu từng `@throws` với code.

</Callout>

<Callout kind="link">

J4 dạy thiết kế exception, nội dung chính của `@throws`. J5 dùng Javadoc để chọn collection và hiểu collection bất biến. J7 dùng `.gitignore` và wrapper của build tool; J20 dùng ADR và review code, nơi lịch sử Git sạch trở nên quan trọng.

</Callout>
