<Goal>

Dùng được một IDE để điều hướng project Java, và dùng debugger để tìm nguyên nhân một kết quả sai mà không phải đoán. Học xong bài này, bạn giải thích được:

- Vì sao một phép tính tiền ra `0` dù code nhìn có vẻ đúng, và debugger chỉ ra chỗ đó ra sao trước khi bạn sửa dòng nào.
- Vì sao một breakpoint đặt trong một method lại dừng nhiều lần hơn bạn nghĩ.
- Vì sao bật cổng debug trên server production là chuyện nguy hiểm, cả về bảo mật lẫn về độ ổn định.

</Goal>

<Knowledge>

Ví dụ trong bài dùng tiếp hoá đơn của J1.1, thêm quy tắc giảm giá. Debugger trong IntelliJ IDEA, VS Code và lệnh `jdb` của JDK làm cùng một việc; bài minh hoạ bằng `jdb` vì output của nó là chữ, và có bảng cho biết mỗi lệnh `jdb` ứng với thao tác nào trong IDE.

### IDE hiểu cả project, không chỉ từng file

Bạn muốn đổi tên method `discount` thành `discountAmount`. Tìm và thay chữ "discount" trong mọi file sẽ đổi luôn chuỗi `"discount="` trong lệnh in, tên field `discountPercent` và cả comment. Nếu một class khác cũng có method `discount()`, thay chữ còn đổi nhầm cả method đó.

**IDE** (Integrated Development Environment) đọc toàn bộ project và dựng một **chỉ mục** (index) gồm mọi class, method, field và chỗ gọi. Nhờ chỉ mục, IDE biết `invoice.discount()` trỏ tới đúng method nào, nên làm được những việc mà tìm kiếm chữ không làm được: đi tới định nghĩa, tìm mọi nơi gọi một method, đổi tên ở mọi chỗ gọi mà không đụng tới chuỗi hay tên khác, chạy và debug.

| | IntelliJ IDEA | VS Code + Extension Pack for Java |
|---|---|---|
| Cài | Một ứng dụng, có sẵn hỗ trợ Java | Cài VS Code, rồi cài Extension Pack for Java của Microsoft |
| Thế mạnh | Hiểu Java và Spring rất sâu, refactor mạnh | Nhẹ, dùng chung cho nhiều ngôn ngữ |
| Phù hợp | Làm Java hằng ngày | Đã quen VS Code, project nhỏ hoặc nhiều ngôn ngữ |

Để dựng chỉ mục, IDE cần biết hai điều về project: dùng JDK nào để hiểu thư viện chuẩn, và thư mục nào chứa mã nguồn (**source root**). Với project Maven hay Gradle (J7), IDE đọc cả hai từ file build. Với một thư mục chỉ có `src/*.java` như project hoá đơn, bạn tự khai báo:

| Việc | IntelliJ IDEA | VS Code |
|---|---|---|
| Chọn JDK | File → Project Structure → Project → SDK | Command Palette (⇧⌘P) → `Java: Configure Java Runtime` |
| Đánh dấu thư mục mã nguồn | Chuột phải `src` → Mark Directory as → Sources Root | Chuột phải `src` → Add Folder to Java Source Path |

Dấu hiệu IDE chưa hiểu project: không có nút ▶ cạnh method `main`, tên class bị gạch đỏ dù chương trình chạy được bằng `java`, hoặc "đi tới định nghĩa" không đi đâu cả.

Chọn một IDE và dùng thành thạo; phím tắt quan trọng hơn IDE nào. Bảng dưới là phím mặc định trên macOS:

### Một kết quả sai cần giải thích

Cửa hàng thêm quy tắc: đơn từ 500.000 đồng được giảm `discountPercent` phần trăm, VAT 10% tính trên số tiền sau giảm. Chương trình dưới gộp `Invoice` và `Main` vào một file `Main.java` để dễ theo dõi số dòng; đơn có ba món, tổng 550.000 đồng, giảm 10%:

```java
import java.util.ArrayList;
import java.util.List;

class Invoice {
    private final List<Long> prices = new ArrayList<>();
    private final int discountPercent;

    Invoice(int discountPercent) {
        this.discountPercent = discountPercent;
    }

    void add(long price) {
        prices.add(price);
    }

    long subtotal() {
        long sum = 0;
        for (long price : prices) {
            sum += price;
        }
        return sum;
    }

    long discount() {
        if (subtotal() < 500_000) {
            return 0;
        }
        return subtotal() * (discountPercent / 100);
    }

    long vat() {
        return (subtotal() - discount()) * 10 / 100;
    }

    long total() {
        return subtotal() - discount() + vat();
    }
}

public class Main {
    public static void main(String[] args) {
        Invoice invoice = new Invoice(10);
        invoice.add(120_000);
        invoice.add(180_000);
        invoice.add(250_000);
        long total = invoice.total();
        System.out.println("subtotal=" + invoice.subtotal());
        System.out.println("discount=" + invoice.discount());
        System.out.println("total=" + total);
    }
}
```

Kết quả:

```text
subtotal=550000
discount=0
total=605000
```

Tính tay: giảm 10% của 550.000 là 55.000, còn 495.000, cộng VAT 49.500 thì `total` phải là 544.500. Chương trình lại cho `discount=0`. Cách quen thuộc là rải `System.out.println` vào từng method, chạy lại, đọc, rồi thêm `println` khác cho câu hỏi tiếp theo. Mục sau tìm ra nguyên nhân mà không sửa dòng code nào.

### Debugger: dừng chương trình để nhìn vào bên trong

**Debugger** là công cụ dừng một chương trình đang chạy tại chỗ bạn chọn, cho bạn xem giá trị của mọi biến ở đó và chạy tiếp từng bước. Các khái niệm:

| Khái niệm | Ý nghĩa |
|---|---|
| Breakpoint | Điểm dừng ở một dòng. **Thread** (luồng thực thi, thứ đang chạy code của bạn) chạy tới dòng đó thì dừng lại, trước khi dòng đó chạy |
| Frames (Call Stack) | Chuỗi method đang gọi nhau, từ `main` tới chỗ đang dừng |
| Variables | Giá trị biến cục bộ và field của `this` tại chỗ đang dừng |
| Evaluate | Chạy một biểu thức Java bất kỳ trong ngữ cảnh đang dừng |
| Resume | Chạy tiếp tới breakpoint kế tiếp hoặc tới khi chương trình kết thúc |

Nghi vấn đầu tiên là dòng 28, `return subtotal() * (discountPercent / 100);`, nơi tính tiền giảm. Để debugger đọc được tên biến cục bộ, biên dịch với `-g` (mục "Tên biến cần javac -g" giải thích vì sao), rồi mở `jdb` cho class `Main`:

<Terminal where="mac">

```bash
javac -g -d out Main.java && jdb -classpath out Main
```

</Terminal>

Ở dấu nhắc `>` của `jdb`, phiên dưới đặt breakpoint ở dòng 28 của class `Invoice`, chạy chương trình, rồi khi dừng thì in `this`, tính hai biểu thức và in chuỗi gọi:

</Predict>

Đọc output theo thứ tự lệnh:

- `Deferring breakpoint`: lúc đặt breakpoint, class `Invoice` chưa được nạp (J1.1: JVM nạp class khi cần lần đầu), nên `jdb` hẹn đặt sau.
- `Breakpoint hit` cho biết đang dừng ở dòng 28 của `Invoice.discount()`. `bci` là vị trí trong bytecode của method, chưa cần để ý.
- `dump this` in field của đối tượng, như khung Variables của IDE: `discountPercent` đúng là `10`. Số `id=442` là mã `jdb` đặt cho đối tượng và sẽ khác trên máy bạn.
- Hai lệnh `print` là Evaluate: `10 / 100` là phép chia nguyên giữa hai `int` (J1.1), phần thập phân bị bỏ, nên mọi thứ nhân với nó đều bằng 0. Nhân trước rồi chia sau, `550000 * 10 / 100` không mất gì.
- `where` in chuỗi gọi như khung Frames: `discount` được gọi từ `total`, `total` được gọi từ dòng 46 của `main`.

Bạn vừa chứng minh được nguyên nhân bằng giá trị thật, chưa sửa dòng nào. Sau khi sửa dòng 28 thành `return subtotal() * discountPercent / 100;`, chạy lại chương trình:

<Terminal where="mac">

```bash
java Main.java
```

</Terminal>

Kết quả:

```text

discount=55000
total=544500
```

`discount` và `total` giờ khớp với con số tính tay. So với rải `println`, debugger không cần sửa code để hỏi, không cần chạy lại cho mỗi câu hỏi mới, và Evaluate cho bạn thử ngay một giả thuyết, kể cả bản sửa, trên đúng dữ liệu đang có.

Mỗi lệnh `jdb` ở trên ứng với một thao tác trong IDE:

| `jdb` | IntelliJ IDEA | VS Code |
|---|---|---|
| `stop at Invoice:28` | Bấm vào lề trái dòng 28, hiện chấm đỏ | Bấm vào lề trái dòng 28 |
| `run` | Debug thay vì Run | Debug thay vì Run |
| `dump this`, `locals` | Khung Variables | Khung Variables |
| `print <biểu thức>` | Evaluate (⌥F8) | Gõ vào Debug Console |
| `where` | Khung Frames | Khung Call Stack |
| `cont` | Resume | Continue |
| `step`, `next`, `step up` | Step Into, Step Over, Step Out | Step Into, Step Over, Step Out |

### Một breakpoint, nhiều lần dừng

Giữ breakpoint ở dòng 28 và chạy tiếp bằng `cont`. Chương trình lại dừng ở đúng dòng đó, dù `main` chỉ gọi `total()` một lần.

Phiên dưới nối tiếp phiên ở mục trước: mỗi lần dừng, gõ `where` để xem lần dừng này đến từ đâu, rồi `cont`:

<Predict question="Breakpoint ở dòng 28 dừng tổng cộng bao nhiêu lần?">

```text
main[1] cont
>
Breakpoint hit: "thread=main", Invoice.discount(), line=28 bci=13

main[1] where
  [1] Invoice.discount (Main.java:28)
  [2] Invoice.vat (Main.java:32)
  [3] Invoice.total (Main.java:36)
  [4] Main.main (Main.java:46)
main[1] cont
> subtotal=550000

Breakpoint hit: "thread=main", Invoice.discount(), line=28 bci=13

main[1] where
  [1] Invoice.discount (Main.java:28)
  [2] Main.main (Main.java:48)
main[1] cont
> discount=0
total=605000

```

Ba lần tất cả: lần ở mục trước và hai lần trên. Dòng `subtotal=550000` xen giữa là output của chương trình, in ra trong lúc nó chạy tiếp.

</Predict>

Ba lần dừng có ba chuỗi gọi khác nhau:

1. `main` → `total()` → `discount()`.
2. `main` → `total()` → `vat()` → `discount()`.
3. `main` → `discount()`, ở dòng in `discount=`.

Một method có thể được gọi từ nhiều đường, và khung Frames cho biết lần dừng này đến từ đường nào. Khi một giá trị chỉ sai ở một trong các đường, đọc Frames trước khi đọc Variables.

**Conditional breakpoint** (breakpoint có điều kiện) chỉ dừng khi một biểu thức đúng. Trong IntelliJ, bấm chuột phải vào chấm đỏ và nhập vào ô Condition; trong VS Code, chuột phải chấm đỏ → Edit Condition → Expression. `jdb` không có loại breakpoint này. Đặt breakpoint ở dòng 19, `sum += price;`, với điều kiện `price > 200000`: mỗi lần dừng, `price` là `250000`, món duy nhất trên 200.000 đồng.

Thử tự trả lời trước khi đọc tiếp: breakpoint có điều kiện này dừng bao nhiêu lần?

Chín lần. Mỗi lần `subtotal()` chạy, vòng lặp gặp đúng một giá trị lớn hơn 200.000, nên số lần dừng bằng số lần `subtotal()` được gọi. `discount()` gọi `subtotal()` hai lần (ở `if` và ở `return`), nên:

| Ai gọi | Số lần `subtotal()` chạy |
|---|---|
| `total()` gọi thẳng | 1 |
| `total()` → `discount()` | 2 |
| `total()` → `vat()`, gọi thẳng và qua `discount()` | 3 |
| `main` in `subtotal=` | 1 |
| `main` in `discount=`, qua `discount()` | 2 |

Breakpoint có điều kiện vừa cho thấy code tính đi tính lại cùng một tổng chín lần cho một hoá đơn. Với ba món thì không sao; với hoá đơn hàng nghìn dòng đọc từ database thì đó là vấn đề hiệu năng.

### Đi từng bước: Step Into, Step Over, Step Out

Breakpoint cho bạn dừng ở một chỗ; các lệnh step cho bạn đi tiếp từng dòng từ chỗ đó, vào hoặc vượt qua các method được gọi.

| Lệnh | Việc nó làm |
|---|---|
| Step Into (`step`) | Đi vào bên trong method được gọi ở dòng hiện tại |
| Step Over (`next`) | Chạy hết dòng hiện tại, kể cả các method nó gọi, rồi dừng ở dòng kế tiếp |
| Step Out (`step up`) | Chạy nốt method hiện tại, dừng lại ở chỗ đã gọi nó |

Phiên dưới đặt breakpoint ở dòng 46 của `Main`, `long total = invoice.total();`, rồi Step Into hai lần và Step Out một lần:

```text
> stop at Main:46
Deferring breakpoint Main:46.
It will be set after the class is loaded.
> run
run Main
Set uncaught java.lang.Throwable
Set deferred uncaught java.lang.Throwable
>
VM Started: Set deferred breakpoint Main:46

Breakpoint hit: "thread=main", Main.main(), line=46 bci=31

main[1] step
>
Step completed: "thread=main", Invoice.total(), line=36 bci=0

main[1] step
>
Step completed: "thread=main", Invoice.subtotal(), line=17 bci=0

main[1] step up
>
Step completed: "thread=main", Invoice.total(), line=36 bci=4
```

`step` thứ nhất đi từ dòng 46 vào `total()`. `step` thứ hai đi vào lời gọi đầu tiên trên dòng 36, là `subtotal()`, và dừng ở dòng đầu của nó. `step up` chạy hết `subtotal()` rồi quay về dòng 36 của `total()`, ở `bci=4`, ngay sau lời gọi vừa xong. Dòng 36 còn gọi `discount()` và `vat()`; `next` ở đây sẽ chạy hết chúng mà không dừng bên trong.

Khi một dòng gọi nhiều method, Step Into luôn vào lời gọi chạy đầu tiên. Muốn vào một method cụ thể trên dòng đó, IntelliJ có Smart Step Into (⇧F7) cho bạn chọn method.

### Tên biến cần javac -g

Bạn đặt breakpoint trong `subtotal()` để xem biến `sum`, và debugger không cho xem.

File `.class` mặc định chỉ giữ số dòng và tên file nguồn, không giữ tên biến cục bộ. `javac -g` ghi thêm **thông tin debug** (debug information): bảng tên và vị trí của từng biến cục bộ. Phiên dưới chạy trên class biên dịch bằng `javac -d out0 Main.java`, không có `-g`, đặt breakpoint ở dòng 19 rồi gõ `locals` khi dừng. Phần đầu phiên giống mục trước nên được lược, output bắt đầu từ lúc dừng:

```text
Breakpoint hit: "thread=main", Invoice.subtotal(), line=19 bci=35

main[1] locals
Local variable information not available.  Compile with -g to generate variable information
```

Breakpoint vẫn dừng được, vì số dòng có sẵn. Chỉ tên biến là mất. Với class biên dịch bằng `-g`, `locals` in đủ tên và giá trị, ví dụ ở dòng 46 của `main`:

```text
main[1] locals
Method arguments:
args = instance of java.lang.String[0] (id=441)
Local variables:
invoice = instance of Invoice(id=442)
```

Biến `total` chưa có trong danh sách vì dòng 46 chưa chạy xong: breakpoint dừng **trước** khi dòng đó chạy. IDE và Maven bật `-g` sẵn khi build, nên bạn chỉ gặp thông báo này khi tự gọi `javac`, hoặc khi debug một thư viện được build không kèm thông tin debug.

### Bên dưới: debugger nối với JVM qua JDWP

Debugger của IDE và `jdb` đều không chạy code của bạn. Chương trình chạy trong một JVM riêng, và debugger điều khiển JVM đó từ bên ngoài.

| Thành phần | Vai trò |
|---|---|
| Agent `jdwp` | Module nạp vào JVM lúc khởi động bằng tuỳ chọn `-agentlib:jdwp=...`; dừng thread, đọc biến, chạy biểu thức theo lệnh nhận được |
| **JDWP** (Java Debug Wire Protocol) | Giao thức trao đổi lệnh debug qua một kết nối mạng (socket) |
| Debugger (IDE, `jdb`) | Giao diện: gửi lệnh "đặt breakpoint", "đọc biến", "chạy tiếp" và hiển thị kết quả |

```text
 IDE hoặc jdb                                   JVM đang chạy chương trình
+------------------+     JDWP qua socket     +-----------------------------+
| giao diện debug  | <---------------------> | agent jdwp                  |
| đặt breakpoint,  |   "dừng ở Invoice:28"   |  dừng thread, đọc biến,     |
| hỏi giá trị biến |   "this.discountPercent"|  chạy biểu thức, chạy tiếp  |
+------------------+                         +-----------------------------+
```

Khi bạn bấm Debug, IDE thêm `-agentlib:jdwp=...` vào lệnh `java` rồi tự kết nối. Bạn cũng có thể khởi động JVM với agent trước, rồi gắn debugger vào sau. Đó là cách debug một service đang chạy ở chỗ khác. Ở Terminal thứ nhất:

<Terminal where="mac">

```bash
java -agentlib:jdwp=transport=dt_socket,server=y,suspend=y,address=localhost:5005 -cp out Main
```

</Terminal>

Kết quả:

```text
Listening for transport dt_socket at address: 5005
```

JVM mở cổng 5005 và đứng chờ, chưa chạy dòng nào của `main`, vì `suspend=y`. Với `suspend=n`, nó chạy luôn và debugger gắn vào lúc nào cũng được. `address=localhost:5005` chỉ nhận kết nối từ chính máy đó. Ở Terminal thứ hai, gắn `jdb` vào cổng đó:

<Terminal where="mac">

```bash
jdb -attach localhost:5005
```

</Terminal>

Phiên dưới đặt breakpoint, cho JVM chạy tiếp, tính một biểu thức, rồi bỏ breakpoint để chương trình chạy hết:

```text
Set uncaught java.lang.Throwable
Set deferred uncaught java.lang.Throwable
Initializing jdb ...

VM Started: > No frames on the current call stack

main[1] stop at Invoice:28
Deferring breakpoint Invoice:28.
It will be set after the class is loaded.
main[1] cont
> Set deferred breakpoint Invoice:28

Breakpoint hit: "thread=main", Invoice.discount(), line=28 bci=13

main[1] print discountPercent / 100

main[1] clear Invoice:28
Removed: breakpoint Invoice:28
main[1] cont
>

```

Breakpoint và giá trị in ra giống phiên `jdb` chạy chương trình trực tiếp. Output của chương trình (`subtotal=...`) in ở Terminal thứ nhất, nơi JVM chạy. Trong IntelliJ, cấu hình tương ứng là Remote JVM Debug; trong VS Code là một cấu hình `attach` trong `launch.json`. Với máy ở xa, chuyển tiếp cổng qua SSH tunnel thay vì mở cổng debug ra mạng.

Evaluate chạy được biểu thức Java bất kỳ, không chỉ đọc biến. Ở cùng chỗ dừng đó, `print java.lang.System.getProperty("java.version")` trả `"25.0.3"`, còn `print java.lang.System.exit(0)` tắt luôn JVM. Ai kết nối được tới cổng JDWP thì chạy được code tuỳ ý trong service của bạn, với mọi quyền của tiến trình đó.

Breakpoint còn một tác dụng phụ: nó làm thread dừng thật. IntelliJ mặc định dừng **mọi thread** khi chạm breakpoint (Suspend: All); bạn đổi được sang Suspend: Thread để các thread khác chạy tiếp. Với service đang nhận request, dừng mọi thread nghĩa là mọi request bị treo.

<Callout kind="production">

Một service trên staging (môi trường thử, giống production) chạy chậm bất thường. Ai đó bật JDWP, gắn IDE vào và đặt breakpoint. Mọi thread dừng, mọi request treo; health check (lời gọi định kỳ để hỏi service còn sống không) thất bại, và Kubernetes, hệ thống đang chạy service, khởi động lại nó giữa lúc đang debug. Vì vậy: không mở cổng JDWP trên production, chỉ nghe ở `localhost` trên môi trường thử, và trên production thì điều tra bằng log, metric, trace (SB8).

</Callout>

### Khi nào log tốt hơn debugger

Debugger không phải lúc nào cũng là công cụ đúng. Log, tức những dòng chương trình tự ghi ra trong lúc chạy, hợp hơn trong ba tình huống:

- Lỗi chỉ xuất hiện trên production, nơi bạn không được dừng service.
- Cần quan sát hàng nghìn sự kiện theo thời gian, ví dụ thứ tự xử lý của hàng nghìn đơn hàng.
- Việc dừng chương trình làm đổi hành vi: request bị timeout trong lúc bạn đang đọc biến, hoặc lỗi giữa nhiều thread (race condition) biến mất vì breakpoint làm đổi thứ tự chạy của các thread. J11 nói về cách điều tra loại lỗi này.

Ở giữa hai cách có breakpoint không dừng: nó in một biểu thức mỗi lần chạy qua rồi cho chương trình chạy tiếp, gần với `println` nhưng không phải sửa code. Trong IntelliJ, bỏ chọn Suspend và bật "Evaluate and log" trong cài đặt của breakpoint; VS Code gọi nó là Logpoint.

<Callout kind="ai">

Đưa AI đoạn code và output sai, nhờ nó liệt kê các giả thuyết, rồi dùng Evaluate kiểm từng giả thuyết. AI thường đoán đúng loại lỗi phổ biến như chia nguyên, nhưng cũng hay tự tin "sửa" chỗ không sai, hoặc sửa thêm nhiều dòng khác. Nó cũng hay đưa cấu hình debug từ xa nghe ở `*:5005` (mọi địa chỉ mạng) mà không cảnh báo. Chỉ nhận bản sửa khi bạn đã thấy giá trị sai trong debugger và chạy lại thấy output đúng.

</Callout>

<Callout kind="link">

J1.1 giải thích phép chia nguyên và việc JVM nạp class khi cần; J2 học kỹ các kiểu số. J1.3 đưa project hoá đơn đã sửa vào Git. J4 dùng khung Frames để đọc stack trace của exception. J8 biến kết quả mong đợi `discount=55000` thành test tự động để lỗi này không quay lại. J11 và SB8 dùng lại ý "không dừng production": điều tra bằng thread dump, log và trace.

</Callout>
