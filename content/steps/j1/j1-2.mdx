<Goal>

Dùng được một IDE để mở, chạy và điều hướng project Java, và dùng debugger để tìm nguyên nhân một kết quả sai. Học xong bài này, bạn giải thích được:

- Vì sao một phép tính tiền ra `0` dù code nhìn có vẻ đúng, và debugger chỉ ra chỗ đó trong vài giây ra sao.
- Vì sao một breakpoint đặt trong một method lại dừng nhiều lần hơn bạn nghĩ.
- Vì sao bật cổng debug trên server production là chuyện nguy hiểm.

</Goal>

<Knowledge>

### IDE làm được gì mà trình soạn thảo thường không làm

**IDE (Integrated Development Environment)** đọc toàn bộ project và dựng một chỉ mục (index) gồm mọi class, method, chỗ gọi. Nhờ đó nó biết `invoice.total()` trỏ tới method nào, nên làm được những việc mà tìm kiếm chữ không làm được: đi tới định nghĩa, tìm mọi nơi dùng, đổi tên ở mọi chỗ cùng lúc, chạy và debug.

| | IntelliJ IDEA | VS Code + Extension Pack for Java |
|---|---|---|
| Cài | Một ứng dụng, có sẵn hỗ trợ Java | Cài VS Code, rồi cài Extension Pack for Java của Microsoft |
| Thế mạnh | Hiểu Java và Spring rất sâu, refactor mạnh | Nhẹ, dùng chung cho nhiều ngôn ngữ |
| Phù hợp | Làm Java hằng ngày | Đã quen VS Code, project nhỏ hoặc nhiều ngôn ngữ |

Chọn một và dùng thành thạo. Phím tắt quan trọng hơn IDE nào. Bảng dưới là phím mặc định trên macOS:

| Việc | IntelliJ IDEA | VS Code |
|---|---|---|
| Tìm bất kỳ file, class | Nhấn ⇧ hai lần | ⌘P |
| Đi tới định nghĩa | ⌘B | F12 |
| Tìm mọi nơi dùng | ⌥F7 | ⇧⌥F12 |
| Đổi tên an toàn | ⇧F6 | F2 |
| Debug | ⌃D | F5 |
| Bật, tắt breakpoint | ⌘F8 | F9 |
| Step Over / Into / Out | F8 / F7 / ⇧F8 | F10 / F11 / ⇧F11 |
| Chạy tiếp (Resume) | ⌥⌘R | F5 |
| Evaluate | ⌥F8 | Gõ trong Debug Console |

<Check id="j1.2.ide-navigation">Trong IDE đã chọn, đi được tới định nghĩa của một method, tìm mọi nơi gọi nó và đổi tên nó bằng phím tắt.</Check>

### Debugger: dừng chương trình để nhìn vào bên trong

| Khái niệm | Ý nghĩa |
|---|---|
| Breakpoint | Điểm dừng ở một dòng. Thread chạy tới dòng đó thì dừng lại, trước khi dòng đó chạy |
| Conditional breakpoint | Breakpoint chỉ dừng khi một biểu thức, ví dụ `price > 200000`, đúng |
| Step Over | Chạy hết dòng hiện tại, kể cả các method nó gọi, rồi dừng ở dòng kế tiếp |
| Step Into | Đi vào bên trong method được gọi ở dòng hiện tại |
| Step Out | Chạy nốt method hiện tại, dừng lại ở chỗ đã gọi nó |
| Frames (Call Stack) | Chuỗi method đang gọi nhau, từ `main` tới chỗ đang dừng |
| Variables | Giá trị biến cục bộ và field của `this` tại chỗ đang dừng |
| Evaluate | Chạy một biểu thức Java bất kỳ trong ngữ cảnh đang dừng |

So với rải `System.out.println`, debugger không cần sửa code, không cần chạy lại cho mỗi câu hỏi mới, và cho bạn thử ngay một giả thuyết bằng Evaluate.

### Bên dưới, debugger nối với JVM thế nào

```text
 IDE hoặc jdb                                   JVM đang chạy chương trình
+------------------+     JDWP qua socket     +-----------------------------+
| giao diện debug  | <---------------------> | agent jdwp                  |
| đặt breakpoint,  |   "dừng ở Invoice:28"   |  dừng thread, đọc biến,     |
| hỏi giá trị biến |   "this.discountPercent"|  chạy biểu thức, chạy tiếp  |
+------------------+                         +-----------------------------+
```

- JVM được khởi động kèm agent **JDWP (Java Debug Wire Protocol)**. IDE làm việc này cho bạn khi bấm Debug; nó thêm tuỳ chọn `-agentlib:jdwp=...` vào lệnh `java`.
- IDE gửi lệnh qua JDWP: đặt breakpoint, dừng, đọc biến, chạy tiếp. `jdb` trong JDK dùng đúng giao thức đó, chỉ là không có giao diện đồ hoạ.
- Tên biến cục bộ chỉ có khi class được biên dịch với `javac -g`. IDE bật sẵn; khi tự dùng `javac` thì bạn phải thêm.

<Callout kind="production">

Một service trên staging chậm bất thường, ai đó bật JDWP rồi gắn IDE vào và đặt breakpoint. IntelliJ mặc định dừng **mọi thread** khi chạm breakpoint, nên toàn bộ request bị treo, health check thất bại và Kubernetes khởi động lại pod. Tệ hơn, ai kết nối được cổng JDWP thì chạy được code tuỳ ý trong JVM qua Evaluate. Vì vậy: không mở cổng JDWP trên production, chỉ nghe ở `localhost` trên môi trường thử, và trên production thì dựa vào log, metric, trace (SB8).

</Callout>

<Check id="j1.2.debugger-mechanism">Giải thích được debugger nói chuyện với JVM qua JDWP, và vì sao cổng debug là rủi ro bảo mật lẫn rủi ro treo service.</Check>

**Chuẩn bị:** đã làm bài J1.1 (có thư mục `~/masteva-j1` và JDK 25), đã cài IntelliJ IDEA hoặc VS Code kèm Extension Pack for Java. Lệnh terminal chạy giống nhau trên Mac và Linux; phần thao tác trong IDE là giao diện đồ hoạ, tên menu có thể lệch đôi chút giữa các phiên bản IDE.

### 1. Một chương trình có lỗi

Cửa hàng thêm quy tắc: đơn từ 500.000 đồng được giảm `discountPercent` phần trăm, VAT tính trên số tiền sau giảm. Thay hai file bằng phiên bản mới:

<Terminal where="mac" title="Thay src/Invoice.java và src/Main.java">

```bash
cd ~/masteva-j1
cat > src/Invoice.java <<'EOF'
import java.util.ArrayList;
import java.util.List;

public class Invoice {
    private final List<Long> prices = new ArrayList<>();
    private final int discountPercent;

    public Invoice(int discountPercent) {
        this.discountPercent = discountPercent;
    }

    public void add(long price) {
        prices.add(price);
    }

    public long subtotal() {
        long sum = 0;
        for (long price : prices) {
            sum += price;
        }
        return sum;
    }

    public long discount() {
        if (subtotal() < 500_000) {
            return 0;
        }
        return subtotal() * (discountPercent / 100);
    }

    public long vat() {
        return (subtotal() - discount()) * 10 / 100;
    }

    public long total() {
        return subtotal() - discount() + vat();
    }
}
EOF
cat > src/Main.java <<'EOF'
public class Main {
    public static void main(String[] args) {
        Invoice invoice = new Invoice(10);
        invoice.add(120_000);
        invoice.add(180_000);
        invoice.add(250_000);
        long total = invoice.total();
        System.out.println("subtotal=" + invoice.subtotal());
        System.out.println("discount=" + invoice.discount());
        System.out.println("total=" + total);
    }
}
EOF
java src/Main.java
```

</Terminal>

<Expected>

```text
subtotal=550000
discount=0
total=605000
```

</Expected>

Đơn 550.000 đồng, giảm 10% thì `discount` phải là `55000` và `total` là `544500`. Đừng sửa vội; hãy để debugger chỉ ra chỗ sai.

### 2. Mở project trong IDE

**IntelliJ IDEA:**

1. File → Open, chọn thư mục `~/masteva-j1`, chọn Trust Project.
2. Nếu IDE báo chưa có JDK, mở File → Project Structure → Project và chọn JDK 25 ở mục SDK.
3. Mở `src/Main.java`. Nếu lề trái cạnh `main` không có nút ▶ màu xanh, bấm chuột phải thư mục `src` → Mark Directory as → Sources Root.
4. Bấm ▶ → Run 'Main.main()'. Cửa sổ Run in đúng ba dòng như bước 1.

**VS Code:**

1. File → Open Folder, chọn `~/masteva-j1`. Cài Extension Pack for Java nếu VS Code gợi ý.
2. Nếu VS Code không thấy JDK, mở Command Palette (⇧⌘P) và chạy `Java: Configure Java Runtime`.
3. Mở `src/Main.java`. Phía trên `main` có dòng chữ `Run | Debug`. Nếu không có, bấm chuột phải thư mục `src` → Add Folder to Java Source Path.
4. Bấm `Run`. Tab Debug Console hoặc Terminal in ba dòng như bước 1.

Tập ngay phím tắt: đặt con trỏ vào `discount()` trong `Main.java`, nhảy tới định nghĩa, rồi tìm mọi nơi gọi nó.

<Callout kind="pitfall">

Trên Mac, phím F7, F8, F10… mặc định điều khiển độ sáng và âm lượng. Nhấn kèm `fn`, hoặc bật "Use F1, F2, etc. keys as standard function keys" trong System Settings → Keyboard.

</Callout>

### 3. Breakpoint, Frames và Evaluate

1. Trong `Invoice.java`, bấm vào lề trái dòng 28 (`return subtotal() * (discountPercent / 100);`). Một chấm đỏ hiện ra.
2. Chạy bằng Debug thay vì Run. Chương trình dừng ở dòng 28, dòng đó chưa chạy.
3. Ở khung Variables, mở `this`: `discountPercent` là `10`, `prices` có 3 phần tử.
4. Ở khung Frames (IntelliJ) hoặc Call Stack (VS Code), đọc chuỗi gọi: `discount` ← `total` ← `main`.
5. Mở Evaluate (IntelliJ: ⌥F8; VS Code: gõ vào Debug Console) và lần lượt thử `discountPercent / 100` rồi `subtotal() * discountPercent / 100`.

<Predict question="Hai biểu thức trên cho ra bao nhiêu?">

`discountPercent / 100` ra `0`: `10 / 100` là phép chia nguyên giữa hai `int`, phần thập phân bị bỏ, nên mọi thứ nhân với nó đều bằng 0. `subtotal() * discountPercent / 100` ra `55000`: phép nhân chạy trước, `550000 * 10 / 100` không mất gì. Bạn vừa tìm ra lỗi mà chưa sửa dòng nào.

</Predict>

Giờ bấm Resume (chạy tiếp) cho tới khi chương trình kết thúc, mỗi lần dừng thì nhìn lại Frames.

<Predict question="Breakpoint ở dòng 28 dừng bao nhiêu lần?">

Ba lần, với ba chuỗi gọi khác nhau:

1. `main` → `total()` → `discount()`.
2. `main` → `total()` → `vat()` → `discount()`.
3. `main` → `discount()`, ở dòng in `discount=`.

Một method có thể được gọi từ nhiều đường. Frames cho biết lần dừng này đến từ đường nào.

</Predict>

Cuối cùng, thử ba kiểu step: đặt breakpoint ở dòng 7 của `Main.java` (`long total = invoice.total();`), Debug lại, rồi Step Into để vào `total()`, Step Into lần nữa để vào `subtotal()`, Step Out để quay về `total()`, và Step Over để chạy hết dòng mà không đi vào method nào.

<Check id="j1.2.lab-breakpoint-step">Dừng được ở breakpoint, đọc giá trị trong Variables, đọc chuỗi gọi trong Frames và dùng đúng Step Into, Step Over, Step Out.</Check>

<Check id="j1.2.lab-evaluate">Dùng Evaluate chứng minh được `discountPercent / 100` bằng `0` trước khi sửa code.</Check>

### 4. Breakpoint có điều kiện

Xoá các breakpoint cũ. Đặt breakpoint ở dòng 19 (`sum += price;`), bấm chuột phải vào chấm đỏ và nhập điều kiện `price > 200000` (IntelliJ: ô Condition; VS Code: Edit Condition → Expression). Debug lại và đếm số lần dừng.

<Predict question="Mỗi lần dừng, price là 250000. Có bao nhiêu lần dừng?">

Chín lần. Mỗi lần `subtotal()` chạy, vòng lặp chỉ gặp một giá trị lớn hơn 200.000, nhưng `subtotal()` được gọi 9 lần: 6 lần trong `total()` (trực tiếp, qua `discount()` và qua `vat()`), 1 lần khi in `subtotal=`, 2 lần khi in `discount=`. Breakpoint có điều kiện vừa cho bạn thấy code tính đi tính lại cùng một tổng. Với 3 món thì không sao; với hoá đơn hàng nghìn dòng đọc từ database thì đó là vấn đề hiệu năng.

</Predict>

<Check id="j1.2.lab-conditional">Đặt được breakpoint có điều kiện và giải thích được vì sao nó dừng 9 lần.</Check>

### 5. Cùng lỗi đó, chỉ với jdb

Không phải lúc nào cũng có IDE, ví dụ khi SSH vào một máy Linux. `jdb` có sẵn trong JDK:

<Terminal where="mac">

```bash
cd ~/masteva-j1 && javac -g -d out src/*.java && jdb -classpath out Main
```

</Terminal>

Ở dấu nhắc `>` của jdb, gõ lần lượt `stop at Invoice:28`, `run`, `dump this`, `print discountPercent / 100`, `print subtotal() * discountPercent / 100`, `where`, rồi `exit`.

<Expected>

```text
> stop at Invoice:28
Deferring breakpoint Invoice:28.
It will be set after the class is loaded.
> run
...
Breakpoint hit: "thread=main", Invoice.discount(), line=28 bci=13

main[1] dump this
 this = {
    prices: instance of java.util.ArrayList(id=442)
    discountPercent: 10
}
main[1] print discountPercent / 100
 discountPercent / 100 = 0
main[1] print subtotal() * discountPercent / 100
 subtotal() * discountPercent / 100 = 55000
main[1] where
  [1] Invoice.discount (Invoice.java:28)
  [2] Invoice.total (Invoice.java:36)
  [3] Main.main (Main.java:7)
```

</Expected>

Phần `...` là vài dòng khởi động của jdb; số `id=442` khác nhau mỗi lần. Thử biên dịch lại không có `-g`, đặt breakpoint ở dòng 19 và gõ `locals`: jdb báo `Local variable information not available. Compile with -g to generate variable information`.

<Check id="j1.2.lab-jdb">Dùng `jdb` đặt breakpoint, in giá trị biểu thức và xem stack bằng `where`.</Check>

<DeepDive>

<Reveal title="Làm sao debug một service đang chạy trên máy khác?">

Khởi động JVM với `-agentlib:jdwp=transport=dt_socket,server=y,suspend=y,address=localhost:5005`. JVM in `Listening for transport dt_socket at address: 5005` và chờ, vì `suspend=y`. Rồi tạo cấu hình Remote JVM Debug trong IntelliJ, hoặc `attach` trong `launch.json` của VS Code, trỏ tới cổng 5005; `jdb -attach localhost:5005` cũng được. Với máy ở xa, dùng SSH tunnel thay vì mở cổng ra mạng.

</Reveal>

<Reveal title="Breakpoint dừng mọi thread hay chỉ một thread?">

Tuỳ cấu hình. IntelliJ mặc định dừng mọi thread (Suspend: All); bạn có thể đổi sang Thread để các thread khác chạy tiếp. Với code đa luồng, dừng mọi thread làm mất đúng thứ tự thời gian gây ra lỗi, nên lỗi race condition thường biến mất khi debug. J11 nói về cách điều tra loại lỗi này.

</Reveal>

<Reveal title="Khi nào println hoặc log vẫn tốt hơn debugger?">

Khi lỗi chỉ xuất hiện trên production, khi cần quan sát hàng nghìn sự kiện theo thời gian, hoặc khi việc dừng chương trình làm thay đổi hành vi (timeout, đa luồng). Lúc đó log có cấu trúc và trace hợp hơn. IntelliJ có breakpoint không dừng mà chỉ in log (bỏ chọn Suspend, bật "Evaluate and log"), gần với println nhưng không phải sửa code.

</Reveal>

<Callout kind="ai">

Đưa AI đoạn code và output sai, nhờ nó liệt kê các giả thuyết, rồi dùng Evaluate kiểm từng giả thuyết. AI thường đoán đúng loại lỗi phổ biến như chia nguyên, nhưng cũng hay tự tin "sửa" chỗ không sai, hoặc sửa thêm nhiều dòng khác. Chỉ nhận bản sửa khi bạn đã thấy giá trị sai trong debugger và chạy lại thấy output đúng.

</Callout>

<Callout kind="link">

Phép chia nguyên và ép kiểu được học kỹ ở J2. J8 biến kết quả mong đợi `discount=55000` thành test tự động để lỗi này không quay lại. J11 và SB8 dùng lại ý "không dừng production": điều tra bằng thread dump, log và trace.

</Callout>
