<Goal>

Hiểu JDK gồm những gì, chọn được bản phân phối và phiên bản phù hợp, và biết chuyện gì xảy ra từ lúc bạn gõ `javac` tới lúc chương trình in ra kết quả. Học xong bài này, bạn giải thích được:

- Vì sao ứng dụng chạy tốt trên máy bạn nhưng trên server báo `UnsupportedClassVersionError`, và hai con số trong thông báo lỗi nói gì.
- Vì sao build bằng `-source 21 -target 21` vẫn có thể chết trên Java 21, còn `--release 21` thì bắt lỗi ngay lúc biên dịch.
- Vì sao `java Main.java` chạy được mà không cần `javac`, và vì sao dự án thật vẫn cần build tool.
- Vì sao `99_999 * 10 / 100` trong Java ra `9999` chứ không phải `9999.9`.

</Goal>

<Knowledge>

Ví dụ trong chặng J1 là một hoá đơn bán hàng: cộng giá các món rồi tính VAT 10%. Tiền để ở kiểu `long`, đơn vị là đồng. Dấu `_` trong `120_000` chỉ giúp dễ đọc, trình biên dịch bỏ qua nó.

### JDK: bộ công cụ để viết và chạy Java

Bạn cài "Java" lên máy và thư mục `bin` của nó có vài chục lệnh. Hằng ngày bạn dùng khoảng bốn lệnh trong số đó, và cần biết lệnh nào làm việc gì trước khi đọc được bất kỳ thông báo lỗi nào.

**JDK (Java Development Kit)** là bộ công cụ để viết và chạy chương trình Java. Nó gồm ba phần:

| Thành phần | Vai trò |
|---|---|
| **JVM** (Java Virtual Machine) | Máy ảo chạy **bytecode**, dạng lệnh trung gian mà trình biên dịch Java sinh ra |
| Thư viện chuẩn | Các class có sẵn như `String`, `List`, `ArrayList` |
| Công cụ dòng lệnh | `javac`, `java`, `jshell` và các lệnh trong bảng dưới |

Các lệnh của JDK mà chặng J1 dùng:

| Lệnh | Việc nó làm | Bạn dùng khi |
|---|---|---|
| `javac` | Biên dịch file `.java` thành bytecode trong file `.class` | Build thủ công, hoặc gián tiếp qua Maven, Gradle (J7) |
| `java` | Khởi động JVM và chạy một class có method `main` | Chạy ứng dụng, chạy thẳng file nguồn |
| `jshell` | REPL (vòng đọc, chạy, in kết quả): gõ từng dòng Java và xem kết quả ngay | Thử một API, kiểm tra một phép tính |
| `javap` | Đọc file `.class`: phiên bản bytecode, method, lệnh bytecode | Kiểm tra class được build cho Java bản nào |
| `javadoc` | Sinh tài liệu HTML từ chú thích trong code | Bài J1.3 |
| `jdb` | Debugger dòng lệnh | Bài J1.2 |

Lệnh đầu tiên nên chạy trên một máy lạ là hỏi phiên bản của `java` và `javac`:

<Terminal where="mac">

```bash
java -version && javac -version
```

</Terminal>

Kết quả trên một máy cài Oracle JDK 25:

```text
java version "25.0.3" 2026-04-21 LTS
Java(TM) SE Runtime Environment (build 25.0.3+9-LTS-195)
Java HotSpot(TM) 64-Bit Server VM (build 25.0.3+9-LTS-195, mixed mode, sharing)
javac 25.0.3
```

Ba dòng đầu do `java` in, dòng cuối do `javac` in. `25` là phiên bản chính, `0.3` là bản vá; `LTS` cho biết đây là bản được hỗ trợ dài hạn (mục sau). Bản phân phối của hãng khác in tên khác ở dòng hai và dòng ba, nhưng con số phiên bản đọc theo cùng cách. Điều cần kiểm là `java` và `javac` cùng một phiên bản chính. Nếu Terminal báo `Unable to locate a Java Runtime` (Mac) hoặc `command not found` (Linux), máy chưa có JDK.

Máy chỉ chạy ứng dụng, như một image container trên production, không cần trình biên dịch. Gói chỉ có JVM và thư viện chuẩn gọi là **JRE** (Java Runtime Environment); nó không có `javac`. Một số bản phân phối, như Eclipse Temurin, phát hành cả gói JDK lẫn gói JRE.

### Từ file .java tới chương trình đang chạy

Bạn chạy `javac` xong và không thấy file nào chạy được như một ứng dụng thường. Lý do là `javac` không sinh mã máy cho Mac hay Linux: nó sinh bytecode, và chỉ JVM chạy được bytecode.

Project hoá đơn có hai file trong thư mục `src`. `Invoice.java` giữ giá các món và tính tiền:

```java norun
import java.util.ArrayList;
import java.util.List;

public class Invoice {
    private final List<Long> prices = new ArrayList<>();

    public void add(long price) {
        prices.add(price);
    }

    public long subtotal() {
        long sum = 0;
        for (long price : prices) {
            sum += price;
        }
        return sum;
    }

    public long vat() {
        return subtotal() * 10 / 100;
    }

    public long total() {
        return subtotal() + vat();
    }
}
```

Cú pháp Java (kiểu `long`, `List`, vòng `for`) được học kỹ từ J2; ở bài này, điều cần nắm là `Invoice` cộng giá các món và tính VAT. `Main.java` tạo một hoá đơn hai món và in kết quả. Đây là cách viết `main` truyền thống; mục "Hai cách viết main" ở cuối bài giới thiệu cách viết ngắn hơn của Java 25.

```java norun
public class Main {
    public static void main(String[] args) {
        Invoice invoice = new Invoice();
        invoice.add(120_000);
        invoice.add(180_000);
        System.out.println("subtotal=" + invoice.subtotal());
        System.out.println("vat=" + invoice.vat());
        System.out.println("total=" + invoice.total());
    }
}
```

Lệnh dưới, chạy ở thư mục project, biên dịch cả hai file vào thư mục `out`, liệt kê `out`, rồi chạy class `Main`:

<Terminal where="mac">

```bash
javac -d out src/*.java && ls out && java -cp out Main
```

</Terminal>

Kết quả:

```text
Invoice.class
Main.class
subtotal=300000
vat=30000
total=330000
```

Hai dòng đầu do `ls` in: mỗi class thành một file `.class`. Ba dòng sau là output của chương trình: 120.000 + 180.000 = 300.000, VAT 10% là 30.000. `-d out` gom các file `.class` vào `out` thay vì để lẫn với mã nguồn. `-cp out` là **classpath**: danh sách thư mục (hoặc file `.jar`) mà JVM tìm class trong đó. Đối số cuối là tên class, `Main`, không phải tên file.

Sau khi `java` nhận tên class, JVM làm tiếp bốn việc:

```text
src/Main.java, src/Invoice.java      mã nguồn, bạn viết
        |
        |  javac -d out src/*.java
        v
out/Main.class, out/Invoice.class    bytecode, giống nhau trên Mac, Linux, Windows
        |
        |  java -cp out Main
        v
JVM: nạp class -> kiểm tra bytecode -> thông dịch -> JIT dịch đoạn chạy nhiều thành mã máy
```

JVM nạp `Main.class` từ classpath, và nạp `Invoice.class` khi code cần tới nó lần đầu. Trước khi chạy, nó kiểm tra bytecode có hợp lệ không, để một file `.class` hỏng hay bị sửa tay không làm sập máy ảo. Lúc đầu JVM thông dịch từng lệnh bytecode. **JIT** (Just-In-Time compiler) theo dõi đoạn code chạy nhiều lần và dịch nó thành mã máy ngay lúc đang chạy. Vì vậy ứng dụng Java thường chậm ở những request đầu tiên rồi nhanh dần; J12 đo hiện tượng này.

Vì `java` nhận tên class chứ không nhận tên file, hai lỗi sau rất hay gặp. Lệnh thứ nhất ghi thêm đuôi `.class`, lệnh thứ hai quên `-cp`:

<Terminal where="mac">

```bash
java -cp out Main.class
java Main
```

</Terminal>

Kết quả:

```text
Error: Could not find or load main class Main.class
Caused by: java.lang.ClassNotFoundException: Main.class
Error: Could not find or load main class Main
Caused by: java.lang.ClassNotFoundException: Main
```

Ở lệnh đầu, JVM coi cả chuỗi `Main.class` là tên class cần tìm, và không có class nào tên như vậy. Ở lệnh sau, không có `-cp` nên classpath mặc định là thư mục hiện tại, nơi chỉ có `src` và `out` chứ không có `Main.class`. Gặp `ClassNotFoundException` khi khởi động, hãy kiểm tra hai điều: tên class có đúng không, và classpath có trỏ tới thư mục chứa file `.class` không.

### Phiên bản bytecode và UnsupportedClassVersionError

Ứng dụng chạy tốt trên máy bạn, nhưng lên server thì chết ngay khi khởi động với `UnsupportedClassVersionError`. Code không đổi một dòng nào; thứ khác nhau là phiên bản Java ở hai nơi.

Mỗi file `.class` ghi **major version** của bytecode. JVM chỉ chạy bytecode có major version bằng hoặc thấp hơn phiên bản của chính nó:

| Java | 8 | 11 | 17 | 21 | 25 |
|---|---|---|---|---|---|
| Major version | 52 | 55 | 61 | 65 | 69 |

`javap -v` in toàn bộ thông tin của một file `.class`; `grep major` giữ lại đúng dòng phiên bản. Dòng thứ hai build lại vào thư mục `out21` với `--release 21` rồi đọc phiên bản của bản mới:

<Terminal where="mac">

```bash
javap -v out/Main.class | grep major
javac --release 21 -d out21 src/*.java && javap -v out21/Main.class | grep major
```

</Terminal>

<Predict question="Hai dòng major version khác nhau thế nào?">

```text
  major version: 69
  major version: 65
```

`javac` của JDK 25 mặc định sinh bytecode cho Java 25 (69). `--release 21` bảo nó sinh bytecode cho Java 21 (65).

</Predict>

Đưa bytecode 69 cho JVM 21 thì thấy đúng lỗi của server. `/usr/libexec/java_home -v 21` là lệnh của macOS in đường dẫn tới JDK 21 (mục sau giải thích), nên lệnh dưới chạy `java` của JDK 21 thay cho JDK mặc định:

<Terminal where="mac">

```bash
"$(/usr/libexec/java_home -v 21)/bin/java" -cp out Main
```

</Terminal>

Kết quả:

```text
Error: LinkageError occurred while loading main class Main
	java.lang.UnsupportedClassVersionError: Main has been compiled by a more recent version of the Java Runtime (class file version 69.0), this version of the Java Runtime only recognizes class file versions up to 65.0
```

Đọc lỗi theo hai con số: class được build với version 69 (Java 25), còn JVM này chỉ hiểu tới 65 (Java 21). Đổi `out` thành `out21` thì cùng JVM 21 chạy chương trình bình thường và in ba dòng như ở mục trước.

<Callout kind="production">

CI build ứng dụng bằng JDK 25, nhưng Dockerfile chạy bằng image JRE 21. Container khởi động là chết ngay với dòng `class file version 69.0 ... only recognizes class file versions up to 65.0`, rồi Kubernetes khởi động lại nó liên tục. Cách sửa là dùng cùng phiên bản Java cho build và runtime, hoặc build với `--release 21` nếu buộc phải chạy trên 21.

</Callout>

`javac` còn một cách cũ để nhắm phiên bản: `-source 21 -target 21`. Nhiều hướng dẫn trên mạng vẫn dùng nó, và nhìn qua thì nó làm cùng việc với `--release 21`. Hai cách khác nhau ở thư viện chuẩn. Class dưới gọi `IO.println`, method của class `IO`, class chỉ có từ Java 25:

```java
public class Report {
    public static void main(String[] args) {
        long subtotal = 300_000;
        IO.println("total=" + (subtotal + subtotal * 10 / 100));
    }
}
```

Lệnh dưới biên dịch class này bằng `-source 21 -target 21`, rồi chạy kết quả trên JVM 21:

<Terminal where="mac">

```bash
javac -source 21 -target 21 -d out Report.java
"$(/usr/libexec/java_home -v 21)/bin/java" -cp out Report
```

</Terminal>

Kết quả:

```text
warning: [options] location of system modules is not set in conjunction with -source 21
  not setting the location of system modules may lead to class files that cannot run on JDK 21
    --release 21 is recommended instead of -source 21 -target 21 because it sets the location of system modules automatically
1 warning
Exception in thread "main" java.lang.NoClassDefFoundError: java/lang/IO
	at Report.main(Report.java:4)
Caused by: java.lang.ClassNotFoundException: java.lang.IO
	at java.base/jdk.internal.loader.BuiltinClassLoader.loadClass(BuiltinClassLoader.java:641)
	at java.base/jdk.internal.loader.ClassLoaders$AppClassLoader.loadClass(ClassLoaders.java:188)
	at java.base/java.lang.ClassLoader.loadClass(ClassLoader.java:526)
	... 1 more
```

Thử tự trả lời trước khi đọc tiếp: vì sao `javac` biên dịch thành công một class dùng `IO`, trong khi đã được bảo nhắm Java 21?

`-source 21` chỉ giới hạn cú pháp được phép, `-target 21` chỉ đặt major version 65. Cả hai không đổi thư viện chuẩn mà `javac` dùng để kiểm tra code: đó vẫn là thư viện của JDK 25, nơi có `IO`. Biên dịch qua, lỗi chỉ lộ ra khi chạy trên Java 21, có khi sau nhiều ngày ở production. `javac` có in cảnh báo và gợi ý `--release`, nhưng cảnh báo rất dễ bị bỏ qua trong log build. Cùng file đó với `--release 21`:

<Terminal where="mac">

```bash
javac --release 21 -d out Report.java
```

</Terminal>

Kết quả:

```text
Report.java:4: error: cannot find symbol
        IO.println("total=" + (subtotal + subtotal * 10 / 100));
        ^
  symbol:   variable IO
  location: class Report
1 error
```

`--release 21` kiểm tra code với đúng API của Java 21, nên lỗi lộ ra ngay lúc biên dịch, trên máy bạn. Khi cần build cho một phiên bản cũ hơn JDK đang dùng, luôn dùng `--release`. Maven và Gradle có tuỳ chọn tương ứng (J7).

### Bản phân phối, LTS và nhiều JDK trên một máy

Trang tải Java của mỗi hãng có hàng chục lựa chọn: Oracle, Temurin, Corretto, phiên bản 21, 25, 27. Chọn sai thì vài tháng sau bạn phải nâng cấp gấp vì hết bản vá bảo mật.

Mã nguồn của Java nằm ở dự án **OpenJDK**. Nhiều hãng lấy cùng mã nguồn đó, build, kiểm thử và phát hành bản của mình, gọi là **bản phân phối** (distribution). Các bản này chạy code của bạn như nhau; chúng khác ở giấy phép, lịch phát hành bản vá và hỗ trợ trả phí.

| Bản phân phối | Ai phát hành | Ghi chú |
|---|---|---|
| Eclipse Temurin | Eclipse Adoptium | Miễn phí, phổ biến để cài trên máy và trong image Docker |
| Oracle JDK | Oracle | Điều khoản giấy phép thay đổi theo từng phiên bản; đọc kỹ trước khi dùng cho production |
| Amazon Corretto | Amazon | Hay gặp trên AWS |
| Microsoft Build of OpenJDK | Microsoft | Hay gặp trên Azure |

Phiên bản là chuyện khác với bản phân phối. Java ra một phiên bản mới mỗi 6 tháng, vào tháng 3 và tháng 9. Cứ hai năm có một bản **LTS** (Long-Term Support), được vá lỗi và bảo mật trong nhiều năm; bản không phải LTS chỉ được vá tới khi bản kế tiếp ra. Theo [Oracle Java SE Support Roadmap](https://www.oracle.com/java/technologies/java-se-support-roadmap.html):

| Phiên bản | Loại | Phát hành | Oracle hỗ trợ Premier tới |
|---|---|---|---|
| 21 | LTS | 9/2023 | 9/2028 |
| 25 | LTS | 9/2025 | 9/2030 |
| 26, 27 | Không LTS | 3/2026, 9/2026 | 9/2026, 3/2027 |
| 29 | LTS, theo kế hoạch | 9/2027 | 9/2032 |

Với dự án mới, chọn **21 hoặc 25**. Các bài trong Masteva dùng JDK 25. Các hãng khác công bố lịch hỗ trợ riêng trên trang của họ, thường bám theo các bản LTS.

Một máy có thể cài nhiều JDK cùng lúc, và đây là nguồn gốc của nhiều lỗi "máy tôi chạy được". Trên macOS, `/usr/libexec/java_home -V` liệt kê mọi JDK đã cài; `-v 25` in đường dẫn tới JDK 25:

<Terminal where="mac">

```bash
/usr/libexec/java_home -V; /usr/libexec/java_home -v 25
```

</Terminal>

Kết quả trên một máy có bốn JDK; danh sách trên máy bạn sẽ khác:

```text
Matching Java Virtual Machines (4):
    25.0.3 (arm64) "Oracle Corporation" - "Java SE 25.0.3" /Library/Java/JavaVirtualMachines/jdk-25.jdk/Contents/Home
    21.0.3 (arm64) "Oracle Corporation" - "Java SE 21.0.3" /Library/Java/JavaVirtualMachines/jdk-21.jdk/Contents/Home
    19.0.2 (arm64) "Oracle Corporation" - "Java SE 19.0.2" /Library/Java/JavaVirtualMachines/jdk-19.jdk/Contents/Home
    17.0.2 (x86_64) "Oracle Corporation" - "Java SE 17.0.2" /Library/Java/JavaVirtualMachines/jdk-17.0.2.jdk/Contents/Home
/Library/Java/JavaVirtualMachines/jdk-25.jdk/Contents/Home
```

`-V` in danh sách rồi in đường dẫn của JDK mặc định; dòng cuối cùng do `-v 25` in. Đường dẫn đó là giá trị nên đặt cho biến môi trường **`JAVA_HOME`**: Maven, Gradle và IDE đọc biến này để biết dùng JDK nào. Trên macOS, lệnh `/usr/bin/java` có sẵn của hệ điều hành cũng chạy JDK mà `JAVA_HOME` trỏ tới. Lệnh dưới đặt `JAVA_HOME` về JDK 21 cho riêng một lần chạy:

<Terminal where="mac">

```bash
JAVA_HOME=$(/usr/libexec/java_home -v 21) /usr/bin/java -version
```

</Terminal>

Kết quả:

```text
java version "21.0.3" 2024-04-16 LTS
Java(TM) SE Runtime Environment (build 21.0.3+7-LTS-152)
Java HotSpot(TM) 64-Bit Server VM (build 21.0.3+7-LTS-152, mixed mode, sharing)
```

Cùng một lệnh `java`, đổi `JAVA_HOME` là đổi JDK. Để cố định JDK 25 cho mọi Terminal, thêm dòng `export JAVA_HOME=$(/usr/libexec/java_home -v 25)` vào `~/.zshrc` rồi mở lại Terminal. Trên Linux không có `java_home`; bạn đặt `JAVA_HOME` bằng đường dẫn cài JDK và đưa `$JAVA_HOME/bin` lên đầu `PATH`, danh sách thư mục mà shell tìm lệnh trong đó. Khi `java -version` và `javac -version` báo hai phiên bản khác nhau, `PATH` đang trỏ lẫn lộn giữa hai JDK, và đây là chỗ cần sửa.

Nếu máy chưa có JDK 21 hoặc 25, trên Mac có thể cài Temurin 25 bằng Homebrew:

<Terminal where="mac">

```bash
brew install --cask temurin@25
```

</Terminal>

Thêm `--dry-run` vào lệnh trên để xem Homebrew sẽ cài gì mà chưa cài thật. Cách khác là tải bộ cài `.pkg` từ trang Temurin, hoặc dùng [SDKMAN](https://sdkman.io/), công cụ quản lý nhiều JDK chạy được cả trên Mac lẫn Linux.

<Callout kind="pitfall">

`brew install --cask temurin`, không có `@25`, cài bản mới nhất hiện có (27), không phải bản LTS. Luôn ghi rõ phiên bản khi cài JDK.

</Callout>

### Chạy thẳng file nguồn

Với một chương trình nhỏ, gọi `javac` rồi `java` với `-d`, `-cp` là hơi nhiều bước. Từ Java 11, `java` nhận thẳng một file `.java`:

<Terminal where="mac">

```bash
java src/Main.java
```

</Terminal>

Kết quả:

```text
subtotal=300000
vat=30000
total=330000
```

Đây là **chế độ chạy từ mã nguồn** (source-file mode): `java` biên dịch file trong bộ nhớ rồi chạy ngay, không ghi file `.class` nào ra đĩa ([JEP 330](https://openjdk.org/jeps/330)). `Main.java` dùng class `Invoice` nằm ở file khác, vậy mà lệnh vẫn chạy. Từ Java 22 ([JEP 458](https://openjdk.org/jeps/458)), khi chương trình cần một class chưa biên dịch, `java` tìm file nguồn của class đó trong cùng thư mục và biên dịch nó.

<Predict question="Cùng lệnh java src/Main.java, chạy bằng JDK 21 thì sao?">

```text
src/Main.java:3: error: cannot find symbol
        Invoice invoice = new Invoice();
        ^
  symbol:   class Invoice
  location: class Main
src/Main.java:3: error: cannot find symbol
        Invoice invoice = new Invoice();
                              ^
  symbol:   class Invoice
  location: class Main
2 errors
error: compilation failed
```

JDK 21 chỉ biên dịch đúng một file bạn đưa vào, nên không biết `Invoice` là gì. Một nội dung, hai kết quả, chỉ vì phiên bản JDK: thêm một lý do để kiểm tra `java -version` trước tiên.

</Predict>

Chế độ này hợp với script, ví dụ và bài tập, nhưng không thay được `javac` hay build tool trong dự án thật:

- Nó biên dịch lại toàn bộ mỗi lần bạn gọi `java`, và không để lại file `.class` hay `.jar` nào để giao cho server.
- Nó không tải và quản lý thư viện bên ngoài, không chạy test, không đóng gói.

Dự án có nhiều package và thư viện dùng Maven hoặc Gradle, học ở J7.

### Hai cách viết main

Các bài sau trong Masteva viết chương trình bằng `void main()` và `IO.println`, trong khi code ở hầu hết dự án hiện tại viết `public static void main(String[] args)` và `System.out.println`. Bạn cần đọc được cả hai.

Từ Java 25 ([JEP 512](https://openjdk.org/jeps/512)), một file nguồn có thể chỉ gồm method và field, không cần khai báo class. File như vậy gọi là **compact source file**: Java tự bọc nội dung vào một class ngầm, và `main` không cần `public`, `static` hay tham số. Class `IO` (cũng từ Java 25) có `IO.println` để in một dòng. Đoạn sau là một chương trình hoàn chỉnh:

```java
void main() {
    long subtotal = 300_000;
    IO.println("total=" + (subtotal + subtotal * 10 / 100));
}
```

Kết quả:

```text
total=330000
```

Cùng chương trình, viết theo cách truyền thống:

```java
public class Main {
    public static void main(String[] args) {
        long subtotal = 300_000;
        System.out.println("total=" + (subtotal + subtotal * 10 / 100));
    }
}
```

Kết quả:

```text
total=330000
```

Hai chương trình in cùng một dòng. Compact source file còn tự import mọi package của module `java.base`, nên các bài sau dùng `List`, `ArrayList`, `Map` mà không cần dòng `import`. Cách viết này dành cho chương trình nhỏ và người mới học; class trong một dự án nhiều file vẫn khai báo đầy đủ. Đây cũng là tính năng của Java 25: chạy file `void main()` ở trên bằng JDK 21 thì `java` báo `unnamed classes are a preview feature and are disabled by default`.

### jshell: thử code trong vài giây

Bạn muốn biết `99_999 * 10 / 100` ra bao nhiêu, hoặc một method của `String` trả gì. Tạo file, viết `main`, biên dịch rồi chạy cho một phép tính là quá nhiều việc.

**jshell** là REPL của Java: bạn gõ một biểu thức, jshell in kết quả ngay, không cần class hay `main`. Mở nó bằng lệnh `jshell`, gõ từng dòng sau dấu nhắc `jshell>`, và thoát bằng `/exit`. Phiên dưới tính ba biểu thức rồi gọi `/vars`:

<Terminal where="mac">

```bash
jshell
```

</Terminal>

<Predict question="99_999 * 10 / 100 cho ra bao nhiêu? Còn 99_999 * 10 / 100.0?">

```text
jshell> 2 + 3 * 4
$1 ==> 14

jshell> 99_999 * 10 / 100
$2 ==> 9999

jshell> 99_999 * 10 / 100.0
$3 ==> 9999.9

jshell> /vars
|    int $1 = 14
|    int $2 = 9999
|    double $3 = 9999.9
```

`99_999 * 10 / 100` ra `9999`, không phải `9999.9`.

</Predict>

Khi cả hai toán hạng là số nguyên, `/` là **phép chia nguyên**: phần thập phân bị bỏ, không làm tròn. Khi một trong hai toán hạng là số thực, như `100.0`, phép chia thành phép chia số thực và giữ phần thập phân. `vat()` của `Invoice` dùng đúng phép chia nguyên này, nên VAT của món 99.999 đồng là 9.999 đồng, không phải 10.000. Với tiền, làm tròn xuống, làm tròn gần nhất hay dùng `BigDecimal` là quyết định nghiệp vụ; đừng để nó xảy ra tình cờ. J2 học kỹ các kiểu số và phép chia.

Biểu thức không gán vào biến nào được jshell đặt tên tự động là `$1`, `$2`, và cứ thế tăng dần. Lệnh của chính jshell bắt đầu bằng `/`: `/vars` liệt kê biến cùng kiểu của chúng, `/open` nạp một file nguồn, `/exit` thoát. Nhờ `/open`, bạn thử được class của chính project mà không cần `main`. Phiên dưới mở jshell ở thư mục project, nạp `Invoice.java` rồi gọi method của nó. `var inv = ...` khai báo biến `inv` và để Java tự suy ra kiểu từ vế phải; J2 học kỹ `var`.

```text varies
jshell> /open src/Invoice.java

jshell> var inv = new Invoice()
inv ==> Invoice@439f5b3d

jshell> inv.add(99_999)

jshell> inv.vat()
$6 ==> 9999
```

`/open` và `inv.add(...)` không in gì: `add` trả `void`. `Invoice@439f5b3d` là cách mặc định Java in một đối tượng: tên class, `@`, rồi mã băm; số sau `@` trên máy bạn sẽ khác. `inv.vat()` mang tên `$6` vì jshell đánh số cả những gì `/open` nạp vào (hai dòng `import`, class `Invoice`) và lệnh `inv.add(...)`.

AI hay đưa lệnh cũ như `brew cask install`, gói `openjdk@11`, nói sai bản nào là LTS, hoặc khuyên `-source` và `-target` thay cho `--release`. Code AI viết cũng có thể dùng API mới hơn JDK mà server của bạn chạy. Kiểm tra lại bằng `java -version`, `javap -v ... | grep major`, build với `--release` đúng phiên bản server, và trang Support Roadmap của Oracle.

</Callout>
