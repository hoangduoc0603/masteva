<Goal>

<Knowledge>

### Hai cách tích hợp: GitFlow và trunk-based

Vấn đề gốc của làm việc nhóm với Git không phải lệnh, mà là **bao lâu thì code của mỗi người gặp nhau**. Nhánh càng sống lâu, khác biệt với nhánh chính càng lớn, merge càng đau và lỗi tích hợp càng lộ muộn.

**GitFlow** (Vincent Driessen, 2010) dùng nhiều nhánh sống lâu, mỗi loại một vai trò:

```text
 main     ●───────────────────●─────────────●        chỉ chứa bản đã phát hành (tag)
           \                 / \           /
 hotfix     \               /   ●─────────●          sửa gấp từ main, merge về main và develop
             \             /
 release      \       ●───●                          ổn định bản sắp phát hành, chỉ sửa lỗi
               \     /     \
 develop  ●─────●───●───────●───●──────●             nhánh tích hợp hằng ngày
           \       /             \    /
 feature    ●─●─●─●               ●──●               mỗi tính năng một nhánh, có thể sống nhiều tuần
```

**Trunk-based development**: mọi người tích hợp vào một nhánh chính (trunk, ở đây là `main`) **ít nhất mỗi ngày một lần**. Nhánh, nếu có, chỉ sống vài giờ tới một hai ngày, đủ để mở pull request và review. Phần việc chưa xong vẫn được merge, nhưng ẩn sau **feature flag** (cờ bật tắt tính năng lúc chạy) để không ảnh hưởng người dùng. Phát hành bằng cách gắn tag trên trunk, hoặc cắt nhánh release từ trunk chỉ để vá; bản vá luôn vào trunk trước rồi `cherry-pick` sang.

```text
 main   ●──●──●──●──●──●──●──●──●──●──●──●──●    mỗi ● là một PR nhỏ đã review, CI xanh
         \_/   \_/    \__/  \_/      \_/          nhánh sống vài giờ
                  tag v1.4       tag v1.5         phát hành từ main
```

| | GitFlow | Trunk-based |
|---|---|---|
| Nhánh sống lâu | `main`, `develop`, release, hotfix, feature nhiều tuần | Chỉ `main` (và nhánh release ngắn hạn nếu cần) |
| Thời điểm phát hiện lỗi tích hợp | Khi merge feature vào develop, hay ở giai đoạn release | Trong ngày, ở mỗi PR |
| Code chưa xong | Nằm trên nhánh feature | Nằm trên `main`, tắt bằng feature flag |
| Đòi hỏi | Ít đòi hỏi tự động hoá | CI nhanh và đáng tin, test tốt, review nhanh, feature flag |
| Hợp với | Phần mềm có phiên bản rõ ràng, phải duy trì nhiều phiên bản song song (thư viện, ứng dụng cài tại chỗ) | Dịch vụ web triển khai liên tục |

DORA (chương trình nghiên cứu về hiệu quả giao hàng phần mềm, nay thuộc Google Cloud) coi trunk-based là điều kiện bắt buộc của continuous integration. Dữ liệu khảo sát 2016–2017 của họ cho thấy các đội có **không quá ba nhánh đang hoạt động**, **merge vào trunk ít nhất mỗi ngày** và **không có giai đoạn đóng băng code** đạt hiệu quả giao hàng và vận hành cao hơn (tốc độ, độ ổn định, độ sẵn sàng). Lý do cơ học: thay đổi nhỏ thì review kỹ được, lỗi dễ tìm, rollback rẻ. Chính tác giả GitFlow, trong ghi chú thêm vào bài gốc năm 2020, khuyên đội làm continuous delivery dùng quy trình đơn giản hơn và chỉ giữ GitFlow cho phần mềm có phiên bản rõ ràng.

Trunk-based không có nghĩa là push thẳng lên `main`. Ở hầu hết đội, mỗi thay đổi vẫn đi qua một **pull request ngắn** có CI và review; điểm khác là nó nhỏ và được merge trong ngày. D7 đo các chỉ số DORA trên chính quy trình này.

<Check id="d4.2.trunk-vs-gitflow">So sánh được GitFlow với trunk-based theo nhánh sống lâu, thời điểm lộ lỗi tích hợp và cách xử lý code chưa xong, và nói được ba ngưỡng DORA dùng để mô tả trunk-based.</Check>

### Pull request: hàng rào nằm ở máy chủ

Pull request (GitHub, Gitea) hay merge request (GitLab) là đề nghị "gộp nhánh này vào nhánh kia", kèm chỗ thảo luận, review và kết quả CI. Nhưng PR chỉ là hàng rào thật khi máy chủ **bắt buộc** đi qua nó. Hàng rào đó là **branch protection** (bảo vệ nhánh), kiểm ở phía server lúc nhận push (pre-receive hook) và lúc merge:

```text
 git push origin main ───▶ máy chủ Git: pre-receive hook
                             ├─ nhánh main được bảo vệ, push trực tiếp bị cấm ──▶ từ chối
                             └─ (nhánh khác) nhận

 Merge PR ───▶ máy chủ kiểm:
                 ├─ đủ số approval chưa (approval cũ đã bị huỷ thì không tính)
                 ├─ có reviewer nào đang "request changes" không
                 ├─ code owner của file bị sửa đã approve chưa
                 ├─ CI (status check) bắt buộc đã xanh chưa
                 └─ nhánh có conflict không
               tất cả qua ──▶ merge theo kiểu đã chọn ──▶ main có commit mới
```

Các thiết lập đáng bật cho nhánh chính, và lý do:

| Thiết lập (tên trong Gitea) | Chặn chuyện gì |
|---|---|
| Không cho push trực tiếp (`enable_push: false`) | Code vào `main` không qua review |
| Không cho force push (mặc định khi bảo vệ) | Viết lại lịch sử chung, vụ Jenkins ở D4.1 |
| Số approval tối thiểu (`required_approvals`) | Tác giả tự merge. Gitea và GitHub không cho tác giả approve PR của mình; trên GitLab đó là thiết lập "Prevent approval by merge request creator", bật mặc định nhưng tắt được |
| Không cho admin ghi đè khi merge (`block_admin_merge_override`) | Admin của repo dùng "force merge" để bỏ qua các điều kiện trên. Mặc định Gitea **cho phép** việc này |
| Huỷ approval khi có commit mới (`dismiss_stale_approvals`) | Lén thêm code sau khi đã được approve |
| Chặn khi có review "request changes" (`block_on_rejected_reviews`) | Merge khi reviewer còn phản đối |
| Bắt buộc code owner approve (`block_on_codeowner_reviews`) | Sửa phần nhạy cảm mà người hiểu nó không được hỏi |
| Bắt buộc status check (`enable_status_check`) | Merge khi CI đỏ; chặng D6 nối CI vào |

**CODEOWNERS** là file ánh xạ đường dẫn tới người hoặc nhóm chịu trách nhiệm. Khi PR sửa file khớp một dòng, máy chủ tự yêu cầu những người đó review, và nếu bật thiết lập tương ứng thì PR chỉ merge được khi họ approve. Hợp để đặt quanh phần có rủi ro cao: migration database, cấu hình CI, mã thanh toán, phân quyền.

<Check id="d4.2.branch-protection">Giải thích được branch protection kiểm ở đâu và lúc nào, chọn được các thiết lập cho nhánh chính và nói được mỗi thiết lập chặn chuyện gì.</Check>

### Kiểu merge của pull request

| Kiểu | Kết quả trên `main` | Đánh đổi |
|---|---|---|
| Merge commit | Giữ mọi commit của nhánh và thêm một merge commit | Lịch sử đầy đủ nhưng rối nếu nhánh có nhiều commit "sửa" |
| Squash | Một commit duy nhất, message lấy từ tiêu đề PR | Gọn, mỗi PR một commit dễ revert; mất các commit nhỏ bên trong. Tiêu đề PR phải đúng với nội dung cuối. Commit squash là commit mới, nên Git không coi nhánh cũ là "đã merge": `git branch -d` từ chối xoá nó (bước 11) |
| Rebase | Áp lại từng commit lên `main`, không có merge commit | Thẳng và giữ từng commit; mỗi commit phải tự đứng được (D4.1) |
| Fast-forward only | Chỉ dời con trỏ, từ chối nếu nhánh chưa cập nhật | Hash trên `main` giống hệt hash đã review; tác giả phải rebase trước |

Đội trunk-based hay chọn squash cho PR nhỏ: một PR, một commit, một dòng trong `git log --first-parent`.

### Review có trọng tâm

Review tốt bắt đầu từ PR tốt. Tài liệu review công khai của Google khuyên thay đổi nhỏ (khoảng 100 dòng là hợp lý, 1000 dòng thường là quá lớn), mỗi PR một ý, mô tả nói "vì sao", và reviewer trả lời trong một ngày làm việc. Danh sách kiểm tra gọn cho reviewer:

| Câu hỏi | Ví dụ điều cần tìm |
|---|---|
| Thay đổi có làm đúng điều mô tả nói không | Đọc mô tả trước, rồi đọc diff để đối chiếu |
| Có test cho hành vi mới hoặc lỗi vừa sửa không | Test có thể thất bại nếu code sai, không chỉ chạy cho có |
| Trường hợp biên | Đơn 0 đồng, đúng ngưỡng 500.000, input rỗng, timeout |
| Bảo mật | Secret trong diff, quyền mở rộng, input chưa kiểm, log lộ dữ liệu cá nhân |
| Vận hành | Có metric hay log để biết nó chạy, có cách tắt (feature flag) hay rollback; migration có đảo ngược được không |
| Dễ đọc | Tên rõ, không lặp, comment giải thích "vì sao" chứ không tả lại code |

Phần còn lại (format, lint, test chạy được) nên để máy kiểm trong CI, để con người tập trung vào thứ máy không thấy. Review là thảo luận về code, không phải về người: nói "hàm này nhận số âm thì trả gì" thay vì "bạn quên kiểm số âm".

<Callout kind="production">

Ngày 29/03/2024, Andres Freund (kỹ sư Microsoft, một người phát triển PostgreSQL) công bố trên danh sách oss-security rằng thư viện nén `xz` bản 5.6.0 và 5.6.1 chứa backdoor nhắm vào `sshd` trên một số bản Linux (CVE-2024-3094). Người cài nó là một maintainer đã đóng góp nghiêm túc hơn hai năm để được tin tưởng. Payload giấu trong các file nhị phân "dữ liệu test" mà không ai review từng byte, và đoạn kích hoạt chỉ có trong tarball phát hành, không có trong Git. Review và bảo vệ nhánh chỉ che được những gì đi qua pull request. Bài học thực dụng cho đội của bạn: đặt CODEOWNERS cho script build, cấu hình CI và file nhị phân; không phát hành artifact build tay ngoài pipeline; và chặng D14 sẽ ràng artifact với đúng commit đã review.

</Callout>

<Check id="d4.2.review">Viết được mô tả PR nói rõ "vì sao", và dùng được danh sách kiểm tra để review một PR, tách phần để máy kiểm khỏi phần cần con người.</Check>

### GitHub và GitLab: thiết lập tương đương

Lab dùng Gitea tự host để không cần tài khoản thật. Mọi khái niệm chuyển thẳng sang GitHub hay GitLab, khác ở tên gọi và ở gói dịch vụ:

| Khái niệm | Gitea 28 | GitHub | GitLab |
|---|---|---|---|
| Tên | Pull request | Pull request | Merge request (MR) |
| Bảo vệ nhánh | Branch protection rule | Branch protection rule hoặc ruleset | Protected branch (Settings → Repository → Branch rules) |
| Bắt buộc approval | `required_approvals` | "Require approvals" | Approval rules; bản **Free** chỉ có approval tuỳ chọn, không chặn merge. Bắt buộc cần Premium |
| Huỷ approval khi có commit mới | `dismiss_stale_approvals` | "Dismiss stale pull request approvals when new commits are pushed" | "Remove all approvals when commits are added" (Premium) |
| CODEOWNERS | `CODEOWNERS`, `docs/CODEOWNERS` hoặc `.gitea/CODEOWNERS`; **mẫu là regexp của Go** | `.github/`, gốc repo hoặc `docs/`; mẫu kiểu `.gitignore` | `CODEOWNERS` ở gốc, `docs/` hoặc `.gitlab/`; tính năng của **Premium** |
| Mẫu mô tả PR | `.gitea/PULL_REQUEST_TEMPLATE.md` | `.github/pull_request_template.md` | `.gitlab/merge_request_templates/*.md` |
| CLI | `tea` | `gh pr create`, `gh pr review`, `gh pr merge` | `glab mr create`, `glab mr approve`, `glab mr merge` |
| Gói | Tự host, miễn phí, giấy phép MIT | Bảo vệ nhánh cho repo **private** cần Pro, Team hoặc Enterprise; repo public dùng gói Free được | Free có protected branch; approval bắt buộc và CODEOWNERS cần Premium |

Ở Việt Nam, nhiều công ty tự host GitLab CE (bản Free) nên hay gặp đúng giới hạn trên: có protected branch nhưng approval không chặn merge; đội bù bằng quy ước "chỉ maintainer được merge" (cấu hình "Allowed to merge") và CI bắt buộc. **Forgejo** là bản fork của Gitea do tổ chức phi lợi nhuận Codeberg e.V. điều hành, API gần như tương đương. Lab dùng Gitea 28; các lệnh API dưới đây chỉ chạy thử với Gitea, dùng Forgejo có thể phải chỉnh.

<Check id="d4.2.github-gitlab">Ánh xạ được từng thiết lập của lab sang GitHub hoặc GitLab, và chỉ ra được thiết lập nào trên GitLab cần gói Premium.</Check>

### 1. Chạy Gitea

Chạy Gitea trong một container, chờ tới khi nó trả lời health check, rồi hỏi phiên bản:

<Terminal where="mac">

```bash
cd ~/masteva-d4 && . ./env.sh
docker run -d --name d4-gitea -p 9500:3000 \
  -e GITEA__security__INSTALL_LOCK=true \
  -e GITEA__server__ROOT_URL=http://localhost:9500/ \
  -e GITEA__database__DB_TYPE=sqlite3 \
  -e GITEA__service__DISABLE_REGISTRATION=true \
  -v d4-gitea-data:/data gitea/gitea:28.1.0
until curl -sf localhost:9500/api/healthz >/dev/null; do sleep 1; done
curl -s localhost:9500/api/v1/version; echo
```

</Terminal>

<Expected>

```text
2dd0f02dc527299c511dd7f25ff4d2cd5085a87a4cdeb1aa0d8242e19a568f2c
{"version":"28.1.0"}
```

</Expected>

Mã container trên máy bạn sẽ khác. Các biến `GITEA__<mục>__<khoá>` ghi thẳng vào `app.ini`: `INSTALL_LOCK=true` bỏ qua trang cài đặt trên web, `DISABLE_REGISTRATION=true` không cho tự đăng ký tài khoản. Dữ liệu (SQLite, repo) nằm trong volume `d4-gitea-data`. Vòng `until` chờ tới khi Gitea trả lời health check, thường 3–5 giây.

### 2. Tạo người dùng và token

Tạo hai tài khoản bằng CLI `gitea admin` bên trong container, sinh cho mỗi người một token ghi vào `gitea.env`, rồi viết `lab.sh` chứa vài hàm gọi API cho gọn. Lệnh cuối hỏi Gitea "token này là ai" để kiểm tra token của an dùng được:

<Terminal where="mac" title="~/masteva-d4/gitea.env và lab.sh">

```bash
for u in an binh; do
  docker exec -u git d4-gitea gitea admin user create --username $u \
    --email $u@example.com --random-password --must-change-password=false | tail -1
done
{
  echo "AN_TOKEN=$(docker exec -u git d4-gitea gitea admin user generate-access-token \
    -u an -t lab --scopes write:repository,write:user --raw)"
  echo "BINH_TOKEN=$(docker exec -u git d4-gitea gitea admin user generate-access-token \
    -u binh -t lab --scopes write:repository,read:user --raw)"
} > gitea.env
chmod 600 gitea.env
cat > lab.sh <<'EOF'
. "$HOME/masteva-d4/gitea.env"
G=http://localhost:9500/api/v1
api_an()   { curl -s -H "Authorization: token $AN_TOKEN" -H 'Content-Type: application/json' "$@"; }
api_binh() { curl -s -H "Authorization: token $BINH_TOKEN" -H 'Content-Type: application/json' "$@"; }
an_git()   { git -c http.extraHeader="Authorization: token $AN_TOKEN" "$@"; }
EOF
. ./lab.sh
api_an $G/user | jq -c '{login, is_admin}'
```

</Terminal>

<Expected>


### Khi gặp lỗi

<Callout kind="pitfall">

- **`Bind for 0.0.0.0:9500 failed: port is already allocated`:** cổng đang bận. Xem bằng `docker ps` và `lsof -i :9500`, hoặc đổi `-p 9501:3000` cùng `ROOT_URL`.
- **`token does not have at least one of required scope(s), required=[write:user]`** khi tạo repo: token của an thiếu `write:user`. Tạo token mới với tên khác (`-t lab2`) và sửa `gitea.env`.
- **`fatal: could not read Username for 'http://localhost:9500'`:** gọi `git push` hay `git fetch` thường thay vì `an_git`, nên Git không có token. Repo private đòi xác thực cả khi đọc.
- **`requested_reviewers` rỗng:** CODEOWNERS chưa có trên `main` lúc mở PR (Gitea đọc file ở nhánh đích), hoặc mẫu regexp không khớp **trọn** đường dẫn: Gitea bọc mẫu trong `^…$`, nên `ship\\.py` không khớp `src/ship.py`; viết `.*/ship\\.py` hoặc `src/.*`.
- **Bước 10 vẫn merge được:** chạy API merge trước khi Gitea xử lý xong push. Đọc lại danh sách review; nếu approval chưa `dismissed`, chờ vài giây.

</Callout>

Không, nếu code mới nằm sau feature flag tắt mặc định. Đơn giản nhất là một biến cấu hình; phức tạp hơn là dịch vụ flag cho phép bật theo phần trăm người dùng hay theo nhóm. Cái giá: flag là nợ kỹ thuật, phải xoá khi tính năng đã bật cho mọi người, và test phải chạy được với cả hai trạng thái. Với thay đổi lớn không bọc flag được (đổi thư viện nền, đổi schema), dùng "branch by abstraction": thêm lớp trừu tượng, chuyển dần từng chỗ gọi sang cách mới qua nhiều PR nhỏ, cuối cùng xoá cách cũ.

</Reveal>

<Reveal title="Đội chỉ có hai người. Bắt buộc approval có làm chậm không?">

Có, nếu người kia hay vắng. Hai cách cân bằng: giữ approval bắt buộc nhưng cam kết review trong vài giờ và giữ PR nhỏ; hoặc cho phép merge không cần approval với thay đổi rủi ro thấp (tài liệu) qua danh sách file không bảo vệ (Gitea có `unprotected_file_patterns`) và giữ CODEOWNERS cho phần rủi ro cao. Không nên tắt hẳn bảo vệ: chặn push thẳng và force push gần như không tốn gì mà chặn được tai nạn lớn nhất.

</Reveal>

<Reveal title="Squash merge làm mất lịch sử commit nhỏ. Khi nào nên dùng rebase merge thay vì squash?">

Khi PR gồm vài commit mà mỗi commit tự đứng được và có giá trị khi đọc lại riêng, ví dụ "đổi tên hàm" tách khỏi "đổi logic", hoặc một migration tách khỏi code dùng nó. Rebase merge giữ chúng trên `main`, `git bisect` chỉ ra được đúng bước. Điều kiện là tác giả đã dọn lịch sử như D4.1; nếu nhánh còn `wip` và `fixup`, squash an toàn hơn.

</Reveal>

<Reveal title="Branch protection chặn được người trong đội làm sai. Nó có chặn được kẻ tấn công lấy được token của admin không?">

Thường là không đủ. Admin có thể sửa hoặc xoá chính quy tắc bảo vệ, và token có quyền rộng có thể làm như vậy qua API. Phòng thủ nằm ở chỗ khác: token có phạm vi hẹp và có hạn dùng, xác thực hai lớp cho tài khoản admin, nhật ký kiểm toán (audit log) cảnh báo khi quy tắc bảo vệ bị đổi, và Gitea, GitHub đều có tuỳ chọn áp quy tắc cả với admin (`block_admin_merge_override` trên Gitea, "Do not allow bypassing the above settings" trên GitHub). Vụ Trivy năm 2026 ở D5.2 bắt đầu đúng từ một token có quyền cao bị lộ.

</Reveal>

<Callout kind="ai">

Nhờ AI review sơ bộ một diff (tìm trường hợp biên, test còn thiếu, secret lộ) hay viết mô tả PR từ danh sách commit là cách dùng tốt. AI hay sai ở chỗ: khen chung chung thay vì chỉ ra dòng cụ thể, bỏ qua hành vi của code ngoài diff (hàm bị gọi ở chỗ khác), và nhầm cú pháp CODEOWNERS giữa GitHub (glob) với Gitea (regexp). Đối chiếu từng nhận xét của AI với code thật, coi nó là một reviewer thêm chứ không thay approval của người hiểu hệ thống, và kiểm lại cấu hình bảo vệ nhánh bằng API như bước 5 thay vì tin lời mô tả.

</Callout>
