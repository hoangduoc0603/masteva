<Goal>

Hiểu Git lưu dữ liệu thế nào để mọi lệnh hằng ngày (`merge`, `rebase`, `reset`, `push --force`) không còn là phép màu, và để lịch sử của project kể được câu chuyện rõ ràng. Học xong bài này, bạn giải thích được:

- Vì sao rebase một nhánh làm mọi commit trên đó đổi mã hash, dù nội dung không đổi một dòng.
- Vì sao `git merge` lúc thì chỉ "Fast-forward", lúc lại tạo thêm một commit có hai cha.
- Vì sao trong lúc rebase, phần "của mình" trong conflict lại nằm ở dưới, và `--ours` trỏ sang nhánh kia.
- Vì sao commit "biến mất" sau rebase, reset hay force push gần như luôn cứu được, và khi nào thì không.

</Goal>

<Knowledge>

### Git lưu gì: blob, tree, commit

Git là một kho **đối tượng (object)** đánh địa chỉ theo nội dung: mỗi đối tượng được nén, lưu dưới tên là mã hash SHA-1 của chính nội dung đó. Cùng nội dung thì cùng hash, ở mọi máy. Có bốn loại đối tượng, ba loại đầu là đủ để hiểu bài này:

| Đối tượng | Chứa gì | Ví dụ trong lab |
|---|---|---|
| **blob** | Nội dung một file, không có tên file | `3ae30ca` là nội dung `app.py` |
| **tree** | Danh sách mục: quyền, loại, hash, tên. Mục có thể là blob (file) hoặc tree con (thư mục) | `05b06cd` liệt kê `README.md` và `app.py` |
| **commit** | Hash của một tree gốc, hash của commit cha (0, 1 hay nhiều), tác giả, thời điểm, message | `cdd7780` |
| tag (annotated) | Trỏ tới một đối tượng khác, kèm người tạo, message, có thể ký | Dùng khi phát hành phiên bản |

```text
 commit cdd7780 ──tree──▶ tree 05b06cd
   author, date            ├── 100644 blob a00621b  README.md
   message                 └── 100644 blob 3ae30ca  app.py

 commit f5b9643 ──tree──▶ tree (mới) ──▶ blob mới của app.py
   parent cdd7780                    └─▶ blob a00621b  README.md  (dùng lại, không chép)
```

Hai hệ quả quan trọng:

- **Commit là ảnh chụp (snapshot), không phải diff.** Mỗi commit trỏ tới toàn bộ cây thư mục. File không đổi thì tree mới trỏ lại blob cũ, nên không tốn thêm chỗ. Diff mà `git show` in ra được tính lúc xem, bằng cách so hai tree.
- **Hash của commit phụ thuộc vào mọi thứ bên trong nó**, kể cả hash của cha và thời điểm commit. Đổi cha (rebase), đổi message (amend) hay đổi giờ thì ra commit mới với hash mới; commit cũ vẫn nằm nguyên trong kho.

Hash mặc định là SHA-1 (40 ký tự hex). Git hỗ trợ repo dùng SHA-256 (`git init --object-format=sha256`), nhưng phần lớn repo và dịch vụ hosting hiện vẫn dùng SHA-1; mọi khái niệm trong bài giữ nguyên.

<Check id="d4.1.object-model">Giải thích được blob, tree, commit chứa gì, và vì sao đổi cha hay đổi message thì commit có hash mới.</Check>

### Ref, branch, HEAD

Không ai nhớ được hash, nên Git có **ref**: một cái tên trỏ tới một hash.

| Ref | Lưu ở đâu | Ý nghĩa |
|---|---|---|
| Branch `main` | `.git/refs/heads/main` (hoặc dồn vào `.git/packed-refs`) | File một dòng chứa hash của commit mới nhất trên nhánh. Commit mới thì Git ghi đè dòng đó |
| `HEAD` | `.git/HEAD` | Thường là `ref: refs/heads/main`, tức "đang đứng ở nhánh main". Khi trỏ thẳng vào một hash thì gọi là **detached HEAD** |
| Remote-tracking `origin/main` | `.git/refs/remotes/origin/main` | Vị trí của `main` trên remote ở lần `fetch` gần nhất |
| Tag `v1.0.0` | `.git/refs/tags/v1.0.0` | Tên cố định cho một commit, theo quy ước không di chuyển |

Branch chỉ là một con trỏ 41 byte. Tạo nhánh là ghi một file, xoá nhánh là xoá file đó; commit vẫn còn trong kho. "Mất commit" trong Git hầu như luôn là **mất con trỏ**, không phải mất dữ liệu.

Tag cũng chỉ là ref. "Không di chuyển" là quy ước chứ không phải ràng buộc kỹ thuật: ai có quyền push đều có thể `git push --force` để tag trỏ sang commit khác. Đây là lý do pipeline nên ghim action, image theo hash hoặc digest thay vì theo tag; D5.2 kể một vụ tấn công chuỗi cung ứng năm 2026 đi đúng đường này.

<Check id="d4.1.refs">Giải thích được branch, `HEAD`, detached HEAD và tag là gì ở mức file trong `.git`, và vì sao tag không bất biến.</Check>

### Merge: fast-forward và 3-way

`git merge feature` gộp nhánh `feature` vào nhánh đang đứng. Git chọn một trong hai cách, tuỳ hình dạng lịch sử:

```text
 Fast-forward: main chưa có commit nào mới kể từ khi tách nhánh
   trước:  A ── B            main               sau:  A ── B ── C   main, feature
                 \
                  C          feature
   Git chỉ dời con trỏ main tới C. Không có commit mới.

 3-way merge: cả hai nhánh đều có commit mới
   trước:  A ── B ── D       main               sau:  A ── B ── D ── M   main
                 \                                         \        /
                  C          feature                         C ─────     feature
   Git tìm merge base (B), so B→D và B→C, gộp hai thay đổi,
   rồi tạo commit M có HAI cha: D và C.
```

**Merge base** là tổ tiên chung gần nhất (`git merge-base main feature`). "3-way" nghĩa là Git so ba phiên bản: base, bên mình, bên kia. Một dòng chỉ đổi ở một bên thì lấy bên đã đổi; đổi ở cả hai bên theo hai cách khác nhau thì là **conflict**. Từ Git 2.34, thuật toán mặc định là `ort`.

`git merge --no-ff` buộc tạo merge commit ngay cả khi fast-forward được, để lịch sử giữ dấu "nhánh này từng tồn tại". `git merge --ff-only` làm ngược lại: chỉ chịu fast-forward, từ chối nếu phải tạo merge commit.

<Check id="d4.1.merge">Phân biệt được fast-forward với 3-way merge, nói được merge base là gì và khi nào một dòng bị conflict.</Check>

### Conflict

Khi conflict, Git dừng giữa chừng, ghi file với **dấu xung đột** và chờ bạn quyết định. Với `merge.conflictStyle=zdiff3` (từ Git 2.35), file có thêm phần base ở giữa, giúp thấy mỗi bên đã đổi gì so với gốc:

```text
<<<<<<< HEAD                     bên đang đứng (khi merge: nhánh của bạn)
    return round(amount * (1 + VAT), -2)
||||||| 73a8b3b                  base: dòng đó trước khi hai bên sửa
    return round(amount * (1 + VAT))
=======
    return round((amount - discount) * (1 + VAT))
>>>>>>> feature/discount         bên được merge vào
```

So với base, bên trên thêm làm tròn, bên dưới thêm giảm giá. Bản đúng thường là **gộp cả hai ý**, không phải chọn một bên. Quy trình:

1. Sửa file cho đúng, xoá hết dấu `<<<<<<<`, `|||||||`, `=======`, `>>>>>>>`.
2. Chạy test hoặc ít nhất chạy thử đoạn code vừa gộp.
3. `git add <file>` để đánh dấu đã giải quyết, rồi `git commit` (khi merge) hoặc `git rebase --continue` (khi rebase).

Muốn bỏ ngang: `git merge --abort` hoặc `git rebase --abort` đưa mọi thứ về như trước lệnh.

<Check id="d4.1.conflict">Đọc được ba phần của dấu xung đột kiểu zdiff3 và gộp được hai thay đổi thay vì chọn một bên.</Check>

### Rebase

`git rebase main` (đứng ở `feature`) lấy từng commit của `feature` mà `main` chưa có, rồi **áp lại** lần lượt lên đỉnh `main`:

```text
 trước:  A ── B ── D          main
               \
                C1 ── C2      feature

 git switch feature && git rebase main
   1. Tìm các commit của feature không có trong main: C1, C2
   2. Đứng tạm ở D (detached HEAD)
   3. Áp diff của C1 lên D  -> commit mới C1' (cha là D, hash khác C1)
   4. Áp diff của C2 lên C1' -> C2'
   5. Dời nhánh feature tới C2'; ghi vị trí cũ (C2) vào ORIG_HEAD và reflog

 sau:    A ── B ── D          main
                    \
                     C1' ── C2'   feature        (C1, C2 vẫn nằm trong kho)
```

Kết quả là lịch sử thẳng, như thể bạn bắt đầu làm việc từ `D`. Sau đó `git merge --ff-only feature` trên `main` chỉ việc dời con trỏ.

**Bên "ours" và "theirs" bị đảo khi rebase.** Ở bước 2 Git đứng trên `main` rồi áp commit của bạn lên, nên trong dấu xung đột, `HEAD` (phía trên) là `main` cộng các commit đã áp, còn commit của bạn nằm phía dưới. `git checkout --ours file` khi rebase lấy bản của `main`, ngược với khi merge. Đọc dòng `>>>>>>> c7ba90e (...)` để biết phần nào là của mình.

| | Merge | Rebase |
|---|---|---|
| Lịch sử | Giữ đúng như đã xảy ra, có merge commit | Thẳng, như thể làm tuần tự |
| Hash commit cũ | Giữ nguyên | Đổi hết, commit cũ bị bỏ lại |
| Conflict | Giải một lần cho cả nhánh | Có thể phải giải ở từng commit được áp |
| An toàn với commit đã chia sẻ | An toàn | **Không**: người khác đã có commit cũ, sau đó lịch sử của hai bên lệch nhau |
| Push sau khi làm | `git push` bình thường | Phải `git push --force-with-lease` nếu nhánh đã từng push |

Quy tắc vàng: **chỉ rebase commit chưa ai khác dùng**, thường là nhánh cá nhân chưa merge. Không bao giờ rebase `main` đã chia sẻ. Khi phải ghi đè nhánh đã push (sau rebase nhánh của chính mình), dùng `--force-with-lease`: Git chỉ ghi đè nếu nhánh trên remote vẫn ở vị trí bạn thấy lần cuối, nên không xoá mất commit người khác vừa đẩy lên.

### Lịch sử sạch: commit nhỏ, message tốt

Lịch sử Git là tài liệu bạn đọc lúc có sự cố: `git log` để biết thay đổi nào vào lúc nào, `git blame` để biết vì sao dòng này tồn tại, `git bisect` để tìm commit gây lỗi, `git revert` để gỡ một thay đổi. Cả bốn chỉ hữu ích khi mỗi commit là **một thay đổi trọn vẹn, có lý do rõ**.

| Thói quen | Vì sao |
|---|---|
| Mỗi commit một ý, build và test vẫn qua | `bisect` dừng ở commit nào cũng chạy được; `revert` gỡ đúng một ý mà không kéo theo thứ khác |
| Tách đổi tên, format code khỏi đổi logic | Reviewer thấy được thay đổi thật thay vì 500 dòng đổi khoảng trắng |
| Dòng đầu message ngắn (khoảng 50, tối đa 72 ký tự), dạng mệnh lệnh: "Thêm…", "Sửa…" | Hiện gọn trong `git log --oneline` và tiêu đề pull request |
| Dòng trống, rồi phần thân nói **vì sao** và ảnh hưởng | Diff đã cho biết "cái gì"; "vì sao" thì chỉ người viết biết |
| Không để lại `wip`, `fix`, `sửa lại` trong lịch sử của nhánh chính | Mười commit "sửa" là nhiễu khi đọc lại sau sáu tháng |

Một số đội dùng quy ước **Conventional Commits** (`feat:`, `fix:`, `chore:`…) để công cụ tự sinh changelog và tự tăng số phiên bản. Hữu ích khi có công cụ dùng tới nó; nếu không, một dòng đầu rõ nghĩa quan trọng hơn tiền tố.

Bạn không cần commit hoàn hảo ngay từ đầu. Cứ commit thường xuyên khi làm, rồi **dọn trước khi mở pull request** bằng `git rebase -i` (interactive): Git mở một danh sách việc (todo list), mỗi dòng một commit, bạn đổi chữ đầu dòng để nói làm gì với nó:

| Lệnh | Tác dụng |
|---|---|
| `pick` | Giữ commit như cũ |
| `reword` | Giữ thay đổi, sửa message |
| `squash` | Gộp vào commit phía trên, nối hai message để sửa |
| `fixup` | Gộp vào commit phía trên, **bỏ** message của commit này |
| `drop` | Bỏ hẳn commit |
| `edit` | Dừng lại ở commit này để sửa (tách đôi, thêm file) |
| `exec <lệnh>` | Chạy lệnh shell sau commit phía trên, ví dụ chạy test; lệnh lỗi thì rebase dừng |

Đổi thứ tự dòng là đổi thứ tự commit. Hai công cụ làm việc này gần như tự động:

- `git commit --fixup=<hash>` tạo commit có message `fixup! <tiêu đề commit đích>`.
- `git rebase -i --autosquash` tự dời các commit `fixup!` xuống ngay dưới commit đích và đổi `pick` thành `fixup`.

Git mở todo list bằng trình soạn thảo trong biến `GIT_SEQUENCE_EDITOR` (mặc định là editor thường của bạn). Gán cho nó một lệnh hay một script là chạy được `rebase -i` không cần mở editor; lab làm đúng như vậy, và CI hay script tự động cũng dùng cách này.

<Check id="d4.1.clean-history">Kể được ít nhất bốn thói quen giữ lịch sử sạch, và dùng được `--fixup`, `--autosquash` cùng các lệnh `pick`, `fixup`, `squash`, `reword` của `rebase -i`.</Check>

### reflog: lưới an toàn

Mỗi lần một ref đổi vị trí trên **máy bạn** (commit, checkout, merge, rebase, reset, pull), Git ghi một dòng vào **reflog**: vị trí cũ, vị trí mới, lý do. Có reflog cho `HEAD` và cho từng branch.

```text
 git reflog                         git reflog show feature/free-ship
 0570ac9 HEAD@{0}: merge ...        0570ac9 feature/free-ship@{0}: rebase (finish) ...
 9ddedf5 HEAD@{1}: checkout ...     5b6df92 feature/free-ship@{1}: commit: wip      <- trước rebase
 ...                                ...
 Cú pháp tham chiếu: HEAD@{1} = vị trí của HEAD một bước trước; main@{2.days.ago} cũng được.
```

Vì commit không bị xoá ngay khi mất ref, gần như mọi thao tác "lỡ tay" đều đảo được: tìm dòng reflog trước sự cố, tạo branch trỏ vào đó (`git branch cuu-ho <hash>`) hoặc dời branch hiện tại về đó.

Giới hạn của lưới an toàn:

- reflog **chỉ có ở máy cục bộ**, không đi theo `push` hay `clone`. Commit mà bạn chưa từng có trên máy (người khác đẩy rồi bị force push đè) thì reflog của bạn không cứu được.
- Mặc định mục reflog sống 90 ngày, mục trỏ tới commit không còn branch nào với tới được sống 30 ngày (`gc.reflogExpire`, `gc.reflogExpireUnreachable`). Sau đó `git gc` có thể dọn hẳn đối tượng.
- reflog trả lại **commit**, không trả lại thay đổi chưa commit. `git reset --hard` và `git checkout -- file` ghi đè thay đổi chưa `git add` ở những file Git đang theo dõi, và phần đó mất vĩnh viễn. File chưa theo dõi (untracked) thì `reset --hard` không đụng tới; chúng chỉ mất khi bạn `git clean`. Nội dung đã `git add` nhưng chưa commit vẫn là một blob trong kho, tìm lại được bằng `git fsck --lost-found`.
- `ORIG_HEAD` là lối tắt: sau `merge`, `rebase`, `reset`, nó trỏ tới vị trí trước lệnh.

<Check id="d4.1.reflog">Giải thích được reflog ghi gì, cứu được commit mất sau rebase hay detached HEAD, và nói được ba trường hợp reflog không cứu được.</Check>

### 6. Dọn lịch sử bằng rebase -i không tương tác

Làm nhánh miễn phí ship theo kiểu thật ngoài đời: commit tính năng (có lỗi gõ nhầm 50.000 thay vì 500.000), commit test, rồi phát hiện lỗi, rồi thêm test với message `wip`.

<Terminal where="mac">

```bash
git switch -q -c feature/free-ship
cat > ship.py <<'EOF'
FREE_SHIP_FROM = 50000


def ship_fee(weight_kg, order_total=0):
    if order_total >= FREE_SHIP_FROM:
        return 0
    return 15000 if weight_kg <= 1 else 15000 + 5000 * (weight_kg - 1)
EOF
git commit -q -am "Miễn phí ship cho đơn từ 500.000 đồng"
cat > test_ship.py <<'EOF'
from ship import ship_fee


def test_free_ship():
    assert ship_fee(2, order_total=500000) == 0
EOF
git add test_ship.py && git commit -q -m "Thêm test cho miễn phí ship"
perl -pi -e 's/= 50000$/= 500000/' ship.py
git commit -q -a --fixup=HEAD~1
cat >> test_ship.py <<'EOF'


def test_paid_ship():
    assert ship_fee(2, order_total=100000) == 20000
EOF
git commit -q -am "wip"
git log --oneline main..HEAD
```

</Terminal>

<Expected>

```text

6373e46 fixup! Miễn phí ship cho đơn từ 500.000 đồng
260f0f3 Thêm test cho miễn phí ship

```

</Expected>

`--fixup=HEAD~1` tạo commit đánh dấu "sửa cho commit tính năng" (`HEAD~1` là commit trước `HEAD`). `main..HEAD` nghĩa là "các commit có ở `HEAD` mà `main` chưa có". Bốn commit, hai trong số đó không nên vào `main`.

Viết một "editor" cho todo list: script nhận đường dẫn file todo, đổi `pick ... wip` thành `fixup`, rồi in todo list cuối cùng để bạn thấy Git sẽ làm gì:

<Terminal where="mac" title="~/masteva-d4/squash-wip.sh">

```bash
cat > ../squash-wip.sh <<'EOF'
#!/bin/sh
# Git gọi script này với một tham số: đường dẫn file todo của rebase -i.
perl -pi -e 's/^pick (\w+) wip$/fixup $1 wip/' "$1"
grep -v -e '^#' -e '^$' "$1"
EOF
chmod +x ../squash-wip.sh
GIT_SEQUENCE_EDITOR=../squash-wip.sh git rebase -i --autosquash main
git log --oneline main..HEAD
```

</Terminal>


</Expected>

```bash
git switch -q main && git merge -q --ff-only feature/free-ship
git log --oneline -3
```

</Terminal>

<Expected>


### 7. Cứu commit bằng reflog

**Tình huống 1:** sau khi dọn, bạn muốn xem lại đúng bốn commit cũ (ví dụ reviewer hỏi "commit fixup đã sửa gì"). Chúng không còn trên nhánh nào, nhưng reflog của nhánh vẫn nhớ:

<Terminal where="mac">

```bash
git reflog show feature/free-ship
git branch free-ship-truoc-rebase 'feature/free-ship@{1}'
git log --oneline main..free-ship-truoc-rebase
```

</Terminal>

<Expected>

```text
0570ac9 feature/free-ship@{0}: rebase (finish): refs/heads/feature/free-ship onto 9ddedf5e1ce632568214282c1426797d00c244fe
5b6df92 feature/free-ship@{1}: commit: wip
6373e46 feature/free-ship@{2}: commit: fixup! Miễn phí ship cho đơn từ 500.000 đồng
260f0f3 feature/free-ship@{3}: commit: Thêm test cho miễn phí ship
8780ce0 feature/free-ship@{4}: commit: Miễn phí ship cho đơn từ 500.000 đồng
9ddedf5 feature/free-ship@{5}: branch: Created from HEAD
5b6df92 wip
6373e46 fixup! Miễn phí ship cho đơn từ 500.000 đồng
260f0f3 Thêm test cho miễn phí ship
8780ce0 Miễn phí ship cho đơn từ 500.000 đồng
```

</Expected>

`feature/free-ship@{1}` là vị trí của nhánh một bước trước, tức ngay trước rebase. Dấu nháy đơn giữ nguyên chuỗi có `{}` khi qua shell; với `HEAD^{tree}` ở bước 1, zsh bật `extendedglob` sẽ báo lỗi nếu thiếu nháy.

**Tình huống 2:** thử nghiệm nhanh ở detached HEAD, commit, rồi quay về `main` mà quên tạo nhánh:

<Terminal where="mac">

```bash
git switch -q --detach HEAD~2
printf 'def tax_free(amount):\n    return amount\n' > tax.py
git add tax.py && git commit -q -m "Thử bỏ thuế cho đơn nội bộ"
git switch main
```

</Terminal>

<Expected>

```text

any of your branches:

  d4fd8da Thử bỏ thuế cho đơn nội bộ

to do so with:

 git branch <new-branch-name> d4fd8da

```

</Expected>

Git đã cảnh báo, nhưng giả sử bạn không đọc. Commit `d4fd8da` không thuộc nhánh nào, `git log --all` không thấy nó. Reflog của `HEAD` vẫn có:

<Terminal where="mac">

```bash
git reflog -3
git branch experiment/tax-free 'HEAD@{1}'
git log --oneline -1 experiment/tax-free
```

</Terminal>

<Expected>

```text
0570ac9 HEAD@{0}: checkout: moving from d4fd8dad6a3cca7ac68d2bca7bcdd2ffe6aeb902 to main
d4fd8da HEAD@{1}: commit: Thử bỏ thuế cho đơn nội bộ
9ddedf5 HEAD@{2}: checkout: moving from main to HEAD~2
d4fd8da Thử bỏ thuế cho đơn nội bộ
```

</Expected>

**Tình huống 3:** lùi nhánh nhầm một commit. `git reset --keep HEAD~1` dời `main` về commit trước (và giữ lại thay đổi chưa commit nếu có, khác với `--hard`):

<Terminal where="mac">

```bash
git reset --keep HEAD~1
git log --oneline -1
git reflog -2
git branch cuu-ho 'HEAD@{1}'
git merge --ff-only cuu-ho
git log --oneline -2
```

</Terminal>

<Expected>

```text
1bf0d58 Miễn phí ship cho đơn từ 500.000 đồng
1bf0d58 HEAD@{0}: reset: moving to HEAD~1
0570ac9 HEAD@{1}: checkout: moving from d4fd8dad6a3cca7ac68d2bca7bcdd2ffe6aeb902 to main
Updating 1bf0d58..0570ac9
Fast-forward
 test_ship.py | 9 +++++++++
 1 file changed, 9 insertions(+)
 create mode 100644 test_ship.py
0570ac9 Thêm test cho miễn phí ship
1bf0d58 Miễn phí ship cho đơn từ 500.000 đồng
```

</Expected>

Sau reset, commit `0570ac9` không còn trên `main`, nhưng reflog ghi `reset: moving to HEAD~1` và dòng ngay dưới là vị trí trước đó. Tạo nhánh `cuu-ho` tại `HEAD@{1}` rồi fast-forward `main` về lại: tạo nhánh mới an toàn hơn dời nhánh cũ, vì không ghi đè gì cả.

`git reset --hard` cứu theo đúng cách này ở phần commit. Bài không chạy `reset --hard`: nó còn ghi đè mọi thay đổi chưa commit trong thư mục làm việc, và phần đó reflog không trả lại được.

<Check id="d4.1.lab-reflog">Cứu được commit sau rebase, commit bỏ quên ở detached HEAD và commit bị `git reset` lùi mất bằng `git reflog` và cú pháp `@{n}`.</Check>

### Khi gặp lỗi

<Callout kind="pitfall">

- **Hash khác với bài:** tab Terminal chưa nạp `env.sh` (chạy `. ~/masteva-d4/env.sh`), hoặc nội dung file khác một ký tự (dấu cách cuối dòng, thiếu dòng trống). Git cũ hơn 2.32 không hiểu `GIT_CONFIG_GLOBAL`, nên cấu hình toàn cục của bạn (ký commit, `signoff`, hook) vẫn có hiệu lực và làm lệch hash; kiểm bằng `git config --list --show-origin`, lệnh này chỉ nên in các dòng từ `.git/config`. Cấu hình `core.autocrlf=true` trên Windows cũng đổi nội dung blob; dùng `input` hoặc `false` cho lab.
- **`error: unknown style 'zdiff3'`:** Git cũ hơn 2.35. Dùng `git config merge.conflictStyle diff3`; dấu xung đột vẫn có phần base, chỉ kém gọn hơn.
- **`fatal: Not possible to fast-forward, aborting.`** ở `merge --ff-only`: `main` đã có commit mới mà nhánh chưa có. Rebase nhánh lên `main` trước.
- **Rebase dừng giữa chừng và bạn không nhớ đang ở đâu:** `git status` in rõ "interactive rebase in progress", lệnh đã làm và lệnh còn lại. Muốn bỏ: `git rebase --abort`.
- **zsh báo `no matches found: HEAD^{tree}`:** shell đang bật `extendedglob` và coi `^` là ký tự khớp mẫu. Bọc tham chiếu trong dấu nháy đơn như bài: `'HEAD^{tree}'`, `'HEAD@{1}'`.

</Callout>

<DeepDive>

<Reveal title="Commit là snapshot, vậy repo lớn có phình ra gấp trăm lần không?">

Không. Ở dạng "loose" như lab, mỗi phiên bản file là một blob nén riêng. Khi `git gc` chạy (tự động hoặc khi push, fetch), Git gom đối tượng vào **packfile** và lưu nhiều blob giống nhau dưới dạng delta so với một blob gốc. Nên mô hình bên ngoài là snapshot, còn bên dưới vẫn tiết kiệm như lưu diff. File nhị phân lớn đổi liên tục (ảnh, model, dump database) thì delta kém, vì vậy mới có Git LFS hoặc lưu chúng ngoài Git.

</Reveal>

<Reveal title="Đội nên chọn merge commit hay lịch sử thẳng cho main?">

Hai cách đều chấp nhận được nếu nhất quán. Lịch sử thẳng (rebase rồi fast-forward, hoặc squash merge) dễ đọc, `git bisect` đơn giản. Merge commit giữ dấu một pull request gồm những commit nào, và `git revert -m 1 <merge>` gỡ cả tính năng bằng một lệnh. Điều quan trọng hơn là mỗi commit trên `main` đều build được và có message rõ. D4.2 so sánh các kiểu merge của pull request và cái giá của từng kiểu.

</Reveal>

<Reveal title="--force-with-lease khác --force thế nào, và vì sao vẫn chưa đủ an toàn?">

`--force` ghi đè ref trên remote bất kể nó đang ở đâu. `--force-with-lease` chỉ ghi đè nếu ref trên remote vẫn trùng `origin/<nhánh>` trên máy bạn, tức chưa ai đẩy gì mới kể từ lần `fetch` cuối. Lỗ hổng: nếu bạn vừa `git fetch` (IDE hay tự làm việc này), `origin/<nhánh>` đã cập nhật theo commit của đồng nghiệp, và lease vẫn "khớp" dù bạn chưa từng xem commit đó. Git 2.30 thêm `--force-if-includes` để kiểm thêm rằng commit trên remote đã nằm trong lịch sử của bạn. Hàng rào chắc nhất vẫn là chặn force push trên nhánh chung ở phía server, như D4.2.

</Reveal>

<Reveal title="Lỡ commit một khoá API rồi push. Rebase xoá commit đó đi có đủ không?">

Không đủ. Viết lại lịch sử chỉ đổi ref; commit cũ còn trong reflog của mọi máy đã fetch, trong fork, trong cache của dịch vụ hosting và có thể trong log CI. Bước đầu tiên luôn là **thu hồi và đổi khoá** ngay, coi như khoá đã lộ. Sau đó mới dọn lịch sử nếu cần (`git filter-repo`), và thêm công cụ quét secret trước khi commit để lần sau chặn từ đầu. D5.1 cho thấy chuyện tương tự xảy ra với layer của container image.

</Reveal>

<Callout kind="ai">

AI giúp tốt khi bạn dán đầu ra của `git status`, `git log --graph` hay một conflict và hỏi "chuyện gì đang xảy ra", hoặc nhờ viết message commit từ diff. AI hay sai ở hai chỗ: khuyên `git push --force` hay `git reset --hard` như lệnh vô hại, và nhầm `--ours`/`--theirs` khi đang rebase. Trước khi chạy lệnh viết lại lịch sử do AI gợi ý, ghi lại hash hiện tại (`git rev-parse HEAD`), hỏi lại "lệnh này có đụng tới commit đã push không", và đọc dấu xung đột bằng mắt mình thay vì nhờ AI chọn một bên. Message do AI viết thường tả lại diff; hãy sửa phần thân thành "vì sao".
